# 数据治理检查清单

> [!abstract] 数据治理审计与运营实战手册
> 数据治理检查清单不是把制度条款堆成勾选项，而是围绕资产、标准、责任、质量、血缘、权限和整改建立可抽检、可签字、可复查的证据。清单的价值在于发现真实风险、明确责任人并形成闭环。

## 1. 数据治理检查清单：定义、适用边界与决策出口

数据治理检查清单不是把制度条款堆成勾选项，而是围绕资产、标准、责任、质量、血缘、权限和整改建立可抽检、可签字、可复查的证据。清单的价值在于发现真实风险、明确责任人并形成闭环。

**本篇的适用边界。** 本篇提供可用于季度检查、上线评审和专项审计的操作型清单，覆盖核心数据资产与关键链路；不替代法务、内审或安全等级测评的正式结论。

**最常见的错误替代。** 不能用“已建制度”“已开会议”“平台有功能”证明治理有效，也不能让同一团队既执行又自行认定全部检查通过。

**最终决策。** 治理委员会和数据负责人要判断：哪些资产可以发布，哪些风险必须阻断，哪些问题允许限时豁免，整改是否完成，以及下一次抽检重点是什么。 因此，这篇内容不从“应该建哪张表”开始，而从业务动作、责任人和失败后果开始。只有先确定谁在什么时点做出什么决定，字段、SQL、看板和模型才有明确用途。

围绕“数据治理检查清单”，工作中至少要区分四类问题：

1. **身份问题**：对象是谁，主键能否跨系统稳定关联，合并、拆分、撤销后历史是否还看得见。
2. **时间问题**：业务发生、状态生效、数据入仓、计算完成和人员行动分别发生在哪一刻。
3. **状态问题**：当前状态是一段事件、一张快照还是最终结果，空值代表未发生、未采集还是已删除。
4. **责任问题**：谁确认口径，谁处理异常，谁有权放行或停止，谁在观察期后复盘。

## 2. 数据治理检查清单的完整业务流程

| 环节 | 要做的事 | 最小证据 | 失败后先查什么 |
| --- | --- | --- | --- |
| 确定检查范围 | 按业务域、关键指标、监管要求和近期变更选样 | 资产清单、风险分级、抽样规则和检查授权 | 只上传截图，没有查询、版本和抽样范围 |
| 资产与责任核验 | 确认所有者、管理者、使用者和有效期 | 资产卡、责任矩阵和签字记录 | 团队自行勾选全部通过 |
| 标准与质量抽检 | 检查命名、编码、口径和质量规则执行 | 标准版本、规则结果和异常样本 | 问题状态已关闭但根因仍在 |
| 血缘与变更检查 | 确认上下游、代码版本和近期变更影响 | 字段级血缘、发布记录和影响分析 | 只检查容易获取的资产 |
| 权限与使用检查 | 验证最小权限、用途、导出和访问日志 | 角色授权、审批、日志和撤回记录 | 只上传截图，没有查询、版本和抽样范围 |
| 问题定级与整改 | 区分阻断、严重、一般和观察项并分派责任 | 问题单、期限、证据和复核人 | 团队自行勾选全部通过 |
| 复查与制度化 | 抽查整改效果并更新规则、模板和培训 | 复盘、复发率、清单版本和发布记录 | 问题状态已关闭但根因仍在 |

把 确定检查范围、资产与责任核验、标准与质量抽检、血缘与变更检查、权限与使用检查、问题定级与整改、复查与制度化 串起来后可以看出，数据治理检查清单不是一个孤立字段，而是一条会跨系统、跨岗位、跨时间的证据链。流程图上每一段都应标出输入、输出、状态、时间戳、责任人和异常出口。只要其中一段只能靠口头解释，后续的统计、追责和自动化就会失去基础。

一个合格的需求说明应该写成：

> 在【授权数据范围】和【观察窗口】内，围绕“数据治理检查清单”的【检查批次】，按【business_domain、asset_type、risk_level、owner_team】比较【关键资产覆盖率】及其【证据一次通过率】，定位一个可干预节点；行动后同时观察主指标、样本量和护栏，任何高风险异常先阻断再调查。

## 3. 数据治理检查清单的数据对象与系统契约

| 数据对象 | 建议主键 | 一行代表什么 | 不允许混淆 |
| --- | --- | --- | --- |
| 检查批次 | `audit_batch_id` | 一次具有范围、时间和授权边界的检查 | 对象身份与业务事件 |
| 受检资产 | `governed_asset_id` | 表、指标、接口、模型或报表等治理对象 | 事件、状态快照和结果粒度 |
| 检查项 | `checklist_item_id` | 一条具有证据要求和判定规则的检查 | 事件、状态快照和结果粒度 |
| 证据 | `audit_evidence_id` | 截图、查询结果、审批或抽样的可复核记录 | 事件、状态快照和结果粒度 |
| 问题 | `governance_issue_id` | 检查发现的差距、风险和整改要求 | 事件、状态快照和结果粒度 |
| 豁免 | `exception_id` | 经授权在限定范围和期限内接受的风险 | 事件、状态快照和结果粒度 |

对象表不是把所有字段塞进一张宽表。事件、状态快照和结果表应该分别保留粒度，再通过稳定主键与版本建立关联。尤其要避免三个常见混算：把一次业务事件算成多个对象、把每日快照相加当事件总量、把最新状态覆盖历史状态。

本主题的数据契约至少应包含：

- `governance_issue_id` 的唯一性规则、生成方式和跨系统映射。
- `identified_at` 的业务含义、时区、迟到和补录规则。
- `issue_status` 的完整状态集合，以及删除、撤销、冻结和失效的表示方法。
- 控制对象 `governance_audit_evidence.audit_evidence_id` 与主对象的关系。
- 每次口径、规则、模型或源版本变化的影响范围和下游通知对象。
- 敏感字段、允许用途、访问角色、导出限制和审计保留时间。

## 4. 数据治理检查清单的指标、样本与验收口径

| 指标 | 公式或定义 | 口径提醒 |
| --- | --- | --- |
| 关键资产覆盖率 | 本周期已检查的关键资产数 / 应检查关键资产数 | 抽样方法必须说明，不能用容易检查的资产替代 |
| 证据一次通过率 | 首次提交即满足证据要求的检查项数 / 已提交检查项数 | 退回原因要分类 |
| 阻断问题关闭率 | 验收通过的阻断问题数 / 已发现阻断问题数 | 仅关闭工单不算通过 |
| 整改按期率 | 在批准期限内完成证据验收的问题数 / 到期问题数 | 延期必须有新批准记录 |
| 问题复发率 | 复查再次出现的同类问题数 / 已关闭问题数 | 按根因和业务域比较 |

指标字典至少写到“任何人都能按同一份数据复跑”的程度：中文名、业务定义、公式、分子、分母、事实粒度、时间字段、对象范围、排除项、版本、负责人和验收样例，一个都不能少。比例指标必须同时展示分子、分母和样本量；金额或数量必须做守恒；状态指标必须能回到事件时间线。

对于“数据治理检查清单”，建议把观察分成三层：

| 层次 | 看什么 | 不能替代什么 |
| --- | --- | --- |
| 业务结果 | 关键资产覆盖率、证据一次通过率 | 不能替代过程证据和个案回查 |
| 过程护栏 | 阻断问题关闭率、整改按期率、问题复发率 | 不能因为护栏暂时正常就跳过异常调查 |
| 数据证据 | 主键、时间、状态、版本、来源目标对账 | 不能只看任务成功或报表能打开 |

## 5. 数据治理检查清单：七个真实工作场景

以下七组场景均为公开方法结合常见工作流程构造的“脱敏复合示例”，不对应任何单一企业、患者、客户或雇员事实。场景的目的，是展示如何从现象走到证据、行动和验收，而不是虚构经营成果。

### 1. 制度齐全但无人能说明指标口径

**现场。** 检查材料有制度、流程和签字，现场抽查核心收入指标时三个团队给出不同公式。

**怎么查。** 要求责任人现场从指标卡追到代码、源字段和样本，发现制度没有绑定具体资产版本。

**怎么处理。** 检查从文档审阅改为资产抽样；每个关键指标必须有口径卡、样例和责任人；现场复跑才算通过。

**验收结论。** 治理证据应证明结果可复现，而不是证明文件存在。

### 2. 平台血缘图与生产任务不一致

**现场。** 血缘平台显示字段只影响两张报表，实际停任务后出现大面积缺失。

**怎么查。** 比较任务解析血缘、运行时依赖和最近变更，发现动态 SQL 和外部参数未被解析。

**怎么处理。** 关键链路补充运行时血缘和人工确认；变更发布要求影响分析；血缘缺失列为阻断项。

**验收结论。** 自动血缘是证据之一，不是完整真相。

### 3. 质量规则全部通过但业务投诉增加

**现场。** 核心表完整性规则通过，用户仍反映订单和金额异常。

**怎么查。** 抽样回查发现规则只检查非空，没有检查状态、守恒、重复和跨系统一致性。

**怎么处理。** 按风险重建规则覆盖矩阵；加入业务样本和端到端对账；规则通过率与投诉、事故联合观察。

**验收结论。** 技术规则覆盖率不能替代业务可用性。

### 4. 权限复核流于形式

**现场。** 季度权限复核全部确认，但离职员工账号仍有访问。

**怎么查。** 抽样身份状态、角色、实际访问和审批时间，发现复核人批量点击确认且未查看明细。

**怎么处理。** 按高风险权限逐项确认；离职与转岗自动触发回收；抽查导出日志；批量确认需附加风险说明。

**验收结论。** 签字不是控制，控制必须能改变系统状态并留下证据。

### 5. 豁免无限延长

**现场。** 某关键数据质量问题连续多个季度以“系统改造中”豁免。

**怎么查。** 检查豁免原因、影响、替代控制和原批准期限，发现没有升级机制。

**怎么处理。** 豁免设置期限、影响范围和补偿控制；到期自动升级；重大风险需委员会重新批准。

**验收结论。** 合理例外必须有退出条件，否则豁免会变成永久忽略。

### 6. 整改只修当天数据

**现场。** 对账差异通过手工补数消除，下一周期再次出现。

**怎么查。** 比较修复脚本、源字段和历史复发记录，发现根因是上游状态映射错误。

**怎么处理。** 整改分为临时修复与根因修复；验收必须覆盖一个完整业务周期；复发纳入责任域指标。

**验收结论。** 把结果改对不等于把系统改对。

### 7. 检查范围总绕开高风险资产

**现场。** 检查覆盖率很高，但涉及资金和患者安全的核心链路很少抽到。

**怎么查。** 按资产等级、变更频率和事故历史重新分层，发现抽查偏向低风险文档表。

**怎么处理。** 采用风险权重抽样；高风险资产提高频率；未覆盖原因必须记录；检查计划由委员会批准。

**验收结论。** 覆盖率也会被样本选择操纵，检查范围本身需要审计。

七个场景可以归成一条共同判断顺序：先确认对象和时间，再确认状态和版本；然后做总量、结构和明细三层对账；最后才讨论策略、模型或工具。若一条结论不能指出对应的原始记录、责任人和行动出口，就只能算观察，不能作为生产结论。

## 6. 数据治理检查清单的第一段 SQL：重建业务链路

下面的 SQL 用于说明对象、时间、状态、版本和分层口径如何进入同一条可复查路径。表名和部分字段是通用示例，落地时应映射到企业数据字典；SQL 方言也需按实际引擎调整。

```sql
-- 数据治理检查清单：按业务对象重建链路，避免事件、快照和结果混算
WITH ranked_governance_issue_id AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY governance_issue_id
      ORDER BY updated_at DESC
    ) AS version_no
  FROM governance_audit_finding
  WHERE identified_at >= TIMESTAMP '{start_time}'
    AND identified_at <  TIMESTAMP '{end_time}'
    AND issue_status NOT IN ('deleted', 'test')
),
valid_rows AS (
  SELECT
    governance_issue_id,
    business_domain,
    asset_type,
    risk_level,
    owner_team,
    identified_at,
    issue_status,
    ingested_at
  FROM ranked_governance_issue_id
  WHERE version_no = 1
)
SELECT
  business_domain, asset_type, risk_level, owner_team,
  COUNT(DISTINCT governance_issue_id) AS object_cnt,
  COUNT(DISTINCT CASE WHEN verified_closed_at IS NOT NULL THEN governance_issue_id END) AS numerator_value,
  COUNT(DISTINCT governance_issue_id) AS denominator_value,
  CAST(COUNT(DISTINCT CASE WHEN verified_closed_at IS NOT NULL THEN governance_issue_id END) AS DOUBLE PRECISION)
    / NULLIF(COUNT(DISTINCT governance_issue_id), 0) AS metric_value,
  MIN(identified_at) AS first_event_at,
  MAX(identified_at) AS last_event_at
FROM valid_rows
GROUP BY business_domain, asset_type, risk_level, owner_team
ORDER BY metric_value DESC, object_cnt DESC;
```

执行后至少回答六个问题：

- 同一对象是否因为多源回传产生多版本，版本保留是否符合业务要求？
- 业务时间与入仓时间是否分开，补录和迟到数据是否进入正确分区？
- 分子分母是否来自同一对象范围和同一统计窗口？
- 维度使用的是事件当时值还是当前值，跨期比较是否一致？
- 删除、撤销、冻结和测试数据是否按规则处理？
- 分组结果能否在明细中抽样复现？

## 7. 数据治理检查清单的第二段 SQL：源、控制和结果三方对账

```sql
-- 数据治理检查清单：源对象、控制对象和结果对象三方对账
WITH population AS (
  SELECT
    governance_issue_id,
    identified_at,
    issue_status
  FROM governance_audit_finding
  WHERE identified_at >= TIMESTAMP '{start_time}'
    AND identified_at <  TIMESTAMP '{end_time}'
),
control AS (
  SELECT
    governance_issue_id,
    SUM(accepted_flag) AS control_value,
    COUNT(DISTINCT audit_evidence_id) AS control_cnt,
    MAX(updated_at) AS control_updated_at
  FROM governance_audit_evidence
  WHERE updated_at >= TIMESTAMP '{start_time}'
  GROUP BY governance_issue_id
),
result AS (
  SELECT
    governance_issue_id,
    COUNT(*) AS result_cnt,
    MAX(calculated_at) AS calculated_at
  FROM mart_governance_issue_id
  WHERE business_date BETWEEN DATE '{start_date}' AND DATE '{end_date}'
  GROUP BY governance_issue_id
)
SELECT
  COALESCE(p.governance_issue_id, c.governance_issue_id, r.governance_issue_id) AS object_key,
  CASE
    WHEN p.governance_issue_id IS NULL THEN 'source_missing'
    WHEN c.governance_issue_id IS NULL THEN 'control_missing'
    WHEN r.governance_issue_id IS NULL THEN 'result_missing'
    WHEN ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0 THEN 'count_or_value_gap'
    ELSE 'matched'
  END AS reconciliation_status,
  p.issue_status,
  c.control_value,
  c.control_cnt,
  r.result_cnt,
  c.control_updated_at,
  r.calculated_at
FROM population p
FULL OUTER JOIN control c ON p.governance_issue_id = c.governance_issue_id
FULL OUTER JOIN result r ON COALESCE(p.governance_issue_id, c.governance_issue_id) = r.governance_issue_id
WHERE p.governance_issue_id IS NULL
   OR c.governance_issue_id IS NULL
   OR r.governance_issue_id IS NULL
   OR ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0;
```

这段查询故意不使用“总数相差小于某个随意百分比就算通过”。它先找出缺失对象和状态差异，再检查控制值与结果值。对于数据治理检查清单，数量、金额、时长或状态任意一项无法解释，都不能用“业务波动”代替排查。

对账结果建议分成四类处理：

1. **阻断**：对象缺失、关键时间为空、状态非法、金额或数量不守恒、权限越界。
2. **严重**：比例或总量显著偏离基线，且无法由已确认的对象结构变化解释。
3. **观察**：小范围波动但来源、样本和趋势可控，进入责任人和观察窗口。
4. **探索**：只有弱信号或假设，不进入正式结论，更不直接触发业务处罚。

## 8. 数据治理检查清单的 Python 发布门禁与指标护栏

第一段代码把发布条件写成可执行对象，避免“检查过了”只存在聊天记录里：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class GovernanceIssueIdBatch:
    batch_id: str
    source_rows: int
    valid_rows: int
    duplicate_keys: int
    missing_required_fields: int
    reconciliation_gap: float

def release_governance_issue_id(batch: GovernanceIssueIdBatch) -> dict:
    checks = {
        "source_not_empty": batch.source_rows > 0,
        "valid_rows_in_range": 0 <= batch.valid_rows <= batch.source_rows,
        "duplicate_rate_ok": batch.duplicate_keys / max(batch.source_rows, 1) <= 0.001,
        "required_fields_ok": batch.missing_required_fields == 0,
        "reconciliation_ok": abs(batch.reconciliation_gap) <= 0.01,
    }
    return {
        "topic": "数据治理检查清单",
        "batch_id": batch.batch_id,
        "checks": checks,
        "release_allowed": all(checks.values()),
        "blocking_checks": [name for name, passed in checks.items() if not passed],
    }
```

第二段代码演示如何为比例类结果附带样本证据和小样本下界。它不是替代统计学家的模型，而是防止把少量偶然样本直接包装成稳定结论：

```python
from dataclasses import dataclass
from math import sqrt

@dataclass(frozen=True)
class GovernanceIssueIdObservation:
    object_id: str
    numerator: float
    denominator: float
    sample_size: int
    scope_version: str

def calculate_governance_issue_id(rows: list[GovernanceIssueIdObservation]) -> list[dict]:
    output = []
    for row in rows:
        value = row.numerator / row.denominator if row.denominator > 0 else None
        # 小样本用 Wilson 下界做护栏，不把偶然的高比例直接当稳定结果。
        z = 1.96
        p = value or 0
        n = max(row.sample_size, 1)
        center = p + z * z / (2 * n)
        margin = z * sqrt((p * (1 - p) + z * z / (4 * n)) / n)
        lower = max(0, (center - margin) / (1 + z * z / n))
        output.append({
            "object_id": row.object_id,
            "metric": "关键资产覆盖率",
            "value": value,
            "lower_bound": lower if value is not None else None,
            "sample_size": row.sample_size,
            "scope_version": row.scope_version,
            "caution": "抽样方法必须说明，不能用容易检查的资产替代",
        })
    return output
```

真正上线时还要补充参数配置、日志、血缘、告警级别、重跑幂等、异常样本保存和审批记录。代码通过不代表业务通过；自动检查只能证明已经定义的规则没有被违反，无法证明规则本身一定正确。

## 9. 数据治理检查清单的失败反例与上线验收

| 风险信号 | 错误做法 | 必须补齐的证据 | 发布或行动规则 |
| --- | --- | --- | --- |
| 证据标准含糊 | 只上传截图，没有查询、版本和抽样范围 | 证据模板和复核人 | 关键项要求可复跑证据 |
| 执行与检查同体 | 团队自行勾选全部通过 | 独立抽查和权限分离 | 高风险项引入第二人复核 |
| 只关闭工单 | 问题状态已关闭但根因仍在 | 整改证据和完整周期复查 | 关闭前执行复发测试 |
| 样本选择偏差 | 只检查容易获取的资产 | 风险分层和抽样覆盖率 | 委员会审阅未覆盖原因 |

上线验收不应只有一句“报表正常”。建议按下面四层验收：

| 验收对象 | 结构要求 | 测试样本 | 结果证据 |
| --- | --- | --- | --- |
| 检查批次 | `audit_batch_id` 能唯一定位一次具有范围、时间和授权边界的检查 | 正常、重复、缺失、撤销与跨期样本 | 关键资产覆盖率可回到原始对象 |
| 受检资产 | `governed_asset_id` 能唯一定位表、指标、接口、模型或报表等治理对象 | 正常、重复、缺失、撤销与跨期样本 | 证据一次通过率可回到原始对象 |
| 检查项 | `checklist_item_id` 能唯一定位一条具有证据要求和判定规则的检查 | 正常、重复、缺失、撤销与跨期样本 | 阻断问题关闭率可回到原始对象 |
| 证据 | `audit_evidence_id` 能唯一定位截图、查询结果、审批或抽样的可复核记录 | 正常、重复、缺失、撤销与跨期样本 | 整改按期率可回到原始对象 |
| 问题 | `governance_issue_id` 能唯一定位检查发现的差距、风险和整改要求 | 正常、重复、缺失、撤销与跨期样本 | 问题复发率可回到原始对象 |
| 豁免 | `exception_id` 能唯一定位经授权在限定范围和期限内接受的风险 | 正常、重复、缺失、撤销与跨期样本 | 关键资产覆盖率可回到原始对象 |

还应为每一次发布保留一组固定回归样本：正常对象、边界状态、重复记录、缺失字段、撤销或退款、跨期、权限拒绝和失败恢复。回归样本不是演示数据，而是以后每次改规则都能重复执行的质量资产。

## 10. 数据治理检查清单的 30 天落地与复盘

| 阶段 | 主要交付 | 通过条件 |
| --- | --- | --- |
| 第 1 周：定义 | 对象、流程、状态、指标、排除项和责任矩阵 | 业务、数据、安全或质量负责人对同一口径签字 |
| 第 2 周：打通 | 源字段、主键、时间、版本、控制对象和失败样本 | 正常与异常样本都能回到原始记录 |
| 第 3 周：验证 | 总量对账、分层对账、抽样回查、权限测试、回滚演练 | 阻断问题清零，严重问题有责任人与期限 |
| 第 4 周：发布 | 灰度、SLO、监控、行动清单、停止条件和复盘模板 | 使用者在真实场景中完成一次闭环行动 |

如果必须用 90 秒说明“数据治理检查清单”是否做对，可以按这个顺序自测：

1. 一行数据代表什么，主键是什么，哪些对象绝不能混在同一粒度？
2. 业务发生、数据可见、计算完成和行动确认分别在哪个时间点？
3. 本主题最重要的两个主指标、三个护栏和最小样本量是什么？
4. 一个异常出现时，先从原始记录、链路版本还是业务动作开始查？
5. 哪类错误必须阻断发布或停止使用，谁有权批准例外？
6. 上线后由谁在多长时间内观察，什么条件下回滚或结束？

> [!check] 完成标准
> 当另一位数据同事不看聊天记录，只根据口径卡、回归样本和代码就能复跑同一结果；当业务负责人能指出一个异常对应的原始对象、处置动作和复核证据；当系统能够阻止未授权或状态非法的数据进入下游，这篇“数据治理检查清单”才算真正落到工作里。
