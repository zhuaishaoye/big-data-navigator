# 数据治理风险管理

> [!abstract] 场景速览
> “数据治理风险管理”在会议里常常只有一句话，落到数据团队却会展开成口径、主键、时间、状态、权限和交付责任。下面用一个从问题到上线的顺序展开，并穿插三个脱敏的复合案例，帮助你把标题里的知识迁移到真实项目。

## 1. “数据治理风险管理”在数据治理与数据管理业务链中的位置

数据治理与数据管理的核心流程可以概括为：资产盘点 → 标准定义 → 责任认领 → 规则设计 → 执行监控 → 问题闭环 → 成熟度评估。参与角色包括数据治理办公室、业务数据负责人、数据开发、数据分析、安全合规、平台团队、审计。“数据治理风险管理”通常不是一个孤立字段，而是连接业务动作、数据记录和管理决策的一层能力。

从数据团队视角，至少要回答四个问题：

1. **谁使用**：数据治理办公室、业务数据负责人、数据开发、数据分析分别要用它做判断、执行还是审计。
2. **对象是什么**：一行数据代表数据资产、一次事件、一个批次还是一天快照。
3. **流程在哪里变化**：通过标准定义、责任认领、规则设计、执行监控之间的状态和时间差定位问题。
4. **结果如何被采用**：谁在什么时间前采取行动，使用哪个指标观察改善或副作用。

一个合格的专题目标可以写成：

> 在【时间窗】和【授权数据范围】内，围绕“数据治理风险管理”，按【业务域、资产层级、规则类型】比较【平均修复时长】与【规则通过率】，定位一个可干预流程节点，并记录行动后的变化与边界。

## 2. 一张图看清角色、流程和数据

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 数据资产 | `asset_id` | 资产盘点 |
| 过程对象 | 字段 | `column_id` | 标准定义 |
| 过程对象 | 指标 | `metric_id` | 责任认领 |
| 结果对象 | 质量规则 | `rule_id` | 规则设计 |
| 结果对象 | 问题工单 | `issue_id` | 执行监控 |
| 专题分析 | 数据治理风险管理 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

建模时不要先把所有系统字段堆进一张大表。更稳妥的做法是分别保留三类事实：

- **事件事实**：谁在什么时间做了动作，例如挂号、下单、开工、报警或学习。
- **状态快照**：对象在某一天的状态，例如会员等级、租约、账户余额或设备资产关系。
- **结果事实**：流程完成后的产出，例如结算金额、良品数量、签收结果或考试分数。

三者的粒度不同。把事件、快照和结果强行放在同一行，会让金额、数量和转化率在汇总时重复。若“数据治理风险管理”涉及状态变化，优先建立状态机；若涉及金额，先做借贷或收付平衡；若涉及对象归属，保留维度有效期。

## 3. 指标与口径：不要把相关数字直接当答案

| 专题观测面 | 需要回答的问题 | 关键证据 | 判定与动作 |
| --- | --- | --- | --- |
| 采用与收益（本标题优先） | 谁在使用，是否改变决策，副作用如何 | 使用日志、主指标、护栏和复盘 | 上线数量不等于项目成功 |
| 上线 | 权限、质量、监控、培训和回滚是否就绪 | 上线清单、演练、验收和责任人 | 关键风险未关闭不发布 |
| 问题与范围 | 项目改变什么行为，边界和不做什么是什么 | 决策记录、需求说明和现状基线 | 范围不清时先做诊断 |
| 方案与证据 | 为什么选择当前方案，关键假设如何验证 | 替代方案、原型、数据和评审记录 | 重大假设必须有试验 |

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 规则通过率 | `COUNT(DISTINCT passed_rule_id) / COUNT(DISTINCT executed_rule_id)`（视图字段 `rule_pass_rate`） | 业务域、资产层级、规则类型 | 不混用测试、撤销和跨期状态；与“数据治理风险管理”相关时还要补充主题筛选 |
| 问题闭环率 | `COUNT(DISTINCT closed_issue_id) / COUNT(DISTINCT raised_issue_id)`（视图字段 `issue_closure_rate`） | 资产层级、规则类型、责任团队 | 不混用测试、撤销和跨期状态；与“数据治理风险管理”相关时还要补充主题筛选 |
| 资产完整率 | `COUNT(DISTINCT complete_asset_id) / COUNT(DISTINCT asset_id)`（视图字段 `asset_completeness`） | 规则类型、责任团队、严重等级 | 不混用测试、撤销和跨期状态；与“数据治理风险管理”相关时还要补充主题筛选 |
| 血缘覆盖率 | `COUNT(DISTINCT lineage_asset_id) / COUNT(DISTINCT critical_asset_id)`（视图字段 `lineage_coverage`） | 责任团队、严重等级 | 不混用测试、撤销和跨期状态；与“数据治理风险管理”相关时还要补充主题筛选 |

指标字典至少应包含：中文名、英文编码、业务定义、计算公式、事实粒度、时间字段、对象范围、排除条件、负责人和验收样例。对于“数据治理风险管理”，还应注明它使用的是业务发生时间还是入仓时间，是否包含撤销、退费、测试、跨期和补录记录。

一个常见误区是看到平均修复时长变化就立即解释业务原因。更可靠的顺序是：

1. 检查数据覆盖和延迟是否变化。
2. 检查对象范围、状态映射和维度归属是否变化。
3. 按时间、结构和分组拆解贡献。
4. 回到明细寻找能解释变化的事件。
5. 如果已经采取行动，再评估行动带来的增量，而不是事后挑一个相关指标。

## 4. 工作案例：从现象到数据处理

### 案例 1：华南某银行数据中台项目的“数据治理风险管理”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“数据治理风险管理”映射到“数据项目交付、验收与运营”中的采用与收益，而不是泛泛讨论概念。
- **触发事件**：平台组件全部交付，但跨部门数据接入进度严重滞后。
- **业务与数据范围**：资产范围、责任矩阵、接口、权限、迁移批次和依赖。数据侧重点采集使用日志、主指标、护栏和复盘，并与数据目录、元数据平台、质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：谁在使用，是否改变决策，副作用如何。
- **关键障碍**：技术任务完成被当作项目进度，业务口径、数据授权和源系统改造没有纳入计划。同时要防止资产没有负责人把表面指标带偏。
- **处理过程**：建立跨域里程碑和升级路径，把数据契约、权限与源系统验收作为接入完成标准。实施时把“项目复盘同时衡量采用、收益、副作用和可复制性”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例项目管理按可用资产、业务验收和依赖关闭而不是代码提交衡量。验收至少同时看主指标、使用日志、主指标、护栏和复盘和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“从问题、范围、基线、方案、数据、上线、采用和复盘管理项目，确保交付的是可验证的业务能力而不是一次性材料。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

这个案例最关键的动作不是“跑一条 SQL”，而是把“数据治理风险管理”对应的业务对象和上下游系统放在同一张链路图上。链路图至少要标出源系统、事件时间、关联主键、状态变化、数据负责人和消费方。

## 5. SQL 示例：在统一口径下做分层诊断

下面的查询用于展示分析结构，表名和字段需映射到实际环境。重点是去重、范围筛选、基线比较和贡献率，而不是代码本身。

### 标题专属诊断 SQL

```sql
-- 数据治理风险管理：留存同期群诊断（严重等级 × 资产层级）
WITH scoped AS (
  SELECT
    asset_id AS entity_key,
    event_id,
    check_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_data_quality_result
  WHERE check_time >= DATE '2026-08-01'
    AND check_time <  DATE '2026-11-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '问题闭环率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

执行后要回答四类验证题：

- 结果总量能否与源系统或既有报表在相同口径下解释差异？
- 排名前几位的分组是否由少数超长、重复或补录记录造成？
- 缺失日期表现为“未发生”还是“未采集”，是否改变分母？
- 维度使用的是当时归属还是当前归属，跨期比较是否一致？

## 6. 第二个案例：跨系统、跨部门时怎样不失控

### 案例 2：华北某制造数据治理项目的“数据治理风险管理”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“数据治理风险管理”映射到“数据项目交付、验收与运营”中的上线，而不是泛泛讨论概念。
- **触发事件**：试点质量问题改善明显，但推广到更多工厂后效果迅速衰减。
- **业务与数据范围**：试点机制、责任人、规则、工单、培训和复制成本。数据侧重点采集上线清单、演练、验收和责任人，并与数据目录、元数据平台、质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：权限、质量、监控、培训和回滚是否就绪。
- **关键障碍**：项目依赖少数专家手工推动，没有形成角色、模板和自动化。同时要防止规则只告警不闭环把表面指标带偏。
- **处理过程**：把试点拆成可复制资产，建立本地负责人、规则模板、培训认证和月度复核。实施时把“项目目标包含业务行为、主指标、护栏指标和观察周期”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例推广以复制周期、规则复用、问题复发和本地自治能力评估。验收至少同时看主指标、上线清单、演练、验收和责任人和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“从问题、范围、基线、方案、数据、上线、采用和复盘管理项目，确保交付的是可验证的业务能力而不是一次性材料。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

跨部门项目最容易在三个地方返工：业务术语没有冻结、主数据映射没有版本、验收时才发现权限不足。建议在开发前让业务负责人签字确认指标定义，让数据负责人确认粒度与主键，让安全负责人确认字段范围，让运维负责人确认发布与回滚窗口。

## 7. Python 示例：把数据质量变成发布门禁

### 可执行质量门禁

```python
# 数据治理风险管理：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "数据治理风险管理"
TOPIC_KEY = "subject"
RULE_ID = "rule_governance_1qik4ev"
GUIDE_CHECKS = [
    "项目目标包含业务行为、主指标、护栏指标和观察周期",
    "范围明确数据、系统、团队、权限和不在本期处理的事项",
    "上线前完成质量、权限、监控、培训和回滚验收",
    "项目复盘同时衡量采用、收益、副作用和可复制性"
]
RULES = {
    "required_columns": ["event_id", "asset_id", "check_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "asset_id",
    "time_field": "check_time",
    "max_duplicate_rate": 0.0006,
    "max_null_rate": 0.006,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：项目目标包含业务行为、主指标、护栏指标和观察周期；范围明确数据、系统、团队、权限和不在本期处理的事项；上线前完成质量、权限、监控、培训和回滚验收；项目复盘同时衡量采用、收益、副作用和可复制性
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

这段代码适合放在离线任务完成之后、指标发布之前。真实环境还应从调度平台读取分区参数、把结果写入质量平台，并在关键规则失败时阻断下游。告警不是终点，工单中要记录影响资产、发现时间、临时处理、根因、修复时间和防复发动作。

## 8. 异常排查：从指标异常回到业务事件

| 专题检查项 | 失败时会看到什么 | 首选证据 | 处理动作 |
| --- | --- | --- | --- |
| 项目目标包含业务行为、主指标、护栏指标和观察周期 | 谁在使用，是否改变决策，副作用如何 | 使用日志、主指标、护栏和复盘 | 上线数量不等于项目成功 |
| 范围明确数据、系统、团队、权限和不在本期处理的事项 | 权限、质量、监控、培训和回滚是否就绪 | 上线清单、演练、验收和责任人 | 关键风险未关闭不发布 |
| 上线前完成质量、权限、监控、培训和回滚验收 | 项目改变什么行为，边界和不做什么是什么 | 决策记录、需求说明和现状基线 | 范围不清时先做诊断 |
| 项目复盘同时衡量采用、收益、副作用和可复制性 | 为什么选择当前方案，关键假设如何验证 | 替代方案、原型、数据和评审记录 | 重大假设必须有试验 |

围绕“数据治理风险管理”排查时，可以按以下顺序进行：

1. **影响面**：哪些指标、报表、接口或业务团队受影响，是否需要暂停对外发布。
2. **时间线**：源系统变更、任务发布、数据回刷、组织调整和业务活动分别发生在什么时候。
3. **数据链路**：上游是否延迟，分区是否缺失，主键是否重复，状态是否映射错误。
4. **业务证据**：抽取异常记录，与原始单据、操作日志、客服记录或现场系统核对。
5. **修复与复核**：明确补数范围、重跑粒度、回滚版本和验收样例。
6. **防复发**：把一次性排查升级为规则、监控、责任人和变更评审。

特别要注意：资产没有负责人；规则只告警不闭环；口径变更缺少影响分析；权限长期累积。这些问题如果不被单独标记，很容易被误写成业务趋势。

## 9. 第三个案例与延伸场景

### 案例 3：华东某零售数据项目组的“数据治理风险管理”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“数据治理风险管理”映射到“数据项目交付、验收与运营”中的问题与范围，而不是泛泛讨论概念。
- **触发事件**：项目按期上线看板，但业务仍用 Excel 决策，数据团队无法证明价值。
- **业务与数据范围**：需求访谈、用户任务、使用日志、指标口径、决策记录和反馈。数据侧重点采集决策记录、需求说明和现状基线，并与数据目录、元数据平台、质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：项目改变什么行为，边界和不做什么是什么。
- **关键障碍**：项目只定义功能范围，没有定义采用动作和决策改变。同时要防止口径变更缺少影响分析把表面指标带偏。

另外两个适合继续拆分的工作场景是：

- **某全国连锁服务企业**：管理层发现营业额增长但利润下降，跨部门对原因判断不一致。可以先从门店、订单、客户、活动、成本、人员和工单数据建立最小数据闭环，再围绕“数据治理风险管理”检查收入与成本时间归属不同，活动优惠分摊不完整，组织调整导致门店历史归属变化。

团队准备把“数据治理风险管理”从个人分析脚本升级为多人共用的数据能力。第一次评审就暴露出：方案上线后主指标出现变化，但同期还有活动、季节性和渠道结构调整，无法证明变化来自本次动作。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 把观察结果与可执行动作分开，判断方案是否带来可解释增量，并明确停止或扩大的条件。在本场景里，核心风险还包括数据目录与真实血缘脱节，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。

- **处理步骤：** 第一步先冻结“数据治理风险管理”的当前定义并记录版本；第二步用指标明细核对调度平台到工单系统的关联；第三步按资产层级与责任团队做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察问题闭环率和护栏指标血缘覆盖率。
- **行动与护栏：** 先按使用场景和截止时间分级，再比较预聚合、增量计算、缓存、并发调整和生命周期策略。专题检查项“上线前完成质量、权限、监控、培训和回滚验收”被写成发布门禁，任何优化都必须同时通过结果对账、延迟目标与成本预算，不能只展示一次最快执行。
- **失败路径：** 为了压缩账单关闭质量检查，或为了刷新频率重复计算无人消费的全量结果。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“数据治理风险管理”时，先验证决策记录、需求说明和现状基线，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由安全合规在明确时限内，根据问题闭环率、血缘覆盖率和规则可执行且可解释决定继续、回退、补查还是转人工。 若规则只告警不闭环或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。
### 案例 7：数据治理风险管理的最小权限与越权核查

一个看似普通的“数据治理风险管理”需求，在跨系统核验后变成了围绕“权限、隐私与审计”的专项排查。触发排查的不是一次严重事故，而是连续几次解释不清的数据差异。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 让数据用途、最小字段、访问角色、加工产物、保存期限和撤回机制都可追溯。在本场景里，核心风险还包括口径变更缺少影响分析，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：质量规则、问题工单及其在问题闭环前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注rule_id与issue_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 分析结果本身可以访问，但派生字段、导出文件和临时表扩大了敏感数据范围，现有流程没有及时识别。初看时，工单系统与审计平台的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 分类分级、授权记录、字段血缘、访问日志、导出清单、脱敏规则和过期清理记录。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“平台团队”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“数据治理风险管理”的当前定义并记录版本；第二步用质量规则明细核对工单系统到审计平台的关联；第三步按规则类型与严重等级做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察资产完整率和护栏指标平均修复时长。
- **行动与护栏：** 按任务拆分数据集与角色，使用最小字段和临时授权，发布前检查派生表与导出是否出现敏感扩散。专题检查项“项目复盘同时衡量采用、收益、副作用和可复制性”被写成发布门禁，高风险字段缺少授权、脱敏或审计时不进入分析环境，紧急访问必须到期自动回收。
- **失败路径：** 把“内网可访问”当成“业务已授权”，或者用永久大权限账号支撑临时分析。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“数据治理风险管理”时，先验证替代方案、原型、数据和评审记录，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由平台团队在明确时限内，根据资产完整率、平均修复时长和问题分级明确决定继续、回退、补查还是转人工。 若口径变更缺少影响分析或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从数据治理风险管理回到可核对明细

```sql
-- 数据治理风险管理：状态链与时间间隔核查
WITH ordered_events AS (
  SELECT
    asset_id AS entity_key,
    event_id,
    stage_code,
    check_time AS event_time,
    LAG(stage_code) OVER (
      PARTITION BY asset_id
      ORDER BY check_time, event_id
    ) AS previous_stage,
    LAG(check_time) OVER (
      PARTITION BY asset_id
      ORDER BY check_time, event_id
    ) AS previous_time
  FROM fact_data_quality_result
  WHERE check_time >= :start_date
    AND check_time <  :end_date
    AND subject_key = 'subject'
)
SELECT
  entity_key,
  previous_stage,
  stage_code,
  event_time,
  event_time - previous_time AS elapsed,
  CASE
    WHEN event_time < previous_time THEN 'time_reversed'
    WHEN previous_stage = stage_code THEN 'duplicate_stage'
    WHEN previous_stage IS NULL THEN 'missing_prefix'
    ELSE 'candidate_delay'
  END AS exception_type
FROM ordered_events
WHERE event_time < previous_time
   OR previous_stage = stage_code
   OR event_time - previous_time > INTERVAL '1 hour'
ORDER BY exception_type, elapsed DESC;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把数据治理风险管理的验收证据写成门禁

```python
import json
from pathlib import Path


def build_evidence_manifest(
    subject: str,
    scope: dict,
    checks: dict,
    samples: list[dict],
    owner: str,
) -> dict:
    failed = [name for name, passed in checks.items() if not passed]
    return {
        "subject": subject,
        "scope": scope,
        "checks": checks,
        "failed_checks": failed,
        "sample_evidence": samples[:5],
        "owner": owner,
        "decision": "block" if failed else "review",
        "manual_questions": [
            "每一项失败是否已回到原始记录",
            "对象、时间和状态是否与指标字典一致",
            "回滚或修复后是否重新完成对账",
        ],
    }


manifest = build_evidence_manifest(
    subject="数据治理风险管理",
    scope={"systems": ["数据目录","元数据平台","质量平台","权限系统"]},
    checks={"definition_frozen": False, "reconciled": False},
    samples=[],
    owner="数据治理办公室",
)
Path("release-evidence.json").write_text(
    json.dumps(manifest, ensure_ascii=False, indent=2),
    encoding="utf-8",
)
print(manifest["decision"])
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
