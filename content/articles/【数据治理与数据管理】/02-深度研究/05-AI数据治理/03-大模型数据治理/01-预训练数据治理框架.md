# 预训练数据治理框架

> [!warning] 核心判断
> 一个关于“预训练数据治理框架”的结论能不能被信任，取决于它是否能回到原始事件、明确时间和对象，并说明排除了哪些记录。下面不会用单一模板概括所有场景，而是结合数据治理与数据管理中的多类任务，展示数据建模、代码分析和项目验收之间如何衔接。

## 1. 先判断应治理什么风险

“预训练数据治理框架”通常不是买一个平台就能解决的问题。它至少涉及制度、标准、责任、流程、技术和审计六层。开始前先把风险写成可观察事实：

| 风险问题 | 观察信号 | 可能影响 | 首先核查 |
| --- | --- | --- | --- |
| 定义不一致 | 同名指标多个 SQL、多个业务解释 | 决策冲突、返工 | 指标字典与负责人 |
| 数据不完整 | 分区缺失、关键字段空值 | 报表失真、流程中断 | 采集与任务日志 |
| 责任不清 | 问题工单长期无人认领 | 修复延迟、同类复发 | 资产责任矩阵 |
| 访问过宽 | 长期权限、共享账号、无审计 | 泄漏与合规风险 | 权限清单与访问日志 |
| 变更不可见 | 表结构或逻辑变更无通知 | 下游批量故障 | 血缘与发布记录 |

1. **资产没有负责人**：需要在标准、系统或组织流程中设置对应控制。
2. **规则只告警不闭环**：需要在标准、系统或组织流程中设置对应控制。
3. **口径变更缺少影响分析**：需要在标准、系统或组织流程中设置对应控制。
4. **权限长期累积**：需要在标准、系统或组织流程中设置对应控制。
5. **数据目录与真实血缘脱节**：需要在标准、系统或组织流程中设置对应控制。

## 2. 用 DAMA 思路拆成可执行组件

| 组件 | 本文关注对象 | 最小可执行机制 |
| --- | --- | --- |
| 数据标准 | 字段、代码、指标和业务术语；结合“预训练数据治理框架”重点检查资产责任唯一 | 标准登记、评审、版本与废弃 |
| 元数据 | 表、字段、任务、接口、负责人；结合“预训练数据治理框架”重点检查规则可执行且可解释 | 自动采集、业务补充、变更通知 |
| 数据质量 | 完整性、唯一性、及时性、准确性；结合“预训练数据治理框架”重点检查问题分级明确 | 规则、阈值、工单与复盘 |
| 主数据 | 客户、商品、设备、机构等共享对象；结合“预训练数据治理框架”重点检查变更留痕完整 | 源权威、去重、合并、历史关系 |
| 数据安全 | 分类分级、权限、脱敏和审计；结合“预训练数据治理框架”重点检查敏感字段访问可审计 | 审批、最小权限、访问复核 |
| 数据血缘 | 表、字段、任务和指标关系；结合“预训练数据治理框架”重点检查资产责任唯一 | 影响分析、问题追踪、变更评审 |

治理不是把所有数据都按同一优先级管理。建议依据使用范围、监管要求、决策影响和故障历史划分关键资产，再决定投入。关键资产应有唯一负责人、明确消费者、质量目标、访问策略和变更通知。

## 3. 资产、标准与责任矩阵

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 数据资产 | `asset_id` | 资产盘点 |
| 过程对象 | 字段 | `column_id` | 标准定义 |
| 过程对象 | 指标 | `metric_id` | 责任认领 |
| 结果对象 | 质量规则 | `rule_id` | 规则设计 |
| 结果对象 | 问题工单 | `issue_id` | 执行监控 |
| 专题分析 | 预训练数据治理框架 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

一个可执行的数据标准至少包括：

- **业务定义**：业务人员如何理解和适用。
- **技术定义**：字段类型、长度、格式、枚举和空值语义。
- **计算口径**：时间、粒度、分子分母和排除项。
- **权威来源**：哪个系统是事实源，冲突时以谁为准。
- **生命周期**：创建、变更、废弃和归档规则。
- **责任人**：业务负责人、数据负责人、技术负责人和审批人。

资产责任可以使用 RACI：业务负责人对定义负责，数据负责人对实现与质量负责，平台团队对工具和权限负责，安全合规对访问与审计负责，消费者对使用边界负责。只有“责任人”一个字段，没有决策权和时限，问题仍会回到治理团队自己处理。

## 4. 案例一：华东某医疗 AI 团队

### 案例 1：华东某医疗 AI 团队的“预训练数据治理框架”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“预训练数据治理框架”映射到“AI 数据治理、合规与可解释性”中的来源，而不是泛泛讨论概念。
- **触发事件**：模型在总体测试集表现良好，但老年与罕见病人群错误率明显更高。
- **业务与数据范围**：影像、病历、年龄、疾病亚型、标注来源、训练版本和分群评估结果。数据侧重点采集数据卡、授权依据、采集时间和用途，并与数据目录、元数据平台、质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：数据从哪里来、是否授权、能否用于训练或评测。
- **关键障碍**：评测集人群结构失衡，数据卡没有记录排除标准。同时要防止资产没有负责人把表面指标带偏。
- **处理过程**：补充分群样本和专家复核，建立数据卡与模型卡，发布前检查弱势群体指标和错误类型。实施时把“建立隐私、越权、错误信息、滥用和人工复核控制”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例治理将总体准确率改为分群效果、风险差异和人工复核共同验收。验收至少同时看主指标、数据卡、授权依据、采集时间和用途和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“为 AI 数据建立来源、授权、质量、版本、偏差、隐私、血缘和使用反馈的控制链，让模型效果与风险都能解释和追溯。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

治理项目应先做小范围闭环，不要一开始铺满全公司。选择一个高影响业务域，完成从资产盘点、标准确认、质量规则、问题整改到复盘的完整链路，再复制机制。

## 5. 规则与代码：让控制可执行

### 发布前规则门禁

```python
# 预训练数据治理框架：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "预训练数据治理框架"
TOPIC_KEY = "subject"
RULE_ID = "rule_governance_b1syl3"
GUIDE_CHECKS = [
    "训练、评测和生产数据记录来源、授权、用途、版本和负责人",
    "按人群、场景和风险等级评估质量与偏差，不只报告总体平均",
    "数据、Prompt、特征、索引、模型和评测版本可以互相对应和回放",
    "建立隐私、越权、错误信息、滥用和人工复核控制"
]
RULES = {
    "required_columns": ["event_id", "asset_id", "check_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "asset_id",
    "time_field": "check_time",
    "max_duplicate_rate": 0.0004,
    "max_null_rate": 0.005,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：训练、评测和生产数据记录来源、授权、用途、版本和负责人；按人群、场景和风险等级评估质量与偏差，不只报告总体平均；数据、Prompt、特征、索引、模型和评测版本可以互相对应和回放；建立隐私、越权、错误信息、滥用和人工复核控制
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

### 治理对象与风险分层 SQL

```sql
-- 预训练数据治理框架：留存同期群诊断（责任团队 × 业务域）
WITH scoped AS (
  SELECT
    asset_id AS entity_key,
    event_id,
    check_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_data_quality_result
  WHERE check_time >= DATE '2026-08-01'
    AND check_time <  DATE '2026-11-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '规则通过率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

规则设计要同时考虑三件事：能否自动执行、误报成本是否可接受、失败后谁来处理。只写“不能为空”不够，必须明确哪类对象允许为空、谁能在何种情况下豁免、豁免多久、是否需要审批和复核。

建议把规则分成四级：

1. **阻断**：涉及监管、资金、身份或核心发布，失败即停止。
2. **严重告警**：影响大但可先隔离，要求在约定时间内响应。
3. **观察告警**：可能是正常业务变化，先记录趋势。
4. **探索检查**：尚未形成稳定阈值，仅用于发现异常模式。

## 6. 案例二：华南某客服 AI 团队

### 案例 2：华南某客服 AI 团队的“预训练数据治理框架”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“预训练数据治理框架”映射到“AI 数据治理、合规与可解释性”中的版本，而不是泛泛讨论概念。
- **触发事件**：模型升级后回答质量波动，无法确认是数据、Prompt 还是检索变化。
- **业务与数据范围**：训练与评测数据、Prompt、检索索引、模型、请求日志和反馈。数据侧重点采集版本标识、变更记录、回放和血缘，并与数据目录、元数据平台、质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：数据、Prompt、特征、模型和评测能否互相对应。
- **关键障碍**：各组件独立发布，没有统一版本和回放能力。同时要防止规则只告警不闭环把表面指标带偏。
- **处理过程**：为每次请求记录数据、索引、Prompt、模型和代码版本，建立可重放评测与一键回滚。实施时把“训练、评测和生产数据记录来源、授权、用途、版本和负责人”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：复合案例缩短问题定位时间，并支持影响范围分析。验收至少同时看主指标、版本标识、变更记录、回放和血缘和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“为 AI 数据建立来源、授权、质量、版本、偏差、隐私、血缘和使用反馈的控制链，让模型效果与风险都能解释和追溯。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

治理指标不要只统计“生成了多少文档、接入了多少资产”。更值得观察的是规则覆盖的关键资产、问题发现前移比例、问题复发率、变更影响分析耗时和业务是否愿意使用。

## 7. 权限、安全与审计

围绕“预训练数据治理框架”，权限治理至少应回答：

- 谁能申请、谁审批、审批依据是什么？
- 权限是否按角色、数据级别和用途最小化？
- 临时权限何时收回，离职和转岗是否自动处理？
- 查询、下载和导出是否留痕，异常访问如何发现？
- 脱敏、加密、水印和审计日志是否与数据类型匹配？

敏感字段不应通过“复制一份测试数据”绕过问题。更合适的做法是分级脱敏、合成数据或受控计算环境。所有示例和代码都不应包含真实身份、账号、密钥、客户名单或未公开经营数据。

## 8. 第三个案例：华北某政务问答团队

### 案例 3：华北某政务问答团队的“预训练数据治理框架”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“预训练数据治理框架”映射到“AI 数据治理、合规与可解释性”中的风险，而不是泛泛讨论概念。
- **触发事件**：生成式问答引用了过期政策，并可能包含个人信息。
- **业务与数据范围**：政策版本、权限、问题、检索片段、输出、敏感检测和人工反馈。数据侧重点采集红队、审计、人工复核和事故记录，并与数据目录、元数据平台、质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：隐私、偏见、越权、错误信息和滥用如何控制。
- **关键障碍**：知识更新没有失效机制，日志中保存了原始敏感文本。同时要防止口径变更缺少影响分析把表面指标带偏。
- **处理过程**：建立政策有效期与来源校验，日志脱敏，输出前做敏感和引用检查，高风险问题转人工。实施时把“按人群、场景和风险等级评估质量与偏差，不只报告总体平均”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例项目以引用正确率、过期命中率、敏感输出率和转人工率评估。验收至少同时看主指标、红队、审计、人工复核和事故记录和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“为 AI 数据建立来源、授权、质量、版本、偏差、隐私、血缘和使用反馈的控制链，让模型效果与风险都能解释和追溯。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

## 扩展实战：预训练数据治理框架的四个可执行案例

> [!info] 内容说明

| 案例 | 观察角度 | 首要对象 | 关键证据 | 失败时先停什么 |
| --- | --- | --- | --- | --- |
| 案例 4 | 权限、隐私与审计 | 数据资产 / 字段 | 分类分级、授权记录、字段血缘 | 高风险字段缺少授权、脱敏或审计时不进入分析环境，紧急访问必须到期自动回收 |

### 案例 4：预训练数据治理框架的最小权限与越权核查

某组织希望用“预训练数据治理框架”支持一次真实决策，但在取数与评审阶段发现，分析结果本身可以访问，但派生字段、导出文件和临时表扩大了敏感数据范围，现有流程没有及时识别。这个案例因此从问题定义重新开始。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 让数据用途、最小字段、访问角色、加工产物、保存期限和撤回机制都可追溯。在本场景里，核心风险还包括权限长期累积，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：数据资产、字段及其在资产盘点前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注asset_id与column_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 分析结果本身可以访问，但派生字段、导出文件和临时表扩大了敏感数据范围，现有流程没有及时识别。初看时，数据目录与元数据平台的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 分类分级、授权记录、字段血缘、访问日志、导出清单、脱敏规则和过期清理记录。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“数据治理办公室”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“预训练数据治理框架”的当前定义并记录版本；第二步用数据资产明细核对数据目录到元数据平台的关联；第三步按责任团队与业务域做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察血缘覆盖率和护栏指标规则通过率。
- **行动与护栏：** 按任务拆分数据集与角色，使用最小字段和临时授权，发布前检查派生表与导出是否出现敏感扩散。专题检查项“训练、评测和生产数据记录来源、授权、用途、版本和负责人”被写成发布门禁，高风险字段缺少授权、脱敏或审计时不进入分析环境，紧急访问必须到期自动回收。
- **失败路径：** 把“内网可访问”当成“业务已授权”，或者用永久大权限账号支撑临时分析。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“预训练数据治理框架”时，先验证数据卡、授权依据、采集时间和用途，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由数据治理办公室在明确时限内，根据血缘覆盖率、规则通过率和变更留痕完整决定继续、回退、补查还是转人工。 若权限长期累积或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：质量规则、问题工单及其在规则设计前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注rule_id与issue_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 为追求更快结果不断增加资源，账单和重复计算同步上升，但业务真正使用的时效并没有显著改善。初看时，权限系统与调度平台的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 执行计划、扫描量、文件数、峰值资源、单位产出成本、业务截止时间和质量门禁。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“数据分析”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“预训练数据治理框架”的当前定义并记录版本；第二步用质量规则明细核对权限系统到调度平台的关联；第三步按资产层级与责任团队做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察问题闭环率和护栏指标血缘覆盖率。
- **行动与护栏：** 先按使用场景和截止时间分级，再比较预聚合、增量计算、缓存、并发调整和生命周期策略。专题检查项“建立隐私、越权、错误信息、滥用和人工复核控制”被写成发布门禁，任何优化都必须同时通过结果对账、延迟目标与成本预算，不能只展示一次最快执行。
- **失败路径：** 为了压缩账单关闭质量检查，或为了刷新频率重复计算无人消费的全量结果。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“预训练数据治理框架”时，先验证抽样审核、标注一致性、分群覆盖和反例，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由数据分析在明确时限内，根据问题闭环率、血缘覆盖率和规则可执行且可解释决定继续、回退、补查还是转人工。 若规则只告警不闭环或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从预训练数据治理框架回到可核对明细

```sql
-- 预训练数据治理框架：行动前后与分组增量
WITH scoped AS (
  SELECT
    asset_id AS entity_key,
    责任团队 AS decision_group,
    check_time AS event_date,
    metric_value,
    CASE
      WHEN check_time <  :action_date THEN 'before'
      ELSE 'after'
    END AS period_label
  FROM fact_data_quality_result
  WHERE check_time >= :analysis_start
    AND check_time <  :analysis_end
    AND subject_key = 'subject'
),
grouped AS (
  SELECT
    decision_group,
    period_label,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    AVG(metric_value) AS metric_avg,
    SUM(metric_value) AS metric_sum
  FROM scoped
  GROUP BY decision_group, period_label
),
compared AS (
  SELECT
    decision_group,
    MAX(CASE WHEN period_label = 'before' THEN metric_avg END) AS before_avg,
    MAX(CASE WHEN period_label = 'after' THEN metric_avg END) AS after_avg,
    MAX(CASE WHEN period_label = 'before' THEN entity_cnt END) AS before_cnt,
    MAX(CASE WHEN period_label = 'after' THEN entity_cnt END) AS after_cnt
  FROM grouped
  GROUP BY decision_group
)
SELECT
  decision_group,
  before_avg,
  after_avg,
  after_avg - before_avg AS naive_delta,
  '平均修复时长' AS metric_name,
  '训练、评测和生产数据记录来源、授权、用途、版本和负责人' AS required_evidence
FROM compared
WHERE before_cnt >= 30 AND after_cnt >= 30
ORDER BY ABS(after_avg - before_avg) DESC;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把预训练数据治理框架的验收证据写成门禁

```python
from datetime import date
from hashlib import sha256

import pandas as pd

SUBJECT = "预训练数据治理框架"
BLOCKING_RULES = ["资产责任唯一","规则可执行且可解释","问题分级明确"]


def validate_release(frame: pd.DataFrame, start: date, end: date) -> dict:
    scoped = frame.loc[
        frame["event_date"].between(pd.Timestamp(start), pd.Timestamp(end))
        & (frame["subject_key"] == "subject")
    ].copy()
    checks = {
        "has_rows": len(scoped) > 0,
        "event_id_unique": not scoped["event_id"].duplicated().any(),
        "entity_key_complete": scoped["entity_key"].notna().all(),
        "event_time_present": scoped["event_time"].notna().all(),
        "scope_matches": scoped["subject_key"].nunique() == 1,
    }
    payload = f"{SUBJECT}|{start}|{end}|{len(scoped)}|{sorted(checks.items())}"
    return {
        "subject": SUBJECT,
        "rows": len(scoped),
        "checks": checks,
        "blocking_rules": BLOCKING_RULES,
        "release_allowed": all(checks.values()),
        "evidence_hash": sha256(payload.encode("utf-8")).hexdigest(),
    }
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。

### 四个案例共用的验收清单

| 验证面 | 发布前问题 | 证据 | 不通过时 |
| --- | --- | --- | --- |
| 对象与粒度 | 一行数据代表数据资产、事件、快照还是结果 | 主键、版本、有效时间和边界样本 | 阻断 |
| 时间语义 | 业务发生、数据可见、决策采用是否混用 | check_time、入仓时间、行动时间轴 | 阻断 |
| 指标口径 | 规则通过率的分子、分母和排除项是否冻结 | 指标字典、SQL、对账结果 | 阻断正式指标 |
| 状态与关联 | 资产盘点 → 标准定义 → 责任认领 → 规则设计是否可达且可追溯 | 状态机、明细、操作日志 | 阻断关键链路 |
| 权限与最小字段 | 派生表、导出和临时授权是否扩大访问范围 | 分类分级、字段血缘、访问日志 | 阻断导出 |
| 恢复与审计 | 失败后能否定位影响范围并幂等重跑 | 参数、版本、分区清单、补数对账 | 阻断发布 |
