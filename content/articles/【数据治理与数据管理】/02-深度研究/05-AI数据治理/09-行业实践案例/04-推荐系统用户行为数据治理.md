# 推荐系统用户行为数据治理

> [!tip] 分析目标
> “推荐系统用户行为数据治理”既可能是业务概念，也可能是技术方案，还可能是岗位能力。判断学习是否有效，要看能否在数据标准、元数据、主数据、质量规则、权限审计、血缘和问题闭环中做出一个可复现的小闭环。本文用多个案例展示从需求到数据结果，再回到业务行动和复盘的完整路径。

## 1. 把主题翻译成可验证的问题

“推荐系统用户行为数据治理”不能直接等同于“做一张趋势图”。一个可执行的分析问题至少包含对象、时间、比较基准和行动：

> 在【观察周期】内，对【有效对象】按【业务域、资产层级、规则类型】比较【问题闭环率】与【资产完整率】，判断变化来自结构、行为还是数据口径，并验证【策略动作】是否带来可解释的增量。

在数据治理与数据管理场景中，用户行为、交易结果和策略曝光经常来自不同系统。先画数据流：

数据目录 → 元数据平台 → 质量平台 → 权限系统 → 调度平台 → 工单系统

图中至少要有三个标记：业务事件发生时间、数据可见时间、策略或行动时间。只有三者分开，后续才能判断问题发生在业务、链路还是观察窗口。

## 2. 指标定义与分母检查

| 专题观测面 | 需要回答的问题 | 关键证据 | 判定与动作 |
| --- | --- | --- | --- |
| 特征（本标题优先） | 特征在预测时是否可得，训练与线上计算是否一致 | 特征时间、版本、缺失率、训练服务一致性和血缘 | 禁止使用未来信息 |
| 标签 | 标签代表什么、何时可用、是否有延迟或反馈偏差 | 标签定义、成熟窗口、正负样本和标注质量 | 标签泄漏时停止训练 |
| 运营 | 数据漂移、模型漂移、延迟、成本和回滚是否可观察 | 输入分布、预测分布、业务指标、版本和告警 | 设置自动降级与人工复核 |
| 评估 | 时间、用户、设备分组是否防止泄漏，误报成本如何 | 时间切分、分组验证、基线和成本矩阵 | 离线提升不等于线上有效 |

针对“推荐系统用户行为数据治理”，建议分别定义诊断指标、结果指标和护栏指标：

- **诊断指标**用于定位流程，例如曝光、有效访问、符合条件对象数和异常节点。
- **结果指标**用于判断是否改善，例如转化、留存、客单、毛利或处理时长。
- **护栏指标**用于防止局部优化伤害整体，例如退款、投诉、成本、公平性和长期留存。

每次计算都问四个问题：分母是谁、对象何时进入分母、例外状态怎么处理、窗口是否足够覆盖行为完成。尤其是资产没有负责人；规则只告警不闭环；口径变更缺少影响分析，任何一项没有解释清楚，指标都可能“看起来合理但无法决策”。

## 3. 方法选择：描述、诊断、预测还是因果

| 目标 | 适合的方法 | 需要的证据 | 不要混淆 |
| --- | --- | --- | --- |
| 描述现状 | 趋势、结构、同期群 | 完整口径、稳定时间窗 | 描述不等于原因 |
| 定位异常 | 分层、贡献度、漏斗、异常检测 | 原始事件、基线和质量检查 | 排名靠前不等于因果 |
| 预测未来 | 时间序列、回归、机器学习 | 时间切分验证、误差成本 | 离线准确率不等于业务收益 |
| 评估策略 | A/B、灰度、准实验 | 对照组、样本量、护栏指标 | 上线前后对比容易混入季节和选择偏差 |

如果问题只是“发生了什么”，先别急着建模；如果问题涉及“采取某策略会怎样”，就必须讨论反事实和识别条件。围绕“推荐系统用户行为数据治理”，应把观察分析、预测和因果评估的产出分开标注。

## 4. 案例一：华北某制造设备团队

### 案例 1：华北某制造设备团队的“推荐系统用户行为数据治理”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“推荐系统用户行为数据治理”映射到“机器学习、特征与 MLOps”中的特征，而不是泛泛讨论概念。
- **触发事件**：故障预测模型准确率高，但现场维修成本反而增加。
- **业务与数据范围**：传感器、设备、故障、维修、备件、停机和人工标注。数据侧重点采集特征时间、版本、缺失率、训练服务一致性和血缘，并与数据目录、元数据平台、质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：特征在预测时是否可得，训练与线上计算是否一致。
- **关键障碍**：随机切分造成同设备信息泄漏，误报成本没有进入目标，预测与维修排班脱节。同时要防止资产没有负责人把表面指标带偏。
- **处理过程**：按设备和时间分组验证，以提前预警窗口和成本矩阵评估，建立人工确认与持续学习闭环。实施时把“上线监控覆盖数据漂移、模型漂移、业务指标、成本和回滚”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例项目把模型指标转换为可执行的维修收益与风险。验收至少同时看主指标、特征时间、版本、缺失率、训练服务一致性和血缘和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把问题定义、标签、特征、时间切分、基线、离线评估、线上服务、漂移和回滚连接起来，避免用随机切分和单一准确率掩盖真实风险。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

## 5. SQL：计算趋势、结构和贡献度

### 趋势、结构与贡献度诊断

```sql
-- 推荐系统用户行为数据治理：留存同期群诊断（资产层级 × 责任团队）
WITH scoped AS (
  SELECT
    asset_id AS entity_key,
    event_id,
    check_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_data_quality_result
  WHERE check_time >= DATE '2026-08-01'
    AND check_time <  DATE '2026-11-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '血缘覆盖率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

示例 SQL 只表达计算逻辑。实际实施应加入分区条件、业务状态过滤、时区和主题范围，并在结果中保留口径版本。

- **业务与数据范围**：曝光、点击、购买、用户特征、商品特征、召回、排序和实验分组。数据侧重点采集标签定义、成熟窗口、正负样本和标注质量，并与数据目录、元数据平台、质量平台中的时间、状态和责任人信息对齐。

当业务方要求“解释为什么下降”时，可以按下面顺序回答：

1. 先确认下降是否真实存在，排查采集、任务、维表和状态映射。
2. 把变化拆成对象数量、行为强度和结构占比。
3. 找到贡献最大的分组，但保留其他分组的抵消效应。
4. 抽取正负样本回查业务事件和操作日志。
5. 把尚不能证明的解释标为假设，并设计下一轮验证。

## 7. 代码验证：专题指标、实验或模型

### 专题验证代码

```python
import pandas as pd
from sklearn.model_selection import TimeSeriesSplit
from sklearn.metrics import roc_auc_score
from sklearn.ensemble import HistGradientBoostingClassifier

def evaluate_time_aware(frame: pd.DataFrame, features: list[str], target: str) -> list[dict]:
    frame = frame.sort_values("event_date").reset_index(drop=True)
    scores = []
    for train_idx, test_idx in TimeSeriesSplit(n_splits=5, gap=7).split(frame):
        train, test = frame.iloc[train_idx], frame.iloc[test_idx]
        if train[target].nunique() < 2 or test[target].nunique() < 2:
            continue
        model = HistGradientBoostingClassifier(max_depth=4)
        model.fit(train[features], train[target])
        proba = model.predict_proba(test[features])[:, 1]
        scores.append({"model_auc": roc_auc_score(test[target], proba)})
    return scores
```

## 8. 异常、偏差与常见误区

- **辛普森悖论**：总体改善但每个分组都变差，可能由对象结构变化造成。
- **幸存者偏差**：只分析完成流程的对象，忽略中途流失和中止。
- **分母漂移**：渠道口径、登录状态、版本或活动范围变化，改变可比性。
- **回传延迟**：当天数据未回补，导致近期效果被系统性低估。
- **多重比较**：反复寻找显著分组，实际只是随机波动。
- **行动偏差**：只报告支持既定方案的结果，忽略反例和护栏指标。

围绕“推荐系统用户行为数据治理”，应预先写出至少三条反例检查。比如权限和敏感信息是否遵循最小必要原则、结论是否能回到明细，以及 指标是否在同一对象和同一时间窗内计算。

### 案例 3：华南某银行风控团队的“推荐系统用户行为数据治理”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“推荐系统用户行为数据治理”映射到“机器学习、特征与 MLOps”中的运营，而不是泛泛讨论概念。
- **触发事件**：模型在历史数据表现很好，但新客群逾期率明显高于预期。
- **业务与数据范围**：申请、授信、交易、还款、客群、规则版本、模型分数和人工审批。数据侧重点采集输入分布、预测分布、业务指标、版本和告警，并与数据目录、元数据平台、质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：数据漂移、模型漂移、延迟、成本和回滚是否可观察。
- **关键障碍**：拒绝样本被排除，模型只学习已通过客户；规则变化又没有进入特征版本。同时要防止口径变更缺少影响分析把表面指标带偏。
- **处理过程**：分析选择偏差，建立时间外验证和分群监控，记录规则版本并保留人工复核样本。实施时把“训练、验证和测试按时间或实体隔离，检查标签与特征泄漏”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：复合案例用召回、误拒、逾期、稳定性和可解释性多维评估。验收至少同时看主指标、输入分布、预测分布、业务指标、版本和告警和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把问题定义、标签、特征、时间切分、基线、离线评估、线上服务、漂移和回滚连接起来，避免用随机切分和单一准确率掩盖真实风险。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

- **核验证据：** 基线、对照或趋势拟合、分组分配、主指标、护栏指标、动作时间和成本记录。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“审计”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“推荐系统用户行为数据治理”的当前定义并记录版本；第二步用质量规则明细核对审计平台到数据目录的关联；第三步按严重等级与资产层级做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察平均修复时长和护栏指标问题闭环率。
- **行动与护栏：** 在行动前冻结观察窗口与分组规则，上线后同时报告总体结果、分层结果、置信区间和反例。专题检查项“上线监控覆盖数据漂移、模型漂移、业务指标、成本和回滚”被写成发布门禁，收益只在少数子组出现且护栏恶化时，不扩大全量使用。
- **失败路径：** 用上线前后两张趋势图直接宣称方案有效，忽略选择偏差与自然增长。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“推荐系统用户行为数据治理”时，先验证时间切分、分组验证、基线和成本矩阵，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由审计在明确时限内，根据平均修复时长、问题闭环率和敏感字段访问可审计决定继续、回退、补查还是转人工。 若数据目录与真实血缘脱节或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从推荐系统用户行为数据治理回到可核对明细

```sql
-- 推荐系统用户行为数据治理：恢复后缺失、重复与跨期检查
WITH expected_keys AS (
  SELECT DISTINCT asset_id AS entity_key, event_id
  FROM fact_data_quality_result
  WHERE check_time >= :restore_start
    AND check_time <  :restore_end
    AND subject_key = 'subject'
),
restored_keys AS (
  SELECT asset_id AS entity_key, event_id, load_version, loaded_at
  FROM fact_data_quality_result
  WHERE check_time >= :restore_start
    AND check_time <  :restore_end
    AND subject_key = 'subject'
    AND load_version = :restore_version
),
coverage AS (
  SELECT
    (SELECT COUNT(*) FROM expected_keys) AS expected_cnt,
    (SELECT COUNT(*) FROM restored_keys) AS restored_cnt,
    (SELECT COUNT(*) FROM (
      SELECT entity_key, event_id
      FROM restored_keys
      GROUP BY entity_key, event_id
      HAVING COUNT(*) > 1
    ) duplicate_keys) AS duplicated_cnt,
    (SELECT COUNT(*) FROM (
      SELECT e.entity_key, e.event_id
      FROM expected_keys e
      LEFT JOIN restored_keys r USING (entity_key, event_id)
      WHERE r.entity_key IS NULL
    ) missing_keys) AS missing_cnt
)
SELECT *,
  CASE
    WHEN expected_cnt <> restored_cnt OR duplicated_cnt > 0 OR missing_cnt > 0
      THEN 'reject_release'
    ELSE 'accept_restore'
  END AS gate_result
FROM coverage;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

```python
import json
from pathlib import Path


def build_evidence_manifest(
    subject: str,
    scope: dict,
    checks: dict,
    samples: list[dict],

        ],
    }


manifest = build_evidence_manifest(
```
