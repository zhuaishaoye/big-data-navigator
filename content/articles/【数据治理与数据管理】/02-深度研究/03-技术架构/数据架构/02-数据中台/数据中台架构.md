# 数据中台架构

> [!abstract] 企业数据平台落地实战手册
> 数据中台架构的核心不是建一个集中库，而是把数据资产、指标、标签、接口、权限和运行契约组织成可复用的生产能力。它同时包含承载数据和任务的数据面，以及负责目录、准入、版本、配额、审计与退出的控制面。

## 1. 数据中台架构：定义、适用边界与决策出口

数据中台架构的核心不是建一个集中库，而是把数据资产、指标、标签、接口、权限和运行契约组织成可复用的生产能力。它同时包含承载数据和任务的数据面，以及负责目录、准入、版本、配额、审计与退出的控制面。

**本篇的适用边界。** 本篇讨论已经决定建设中台之后，如何划分平台边界、公共资产、服务契约和运行责任；不讨论是否应该跟风建设中台，也不把采购某套工具当成架构完成。

**最常见的错误替代。** 不能把所有源表直接复制到公共层，也不能用调用次数证明资产有效；强制接入、无责任人目录和无法下线的数据产品都会把集中化变成瓶颈。

**最终决策。** 架构委员会、平台团队和业务数据负责人要共同判断：哪些能力进入公共层，哪些留在业务域，接口以什么版本发布，异常时谁降级、谁回滚，资产何时退出。 因此，这篇内容不从“应该建哪张表”开始，而从业务动作、责任人和失败后果开始。只有先确定谁在什么时点做出什么决定，字段、SQL、看板和模型才有明确用途。

围绕“数据中台架构”，工作中至少要区分四类问题：

1. **身份问题**：对象是谁，主键能否跨系统稳定关联，合并、拆分、撤销后历史是否还看得见。
2. **时间问题**：业务发生、状态生效、数据入仓、计算完成和人员行动分别发生在哪一刻。
3. **状态问题**：当前状态是一段事件、一张快照还是最终结果，空值代表未发生、未采集还是已删除。
4. **责任问题**：谁确认口径，谁处理异常，谁有权放行或停止，谁在观察期后复盘。

## 2. 数据中台架构的完整业务流程

| 环节 | 要做的事 | 最小证据 | 失败后先查什么 |
| --- | --- | --- | --- |
| 域与能力盘点 | 确认业务域、共享对象、重复建设点和真实消费方 | 域责任表、能力地图、建设与运行成本 | 以资产数量作为建设成果 |
| 公共资产准入 | 评估跨域复用、稳定程度、合规等级和归属责任 | 准入评审、消费证据、资产卡和 SLA | 指标逻辑更新后所有消费方立即变化 |
| 数据面分层 | 区分贴源、明细、汇总、指标和标签的粒度与生命周期 | 模型说明、字段血缘、分区与保留策略 | 共享接口无租户配额和降级 |
| 控制面建设 | 管理目录、版本、审批、配额、订阅、审计和下线 | 契约登记、变更单、权限记录和调用日志 | 历史产品永久保留 |
| 服务发布 | 通过 API、数据集或指标服务交付并设置配额与降级 | 服务目录、接口样例、限流和故障预案 | 以资产数量作为建设成果 |
| 运行与成本 | 观测质量、时延、可用性、使用和单位产出成本 | SLO 看板、账单分摊、工单和复盘 | 指标逻辑更新后所有消费方立即变化 |
| 复审与退出 | 按消费、风险和成本决定升级、合并、迁移或下线 | 复审记录、迁移对账和残留调用清单 | 共享接口无租户配额和降级 |

把 域与能力盘点、公共资产准入、数据面分层、控制面建设、服务发布、运行与成本、复审与退出 串起来后可以看出，数据中台架构不是一个孤立字段，而是一条会跨系统、跨岗位、跨时间的证据链。流程图上每一段都应标出输入、输出、状态、时间戳、责任人和异常出口。只要其中一段只能靠口头解释，后续的统计、追责和自动化就会失去基础。

一个合格的需求说明应该写成：

> 在【授权数据范围】和【观察窗口】内，围绕“数据中台架构”的【业务域】，按【business_domain_id、data_product_id、service_tier、region_code】比较【有效跨域复用资产率】及其【服务契约履约率】，定位一个可干预节点；行动后同时观察主指标、样本量和护栏，任何高风险异常先阻断再调查。

## 3. 数据中台架构的数据对象与系统契约

| 数据对象 | 建议主键 | 一行代表什么 | 不允许混淆 |
| --- | --- | --- | --- |
| 业务域 | `business_domain_id` | 一个具有业务责任和稳定边界的领域 | 对象身份与业务事件 |
| 数据资产版本 | `asset_version_id` | 一次可发布、可订阅并可审计的资产定义 | 事件、状态快照和结果粒度 |
| 服务契约 | `service_contract_id` | 一类服务在指定版本下的字段、SLA 和配额 | 事件、状态快照和结果粒度 |
| 订阅关系 | `subscription_id` | 一个消费应用与一个服务版本的有效期关系 | 事件、状态快照和结果粒度 |
| 运行事件 | `platform_run_event_id` | 一次发布、调用、限流、故障或回滚事件 | 事件、状态快照和结果粒度 |
| 成本分摊单 | `cost_allocation_id` | 一个周期内资源成本归属到资产和消费方 | 事件、状态快照和结果粒度 |

对象表不是把所有字段塞进一张宽表。事件、状态快照和结果表应该分别保留粒度，再通过稳定主键与版本建立关联。尤其要避免三个常见混算：把一次业务事件算成多个对象、把每日快照相加当事件总量、把最新状态覆盖历史状态。

本主题的数据契约至少应包含：

- `asset_version_id` 的唯一性规则、生成方式和跨系统映射。
- `observed_at` 的业务含义、时区、迟到和补录规则。
- `runtime_status` 的完整状态集合，以及删除、撤销、冻结和失效的表示方法。
- 控制对象 `platform_service_contract.service_contract_id` 与主对象的关系。
- 每次口径、规则、模型或源版本变化的影响范围和下游通知对象。
- 敏感字段、允许用途、访问角色、导出限制和审计保留时间。

## 4. 数据中台架构的指标、样本与验收口径

| 指标 | 公式或定义 | 口径提醒 |
| --- | --- | --- |
| 有效跨域复用资产率 | 被两个以上独立业务域真实使用的认证资产数 / 认证资产总数 | 测试、压测和同域复制调用不计入 |
| 服务契约履约率 | 观察窗口内达到质量、时延和可用性目标的契约数 / 有流量的契约数 | 按服务等级分层，不把低等级接口混入 |
| 公共资产变更影响覆盖率 | 发布前完成订阅方影响确认的变更数 / 有订阅的变更数 | 影响确认必须绑定具体版本和消费方 |
| 单位有效请求成本 | 平台总成本 / 产生业务结果的去重请求量 | 排除重试、扫描、测试和失败调用 |
| 退出按期完成率 | 在批准窗口内完成迁移和下线的资产数 / 计划退出资产数 | 旧版本残留调用和归档也要验收 |

指标字典至少写到“任何人都能按同一份数据复跑”的程度：中文名、业务定义、公式、分子、分母、事实粒度、时间字段、对象范围、排除项、版本、负责人和验收样例，一个都不能少。比例指标必须同时展示分子、分母和样本量；金额或数量必须做守恒；状态指标必须能回到事件时间线。

对于“数据中台架构”，建议把观察分成三层：

| 层次 | 看什么 | 不能替代什么 |
| --- | --- | --- |
| 业务结果 | 有效跨域复用资产率、服务契约履约率 | 不能替代过程证据和个案回查 |
| 过程护栏 | 公共资产变更影响覆盖率、单位有效请求成本、退出按期完成率 | 不能因为护栏暂时正常就跳过异常调查 |
| 数据证据 | 主键、时间、状态、版本、来源目标对账 | 不能只看任务成功或报表能打开 |

## 5. 数据中台架构：七个真实工作场景

以下七组场景均为公开方法结合常见工作流程构造的“脱敏复合示例”，不对应任何单一企业、患者、客户或雇员事实。场景的目的，是展示如何从现象走到证据、行动和验收，而不是虚构经营成果。

### 1. 资产目录很全但没人敢用

**现场。** 目录里有上千个资产，业务仍重复建设客户标签。

**怎么查。** 抽取真实订阅、调用账号、工单和资产卡，发现大量条目没有责任人、SLA、字段解释或近期消费记录。

**怎么处理。** 把认证拆成可发现、可试用、可订阅和可运营四级；无消费证据的资产不进入首页推荐；重复标签先合并口径再迁移。

**验收结论。** 目录规模不是复用能力。只有责任、契约和真实使用同时成立，资产才算可用。

### 2. 公共指标升级导致下游批量漂移

**现场。** 公共 GMV 调整退款处理，十几个看板一起变化。

**怎么查。** 对比资产版本、订阅关系、任务执行和看板取数，发现多数消费方直接读取最新视图，没有固定契约版本。

**怎么处理。** 公共指标采用语义版本；破坏性变更先影子发布；按订阅关系生成影响清单；旧版本保留过渡期并记录退出。

**验收结论。** 复用会放大收益，也会放大变更影响。版本与通知必须进入服务运行机制。

### 3. 实时标签与离线标签同名不同义

**现场。** 推荐团队发现同一用户在两套服务里得到不同风险标签。

**怎么查。** 追溯标签定义、更新时点、缺失值处理和回刷规则，发现离线清空状态、实时只发送变化事件。

**怎么处理。** 为标签建立唯一语义 ID；实时状态服务先消费全量快照再增量更新；同名字段必须共享口径卡并标明时效。

**验收结论。** 同名字段不等同一定义。离线快照与流式状态需要在契约层明确更新和补全机制。

### 4. 数据服务没有限流拖垮全平台

**现场。** 一个高并发报表绕过缓存直查公共明细，其他接口延迟上升。

**怎么查。** 关联调用方、SQL、扫描量、并发和资源池，发现服务没有按租户和接口设置配额。

**怎么处理。** 按消费者 SLA 分级；热点结果缓存和物化；设置租户并发与扫描预算；超限返回可解释降级而不是无限排队。

**验收结论。** 服务化必须包含容量边界。没有配额的共享能力会把一个使用方的问题扩散给所有人。

### 5. 成本分摊只能算到部门

**现场。** 平台成本增长，但无法判断哪些资产或数据产品值得继续投入。

**怎么查。** 把任务、存储、查询、接口和缓存映射到资产版本与订阅关系，拆出共享开销、空转任务和一次性分析。

**怎么处理。** 成本按可解释驱动量分摊；设置资产预算与异常增长告警；低使用高成本资产进入复审，不直接砍共享基础能力。

**验收结论。** 成本治理要区分公共固定成本、真实共享成本与单一消费方增量，否则会误伤基础服务。

### 6. 老资产无人使用但没人敢下线

**现场。** 早期数据产品长期零业务调用，仍被视为历史核心。

**怎么查。** 核对真实登录、API 调用、下游血缘、账号状态和迁移记录，区分监控探测、测试流量和真实依赖。

**怎么处理。** 停止新订阅，通知存量消费方，提供迁移模板和归档；到期复核后下线，保留审计和恢复路径。

**验收结论。** 没有退出机制的中台会持续累积维护、权限和安全成本。

### 7. 应急权限绕过服务契约

**现场。** 线上事故中临时账号直接改公共结果表，导致版本与目录失真。

**怎么查。** 从操作审计、发布系统和调用日志还原临时变更，发现应急流程没有登记、到期和复核。

**怎么处理。** 建立限时应急权限、双人批准、变更登记和自动回收；应急后补做版本、对账和订阅影响；生产修复不能只存在于聊天记录。

**验收结论。** 应急能力不能破坏可追溯性。越紧急的变更越需要自动记录边界和恢复证据。

七个场景可以归成一条共同判断顺序：先确认对象和时间，再确认状态和版本；然后做总量、结构和明细三层对账；最后才讨论策略、模型或工具。若一条结论不能指出对应的原始记录、责任人和行动出口，就只能算观察，不能作为生产结论。

## 6. 数据中台架构的第一段 SQL：重建业务链路

下面的 SQL 用于说明对象、时间、状态、版本和分层口径如何进入同一条可复查路径。表名和部分字段是通用示例，落地时应映射到企业数据字典；SQL 方言也需按实际引擎调整。

```sql
-- 数据中台架构：按业务对象重建链路，避免事件、快照和结果混算
WITH ranked_asset_version_id AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY asset_version_id
      ORDER BY updated_at DESC
    ) AS version_no
  FROM platform_asset_runtime_event
  WHERE observed_at >= TIMESTAMP '{start_time}'
    AND observed_at <  TIMESTAMP '{end_time}'
    AND runtime_status NOT IN ('deleted', 'test')
),
valid_rows AS (
  SELECT
    asset_version_id,
    business_domain_id,
    data_product_id,
    service_tier,
    region_code,
    observed_at,
    runtime_status,
    ingested_at
  FROM ranked_asset_version_id
  WHERE version_no = 1
)
SELECT
  business_domain_id, data_product_id, service_tier, region_code,
  COUNT(DISTINCT asset_version_id) AS object_cnt,
  COUNT(DISTINCT CASE WHEN verified_business_use THEN consumer_app_id END) AS numerator_value,
  COUNT(DISTINCT subscribed_asset_version_id) AS denominator_value,
  CAST(COUNT(DISTINCT CASE WHEN verified_business_use THEN consumer_app_id END) AS DOUBLE PRECISION)
    / NULLIF(COUNT(DISTINCT subscribed_asset_version_id), 0) AS metric_value,
  MIN(observed_at) AS first_event_at,
  MAX(observed_at) AS last_event_at
FROM valid_rows
GROUP BY business_domain_id, data_product_id, service_tier, region_code
ORDER BY metric_value DESC, object_cnt DESC;
```

执行后至少回答六个问题：

- 同一对象是否因为多源回传产生多版本，版本保留是否符合业务要求？
- 业务时间与入仓时间是否分开，补录和迟到数据是否进入正确分区？
- 分子分母是否来自同一对象范围和同一统计窗口？
- 维度使用的是事件当时值还是当前值，跨期比较是否一致？
- 删除、撤销、冻结和测试数据是否按规则处理？
- 分组结果能否在明细中抽样复现？

## 7. 数据中台架构的第二段 SQL：源、控制和结果三方对账

```sql
-- 数据中台架构：源对象、控制对象和结果对象三方对账
WITH population AS (
  SELECT
    asset_version_id,
    observed_at,
    runtime_status
  FROM platform_asset_runtime_event
  WHERE observed_at >= TIMESTAMP '{start_time}'
    AND observed_at <  TIMESTAMP '{end_time}'
),
control AS (
  SELECT
    asset_version_id,
    SUM(contracted_slo_count) AS control_value,
    COUNT(DISTINCT service_contract_id) AS control_cnt,
    MAX(updated_at) AS control_updated_at
  FROM platform_service_contract
  WHERE updated_at >= TIMESTAMP '{start_time}'
  GROUP BY asset_version_id
),
result AS (
  SELECT
    asset_version_id,
    COUNT(*) AS result_cnt,
    MAX(calculated_at) AS calculated_at
  FROM mart_asset_version_id
  WHERE business_date BETWEEN DATE '{start_date}' AND DATE '{end_date}'
  GROUP BY asset_version_id
)
SELECT
  COALESCE(p.asset_version_id, c.asset_version_id, r.asset_version_id) AS object_key,
  CASE
    WHEN p.asset_version_id IS NULL THEN 'source_missing'
    WHEN c.asset_version_id IS NULL THEN 'control_missing'
    WHEN r.asset_version_id IS NULL THEN 'result_missing'
    WHEN ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0 THEN 'count_or_value_gap'
    ELSE 'matched'
  END AS reconciliation_status,
  p.runtime_status,
  c.control_value,
  c.control_cnt,
  r.result_cnt,
  c.control_updated_at,
  r.calculated_at
FROM population p
FULL OUTER JOIN control c ON p.asset_version_id = c.asset_version_id
FULL OUTER JOIN result r ON COALESCE(p.asset_version_id, c.asset_version_id) = r.asset_version_id
WHERE p.asset_version_id IS NULL
   OR c.asset_version_id IS NULL
   OR r.asset_version_id IS NULL
   OR ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0;
```

这段查询故意不使用“总数相差小于某个随意百分比就算通过”。它先找出缺失对象和状态差异，再检查控制值与结果值。对于数据中台架构，数量、金额、时长或状态任意一项无法解释，都不能用“业务波动”代替排查。

对账结果建议分成四类处理：

1. **阻断**：对象缺失、关键时间为空、状态非法、金额或数量不守恒、权限越界。
2. **严重**：比例或总量显著偏离基线，且无法由已确认的对象结构变化解释。
3. **观察**：小范围波动但来源、样本和趋势可控，进入责任人和观察窗口。
4. **探索**：只有弱信号或假设，不进入正式结论，更不直接触发业务处罚。

## 8. 数据中台架构的 Python 发布门禁与指标护栏

第一段代码把发布条件写成可执行对象，避免“检查过了”只存在聊天记录里：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class AssetVersionIdBatch:
    batch_id: str
    source_rows: int
    valid_rows: int
    duplicate_keys: int
    missing_required_fields: int
    reconciliation_gap: float

def release_asset_version_id(batch: AssetVersionIdBatch) -> dict:
    checks = {
        "source_not_empty": batch.source_rows > 0,
        "valid_rows_in_range": 0 <= batch.valid_rows <= batch.source_rows,
        "duplicate_rate_ok": batch.duplicate_keys / max(batch.source_rows, 1) <= 0.001,
        "required_fields_ok": batch.missing_required_fields == 0,
        "reconciliation_ok": abs(batch.reconciliation_gap) <= 0.01,
    }
    return {
        "topic": "数据中台架构",
        "batch_id": batch.batch_id,
        "checks": checks,
        "release_allowed": all(checks.values()),
        "blocking_checks": [name for name, passed in checks.items() if not passed],
    }
```

第二段代码演示如何为比例类结果附带样本证据和小样本下界。它不是替代统计学家的模型，而是防止把少量偶然样本直接包装成稳定结论：

```python
from dataclasses import dataclass
from math import sqrt

@dataclass(frozen=True)
class AssetVersionIdObservation:
    object_id: str
    numerator: float
    denominator: float
    sample_size: int
    scope_version: str

def calculate_asset_version_id(rows: list[AssetVersionIdObservation]) -> list[dict]:
    output = []
    for row in rows:
        value = row.numerator / row.denominator if row.denominator > 0 else None
        # 小样本用 Wilson 下界做护栏，不把偶然的高比例直接当稳定结果。
        z = 1.96
        p = value or 0
        n = max(row.sample_size, 1)
        center = p + z * z / (2 * n)
        margin = z * sqrt((p * (1 - p) + z * z / (4 * n)) / n)
        lower = max(0, (center - margin) / (1 + z * z / n))
        output.append({
            "object_id": row.object_id,
            "metric": "有效跨域复用资产率",
            "value": value,
            "lower_bound": lower if value is not None else None,
            "sample_size": row.sample_size,
            "scope_version": row.scope_version,
            "caution": "测试、压测和同域复制调用不计入",
        })
    return output
```

真正上线时还要补充参数配置、日志、血缘、告警级别、重跑幂等、异常样本保存和审批记录。代码通过不代表业务通过；自动检查只能证明已经定义的规则没有被违反，无法证明规则本身一定正确。

## 9. 数据中台架构的失败反例与上线验收

| 风险信号 | 错误做法 | 必须补齐的证据 | 发布或行动规则 |
| --- | --- | --- | --- |
| 目录当能力 | 以资产数量作为建设成果 | 责任人、文档、SLA 和真实消费方 | 没有使用证据不认证 |
| 无版本直接覆盖 | 指标逻辑更新后所有消费方立即变化 | 语义版本、影响清单和迁移记录 | 破坏性变更默认阻断 |
| 服务无限并发 | 共享接口无租户配额和降级 | 调用日志、扫描量和容量基线 | 超限时限流并可解释降级 |
| 资产不能退出 | 历史产品永久保留 | 订阅、调用和迁移证据 | 按复审日期完成下线或续期 |

上线验收不应只有一句“报表正常”。建议按下面四层验收：

| 验收对象 | 结构要求 | 测试样本 | 结果证据 |
| --- | --- | --- | --- |
| 业务域 | `business_domain_id` 能唯一定位一个具有业务责任和稳定边界的领域 | 正常、重复、缺失、撤销与跨期样本 | 有效跨域复用资产率可回到原始对象 |
| 数据资产版本 | `asset_version_id` 能唯一定位一次可发布、可订阅并可审计的资产定义 | 正常、重复、缺失、撤销与跨期样本 | 服务契约履约率可回到原始对象 |
| 服务契约 | `service_contract_id` 能唯一定位一类服务在指定版本下的字段、SLA 和配额 | 正常、重复、缺失、撤销与跨期样本 | 公共资产变更影响覆盖率可回到原始对象 |
| 订阅关系 | `subscription_id` 能唯一定位一个消费应用与一个服务版本的有效期关系 | 正常、重复、缺失、撤销与跨期样本 | 单位有效请求成本可回到原始对象 |
| 运行事件 | `platform_run_event_id` 能唯一定位一次发布、调用、限流、故障或回滚事件 | 正常、重复、缺失、撤销与跨期样本 | 退出按期完成率可回到原始对象 |
| 成本分摊单 | `cost_allocation_id` 能唯一定位一个周期内资源成本归属到资产和消费方 | 正常、重复、缺失、撤销与跨期样本 | 有效跨域复用资产率可回到原始对象 |

还应为每一次发布保留一组固定回归样本：正常对象、边界状态、重复记录、缺失字段、撤销或退款、跨期、权限拒绝和失败恢复。回归样本不是演示数据，而是以后每次改规则都能重复执行的质量资产。

## 10. 数据中台架构的 30 天落地与复盘

| 阶段 | 主要交付 | 通过条件 |
| --- | --- | --- |
| 第 1 周：定义 | 对象、流程、状态、指标、排除项和责任矩阵 | 业务、数据、安全或质量负责人对同一口径签字 |
| 第 2 周：打通 | 源字段、主键、时间、版本、控制对象和失败样本 | 正常与异常样本都能回到原始记录 |
| 第 3 周：验证 | 总量对账、分层对账、抽样回查、权限测试、回滚演练 | 阻断问题清零，严重问题有责任人与期限 |
| 第 4 周：发布 | 灰度、SLO、监控、行动清单、停止条件和复盘模板 | 使用者在真实场景中完成一次闭环行动 |

如果必须用 90 秒说明“数据中台架构”是否做对，可以按这个顺序自测：

1. 一行数据代表什么，主键是什么，哪些对象绝不能混在同一粒度？
2. 业务发生、数据可见、计算完成和行动确认分别在哪个时间点？
3. 本主题最重要的两个主指标、三个护栏和最小样本量是什么？
4. 一个异常出现时，先从原始记录、链路版本还是业务动作开始查？
5. 哪类错误必须阻断发布或停止使用，谁有权批准例外？
6. 上线后由谁在多长时间内观察，什么条件下回滚或结束？

> [!check] 完成标准
> 当另一位数据同事不看聊天记录，只根据口径卡、回归样本和代码就能复跑同一结果；当业务负责人能指出一个异常对应的原始对象、处置动作和复核证据；当系统能够阻止未授权或状态非法的数据进入下游，这篇“数据中台架构”才算真正落到工作里。
