# 数据治理成熟度评估与路线图制定

> [!abstract] 项目视角
> 如果只记住“数据治理成熟度评估与路线图制定”的定义，遇到真实数据时仍然很难行动。本文把它拆成五个可检查问题：谁在使用、流程在哪里变化、数据一行代表什么、异常如何发现、上线后用哪个指标验收。每个部分都配一个工作案例或代码片段。

## 1. 项目背景与边界

“数据治理成熟度评估与路线图制定”作为项目，必须同时定义业务目标、数据范围、技术边界和验收方式。建议在立项材料里写清：

- **业务目标**：改善哪个流程、服务哪个角色、影响什么决策。
- **现状基线**：当前耗时、错误率、覆盖率、成本或用户反馈，不能只写“比较落后”。
- **范围**：覆盖业务域、系统、表、指标和团队；明确不做什么。
- **约束**：数据权限、上线窗口、依赖系统、预算、合规和人员。
- **成功标准**：主指标、护栏指标、验收样例和观察周期。

一个合格目标示例：

> 在【时间】前，为【用户】交付“数据治理成熟度评估与路线图制定”能力，使【规则通过率】达到【可解释目标】，同时保证资产责任唯一、规则可执行且可解释、问题分级明确，上线后由【负责人】按周复盘。

## 2. 现状诊断与数据资产盘点

先梳理数据目录、元数据平台、质量平台、权限系统、调度平台、工单系统之间的数据流，记录源系统、接口、表、任务、负责人和延迟。不要用一张“系统架构图”掩盖数据质量问题，必须把主键、时间、状态和数量关系标出来。

| --- | --- | --- | --- |
| 核心对象 | 数据资产 | `asset_id` | 资产盘点 |
| 过程对象 | 字段 | `column_id` | 标准定义 |
| 过程对象 | 指标 | `metric_id` | 责任认领 |

盘点阶段至少输出：资产清单、接口清单、指标基线、质量问题清单、权限清单和依赖矩阵。对每个问题标记影响范围、发生频率、现有临时方案和根本原因。

## 3. 目标架构与方案取舍

| 层次 | 本文建议 | 关键问题 | 验收证据 |
| --- | --- | --- | --- |
| 数据源 | 数据目录、元数据平台、质量平台 | 权威源、更新频率、主键和权限 | 接口或表清单 |
| 接入 | 批、流或 CDC 按业务时延选择 | 重复、顺序、断点续传和回放 | 延迟与幂等测试 |
| 存储 | 按访问模式选择数据湖、数仓或 OLAP | 分区、格式、生命周期和成本 | 容量与查询评测 |
| 计算 | SQL、Spark、Flink 或 Python 服务 | 粒度、状态、资源和失败恢复 | 压测与执行计划 |

方案评审至少比较两种选择。例如批处理与实时处理、现成工具与自研、集中式平台与数据网格。比较维度包括交付速度、时延、成本、可维护性、权限边界、扩展性和失败恢复，而不是只比较功能清单。

## 4. 数据模型与指标口径

| 专题观测面 | 需要回答的问题 | 关键证据 | 判定与动作 |
| --- | --- | --- | --- |
| 落地（本标题优先） | 试点、迁移、并行、验收和回滚如何安排 | PoC、灰度、双跑和决策门禁 | 演示成功不等于生产可用 |

| 资产完整率 | `COUNT(DISTINCT complete_asset_id) / COUNT(DISTINCT asset_id)`（视图字段 `asset_completeness`） | 规则类型、责任团队、严重等级 | 不混用测试、撤销和跨期状态；与“数据治理成熟度评估与路线图制定”相关时还要补充主题筛选 |
| 血缘覆盖率 | `COUNT(DISTINCT lineage_asset_id) / COUNT(DISTINCT critical_asset_id)`（视图字段 `lineage_coverage`） | 责任团队、严重等级 | 不混用测试、撤销和跨期状态；与“数据治理成熟度评估与路线图制定”相关时还要补充主题筛选 |

模型设计优先保证粒度清晰和可重算。事实表负责事件或结果，维度表负责对象属性与历史归属，汇总表负责稳定消费。对于“数据治理成熟度评估与路线图制定”，如果既有事件又有状态，应分别建模，避免用最新状态覆盖历史。

## 5. 案例一：华南某制造集团

### 案例 1：华南某制造集团的“数据治理成熟度评估与路线图制定”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“数据治理成熟度评估与路线图制定”映射到“技术选型、路线图与架构演进”中的落地，而不是泛泛讨论概念。
- **触发事件**：多个工厂希望采用不同湖仓产品，集团担心重复平台和长期维护成本。
- **业务与数据范围**：工厂规模、网络、实时需求、数据主权、现有技能和三年预算。数据侧重点采集PoC、灰度、双跑和决策门禁，并与数据目录、元数据平台、质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：试点、迁移、并行、验收和回滚如何安排。
- **关键障碍**：选型只比较存储格式和查询速度，没有计算跨厂治理与运维总成本。同时要防止资产没有负责人把表面指标带偏。
- **处理过程**：区分集团标准能力与工厂本地能力，建立兼容接口和集中元数据，保留例外审批。实施时把“选型从真实问题和现状基线出发，不使用厂商演示作为唯一证据”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例架构在标准化与业务灵活性之间设置可量化边界。验收至少同时看主指标、PoC、灰度、双跑和决策门禁和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把业务约束、总拥有成本、团队能力、迁移风险和退出策略放进同一决策框架，避免用功能清单和短期演示做技术选型。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

项目里最重要的一次评审通常发生在写代码之前。把对象、粒度、时间和成功标准画在白板上，让业务、数据、安全和运维共同指出歧义，往往比上线后修复便宜得多。

```python
TOPIC = "数据治理成熟度评估与路线图制定"
EVALUATION_ID = "g_technology_strategy_11jpedg"

@dataclass
class Candidate:
    name: str
    problem_fit: float
    production_perf: float
    tco_score: float
    migration_score: float
    exit_score: float
    evidence: list[str] = field(default_factory=list)

def weighted_decision(candidate: Candidate) -> dict:
    weights = {
        "problem_fit": 0.24,
        "production_perf": 0.22,
        "tco": 0.20,
        "migration": 0.16,
        "exit": 0.18,
    }
    scores = {
        "problem_fit": candidate.problem_fit,
        "production_perf": candidate.production_perf,
        "tco": candidate.tco_score,
        "migration": candidate.migration_score,
        "exit": candidate.exit_score,
    }
    total = sum(scores[key] * weights[key] for key in weights)
    return {
        "candidate": candidate.name,
        "score": round(total, 4),
        "evidence_count": len(candidate.evidence),
        "decision": "poc" if len(candidate.evidence) < 3 else "review",
    }
```

### 上线前质量门禁

```python
# 数据治理成熟度评估与路线图制定：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "数据治理成熟度评估与路线图制定"
TOPIC_KEY = "subject"
RULE_ID = "rule_governance_11jpedg"
GUIDE_CHECKS = [
    "选型从真实问题和现状基线出发，不使用厂商演示作为唯一证据",
    "评估功能、性能、总成本、风险、团队能力和迁移工作量",
    "PoC 覆盖真实查询、并发、权限、故障恢复和升级",
    "记录被否决方案、决策假设、退出策略和复审日期"
]
RULES = {
    "required_columns": ["event_id", "asset_id", "check_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "asset_id",
    "time_field": "check_time",
    "max_duplicate_rate": 0.0009,
    "max_null_rate": 0.006,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：选型从真实问题和现状基线出发，不使用厂商演示作为唯一证据；评估功能、性能、总成本、风险、团队能力和迁移工作量；PoC 覆盖真实查询、并发、权限、故障恢复和升级；记录被否决方案、决策假设、退出策略和复审日期
```

## 8. 测试、灰度与上线

| 测试类型 | 检查内容 | 通过标准 |
| --- | --- | --- |
| 单元测试 | 字段映射、计算逻辑、边界条件 | 用例覆盖正常、异常和极端值 |
| 集成测试 | 上下游接口、主键关联、权限 | 端到端能跑通 |
| 数据测试 | 唯一、完整、及时、平衡 | 关键规则通过并留存结果 |
| 性能测试 | 扫描量、执行时长、并发和资源 | 在容量预算内且可扩展 |
| 灰度 | 小范围业务与新旧结果对照 | 差异可解释，问题可回滚 |
| 验收 | 业务样例、指标和操作流程 | 验收人签字或有系统记录 |

灰度阶段应保留新旧链路对照。差异不能简单要求“完全一致”，因为修复本身可能改变结果；正确做法是对每类差异给出原因、影响和审批。

- **处理过程**：建立生产查询回放集与加权评分，按功能、性能、成本、风险和迁移工作量做 PoC。实施时把“PoC 覆盖真实查询、并发、权限、故障恢复和升级”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例评审保留不选方案的理由和退出条件，而不是只记录最终赢家。验收至少同时看主指标、基准任务、现状基线、失败案例和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把业务约束、总拥有成本、团队能力、迁移风险和退出策略放进同一决策框架，避免用功能清单和短期演示做技术选型。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

- **为什么要做：** 在开发报表或模型前，把对象、粒度、时间、状态和排除条件形成可执行的共同定义。在本场景里，核心风险还包括口径变更缺少影响分析，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：质量规则、问题工单及其在标准定义前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注rule_id与issue_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 两个团队都声称在统计同一主题，但一行数据代表的业务对象不同，时间字段也不同。初看时，元数据平台与质量平台的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 指标字典版本、源系统样例、两条计算链路、差异清单和业务确认记录。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“业务数据负责人”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“数据治理成熟度评估与路线图制定”的当前定义并记录版本；第二步用质量规则明细核对元数据平台到质量平台的关联；第三步按规则类型与严重等级做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察资产完整率和护栏指标平均修复时长。
- **行动与护栏：** 先冻结本期对象范围，再分别按源系统口径和目标口径重算，对每一类差异写明原因和暂定处理。专题检查项“记录被否决方案、决策假设、退出策略和复审日期”被写成发布门禁，口径未确认时只发布差异分析，不把任一结果包装成正式经营指标。
- **失败路径：** 用平均值掩盖差异，或直接把对不上的明细删掉。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“数据治理成熟度评估与路线图制定”时，先验证三年 TCO、人员投入和沉淀资产，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由业务数据负责人在明确时限内，根据资产完整率、平均修复时长和问题分级明确决定继续、回退、补查还是转人工。 若口径变更缺少影响分析或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从数据治理成熟度评估与路线图制定回到可核对明细

```sql
-- 数据治理成熟度评估与路线图制定：字段血缘与影响范围
WITH changed_columns AS (
  SELECT column_name
  FROM information_schema.columns
  WHERE table_schema = :source_schema
    AND table_name = :source_table
    AND last_altered_at >= :change_time
),
downstream_assets AS (
  SELECT
    asset_id,
    asset_name,
    asset_type,
    owner_name,
    criticality,
    last_used_at
  FROM metadata_asset_relation
  WHERE upstream_asset_id = :source_asset_id
    AND relation_status = 'active'
)
SELECT
  d.asset_id,
  d.asset_name,
  d.asset_type,
  d.owner_name,
  d.criticality,
  d.last_used_at,
  COUNT(c.column_name) AS changed_column_cnt,
  CASE
    WHEN d.criticality IN ('core', 'regulated') THEN 'block_release'
    WHEN d.last_used_at >= CURRENT_DATE - INTERVAL '7 days' THEN 'notify_owner'
    ELSE 'register_review'
  END AS required_action
FROM downstream_assets d
CROSS JOIN changed_columns c
GROUP BY d.asset_id, d.asset_name, d.asset_type, d.owner_name, d.criticality, d.last_used_at
ORDER BY
  CASE WHEN d.criticality IN ('core', 'regulated') THEN 0 ELSE 1 END,
  d.last_used_at DESC;

-- 目标：变更前识别 数据目录、元数据平台、质量平台 之后的所有结果与消费者。
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把数据治理成熟度评估与路线图制定的验收证据写成门禁

```python
import json
from pathlib import Path


def build_evidence_manifest(
    subject: str,
    scope: dict,
    checks: dict,
    samples: list[dict],
    owner: str,
) -> dict:
    failed = [name for name, passed in checks.items() if not passed]
    return {
        "subject": subject,
        "scope": scope,
        "checks": checks,
        "failed_checks": failed,
        "sample_evidence": samples[:5],
        "owner": owner,
        "decision": "block" if failed else "review",
        "manual_questions": [
            "每一项失败是否已回到原始记录",
            "对象、时间和状态是否与指标字典一致",
            "回滚或修复后是否重新完成对账",
        ],
    }


manifest = build_evidence_manifest(
    subject="数据治理成熟度评估与路线图制定",
    scope={"systems": ["数据目录","元数据平台","质量平台","权限系统"]},
    checks={"definition_frozen": False, "reconciled": False},
    samples=[],
    owner="数据治理办公室",
)
Path("release-evidence.json").write_text(
    json.dumps(manifest, ensure_ascii=False, indent=2),
    encoding="utf-8",
)
print(manifest["decision"])
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。

### 四个案例共用的验收清单

| 验证面 | 发布前问题 | 证据 | 不通过时 |
| --- | --- | --- | --- |
| 对象与粒度 | 一行数据代表数据资产、事件、快照还是结果 | 主键、版本、有效时间和边界样本 | 阻断 |
| 时间语义 | 业务发生、数据可见、决策采用是否混用 | check_time、入仓时间、行动时间轴 | 阻断 |
| 指标口径 | 规则通过率的分子、分母和排除项是否冻结 | 指标字典、SQL、对账结果 | 阻断正式指标 |
| 状态与关联 | 资产盘点 → 标准定义 → 责任认领 → 规则设计是否可达且可追溯 | 状态机、明细、操作日志 | 阻断关键链路 |
| 权限与最小字段 | 派生表、导出和临时授权是否扩大访问范围 | 分类分级、字段血缘、访问日志 | 阻断导出 |
| 恢复与审计 | 失败后能否定位影响范围并幂等重跑 | 参数、版本、分区清单、补数对账 | 阻断发布 |
