# 金融行业实践

> [!tip] 分析目标
> 讨论“金融行业实践”时，最容易犯的错误是直接从工具或报表开始。更有用的顺序是：先看业务链条，再找可观察指标，随后确认数据粒度，最后才选择 SQL、模型或平台组件。本文按这个顺序给出可执行方案和常见的失败样本。

## 1. 把主题翻译成可验证的问题

“金融行业实践”不能直接等同于“做一张趋势图”。一个可执行的分析问题至少包含对象、时间、比较基准和行动：

> 在【观察周期】内，对【有效对象】按【机构、产品、渠道】比较【风险拦截率】与【客户流失率】，判断变化来自结构、行为还是数据口径，并验证【策略动作】是否带来可解释的增量。

在金融行业场景中，用户行为、交易结果和策略曝光经常来自不同系统。先画数据流：

核心银行系统 → 信贷系统 → 支付清算系统 → 反洗钱系统 → CRM → 数据仓库

图中至少要有三个标记：业务事件发生时间、数据可见时间、策略或行动时间。只有三者分开，后续才能判断问题发生在业务、链路还是观察窗口。

## 2. 指标定义与分母检查

| 专题观测面 | 需要回答的问题 | 关键证据 | 判定与动作 |
| --- | --- | --- | --- |
| 资产（本标题优先） | 哪些数据影响关键决策、监管和资金 | 资产清单、等级、消费者和故障历史 | 先从高价值资产开始 |
| 运营 | 治理是否进入发布、事件和绩效流程 | 评审、复盘、成熟度和采用记录 | 没有业务使用的治理活动应重做 |
| 责任 | 谁定义、谁生产、谁使用、谁批准变更 | RACI、数据 steward 和升级路径 | 责任必须带决策权与时限 |
| 规则 | 哪些标准和质量规则需要自动执行 | 规则、阈值、样本、工单和豁免 | 规则失败要对应动作 |

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 活跃客户数 | `COUNT(DISTINCT active_customer_id)`（视图字段 `active_customers`） | 机构、产品、渠道 | 不混用测试、撤销和跨期状态；与“金融行业实践”相关时还要补充主题筛选 |
| 资产规模 | `SUM(end_of_day_balance)`（视图字段 `aum`） | 产品、渠道、客户等级 | 不混用测试、撤销和跨期状态；与“金融行业实践”相关时还要补充主题筛选 |
| 逾期率 | `SUM(overdue_principal) / SUM(outstanding_principal)`（视图字段 `overdue_rate`） | 渠道、客户等级、风险等级 | 不混用测试、撤销和跨期状态；与“金融行业实践”相关时还要补充主题筛选 |
| 风险拦截率 | `COUNT(DISTINCT blocked_event_id) / COUNT(DISTINCT risk_event_id)`（视图字段 `block_rate`） | 客户等级、风险等级 | 不混用测试、撤销和跨期状态；与“金融行业实践”相关时还要补充主题筛选 |

针对“金融行业实践”，建议分别定义诊断指标、结果指标和护栏指标：

- **诊断指标**用于定位流程，例如曝光、有效访问、符合条件对象数和异常节点。
- **结果指标**用于判断是否改善，例如转化、留存、客单、毛利或处理时长。
- **护栏指标**用于防止局部优化伤害整体，例如退款、投诉、成本、公平性和长期留存。

每次计算都问四个问题：分母是谁、对象何时进入分母、例外状态怎么处理、窗口是否足够覆盖行为完成。尤其是敏感数据越权访问；授信金额与借据余额混用；产品口径随组织调整无法比较，任何一项没有解释清楚，指标都可能“看起来合理但无法决策”。

## 3. 方法选择：描述、诊断、预测还是因果

| 目标 | 适合的方法 | 需要的证据 | 不要混淆 |
| --- | --- | --- | --- |
| 描述现状 | 趋势、结构、同期群 | 完整口径、稳定时间窗 | 描述不等于原因 |
| 定位异常 | 分层、贡献度、漏斗、异常检测 | 原始事件、基线和质量检查 | 排名靠前不等于因果 |
| 预测未来 | 时间序列、回归、机器学习 | 时间切分验证、误差成本 | 离线准确率不等于业务收益 |
| 评估策略 | A/B、灰度、准实验 | 对照组、样本量、护栏指标 | 上线前后对比容易混入季节和选择偏差 |

如果问题只是“发生了什么”，先别急着建模；如果问题涉及“采取某策略会怎样”，就必须讨论反事实和识别条件。围绕“金融行业实践”，应把观察分析、预测和因果评估的产出分开标注。

## 4. 案例一：华北某工业集团

### 案例 1：华北某工业集团的“金融行业实践”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“金融行业实践”映射到“数据治理制度、责任与运营”中的资产，而不是泛泛讨论概念。
- **触发事件**：各工厂治理成熟度差异大，总部统一规则难以落地。
- **业务与数据范围**：工厂资产、系统、人员、问题、规则执行和本地流程。数据侧重点采集资产清单、等级、消费者和故障历史，并与核心银行系统、信贷系统、支付清算系统中的时间、状态和责任人信息对齐。
- **需要回答的问题**：哪些数据影响关键决策、监管和资金。
- **关键障碍**：总部按同一优先级推广全部规则，缺少本地负责人和差异化路径。同时要防止敏感数据越权访问把表面指标带偏。
- **处理过程**：按风险和场景分级，建立总部标准、本地执行、例外审批和成熟度评审。实施时把“血缘、版本和问题工单支持影响分析与审计”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例机制兼顾统一控制与现场可执行性。验收至少同时看主指标、资产清单、等级、消费者和故障历史和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“围绕关键数据资产建立标准、责任、质量、安全、血缘、变更和问题闭环，让治理机制进入日常交付。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

落地时建议先把一个总指标拆成可行动的树：

```text
金融行业实践｜从总量到单条证据
├── ① 同期基线：先排除节假日、活动和口径切换
├── ② 结构贡献：按机构、产品、渠道比较增量和抵消
├── ③ 状态漏斗：开户 → 交易或授信 → 风险监测 → 结算
├── ④ 记录回查：正常、边界、异常各抽 N 条
└── ⑤ 闭环验证：客户流失率与护栏指标同时恢复才算解决
```

如果某一分支变化最大，再进入下一层，而不是一开始就按十几个维度切碎。每个分层结果都应同时报告样本量，避免小样本的极端比例抢走注意力。

## 5. SQL：计算趋势、结构和贡献度

### 趋势、结构与贡献度诊断

```sql
-- 金融行业实践：分位对比诊断（客户等级 × 机构）
WITH scoped AS (
  SELECT
    customer_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_finance_event
  WHERE event_time >= DATE '2026-03-01'
    AND event_time <  DATE '2026-06-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '活跃客户数' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

示例 SQL 只表达计算逻辑。实际实施应加入分区条件、业务状态过滤、时区和主题范围，并在结果中保留口径版本。

## 6. 案例二：华东某集团数据治理办公室

### 案例 2：华东某集团数据治理办公室的“金融行业实践”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“金融行业实践”映射到“数据治理制度、责任与运营”中的运营，而不是泛泛讨论概念。
- **触发事件**：治理制度发布一年，但新项目仍绕过标准并持续产生重复指标。
- **业务与数据范围**：项目流程、指标清单、评审记录、责任人、问题工单和系统门禁。数据侧重点采集评审、复盘、成熟度和采用记录，并与核心银行系统、信贷系统、支付清算系统中的时间、状态和责任人信息对齐。
- **需要回答的问题**：治理是否进入发布、事件和绩效流程。
- **关键障碍**：治理只靠培训和文档，没有进入立项、开发和发布流程。同时要防止授信金额与借据余额混用把表面指标带偏。
- **处理过程**：把资产登记、口径评审、质量门禁和安全检查嵌入项目里程碑，关键资产设置联合负责人。实施时把“治理成效由风险、返工、故障和采用衡量”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例治理用绕过率、重复指标、返工和问题闭环衡量制度是否生效。验收至少同时看主指标、评审、复盘、成熟度和采用记录和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“围绕关键数据资产建立标准、责任、质量、安全、血缘、变更和问题闭环，让治理机制进入日常交付。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

当业务方要求“解释为什么下降”时，可以按下面顺序回答：

1. 先确认下降是否真实存在，排查采集、任务、维表和状态映射。
2. 把变化拆成对象数量、行为强度和结构占比。
3. 找到贡献最大的分组，但保留其他分组的抵消效应。
4. 抽取正负样本回查业务事件和操作日志。
5. 把尚不能证明的解释标为假设，并设计下一轮验证。

    "治理成效由风险、返工、故障和采用衡量"

def validate_asset(item: DataAsset, checks: list[str]) -> list[str]:

        failures.append("owner_chain_incomplete")
    if item.criticality not in {"critical", "high", "medium", "low"}:
        failures.append("risk_level_invalid")
    if not item.consumers:
        failures.append("consumer_list_missing")
    if len(item.controls) < len(checks):
        failures.append("controls_do_not_cover_checks")
    return failures

print({"policy": POLICY_ID, "failures": validate_asset(asset, governance_checks)})

## 8. 异常、偏差与常见误区

- **辛普森悖论**：总体改善但每个分组都变差，可能由对象结构变化造成。
- **幸存者偏差**：只分析完成流程的对象，忽略中途流失和中止。
- **分母漂移**：渠道口径、登录状态、版本或活动范围变化，改变可比性。
- **回传延迟**：当天数据未回补，导致近期效果被系统性低估。
- **多重比较**：反复寻找显著分组，实际只是随机波动。
- **行动偏差**：只报告支持既定方案的结果，忽略反例和护栏指标。

围绕“金融行业实践”，应预先写出至少三条反例检查。比如数据质量异常是否与业务变化分开、方案是否说明了成本、边界和停止条件，以及 上线后是否有人负责观察和复盘。

## 9. 第三个案例：华南某保险公司

### 案例 3：华南某保险公司的“金融行业实践”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **触发事件**：监管口径变更后多个报表难以在期限内完成影响分析。
- **业务与数据范围**：指标、SQL、字段血缘、报表、责任人、版本和变更历史。数据侧重点采集RACI、数据 steward 和升级路径，并与核心银行系统、信贷系统、支付清算系统中的时间、状态和责任人信息对齐。

### 案例 4：金融行业实践上线前的质量门禁

某组织希望用“金融行业实践”支持一次真实决策，但在取数与评审阶段发现，常规日期下结果看起来正常，一旦遇到空值、重复、跨期、撤销或历史归属，报表口径便无法解释。这个案例因此从问题定义重新开始。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 把关键质量规则、阈值、例外审批、阻断动作和复核人写入发布流程。在本场景里，核心风险还包括风险规则版本不可追溯，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。

- **关键异常或争议：** 常规日期下结果看起来正常，一旦遇到空值、重复、跨期、撤销或历史归属，报表口径便无法解释。初看时，支付清算系统与反洗钱系统的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 五类边界样本、规则命中率、趋势对比、豁免记录、责任人、阻断结果和复盘工单。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“产品团队”确认什么结果可以进入下一步。

- **可迁移结论：** 处理“金融行业实践”时，先验证资产清单、等级、消费者和故障历史，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

- **可迁移结论：** 处理“金融行业实践”时，先验证规则、阈值、样本、工单和豁免，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

### 扩展代码一：从金融行业实践回到可核对明细

```sql
-- 金融行业实践：发布前质量画像
SELECT
  'subject' AS subject_key,
  stat_date,
  COUNT(*) AS row_cnt,
  COUNT(DISTINCT event_id) AS distinct_event_cnt,
  SUM(CASE WHEN event_id IS NULL THEN 1 ELSE 0 END) AS null_event_cnt,
  SUM(CASE WHEN event_time < business_time THEN 1 ELSE 0 END) AS time_reverse_cnt,
  SUM(CASE WHEN status NOT IN ('valid', 'completed', 'cancelled') THEN 1 ELSE 0 END) AS invalid_status_cnt,
  ROUND(COUNT(*) * 1.0 / NULLIF(COUNT(DISTINCT event_id), 0), 4) AS duplication_ratio
FROM fact_finance_event
WHERE stat_date BETWEEN :start_date AND :end_date
GROUP BY stat_date
HAVING SUM(CASE WHEN event_id IS NULL THEN 1 ELSE 0 END) > 0
    OR SUM(CASE WHEN event_time < business_time THEN 1 ELSE 0 END) > 0
    OR COUNT(*) <> COUNT(DISTINCT event_id)
ORDER BY stat_date;

-- 至少人工核对一次：客户号脱敏且跨系统映射一致；借贷与支付金额平衡；交易时间与入账时间区分。
```

### 扩展代码二：把金融行业实践的验收证据写成门禁

```python
from datetime import date
from hashlib import sha256

import pandas as pd

SUBJECT = "金融行业实践"
BLOCKING_RULES = ["客户号脱敏且跨系统映射一致","借贷与支付金额平衡","交易时间与入账时间区分"]


def validate_release(frame: pd.DataFrame, start: date, end: date) -> dict:
    scoped = frame.loc[
        frame["event_date"].between(pd.Timestamp(start), pd.Timestamp(end))
        & (frame["subject_key"] == "subject")
    ].copy()
    checks = {
        "has_rows": len(scoped) > 0,
        "event_id_unique": not scoped["event_id"].duplicated().any(),
        "entity_key_complete": scoped["entity_key"].notna().all(),
        "event_time_present": scoped["event_time"].notna().all(),
        "scope_matches": scoped["subject_key"].nunique() == 1,
    }
    payload = f"{SUBJECT}|{start}|{end}|{len(scoped)}|{sorted(checks.items())}"
    return {
        "subject": SUBJECT,
        "rows": len(scoped),
        "checks": checks,
        "blocking_rules": BLOCKING_RULES,
        "release_allowed": all(checks.values()),
        "evidence_hash": sha256(payload.encode("utf-8")).hexdigest(),
    }
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
