# 数据空间与可信数据流通

> [!tip] 分析目标
> 把“数据空间与可信数据流通”放进数据标准、元数据、主数据、质量规则、权限审计、血缘和问题闭环，真正困难的通常不是解释名词，而是把它变成一条能被核对、能被复现、也能推动行动的工程链路。本文不追求堆满概念，而是围绕这个主题拆出业务对象、数据粒度、典型故障、代码验证和验收方式。

## 1. 把主题翻译成可验证的问题

“数据空间与可信数据流通”不能直接等同于“做一张趋势图”。一个可执行的分析问题至少包含对象、时间、比较基准和行动：

> 在【观察周期】内，对【有效对象】按【业务域、资产层级、规则类型】比较【问题闭环率】与【资产完整率】，判断变化来自结构、行为还是数据口径，并验证【策略动作】是否带来可解释的增量。

在数据治理与数据管理场景中，用户行为、交易结果和策略曝光经常来自不同系统。先画数据流：

数据目录 → 元数据平台 → 质量平台 → 权限系统 → 调度平台 → 工单系统

图中至少要有三个标记：业务事件发生时间、数据可见时间、策略或行动时间。只有三者分开，后续才能判断问题发生在业务、链路还是观察窗口。

## 2. 指标定义与分母检查

| 专题观测面 | 需要回答的问题 | 关键证据 | 判定与动作 |
| --- | --- | --- | --- |
| 资产（本标题优先） | 哪些数据影响关键决策、监管和资金 | 资产清单、等级、消费者和故障历史 | 先从高价值资产开始 |
| 运营 | 治理是否进入发布、事件和绩效流程 | 评审、复盘、成熟度和采用记录 | 没有业务使用的治理活动应重做 |
| 责任 | 谁定义、谁生产、谁使用、谁批准变更 | RACI、数据 steward 和升级路径 | 责任必须带决策权与时限 |
| 规则 | 哪些标准和质量规则需要自动执行 | 规则、阈值、样本、工单和豁免 | 规则失败要对应动作 |

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 规则通过率 | `COUNT(DISTINCT passed_rule_id) / COUNT(DISTINCT executed_rule_id)`（视图字段 `rule_pass_rate`） | 业务域、资产层级、规则类型 | 不混用测试、撤销和跨期状态；与“数据空间与可信数据流通”相关时还要补充主题筛选 |
| 问题闭环率 | `COUNT(DISTINCT closed_issue_id) / COUNT(DISTINCT raised_issue_id)`（视图字段 `issue_closure_rate`） | 资产层级、规则类型、责任团队 | 不混用测试、撤销和跨期状态；与“数据空间与可信数据流通”相关时还要补充主题筛选 |
| 资产完整率 | `COUNT(DISTINCT complete_asset_id) / COUNT(DISTINCT asset_id)`（视图字段 `asset_completeness`） | 规则类型、责任团队、严重等级 | 不混用测试、撤销和跨期状态；与“数据空间与可信数据流通”相关时还要补充主题筛选 |
| 血缘覆盖率 | `COUNT(DISTINCT lineage_asset_id) / COUNT(DISTINCT critical_asset_id)`（视图字段 `lineage_coverage`） | 责任团队、严重等级 | 不混用测试、撤销和跨期状态；与“数据空间与可信数据流通”相关时还要补充主题筛选 |

针对“数据空间与可信数据流通”，建议分别定义诊断指标、结果指标和护栏指标：

- **诊断指标**用于定位流程，例如曝光、有效访问、符合条件对象数和异常节点。
- **结果指标**用于判断是否改善，例如转化、留存、客单、毛利或处理时长。
- **护栏指标**用于防止局部优化伤害整体，例如退款、投诉、成本、公平性和长期留存。

每次计算都问四个问题：分母是谁、对象何时进入分母、例外状态怎么处理、窗口是否足够覆盖行为完成。尤其是资产没有负责人；规则只告警不闭环；口径变更缺少影响分析，任何一项没有解释清楚，指标都可能“看起来合理但无法决策”。

## 3. 方法选择：描述、诊断、预测还是因果

| 目标 | 适合的方法 | 需要的证据 | 不要混淆 |
| --- | --- | --- | --- |
| 描述现状 | 趋势、结构、同期群 | 完整口径、稳定时间窗 | 描述不等于原因 |
| 定位异常 | 分层、贡献度、漏斗、异常检测 | 原始事件、基线和质量检查 | 排名靠前不等于因果 |
| 预测未来 | 时间序列、回归、机器学习 | 时间切分验证、误差成本 | 离线准确率不等于业务收益 |
| 评估策略 | A/B、灰度、准实验 | 对照组、样本量、护栏指标 | 上线前后对比容易混入季节和选择偏差 |

如果问题只是“发生了什么”，先别急着建模；如果问题涉及“采取某策略会怎样”，就必须讨论反事实和识别条件。围绕“数据空间与可信数据流通”，应把观察分析、预测和因果评估的产出分开标注。

## 4. 案例一：华东某集团数据治理办公室

### 案例 1：华东某集团数据治理办公室的“数据空间与可信数据流通”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“数据空间与可信数据流通”映射到“数据治理制度、责任与运营”中的资产，而不是泛泛讨论概念。
- **触发事件**：治理制度发布一年，但新项目仍绕过标准并持续产生重复指标。
- **业务与数据范围**：项目流程、指标清单、评审记录、责任人、问题工单和系统门禁。数据侧重点采集资产清单、等级、消费者和故障历史，并与数据目录、元数据平台、质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：哪些数据影响关键决策、监管和资金。
- **关键障碍**：治理只靠培训和文档，没有进入立项、开发和发布流程。同时要防止资产没有负责人把表面指标带偏。
- **处理过程**：把资产登记、口径评审、质量门禁和安全检查嵌入项目里程碑，关键资产设置联合负责人。实施时把“血缘、版本和问题工单支持影响分析与审计”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例治理用绕过率、重复指标、返工和问题闭环衡量制度是否生效。验收至少同时看主指标、资产清单、等级、消费者和故障历史和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“围绕关键数据资产建立标准、责任、质量、安全、血缘、变更和问题闭环，让治理机制进入日常交付。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

落地时建议先把一个总指标拆成可行动的树：

```text
数据空间与可信数据流通｜从总量到单条证据
├── ① 同期基线：先排除节假日、活动和口径切换
├── ② 结构贡献：按业务域、资产层级、规则类型比较增量和抵消
├── ③ 状态漏斗：标准定义 → 责任认领 → 规则设计 → 执行监控
├── ④ 记录回查：正常、边界、异常各抽 N 条
└── ⑤ 闭环验证：资产完整率与护栏指标同时恢复才算解决
```

如果某一分支变化最大，再进入下一层，而不是一开始就按十几个维度切碎。每个分层结果都应同时报告样本量，避免小样本的极端比例抢走注意力。

## 5. SQL：计算趋势、结构和贡献度

### 趋势、结构与贡献度诊断

```sql
-- 数据空间与可信数据流通：分位对比诊断（资产层级 × 责任团队）
WITH scoped AS (
  SELECT
    asset_id AS entity_key,
    event_id,
    check_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_data_quality_result
  WHERE check_time >= DATE '2026-03-01'
    AND check_time <  DATE '2026-06-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '血缘覆盖率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

示例 SQL 只表达计算逻辑。实际实施应加入分区条件、业务状态过滤、时区和主题范围，并在结果中保留口径版本。

## 6. 案例二：华南某保险公司

### 案例 2：华南某保险公司的“数据空间与可信数据流通”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“数据空间与可信数据流通”映射到“数据治理制度、责任与运营”中的运营，而不是泛泛讨论概念。
- **触发事件**：监管口径变更后多个报表难以在期限内完成影响分析。
- **业务与数据范围**：指标、SQL、字段血缘、报表、责任人、版本和变更历史。数据侧重点采集评审、复盘、成熟度和采用记录，并与数据目录、元数据平台、质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：治理是否进入发布、事件和绩效流程。
- **关键障碍**：制度有流程，但血缘和指标定义不可追踪，依赖专家回忆。同时要防止规则只告警不闭环把表面指标带偏。
- **处理过程**：建立指标到字段的可追溯链路，变更模板自动生成下游清单和验证任务。实施时把“治理成效由风险、返工、故障和采用衡量”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例项目把影响分析从人工搜索转为可审计流程。验收至少同时看主指标、评审、复盘、成熟度和采用记录和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“围绕关键数据资产建立标准、责任、质量、安全、血缘、变更和问题闭环，让治理机制进入日常交付。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

当业务方要求“解释为什么下降”时，可以按下面顺序回答：

1. 先确认下降是否真实存在，排查采集、任务、维表和状态映射。
2. 把变化拆成对象数量、行为强度和结构占比。
3. 找到贡献最大的分组，但保留其他分组的抵消效应。
4. 抽取正负样本回查业务事件和操作日志。
5. 把尚不能证明的解释标为假设，并设计下一轮验证。

### 专题验证代码

```python
from dataclasses import dataclass

TOPIC = "数据空间与可信数据流通"
POLICY_ID = "g_data_governance_148dfwi"

@dataclass(frozen=True)
class DataAsset:
    name: str
    criticality: str
    owner: str
    steward: str
    consumers: tuple[str, ...]
    controls: tuple[str, ...]
    last_reviewed: str

asset = DataAsset(
    name="enterprise_metric_snapshot",
    criticality="high",
    owner="business-domain-owner",
    steward="data-governance-steward",
    consumers=("management-reporting", "risk-monitor"),
    controls=("definition-version", "quality-gate", "lineage", "access-review"),
    last_reviewed="2026-11-06",
)

governance_checks = [
    "关键资产具有唯一负责人、业务定义、消费者和风险等级",
    "标准、质量和安全规则进入项目与发布流程",
    "血缘、版本和问题工单支持影响分析与审计",
    "治理成效由风险、返工、故障和采用衡量"
]

def validate_asset(item: DataAsset, checks: list[str]) -> list[str]:
    failures = []
    if not item.owner or not item.steward:
        failures.append("owner_chain_incomplete")
    if item.criticality not in {"critical", "high", "medium", "low"}:
        failures.append("risk_level_invalid")
    if not item.consumers:
        failures.append("consumer_list_missing")
    if len(item.controls) < len(checks):
        failures.append("controls_do_not_cover_checks")
    return failures

print({"policy": POLICY_ID, "failures": validate_asset(asset, governance_checks)})

# 规则必须绑定严重等级、阈值依据、责任人和豁免期限；问题关闭前保留样本、影响范围和复核证据。
```

## 8. 异常、偏差与常见误区

- **辛普森悖论**：总体改善但每个分组都变差，可能由对象结构变化造成。
- **幸存者偏差**：只分析完成流程的对象，忽略中途流失和中止。
- **分母漂移**：渠道口径、登录状态、版本或活动范围变化，改变可比性。
- **回传延迟**：当天数据未回补，导致近期效果被系统性低估。
- **多重比较**：反复寻找显著分组，实际只是随机波动。
- **行动偏差**：只报告支持既定方案的结果，忽略反例和护栏指标。

围绕“数据空间与可信数据流通”，应预先写出至少三条反例检查。比如数据质量异常是否与业务变化分开、方案是否说明了成本、边界和停止条件，以及 上线后是否有人负责观察和复盘。

## 9. 第三个案例：华北某工业集团

### 案例 3：华北某工业集团的“数据空间与可信数据流通”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“数据空间与可信数据流通”映射到“数据治理制度、责任与运营”中的责任，而不是泛泛讨论概念。
- **触发事件**：各工厂治理成熟度差异大，总部统一规则难以落地。
- **业务与数据范围**：工厂资产、系统、人员、问题、规则执行和本地流程。数据侧重点采集RACI、数据 steward 和升级路径，并与数据目录、元数据平台、质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：谁定义、谁生产、谁使用、谁批准变更。
- **关键障碍**：总部按同一优先级推广全部规则，缺少本地负责人和差异化路径。同时要防止口径变更缺少影响分析把表面指标带偏。
- **处理过程**：按风险和场景分级，建立总部标准、本地执行、例外审批和成熟度评审。实施时把“关键资产具有唯一负责人、业务定义、消费者和风险等级”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例机制兼顾统一控制与现场可执行性。验收至少同时看主指标、RACI、数据 steward 和升级路径和一次故障回放，不能只截取优化后最快的一次结果。

- **行动与护栏：** 按任务拆分数据集与角色，使用最小字段和临时授权，发布前检查派生表与导出是否出现敏感扩散。专题检查项“治理成效由风险、返工、故障和采用衡量”被写成发布门禁，高风险字段缺少授权、脱敏或审计时不进入分析环境，紧急访问必须到期自动回收。
- **失败路径：** 把“内网可访问”当成“业务已授权”，或者用永久大权限账号支撑临时分析。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“数据空间与可信数据流通”时，先验证规则、阈值、样本、工单和豁免，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由数据分析在明确时限内，根据平均修复时长、问题闭环率和敏感字段访问可审计决定继续、回退、补查还是转人工。 若数据目录与真实血缘脱节或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从数据空间与可信数据流通回到可核对明细

```sql
-- 数据空间与可信数据流通：源表与结果表按对象对账
WITH source_side AS (
  SELECT
    asset_id AS entity_key,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum
  FROM fact_data_quality_result
  WHERE check_time >= :start_date
    AND check_time <  :end_date
    AND subject_key = 'subject'
    AND is_deleted = 0
  GROUP BY asset_id
),
result_side AS (
  SELECT
    asset_id AS entity_key,
    event_cnt,
    metric_sum
  FROM fact_data_quality_result_result
  WHERE stat_date BETWEEN :start_date AND :end_date
    AND subject_key = 'subject'
)
SELECT
  COALESCE(s.entity_key, r.entity_key) AS entity_key,
  s.event_cnt AS source_event_cnt,
  r.event_cnt AS result_event_cnt,
  s.metric_sum AS source_metric_sum,
  r.metric_sum AS result_metric_sum,
  COALESCE(r.metric_sum, 0) - COALESCE(s.metric_sum, 0) AS metric_diff
FROM source_side s
FULL OUTER JOIN result_side r USING (entity_key)
WHERE ABS(COALESCE(r.metric_sum, 0) - COALESCE(s.metric_sum, 0)) > 0
   OR COALESCE(s.event_cnt, 0) <> COALESCE(r.event_cnt, 0)
ORDER BY ABS(metric_diff) DESC;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把数据空间与可信数据流通的验收证据写成门禁

```python
import pandas as pd

KEY = ["entity_key", "event_id"]
AMOUNT_COLUMNS = ["metric_value", "adjustment_value"]


def reconcile(source: pd.DataFrame, result: pd.DataFrame) -> pd.DataFrame:
    def aggregate(frame: pd.DataFrame, side: str) -> pd.DataFrame:
        grouped = (
            frame.groupby("entity_key", dropna=False)
            .agg(
                event_cnt=("event_id", "nunique"),
                metric_sum=("metric_value", "sum"),
                adjustment_sum=("adjustment_value", "sum"),
            )
            .reset_index()
        )
        return grouped.rename(columns={
            "event_cnt": f"{side}_event_cnt",
            "metric_sum": f"{side}_metric_sum",
            "adjustment_sum": f"{side}_adjustment_sum",
        })

    compared = aggregate(source, "source").merge(
        aggregate(result, "result"),
        on="entity_key",
        how="outer",
    )
    compared["metric_diff"] = (
        compared["result_metric_sum"].fillna(0)
        - compared["source_metric_sum"].fillna(0)
    )
    compared["event_diff"] = (
        compared["result_event_cnt"].fillna(0)
        - compared["source_event_cnt"].fillna(0)
    )
    compared["exception"] = compared.apply(
        lambda row: "missing_result" if pd.isna(row["result_metric_sum"])
        else "unexpected_result" if pd.isna(row["source_metric_sum"])
        else "count_diff" if row["event_diff"] != 0
        else "amount_diff",
        axis=1,
    )
    return compared.loc[
        (compared["metric_diff"].abs() > 0) | (compared["event_diff"] != 0)
    ].sort_values("metric_diff", key=lambda values: values.abs(), ascending=False)
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
