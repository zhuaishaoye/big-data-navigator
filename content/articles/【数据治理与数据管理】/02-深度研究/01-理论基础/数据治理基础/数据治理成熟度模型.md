# 数据治理成熟度模型

> [!tip] 分析目标
> 如果只记住“数据治理成熟度模型”的定义，遇到真实数据时仍然很难行动。本文把它拆成五个可检查问题：谁在使用、流程在哪里变化、数据一行代表什么、异常如何发现、上线后用哪个指标验收。每个部分都配一个工作案例或代码片段。

## 1. 把主题翻译成可验证的问题

“数据治理成熟度模型”不能直接等同于“做一张趋势图”。一个可执行的分析问题至少包含对象、时间、比较基准和行动：

> 在【观察周期】内，对【有效对象】按【业务域、资产层级、规则类型】比较【血缘覆盖率】与【平均修复时长】，判断变化来自结构、行为还是数据口径，并验证【策略动作】是否带来可解释的增量。

在数据治理与数据管理场景中，用户行为、交易结果和策略曝光经常来自不同系统。先画数据流：

数据目录 → 元数据平台 → 质量平台 → 权限系统 → 调度平台 → 工单系统

图中至少要有三个标记：业务事件发生时间、数据可见时间、策略或行动时间。只有三者分开，后续才能判断问题发生在业务、链路还是观察窗口。

## 2. 指标定义与分母检查

| 专题观测面 | 需要回答的问题 | 关键证据 | 判定与动作 |
| --- | --- | --- | --- |
| 运营（本标题优先） | 治理是否进入发布、事件和绩效流程 | 评审、复盘、成熟度和采用记录 | 没有业务使用的治理活动应重做 |
| 规则 | 哪些标准和质量规则需要自动执行 | 规则、阈值、样本、工单和豁免 | 规则失败要对应动作 |
| 责任 | 谁定义、谁生产、谁使用、谁批准变更 | RACI、数据 steward 和升级路径 | 责任必须带决策权与时限 |
| 资产 | 哪些数据影响关键决策、监管和资金 | 资产清单、等级、消费者和故障历史 | 先从高价值资产开始 |

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 规则通过率 | `COUNT(DISTINCT passed_rule_id) / COUNT(DISTINCT executed_rule_id)`（视图字段 `rule_pass_rate`） | 业务域、资产层级、规则类型 | 不混用测试、撤销和跨期状态；与“数据治理成熟度模型”相关时还要补充主题筛选 |
| 问题闭环率 | `COUNT(DISTINCT closed_issue_id) / COUNT(DISTINCT raised_issue_id)`（视图字段 `issue_closure_rate`） | 资产层级、规则类型、责任团队 | 不混用测试、撤销和跨期状态；与“数据治理成熟度模型”相关时还要补充主题筛选 |
| 资产完整率 | `COUNT(DISTINCT complete_asset_id) / COUNT(DISTINCT asset_id)`（视图字段 `asset_completeness`） | 规则类型、责任团队、严重等级 | 不混用测试、撤销和跨期状态；与“数据治理成熟度模型”相关时还要补充主题筛选 |
| 血缘覆盖率 | `COUNT(DISTINCT lineage_asset_id) / COUNT(DISTINCT critical_asset_id)`（视图字段 `lineage_coverage`） | 责任团队、严重等级 | 不混用测试、撤销和跨期状态；与“数据治理成熟度模型”相关时还要补充主题筛选 |

针对“数据治理成熟度模型”，建议分别定义诊断指标、结果指标和护栏指标：

- **诊断指标**用于定位流程，例如曝光、有效访问、符合条件对象数和异常节点。
- **结果指标**用于判断是否改善，例如转化、留存、客单、毛利或处理时长。
- **护栏指标**用于防止局部优化伤害整体，例如退款、投诉、成本、公平性和长期留存。

每次计算都问四个问题：分母是谁、对象何时进入分母、例外状态怎么处理、窗口是否足够覆盖行为完成。尤其是资产没有负责人；规则只告警不闭环；口径变更缺少影响分析，任何一项没有解释清楚，指标都可能“看起来合理但无法决策”。

## 3. 方法选择：描述、诊断、预测还是因果

| 目标 | 适合的方法 | 需要的证据 | 不要混淆 |
| --- | --- | --- | --- |
| 描述现状 | 趋势、结构、同期群 | 完整口径、稳定时间窗 | 描述不等于原因 |
| 定位异常 | 分层、贡献度、漏斗、异常检测 | 原始事件、基线和质量检查 | 排名靠前不等于因果 |
| 预测未来 | 时间序列、回归、机器学习 | 时间切分验证、误差成本 | 离线准确率不等于业务收益 |
| 评估策略 | A/B、灰度、准实验 | 对照组、样本量、护栏指标 | 上线前后对比容易混入季节和选择偏差 |

如果问题只是“发生了什么”，先别急着建模；如果问题涉及“采取某策略会怎样”，就必须讨论反事实和识别条件。围绕“数据治理成熟度模型”，应把观察分析、预测和因果评估的产出分开标注。

## 4. 案例一：华南某保险公司

### 案例 1：华南某保险公司的“数据治理成熟度模型”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“数据治理成熟度模型”映射到“数据治理制度、责任与运营”中的运营，而不是泛泛讨论概念。
- **触发事件**：监管口径变更后多个报表难以在期限内完成影响分析。
- **业务与数据范围**：指标、SQL、字段血缘、报表、责任人、版本和变更历史。数据侧重点采集评审、复盘、成熟度和采用记录，并与数据目录、元数据平台、质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：治理是否进入发布、事件和绩效流程。
- **关键障碍**：制度有流程，但血缘和指标定义不可追踪，依赖专家回忆。同时要防止资产没有负责人把表面指标带偏。
- **处理过程**：建立指标到字段的可追溯链路，变更模板自动生成下游清单和验证任务。实施时把“血缘、版本和问题工单支持影响分析与审计”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例项目把影响分析从人工搜索转为可审计流程。验收至少同时看主指标、评审、复盘、成熟度和采用记录和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“围绕关键数据资产建立标准、责任、质量、安全、血缘、变更和问题闭环，让治理机制进入日常交付。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

落地时建议先把一个总指标拆成可行动的树：

```text
数据治理成熟度模型｜从总量到单条证据
├── ① 同期基线：先排除节假日、活动和口径切换
├── ② 结构贡献：按业务域、资产层级、规则类型比较增量和抵消
├── ③ 状态漏斗：标准定义 → 责任认领 → 规则设计 → 执行监控
├── ④ 记录回查：正常、边界、异常各抽 N 条
└── ⑤ 闭环验证：平均修复时长与护栏指标同时恢复才算解决
```

如果某一分支变化最大，再进入下一层，而不是一开始就按十几个维度切碎。每个分层结果都应同时报告样本量，避免小样本的极端比例抢走注意力。

## 5. SQL：计算趋势、结构和贡献度

### 趋势、结构与贡献度诊断

```sql
-- 数据治理成熟度模型：分位对比诊断（责任团队 × 业务域）
WITH scoped AS (
  SELECT
    asset_id AS entity_key,
    event_id,
    check_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_data_quality_result
  WHERE check_time >= DATE '2026-03-01'
    AND check_time <  DATE '2026-06-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '规则通过率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

示例 SQL 只表达计算逻辑。实际实施应加入分区条件、业务状态过滤、时区和主题范围，并在结果中保留口径版本。

## 6. 案例二：华北某工业集团

### 案例 2：华北某工业集团的“数据治理成熟度模型”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“数据治理成熟度模型”映射到“数据治理制度、责任与运营”中的规则，而不是泛泛讨论概念。
- **触发事件**：各工厂治理成熟度差异大，总部统一规则难以落地。
- **业务与数据范围**：工厂资产、系统、人员、问题、规则执行和本地流程。数据侧重点采集规则、阈值、样本、工单和豁免，并与数据目录、元数据平台、质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：哪些标准和质量规则需要自动执行。
- **关键障碍**：总部按同一优先级推广全部规则，缺少本地负责人和差异化路径。同时要防止规则只告警不闭环把表面指标带偏。
- **处理过程**：按风险和场景分级，建立总部标准、本地执行、例外审批和成熟度评审。实施时把“治理成效由风险、返工、故障和采用衡量”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例机制兼顾统一控制与现场可执行性。验收至少同时看主指标、规则、阈值、样本、工单和豁免和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“围绕关键数据资产建立标准、责任、质量、安全、血缘、变更和问题闭环，让治理机制进入日常交付。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

当业务方要求“解释为什么下降”时，可以按下面顺序回答：

1. 先确认下降是否真实存在，排查采集、任务、维表和状态映射。
2. 把变化拆成对象数量、行为强度和结构占比。
3. 找到贡献最大的分组，但保留其他分组的抵消效应。
4. 抽取正负样本回查业务事件和操作日志。
5. 把尚不能证明的解释标为假设，并设计下一轮验证。

## 7. 代码验证：专题指标、实验或模型

### 专题验证代码

```python
from dataclasses import dataclass

TOPIC = "数据治理成熟度模型"
POLICY_ID = "g_data_governance_1x3cllm"

@dataclass(frozen=True)
class DataAsset:
    name: str
    criticality: str
    owner: str
    steward: str
    consumers: tuple[str, ...]
    controls: tuple[str, ...]
    last_reviewed: str

asset = DataAsset(
    name="enterprise_metric_snapshot",
    criticality="high",
    owner="business-domain-owner",
    steward="data-governance-steward",
    consumers=("management-reporting", "risk-monitor"),
    controls=("definition-version", "quality-gate", "lineage", "access-review"),
    last_reviewed="2026-11-06",
)

governance_checks = [
    "关键资产具有唯一负责人、业务定义、消费者和风险等级",
    "标准、质量和安全规则进入项目与发布流程",
    "血缘、版本和问题工单支持影响分析与审计",
    "治理成效由风险、返工、故障和采用衡量"
]

def validate_asset(item: DataAsset, checks: list[str]) -> list[str]:
    failures = []
    if not item.owner or not item.steward:
        failures.append("owner_chain_incomplete")
    if item.criticality not in {"critical", "high", "medium", "low"}:
        failures.append("risk_level_invalid")
    if not item.consumers:
        failures.append("consumer_list_missing")
    if len(item.controls) < len(checks):
        failures.append("controls_do_not_cover_checks")
    return failures

print({"policy": POLICY_ID, "failures": validate_asset(asset, governance_checks)})

# 规则必须绑定严重等级、阈值依据、责任人和豁免期限；问题关闭前保留样本、影响范围和复核证据。
```

## 8. 异常、偏差与常见误区

- **辛普森悖论**：总体改善但每个分组都变差，可能由对象结构变化造成。
- **幸存者偏差**：只分析完成流程的对象，忽略中途流失和中止。
- **分母漂移**：渠道口径、登录状态、版本或活动范围变化，改变可比性。
- **回传延迟**：当天数据未回补，导致近期效果被系统性低估。
- **多重比较**：反复寻找显著分组，实际只是随机波动。
- **行动偏差**：只报告支持既定方案的结果，忽略反例和护栏指标。

围绕“数据治理成熟度模型”，应预先写出至少三条反例检查。比如数据质量异常是否与业务变化分开、方案是否说明了成本、边界和停止条件，以及 上线后是否有人负责观察和复盘。

## 9. 第三个案例：华东某集团数据治理办公室

### 案例 3：华东某集团数据治理办公室的“数据治理成熟度模型”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“数据治理成熟度模型”映射到“数据治理制度、责任与运营”中的责任，而不是泛泛讨论概念。
- **触发事件**：治理制度发布一年，但新项目仍绕过标准并持续产生重复指标。
- **业务与数据范围**：项目流程、指标清单、评审记录、责任人、问题工单和系统门禁。数据侧重点采集RACI、数据 steward 和升级路径，并与数据目录、元数据平台、质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：谁定义、谁生产、谁使用、谁批准变更。
- **关键障碍**：治理只靠培训和文档，没有进入立项、开发和发布流程。同时要防止口径变更缺少影响分析把表面指标带偏。
- **处理过程**：把资产登记、口径评审、质量门禁和安全检查嵌入项目里程碑，关键资产设置联合负责人。实施时把“关键资产具有唯一负责人、业务定义、消费者和风险等级”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例治理用绕过率、重复指标、返工和问题闭环衡量制度是否生效。验收至少同时看主指标、RACI、数据 steward 和升级路径和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“围绕关键数据资产建立标准、责任、质量、安全、血缘、变更和问题闭环，让治理机制进入日常交付。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

### 案例 4：数据治理成熟度模型上线前的质量门禁

某数据治理与数据管理团队在季度复盘时重新讨论“数据治理成熟度模型”。讨论并没有从工具选型开始，而是先追问一个更基础的问题：常规日期下结果看起来正常，一旦遇到空值、重复、跨期、撤销或历史归属，报表口径便无法解释。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 把关键质量规则、阈值、例外审批、阻断动作和复核人写入发布流程。在本场景里，核心风险还包括权限长期累积，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：数据资产、字段及其在标准定义前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注asset_id与column_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 常规日期下结果看起来正常，一旦遇到空值、重复、跨期、撤销或历史归属，报表口径便无法解释。初看时，元数据平台与质量平台的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 五类边界样本、规则命中率、趋势对比、豁免记录、责任人、阻断结果和复盘工单。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“业务数据负责人”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“数据治理成熟度模型”的当前定义并记录版本；第二步用数据资产明细核对元数据平台到质量平台的关联；第三步按责任团队与业务域做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察血缘覆盖率和护栏指标规则通过率。

- **失败路径：** 一直调低阈值让报表通过，却没有处理规则为何持续失败。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“数据治理成熟度模型”时，先验证评审、复盘、成熟度和采用记录，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由业务数据负责人在明确时限内，根据血缘覆盖率、规则通过率和变更留痕完整决定继续、回退、补查还是转人工。 若权限长期累积或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

- **失败路径：** 用平均值掩盖差异，或直接把对不上的明细删掉。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“数据治理成熟度模型”时，先验证资产清单、等级、消费者和故障历史，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由安全合规在明确时限内，根据问题闭环率、血缘覆盖率和规则可执行且可解释决定继续、回退、补查还是转人工。 若规则只告警不闭环或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从数据治理成熟度模型回到可核对明细

```sql
-- 数据治理成熟度模型：字段血缘与影响范围
WITH changed_columns AS (
  SELECT column_name
  FROM information_schema.columns
  WHERE table_schema = :source_schema
    AND table_name = :source_table
    AND last_altered_at >= :change_time
),
downstream_assets AS (
  SELECT
    asset_id,
    asset_name,
    asset_type,
    owner_name,
    criticality,
    last_used_at
  FROM metadata_asset_relation
  WHERE upstream_asset_id = :source_asset_id
    AND relation_status = 'active'
)
SELECT
  d.asset_id,
  d.asset_name,
  d.asset_type,
  d.owner_name,
  d.criticality,
  d.last_used_at,
  COUNT(c.column_name) AS changed_column_cnt,
  CASE
    WHEN d.criticality IN ('core', 'regulated') THEN 'block_release'
    WHEN d.last_used_at >= CURRENT_DATE - INTERVAL '7 days' THEN 'notify_owner'
    ELSE 'register_review'
  END AS required_action
FROM downstream_assets d
CROSS JOIN changed_columns c
GROUP BY d.asset_id, d.asset_name, d.asset_type, d.owner_name, d.criticality, d.last_used_at
ORDER BY
  CASE WHEN d.criticality IN ('core', 'regulated') THEN 0 ELSE 1 END,
  d.last_used_at DESC;

-- 目标：变更前识别 数据目录、元数据平台、质量平台 之后的所有结果与消费者。
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把数据治理成熟度模型的验收证据写成门禁

```python
import json
from pathlib import Path


def build_evidence_manifest(
    subject: str,
    scope: dict,
    checks: dict,
    samples: list[dict],
    owner: str,
) -> dict:
    failed = [name for name, passed in checks.items() if not passed]
    return {
        "subject": subject,
        "scope": scope,
        "checks": checks,
        "failed_checks": failed,
        "sample_evidence": samples[:5],
        "owner": owner,
        "decision": "block" if failed else "review",
        "manual_questions": [
            "每一项失败是否已回到原始记录",
            "对象、时间和状态是否与指标字典一致",
            "回滚或修复后是否重新完成对账",
        ],
    }


manifest = build_evidence_manifest(
    subject="数据治理成熟度模型",
    scope={"systems": ["数据目录","元数据平台","质量平台","权限系统"]},
    checks={"definition_frozen": False, "reconciled": False},
    samples=[],
    owner="数据治理办公室",
)
Path("release-evidence.json").write_text(
    json.dumps(manifest, ensure_ascii=False, indent=2),
    encoding="utf-8",
)
print(manifest["decision"])
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。

### 四个案例共用的验收清单

| 验证面 | 发布前问题 | 证据 | 不通过时 |
| --- | --- | --- | --- |
| 对象与粒度 | 一行数据代表数据资产、事件、快照还是结果 | 主键、版本、有效时间和边界样本 | 阻断 |
| 时间语义 | 业务发生、数据可见、决策采用是否混用 | check_time、入仓时间、行动时间轴 | 阻断 |
| 指标口径 | 规则通过率的分子、分母和排除项是否冻结 | 指标字典、SQL、对账结果 | 阻断正式指标 |
| 状态与关联 | 资产盘点 → 标准定义 → 责任认领 → 规则设计是否可达且可追溯 | 状态机、明细、操作日志 | 阻断关键链路 |

| 恢复与审计 | 失败后能否定位影响范围并幂等重跑 | 参数、版本、分区清单、补数对账 | 阻断发布 |
