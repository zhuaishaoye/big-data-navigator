# 数据开发工程师成长路径

> [!tip] 使用方式
> “数据开发工程师成长路径”既可能是业务概念，也可能是技术方案，还可能是岗位能力。判断学习是否有效，要看能否在数据接入、离线与实时处理、数仓建模、调度发布、数据服务、稳定性和成本治理中做出一个可复现的小闭环。本文用多个案例展示从需求到数据结果，再回到业务行动和复盘的完整路径。

## 1. 岗位到底在解决什么问题

围绕“数据开发工程师成长路径”，数据分析相关岗位的价值不是掌握多少工具名称，而是能在数据接入、离线与实时处理、数仓建模、调度发布、数据服务、稳定性和成本治理中把模糊问题转成可验证交付。看岗位 JD 时，把要求分成四层：

| 层级 | JD 常见表述 | 面试官真正想确认 | 可提供的证据 |
| --- | --- | --- | --- |
| 业务 | 理解业务、推动增长、支持决策 | 能否找到问题和行动 | 场景、口径、决策与复盘 |
| 方法 | 指标体系、实验、建模、治理 | 是否会选择合适方法 | 方案对比、假设、反例 |
| 工程 | SQL、Python、平台、调度、质量 | 能否稳定交付和排障 | 代码、监控、回滚记录 |
| 协作 | 跨团队、沟通、项目管理 | 是否能把事情推进完 | 争议、决策、责任和时间线 |

“数据开发工程师成长路径”在面试中不能只回答定义。准备一个真实案例，说明为什么做、你个人做了什么、如何验证、结果怎样、如果重做会改什么。团队成果和个人贡献要明确分开。

## 3. 案例一：用业务问题讲清技术选择

### 案例 1：华北某制造数据团队的“数据开发工程师成长路径”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“数据开发工程师成长路径”映射到“数据开发、ETL 与交付流程”中的接口与变更，而不是泛泛讨论概念。
- **触发事件**：历史补数运行三天仍未完成，正常日批任务同时出现资源争抢。
- **业务与数据范围**：补数分区、任务耗时、资源队列、依赖层级、下游锁和人工处理记录。数据侧重点采集接口契约、DDL、版本和变更记录，并与调度平台、元数据平台、数据质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：字段、分区、更新频率和 Schema 如何演进。
- **关键障碍**：所有日期一次性并发启动，任务内部没有分区级状态，失败后只能整批重跑。同时要防止重复写入把表面指标带偏。
- **处理过程**：按依赖层级和业务优先级分批，记录每个分区的输入输出计数，并对重跑设置幂等与限流。实施时把“每个任务声明输入输出粒度、分区、幂等键和重跑边界”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例项目用补数进度、正常任务 SLA、重复率和人工介入次数衡量稳定性。验收至少同时看主指标、接口契约、DDL、版本和变更记录和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把需求、源接口、分层模型、代码、配置、测试、发布和回滚连成一条可重复执行的数据交付链路。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

面试表达可以压缩成 90 秒：

> 背景是【历史补数运行三天仍未完成，正常日批任务同时出现资源争抢】。我负责【对象、范围、数据与方案】。先处理【主键、时间、状态或权限】，再用【方法】验证。最终交付【表/指标/服务/规则】，业务采取【行动】。结果是【有口径的改善】，但仍有【限制】，下一版会【改进】。

数字要能回答来源、时间窗、计算方法和你的贡献，不要使用无法解释的百分比。

## 4. 案例二：故障与复盘如何讲

### 案例 2：华东某零售数据开发组的“数据开发工程师成长路径”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“数据开发工程师成长路径”映射到“数据开发、ETL 与交付流程”中的测试与幂等，而不是泛泛讨论概念。
- **触发事件**：订单日报连续两天出现重复金额，重跑后差异进一步扩大。
- **业务与数据范围**：源订单、支付、退款、任务实例、写入模式、分区和质量结果。数据侧重点采集测试数据、重跑结果、唯一键和事务，并与调度平台、元数据平台、数据质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：重复运行、空分区、乱序和边界值是否安全。
- **关键障碍**：任务使用追加写，支付回调重复进入 ODS，开发只按订单号关联而没有确认退款粒度。同时要防止依赖环把表面指标带偏。
- **处理过程**：为源事件补充唯一键和版本，按订单行统一事实粒度，改为分区幂等合并并建立金额桥接对账。实施时把“测试覆盖空分区、重复数据、迟到数据、Schema 变化和失败恢复”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例交付以重跑一致、金额平衡、分区覆盖和下游验收作为恢复条件。验收至少同时看主指标、测试数据、重跑结果、唯一键和事务和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把需求、源接口、分层模型、代码、配置、测试、发布和回滚连成一条可重复执行的数据交付链路。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

故障题按“影响、止血、定位、修复、复核、防复发”回答。比如数据异常时，先判断是否阻断发布和通知消费者，再检查源系统、任务、分区、口径、代码和维度映射。修复后要保留问题时间线、影响资产、根因和自动化措施。

from dataclasses import dataclass
from datetime import datetime

TOPIC = "数据开发工程师成长路径"
TASK_ID = "g_data_development_y799ih"
PARTITION_KEY = "business_date"
GATE_RULES = [
    "代码、配置、DDL、权限和调度依赖进入同一版本与发布记录",
    "每个任务声明输入输出粒度、分区、幂等键和重跑边界",
    "测试覆盖空分区、重复数据、迟到数据、Schema 变化和失败恢复"
]

@dataclass(frozen=True)
class PartitionResult:
    partition: str
    input_rows: int
    output_rows: int
    duplicate_keys: int
    rejected_rows: int
    checksum: str

def publish_idempotent(spark, source_table: str, target_table: str, ds: str) -> PartitionResult:
    source = spark.read.table(source_table).where(f"{PARTITION_KEY} = '{ds}'")
    source.createOrReplaceTempView("staged_source")
    deduped = spark.sql("""
        SELECT *
        FROM (
          SELECT *,
                 ROW_NUMBER() OVER (
                   PARTITION BY business_key
                   ORDER BY updated_at DESC
                 ) AS version_no
          FROM staged_source
        )
        WHERE version_no = 1
    """)
    duplicate_keys = spark.sql("""
        SELECT COUNT(*) AS duplicate_keys
        FROM (
          SELECT business_key
          FROM staged_source
          GROUP BY business_key
          HAVING COUNT(*) > 1
        )
    """).first()["duplicate_keys"]
    assert duplicate_keys == 0, f"{TASK_ID}/{ds}: duplicate business keys must be quarantined"

    # 重跑同一分区先覆盖该分区，再原子切换；若平台不支持事务，使用影子分区和版本指针。
    deduped.write.mode("overwrite").insertInto(target_table)
    checksum = str(deduped.selectExpr("count(*) AS row_cnt").first()["row_cnt"])
    return PartitionResult(ds, source.count(), deduped.count(), duplicate_keys, 0, checksum)

# 上线证据：分区覆盖、主键唯一、数量/金额对账、执行版本、输入输出计数和回滚记录必须同批保存。

### 质量验证与发布门禁

```python
# 数据开发工程师成长路径：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "数据开发工程师成长路径"
TOPIC_KEY = "subject"
RULE_ID = "rule_engineering_y799ih"
GUIDE_CHECKS = [
    "代码、配置、DDL、权限和调度依赖进入同一版本与发布记录",
    "每个任务声明输入输出粒度、分区、幂等键和重跑边界",
    "测试覆盖空分区、重复数据、迟到数据、Schema 变化和失败恢复",
    "上线前完成数量、金额、主键、时延和下游可读性验收"
]
RULES = {
    "required_columns": ["event_id", "source_id", "run_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "source_id",
    "time_field": "run_time",
    "max_duplicate_rate": 0.0007,
    "max_null_rate": 0.006,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：代码、配置、DDL、权限和调度依赖进入同一版本与发布记录；每个任务声明输入输出粒度、分区、幂等键和重跑边界；测试覆盖空分区、重复数据、迟到数据、Schema 变化和失败恢复；上线前完成数量、金额、主键、时延和下游可读性验收
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

## 6. 高频追问与回答骨架

**问：你如何定义“数据开发工程师成长路径”的成功？**

答：同时给出业务结果、过程诊断和护栏指标。业务结果说明是否改善，过程指标解释改善来自哪里，护栏指标防止成本、投诉、风险或长期价值恶化。

**问：指标下降了怎么办？**

答：先确认数据是否真实完整，再按对象、结构、行为和外部因素拆分，抽取正负样本回查，最后给出行动和验证方式。分区覆盖完整、任务幂等、依赖无环。

**问：为什么选择这个方案？**

答：说明约束和目标，再比较至少两个替代方案。回答应包括开发成本、维护成本、时延、准确性、扩展性和失败后的影响。

**问：最大的困难是什么？**

答：选择一个可复现的技术或协作问题，例如“重复写入”，讲清你如何定位、谁参与、采取了什么折中和最终防复发措施。

**问：如果重做会改什么？**

答：优先说可验证的改进，例如更早冻结口径、增加质量门禁、用小范围灰度、补充长期护栏指标或减少手工依赖。

## 8. 案例三：把岗位要求转成可验证练习

### 案例 3：华南某 SaaS 数据平台的“数据开发工程师成长路径”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“数据开发工程师成长路径”映射到“数据开发、ETL 与交付流程”中的发布与回滚，而不是泛泛讨论概念。
- **触发事件**：一次上游字段扩容导致多个 ETL 任务失败，发布窗口内无法快速定位影响。
- **业务与数据范围**：接口契约、DDL 历史、字段血缘、任务依赖、失败日志和下游资产。数据侧重点采集发布单、监控、回滚脚本和验收记录，并与调度平台、元数据平台、数据质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：谁审批、如何灰度、失败后怎样恢复。
- **关键障碍**：代码、表结构和调度配置分别发布，测试环境长期使用旧 Schema。同时要防止热点倾斜把表面指标带偏。
- **处理过程**：建立契约兼容检查、字段级影响分析、影子表和灰度发布，生产前自动跑新旧结果对照。实施时把“上线前完成数量、金额、主键、时延和下游可读性验收”写成上线检查项，并为每一项保留日志、样本和负责人。

- **行动与护栏：** 在行动前冻结观察窗口与分组规则，上线后同时报告总体结果、分层结果、置信区间和反例。专题检查项“上线前完成数量、金额、主键、时延和下游可读性验收”被写成发布门禁，收益只在少数子组出现且护栏恶化时，不扩大全量使用。
- **失败路径：** 用上线前后两张趋势图直接宣称方案有效，忽略选择偏差与自然增长。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“数据开发工程师成长路径”时，先验证需求说明、粒度声明、样例单据，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由平台团队在明确时限内，根据资源消耗、服务可用率和依赖无环决定继续、回退、补查还是转人工。 若热点倾斜或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从数据开发工程师成长路径回到可核对明细

```sql
-- 数据开发工程师成长路径：恢复后缺失、重复与跨期检查
WITH expected_keys AS (
  SELECT DISTINCT source_id AS entity_key, event_id
  FROM fact_pipeline_run
  WHERE run_time >= :restore_start
    AND run_time <  :restore_end
    AND subject_key = 'subject'
),
restored_keys AS (
  SELECT source_id AS entity_key, event_id, load_version, loaded_at
  FROM fact_pipeline_run
  WHERE run_time >= :restore_start
    AND run_time <  :restore_end
    AND subject_key = 'subject'
    AND load_version = :restore_version
),
coverage AS (
  SELECT
    (SELECT COUNT(*) FROM expected_keys) AS expected_cnt,
    (SELECT COUNT(*) FROM restored_keys) AS restored_cnt,
    (SELECT COUNT(*) FROM (
      SELECT entity_key, event_id
      FROM restored_keys
      GROUP BY entity_key, event_id
      HAVING COUNT(*) > 1
    ) duplicate_keys) AS duplicated_cnt,
    (SELECT COUNT(*) FROM (
      SELECT e.entity_key, e.event_id
      FROM expected_keys e
      LEFT JOIN restored_keys r USING (entity_key, event_id)
      WHERE r.entity_key IS NULL
    ) missing_keys) AS missing_cnt
)
SELECT *,
  CASE
    WHEN expected_cnt <> restored_cnt OR duplicated_cnt > 0 OR missing_cnt > 0
      THEN 'reject_release'
    ELSE 'accept_restore'
  END AS gate_result
FROM coverage;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把数据开发工程师成长路径的验收证据写成门禁

```python
from datetime import date
from hashlib import sha256

import pandas as pd

SUBJECT = "数据开发工程师成长路径"
BLOCKING_RULES = ["分区覆盖完整","任务幂等","依赖无环"]


def validate_release(frame: pd.DataFrame, start: date, end: date) -> dict:
    scoped = frame.loc[
        frame["event_date"].between(pd.Timestamp(start), pd.Timestamp(end))
        & (frame["subject_key"] == "subject")
    ].copy()
    checks = {
        "has_rows": len(scoped) > 0,
        "event_id_unique": not scoped["event_id"].duplicated().any(),
        "entity_key_complete": scoped["entity_key"].notna().all(),
        "event_time_present": scoped["event_time"].notna().all(),
        "scope_matches": scoped["subject_key"].nunique() == 1,
    }
    payload = f"{SUBJECT}|{start}|{end}|{len(scoped)}|{sorted(checks.items())}"
    return {
        "subject": SUBJECT,
        "rows": len(scoped),
        "checks": checks,
        "blocking_rules": BLOCKING_RULES,
        "release_allowed": all(checks.values()),
        "evidence_hash": sha256(payload.encode("utf-8")).hexdigest(),
    }
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
