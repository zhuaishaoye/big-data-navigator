# 数据技术选型能力

> [!tip] 使用方式
> “数据技术选型能力”既可能是业务概念，也可能是技术方案，还可能是岗位能力。判断学习是否有效，要看能否在数据接入、离线与实时处理、数仓建模、调度发布、数据服务、稳定性和成本治理中做出一个可复现的小闭环。本文用多个案例展示从需求到数据结果，再回到业务行动和复盘的完整路径。

## 1. 岗位到底在解决什么问题

围绕“数据技术选型能力”，数据分析相关岗位的价值不是掌握多少工具名称，而是能在数据接入、离线与实时处理、数仓建模、调度发布、数据服务、稳定性和成本治理中把模糊问题转成可验证交付。看岗位 JD 时，把要求分成四层：

| 层级 | JD 常见表述 | 面试官真正想确认 | 可提供的证据 |
| --- | --- | --- | --- |
| 业务 | 理解业务、推动增长、支持决策 | 能否找到问题和行动 | 场景、口径、决策与复盘 |
| 方法 | 指标体系、实验、建模、治理 | 是否会选择合适方法 | 方案对比、假设、反例 |
| 工程 | SQL、Python、平台、调度、质量 | 能否稳定交付和排障 | 代码、监控、回滚记录 |
| 协作 | 跨团队、沟通、项目管理 | 是否能把事情推进完 | 争议、决策、责任和时间线 |

“数据技术选型能力”在面试中不能只回答定义。准备一个真实案例，说明为什么做、你个人做了什么、如何验证、结果怎样、如果重做会改什么。团队成果和个人贡献要明确分开。

## 2. 能力地图：从知道到能交付

| 能力项 | 合格表现 | 进阶表现 | 证据 |
| --- | --- | --- | --- |
| 业务理解 | 能说明“数据技术选型能力”服务谁、影响什么决策 | 能识别错误问题和隐藏约束 | 访谈记录、问题说明 |
| 指标口径 | 能定义对象、粒度、时间和排除项 | 能处理历史变更、实验和护栏指标 | 指标字典、对账样例 |
| 数据处理 | 能写可运行的 SQL/Python 并验证质量 | 能设计增量、幂等、监控和回滚 | 代码、执行日志 |
| 分析判断 | 能分层定位并回到明细 | 能区分描述、预测和因果 | 专题分析、反例清单 |
| 工程意识 | 知道时延、成本、权限和稳定性边界 | 能做方案取舍与容量评估 | 架构图、压测或故障复盘 |
| 协作推动 | 能记录争议、结论和负责人 | 能把一次性项目沉淀为机制 | 评审纪要、上线复盘 |
| 岗位迁移 | 能针对不同 JD 调整证据顺序 | 能解释长期能力与行业选择 | 定制简历、作品集 |

建议每个能力项准备三份材料：一页知识笔记、一段可运行代码或分析、一条项目证据。没有项目证据的内容可以保留在学习清单，但不要写成“精通”。

## 3. 案例一：用业务问题讲清技术选择

### 案例 1：华北某金融机构的“数据技术选型能力”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“数据技术选型能力”映射到“技术选型、路线图与架构演进”中的总成本，而不是泛泛讨论概念。
- **触发事件**：新技术 PoC 效果良好，但上线后版本升级和安全补丁无人负责。
- **业务与数据范围**：产品生命周期、供应商支持、内部技能、漏洞、升级和替代方案。数据侧重点采集三年 TCO、人员投入和沉淀资产，并与调度平台、元数据平台、数据质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：许可、开发、运维、迁移、培训、退出成本各是多少。
- **关键障碍**：评审只看短期性能，没有定义运维所有者、升级节奏和退出计划。同时要防止重复写入把表面指标带偏。
- **处理过程**：补充总拥有成本和生命周期评估，设置版本基线、责任人和季度退出演练。实施时把“记录被否决方案、决策假设、退出策略和复审日期”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例决策把长期可维护性纳入上线门槛。验收至少同时看主指标、三年 TCO、人员投入和沉淀资产和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把业务约束、总拥有成本、团队能力、迁移风险和退出策略放进同一决策框架，避免用功能清单和短期演示做技术选型。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

面试表达可以压缩成 90 秒：

> 背景是【新技术 PoC 效果良好，但上线后版本升级和安全补丁无人负责】。我负责【对象、范围、数据与方案】。先处理【主键、时间、状态或权限】，再用【方法】验证。最终交付【表/指标/服务/规则】，业务采取【行动】。结果是【有口径的改善】，但仍有【限制】，下一版会【改进】。

数字要能回答来源、时间窗、计算方法和你的贡献，不要使用无法解释的百分比。

## 4. 案例二：故障与复盘如何讲

### 案例 2：华东某互联网公司的“数据技术选型能力”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“数据技术选型能力”映射到“技术选型、路线图与架构演进”中的问题适配，而不是泛泛讨论概念。
- **触发事件**：团队准备替换现有查询引擎，候选方案在小型演示中性能差异明显。
- **业务与数据范围**：真实查询模板、数据规模、并发、P95、资源成本、兼容性和运维复杂度。数据侧重点采集基准任务、现状基线、失败案例，并与调度平台、元数据平台、数据质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：候选技术解决的具体瓶颈是否真实存在。
- **关键障碍**：演示只跑单条扫描查询，没有覆盖 Join、更新、权限和故障恢复。同时要防止依赖环把表面指标带偏。
- **处理过程**：建立生产查询回放集与加权评分，按功能、性能、成本、风险和迁移工作量做 PoC。实施时把“选型从真实问题和现状基线出发，不使用厂商演示作为唯一证据”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例评审保留不选方案的理由和退出条件，而不是只记录最终赢家。验收至少同时看主指标、基准任务、现状基线、失败案例和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把业务约束、总拥有成本、团队能力、迁移风险和退出策略放进同一决策框架，避免用功能清单和短期演示做技术选型。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

故障题按“影响、止血、定位、修复、复核、防复发”回答。比如数据异常时，先判断是否阻断发布和通知消费者，再检查源系统、任务、分区、口径、代码和维度映射。修复后要保留问题时间线、影响资产、根因和自动化措施。

```python
from dataclasses import dataclass, field

TOPIC = "数据技术选型能力"
EVALUATION_ID = "g_technology_strategy_47v4gb"

@dataclass
class Candidate:
    name: str
    problem_fit: float
    production_perf: float
    tco_score: float
    migration_score: float
    exit_score: float
    evidence: list[str] = field(default_factory=list)

def weighted_decision(candidate: Candidate) -> dict:
    weights = {
        "problem_fit": 0.24,
        "production_perf": 0.22,
        "tco": 0.20,
        "migration": 0.16,
        "exit": 0.18,
    }
    scores = {
        "problem_fit": candidate.problem_fit,
        "production_perf": candidate.production_perf,
        "tco": candidate.tco_score,
        "migration": candidate.migration_score,
        "exit": candidate.exit_score,
    }
    total = sum(scores[key] * weights[key] for key in weights)
    return {
        "candidate": candidate.name,
        "score": round(total, 4),
        "evidence_count": len(candidate.evidence),
        "decision": "poc" if len(candidate.evidence) < 3 else "review",
    }

POLICY = {
    "topic": TOPIC,
    "evaluation_id": EVALUATION_ID,
    "required_evidence": ["真实任务回放", "并发与故障测试", "三年TCO", "迁移评估", "退出方案"],
    "forbidden_shortcut": ["只看厂商演示", "只比较单条查询", "忽略版本生命周期"],
}
print(POLICY)

# 决策记录必须包含被否决方案、权重来源、假设、风险负责人、复审日期与退出触发条件。
```

### 质量验证与发布门禁

```python
# 数据技术选型能力：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "数据技术选型能力"
TOPIC_KEY = "subject"
RULE_ID = "rule_engineering_47v4gb"
GUIDE_CHECKS = [
    "选型从真实问题和现状基线出发，不使用厂商演示作为唯一证据",
    "评估功能、性能、总成本、风险、团队能力和迁移工作量",
    "PoC 覆盖真实查询、并发、权限、故障恢复和升级",
    "记录被否决方案、决策假设、退出策略和复审日期"
]
RULES = {
    "required_columns": ["event_id", "source_id", "run_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "source_id",
    "time_field": "run_time",
    "max_duplicate_rate": 0.0007,
    "max_null_rate": 0.005,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：选型从真实问题和现状基线出发，不使用厂商演示作为唯一证据；评估功能、性能、总成本、风险、团队能力和迁移工作量；PoC 覆盖真实查询、并发、权限、故障恢复和升级；记录被否决方案、决策假设、退出策略和复审日期
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

现场回答代码题时，建议边写边讲：

1. 先确认表粒度、状态定义和时间字段。
2. 说明去重策略及为什么选择该窗口。
3. 指出可能全表扫描、数据倾斜或空值影响。
4. 给出验证 SQL 或抽样方式。
5. 说明数据量扩大十倍时先测什么，而不是直接说加机器。

## 6. 高频追问与回答骨架

**问：你如何定义“数据技术选型能力”的成功？**

答：同时给出业务结果、过程诊断和护栏指标。业务结果说明是否改善，过程指标解释改善来自哪里，护栏指标防止成本、投诉、风险或长期价值恶化。

**问：指标下降了怎么办？**

答：先确认数据是否真实完整，再按对象、结构、行为和外部因素拆分，抽取正负样本回查，最后给出行动和验证方式。分区覆盖完整、任务幂等、依赖无环。

**问：为什么选择这个方案？**

答：说明约束和目标，再比较至少两个替代方案。回答应包括开发成本、维护成本、时延、准确性、扩展性和失败后的影响。

**问：最大的困难是什么？**

答：选择一个可复现的技术或协作问题，例如“重复写入”，讲清你如何定位、谁参与、采取了什么折中和最终防复发措施。

**问：如果重做会改什么？**

答：优先说可验证的改进，例如更早冻结口径、增加质量门禁、用小范围灰度、补充长期护栏指标或减少手工依赖。

## 7. 简历和作品集怎么写

弱表达：

> 使用 SQL 和 Python 完成“数据技术选型能力”相关数据分析，制作报表并优化流程。

更可信的表达：

> 负责【业务域】的“数据技术选型能力”专题，统一【对象/时间/状态】口径，完成【模型、代码、规则或服务】；通过【验证方法】定位【具体问题】，推动【业务动作】；沉淀【指标字典、监控或复用方案】，并使用【可解释的效率、质量、时效或范围指标】验收。

作品集至少包含背景、数据范围、架构或分析流程、关键代码、质量验证、结果限制和复盘。不能披露公司数据时，使用合成数据和脱敏边界，不要为了好看虚构业务增长。

## 8. 案例三：把岗位要求转成可验证练习

### 案例 3：华南某制造集团的“数据技术选型能力”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“数据技术选型能力”映射到“技术选型、路线图与架构演进”中的风险，而不是泛泛讨论概念。
- **触发事件**：多个工厂希望采用不同湖仓产品，集团担心重复平台和长期维护成本。
- **业务与数据范围**：工厂规模、网络、实时需求、数据主权、现有技能和三年预算。数据侧重点采集版本路线、支持条款、漏洞和替代方案，并与调度平台、元数据平台、数据质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：供应商锁定、版本生命周期、社区活跃度和合规如何。
- **关键障碍**：选型只比较存储格式和查询速度，没有计算跨厂治理与运维总成本。同时要防止热点倾斜把表面指标带偏。
- **处理过程**：区分集团标准能力与工厂本地能力，建立兼容接口和集中元数据，保留例外审批。实施时把“评估功能、性能、总成本、风险、团队能力和迁移工作量”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例架构在标准化与业务灵活性之间设置可量化边界。验收至少同时看主指标、版本路线、支持条款、漏洞和替代方案和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把业务约束、总拥有成本、团队能力、迁移风险和退出策略放进同一决策框架，避免用功能清单和短期演示做技术选型。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

把案例改写成练习时，不要直接复述团队成果。先列出你个人能复跑的部分，例如定义一行数据、写出三个指标、实现一个质量检查、解释一次失败回滚，再为每个部分找评审人或可验证结果。面试中的“熟悉”必须能落到这些证据上。

### 案例 4：数据技术选型能力跨团队交接的契约缺口

- **为什么要做：** 把数据定义、变更通知、失败动作、服务时限和责任人写成可测试的运行契约。在本场景里，核心风险还包括全量重算成本失控，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：数据源、数据表及其在开发测试前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注source_id与table_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 上游认为字段已经交付，下游却持续遇到状态含义、历史归属和异常处理不一致，问题在群聊中反复流转。初看时，Kafka与Flink的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 数据契约版本、字段语义、接口样例、变更记录、工单时效、消费者验收和升级路径。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“业务产品”确认什么结果可以进入下一步。

- **可迁移结论：** 处理“数据技术选型能力”时，先验证三年 TCO、人员投入和沉淀资产，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

```sql
coverage AS (
  SELECT
    (SELECT COUNT(*) FROM expected_keys) AS expected_cnt,
    (SELECT COUNT(*) FROM restored_keys) AS restored_cnt,
    (SELECT COUNT(*) FROM (
      SELECT entity_key, event_id
      FROM restored_keys
      GROUP BY entity_key, event_id
      HAVING COUNT(*) > 1
    ) duplicate_keys) AS duplicated_cnt,
    (SELECT COUNT(*) FROM (
      SELECT e.entity_key, e.event_id
      FROM expected_keys e
      LEFT JOIN restored_keys r USING (entity_key, event_id)
      WHERE r.entity_key IS NULL
    ) missing_keys) AS missing_cnt
)
SELECT *,
  CASE
    WHEN expected_cnt <> restored_cnt OR duplicated_cnt > 0 OR missing_cnt > 0
      THEN 'reject_release'
    ELSE 'accept_restore'
  END AS gate_result
FROM coverage;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把数据技术选型能力的验收证据写成门禁

```python
import json
from pathlib import Path


def build_evidence_manifest(
    subject: str,
    scope: dict,
    checks: dict,
    samples: list[dict],
    owner: str,
) -> dict:
    failed = [name for name, passed in checks.items() if not passed]
    return {
        "subject": subject,
        "scope": scope,
        "checks": checks,
        "failed_checks": failed,
        "sample_evidence": samples[:5],
        "owner": owner,
        "decision": "block" if failed else "review",
        "manual_questions": [
            "每一项失败是否已回到原始记录",
            "对象、时间和状态是否与指标字典一致",
            "回滚或修复后是否重新完成对账",
        ],
    }


manifest = build_evidence_manifest(
    subject="数据技术选型能力",
    scope={"systems": ["调度平台","元数据平台","数据质量平台","Kafka"]},
    checks={"definition_frozen": False, "reconciled": False},
    samples=[],
    owner="数据开发",
)
Path("release-evidence.json").write_text(
    json.dumps(manifest, ensure_ascii=False, indent=2),
    encoding="utf-8",
)
print(manifest["decision"])
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
