# 实时数据架构导览

> [!abstract] 流式数据与实时服务实战手册
> 实时数据架构的核心不是“越快越好”，而是在明确业务截止时间下，保证事件时间、状态、顺序、幂等、Checkpoint、回放和可观测性的一致。一个好的实时系统能够说明什么延迟可接受、失败时如何恢复、结果何时可信。

## 1. 实时数据架构导览：定义、适用边界与决策出口

实时数据架构的核心不是“越快越好”，而是在明确业务截止时间下，保证事件时间、状态、顺序、幂等、Checkpoint、回放和可观测性的一致。一个好的实时系统能够说明什么延迟可接受、失败时如何恢复、结果何时可信。

**本篇的适用边界。** 本篇讨论事件流、状态计算、实时指标、在线服务和回放恢复的架构方法；不把批处理缩短调度周期自动称为实时。

**最常见的错误替代。** 不能用处理时间代替事件时间，不能把 At-least-once 消费默认视为结果只计算一次，也不能只监控进程存活而忽略端到端新鲜度。

**最终决策。** 架构和业务团队要判断：哪些场景确实需要实时，SLO 和截止时间是多少，异常时保留旧结果还是阻断，如何回放和修复，以及实时链路是否值得其成本。 因此，这篇内容不从“应该建哪张表”开始，而从业务动作、责任人和失败后果开始。只有先确定谁在什么时点做出什么决定，字段、SQL、看板和模型才有明确用途。

围绕“实时数据架构导览”，工作中至少要区分四类问题：

1. **身份问题**：对象是谁，主键能否跨系统稳定关联，合并、拆分、撤销后历史是否还看得见。
2. **时间问题**：业务发生、状态生效、数据入仓、计算完成和人员行动分别发生在哪一刻。
3. **状态问题**：当前状态是一段事件、一张快照还是最终结果，空值代表未发生、未采集还是已删除。
4. **责任问题**：谁确认口径，谁处理异常，谁有权放行或停止，谁在观察期后复盘。

## 2. 实时数据架构导览的完整业务流程

| 环节 | 要做的事 | 最小证据 | 失败后先查什么 |
| --- | --- | --- | --- |
| 实时场景与 SLO | 定义业务动作、截止时间、允许延迟和失败后果 | 场景卡、事件量、SLO 和使用方 | 窗口按消费时钟切分，迟到数据错位 |
| 事件契约 | 定义事件键、事件时间、版本、状态和 Schema | 事件规范、兼容性规则和样例 | 重试后同一事件生成多条结果 |
| 采集与传输 | 确保分区、顺序、保留期和消费隔离 | Topic、分区键、Offset 和保留策略 | 任务运行但数据已停止更新 |
| 有状态计算 | 实现窗口、聚合、Join、去重和迟到处理 | 算子版本、State、Watermark 和 Checkpoint | 长期运行后 Checkpoint 和恢复失控 |
| 结果发布 | 以幂等键和版本对外提供指标或状态 | 结果表、缓存、API 和版本 | 窗口按消费时钟切分，迟到数据错位 |
| 监控与告警 | 观测摄入、延迟、反压、错误、State 和结果新鲜度 | 分区 Lag、Checkpoint、P95/P99 和业务探针 | 重试后同一事件生成多条结果 |
| 回放与修复 | 定义故障恢复、版本回滚和历史重算 | 回放脚本、影响范围、对账和通知 | 任务运行但数据已停止更新 |

把 实时场景与 SLO、事件契约、采集与传输、有状态计算、结果发布、监控与告警、回放与修复 串起来后可以看出，实时数据架构导览不是一个孤立字段，而是一条会跨系统、跨岗位、跨时间的证据链。流程图上每一段都应标出输入、输出、状态、时间戳、责任人和异常出口。只要其中一段只能靠口头解释，后续的统计、追责和自动化就会失去基础。

一个合格的需求说明应该写成：

> 在【授权数据范围】和【观察窗口】内，围绕“实时数据架构导览”的【事件流】，按【stream_job_id、business_domain、result_key、rule_version】比较【端到端新鲜度 P95】及其【消费 Lag】，定位一个可干预节点；行动后同时观察主指标、样本量和护栏，任何高风险异常先阻断再调查。

## 3. 实时数据架构导览的数据对象与系统契约

| 数据对象 | 建议主键 | 一行代表什么 | 不允许混淆 |
| --- | --- | --- | --- |
| 事件流 | `event_stream_id` | 具有 Schema、分区和保留策略的事件集合 | 对象身份与业务事件 |
| 业务事件 | `event_id` | 一次不可重复的业务事实 | 事件、状态快照和结果粒度 |
| 计算作业 | `stream_job_id` | 一个部署版本和状态配置明确的流式任务 | 事件、状态快照和结果粒度 |
| 状态快照 | `checkpoint_id` | 某时点用于恢复的算子状态 | 事件、状态快照和结果粒度 |
| 结果版本 | `realtime_result_id` | 按事件时间窗口和规则版本生成的结果 | 事件、状态快照和结果粒度 |
| 新鲜度探测 | `freshness_probe_id` | 从事件产生到消费端可见的端到端证据 | 事件、状态快照和结果粒度 |

对象表不是把所有字段塞进一张宽表。事件、状态快照和结果表应该分别保留粒度，再通过稳定主键与版本建立关联。尤其要避免三个常见混算：把一次业务事件算成多个对象、把每日快照相加当事件总量、把最新状态覆盖历史状态。

本主题的数据契约至少应包含：

- `realtime_result_id` 的唯一性规则、生成方式和跨系统映射。
- `event_occurred_at` 的业务含义、时区、迟到和补录规则。
- `result_status` 的完整状态集合，以及删除、撤销、冻结和失效的表示方法。
- 控制对象 `stream_freshness_probe.freshness_probe_id` 与主对象的关系。
- 每次口径、规则、模型或源版本变化的影响范围和下游通知对象。
- 敏感字段、允许用途、访问角色、导出限制和审计保留时间。

## 4. 实时数据架构导览的指标、样本与验收口径

| 指标 | 公式或定义 | 口径提醒 |
| --- | --- | --- |
| 端到端新鲜度 P95 | 消费端可见时间 - 事件发生时间 | 禁止用单机处理时长替代 |
| 消费 Lag | 分区最新 Offset - 已提交 Offset | 需结合消息速率换算预计清积时间 |
| 重复结果率 | 重复幂等键结果数 / 输出结果数 | 按窗口和结果版本检查 |
| Checkpoint 成功率 | 成功完成的 Checkpoint 数 / 计划 Checkpoint 数 | 还需检查耗时和失败恢复验证 |
| 实时结果对账差异率 | 与离线基准不一致的业务对象数 / 对账对象数 | 必须定义允许延迟窗口 |

指标字典至少写到“任何人都能按同一份数据复跑”的程度：中文名、业务定义、公式、分子、分母、事实粒度、时间字段、对象范围、排除项、版本、负责人和验收样例，一个都不能少。比例指标必须同时展示分子、分母和样本量；金额或数量必须做守恒；状态指标必须能回到事件时间线。

对于“实时数据架构导览”，建议把观察分成三层：

| 层次 | 看什么 | 不能替代什么 |
| --- | --- | --- |
| 业务结果 | 端到端新鲜度 P95、消费 Lag | 不能替代过程证据和个案回查 |
| 过程护栏 | 重复结果率、Checkpoint 成功率、实时结果对账差异率 | 不能因为护栏暂时正常就跳过异常调查 |
| 数据证据 | 主键、时间、状态、版本、来源目标对账 | 不能只看任务成功或报表能打开 |

## 5. 实时数据架构导览：七个真实工作场景

以下七组场景均为公开方法结合常见工作流程构造的“脱敏复合示例”，不对应任何单一企业、患者、客户或雇员事实。场景的目的，是展示如何从现象走到证据、行动和验收，而不是虚构经营成果。

### 1. 业务说要实时但没有截止时间

**现场。** 需求方要求所有指标秒级更新。

**怎么查。** 分析实际动作，发现补货每 15 分钟一次、风控才需要秒级，其他看板无需毫秒延迟。

**怎么处理。** 按场景拆分 SLO；风控走低延迟链路，经营指标用微批；成本敏感场景保留批量回算。

**验收结论。** 实时是成本约束下的决策能力，不是统一速度目标。

### 2. 事件迟到导致窗口结果反复变化

**现场。** 某实时销售指标在一天内多次修订。

**怎么查。** 按事件时间、Watermark 和迟到事件回查，发现渠道补传数据延迟很长。

**怎么处理。** 明确允许迟到窗口；超过窗口进入修正流；对外结果标注版本和可信时间；与离线日终对账。

**验收结论。** 实时结果不是最终真相。要告诉使用者在哪一刻可以相信什么。

### 3. At-least-once 造成重复计数

**现场。** 作业故障恢复后订单数突然增加。

**怎么查。** 检查消费语义、输出幂等键和 Checkpoint，发现结果表按处理次数追加。

**怎么处理。** 以业务事件 ID 和窗口键做幂等写入；事务或去重表保障输出；故障样本进入回归。

**验收结论。** 消费不丢不代表结果不重。端到端幂等必须单独设计。

### 4. Checkpoint 成功但恢复极慢

**现场。** 监控显示状态备份正常，故障恢复却超过 SLO。

**怎么查。** 测量 Checkpoint 大小、上传下载时间、状态后端和恢复重放速度，发现状态无限增长。

**怎么处理。** 设置 State TTL 和窗口清理；优化 Key 结构；定期做恢复演练而不只看备份状态。

**验收结论。** 备份成功不等于可恢复。恢复时间才是业务连续性指标。

### 5. 事件时间晚于处理时间被误判

**现场。** 设备时钟漂移导致实时告警频繁乱序。

**怎么查。** 比较设备、边缘网关、消息平台和消费端时间，发现源头校时失败。

**怎么处理。** 采集端做时间质量检查；保留原始事件时间；严重偏移事件进入隔离；监控时钟漂移。

**验收结论。** 时间戳本身就是数据质量字段。

### 6. 实时和离线报表长期对不上

**现场。** 两个系统使用同名 GMV，数字差异无法解释。

**怎么查。** 对比订单状态、退款回冲、时间窗、迟到和去重规则，发现实时只算支付，离线扣退款。

**怎么处理。** 建立统一指标语义和分层对账；实时展示口径明确标签；日终以离线结算基准修正。

**验收结论。** 实时与离线不是两套事实，而是不同可信时点的同一事实。

### 7. 业务高峰反压引发全链路雪崩

**现场。** 上游事件量增加后，消费积压、数据库写入超时和 API 变慢。

**怎么查。** 查看分区热点、消费速率、下游写入、连接池和重试策略，发现失败后无限重试。

**怎么处理。** 设置背压和熔断；按事件优先级隔离；限制重试并进入死信；扩展前先定位瓶颈。

**验收结论。** 扩容不是默认答案。无边界重试会把局部故障放大成系统故障。

七个场景可以归成一条共同判断顺序：先确认对象和时间，再确认状态和版本；然后做总量、结构和明细三层对账；最后才讨论策略、模型或工具。若一条结论不能指出对应的原始记录、责任人和行动出口，就只能算观察，不能作为生产结论。

## 6. 实时数据架构导览的第一段 SQL：重建业务链路

下面的 SQL 用于说明对象、时间、状态、版本和分层口径如何进入同一条可复查路径。表名和部分字段是通用示例，落地时应映射到企业数据字典；SQL 方言也需按实际引擎调整。

```sql
-- 实时数据架构导览：按业务对象重建链路，避免事件、快照和结果混算
WITH ranked_realtime_result_id AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY realtime_result_id
      ORDER BY updated_at DESC
    ) AS version_no
  FROM realtime_service_event
  WHERE event_occurred_at >= TIMESTAMP '{start_time}'
    AND event_occurred_at <  TIMESTAMP '{end_time}'
    AND result_status NOT IN ('deleted', 'test')
),
valid_rows AS (
  SELECT
    realtime_result_id,
    stream_job_id,
    business_domain,
    result_key,
    rule_version,
    event_occurred_at,
    result_status,
    ingested_at
  FROM ranked_realtime_result_id
  WHERE version_no = 1
)
SELECT
  stream_job_id, business_domain, result_key, rule_version,
  COUNT(DISTINCT realtime_result_id) AS object_cnt,
  SUM(CASE WHEN duplicate_flag = 0 THEN 1 ELSE 0 END) AS numerator_value,
  COUNT(DISTINCT event_id) AS denominator_value,
  CAST(SUM(CASE WHEN duplicate_flag = 0 THEN 1 ELSE 0 END) AS DOUBLE PRECISION)
    / NULLIF(COUNT(DISTINCT event_id), 0) AS metric_value,
  MIN(event_occurred_at) AS first_event_at,
  MAX(event_occurred_at) AS last_event_at
FROM valid_rows
GROUP BY stream_job_id, business_domain, result_key, rule_version
ORDER BY metric_value DESC, object_cnt DESC;
```

执行后至少回答六个问题：

- 同一对象是否因为多源回传产生多版本，版本保留是否符合业务要求？
- 业务时间与入仓时间是否分开，补录和迟到数据是否进入正确分区？
- 分子分母是否来自同一对象范围和同一统计窗口？
- 维度使用的是事件当时值还是当前值，跨期比较是否一致？
- 删除、撤销、冻结和测试数据是否按规则处理？
- 分组结果能否在明细中抽样复现？

## 7. 实时数据架构导览的第二段 SQL：源、控制和结果三方对账

```sql
-- 实时数据架构导览：源对象、控制对象和结果对象三方对账
WITH population AS (
  SELECT
    realtime_result_id,
    event_occurred_at,
    result_status
  FROM realtime_service_event
  WHERE event_occurred_at >= TIMESTAMP '{start_time}'
    AND event_occurred_at <  TIMESTAMP '{end_time}'
),
control AS (
  SELECT
    realtime_result_id,
    SUM(end_to_end_latency_ms) AS control_value,
    COUNT(DISTINCT freshness_probe_id) AS control_cnt,
    MAX(updated_at) AS control_updated_at
  FROM stream_freshness_probe
  WHERE updated_at >= TIMESTAMP '{start_time}'
  GROUP BY realtime_result_id
),
result AS (
  SELECT
    realtime_result_id,
    COUNT(*) AS result_cnt,
    MAX(calculated_at) AS calculated_at
  FROM mart_realtime_result_id
  WHERE business_date BETWEEN DATE '{start_date}' AND DATE '{end_date}'
  GROUP BY realtime_result_id
)
SELECT
  COALESCE(p.realtime_result_id, c.realtime_result_id, r.realtime_result_id) AS object_key,
  CASE
    WHEN p.realtime_result_id IS NULL THEN 'source_missing'
    WHEN c.realtime_result_id IS NULL THEN 'control_missing'
    WHEN r.realtime_result_id IS NULL THEN 'result_missing'
    WHEN ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0 THEN 'count_or_value_gap'
    ELSE 'matched'
  END AS reconciliation_status,
  p.result_status,
  c.control_value,
  c.control_cnt,
  r.result_cnt,
  c.control_updated_at,
  r.calculated_at
FROM population p
FULL OUTER JOIN control c ON p.realtime_result_id = c.realtime_result_id
FULL OUTER JOIN result r ON COALESCE(p.realtime_result_id, c.realtime_result_id) = r.realtime_result_id
WHERE p.realtime_result_id IS NULL
   OR c.realtime_result_id IS NULL
   OR r.realtime_result_id IS NULL
   OR ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0;
```

这段查询故意不使用“总数相差小于某个随意百分比就算通过”。它先找出缺失对象和状态差异，再检查控制值与结果值。对于实时数据架构导览，数量、金额、时长或状态任意一项无法解释，都不能用“业务波动”代替排查。

对账结果建议分成四类处理：

1. **阻断**：对象缺失、关键时间为空、状态非法、金额或数量不守恒、权限越界。
2. **严重**：比例或总量显著偏离基线，且无法由已确认的对象结构变化解释。
3. **观察**：小范围波动但来源、样本和趋势可控，进入责任人和观察窗口。
4. **探索**：只有弱信号或假设，不进入正式结论，更不直接触发业务处罚。

## 8. 实时数据架构导览的 Python 发布门禁与指标护栏

第一段代码把发布条件写成可执行对象，避免“检查过了”只存在聊天记录里：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class RealtimeResultIdBatch:
    batch_id: str
    source_rows: int
    valid_rows: int
    duplicate_keys: int
    missing_required_fields: int
    reconciliation_gap: float

def release_realtime_result_id(batch: RealtimeResultIdBatch) -> dict:
    checks = {
        "source_not_empty": batch.source_rows > 0,
        "valid_rows_in_range": 0 <= batch.valid_rows <= batch.source_rows,
        "duplicate_rate_ok": batch.duplicate_keys / max(batch.source_rows, 1) <= 0.001,
        "required_fields_ok": batch.missing_required_fields == 0,
        "reconciliation_ok": abs(batch.reconciliation_gap) <= 0.01,
    }
    return {
        "topic": "实时数据架构导览",
        "batch_id": batch.batch_id,
        "checks": checks,
        "release_allowed": all(checks.values()),
        "blocking_checks": [name for name, passed in checks.items() if not passed],
    }
```

第二段代码演示如何为比例类结果附带样本证据和小样本下界。它不是替代统计学家的模型，而是防止把少量偶然样本直接包装成稳定结论：

```python
from dataclasses import dataclass
from math import sqrt

@dataclass(frozen=True)
class RealtimeResultIdObservation:
    object_id: str
    numerator: float
    denominator: float
    sample_size: int
    scope_version: str

def calculate_realtime_result_id(rows: list[RealtimeResultIdObservation]) -> list[dict]:
    output = []
    for row in rows:
        value = row.numerator / row.denominator if row.denominator > 0 else None
        # 小样本用 Wilson 下界做护栏，不把偶然的高比例直接当稳定结果。
        z = 1.96
        p = value or 0
        n = max(row.sample_size, 1)
        center = p + z * z / (2 * n)
        margin = z * sqrt((p * (1 - p) + z * z / (4 * n)) / n)
        lower = max(0, (center - margin) / (1 + z * z / n))
        output.append({
            "object_id": row.object_id,
            "metric": "端到端新鲜度 P95",
            "value": value,
            "lower_bound": lower if value is not None else None,
            "sample_size": row.sample_size,
            "scope_version": row.scope_version,
            "caution": "禁止用单机处理时长替代",
        })
    return output
```

真正上线时还要补充参数配置、日志、血缘、告警级别、重跑幂等、异常样本保存和审批记录。代码通过不代表业务通过；自动检查只能证明已经定义的规则没有被违反，无法证明规则本身一定正确。

## 9. 实时数据架构导览的失败反例与上线验收

| 风险信号 | 错误做法 | 必须补齐的证据 | 发布或行动规则 |
| --- | --- | --- | --- |
| 处理时间冒充事件时间 | 窗口按消费时钟切分，迟到数据错位 | 事件时间、Watermark 和迟到规则 | 关键结果必须按业务事件时间计算 |
| 重复写结果 | 重试后同一事件生成多条结果 | 业务键、幂等表和输出版本 | 端到端去重并验证恢复 |
| 监控只看进程 | 任务运行但数据已停止更新 | 端到端新鲜度和业务探针 | 无结果也触发告警 |
| 无限 State | 长期运行后 Checkpoint 和恢复失控 | State TTL、大小和恢复演练 | 状态生命周期纳入发布门禁 |

上线验收不应只有一句“报表正常”。建议按下面四层验收：

| 验收对象 | 结构要求 | 测试样本 | 结果证据 |
| --- | --- | --- | --- |
| 事件流 | `event_stream_id` 能唯一定位具有 Schema、分区和保留策略的事件集合 | 正常、重复、缺失、撤销与跨期样本 | 端到端新鲜度 P95可回到原始对象 |
| 业务事件 | `event_id` 能唯一定位一次不可重复的业务事实 | 正常、重复、缺失、撤销与跨期样本 | 消费 Lag可回到原始对象 |
| 计算作业 | `stream_job_id` 能唯一定位一个部署版本和状态配置明确的流式任务 | 正常、重复、缺失、撤销与跨期样本 | 重复结果率可回到原始对象 |
| 状态快照 | `checkpoint_id` 能唯一定位某时点用于恢复的算子状态 | 正常、重复、缺失、撤销与跨期样本 | Checkpoint 成功率可回到原始对象 |
| 结果版本 | `realtime_result_id` 能唯一定位按事件时间窗口和规则版本生成的结果 | 正常、重复、缺失、撤销与跨期样本 | 实时结果对账差异率可回到原始对象 |
| 新鲜度探测 | `freshness_probe_id` 能唯一定位从事件产生到消费端可见的端到端证据 | 正常、重复、缺失、撤销与跨期样本 | 端到端新鲜度 P95可回到原始对象 |

还应为每一次发布保留一组固定回归样本：正常对象、边界状态、重复记录、缺失字段、撤销或退款、跨期、权限拒绝和失败恢复。回归样本不是演示数据，而是以后每次改规则都能重复执行的质量资产。

## 10. 实时数据架构导览的 30 天落地与复盘

| 阶段 | 主要交付 | 通过条件 |
| --- | --- | --- |
| 第 1 周：定义 | 对象、流程、状态、指标、排除项和责任矩阵 | 业务、数据、安全或质量负责人对同一口径签字 |
| 第 2 周：打通 | 源字段、主键、时间、版本、控制对象和失败样本 | 正常与异常样本都能回到原始记录 |
| 第 3 周：验证 | 总量对账、分层对账、抽样回查、权限测试、回滚演练 | 阻断问题清零，严重问题有责任人与期限 |
| 第 4 周：发布 | 灰度、SLO、监控、行动清单、停止条件和复盘模板 | 使用者在真实场景中完成一次闭环行动 |

如果必须用 90 秒说明“实时数据架构导览”是否做对，可以按这个顺序自测：

1. 一行数据代表什么，主键是什么，哪些对象绝不能混在同一粒度？
2. 业务发生、数据可见、计算完成和行动确认分别在哪个时间点？
3. 本主题最重要的两个主指标、三个护栏和最小样本量是什么？
4. 一个异常出现时，先从原始记录、链路版本还是业务动作开始查？
5. 哪类错误必须阻断发布或停止使用，谁有权批准例外？
6. 上线后由谁在多长时间内观察，什么条件下回滚或结束？

> [!check] 完成标准
> 当另一位数据同事不看聊天记录，只根据口径卡、回归样本和代码就能复跑同一结果；当业务负责人能指出一个异常对应的原始对象、处置动作和复核证据；当系统能够阻止未授权或状态非法的数据进入下游，这篇“实时数据架构导览”才算真正落到工作里。
