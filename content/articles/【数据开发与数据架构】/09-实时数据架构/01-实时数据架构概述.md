# 实时数据架构概述

> [!abstract] 事件驱动与流式架构实战手册
> 实时数据架构成败取决于时间语义、状态、顺序、水位、幂等和降级，而不是引擎是否能把延迟压到毫秒。业务事件时间、处理时间和数据可见时间必须分开，迟到、重复、撤销和回放都要成为明确设计对象。

## 1. 实时数据架构概述：定义、适用边界与决策出口

实时数据架构成败取决于时间语义、状态、顺序、水位、幂等和降级，而不是引擎是否能把延迟压到毫秒。业务事件时间、处理时间和数据可见时间必须分开，迟到、重复、撤销和回放都要成为明确设计对象。

**本篇的适用边界。** 本篇讨论流式接入、事件处理、有状态计算、实时服务和运行保障；不把实时看板等同于结算系统，也不假设所有业务动作都适合自动触发。

**最常见的错误替代。** 不能只看平均延迟，不记录积压和 P99；不能用处理时间窗口替代业务时间窗；也不能在无人工闸门时让流式结果直接触发高风险动作。

**最终决策。** 架构团队要判断：结果的稳定时点是什么，迟到多久仍接收，重复和乱序如何幂等，状态故障如何恢复，下游不可用时保留还是丢弃，哪些动作必须人工批准。 因此，这篇内容不从“应该建哪张表”开始，而从业务动作、责任人和失败后果开始。只有先确定谁在什么时点做出什么决定，字段、SQL、看板和模型才有明确用途。

围绕“实时数据架构概述”，工作中至少要区分四类问题：

1. **身份问题**：对象是谁，主键能否跨系统稳定关联，合并、拆分、撤销后历史是否还看得见。
2. **时间问题**：业务发生、状态生效、数据入仓、计算完成和人员行动分别发生在哪一刻。
3. **状态问题**：当前状态是一段事件、一张快照还是最终结果，空值代表未发生、未采集还是已删除。
4. **责任问题**：谁确认口径，谁处理异常，谁有权放行或停止，谁在观察期后复盘。

## 2. 实时数据架构概述的完整业务流程

| 环节 | 要做的事 | 最小证据 | 失败后先查什么 |
| --- | --- | --- | --- |
| 事件契约定义 | 明确事件 ID、对象、业务时间、版本和删除语义 | 事件字典、样例、生产责任和兼容规则 | 窗口随系统时钟漂移 |
| 接入与缓冲 | 选择消息、CDC 或网关并设置保留和隔离 | 主题分区、保留期、死信和权限 | 重放重复发券或通知 |
| 时间与水位 | 基于事件时间推进水位并定义允许迟到 | 乱序分布、水位指标和关账窗口 | 单条异常阻塞全分区 |
| 状态与计算 | 设计窗口、去重、连接、状态 TTL 和检查点 | 状态大小、检查点、恢复演练 | 未对账就进入资金流程 |
| 实时服务 | 提供查询、特征或告警，设置缓存、限流和降级 | 服务 SLO、并发、旧值策略 | 窗口随系统时钟漂移 |
| 结果对账 | 与离线或源控制数据持续比较 | 差异分类、稳定版本和公告机制 | 重放重复发券或通知 |
| 应急与回放 | 处理积压、毒消息、下游失败和区域性恢复 | 演练记录、跳过策略和补数对账 | 单条异常阻塞全分区 |

把 事件契约定义、接入与缓冲、时间与水位、状态与计算、实时服务、结果对账、应急与回放 串起来后可以看出，实时数据架构概述不是一个孤立字段，而是一条会跨系统、跨岗位、跨时间的证据链。流程图上每一段都应标出输入、输出、状态、时间戳、责任人和异常出口。只要其中一段只能靠口头解释，后续的统计、追责和自动化就会失去基础。

一个合格的需求说明应该写成：

> 在【授权数据范围】和【观察窗口】内，围绕“实时数据架构概述”的【事件】，按【topic_name、consumer_group、business_domain、event_type】比较【事件端到端延迟】及其【输入输出平衡率】，定位一个可干预节点；行动后同时观察主指标、样本量和护栏，任何高风险异常先阻断再调查。

## 3. 实时数据架构概述的数据对象与系统契约

| 数据对象 | 建议主键 | 一行代表什么 | 不允许混淆 |
| --- | --- | --- | --- |
| 事件 | `event_id` | 一次不可变的业务发生或状态变化 | 对象身份与业务事件 |
| 分区偏移 | `topic_partition_offset` | 某消费者在主题分区中的处理位置 | 事件、状态快照和结果粒度 |
| 水位 | `watermark_id` | 某时间域内已经允许推进完整性的标记 | 事件、状态快照和结果粒度 |
| 实时状态 | `state_record_id` | 有状态作业为业务对象保存的最新可恢复状态 | 事件、状态快照和结果粒度 |
| 结果快照 | `realtime_result_id` | 指定事件水位和处理版本下的可见结果 | 事件、状态快照和结果粒度 |
| 死信记录 | `dead_letter_id` | 无法在当前规则下安全处理并需隔离的事件 | 事件、状态快照和结果粒度 |

对象表不是把所有字段塞进一张宽表。事件、状态快照和结果表应该分别保留粒度，再通过稳定主键与版本建立关联。尤其要避免三个常见混算：把一次业务事件算成多个对象、把每日快照相加当事件总量、把最新状态覆盖历史状态。

本主题的数据契约至少应包含：

- `event_delivery_id` 的唯一性规则、生成方式和跨系统映射。
- `event_time` 的业务含义、时区、迟到和补录规则。
- `delivery_status` 的完整状态集合，以及删除、撤销、冻结和失效的表示方法。
- 控制对象 `stream_checkpoint_state.checkpoint_id` 与主对象的关系。
- 每次口径、规则、模型或源版本变化的影响范围和下游通知对象。
- 敏感字段、允许用途、访问角色、导出限制和审计保留时间。

## 4. 实时数据架构概述的指标、样本与验收口径

| 指标 | 公式或定义 | 口径提醒 |
| --- | --- | --- |
| 事件端到端延迟 | 结果可见时间 - 事件业务时间 | 报告 P50、P95、P99 和超阈值比例 |
| 输入输出平衡率 | 可对账输出对象数 / 输入有效对象数 | 过滤、合并和死信要单独列出 |
| 检查点恢复时长 | 恢复后首次可服务时间 - 故障开始时间 | 必须包含状态验证与重复检查 |
| 死信安全处置率 | 在时限内完成分类、修复或隔离的死信数 / 死信总数 | 不能无审查批量丢弃 |
| 实时离线差异率 | 可解释差异对象数 / 对账对象数 | 先定义允许窗口，再比较稳定版本 |

指标字典至少写到“任何人都能按同一份数据复跑”的程度：中文名、业务定义、公式、分子、分母、事实粒度、时间字段、对象范围、排除项、版本、负责人和验收样例，一个都不能少。比例指标必须同时展示分子、分母和样本量；金额或数量必须做守恒；状态指标必须能回到事件时间线。

对于“实时数据架构概述”，建议把观察分成三层：

| 层次 | 看什么 | 不能替代什么 |
| --- | --- | --- |
| 业务结果 | 事件端到端延迟、输入输出平衡率 | 不能替代过程证据和个案回查 |
| 过程护栏 | 检查点恢复时长、死信安全处置率、实时离线差异率 | 不能因为护栏暂时正常就跳过异常调查 |
| 数据证据 | 主键、时间、状态、版本、来源目标对账 | 不能只看任务成功或报表能打开 |

## 5. 实时数据架构概述：七个真实工作场景

以下七组场景均为公开方法结合常见工作流程构造的“脱敏复合示例”，不对应任何单一企业、患者、客户或雇员事实。场景的目的，是展示如何从现象走到证据、行动和验收，而不是虚构经营成果。

### 1. 晚到事件让日终金额变化

**现场。** 实时支付看板在关账后仍多次改变，财务不认可结果。

**怎么查。** 分析事件时间、水位和更正消息，发现撤销事件使用较晚业务时间，却被水位直接丢弃。

**怎么处理。** 对账口径设置允许迟到窗口；Watermark 后变化进入更正流；界面显示初版、修订版和最终版。

**验收结论。** 实时必须明确稳定时点。不能把无限迟到事件和瞬时看板混成一个定义。

### 2. 重复消费导致余额累计两次

**现场。** 网络重试后同一充值事件被处理两次。

**怎么查。** 检查消息键、唯一约束、状态更新和偏移提交，发现结果表按追加写入但下游按事件累加。

**怎么处理。** 使用事件 ID 和业务键幂等去重；状态更新保存最后处理偏移；重放从检查点开始并做总额对账。

**验收结论。** 消息系统提供至少一次投递时，业务结果必须自己保证幂等。

### 3. 大促积压时自动扩容无效

**现场。** 消费速率下降，扩容后外部数据库连接被打满。

**怎么查。** 查看背压、每分区速率、下游写入和连接池，发现处理算子不是瓶颈。

**怎么处理。** 限制入口和分区并发；批量写下游；对非关键派生指标降级暂停；建立积压优先级和恢复速率目标。

**验收结论。** 实时恢复要保护最慢依赖。盲目扩容会把局部积压变成下游雪崩。

### 4. 毒消息阻塞整个分区

**现场。** 一条字段异常的事件反复重试，后续正常事件全部延迟。

**怎么查。** 检查异常栈、错误分类和重试策略，发现未区分可重试与永久数据错误。

**怎么处理。** 将不可处理事件写入死信并保留原载荷与原因；设置重试上限；人工修复后受控重放；监控死信增长。

**验收结论。** 不让单条坏事件停止全局，但隔离也不能变成静默丢弃。

### 5. 实时特征训练离线特征不一致

**现场。** 模型离线评估正常，上线效果明显下降。

**怎么查。** 比较训练和在线特征的计算时点、缺失填充、窗口和标签泄漏，发现在线使用未来状态补齐。

**怎么处理。** 建立同一特征定义和版本；上线前做回放一致性测试；在线缺失保持真实缺失；监控特征漂移和可用率。

**验收结论。** 线上特征必须能在同一时点复现训练值，不能为了完整率偷偷使用未来数据。

### 6. 自动风控触发误冻结

**现场。** 实时规则更新后，一批正常账户被自动冻结。

**怎么查。** 回放规则版本、特征值、阈值和人工复核记录，发现上游状态字段枚举变化触发默认高风险。

**怎么处理。** 高风险动作设置双阈值和人工闸门；规则发布灰度；未知枚举不按最高风险自动执行；保留申诉与回滚。

**验收结论。** 实时能力不带人工复核直接触发资金、权限或人身风险，是不可接受的设计。

### 7. 区域故障后重复补发通知

**现场。** 消息集群切换后同一批告警重复发送给用户。

**怎么查。** 核对生产游标、消费偏移、通知幂等键和渠道去重，发现故障恢复后从更早偏移重放。

**怎么处理。** 通知按业务事件和渠道建立幂等键；非幂等外部动作由工作流确认；恢复时先重算状态和待发清单。

**验收结论。** 流处理恢复不只恢复计算，还要恢复对不可逆外部副作用的理解。

七个场景可以归成一条共同判断顺序：先确认对象和时间，再确认状态和版本；然后做总量、结构和明细三层对账；最后才讨论策略、模型或工具。若一条结论不能指出对应的原始记录、责任人和行动出口，就只能算观察，不能作为生产结论。

## 6. 实时数据架构概述的第一段 SQL：重建业务链路

下面的 SQL 用于说明对象、时间、状态、版本和分层口径如何进入同一条可复查路径。表名和部分字段是通用示例，落地时应映射到企业数据字典；SQL 方言也需按实际引擎调整。

```sql
-- 实时数据架构概述：按业务对象重建链路，避免事件、快照和结果混算
WITH ranked_event_delivery_id AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY event_delivery_id
      ORDER BY updated_at DESC
    ) AS version_no
  FROM realtime_event_delivery
  WHERE event_time >= TIMESTAMP '{start_time}'
    AND event_time <  TIMESTAMP '{end_time}'
    AND delivery_status NOT IN ('deleted', 'test')
),
valid_rows AS (
  SELECT
    event_delivery_id,
    topic_name,
    consumer_group,
    business_domain,
    event_type,
    event_time,
    delivery_status,
    ingested_at
  FROM ranked_event_delivery_id
  WHERE version_no = 1
)
SELECT
  topic_name, consumer_group, business_domain, event_type,
  COUNT(DISTINCT event_delivery_id) AS object_cnt,
  COUNT(DISTINCT CASE WHEN delivery_status = 'committed' THEN event_id END) AS numerator_value,
  COUNT(DISTINCT event_id) AS denominator_value,
  CAST(COUNT(DISTINCT CASE WHEN delivery_status = 'committed' THEN event_id END) AS DOUBLE PRECISION)
    / NULLIF(COUNT(DISTINCT event_id), 0) AS metric_value,
  MIN(event_time) AS first_event_at,
  MAX(event_time) AS last_event_at
FROM valid_rows
GROUP BY topic_name, consumer_group, business_domain, event_type
ORDER BY metric_value DESC, object_cnt DESC;
```

执行后至少回答六个问题：

- 同一对象是否因为多源回传产生多版本，版本保留是否符合业务要求？
- 业务时间与入仓时间是否分开，补录和迟到数据是否进入正确分区？
- 分子分母是否来自同一对象范围和同一统计窗口？
- 维度使用的是事件当时值还是当前值，跨期比较是否一致？
- 删除、撤销、冻结和测试数据是否按规则处理？
- 分组结果能否在明细中抽样复现？

## 7. 实时数据架构概述的第二段 SQL：源、控制和结果三方对账

```sql
-- 实时数据架构概述：源对象、控制对象和结果对象三方对账
WITH population AS (
  SELECT
    event_delivery_id,
    event_time,
    delivery_status
  FROM realtime_event_delivery
  WHERE event_time >= TIMESTAMP '{start_time}'
    AND event_time <  TIMESTAMP '{end_time}'
),
control AS (
  SELECT
    event_delivery_id,
    SUM(committed_offset) AS control_value,
    COUNT(DISTINCT checkpoint_id) AS control_cnt,
    MAX(updated_at) AS control_updated_at
  FROM stream_checkpoint_state
  WHERE updated_at >= TIMESTAMP '{start_time}'
  GROUP BY event_delivery_id
),
result AS (
  SELECT
    event_delivery_id,
    COUNT(*) AS result_cnt,
    MAX(calculated_at) AS calculated_at
  FROM mart_event_delivery_id
  WHERE business_date BETWEEN DATE '{start_date}' AND DATE '{end_date}'
  GROUP BY event_delivery_id
)
SELECT
  COALESCE(p.event_delivery_id, c.event_delivery_id, r.event_delivery_id) AS object_key,
  CASE
    WHEN p.event_delivery_id IS NULL THEN 'source_missing'
    WHEN c.event_delivery_id IS NULL THEN 'control_missing'
    WHEN r.event_delivery_id IS NULL THEN 'result_missing'
    WHEN ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0 THEN 'count_or_value_gap'
    ELSE 'matched'
  END AS reconciliation_status,
  p.delivery_status,
  c.control_value,
  c.control_cnt,
  r.result_cnt,
  c.control_updated_at,
  r.calculated_at
FROM population p
FULL OUTER JOIN control c ON p.event_delivery_id = c.event_delivery_id
FULL OUTER JOIN result r ON COALESCE(p.event_delivery_id, c.event_delivery_id) = r.event_delivery_id
WHERE p.event_delivery_id IS NULL
   OR c.event_delivery_id IS NULL
   OR r.event_delivery_id IS NULL
   OR ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0;
```

这段查询故意不使用“总数相差小于某个随意百分比就算通过”。它先找出缺失对象和状态差异，再检查控制值与结果值。对于实时数据架构概述，数量、金额、时长或状态任意一项无法解释，都不能用“业务波动”代替排查。

对账结果建议分成四类处理：

1. **阻断**：对象缺失、关键时间为空、状态非法、金额或数量不守恒、权限越界。
2. **严重**：比例或总量显著偏离基线，且无法由已确认的对象结构变化解释。
3. **观察**：小范围波动但来源、样本和趋势可控，进入责任人和观察窗口。
4. **探索**：只有弱信号或假设，不进入正式结论，更不直接触发业务处罚。

## 8. 实时数据架构概述的 Python 发布门禁与指标护栏

第一段代码把发布条件写成可执行对象，避免“检查过了”只存在聊天记录里：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class EventDeliveryIdBatch:
    batch_id: str
    source_rows: int
    valid_rows: int
    duplicate_keys: int
    missing_required_fields: int
    reconciliation_gap: float

def release_event_delivery_id(batch: EventDeliveryIdBatch) -> dict:
    checks = {
        "source_not_empty": batch.source_rows > 0,
        "valid_rows_in_range": 0 <= batch.valid_rows <= batch.source_rows,
        "duplicate_rate_ok": batch.duplicate_keys / max(batch.source_rows, 1) <= 0.001,
        "required_fields_ok": batch.missing_required_fields == 0,
        "reconciliation_ok": abs(batch.reconciliation_gap) <= 0.01,
    }
    return {
        "topic": "实时数据架构概述",
        "batch_id": batch.batch_id,
        "checks": checks,
        "release_allowed": all(checks.values()),
        "blocking_checks": [name for name, passed in checks.items() if not passed],
    }
```

第二段代码演示如何为比例类结果附带样本证据和小样本下界。它不是替代统计学家的模型，而是防止把少量偶然样本直接包装成稳定结论：

```python
from dataclasses import dataclass
from math import sqrt

@dataclass(frozen=True)
class EventDeliveryIdObservation:
    object_id: str
    numerator: float
    denominator: float
    sample_size: int
    scope_version: str

def calculate_event_delivery_id(rows: list[EventDeliveryIdObservation]) -> list[dict]:
    output = []
    for row in rows:
        value = row.numerator / row.denominator if row.denominator > 0 else None
        # 小样本用 Wilson 下界做护栏，不把偶然的高比例直接当稳定结果。
        z = 1.96
        p = value or 0
        n = max(row.sample_size, 1)
        center = p + z * z / (2 * n)
        margin = z * sqrt((p * (1 - p) + z * z / (4 * n)) / n)
        lower = max(0, (center - margin) / (1 + z * z / n))
        output.append({
            "object_id": row.object_id,
            "metric": "事件端到端延迟",
            "value": value,
            "lower_bound": lower if value is not None else None,
            "sample_size": row.sample_size,
            "scope_version": row.scope_version,
            "caution": "报告 P50、P95、P99 和超阈值比例",
        })
    return output
```

真正上线时还要补充参数配置、日志、血缘、告警级别、重跑幂等、异常样本保存和审批记录。代码通过不代表业务通过；自动检查只能证明已经定义的规则没有被违反，无法证明规则本身一定正确。

## 9. 实时数据架构概述的失败反例与上线验收

| 风险信号 | 错误做法 | 必须补齐的证据 | 发布或行动规则 |
| --- | --- | --- | --- |
| 处理时间当业务时间 | 窗口随系统时钟漂移 | 事件时间、迟到分布和水位 | 按业务时间计算并公布稳定点 |
| 重复外部副作用 | 重放重复发券或通知 | 幂等键、发送清单和渠道记录 | 不可逆动作需工作流幂等 |
| 毒消息无限重试 | 单条异常阻塞全分区 | 死信、重试上限和修复流程 | 隔离后受控重放 |
| 实时结果直接结算 | 未对账就进入资金流程 | 稳定版本、离线对账和审批 | 关键结算使用批准口径 |

上线验收不应只有一句“报表正常”。建议按下面四层验收：

| 验收对象 | 结构要求 | 测试样本 | 结果证据 |
| --- | --- | --- | --- |
| 事件 | `event_id` 能唯一定位一次不可变的业务发生或状态变化 | 正常、重复、缺失、撤销与跨期样本 | 事件端到端延迟可回到原始对象 |
| 分区偏移 | `topic_partition_offset` 能唯一定位某消费者在主题分区中的处理位置 | 正常、重复、缺失、撤销与跨期样本 | 输入输出平衡率可回到原始对象 |
| 水位 | `watermark_id` 能唯一定位某时间域内已经允许推进完整性的标记 | 正常、重复、缺失、撤销与跨期样本 | 检查点恢复时长可回到原始对象 |
| 实时状态 | `state_record_id` 能唯一定位有状态作业为业务对象保存的最新可恢复状态 | 正常、重复、缺失、撤销与跨期样本 | 死信安全处置率可回到原始对象 |
| 结果快照 | `realtime_result_id` 能唯一定位指定事件水位和处理版本下的可见结果 | 正常、重复、缺失、撤销与跨期样本 | 实时离线差异率可回到原始对象 |
| 死信记录 | `dead_letter_id` 能唯一定位无法在当前规则下安全处理并需隔离的事件 | 正常、重复、缺失、撤销与跨期样本 | 事件端到端延迟可回到原始对象 |

还应为每一次发布保留一组固定回归样本：正常对象、边界状态、重复记录、缺失字段、撤销或退款、跨期、权限拒绝和失败恢复。回归样本不是演示数据，而是以后每次改规则都能重复执行的质量资产。

## 10. 实时数据架构概述的 30 天落地与复盘

| 阶段 | 主要交付 | 通过条件 |
| --- | --- | --- |
| 第 1 周：定义 | 对象、流程、状态、指标、排除项和责任矩阵 | 业务、数据、安全或质量负责人对同一口径签字 |
| 第 2 周：打通 | 源字段、主键、时间、版本、控制对象和失败样本 | 正常与异常样本都能回到原始记录 |
| 第 3 周：验证 | 总量对账、分层对账、抽样回查、权限测试、回滚演练 | 阻断问题清零，严重问题有责任人与期限 |
| 第 4 周：发布 | 灰度、SLO、监控、行动清单、停止条件和复盘模板 | 使用者在真实场景中完成一次闭环行动 |

如果必须用 90 秒说明“实时数据架构概述”是否做对，可以按这个顺序自测：

1. 一行数据代表什么，主键是什么，哪些对象绝不能混在同一粒度？
2. 业务发生、数据可见、计算完成和行动确认分别在哪个时间点？
3. 本主题最重要的两个主指标、三个护栏和最小样本量是什么？
4. 一个异常出现时，先从原始记录、链路版本还是业务动作开始查？
5. 哪类错误必须阻断发布或停止使用，谁有权批准例外？
6. 上线后由谁在多长时间内观察，什么条件下回滚或结束？

> [!check] 完成标准
> 当另一位数据同事不看聊天记录，只根据口径卡、回归样本和代码就能复跑同一结果；当业务负责人能指出一个异常对应的原始对象、处置动作和复核证据；当系统能够阻止未授权或状态非法的数据进入下游，这篇“实时数据架构概述”才算真正落到工作里。
