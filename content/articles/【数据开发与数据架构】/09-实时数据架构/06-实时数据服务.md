# 实时数据服务

> [!abstract] 工程视角
> 把“实时数据服务”放进数据接入、离线与实时处理、数仓建模、调度发布、数据服务、稳定性和成本治理，真正困难的通常不是解释名词，而是把它变成一条能被核对、能被复现、也能推动行动的工程链路。本文不追求堆满概念，而是围绕这个主题拆出业务对象、数据粒度、典型故障、代码验证和验收方式。

## 1. 需求、SLA 与边界

“实时数据服务”首先是工程问题，其次才是工具选择。立项时明确：

- 谁消费数据或服务，用来做什么决策或操作。
- 数据从产生到可用允许延迟多久，失败时能否接受部分结果。
- 更新频率、保留周期、回放范围、并发和数据量级。
- 上下游依赖、权限、敏感字段、审计和成本上限。
- 正确性、完整性和一致性中，哪些必须强保证，哪些可最终一致。

数据开发与数据架构中常见的交付指标包括任务成功率、数据延迟、资源消耗。不要只写“稳定”“高效”，应定义可监测的 SLI、SLO 和错误预算。

## 2. 数据链路与模型

| 层次 | 本文建议 | 关键问题 | 验收证据 |
| --- | --- | --- | --- |
| 数据源 | 调度平台、元数据平台、数据质量平台 | 权威源、更新频率、主键和权限 | 接口或表清单 |
| 接入 | 批、流或 CDC 按业务时延选择 | 重复、顺序、断点续传和回放 | 延迟与幂等测试 |
| 存储 | 按访问模式选择数据湖、数仓或 OLAP | 分区、格式、生命周期和成本 | 容量与查询评测 |
| 计算 | SQL、Spark、Flink 或 Python 服务 | 粒度、状态、资源和失败恢复 | 压测与执行计划 |
| 治理 | 元数据、质量、血缘、权限 | 责任、规则、影响分析和审计 | 规则结果与变更记录 |
| 服务 | 指标、API、看板或应用 | SLA、缓存、限流和版本 | 监控与验收样例 |

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 数据源 | `source_id` | 需求评审 |
| 过程对象 | 数据表 | `table_id` | 源系统接入 |
| 过程对象 | 处理任务 | `job_id` | 模型设计 |
| 结果对象 | 数据服务 | `service_id` | 开发测试 |
| 结果对象 | 运行实例 | `run_id` | 发布调度 |
| 专题分析 | 实时数据服务 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

链路设计先明确事实粒度。例如一行代表一次事件、一条订单明细、一个每日快照还是一个任务运行实例。粒度一旦混用，后面即使加了汇总表，也会把数量和金额累计两次。

## 3. 案例一：华东某零售数据平台

### 案例 1：华东某零售数据平台的“实时数据服务”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“实时数据服务”映射到“数据服务、API 与语义层”中的权限，而不是泛泛讨论概念。
- **触发事件**：多个活动页面直接调用明细接口，月初并发升高后数据库变慢。
- **业务与数据范围**：API 调用量、查询参数、热点租户、缓存命中、P95 和数据库执行计划。数据侧重点采集令牌、租户、用途、字段和行过滤记录，并与调度平台、元数据平台、数据质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：调用方、用户身份、数据范围和行级权限如何传递。
- **关键障碍**：接口允许任意维度和时间范围查询，无分页、限流与缓存，权限校验还会触发额外全表扫描。同时要防止重复写入把表面指标带偏。
- **处理过程**：收窄查询契约，增加聚合结果缓存、租户限流、分页和慢查询拒绝，并把数据版本返回给调用方。实施时把“P95、错误率、限流、缓存、慢查询和成本都有监控”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例服务用 P95、错误率、缓存命中、数据库负载和结果一致性验收。验收至少同时看主指标、令牌、租户、用途、字段和行过滤记录和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把数据能力封装成有契约、有版本、有权限、有 SLA、有监控的服务，并明确查询、缓存、限流和失败降级。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

### 专题实现代码

```python
from fastapi import Depends, FastAPI, HTTPException
from pydantic import BaseModel, Field

app = FastAPI()

class MetricQuery(BaseModel):
    metric: str = Field(pattern="^(gmv|paid_orders|refund_rate)$")
    date_from: str
    date_to: str
    merchant_id: str
    page_size: int = Field(default=100, le=500)

def current_user() -> dict:
    return {"tenant_id": "demo", "scopes": {"metric:read"}, "merchant_scope": {"M1001"}}

@app.post("/v1/metrics/query")
def query_metric(body: MetricQuery, user: dict = Depends(current_user)):
    if "metric:read" not in user["scopes"]:
        raise HTTPException(status_code=403, detail="scope_missing")
    if body.merchant_id not in user["merchant_scope"]:
        raise HTTPException(status_code=403, detail="row_scope_denied")
    return {
        "topic": "\"实时数据服务\"",
        "data_version": "2026-11-05T02:15:00+08:00",
        "p95_budget_ms": 800,
    }

# 版本、字段、错误码、权限、数据新鲜度、超时、扫描上限和分页都属于接口契约；
# Text-to-SQL 与 Agent-to-Data 必须经过同一权限、成本和审计链路。
```

### 统一口径诊断 SQL

```sql
-- 实时数据服务：分位对比诊断（数据层 × 调度周期）
WITH scoped AS (
  SELECT
    source_id AS entity_key,
    event_id,
    run_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_pipeline_run
  WHERE run_time >= DATE '2026-07-01'
    AND run_time <  DATE '2026-10-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '重跑率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

工程代码至少要满足以下要求：

1. 输入输出明确，参数来自配置或调度上下文。
2. 重跑同一分区不会产生重复结果。
3. 关键步骤记录度量，便于定位数据量和状态变化。
4. 失败可重试，但不会无限重试或放大副作用。
5. 版本、表结构和依赖变更可追踪。
6. 敏感信息不写进代码、日志和异常信息。

## 5. 测试方法与质量门禁

| 专题检查项 | 失败时会看到什么 | 首选证据 | 处理动作 |
| --- | --- | --- | --- |
| 接口契约覆盖字段、错误码、版本、权限和数据新鲜度 | 调用方、用户身份、数据范围和行级权限如何传递 | 令牌、租户、用途、字段和行过滤记录 | 禁止只在前端做权限 |
| 服务端执行身份、租户、行级和字段级权限校验 | 服务结果来自哪张表、哪个快照和哪次更新 | 数据版本、延迟、对账和回放记录 | 业务必须知道数据新鲜度 |
| P95、错误率、限流、缓存、慢查询和成本都有监控 | 请求、响应、字段、错误码和版本是否稳定 | OpenAPI、Schema、兼容测试和样例 | 不兼容变更必须新版本 |
| 数据版本、查询逻辑和结果快照可追溯 | P50/P95、并发、缓存、扫描量和数据库压力 | 指标、压测、慢查询和容量基线 | 先限流再扩容 |

### 质量门禁与失败样本

```python
# 实时数据服务：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "实时数据服务"
TOPIC_KEY = "subject"
RULE_ID = "rule_engineering_1c3cys6"
GUIDE_CHECKS = [
    "接口契约覆盖字段、错误码、版本、权限和数据新鲜度",
    "服务端执行身份、租户、行级和字段级权限校验",
    "P95、错误率、限流、缓存、慢查询和成本都有监控",
    "数据版本、查询逻辑和结果快照可追溯"
]
RULES = {
    "required_columns": ["event_id", "source_id", "run_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "source_id",
    "time_field": "run_time",
    "max_duplicate_rate": 0.0009,
    "max_null_rate": 0.003,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：接口契约覆盖字段、错误码、版本、权限和数据新鲜度；服务端执行身份、租户、行级和字段级权限校验；P95、错误率、限流、缓存、慢查询和成本都有监控；数据版本、查询逻辑和结果快照可追溯
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

测试分为开发环境和生产前门禁。开发环境可以使用抽样数据快速验证逻辑，生产前门禁必须检查分区覆盖、主键、比例异常、上下游对账和资源消耗。数据发布后还要验证消费者能够读取、权限正确且时延在 SLA 内。

## 7. 性能、容量与成本

| 瓶颈 | 先测量 | 可选手段 | 风险 |
| --- | --- | --- | --- |
| 扫描过多 | 分区命中、文件数、字节数 | 分区裁剪、列裁剪、压缩格式 | 分区过碎 |
| Shuffle 重 | 数据量、键分布、并发 | 预聚合、盐化、调整并发 | 资源争抢 |
| 热点倾斜 | Task 时长、输入大小 | 拆分热点键、两阶段聚合 | 结果顺序变化 |
| 状态过大 | Checkpoint、状态后端 | TTL、增量 Checkpoint、拆分 | 业务语义风险 |
| 查询慢 | 执行计划、缓存命中 | 预聚合、物化视图、OLAP | 数据新鲜度 |
| 成本高 | CPU、内存、存储、调用 | 生命周期、冷热分层、弹性 | SLA 退化 |

调优必须建立基线和回归对比：执行时间、扫描量、Shuffle 量、峰值内存、失败率和成本。只展示一次“从 30 分钟到 3 分钟”不够，还要说明数据量、资源和结果是否正确。

## 9. 发布、监控与故障处理

发布流程建议包括：代码评审、配置评审、数据迁移评审、灰度、对账、可观测性检查和回滚演练。监控至少覆盖任务、数据、服务、资源和业务五层。

故障处理顺序：

1. 确认影响面和是否需要暂停下游。
2. 保存现场：任务日志、参数、版本、输入输出计数。
3. 阻断错误扩散，必要时回滚到上一个稳定版本。
4. 按源系统、接入、计算、存储、服务和消费逐层定位。
5. 修复后按受影响分区补数，并验证重复、缺失和时序。
6. 完成问题时间线、根因、影响、改进和复核。

## 10. 验收清单

- 表结构、主键、分区、生命周期和负责人已登记。
- 关键任务具备幂等、重试、超时、告警和回滚。

### 案例 4：实时数据服务的最小权限与越权核查

某数据开发与数据架构团队在季度复盘时重新讨论“实时数据服务”。讨论并没有从工具选型开始，而是先追问一个更基础的问题：分析结果本身可以访问，但派生字段、导出文件和临时表扩大了敏感数据范围，现有流程没有及时识别。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 让数据用途、最小字段、访问角色、加工产物、保存期限和撤回机制都可追溯。在本场景里，核心风险还包括依赖环，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：数据源、数据表及其在质量监控前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注source_id与table_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 分析结果本身可以访问，但派生字段、导出文件和临时表扩大了敏感数据范围，现有流程没有及时识别。初看时，数据仓库与API 网关的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 分类分级、授权记录、字段血缘、访问日志、导出清单、脱敏规则和过期清理记录。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“安全”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“实时数据服务”的当前定义并记录版本；第二步用数据源明细核对数据仓库到API 网关的关联；第三步按数据层与调度周期做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察数据延迟和护栏指标重跑率。
- **行动与护栏：** 按任务拆分数据集与角色，使用最小字段和临时授权，发布前检查派生表与导出是否出现敏感扩散。专题检查项“接口契约覆盖字段、错误码、版本、权限和数据新鲜度”被写成发布门禁，高风险字段缺少授权、脱敏或审计时不进入分析环境，紧急访问必须到期自动回收。
- **失败路径：** 把“内网可访问”当成“业务已授权”，或者用永久大权限账号支撑临时分析。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“实时数据服务”时，先验证令牌、租户、用途、字段和行过滤记录，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由安全在明确时限内，根据数据延迟、重跑率和任务幂等决定继续、回退、补查还是转人工。 若依赖环或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

```sql
)
SELECT
  COALESCE(s.entity_key, r.entity_key) AS entity_key,
  s.event_cnt AS source_event_cnt,
  r.event_cnt AS result_event_cnt,
  s.metric_sum AS source_metric_sum,
  r.metric_sum AS result_metric_sum,
  COALESCE(r.metric_sum, 0) - COALESCE(s.metric_sum, 0) AS metric_diff
FROM source_side s
FULL OUTER JOIN result_side r USING (entity_key)
WHERE ABS(COALESCE(r.metric_sum, 0) - COALESCE(s.metric_sum, 0)) > 0
   OR COALESCE(s.event_cnt, 0) <> COALESCE(r.event_cnt, 0)
ORDER BY ABS(metric_diff) DESC;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把实时数据服务的验收证据写成门禁

```python
from datetime import date
from hashlib import sha256

import pandas as pd

SUBJECT = "实时数据服务"
BLOCKING_RULES = ["分区覆盖完整","任务幂等","依赖无环"]


def validate_release(frame: pd.DataFrame, start: date, end: date) -> dict:
    scoped = frame.loc[
        frame["event_date"].between(pd.Timestamp(start), pd.Timestamp(end))
        & (frame["subject_key"] == "subject")
    ].copy()
    checks = {
        "has_rows": len(scoped) > 0,
        "event_id_unique": not scoped["event_id"].duplicated().any(),
        "entity_key_complete": scoped["entity_key"].notna().all(),
        "event_time_present": scoped["event_time"].notna().all(),
        "scope_matches": scoped["subject_key"].nunique() == 1,
    }
    payload = f"{SUBJECT}|{start}|{end}|{len(scoped)}|{sorted(checks.items())}"
    return {
        "subject": SUBJECT,
        "rows": len(scoped),
        "checks": checks,
        "blocking_rules": BLOCKING_RULES,
        "release_allowed": all(checks.values()),
        "evidence_hash": sha256(payload.encode("utf-8")).hexdigest(),
    }
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。

### 四个案例共用的验收清单

| 验证面 | 发布前问题 | 证据 | 不通过时 |
| --- | --- | --- | --- |
| 对象与粒度 | 一行数据代表数据源、事件、快照还是结果 | 主键、版本、有效时间和边界样本 | 阻断 |
| 时间语义 | 业务发生、数据可见、决策采用是否混用 | run_time、入仓时间、行动时间轴 | 阻断 |
