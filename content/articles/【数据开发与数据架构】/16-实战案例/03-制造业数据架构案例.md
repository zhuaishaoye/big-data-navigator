# 制造业数据架构案例

> [!abstract] 工程视角
> 讨论“制造业数据架构案例”时，最容易犯的错误是直接从工具或报表开始。更有用的顺序是：先看业务链条，再找可观察指标，随后确认数据粒度，最后才选择 SQL、模型或平台组件。本文按这个顺序给出可执行方案和常见的失败样本。

## 1. 需求、SLA 与边界

“制造业数据架构案例”首先是工程问题，其次才是工具选择。立项时明确：

- 谁消费数据或服务，用来做什么决策或操作。
- 数据从产生到可用允许延迟多久，失败时能否接受部分结果。
- 更新频率、保留周期、回放范围、并发和数据量级。
- 上下游依赖、权限、敏感字段、审计和成本上限。
- 正确性、完整性和一致性中，哪些必须强保证，哪些可最终一致。

制造业中常见的交付指标包括良品率、设备稼动率、计划达成率。不要只写“稳定”“高效”，应定义可监测的 SLI、SLO 和错误预算。

## 2. 数据链路与模型

| 层次 | 本文建议 | 关键问题 | 验收证据 |
| --- | --- | --- | --- |
| 数据源 | ERP、MES、PLM | 权威源、更新频率、主键和权限 | 接口或表清单 |
| 接入 | 批、流或 CDC 按业务时延选择 | 重复、顺序、断点续传和回放 | 延迟与幂等测试 |
| 存储 | 按访问模式选择数据湖、数仓或 OLAP | 分区、格式、生命周期和成本 | 容量与查询评测 |
| 计算 | SQL、Spark、Flink 或 Python 服务 | 粒度、状态、资源和失败恢复 | 压测与执行计划 |
| 治理 | 元数据、质量、血缘、权限 | 责任、规则、影响分析和审计 | 规则结果与变更记录 |
| 服务 | 指标、API、看板或应用 | SLA、缓存、限流和版本 | 监控与验收样例 |

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 工厂 | `plant_id` | 需求计划 |

链路设计先明确事实粒度。例如一行代表一次事件、一条订单明细、一个每日快照还是一个任务运行实例。粒度一旦混用，后面即使加了汇总表，也会把数量和金额累计两次。

## 3. 案例一：华北某制造集团

### 案例 1：华北某制造集团的“制造业数据架构案例”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“制造业数据架构案例”映射到“数据架构、平台与云原生基础设施”中的数据流，而不是泛泛讨论概念。
- **触发事件**：集团建设统一数据中台后，工厂实时数据仍无法稳定支持排产。
- **业务与数据范围**：MES、设备事件、工单、主数据、边缘缓存、网络和下游 API。数据侧重点采集源系统、粒度、频率、容量和延迟，并与ERP、MES、PLM中的时间、状态和责任人信息对齐。
- **需要回答的问题**：批、流、CDC、共享与服务之间如何衔接。
- **关键障碍**：所有数据被集中到中心后才处理，实时链路受网络和跨域权限影响，主数据版本也不一致。同时要防止设备与工单编码变化导致断链把表面指标带偏。
- **处理过程**：采用边缘预处理与中心治理结合，明确设备、工单和批次主键，按场景拆分实时与离线职责。实施时把“跨域数据流有契约、主键、版本、权限和故障隔离”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例项目用端到端延迟、设备覆盖率、数据完整率和恢复时间验收。验收至少同时看主指标、源系统、粒度、频率、容量和延迟和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“从业务能力、数据流、访问模式、一致性、SLA、安全和成本出发拆分组件，并用可验证的非功能指标约束演进。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

### 专题实现代码

```python
from dataclasses import dataclass, field
from statistics import mean

TOPIC = "制造业数据架构案例"
DECISION_ID = "g_data_architecture_1vca3pe"

@dataclass
class ArchitectureOption:
    name: str
    latency_ms: float
    availability: float
    monthly_cost: float
    migration_weeks: float
    operational_risk: float
    evidence: list[str] = field(default_factory=list)

def normalized_score(option: ArchitectureOption) -> dict:
    # 示例权重来自业务约束，生产评审应由业务、平台、安全与运维共同确认。
    values = {
        "latency": max(0.0, 1 - option.latency_ms / 5000),
        "availability": option.availability,
        "cost": max(0.0, 1 - option.monthly_cost / 300000),
        "delivery": max(0.0, 1 - option.migration_weeks / 52),
        "risk": max(0.0, 1 - option.operational_risk),
    }
    weights = {"latency": 0.24, "availability": 0.22, "cost": 0.18, "delivery": 0.16, "risk": 0.20}
    return {
        "option": option.name,
        "score": round(sum(values[key] * weights[key] for key in weights), 4),
        "evidence_complete": len(option.evidence) >= 3,
        **values,
    }

decision_checks = [
    "每个组件都对应明确业务能力、数据流和消费方，而非只为技术栈完整",
    "架构决策同时评估 SLA、一致性、安全、容量、成本和可运维性",
    "跨域数据流有契约、主键、版本、权限和故障隔离"
]
assert all(decision_checks), "architecture decision cannot pass without explicit constraints"

# 主题："制造业数据架构案例"
```

### 统一口径诊断 SQL

```sql
-- 制造业数据架构案例：分位对比诊断（产线 × 班组）
WITH scoped AS (
  SELECT
    plant_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_manufacturing_event
  WHERE event_time >= DATE '2026-03-01'
    AND event_time <  DATE '2026-06-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '单位制造成本' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

工程代码至少要满足以下要求：

1. 输入输出明确，参数来自配置或调度上下文。
2. 重跑同一分区不会产生重复结果。
3. 关键步骤记录度量，便于定位数据量和状态变化。
4. 失败可重试，但不会无限重试或放大副作用。
5. 版本、表结构和依赖变更可追踪。
6. 敏感信息不写进代码、日志和异常信息。

### 质量门禁与失败样本

```python
# 制造业数据架构案例：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "制造业数据架构案例"
TOPIC_KEY = "subject"
RULE_ID = "rule_manufacturing_1vca3pe"
GUIDE_CHECKS = [
    "每个组件都对应明确业务能力、数据流和消费方，而非只为技术栈完整",
    "架构决策同时评估 SLA、一致性、安全、容量、成本和可运维性",
    "跨域数据流有契约、主键、版本、权限和故障隔离",
    "迁移方案包含双跑对账、灰度、数据校验和可执行回滚"
]
RULES = {
    "required_columns": ["event_id", "plant_id", "event_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "plant_id",
    "time_field": "event_time",
    "max_duplicate_rate": 0.0009,
    "max_null_rate": 0.003,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：每个组件都对应明确业务能力、数据流和消费方，而非只为技术栈完整；架构决策同时评估 SLA、一致性、安全、容量、成本和可运维性；跨域数据流有契约、主键、版本、权限和故障隔离；迁移方案包含双跑对账、灰度、数据校验和可执行回滚
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

测试分为开发环境和生产前门禁。开发环境可以使用抽样数据快速验证逻辑，生产前门禁必须检查分区覆盖、主键、比例异常、上下游对账和资源消耗。数据发布后还要验证消费者能够读取、权限正确且时延在 SLA 内。

## 7. 性能、容量与成本

| 瓶颈 | 先测量 | 可选手段 | 风险 |
| --- | --- | --- | --- |
| 扫描过多 | 分区命中、文件数、字节数 | 分区裁剪、列裁剪、压缩格式 | 分区过碎 |
| Shuffle 重 | 数据量、键分布、并发 | 预聚合、盐化、调整并发 | 资源争抢 |
| 热点倾斜 | Task 时长、输入大小 | 拆分热点键、两阶段聚合 | 结果顺序变化 |
| 状态过大 | Checkpoint、状态后端 | TTL、增量 Checkpoint、拆分 | 业务语义风险 |
| 查询慢 | 执行计划、缓存命中 | 预聚合、物化视图、OLAP | 数据新鲜度 |
| 成本高 | CPU、内存、存储、调用 | 生命周期、冷热分层、弹性 | SLA 退化 |

调优必须建立基线和回归对比：执行时间、扫描量、Shuffle 量、峰值内存、失败率和成本。只展示一次“从 30 分钟到 3 分钟”不够，还要说明数据量、资源和结果是否正确。

## 8. 案例三：华南某金融机构

### 案例 3：华南某金融机构的“制造业数据架构案例”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“制造业数据架构案例”映射到“数据架构、平台与云原生基础设施”中的非功能，而不是泛泛讨论概念。

- **可迁移结论**：遇到类似标题时，先按“从业务能力、数据流、访问模式、一致性、SLA、安全和成本出发拆分组件，并用可验证的非功能指标约束演进。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

## 9. 发布、监控与故障处理

发布流程建议包括：代码评审、配置评审、数据迁移评审、灰度、对账、可观测性检查和回滚演练。监控至少覆盖任务、数据、服务、资源和业务五层。

故障处理顺序：

1. 确认影响面和是否需要暂停下游。
2. 保存现场：任务日志、参数、版本、输入输出计数。
3. 阻断错误扩散，必要时回滚到上一个稳定版本。
4. 按源系统、接入、计算、存储、服务和消费逐层定位。
5. 修复后按受影响分区补数，并验证重复、缺失和时序。
6. 完成问题时间线、根因、影响、改进和复核。

### 案例 4：制造业数据架构案例从源事件到结果的长链路核查

一次例行发布后，负责“制造业数据架构案例”的小组收到下游反馈：数字和源系统对不上，但任务本身全部成功。团队决定围绕“链路断点与延迟”做一次完整回放。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 把业务发生时间、数据可见时间、任务完成时间和下游消费时间放到同一条证据链。在本场景里，核心风险还包括停机时长重复计算，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：工厂、产线及其在备料前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注plant_id与line_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 结果表出现缺失或延迟，单看调度状态却显示成功，无法判断问题发生在源端、接入、计算还是服务层。初看时，SCADA与设备物联网平台的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 源端操作日志、CDC/批次水位、分区清单、任务参数、血缘关系、下游请求日志。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“工艺”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“制造业数据架构案例”的当前定义并记录版本；第二步用工厂明细核对SCADA到设备物联网平台的关联；第三步按产线与班组做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察设备稼动率和护栏指标单位制造成本。
- **行动与护栏：** 按时间轴核对每一跳的输入输出计数与水位，先阻断错误结果扩散，再确定重跑范围和补数窗口。专题检查项“每个组件都对应明确业务能力、数据流和消费方，而非只为技术栈完整”被写成发布门禁，无法证明数据完整的链路不进入正式发布，优先保留旧版本供下游读取。
- **失败路径：** 看到任务成功就立即补数，却没有确认重复、乱序和迟到事件。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“制造业数据架构案例”时，先验证源系统、粒度、频率、容量和延迟，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由工艺在明确时限内，根据设备稼动率、单位制造成本和停机区间不重叠决定继续、回退、补查还是转人工。 若停机时长重复计算或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

- **处理步骤：** 第一步先冻结“制造业数据架构案例”的当前定义并记录版本；第二步用工单明细核对MES到PLM的关联；第三步按设备类型与产线做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察准时交付率和护栏指标设备稼动率。
- **行动与护栏：** 保存现场并停止下游扩散，按影响边界回滚或隔离结果，使用幂等任务从最小必要范围重新计算。专题检查项“迁移方案包含双跑对账、灰度、数据校验和可执行回滚”被写成发布门禁，恢复任务没有对账、没有版本记录或无法重复执行时，不宣布故障结束。
- **失败路径：** 直接覆盖目标表，或者把所有分区全部重跑以求省事。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“制造业数据架构案例”时，先验证能力地图、用例、消费方和现状痛点，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由质量在明确时限内，根据准时交付率、设备稼动率和设备组织关系保留有效期决定继续、回退、补查还是转人工。 若在制品状态回退或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从制造业数据架构案例回到可核对明细

```sql
-- 制造业数据架构案例：发布前质量画像
SELECT
  'subject' AS subject_key,
  stat_date,
  COUNT(*) AS row_cnt,
  COUNT(DISTINCT event_id) AS distinct_event_cnt,
  SUM(CASE WHEN event_id IS NULL THEN 1 ELSE 0 END) AS null_event_cnt,
  SUM(CASE WHEN event_time < business_time THEN 1 ELSE 0 END) AS time_reverse_cnt,
  SUM(CASE WHEN status NOT IN ('valid', 'completed', 'cancelled') THEN 1 ELSE 0 END) AS invalid_status_cnt,
  ROUND(COUNT(*) * 1.0 / NULLIF(COUNT(DISTINCT event_id), 0), 4) AS duplication_ratio
FROM fact_manufacturing_event
WHERE stat_date BETWEEN :start_date AND :end_date
GROUP BY stat_date
HAVING SUM(CASE WHEN event_id IS NULL THEN 1 ELSE 0 END) > 0
    OR SUM(CASE WHEN event_time < business_time THEN 1 ELSE 0 END) > 0
    OR COUNT(*) <> COUNT(DISTINCT event_id)
ORDER BY stat_date;

-- 至少人工核对一次：工单与批次关系完整；停机区间不重叠；质检结果可追到工序。
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把制造业数据架构案例的验收证据写成门禁

```python
import json
from pathlib import Path


def build_evidence_manifest(
    subject: str,
    scope: dict,
    checks: dict,
    samples: list[dict],
    owner: str,
) -> dict:
    failed = [name for name, passed in checks.items() if not passed]
    return {
        "subject": subject,
        "scope": scope,
        "checks": checks,
        "failed_checks": failed,
        "sample_evidence": samples[:5],
        "owner": owner,
        "decision": "block" if failed else "review",
        "manual_questions": [
            "每一项失败是否已回到原始记录",
            "对象、时间和状态是否与指标字典一致",
            "回滚或修复后是否重新完成对账",
        ],
    }


manifest = build_evidence_manifest(
    subject="制造业数据架构案例",
    scope={"systems": ["ERP","MES","PLM","QMS"]},
    checks={"definition_frozen": False, "reconciled": False},
    samples=[],
    owner="计划",
)
Path("release-evidence.json").write_text(
    json.dumps(manifest, ensure_ascii=False, indent=2),
    encoding="utf-8",
)
print(manifest["decision"])
```
