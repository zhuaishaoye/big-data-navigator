# 实战案例导览

> [!abstract] 项目视角
> 如果只记住“实战案例导览”的定义，遇到真实数据时仍然很难行动。本文把它拆成五个可检查问题：谁在使用、流程在哪里变化、数据一行代表什么、异常如何发现、上线后用哪个指标验收。每个部分都配一个工作案例或代码片段。

## 1. 项目背景与边界

“实战案例导览”作为项目，必须同时定义业务目标、数据范围、技术边界和验收方式。建议在立项材料里写清：

- **业务目标**：改善哪个流程、服务哪个角色、影响什么决策。
- **现状基线**：当前耗时、错误率、覆盖率、成本或用户反馈，不能只写“比较落后”。
- **范围**：覆盖业务域、系统、表、指标和团队；明确不做什么。
- **约束**：数据权限、上线窗口、依赖系统、预算、合规和人员。
- **成功标准**：主指标、护栏指标、验收样例和观察周期。

一个合格目标示例：

> 在【时间】前，为【用户】交付“实战案例导览”能力，使【任务成功率】达到【可解释目标】，同时保证分区覆盖完整、任务幂等、依赖无环，上线后由【负责人】按周复盘。

## 2. 现状诊断与数据资产盘点

先梳理调度平台、元数据平台、数据质量平台、Kafka、Flink、Spark之间的数据流，记录源系统、接口、表、任务、负责人和延迟。不要用一张“系统架构图”掩盖数据质量问题，必须把主键、时间、状态和数量关系标出来。

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 数据源 | `source_id` | 需求评审 |
| 过程对象 | 数据表 | `table_id` | 源系统接入 |
| 过程对象 | 处理任务 | `job_id` | 模型设计 |
| 结果对象 | 数据服务 | `service_id` | 开发测试 |
| 结果对象 | 运行实例 | `run_id` | 发布调度 |
| 专题分析 | 实战案例导览 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

盘点阶段至少输出：资产清单、接口清单、指标基线、质量问题清单、权限清单和依赖矩阵。对每个问题标记影响范围、发生频率、现有临时方案和根本原因。

## 4. 数据模型与指标口径

| 专题观测面 | 需要回答的问题 | 关键证据 | 判定与动作 |
| --- | --- | --- | --- |
| 发布与回滚（本标题优先） | 谁审批、如何灰度、失败后怎样恢复 | 发布单、监控、回滚脚本和验收记录 | 关键链路必须有回滚演练 |
| 需求与粒度 | 指标和明细分别服务谁，一行数据代表什么 | 需求说明、粒度声明、样例单据 | 粒度未确认不进入编码 |
| 接口与变更 | 字段、分区、更新频率和 Schema 如何演进 | 接口契约、DDL、版本和变更记录 | 不兼容变更先新版本并存 |
| 测试与幂等 | 重复运行、空分区、乱序和边界值是否安全 | 测试数据、重跑结果、唯一键和事务 | 不幂等任务禁止自动补数 |

| --- | --- | --- | --- |
| 任务成功率 | `COUNT(DISTINCT success_run_id) / COUNT(DISTINCT run_id)`（视图字段 `run_success_rate`） | 业务域、数据层、任务类型 | 不混用测试、撤销和跨期状态；与“实战案例导览”相关时还要补充主题筛选 |
| 数据延迟 | `MAX(data_ready_at - expected_ready_at)`（视图字段 `data_latency`） | 数据层、任务类型、调度周期 | 不混用测试、撤销和跨期状态；与“实战案例导览”相关时还要补充主题筛选 |
| 资源消耗 | `SUM(cpu_seconds + memory_gb_seconds)`（视图字段 `resource_usage`） | 任务类型、调度周期、资源队列 | 不混用测试、撤销和跨期状态；与“实战案例导览”相关时还要补充主题筛选 |
| 重跑率 | `COUNT(DISTINCT rerun_id) / COUNT(DISTINCT run_id)`（视图字段 `rerun_rate`） | 调度周期、资源队列 | 不混用测试、撤销和跨期状态；与“实战案例导览”相关时还要补充主题筛选 |

模型设计优先保证粒度清晰和可重算。事实表负责事件或结果，维度表负责对象属性与历史归属，汇总表负责稳定消费。对于“实战案例导览”，如果既有事件又有状态，应分别建模，避免用最新状态覆盖历史。

## 5. 案例一：华南某 SaaS 数据平台

### 案例 1：华南某 SaaS 数据平台的“实战案例导览”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“实战案例导览”映射到“数据开发、ETL 与交付流程”中的发布与回滚，而不是泛泛讨论概念。
- **触发事件**：一次上游字段扩容导致多个 ETL 任务失败，发布窗口内无法快速定位影响。
- **业务与数据范围**：接口契约、DDL 历史、字段血缘、任务依赖、失败日志和下游资产。数据侧重点采集发布单、监控、回滚脚本和验收记录，并与调度平台、元数据平台、数据质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：谁审批、如何灰度、失败后怎样恢复。
- **关键障碍**：代码、表结构和调度配置分别发布，测试环境长期使用旧 Schema。同时要防止重复写入把表面指标带偏。
- **处理过程**：建立契约兼容检查、字段级影响分析、影子表和灰度发布，生产前自动跑新旧结果对照。实施时把“测试覆盖空分区、重复数据、迟到数据、Schema 变化和失败恢复”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例流程把发布前检查、失败阻断、回滚和下游通知串成同一门禁。验收至少同时看主指标、发布单、监控、回滚脚本和验收记录和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把需求、源接口、分层模型、代码、配置、测试、发布和回滚连成一条可重复执行的数据交付链路。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

项目里最重要的一次评审通常发生在写代码之前。把对象、粒度、时间和成功标准画在白板上，让业务、数据、安全和运维共同指出歧义，往往比上线后修复便宜得多。

```python
from dataclasses import dataclass
from datetime import datetime

TOPIC = "实战案例导览"
TASK_ID = "g_data_development_zxu73y"
PARTITION_KEY = "business_date"
GATE_RULES = [
    "代码、配置、DDL、权限和调度依赖进入同一版本与发布记录",
    "每个任务声明输入输出粒度、分区、幂等键和重跑边界",
    "测试覆盖空分区、重复数据、迟到数据、Schema 变化和失败恢复"
]

@dataclass(frozen=True)
class PartitionResult:
    partition: str
    input_rows: int
    output_rows: int
    duplicate_keys: int
    rejected_rows: int
    checksum: str

def publish_idempotent(spark, source_table: str, target_table: str, ds: str) -> PartitionResult:
    source = spark.read.table(source_table).where(f"{PARTITION_KEY} = '{ds}'")
    source.createOrReplaceTempView("staged_source")
    deduped = spark.sql("""
        SELECT *
        FROM (
          SELECT *,
                 ROW_NUMBER() OVER (
                   PARTITION BY business_key
                   ORDER BY updated_at DESC
                 ) AS version_no
          FROM staged_source
        )
        WHERE version_no = 1
    """)
    duplicate_keys = spark.sql("""
        SELECT COUNT(*) AS duplicate_keys
        FROM (
          SELECT business_key
          FROM staged_source
          GROUP BY business_key
          HAVING COUNT(*) > 1
        )
    """).first()["duplicate_keys"]
    assert duplicate_keys == 0, f"{TASK_ID}/{ds}: duplicate business keys must be quarantined"

    # 重跑同一分区先覆盖该分区，再原子切换；若平台不支持事务，使用影子分区和版本指针。
    deduped.write.mode("overwrite").insertInto(target_table)
    checksum = str(deduped.selectExpr("count(*) AS row_cnt").first()["row_cnt"])
    return PartitionResult(ds, source.count(), deduped.count(), duplicate_keys, 0, checksum)
```

### 上线前质量门禁

```python
# 实战案例导览：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "实战案例导览"
TOPIC_KEY = "subject"
RULE_ID = "rule_engineering_zxu73y"
GUIDE_CHECKS = [
    "代码、配置、DDL、权限和调度依赖进入同一版本与发布记录",
    "每个任务声明输入输出粒度、分区、幂等键和重跑边界",
    "测试覆盖空分区、重复数据、迟到数据、Schema 变化和失败恢复",
    "上线前完成数量、金额、主键、时延和下游可读性验收"
]
RULES = {
    "required_columns": ["event_id", "source_id", "run_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "source_id",
    "time_field": "run_time",
    "max_duplicate_rate": 0.0006,
    "max_null_rate": 0.004,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：代码、配置、DDL、权限和调度依赖进入同一版本与发布记录；每个任务声明输入输出粒度、分区、幂等键和重跑边界；测试覆盖空分区、重复数据、迟到数据、Schema 变化和失败恢复；上线前完成数量、金额、主键、时延和下游可读性验收
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

代码交付要求：

- 参数化日期、环境和业务范围，不在代码里硬编码生产密钥。
- 任务可重复运行，重复执行不会产生重复数据。
- 关键步骤记录输入行数、输出行数、过滤行数和质量结果。
- 失败时保留日志和中间状态，支持按分区重跑。
- 代码、配置和表结构纳入版本管理，并有变更记录。

## 7. 案例二：华北某制造数据团队

### 案例 2：华北某制造数据团队的“实战案例导览”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“实战案例导览”映射到“数据开发、ETL 与交付流程”中的需求与粒度，而不是泛泛讨论概念。
- **触发事件**：历史补数运行三天仍未完成，正常日批任务同时出现资源争抢。
- **业务与数据范围**：补数分区、任务耗时、资源队列、依赖层级、下游锁和人工处理记录。数据侧重点采集需求说明、粒度声明、样例单据，并与调度平台、元数据平台、数据质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：指标和明细分别服务谁，一行数据代表什么。
- **关键障碍**：所有日期一次性并发启动，任务内部没有分区级状态，失败后只能整批重跑。同时要防止依赖环把表面指标带偏。
- **处理过程**：按依赖层级和业务优先级分批，记录每个分区的输入输出计数，并对重跑设置幂等与限流。实施时把“上线前完成数量、金额、主键、时延和下游可读性验收”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例项目用补数进度、正常任务 SLA、重复率和人工介入次数衡量稳定性。验收至少同时看主指标、需求说明、粒度声明、样例单据和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把需求、源接口、分层模型、代码、配置、测试、发布和回滚连成一条可重复执行的数据交付链路。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

## 8. 测试、灰度与上线

| 测试类型 | 检查内容 | 通过标准 |
| --- | --- | --- |
| 单元测试 | 字段映射、计算逻辑、边界条件 | 用例覆盖正常、异常和极端值 |
| 集成测试 | 上下游接口、主键关联、权限 | 端到端能跑通 |
| 数据测试 | 唯一、完整、及时、平衡 | 关键规则通过并留存结果 |
| 性能测试 | 扫描量、执行时长、并发和资源 | 在容量预算内且可扩展 |
| 灰度 | 小范围业务与新旧结果对照 | 差异可解释，问题可回滚 |
| 验收 | 业务样例、指标和操作流程 | 验收人签字或有系统记录 |

灰度阶段应保留新旧链路对照。差异不能简单要求“完全一致”，因为修复本身可能改变结果；正确做法是对每类差异给出原因、影响和审批。

## 9. 第三个案例：华东某零售数据开发组

### 案例 3：华东某零售数据开发组的“实战案例导览”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“实战案例导览”映射到“数据开发、ETL 与交付流程”中的接口与变更，而不是泛泛讨论概念。
- **触发事件**：订单日报连续两天出现重复金额，重跑后差异进一步扩大。
- **业务与数据范围**：源订单、支付、退款、任务实例、写入模式、分区和质量结果。数据侧重点采集接口契约、DDL、版本和变更记录，并与调度平台、元数据平台、数据质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：字段、分区、更新频率和 Schema 如何演进。
- **关键障碍**：任务使用追加写，支付回调重复进入 ODS，开发只按订单号关联而没有确认退款粒度。同时要防止热点倾斜把表面指标带偏。

- **行动与护栏：** 按任务拆分数据集与角色，使用最小字段和临时授权，发布前检查派生表与导出是否出现敏感扩散。专题检查项“上线前完成数量、金额、主键、时延和下游可读性验收”被写成发布门禁，高风险字段缺少授权、脱敏或审计时不进入分析环境，紧急访问必须到期自动回收。
- **失败路径：** 把“内网可访问”当成“业务已授权”，或者用永久大权限账号支撑临时分析。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“实战案例导览”时，先验证测试数据、重跑结果、唯一键和事务，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由安全在明确时限内，根据任务成功率、资源消耗和分区覆盖完整决定继续、回退、补查还是转人工。 若重复写入或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从实战案例导览回到可核对明细

```sql
-- 实战案例导览：字段血缘与影响范围
WITH changed_columns AS (
  SELECT column_name
  FROM information_schema.columns
  WHERE table_schema = :source_schema
    AND table_name = :source_table
    AND last_altered_at >= :change_time
),
downstream_assets AS (
  SELECT
    asset_id,
    asset_name,
    asset_type,
    owner_name,
    criticality,
    last_used_at
  FROM metadata_asset_relation
  WHERE upstream_asset_id = :source_asset_id
    AND relation_status = 'active'
)
SELECT
  d.asset_id,
  d.asset_name,
  d.asset_type,
  d.owner_name,
  d.criticality,
  d.last_used_at,
  COUNT(c.column_name) AS changed_column_cnt,
  CASE
    WHEN d.criticality IN ('core', 'regulated') THEN 'block_release'
    WHEN d.last_used_at >= CURRENT_DATE - INTERVAL '7 days' THEN 'notify_owner'
    ELSE 'register_review'
  END AS required_action
FROM downstream_assets d
CROSS JOIN changed_columns c
GROUP BY d.asset_id, d.asset_name, d.asset_type, d.owner_name, d.criticality, d.last_used_at
ORDER BY
  CASE WHEN d.criticality IN ('core', 'regulated') THEN 0 ELSE 1 END,
  d.last_used_at DESC;
```

### 扩展代码二：把实战案例导览的验收证据写成门禁

```python
from datetime import date
from hashlib import sha256

import pandas as pd

SUBJECT = "实战案例导览"
BLOCKING_RULES = ["分区覆盖完整","任务幂等","依赖无环"]


def validate_release(frame: pd.DataFrame, start: date, end: date) -> dict:
    scoped = frame.loc[
        frame["event_date"].between(pd.Timestamp(start), pd.Timestamp(end))
        & (frame["subject_key"] == "subject")
    ].copy()
    checks = {
        "has_rows": len(scoped) > 0,
        "event_id_unique": not scoped["event_id"].duplicated().any(),
        "entity_key_complete": scoped["entity_key"].notna().all(),
        "event_time_present": scoped["event_time"].notna().all(),
        "scope_matches": scoped["subject_key"].nunique() == 1,
    }
    payload = f"{SUBJECT}|{start}|{end}|{len(scoped)}|{sorted(checks.items())}"
    return {
        "subject": SUBJECT,
        "rows": len(scoped),
        "checks": checks,
        "blocking_rules": BLOCKING_RULES,
        "release_allowed": all(checks.values()),
        "evidence_hash": sha256(payload.encode("utf-8")).hexdigest(),
    }
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
