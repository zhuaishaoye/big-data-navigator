# 数据架构分层模型

> [!abstract] 数据仓库与湖仓分层实战手册
> 数据架构分层不是把表名加上 ODS、DWD、DWS、ADS 前缀，而是通过稳定事实粒度、共享语义、历史归属和复用边界，把原始变化逐步加工为可审计的共享数据产品。每一层都应回答谁消费、保留多久、如何重算和谁负责。

## 1. 数据架构分层模型：定义、适用边界与决策出口

数据架构分层不是把表名加上 ODS、DWD、DWS、ADS 前缀，而是通过稳定事实粒度、共享语义、历史归属和复用边界，把原始变化逐步加工为可审计的共享数据产品。每一层都应回答谁消费、保留多久、如何重算和谁负责。

**本篇的适用边界。** 本篇讨论贴源、标准明细、公共汇总、指标服务和应用数据之间的职责边界；不强制所有企业采用相同层数，也不把命名规范等同于建模质量。

**最常见的错误替代。** 不能把最新状态覆盖历史、把每日快照相加当事件、在公共汇总层保留海量无说明宽表，也不能让应用层反向修改公共事实定义。

**最终决策。** 数据架构师与业务数据负责人要判断：某份数据应保留在哪一层，按什么粒度共享，哪些逻辑可复用，口径变化影响哪些应用，何时归档或重建。 因此，这篇内容不从“应该建哪张表”开始，而从业务动作、责任人和失败后果开始。只有先确定谁在什么时点做出什么决定，字段、SQL、看板和模型才有明确用途。

围绕“数据架构分层模型”，工作中至少要区分四类问题：

1. **身份问题**：对象是谁，主键能否跨系统稳定关联，合并、拆分、撤销后历史是否还看得见。
2. **时间问题**：业务发生、状态生效、数据入仓、计算完成和人员行动分别发生在哪一刻。
3. **状态问题**：当前状态是一段事件、一张快照还是最终结果，空值代表未发生、未采集还是已删除。
4. **责任问题**：谁确认口径，谁处理异常，谁有权放行或停止，谁在观察期后复盘。

## 2. 数据架构分层模型的完整业务流程

| 环节 | 要做的事 | 最小证据 | 失败后先查什么 |
| --- | --- | --- | --- |
| 源对象定界 | 确认权威系统、主键、事件和状态语义 | 源资产卡、样例、更新和删除规则 | 只按前缀迁移表，不确认粒度 |
| 贴源接入 | 尽量保留原始结构、批次和变更时间 | 接入日志、分区和源目标计数 | 应用绕过标准语义 |
| 标准明细 | 完成清洗、映射、对象关联和历史化 | 事实粒度、维度关系、质量规则 | 维表只保留最新状态 |
| 公共汇总 | 围绕稳定业务过程沉淀可复用聚合 | 粒度说明、维度一致性和使用方 | 无访问但仍持续计算 |
| 指标服务 | 把核心指标公式、版本和权限独立管理 | 口径卡、服务契约和回归样本 | 只按前缀迁移表，不确认粒度 |
| 应用交付 | 按看板、接口或特定场景组装数据 | 消费登记、查询预算和发布记录 | 应用绕过标准语义 |
| 生命周期 | 按使用与合规管理删除、归档、重算和下线 | 血缘、访问、保留和退出证据 | 维表只保留最新状态 |

把 源对象定界、贴源接入、标准明细、公共汇总、指标服务、应用交付、生命周期 串起来后可以看出，数据架构分层模型不是一个孤立字段，而是一条会跨系统、跨岗位、跨时间的证据链。流程图上每一段都应标出输入、输出、状态、时间戳、责任人和异常出口。只要其中一段只能靠口头解释，后续的统计、追责和自动化就会失去基础。

一个合格的需求说明应该写成：

> 在【授权数据范围】和【观察窗口】内，围绕“数据架构分层模型”的【贴源记录】，按【data_domain、storage_layer、business_process、asset_type】比较【公共层复用消费数】及其【源目标对象平衡率】，定位一个可干预节点；行动后同时观察主指标、样本量和护栏，任何高风险异常先阻断再调查。

## 3. 数据架构分层模型的数据对象与系统契约

| 数据对象 | 建议主键 | 一行代表什么 | 不允许混淆 |
| --- | --- | --- | --- |
| 贴源记录 | `raw_record_id` | 源系统一次完整载荷或变更 | 对象身份与业务事件 |
| 标准事件 | `event_id` | 具有统一类型、时间和对象身份的业务事件 | 事件、状态快照和结果粒度 |
| 状态快照 | `snapshot_id` | 对象在指定时间点的完整状态 | 事件、状态快照和结果粒度 |
| 事实明细 | `fact_line_id` | 按确定业务粒度形成的一行事实 | 事件、状态快照和结果粒度 |
| 公共汇总 | `aggregate_id` | 指定窗口、维度和版本下的聚合结果 | 事件、状态快照和结果粒度 |
| 指标版本 | `metric_version_id` | 一个可发布和可追溯的指标定义 | 事件、状态快照和结果粒度 |

对象表不是把所有字段塞进一张宽表。事件、状态快照和结果表应该分别保留粒度，再通过稳定主键与版本建立关联。尤其要避免三个常见混算：把一次业务事件算成多个对象、把每日快照相加当事件总量、把最新状态覆盖历史状态。

本主题的数据契约至少应包含：

- `layer_assignment_id` 的唯一性规则、生成方式和跨系统映射。
- `effective_from` 的业务含义、时区、迟到和补录规则。
- `assignment_status` 的完整状态集合，以及删除、撤销、冻结和失效的表示方法。
- 控制对象 `warehouse_object_mapping.object_mapping_id` 与主对象的关系。
- 每次口径、规则、模型或源版本变化的影响范围和下游通知对象。
- 敏感字段、允许用途、访问角色、导出限制和审计保留时间。

## 4. 数据架构分层模型的指标、样本与验收口径

| 指标 | 公式或定义 | 口径提醒 |
| --- | --- | --- |
| 公共层复用消费数 | 读取公共层有效结果的不同应用数 | 临时扫描和重复报表不算有效复用 |
| 源目标对象平衡率 | 源与目标可对账对象数 / 应覆盖对象数 | 事件、快照和汇总必须分别对账 |
| 公共口径重复实现数 | 同一指标存在独立生产实现的版本数 | 差异变体需有明确名称和批准 |
| 历史可回溯率 | 能按业务时间还原对象历史状态的测试数 / 抽样测试数 | 覆盖合并、拆分、撤销和迟到 |
| 低使用表占比 | 长期无有效消费的公共表数 / 公共表总数 | 监控探测与测试流量除外 |

指标字典至少写到“任何人都能按同一份数据复跑”的程度：中文名、业务定义、公式、分子、分母、事实粒度、时间字段、对象范围、排除项、版本、负责人和验收样例，一个都不能少。比例指标必须同时展示分子、分母和样本量；金额或数量必须做守恒；状态指标必须能回到事件时间线。

对于“数据架构分层模型”，建议把观察分成三层：

| 层次 | 看什么 | 不能替代什么 |
| --- | --- | --- |
| 业务结果 | 公共层复用消费数、源目标对象平衡率 | 不能替代过程证据和个案回查 |
| 过程护栏 | 公共口径重复实现数、历史可回溯率、低使用表占比 | 不能因为护栏暂时正常就跳过异常调查 |
| 数据证据 | 主键、时间、状态、版本、来源目标对账 | 不能只看任务成功或报表能打开 |

## 5. 数据架构分层模型：七个真实工作场景

以下七组场景均为公开方法结合常见工作流程构造的“脱敏复合示例”，不对应任何单一企业、患者、客户或雇员事实。场景的目的，是展示如何从现象走到证据、行动和验收，而不是虚构经营成果。

### 1. ODS 直接供报表导致口径失控

**现场。** 业务看板绕过明细层直接从贴源表计算订单金额。

**怎么查。** 沿血缘找到多个看板重复处理取消、退款和测试订单，且各自规则不同。

**怎么处理。** 保留贴源层作为审计证据；标准明细层统一对象和状态；看板只能消费已发布指标或批准版本。

**验收结论。** 贴源层适合追溯，不适合承载共享经营语义。

### 2. 明细事实粒度混入事件和快照

**现场。** 订单日表既有下单事件又有每日余额快照，汇总后金额翻倍。

**怎么查。** 按主键、时间、状态和数量关系抽查，发现两类记录共用一张表且没有记录类型。

**怎么处理。** 拆分事件事实和状态快照；各自主键与时间语义清楚；跨层汇总只使用经过定义的对象。

**验收结论。** 粒度不是字段细节，而是能否正确聚合的前提。

### 3. DWS 宽表无法解释指标

**现场。** 公共汇总层有数百字段，业务无法确认某个字段是否含退款。

**怎么查。** 检查血缘、指标登记和使用日志，发现字段由多个脚本拼接且缺少版本。

**怎么处理。** 按业务过程拆分公共汇总；每个输出字段绑定口径卡和负责人；删除无消费字段；指标服务独立管理公式。

**验收结论。** 宽表可以提升查询效率，但不能替代语义模型和指标治理。

### 4. 最新维表覆盖历史归属

**现场。** 组织调整后，历史订单全部按新部门汇总，过去报表无法复现。

**怎么查。** 检查维表历史有效期和事实关联方式，发现查询直接使用当前部门。

**怎么处理。** 使用拉链或生效时间维度；事实记录事件时点和可追溯归属；提供当前与历史两种视图并明确用途。

**验收结论。** 历史分析必须回答“当时属于谁”，不能只回答“现在属于谁”。

### 5. 重复分区造成总量偏高

**现场。** 补数重跑后同一天有两个版本，查询未限制版本直接求和。

**怎么查。** 比较分区清单、批次版本和输出摘要，发现幂等只覆盖写入，没有控制读取。

**怎么处理。** 建立批次与版本表；成功切换后再更新可见指针；查询固定批准版本；旧版本保留审计但不进入默认消费。

**验收结论。** 幂等不仅是重复写不产生重复，还要保证读者只看到唯一批准结果。

### 6. 应用层修改公共事实

**现场。** 一个业务团队为满足自身规则，在应用层覆盖公共明细状态。

**怎么查。** 审视依赖和 SQL 发现应用层创建同名派生表，下游逐渐误用。

**怎么处理。** 应用逻辑保留在应用域并明确标识；公共事实变更走版本和评审；禁止同名覆盖；对反向依赖建立告警。

**验收结论。** 分层边界靠命名不够，必须有权限、血缘和发布机制支持。

### 7. 历史层无限保留但无访问价值

**现场。** 数仓存量和成本持续增长，多个早期汇总层已无人读取。

**怎么查。** 结合访问日志、血缘、业务周期和法规要求分级评估，区分必须保留的原始审计数据和可重建中间结果。

**怎么处理。** 保留法规要求的原始证据；可重建中间层按生命周期归档；退出前做恢复演练和消费方确认。

**验收结论。** 分层也需要退出策略。不是所有中间结果都值得永久保存。

七个场景可以归成一条共同判断顺序：先确认对象和时间，再确认状态和版本；然后做总量、结构和明细三层对账；最后才讨论策略、模型或工具。若一条结论不能指出对应的原始记录、责任人和行动出口，就只能算观察，不能作为生产结论。

## 6. 数据架构分层模型的第一段 SQL：重建业务链路

下面的 SQL 用于说明对象、时间、状态、版本和分层口径如何进入同一条可复查路径。表名和部分字段是通用示例，落地时应映射到企业数据字典；SQL 方言也需按实际引擎调整。

```sql
-- 数据架构分层模型：按业务对象重建链路，避免事件、快照和结果混算
WITH ranked_layer_assignment_id AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY layer_assignment_id
      ORDER BY updated_at DESC
    ) AS version_no
  FROM warehouse_layer_assignment
  WHERE effective_from >= TIMESTAMP '{start_time}'
    AND effective_from <  TIMESTAMP '{end_time}'
    AND assignment_status NOT IN ('deleted', 'test')
),
valid_rows AS (
  SELECT
    layer_assignment_id,
    data_domain,
    storage_layer,
    business_process,
    asset_type,
    effective_from,
    assignment_status,
    ingested_at
  FROM ranked_layer_assignment_id
  WHERE version_no = 1
)
SELECT
  data_domain, storage_layer, business_process, asset_type,
  COUNT(DISTINCT layer_assignment_id) AS object_cnt,
  COUNT(DISTINCT CASE WHEN reconciled_flag THEN source_object_id END) AS numerator_value,
  COUNT(DISTINCT source_object_id) AS denominator_value,
  CAST(COUNT(DISTINCT CASE WHEN reconciled_flag THEN source_object_id END) AS DOUBLE PRECISION)
    / NULLIF(COUNT(DISTINCT source_object_id), 0) AS metric_value,
  MIN(effective_from) AS first_event_at,
  MAX(effective_from) AS last_event_at
FROM valid_rows
GROUP BY data_domain, storage_layer, business_process, asset_type
ORDER BY metric_value DESC, object_cnt DESC;
```

执行后至少回答六个问题：

- 同一对象是否因为多源回传产生多版本，版本保留是否符合业务要求？
- 业务时间与入仓时间是否分开，补录和迟到数据是否进入正确分区？
- 分子分母是否来自同一对象范围和同一统计窗口？
- 维度使用的是事件当时值还是当前值，跨期比较是否一致？
- 删除、撤销、冻结和测试数据是否按规则处理？
- 分组结果能否在明细中抽样复现？

## 7. 数据架构分层模型的第二段 SQL：源、控制和结果三方对账

```sql
-- 数据架构分层模型：源对象、控制对象和结果对象三方对账
WITH population AS (
  SELECT
    layer_assignment_id,
    effective_from,
    assignment_status
  FROM warehouse_layer_assignment
  WHERE effective_from >= TIMESTAMP '{start_time}'
    AND effective_from <  TIMESTAMP '{end_time}'
),
control AS (
  SELECT
    layer_assignment_id,
    SUM(mapped_record_count) AS control_value,
    COUNT(DISTINCT object_mapping_id) AS control_cnt,
    MAX(updated_at) AS control_updated_at
  FROM warehouse_object_mapping
  WHERE updated_at >= TIMESTAMP '{start_time}'
  GROUP BY layer_assignment_id
),
result AS (
  SELECT
    layer_assignment_id,
    COUNT(*) AS result_cnt,
    MAX(calculated_at) AS calculated_at
  FROM mart_layer_assignment_id
  WHERE business_date BETWEEN DATE '{start_date}' AND DATE '{end_date}'
  GROUP BY layer_assignment_id
)
SELECT
  COALESCE(p.layer_assignment_id, c.layer_assignment_id, r.layer_assignment_id) AS object_key,
  CASE
    WHEN p.layer_assignment_id IS NULL THEN 'source_missing'
    WHEN c.layer_assignment_id IS NULL THEN 'control_missing'
    WHEN r.layer_assignment_id IS NULL THEN 'result_missing'
    WHEN ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0 THEN 'count_or_value_gap'
    ELSE 'matched'
  END AS reconciliation_status,
  p.assignment_status,
  c.control_value,
  c.control_cnt,
  r.result_cnt,
  c.control_updated_at,
  r.calculated_at
FROM population p
FULL OUTER JOIN control c ON p.layer_assignment_id = c.layer_assignment_id
FULL OUTER JOIN result r ON COALESCE(p.layer_assignment_id, c.layer_assignment_id) = r.layer_assignment_id
WHERE p.layer_assignment_id IS NULL
   OR c.layer_assignment_id IS NULL
   OR r.layer_assignment_id IS NULL
   OR ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0;
```

这段查询故意不使用“总数相差小于某个随意百分比就算通过”。它先找出缺失对象和状态差异，再检查控制值与结果值。对于数据架构分层模型，数量、金额、时长或状态任意一项无法解释，都不能用“业务波动”代替排查。

对账结果建议分成四类处理：

1. **阻断**：对象缺失、关键时间为空、状态非法、金额或数量不守恒、权限越界。
2. **严重**：比例或总量显著偏离基线，且无法由已确认的对象结构变化解释。
3. **观察**：小范围波动但来源、样本和趋势可控，进入责任人和观察窗口。
4. **探索**：只有弱信号或假设，不进入正式结论，更不直接触发业务处罚。

## 8. 数据架构分层模型的 Python 发布门禁与指标护栏

第一段代码把发布条件写成可执行对象，避免“检查过了”只存在聊天记录里：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class LayerAssignmentIdBatch:
    batch_id: str
    source_rows: int
    valid_rows: int
    duplicate_keys: int
    missing_required_fields: int
    reconciliation_gap: float

def release_layer_assignment_id(batch: LayerAssignmentIdBatch) -> dict:
    checks = {
        "source_not_empty": batch.source_rows > 0,
        "valid_rows_in_range": 0 <= batch.valid_rows <= batch.source_rows,
        "duplicate_rate_ok": batch.duplicate_keys / max(batch.source_rows, 1) <= 0.001,
        "required_fields_ok": batch.missing_required_fields == 0,
        "reconciliation_ok": abs(batch.reconciliation_gap) <= 0.01,
    }
    return {
        "topic": "数据架构分层模型",
        "batch_id": batch.batch_id,
        "checks": checks,
        "release_allowed": all(checks.values()),
        "blocking_checks": [name for name, passed in checks.items() if not passed],
    }
```

第二段代码演示如何为比例类结果附带样本证据和小样本下界。它不是替代统计学家的模型，而是防止把少量偶然样本直接包装成稳定结论：

```python
from dataclasses import dataclass
from math import sqrt

@dataclass(frozen=True)
class LayerAssignmentIdObservation:
    object_id: str
    numerator: float
    denominator: float
    sample_size: int
    scope_version: str

def calculate_layer_assignment_id(rows: list[LayerAssignmentIdObservation]) -> list[dict]:
    output = []
    for row in rows:
        value = row.numerator / row.denominator if row.denominator > 0 else None
        # 小样本用 Wilson 下界做护栏，不把偶然的高比例直接当稳定结果。
        z = 1.96
        p = value or 0
        n = max(row.sample_size, 1)
        center = p + z * z / (2 * n)
        margin = z * sqrt((p * (1 - p) + z * z / (4 * n)) / n)
        lower = max(0, (center - margin) / (1 + z * z / n))
        output.append({
            "object_id": row.object_id,
            "metric": "公共层复用消费数",
            "value": value,
            "lower_bound": lower if value is not None else None,
            "sample_size": row.sample_size,
            "scope_version": row.scope_version,
            "caution": "临时扫描和重复报表不算有效复用",
        })
    return output
```

真正上线时还要补充参数配置、日志、血缘、告警级别、重跑幂等、异常样本保存和审批记录。代码通过不代表业务通过；自动检查只能证明已经定义的规则没有被违反，无法证明规则本身一定正确。

## 9. 数据架构分层模型的失败反例与上线验收

| 风险信号 | 错误做法 | 必须补齐的证据 | 发布或行动规则 |
| --- | --- | --- | --- |
| 层名代替模型 | 只按前缀迁移表，不确认粒度 | 对象、主键、时间和聚合测试 | 每层建立准入标准 |
| 贴源直接供业务 | 应用绕过标准语义 | 血缘、消费登记和指标版本 | 共享消费必须走发布资产 |
| 当前值覆盖历史 | 维表只保留最新状态 | 生效时间、版本和历史回放 | 历史分析使用时间维度 |
| 中间层永久保留 | 无访问但仍持续计算 | 访问、重建成本和合规期限 | 按生命周期归档或下线 |

上线验收不应只有一句“报表正常”。建议按下面四层验收：

| 验收对象 | 结构要求 | 测试样本 | 结果证据 |
| --- | --- | --- | --- |
| 贴源记录 | `raw_record_id` 能唯一定位源系统一次完整载荷或变更 | 正常、重复、缺失、撤销与跨期样本 | 公共层复用消费数可回到原始对象 |
| 标准事件 | `event_id` 能唯一定位具有统一类型、时间和对象身份的业务事件 | 正常、重复、缺失、撤销与跨期样本 | 源目标对象平衡率可回到原始对象 |
| 状态快照 | `snapshot_id` 能唯一定位对象在指定时间点的完整状态 | 正常、重复、缺失、撤销与跨期样本 | 公共口径重复实现数可回到原始对象 |
| 事实明细 | `fact_line_id` 能唯一定位按确定业务粒度形成的一行事实 | 正常、重复、缺失、撤销与跨期样本 | 历史可回溯率可回到原始对象 |
| 公共汇总 | `aggregate_id` 能唯一定位指定窗口、维度和版本下的聚合结果 | 正常、重复、缺失、撤销与跨期样本 | 低使用表占比可回到原始对象 |
| 指标版本 | `metric_version_id` 能唯一定位一个可发布和可追溯的指标定义 | 正常、重复、缺失、撤销与跨期样本 | 公共层复用消费数可回到原始对象 |

还应为每一次发布保留一组固定回归样本：正常对象、边界状态、重复记录、缺失字段、撤销或退款、跨期、权限拒绝和失败恢复。回归样本不是演示数据，而是以后每次改规则都能重复执行的质量资产。

## 10. 数据架构分层模型的 30 天落地与复盘

| 阶段 | 主要交付 | 通过条件 |
| --- | --- | --- |
| 第 1 周：定义 | 对象、流程、状态、指标、排除项和责任矩阵 | 业务、数据、安全或质量负责人对同一口径签字 |
| 第 2 周：打通 | 源字段、主键、时间、版本、控制对象和失败样本 | 正常与异常样本都能回到原始记录 |
| 第 3 周：验证 | 总量对账、分层对账、抽样回查、权限测试、回滚演练 | 阻断问题清零，严重问题有责任人与期限 |
| 第 4 周：发布 | 灰度、SLO、监控、行动清单、停止条件和复盘模板 | 使用者在真实场景中完成一次闭环行动 |

如果必须用 90 秒说明“数据架构分层模型”是否做对，可以按这个顺序自测：

1. 一行数据代表什么，主键是什么，哪些对象绝不能混在同一粒度？
2. 业务发生、数据可见、计算完成和行动确认分别在哪个时间点？
3. 本主题最重要的两个主指标、三个护栏和最小样本量是什么？
4. 一个异常出现时，先从原始记录、链路版本还是业务动作开始查？
5. 哪类错误必须阻断发布或停止使用，谁有权批准例外？
6. 上线后由谁在多长时间内观察，什么条件下回滚或结束？

> 当另一位数据同事不看聊天记录，只根据口径卡、回归样本和代码就能复跑同一结果；当业务负责人能指出一个异常对应的原始对象、处置动作和复核证据；当系统能够阻止未授权或状态非法的数据进入下游，这篇“数据架构分层模型”才算真正落到工作里。
