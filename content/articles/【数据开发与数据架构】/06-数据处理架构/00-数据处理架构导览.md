# 数据处理架构导览

> [!abstract] 批流数据处理选型实战手册
> 数据处理架构导览要帮助团队从业务时限、数据状态、重放要求和成本约束选择批处理、流处理或混合链路，而不是先决定某个引擎。导览的价值在于把问题分类，并说明每一类方案需要付出的运行代价。

## 1. 数据处理架构导览：定义、适用边界与决策出口

数据处理架构导览要帮助团队从业务时限、数据状态、重放要求和成本约束选择批处理、流处理或混合链路，而不是先决定某个引擎。导览的价值在于把问题分类，并说明每一类方案需要付出的运行代价。

**本篇的适用边界。** 本篇用于架构选型入门和评审准备，覆盖采集、存储、计算、编排、质量和服务的主要选择；不展开某个计算引擎的完整调优手册。

**最常见的错误替代。** 不能因为流处理听起来先进就把所有指标做成实时，也不能用批任务每天成功掩盖分钟级业务已经失效。

**最终决策。** 业务、平台和开发负责人要判断：数据最晚何时可用，是否需要按事件回放，错误能否部分输出，峰值成本与延迟如何取舍，后续扩展是否有明确触发条件。 因此，这篇内容不从“应该建哪张表”开始，而从业务动作、责任人和失败后果开始。只有先确定谁在什么时点做出什么决定，字段、SQL、看板和模型才有明确用途。

围绕“数据处理架构导览”，工作中至少要区分四类问题：

1. **身份问题**：对象是谁，主键能否跨系统稳定关联，合并、拆分、撤销后历史是否还看得见。
2. **时间问题**：业务发生、状态生效、数据入仓、计算完成和人员行动分别发生在哪一刻。
3. **状态问题**：当前状态是一段事件、一张快照还是最终结果，空值代表未发生、未采集还是已删除。
4. **责任问题**：谁确认口径，谁处理异常，谁有权放行或停止，谁在观察期后复盘。

## 2. 数据处理架构导览的完整业务流程

| 环节 | 要做的事 | 最小证据 | 失败后先查什么 |
| --- | --- | --- | --- |
| 业务时限访谈 | 记录事件发生、决策、行动和容错的真实时间 | 业务时间线、SLA 和等待成本 | 所有数据都要求秒级更新 |
| 数据形态识别 | 区分事件流、状态快照、主数据和周期性批量文件 | 事件字典、数据量、速度和迟到分布 | 结果随迟到数据随意变化 |
| 接入方式选择 | 在 API、文件、消息、CDC 和日志采集中比较 | 接入样例、顺序、断点和权限证据 | 历史结果静默变化 |
| 计算模式选择 | 比较批、微批、流和有状态处理的重放能力 | 延迟、状态、窗口、乱序和成本评测 | 组件都有人管但链路无人负责 |
| 编排与质量 | 定义依赖、水位、门禁、补数和失败出口 | DAG、规则、输入输出计数和回滚方案 | 所有数据都要求秒级更新 |
| 服务与消费 | 选择报表、指标接口、事件服务或离线文件 | SLO、缓存、限流和消费契约 | 结果随迟到数据随意变化 |
| 运行复盘 | 监测成本、延迟、积压、重跑和人工干预 | 运行基线、事故复盘和扩容触发条件 | 历史结果静默变化 |

把 业务时限访谈、数据形态识别、接入方式选择、计算模式选择、编排与质量、服务与消费、运行复盘 串起来后可以看出，数据处理架构导览不是一个孤立字段，而是一条会跨系统、跨岗位、跨时间的证据链。流程图上每一段都应标出输入、输出、状态、时间戳、责任人和异常出口。只要其中一段只能靠口头解释，后续的统计、追责和自动化就会失去基础。

一个合格的需求说明应该写成：

> 在【授权数据范围】和【观察窗口】内，围绕“数据处理架构导览”的【业务事件】，按【pipeline_id、processing_mode、business_domain、schedule_slot】比较【端到端新鲜度】及其【按时交付率】，定位一个可干预节点；行动后同时观察主指标、样本量和护栏，任何高风险异常先阻断再调查。

## 3. 数据处理架构导览的数据对象与系统契约

| 数据对象 | 建议主键 | 一行代表什么 | 不允许混淆 |
| --- | --- | --- | --- |
| 业务事件 | `event_id` | 一次已经发生的业务动作或状态变化 | 对象身份与业务事件 |
| 处理批次 | `batch_run_id` | 一次有边界和版本的批量计算 | 事件、状态快照和结果粒度 |
| 流式作业 | `stream_job_id` | 一组持续消费、处理和输出规则 | 事件、状态快照和结果粒度 |
| 数据水位 | `watermark_id` | 某分区或主题在指定时刻的完整性标记 | 事件、状态快照和结果粒度 |
| 处理结果 | `result_version_id` | 某对象在特定规则版本下生成的输出 | 事件、状态快照和结果粒度 |
| 补数任务 | `backfill_job_id` | 针对确定时间范围重新计算和替换结果的作业 | 事件、状态快照和结果粒度 |

对象表不是把所有字段塞进一张宽表。事件、状态快照和结果表应该分别保留粒度，再通过稳定主键与版本建立关联。尤其要避免三个常见混算：把一次业务事件算成多个对象、把每日快照相加当事件总量、把最新状态覆盖历史状态。

本主题的数据契约至少应包含：

- `pipeline_run_id` 的唯一性规则、生成方式和跨系统映射。
- `started_at` 的业务含义、时区、迟到和补录规则。
- `run_status` 的完整状态集合，以及删除、撤销、冻结和失效的表示方法。
- 控制对象 `data_pipeline_checkpoint.checkpoint_id` 与主对象的关系。
- 每次口径、规则、模型或源版本变化的影响范围和下游通知对象。
- 敏感字段、允许用途、访问角色、导出限制和审计保留时间。

## 4. 数据处理架构导览的指标、样本与验收口径

| 指标 | 公式或定义 | 口径提醒 |
| --- | --- | --- |
| 端到端新鲜度 | 数据可消费时间 - 业务事件发生时间 | 至少报告 P50、P95 和超 SLA 比例 |
| 按时交付率 | 在业务截止时间前可用的运行次数 / 应完成运行次数 | 成功但迟到不能算按时 |
| 重放一致率 | 重放结果与批准基准一致的对象数 / 对账对象数 | 规则版本差异要单列解释 |
| 单位有效处理成本 | 计算存储资源成本 / 通过质量门禁的输出量 | 失败与重复计算也应计入浪费 |
| 人工干预率 | 需要人工修数、重启或改参数的运行数 / 总运行数 | 按故障类型和责任人分层 |

指标字典至少写到“任何人都能按同一份数据复跑”的程度：中文名、业务定义、公式、分子、分母、事实粒度、时间字段、对象范围、排除项、版本、负责人和验收样例，一个都不能少。比例指标必须同时展示分子、分母和样本量；金额或数量必须做守恒；状态指标必须能回到事件时间线。

对于“数据处理架构导览”，建议把观察分成三层：

| 层次 | 看什么 | 不能替代什么 |
| --- | --- | --- |
| 业务结果 | 端到端新鲜度、按时交付率 | 不能替代过程证据和个案回查 |
| 过程护栏 | 重放一致率、单位有效处理成本、人工干预率 | 不能因为护栏暂时正常就跳过异常调查 |
| 数据证据 | 主键、时间、状态、版本、来源目标对账 | 不能只看任务成功或报表能打开 |

## 5. 数据处理架构导览：七个真实工作场景

以下七组场景均为公开方法结合常见工作流程构造的“脱敏复合示例”，不对应任何单一企业、患者、客户或雇员事实。场景的目的，是展示如何从现象走到证据、行动和验收，而不是虚构经营成果。

### 1. 每天批处理满足不了两小时决策

**现场。** 运营需要在下班前调整库存，但仓库数据每天凌晨才形成完整分区。

**怎么查。** 把订单、库存、仓内作业和业务决策时间放到同一条时间线，确认真正瓶颈是库存移动事件接入而非报表计算。

**怎么处理。** 先对库存移动使用 CDC 和增量流，保留每日批处理做全量对账；不是把全部历史数据实时化。

**验收结论。** 实时化应瞄准有时效价值的对象。把所有层全量双算只会增加成本和一致性风险。

### 2. CDC 重复事件造成库存倒扣

**现场。** 数据库日志重复投递，流任务将同一出库事件计算两次。

**怎么查。** 核对消息键、偏移、事务边界、幂等状态和下游更新方式，发现重试时没有按事件 ID 去重。

**怎么处理。** 以稳定业务键和源事务标识幂等写入；保存偏移与结果版本；补数时按业务时间范围重放而不是重复追加。

**验收结论。** 至少一次投递不等于结果可以重复累计。流处理必须在结果层设计幂等。

### 3. 迟到数据让当天报表反复变化

**现场。** 门店网络不稳定，部分交易在关账后数小时才到。

**怎么查。** 统计迟到分布、水位设置和关账动作，发现水位按处理时间而不是事件时间推进。

**怎么处理。** 使用事件时间和允许迟到窗口；关账后变更进入更正记录；看板区分初版、修订版和最终版。

**验收结论。** 实时结果不是一锤定音。必须告诉消费者何时稳定、后续为何变化。

### 4. 重跑历史分区时覆盖了新规则结果

**现场。** 代码升级后直接重跑三个月，所有历史报表都按新逻辑变化却未标记。

**怎么查。** 对比代码版本、参数、规则配置和输出摘要，确认补数同时改变了业务口径和缺陷修复。

**怎么处理。** 将缺陷修复与口径升级拆开发布；补数任务绑定规则版本；新旧结果影子对账后再切换并通知消费者。

**验收结论。** 补数技术上成功不代表业务上可接受。版本边界必须可审计。

### 5. 流作业积压后先扩资源仍未恢复

**现场。** 消费延迟升高，团队直接增加并发，反让下游数据库压力更大。

**怎么查。** 观察输入速率、消费速率、背压、反压点、状态大小和下游写入耗时，发现瓶颈在外部数据库而不是计算。

**怎么处理。** 先限制入口并保护下游；区分瞬时峰值与持续增长；优化批量写入和分区键；建立积压清除与跳过策略。

**验收结论。** 扩容只能解决计算瓶颈。链路最慢的依赖决定端到端恢复时间。

### 6. 离线与实时指标长期不一致

**现场。** 实时口径 GMV 一直略高，团队各自解释为延迟。

**怎么查。** 用同一批事件分别执行流式和离线规则，比较去重键、乱序、退款状态和时间窗。

**怎么处理。** 建立共享事件字典与口径卡；实时仅做快照和告警，离线作为结算；差异看板按原因分类并设阈值。

**验收结论。** 双链路不需要每秒完全相等，但每个差异必须有定义、边界和可解释范围。

### 7. 批流同时运行但责任无人承担

**现场。** 平台团队维护引擎，业务团队维护逻辑，数据质量异常在两边来回转。

**怎么查。** 梳理作业所有者、代码归属、上游契约、值班表和故障升级路径，发现关键任务没有端到端负责人。

**怎么处理。** 指定每条数据产品的唯一负责人；平台负责基础设施 SLA，业务数据团队负责语义和质量；演练一次跨团队故障。

**验收结论。** 架构图上的组件不等于运行责任。必须有端到端负责人对最终可用性负责。

七个场景可以归成一条共同判断顺序：先确认对象和时间，再确认状态和版本；然后做总量、结构和明细三层对账；最后才讨论策略、模型或工具。若一条结论不能指出对应的原始记录、责任人和行动出口，就只能算观察，不能作为生产结论。

## 6. 数据处理架构导览的第一段 SQL：重建业务链路

下面的 SQL 用于说明对象、时间、状态、版本和分层口径如何进入同一条可复查路径。表名和部分字段是通用示例，落地时应映射到企业数据字典；SQL 方言也需按实际引擎调整。

```sql
-- 数据处理架构导览：按业务对象重建链路，避免事件、快照和结果混算
WITH ranked_pipeline_run_id AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY pipeline_run_id
      ORDER BY updated_at DESC
    ) AS version_no
  FROM data_pipeline_run
  WHERE started_at >= TIMESTAMP '{start_time}'
    AND started_at <  TIMESTAMP '{end_time}'
    AND run_status NOT IN ('deleted', 'test')
),
valid_rows AS (
  SELECT
    pipeline_run_id,
    pipeline_id,
    processing_mode,
    business_domain,
    schedule_slot,
    started_at,
    run_status,
    ingested_at
  FROM ranked_pipeline_run_id
  WHERE version_no = 1
)
SELECT
  pipeline_id, processing_mode, business_domain, schedule_slot,
  COUNT(DISTINCT pipeline_run_id) AS object_cnt,
  COUNT(DISTINCT CASE WHEN delivered_on_time THEN pipeline_run_id END) AS numerator_value,
  COUNT(DISTINCT pipeline_run_id) AS denominator_value,
  CAST(COUNT(DISTINCT CASE WHEN delivered_on_time THEN pipeline_run_id END) AS DOUBLE PRECISION)
    / NULLIF(COUNT(DISTINCT pipeline_run_id), 0) AS metric_value,
  MIN(started_at) AS first_event_at,
  MAX(started_at) AS last_event_at
FROM valid_rows
GROUP BY pipeline_id, processing_mode, business_domain, schedule_slot
ORDER BY metric_value DESC, object_cnt DESC;
```

执行后至少回答六个问题：

- 同一对象是否因为多源回传产生多版本，版本保留是否符合业务要求？
- 业务时间与入仓时间是否分开，补录和迟到数据是否进入正确分区？
- 分子分母是否来自同一对象范围和同一统计窗口？
- 维度使用的是事件当时值还是当前值，跨期比较是否一致？
- 删除、撤销、冻结和测试数据是否按规则处理？
- 分组结果能否在明细中抽样复现？

## 7. 数据处理架构导览的第二段 SQL：源、控制和结果三方对账

```sql
-- 数据处理架构导览：源对象、控制对象和结果对象三方对账
WITH population AS (
  SELECT
    pipeline_run_id,
    started_at,
    run_status
  FROM data_pipeline_run
  WHERE started_at >= TIMESTAMP '{start_time}'
    AND started_at <  TIMESTAMP '{end_time}'
),
control AS (
  SELECT
    pipeline_run_id,
    SUM(committed_offset) AS control_value,
    COUNT(DISTINCT checkpoint_id) AS control_cnt,
    MAX(updated_at) AS control_updated_at
  FROM data_pipeline_checkpoint
  WHERE updated_at >= TIMESTAMP '{start_time}'
  GROUP BY pipeline_run_id
),
result AS (
  SELECT
    pipeline_run_id,
    COUNT(*) AS result_cnt,
    MAX(calculated_at) AS calculated_at
  FROM mart_pipeline_run_id
  WHERE business_date BETWEEN DATE '{start_date}' AND DATE '{end_date}'
  GROUP BY pipeline_run_id
)
SELECT
  COALESCE(p.pipeline_run_id, c.pipeline_run_id, r.pipeline_run_id) AS object_key,
  CASE
    WHEN p.pipeline_run_id IS NULL THEN 'source_missing'
    WHEN c.pipeline_run_id IS NULL THEN 'control_missing'
    WHEN r.pipeline_run_id IS NULL THEN 'result_missing'
    WHEN ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0 THEN 'count_or_value_gap'
    ELSE 'matched'
  END AS reconciliation_status,
  p.run_status,
  c.control_value,
  c.control_cnt,
  r.result_cnt,
  c.control_updated_at,
  r.calculated_at
FROM population p
FULL OUTER JOIN control c ON p.pipeline_run_id = c.pipeline_run_id
FULL OUTER JOIN result r ON COALESCE(p.pipeline_run_id, c.pipeline_run_id) = r.pipeline_run_id
WHERE p.pipeline_run_id IS NULL
   OR c.pipeline_run_id IS NULL
   OR r.pipeline_run_id IS NULL
   OR ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0;
```

这段查询故意不使用“总数相差小于某个随意百分比就算通过”。它先找出缺失对象和状态差异，再检查控制值与结果值。对于数据处理架构导览，数量、金额、时长或状态任意一项无法解释，都不能用“业务波动”代替排查。

对账结果建议分成四类处理：

1. **阻断**：对象缺失、关键时间为空、状态非法、金额或数量不守恒、权限越界。
2. **严重**：比例或总量显著偏离基线，且无法由已确认的对象结构变化解释。
3. **观察**：小范围波动但来源、样本和趋势可控，进入责任人和观察窗口。
4. **探索**：只有弱信号或假设，不进入正式结论，更不直接触发业务处罚。

## 8. 数据处理架构导览的 Python 发布门禁与指标护栏

第一段代码把发布条件写成可执行对象，避免“检查过了”只存在聊天记录里：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class PipelineRunIdBatch:
    batch_id: str
    source_rows: int
    valid_rows: int
    duplicate_keys: int
    missing_required_fields: int
    reconciliation_gap: float

def release_pipeline_run_id(batch: PipelineRunIdBatch) -> dict:
    checks = {
        "source_not_empty": batch.source_rows > 0,
        "valid_rows_in_range": 0 <= batch.valid_rows <= batch.source_rows,
        "duplicate_rate_ok": batch.duplicate_keys / max(batch.source_rows, 1) <= 0.001,
        "required_fields_ok": batch.missing_required_fields == 0,
        "reconciliation_ok": abs(batch.reconciliation_gap) <= 0.01,
    }
    return {
        "topic": "数据处理架构导览",
        "batch_id": batch.batch_id,
        "checks": checks,
        "release_allowed": all(checks.values()),
        "blocking_checks": [name for name, passed in checks.items() if not passed],
    }
```

第二段代码演示如何为比例类结果附带样本证据和小样本下界。它不是替代统计学家的模型，而是防止把少量偶然样本直接包装成稳定结论：

```python
from dataclasses import dataclass
from math import sqrt

@dataclass(frozen=True)
class PipelineRunIdObservation:
    object_id: str
    numerator: float
    denominator: float
    sample_size: int
    scope_version: str

def calculate_pipeline_run_id(rows: list[PipelineRunIdObservation]) -> list[dict]:
    output = []
    for row in rows:
        value = row.numerator / row.denominator if row.denominator > 0 else None
        # 小样本用 Wilson 下界做护栏，不把偶然的高比例直接当稳定结果。
        z = 1.96
        p = value or 0
        n = max(row.sample_size, 1)
        center = p + z * z / (2 * n)
        margin = z * sqrt((p * (1 - p) + z * z / (4 * n)) / n)
        lower = max(0, (center - margin) / (1 + z * z / n))
        output.append({
            "object_id": row.object_id,
            "metric": "端到端新鲜度",
            "value": value,
            "lower_bound": lower if value is not None else None,
            "sample_size": row.sample_size,
            "scope_version": row.scope_version,
            "caution": "至少报告 P50、P95 和超 SLA 比例",
        })
    return output
```

真正上线时还要补充参数配置、日志、血缘、告警级别、重跑幂等、异常样本保存和审批记录。代码通过不代表业务通过；自动检查只能证明已经定义的规则没有被违反，无法证明规则本身一定正确。

## 9. 数据处理架构导览的失败反例与上线验收

| 风险信号 | 错误做法 | 必须补齐的证据 | 发布或行动规则 |
| --- | --- | --- | --- |
| 为实时而实时 | 所有数据都要求秒级更新 | 业务决策时点、等待成本和使用记录 | 按价值分层选择时效 |
| 没有水位 | 结果随迟到数据随意变化 | 事件时间、允许迟到和关账规则 | 明确稳定时点与修订版本 |
| 补数无版本 | 历史结果静默变化 | 代码、规则、输入快照和输出摘要 | 补数必须绑定版本和批准范围 |
| 端到端无 owner | 组件都有人管但链路无人负责 | 数据产品责任表与故障演练 | 指定唯一链路负责人 |

上线验收不应只有一句“报表正常”。建议按下面四层验收：

| 验收对象 | 结构要求 | 测试样本 | 结果证据 |
| --- | --- | --- | --- |
| 业务事件 | `event_id` 能唯一定位一次已经发生的业务动作或状态变化 | 正常、重复、缺失、撤销与跨期样本 | 端到端新鲜度可回到原始对象 |
| 处理批次 | `batch_run_id` 能唯一定位一次有边界和版本的批量计算 | 正常、重复、缺失、撤销与跨期样本 | 按时交付率可回到原始对象 |
| 流式作业 | `stream_job_id` 能唯一定位一组持续消费、处理和输出规则 | 正常、重复、缺失、撤销与跨期样本 | 重放一致率可回到原始对象 |
| 数据水位 | `watermark_id` 能唯一定位某分区或主题在指定时刻的完整性标记 | 正常、重复、缺失、撤销与跨期样本 | 单位有效处理成本可回到原始对象 |
| 处理结果 | `result_version_id` 能唯一定位某对象在特定规则版本下生成的输出 | 正常、重复、缺失、撤销与跨期样本 | 人工干预率可回到原始对象 |
| 补数任务 | `backfill_job_id` 能唯一定位针对确定时间范围重新计算和替换结果的作业 | 正常、重复、缺失、撤销与跨期样本 | 端到端新鲜度可回到原始对象 |

还应为每一次发布保留一组固定回归样本：正常对象、边界状态、重复记录、缺失字段、撤销或退款、跨期、权限拒绝和失败恢复。回归样本不是演示数据，而是以后每次改规则都能重复执行的质量资产。

## 10. 数据处理架构导览的 30 天落地与复盘

| 阶段 | 主要交付 | 通过条件 |
| --- | --- | --- |
| 第 1 周：定义 | 对象、流程、状态、指标、排除项和责任矩阵 | 业务、数据、安全或质量负责人对同一口径签字 |
| 第 2 周：打通 | 源字段、主键、时间、版本、控制对象和失败样本 | 正常与异常样本都能回到原始记录 |
| 第 3 周：验证 | 总量对账、分层对账、抽样回查、权限测试、回滚演练 | 阻断问题清零，严重问题有责任人与期限 |
| 第 4 周：发布 | 灰度、SLO、监控、行动清单、停止条件和复盘模板 | 使用者在真实场景中完成一次闭环行动 |

如果必须用 90 秒说明“数据处理架构导览”是否做对，可以按这个顺序自测：

1. 一行数据代表什么，主键是什么，哪些对象绝不能混在同一粒度？
2. 业务发生、数据可见、计算完成和行动确认分别在哪个时间点？
3. 本主题最重要的两个主指标、三个护栏和最小样本量是什么？
4. 一个异常出现时，先从原始记录、链路版本还是业务动作开始查？
5. 哪类错误必须阻断发布或停止使用，谁有权批准例外？
6. 上线后由谁在多长时间内观察，什么条件下回滚或结束？

> [!check] 完成标准
> 当另一位数据同事不看聊天记录，只根据口径卡、回归样本和代码就能复跑同一结果；当业务负责人能指出一个异常对应的原始对象、处置动作和复核证据；当系统能够阻止未授权或状态非法的数据进入下游，这篇“数据处理架构导览”才算真正落到工作里。
