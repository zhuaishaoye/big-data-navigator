# 数据处理架构概述

> [!abstract] 数据系统参考架构实战手册
> 数据处理架构描述数据从产生、采集、存储、计算、治理到消费的整体组织方式。一个可运行的架构必须同时说明数据对象、时间语义、质量责任、失败恢复和消费契约，而不是只有一张标着数据湖、数仓和实时计算的组件图。

## 1. 数据处理架构概述：定义、适用边界与决策出口

数据处理架构描述数据从产生、采集、存储、计算、治理到消费的整体组织方式。一个可运行的架构必须同时说明数据对象、时间语义、质量责任、失败恢复和消费契约，而不是只有一张标着数据湖、数仓和实时计算的组件图。

**本篇的适用边界。** 本篇给出跨组织通用的参考框架和评审问题，适合建立共同语言；具体技术选型要结合企业规模、现有限制、团队能力和合规要求另行验证。

**最常见的错误替代。** 不能把组件清单当架构，也不能用吞吐量单项测试替代可维护性、成本、安全和故障恢复评估。

**最终决策。** 架构负责人要判断：数据在哪里产生权威版本，在哪一层完成标准化和共享，哪些计算靠近源或消费端，质量与权限在哪一跳阻断，故障时如何降级和恢复。 因此，这篇内容不从“应该建哪张表”开始，而从业务动作、责任人和失败后果开始。只有先确定谁在什么时点做出什么决定，字段、SQL、看板和模型才有明确用途。

围绕“数据处理架构概述”，工作中至少要区分四类问题：

1. **身份问题**：对象是谁，主键能否跨系统稳定关联，合并、拆分、撤销后历史是否还看得见。
2. **时间问题**：业务发生、状态生效、数据入仓、计算完成和人员行动分别发生在哪一刻。
3. **状态问题**：当前状态是一段事件、一张快照还是最终结果，空值代表未发生、未采集还是已删除。
4. **责任问题**：谁确认口径，谁处理异常，谁有权放行或停止，谁在观察期后复盘。

## 2. 数据处理架构概述的完整业务流程

| 环节 | 要做的事 | 最小证据 | 失败后先查什么 |
| --- | --- | --- | --- |
| 源与语义盘点 | 识别业务对象、事件、状态与权威系统 | 对象清单、源权威、字段责任 | 只列产品名称没有对象和数据流 |
| 采集与契约 | 定义接口、频率、顺序、删除和重传规则 | 接入契约、样例、水位和权限 | 用手机号或名称强行关联 |
| 存储与生命周期 | 按访问、更新、保留和成本选择存储组织 | 分层模型、分区、格式和生命周期 | 所有数据永久保留 |
| 计算与编排 | 组织批流任务、依赖、参数和资源 | DAG、规则版本、执行日志和容量基线 | 实时结果直接用于结算 |
| 治理控制 | 建立元数据、质量、血缘、安全和标准 | 资产卡、规则结果、影响分析和审计 | 只列产品名称没有对象和数据流 |
| 服务与消费 | 以指标、接口、文件或应用交付 | SLO、缓存、限流、版本和支持责任 | 用手机号或名称强行关联 |
| 运行与演进 | 监控运行、成本、故障和需求变化 | SLO 看板、事故复盘和技术债清单 | 所有数据永久保留 |

把 源与语义盘点、采集与契约、存储与生命周期、计算与编排、治理控制、服务与消费、运行与演进 串起来后可以看出，数据处理架构概述不是一个孤立字段，而是一条会跨系统、跨岗位、跨时间的证据链。流程图上每一段都应标出输入、输出、状态、时间戳、责任人和异常出口。只要其中一段只能靠口头解释，后续的统计、追责和自动化就会失去基础。

一个合格的需求说明应该写成：

> 在【授权数据范围】和【观察窗口】内，围绕“数据处理架构概述”的【源数据对象】，按【data_domain、pipeline_id、storage_layer、consumer_tier】比较【权威源覆盖率】及其【端到端可用率】，定位一个可干预节点；行动后同时观察主指标、样本量和护栏，任何高风险异常先阻断再调查。

## 3. 数据处理架构概述的数据对象与系统契约

| 数据对象 | 建议主键 | 一行代表什么 | 不允许混淆 |
| --- | --- | --- | --- |
| 源数据对象 | `source_object_id` | 权威业务系统中的一个可识别记录 | 对象身份与业务事件 |
| 标准化对象 | `normalized_object_id` | 完成类型、编码和状态映射后的对象 | 事件、状态快照和结果粒度 |
| 计算事实 | `fact_id` | 按明确粒度和时间窗口产生的计算记录 | 事件、状态快照和结果粒度 |
| 指标结果 | `metric_result_id` | 按口径版本生成的指标值 | 事件、状态快照和结果粒度 |
| 数据契约 | `data_contract_id` | 生产方与消费方对字段和运行的约定 | 事件、状态快照和结果粒度 |
| 运行实例 | `pipeline_instance_id` | 一次从输入到输出可追踪的处理执行 | 事件、状态快照和结果粒度 |

对象表不是把所有字段塞进一张宽表。事件、状态快照和结果表应该分别保留粒度，再通过稳定主键与版本建立关联。尤其要避免三个常见混算：把一次业务事件算成多个对象、把每日快照相加当事件总量、把最新状态覆盖历史状态。

本主题的数据契约至少应包含：

- `contract_run_id` 的唯一性规则、生成方式和跨系统映射。
- `business_window_start` 的业务含义、时区、迟到和补录规则。
- `delivery_status` 的完整状态集合，以及删除、撤销、冻结和失效的表示方法。
- 控制对象 `data_contract_validation.validation_id` 与主对象的关系。
- 每次口径、规则、模型或源版本变化的影响范围和下游通知对象。
- 敏感字段、允许用途、访问角色、导出限制和审计保留时间。

## 4. 数据处理架构概述的指标、样本与验收口径

| 指标 | 公式或定义 | 口径提醒 |
| --- | --- | --- |
| 权威源覆盖率 | 关键对象已确认权威源的数量 / 关键对象总数 | 多源冲突处理规则必须同时登记 |
| 端到端可用率 | 在业务窗口内成功交付的时隙 / 应交付时隙 | 只看单个任务成功率不足以代表可用 |
| 数据契约变更通知率 | 发布前完成消费者确认的变更 / 有消费者的变更 | 通知不等于确认，需有影响清单 |
| 单位业务产出的资源成本 | 全链路资源成本 / 有效使用结果 | 区分共享成本与单场景成本 |
| 故障平均恢复时间 | 恢复可用时间 - 故障开始时间 | 按影响范围、等级和根因分层 |

指标字典至少写到“任何人都能按同一份数据复跑”的程度：中文名、业务定义、公式、分子、分母、事实粒度、时间字段、对象范围、排除项、版本、负责人和验收样例，一个都不能少。比例指标必须同时展示分子、分母和样本量；金额或数量必须做守恒；状态指标必须能回到事件时间线。

对于“数据处理架构概述”，建议把观察分成三层：

| 层次 | 看什么 | 不能替代什么 |
| --- | --- | --- |
| 业务结果 | 权威源覆盖率、端到端可用率 | 不能替代过程证据和个案回查 |
| 过程护栏 | 数据契约变更通知率、单位业务产出的资源成本、故障平均恢复时间 | 不能因为护栏暂时正常就跳过异常调查 |
| 数据证据 | 主键、时间、状态、版本、来源目标对账 | 不能只看任务成功或报表能打开 |

## 5. 数据处理架构概述：七个真实工作场景

以下七组场景均为公开方法结合常见工作流程构造的“脱敏复合示例”，不对应任何单一企业、患者、客户或雇员事实。场景的目的，是展示如何从现象走到证据、行动和验收，而不是虚构经营成果。

### 1. 架构图完整但主键无法跨系统关联

**现场。** 客户分析需要关联 APP、门店和客服系统，首版结果出现大量重复客户。

**怎么查。** 比较三套系统的账号、手机号、会员号和合并规则，发现手机号既是登录字段又被家庭成员共用。

**怎么处理。** 建立客户、账号、设备和关系四层对象；手机号只作弱标识；合并与拆分保留历史；高风险合并进入人工复核。

**验收结论。** 跨系统对象识别是架构语义问题，不能用一个字段 join 掩盖。

### 2. 数据湖成为没有边界的垃圾场

**现场。** 团队把所有源表原样入湖，半年后查询慢、重复多、无人知道来源。

**怎么查。** 按使用、责任人、分区、格式、依赖和最后访问时间画像，发现大量一次性副本和未登记数据。

**怎么处理。** 建立最小入湖准入、资产登记、分区生命周期和消费清单；临时实验进入隔离区；无人使用数据定期清理。

**验收结论。** 灵活不等于无治理。湖的开放能力需要更明确的资产边界。

### 3. 数仓模型反复重算同一业务口径

**现场。** 多个集市各自计算活跃用户，周报数字长期不同。

**怎么查。** 沿 SQL、血缘、指标字典和调度链回查，发现登录、曝光和内容消费被分别当作活跃。

**怎么处理。** 建立共享事件定义和核心指标服务；差异指标作为明确变体登记；集市只使用已发布版本，不改写基础语义。

**验收结论。** 公共口径需要唯一语义和版本，而不是在每个集市复制同一段 SQL。

### 4. 实时链路没有离线对账

**现场。** 实时看板被用于运营动作，但月末结算仍依赖离线表。

**怎么查。** 比较两套链路的事件范围、状态处理和退款回冲，发现实时会遗漏迟到撤销。

**怎么处理。** 实时负责趋势和告警，结算以离线批准版本为准；差异进入统一看板；业务界面标明数据状态。

**验收结论。** 架构应明确每种结果的使用边界。快速结果不一定具备结算资格。

### 5. 权限只在展示层控制

**现场。** 看板隐藏了手机号，但明细导出接口仍能返回原始字段。

**怎么查。** 检查查询接口、临时表、导出、日志和权限继承，发现脱敏只发生在页面模板。

**怎么处理。** 把分类分级和字段策略放在服务端统一执行；导出单独审批和水印；派生敏感表纳入自动发现和定期复核。

**验收结论。** 权限必须靠近数据访问层。展示层伪装无法阻止绕过。

### 6. 一个组件故障导致全链路无法恢复

**现场。** 调度平台停机后无法识别哪些任务已完成，团队只能全量重跑。

**怎么查。** 回放运行日志、检查点、输出摘要和依赖记录，发现任务状态只保存在调度器内存。

**怎么处理。** 把幂等、检查点和可恢复边界写入数据处理；关键输出记录版本和摘要；调度恢复后按依赖重建状态。

**验收结论。** 架构韧性不依赖某个平台永不故障，而依赖故障后能够判定和恢复。

### 7. 新技术引入没有退出条件

**现场。** 试点引擎持续运行两年，效果不明确，却同时保留旧栈和双份成本。

**怎么查。** 对照原目标和试点指标，核对使用场景、团队能力、故障率、迁移成本和供应链风险。

**怎么处理。** 为试点设置继续、扩展、维持和停止四类决策；明确旧栈关闭时间和数据迁移对账。

**验收结论。** 架构演进必须有退出机制，否则试点会变成永久技术债。

七个场景可以归成一条共同判断顺序：先确认对象和时间，再确认状态和版本；然后做总量、结构和明细三层对账；最后才讨论策略、模型或工具。若一条结论不能指出对应的原始记录、责任人和行动出口，就只能算观察，不能作为生产结论。

## 6. 数据处理架构概述的第一段 SQL：重建业务链路

下面的 SQL 用于说明对象、时间、状态、版本和分层口径如何进入同一条可复查路径。表名和部分字段是通用示例，落地时应映射到企业数据字典；SQL 方言也需按实际引擎调整。

```sql
-- 数据处理架构概述：按业务对象重建链路，避免事件、快照和结果混算
WITH ranked_contract_run_id AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY contract_run_id
      ORDER BY updated_at DESC
    ) AS version_no
  FROM data_pipeline_contract_run
  WHERE business_window_start >= TIMESTAMP '{start_time}'
    AND business_window_start <  TIMESTAMP '{end_time}'
    AND delivery_status NOT IN ('deleted', 'test')
),
valid_rows AS (
  SELECT
    contract_run_id,
    data_domain,
    pipeline_id,
    storage_layer,
    consumer_tier,
    business_window_start,
    delivery_status,
    ingested_at
  FROM ranked_contract_run_id
  WHERE version_no = 1
)
SELECT
  data_domain, pipeline_id, storage_layer, consumer_tier,
  COUNT(DISTINCT contract_run_id) AS object_cnt,
  COUNT(DISTINCT CASE WHEN delivery_status = 'available' THEN contract_id END) AS numerator_value,
  COUNT(DISTINCT contract_id) AS denominator_value,
  CAST(COUNT(DISTINCT CASE WHEN delivery_status = 'available' THEN contract_id END) AS DOUBLE PRECISION)
    / NULLIF(COUNT(DISTINCT contract_id), 0) AS metric_value,
  MIN(business_window_start) AS first_event_at,
  MAX(business_window_start) AS last_event_at
FROM valid_rows
GROUP BY data_domain, pipeline_id, storage_layer, consumer_tier
ORDER BY metric_value DESC, object_cnt DESC;
```

执行后至少回答六个问题：

- 同一对象是否因为多源回传产生多版本，版本保留是否符合业务要求？
- 业务时间与入仓时间是否分开，补录和迟到数据是否进入正确分区？
- 分子分母是否来自同一对象范围和同一统计窗口？
- 维度使用的是事件当时值还是当前值，跨期比较是否一致？
- 删除、撤销、冻结和测试数据是否按规则处理？
- 分组结果能否在明细中抽样复现？

## 7. 数据处理架构概述的第二段 SQL：源、控制和结果三方对账

```sql
-- 数据处理架构概述：源对象、控制对象和结果对象三方对账
WITH population AS (
  SELECT
    contract_run_id,
    business_window_start,
    delivery_status
  FROM data_pipeline_contract_run
  WHERE business_window_start >= TIMESTAMP '{start_time}'
    AND business_window_start <  TIMESTAMP '{end_time}'
),
control AS (
  SELECT
    contract_run_id,
    SUM(checked_record_count) AS control_value,
    COUNT(DISTINCT validation_id) AS control_cnt,
    MAX(updated_at) AS control_updated_at
  FROM data_contract_validation
  WHERE updated_at >= TIMESTAMP '{start_time}'
  GROUP BY contract_run_id
),
result AS (
  SELECT
    contract_run_id,
    COUNT(*) AS result_cnt,
    MAX(calculated_at) AS calculated_at
  FROM mart_contract_run_id
  WHERE business_date BETWEEN DATE '{start_date}' AND DATE '{end_date}'
  GROUP BY contract_run_id
)
SELECT
  COALESCE(p.contract_run_id, c.contract_run_id, r.contract_run_id) AS object_key,
  CASE
    WHEN p.contract_run_id IS NULL THEN 'source_missing'
    WHEN c.contract_run_id IS NULL THEN 'control_missing'
    WHEN r.contract_run_id IS NULL THEN 'result_missing'
    WHEN ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0 THEN 'count_or_value_gap'
    ELSE 'matched'
  END AS reconciliation_status,
  p.delivery_status,
  c.control_value,
  c.control_cnt,
  r.result_cnt,
  c.control_updated_at,
  r.calculated_at
FROM population p
FULL OUTER JOIN control c ON p.contract_run_id = c.contract_run_id
FULL OUTER JOIN result r ON COALESCE(p.contract_run_id, c.contract_run_id) = r.contract_run_id
WHERE p.contract_run_id IS NULL
   OR c.contract_run_id IS NULL
   OR r.contract_run_id IS NULL
   OR ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0;
```

这段查询故意不使用“总数相差小于某个随意百分比就算通过”。它先找出缺失对象和状态差异，再检查控制值与结果值。对于数据处理架构概述，数量、金额、时长或状态任意一项无法解释，都不能用“业务波动”代替排查。

对账结果建议分成四类处理：

1. **阻断**：对象缺失、关键时间为空、状态非法、金额或数量不守恒、权限越界。
2. **严重**：比例或总量显著偏离基线，且无法由已确认的对象结构变化解释。
3. **观察**：小范围波动但来源、样本和趋势可控，进入责任人和观察窗口。
4. **探索**：只有弱信号或假设，不进入正式结论，更不直接触发业务处罚。

## 8. 数据处理架构概述的 Python 发布门禁与指标护栏

第一段代码把发布条件写成可执行对象，避免“检查过了”只存在聊天记录里：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class ContractRunIdBatch:
    batch_id: str
    source_rows: int
    valid_rows: int
    duplicate_keys: int
    missing_required_fields: int
    reconciliation_gap: float

def release_contract_run_id(batch: ContractRunIdBatch) -> dict:
    checks = {
        "source_not_empty": batch.source_rows > 0,
        "valid_rows_in_range": 0 <= batch.valid_rows <= batch.source_rows,
        "duplicate_rate_ok": batch.duplicate_keys / max(batch.source_rows, 1) <= 0.001,
        "required_fields_ok": batch.missing_required_fields == 0,
        "reconciliation_ok": abs(batch.reconciliation_gap) <= 0.01,
    }
    return {
        "topic": "数据处理架构概述",
        "batch_id": batch.batch_id,
        "checks": checks,
        "release_allowed": all(checks.values()),
        "blocking_checks": [name for name, passed in checks.items() if not passed],
    }
```

第二段代码演示如何为比例类结果附带样本证据和小样本下界。它不是替代统计学家的模型，而是防止把少量偶然样本直接包装成稳定结论：

```python
from dataclasses import dataclass
from math import sqrt

@dataclass(frozen=True)
class ContractRunIdObservation:
    object_id: str
    numerator: float
    denominator: float
    sample_size: int
    scope_version: str

def calculate_contract_run_id(rows: list[ContractRunIdObservation]) -> list[dict]:
    output = []
    for row in rows:
        value = row.numerator / row.denominator if row.denominator > 0 else None
        # 小样本用 Wilson 下界做护栏，不把偶然的高比例直接当稳定结果。
        z = 1.96
        p = value or 0
        n = max(row.sample_size, 1)
        center = p + z * z / (2 * n)
        margin = z * sqrt((p * (1 - p) + z * z / (4 * n)) / n)
        lower = max(0, (center - margin) / (1 + z * z / n))
        output.append({
            "object_id": row.object_id,
            "metric": "权威源覆盖率",
            "value": value,
            "lower_bound": lower if value is not None else None,
            "sample_size": row.sample_size,
            "scope_version": row.scope_version,
            "caution": "多源冲突处理规则必须同时登记",
        })
    return output
```

真正上线时还要补充参数配置、日志、血缘、告警级别、重跑幂等、异常样本保存和审批记录。代码通过不代表业务通过；自动检查只能证明已经定义的规则没有被违反，无法证明规则本身一定正确。

## 9. 数据处理架构概述的失败反例与上线验收

| 风险信号 | 错误做法 | 必须补齐的证据 | 发布或行动规则 |
| --- | --- | --- | --- |
| 组件图代替架构 | 只列产品名称没有对象和数据流 | 对象、时间、质量、责任与消费契约 | 每个关键链路做端到端评审 |
| 主键不可跨系统 | 用手机号或名称强行关联 | 多源身份、合并历史和回查样本 | 建立稳定对象与弱标识 |
| 无生命周期 | 所有数据永久保留 | 使用频率、合规和恢复要求 | 按资产设置归档与退出 |
| 实时口径越权 | 实时结果直接用于结算 | 稳定时点、对账和批准规则 | 未完成对账不得用于结算 |

上线验收不应只有一句“报表正常”。建议按下面四层验收：

| 验收对象 | 结构要求 | 测试样本 | 结果证据 |
| --- | --- | --- | --- |
| 源数据对象 | `source_object_id` 能唯一定位权威业务系统中的一个可识别记录 | 正常、重复、缺失、撤销与跨期样本 | 权威源覆盖率可回到原始对象 |
| 标准化对象 | `normalized_object_id` 能唯一定位完成类型、编码和状态映射后的对象 | 正常、重复、缺失、撤销与跨期样本 | 端到端可用率可回到原始对象 |
| 计算事实 | `fact_id` 能唯一定位按明确粒度和时间窗口产生的计算记录 | 正常、重复、缺失、撤销与跨期样本 | 数据契约变更通知率可回到原始对象 |
| 指标结果 | `metric_result_id` 能唯一定位按口径版本生成的指标值 | 正常、重复、缺失、撤销与跨期样本 | 单位业务产出的资源成本可回到原始对象 |
| 数据契约 | `data_contract_id` 能唯一定位生产方与消费方对字段和运行的约定 | 正常、重复、缺失、撤销与跨期样本 | 故障平均恢复时间可回到原始对象 |
| 运行实例 | `pipeline_instance_id` 能唯一定位一次从输入到输出可追踪的处理执行 | 正常、重复、缺失、撤销与跨期样本 | 权威源覆盖率可回到原始对象 |

还应为每一次发布保留一组固定回归样本：正常对象、边界状态、重复记录、缺失字段、撤销或退款、跨期、权限拒绝和失败恢复。回归样本不是演示数据，而是以后每次改规则都能重复执行的质量资产。

## 10. 数据处理架构概述的 30 天落地与复盘

| 阶段 | 主要交付 | 通过条件 |
| --- | --- | --- |
| 第 1 周：定义 | 对象、流程、状态、指标、排除项和责任矩阵 | 业务、数据、安全或质量负责人对同一口径签字 |
| 第 2 周：打通 | 源字段、主键、时间、版本、控制对象和失败样本 | 正常与异常样本都能回到原始记录 |
| 第 3 周：验证 | 总量对账、分层对账、抽样回查、权限测试、回滚演练 | 阻断问题清零，严重问题有责任人与期限 |
| 第 4 周：发布 | 灰度、SLO、监控、行动清单、停止条件和复盘模板 | 使用者在真实场景中完成一次闭环行动 |

如果必须用 90 秒说明“数据处理架构概述”是否做对，可以按这个顺序自测：

1. 一行数据代表什么，主键是什么，哪些对象绝不能混在同一粒度？
2. 业务发生、数据可见、计算完成和行动确认分别在哪个时间点？
3. 本主题最重要的两个主指标、三个护栏和最小样本量是什么？
4. 一个异常出现时，先从原始记录、链路版本还是业务动作开始查？
5. 哪类错误必须阻断发布或停止使用，谁有权批准例外？
6. 上线后由谁在多长时间内观察，什么条件下回滚或结束？

> [!check] 完成标准
> 当另一位数据同事不看聊天记录，只根据口径卡、回归样本和代码就能复跑同一结果；当业务负责人能指出一个异常对应的原始对象、处置动作和复核证据；当系统能够阻止未授权或状态非法的数据进入下游，这篇“数据处理架构概述”才算真正落到工作里。
