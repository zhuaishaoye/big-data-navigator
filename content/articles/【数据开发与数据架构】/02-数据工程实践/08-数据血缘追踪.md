# 数据血缘追踪

> [!warning] 核心判断
> “数据血缘追踪”在会议里常常只有一句话，落到数据团队却会展开成口径、主键、时间、状态、权限和交付责任。下面用一个从问题到上线的顺序展开，并穿插三个脱敏的复合案例，帮助你把标题里的知识迁移到真实项目。

## 1. 先判断应治理什么风险

“数据血缘追踪”通常不是买一个平台就能解决的问题。它至少涉及制度、标准、责任、流程、技术和审计六层。开始前先把风险写成可观察事实：

| 风险问题 | 观察信号 | 可能影响 | 首先核查 |
| --- | --- | --- | --- |
| 定义不一致 | 同名指标多个 SQL、多个业务解释 | 决策冲突、返工 | 指标字典与负责人 |
| 数据不完整 | 分区缺失、关键字段空值 | 报表失真、流程中断 | 采集与任务日志 |
| 责任不清 | 问题工单长期无人认领 | 修复延迟、同类复发 | 资产责任矩阵 |
| 访问过宽 | 长期权限、共享账号、无审计 | 泄漏与合规风险 | 权限清单与访问日志 |
| 变更不可见 | 表结构或逻辑变更无通知 | 下游批量故障 | 血缘与发布记录 |

1. **重复写入**：需要在标准、系统或组织流程中设置对应控制。
2. **依赖环**：需要在标准、系统或组织流程中设置对应控制。
3. **热点倾斜**：需要在标准、系统或组织流程中设置对应控制。
4. **全量重算成本失控**：需要在标准、系统或组织流程中设置对应控制。
5. **发布缺少回滚**：需要在标准、系统或组织流程中设置对应控制。

## 2. 用 DAMA 思路拆成可执行组件

| 组件 | 本文关注对象 | 最小可执行机制 |
| --- | --- | --- |
| 数据标准 | 字段、代码、指标和业务术语；结合“数据血缘追踪”重点检查分区覆盖完整 | 标准登记、评审、版本与废弃 |
| 元数据 | 表、字段、任务、接口、负责人；结合“数据血缘追踪”重点检查任务幂等 | 自动采集、业务补充、变更通知 |
| 数据质量 | 完整性、唯一性、及时性、准确性；结合“数据血缘追踪”重点检查依赖无环 | 规则、阈值、工单与复盘 |
| 主数据 | 客户、商品、设备、机构等共享对象；结合“数据血缘追踪”重点检查结果可回溯 | 源权威、去重、合并、历史关系 |
| 数据安全 | 分类分级、权限、脱敏和审计；结合“数据血缘追踪”重点检查资源使用有上限 | 审批、最小权限、访问复核 |
| 数据血缘 | 表、字段、任务和指标关系；结合“数据血缘追踪”重点检查分区覆盖完整 | 影响分析、问题追踪、变更评审 |

治理不是把所有数据都按同一优先级管理。建议依据使用范围、监管要求、决策影响和故障历史划分关键资产，再决定投入。关键资产应有唯一负责人、明确消费者、质量目标、访问策略和变更通知。

## 3. 资产、标准与责任矩阵

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 数据源 | `source_id` | 需求评审 |
| 过程对象 | 数据表 | `table_id` | 源系统接入 |
| 过程对象 | 处理任务 | `job_id` | 模型设计 |
| 结果对象 | 数据服务 | `service_id` | 开发测试 |
| 结果对象 | 运行实例 | `run_id` | 发布调度 |
| 专题分析 | 数据血缘追踪 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

一个可执行的数据标准至少包括：

- **业务定义**：业务人员如何理解和适用。
- **技术定义**：字段类型、长度、格式、枚举和空值语义。
- **计算口径**：时间、粒度、分子分母和排除项。
- **权威来源**：哪个系统是事实源，冲突时以谁为准。
- **生命周期**：创建、变更、废弃和归档规则。
- **责任人**：业务负责人、数据负责人、技术负责人和审批人。

资产责任可以使用 RACI：业务负责人对定义负责，数据负责人对实现与质量负责，平台团队对工具和权限负责，安全合规对访问与审计负责，消费者对使用边界负责。只有“责任人”一个字段，没有决策权和时限，问题仍会回到治理团队自己处理。

## 4. 案例一：华南某保险集团

### 案例 1：华南某保险集团的“数据血缘追踪”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“数据血缘追踪”映射到“数据血缘、元数据与影响分析”中的业务关系，而不是泛泛讨论概念。
- **触发事件**：同一指标存在多个口径，审计要求解释每个数字来自哪些字段和规则。
- **业务与数据范围**：指标版本、计算 SQL、源字段、业务术语、责任人和变更记录。数据侧重点采集指标定义、版本、负责人和消费方，并与调度平台、元数据平台、数据质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：指标由哪些字段和规则组成，谁负责。
- **关键障碍**：指标平台与表级血缘分离，SQL 中的过滤和映射无法回到业务定义。同时要防止重复写入把表面指标带偏。
- **处理过程**：打通指标、字段和任务三层血缘，关键公式保存版本，变更时生成影响与差异报告。实施时把“无法解析的动态 SQL、UDF 与人工操作必须有例外登记”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：复合案例支持从看板数字一路回到源字段和规则版本。验收至少同时看主指标、指标定义、版本、负责人和消费方和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把表、字段、任务、指标和运行时关系连成可更新、可验证的血缘网络，用于影响分析、故障定位、口径追踪和变更评审。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

治理项目应先做小范围闭环，不要一开始铺满全公司。选择一个高影响业务域，完成从资产盘点、标准确认、质量规则、问题整改到复盘的完整链路，再复制机制。

## 5. 规则与代码：让控制可执行

### 发布前规则门禁

```python
# 数据血缘追踪：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "数据血缘追踪"
TOPIC_KEY = "subject"
RULE_ID = "rule_engineering_ayx7fj"
GUIDE_CHECKS = [
    "血缘至少覆盖表、字段、任务、指标、模型和运行实例中的关键层级",
    "静态 SQL 解析与真实运行读写要互相对账",
    "关键资产记录负责人、等级、消费者和变更影响规则",
    "无法解析的动态 SQL、UDF 与人工操作必须有例外登记"
]
RULES = {
    "required_columns": ["event_id", "source_id", "run_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "source_id",
    "time_field": "run_time",
    "max_duplicate_rate": 0.001,
    "max_null_rate": 0.005,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：血缘至少覆盖表、字段、任务、指标、模型和运行实例中的关键层级；静态 SQL 解析与真实运行读写要互相对账；关键资产记录负责人、等级、消费者和变更影响规则；无法解析的动态 SQL、UDF 与人工操作必须有例外登记
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

### 专题专属验证代码

```python
from collections import defaultdict, deque

edges = [
    ("ods.orders", "dwd.order_detail"),
    ("ods.payments", "dwd.order_detail"),
    ("dwd.order_detail", "dws.merchant_sales"),
    ("dws.merchant_sales", "ads.merchant_dashboard"),
]

def downstream_impact(changed_asset: str) -> list[str]:
    graph = defaultdict(list)
    for upstream, downstream in edges:
        graph[upstream].append(downstream)
    visited = set()
    queue = deque([changed_asset])
    while queue:
        for child in graph.get(queue.popleft(), []):
            if child not in visited:
                visited.add(child)
                queue.append(child)
    return sorted(visited)

impact = downstream_impact("ods.orders")
assert "ads.merchant_dashboard" in impact

# 主题："数据血缘追踪"
# 生产版合并字段级 SQL 解析、运行日志、指标血缘和人工登记；
# 动态 SQL、UDF、临时表等低置信度边单独标记，不能静默忽略。
```


### 治理对象与风险分层 SQL

```sql
-- 数据血缘追踪：留存同期群诊断（调度周期 × 业务域）
WITH scoped AS (
  SELECT
    source_id AS entity_key,
    event_id,
    run_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_pipeline_run
  WHERE run_time >= DATE '2026-08-01'
    AND run_time <  DATE '2026-11-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '任务成功率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

规则设计要同时考虑三件事：能否自动执行、误报成本是否可接受、失败后谁来处理。只写“不能为空”不够，必须明确哪类对象允许为空、谁能在何种情况下豁免、豁免多久、是否需要审批和复核。

建议把规则分成四级：

1. **阻断**：涉及监管、资金、身份或核心发布，失败即停止。
2. **严重告警**：影响大但可先隔离，要求在约定时间内响应。
3. **观察告警**：可能是正常业务变化，先记录趋势。
4. **探索检查**：尚未形成稳定阈值，仅用于发现异常模式。

## 6. 案例二：华北某 AI 平台

### 案例 2：华北某 AI 平台的“数据血缘追踪”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“数据血缘追踪”映射到“数据血缘、元数据与影响分析”中的影响分析，而不是泛泛讨论概念。
- **触发事件**：模型效果突然下降，团队无法确认受影响的训练数据和特征版本。
- **业务与数据范围**：数据集、特征、样本、模型、评测、部署和线上请求关系。数据侧重点采集下游清单、关键等级、通知与确认记录，并与调度平台、元数据平台、数据质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：上游变更会影响哪些资产、任务、接口和报表。
- **关键障碍**：模型版本存在，但特征回填和样本筛选脚本没有纳入血缘。同时要防止依赖环把表面指标带偏。
- **处理过程**：把数据卡、特征版本、模型卡与运行请求串联，记录训练、评测和生产数据边界。实施时把“血缘至少覆盖表、字段、任务、指标、模型和运行实例中的关键层级”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例治理能回答某次模型更新使用了哪些数据和特征，并限制问题影响范围。验收至少同时看主指标、下游清单、关键等级、通知与确认记录和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把表、字段、任务、指标和运行时关系连成可更新、可验证的血缘网络，用于影响分析、故障定位、口径追踪和变更评审。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

治理指标不要只统计“生成了多少文档、接入了多少资产”。更值得观察的是规则覆盖的关键资产、问题发现前移比例、问题复发率、变更影响分析耗时和业务是否愿意使用。

## 7. 权限、安全与审计

围绕“数据血缘追踪”，权限治理至少应回答：

- 谁能申请、谁审批、审批依据是什么？
- 权限是否按角色、数据级别和用途最小化？
- 临时权限何时收回，离职和转岗是否自动处理？
- 查询、下载和导出是否留痕，异常访问如何发现？
- 脱敏、加密、水印和审计日志是否与数据类型匹配？

敏感字段不应通过“复制一份测试数据”绕过问题。更合适的做法是分级脱敏、合成数据或受控计算环境。所有示例和代码都不应包含真实身份、账号、密钥、客户名单或未公开经营数据。

## 8. 第三个案例：华东某银行数据平台

### 案例 3：华东某银行数据平台的“数据血缘追踪”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“数据血缘追踪”映射到“数据血缘、元数据与影响分析”中的运行关系，而不是泛泛讨论概念。
- **触发事件**：核心客户表修改字段类型后，任务批量失败，团队只能人工搜索 SQL 定位下游。
- **业务与数据范围**：表字段血缘、调度依赖、查询历史、任务日志、接口和报表消费清单。数据侧重点采集运行日志、输入输出路径、任务实例，并与调度平台、元数据平台、数据质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：实际读写了哪些分区、文件和外部接口。
- **关键障碍**：血缘只到表级且长期不更新，动态 SQL 与临时表没有解析。同时要防止热点倾斜把表面指标带偏。
- **处理过程**：组合 SQL 解析、运行日志和人工登记，建立字段级关系与关键资产等级，接入发布影响分析。实施时把“静态 SQL 解析与真实运行读写要互相对账”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例项目把下游识别从人工搜索变成自动清单，并对无法识别语句设置例外评审。验收至少同时看主指标、运行日志、输入输出路径、任务实例和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把表、字段、任务、指标和运行时关系连成可更新、可验证的血缘网络，用于影响分析、故障定位、口径追踪和变更评审。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

## 扩展实战：数据血缘追踪的四个可执行案例

> [!info] 内容说明
> 以下内容围绕“数据血缘追踪”补充四个相互独立的工作场景，分别落在链路断点与延迟、质量门禁与例外治理、成本、质量与时效取舍、故障恢复与可回放。它们使用公开方法、常见系统边界和脱敏数据构造，重点展示怎样从现象回到对象、流程、代码、行动与验收，而不是给出一个可以套用所有企业的标准答案。

| 案例 | 观察角度 | 首要对象 | 关键证据 | 失败时先停什么 |
| --- | --- | --- | --- | --- |
| 案例 4 | 链路断点与延迟 | 数据源 / 数据表 | 源端操作日志、CDC/批次水位、分区清单 | 无法证明数据完整的链路不进入正式发布，优先保留旧版本供下游读取 |

这四个案例共享一条底线：先证明数据对象和链路能够解释，再讨论优化或决策。任何涉及资金、医疗安全、用户隐私、监管报送或核心权限的结果，都需要保留人工复核、阻断条件和回滚路径。

### 案例 4：数据血缘追踪从源事件到结果的长链路核查

一个看似普通的“数据血缘追踪”需求，在跨系统核验后变成了围绕“链路断点与延迟”的专项排查。触发排查的不是一次严重事故，而是连续几次解释不清的数据差异。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 把业务发生时间、数据可见时间、任务完成时间和下游消费时间放到同一条证据链。在本场景里，核心风险还包括全量重算成本失控，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：数据源、数据表及其在服务与复盘前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注source_id与table_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 结果表出现缺失或延迟，单看调度状态却显示成功，无法判断问题发生在源端、接入、计算还是服务层。初看时，API 网关与调度平台的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 源端操作日志、CDC/批次水位、分区清单、任务参数、血缘关系、下游请求日志。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“平台团队”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“数据血缘追踪”的当前定义并记录版本；第二步用数据源明细核对API 网关到调度平台的关联；第三步按调度周期与业务域做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察重跑率和护栏指标任务成功率。
- **行动与护栏：** 按时间轴核对每一跳的输入输出计数与水位，先阻断错误结果扩散，再确定重跑范围和补数窗口。专题检查项“血缘至少覆盖表、字段、任务、指标、模型和运行实例中的关键层级”被写成发布门禁，无法证明数据完整的链路不进入正式发布，优先保留旧版本供下游读取。
- **失败路径：** 看到任务成功就立即补数，却没有确认重复、乱序和迟到事件。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“数据血缘追踪”时，先验证指标定义、版本、负责人和消费方，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由平台团队在明确时限内，根据重跑率、任务成功率和结果可回溯决定继续、回退、补查还是转人工。 若全量重算成本失控或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。
### 案例 5：数据血缘追踪上线前的质量门禁

一个看似普通的“数据血缘追踪”需求，在跨系统核验后变成了围绕“质量门禁与例外治理”的专项排查。触发排查的不是一次严重事故，而是连续几次解释不清的数据差异。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 把关键质量规则、阈值、例外审批、阻断动作和复核人写入发布流程。在本场景里，核心风险还包括发布缺少回滚，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。

- **关键异常或争议：** 常规日期下结果看起来正常，一旦遇到空值、重复、跨期、撤销或历史归属，报表口径便无法解释。初看时，调度平台与元数据平台的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。

- **可迁移结论：** 处理“数据血缘追踪”时，先验证下游清单、关键等级、通知与确认记录，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由数据开发在明确时限内，根据服务可用率、数据延迟和资源使用有上限决定继续、回退、补查还是转人工。 若发布缺少回滚或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

- **关键异常或争议：** 一次错误发布已经产生结果，团队只能凭负责人记忆寻找影响范围，补数后仍无法确认是否重复或遗漏。初看时，数据质量平台与Kafka的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 运行参数、代码版本、输入快照、输出摘要、受影响分区、回滚记录和补数对账。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“分析师”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“数据血缘追踪”的当前定义并记录版本；第二步用数据服务明细核对数据质量平台到Kafka的关联；第三步按数据层与调度周期做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察数据延迟和护栏指标重跑率。
- **行动与护栏：** 保存现场并停止下游扩散，按影响边界回滚或隔离结果，使用幂等任务从最小必要范围重新计算。专题检查项“无法解析的动态 SQL、UDF 与人工操作必须有例外登记”被写成发布门禁，恢复任务没有对账、没有版本记录或无法重复执行时，不宣布故障结束。
- **失败路径：** 直接覆盖目标表，或者把所有分区全部重跑以求省事。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“数据血缘追踪”时，先验证解析结果、未识别语句和人工补充，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由分析师在明确时限内，根据数据延迟、重跑率和任务幂等决定继续、回退、补查还是转人工。 若依赖环或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从数据血缘追踪回到可核对明细

```sql
-- 数据血缘追踪：状态链与时间间隔核查
WITH ordered_events AS (
  SELECT
    source_id AS entity_key,
    event_id,
    stage_code,
    run_time AS event_time,
    LAG(stage_code) OVER (
      PARTITION BY source_id
      ORDER BY run_time, event_id
    ) AS previous_stage,
    LAG(run_time) OVER (
      PARTITION BY source_id
      ORDER BY run_time, event_id
    ) AS previous_time
  FROM fact_pipeline_run
  WHERE run_time >= :start_date
    AND run_time <  :end_date
    AND subject_key = 'subject'
)
SELECT
  entity_key,
  previous_stage,
  stage_code,
  event_time,
  event_time - previous_time AS elapsed,
  CASE
    WHEN event_time < previous_time THEN 'time_reversed'
    WHEN previous_stage = stage_code THEN 'duplicate_stage'
    WHEN previous_stage IS NULL THEN 'missing_prefix'
    ELSE 'candidate_delay'
  END AS exception_type
FROM ordered_events
WHERE event_time < previous_time
   OR previous_stage = stage_code
   OR event_time - previous_time > INTERVAL '1 hour'
ORDER BY exception_type, elapsed DESC;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把数据血缘追踪的验收证据写成门禁

```python
import pandas as pd

KEY = ["entity_key", "event_id"]
AMOUNT_COLUMNS = ["metric_value", "adjustment_value"]


def reconcile(source: pd.DataFrame, result: pd.DataFrame) -> pd.DataFrame:
    def aggregate(frame: pd.DataFrame, side: str) -> pd.DataFrame:
        grouped = (
            frame.groupby("entity_key", dropna=False)
            .agg(
                event_cnt=("event_id", "nunique"),
                metric_sum=("metric_value", "sum"),
                adjustment_sum=("adjustment_value", "sum"),
            )
            .reset_index()
        )
        return grouped.rename(columns={
            "event_cnt": f"{side}_event_cnt",
            "metric_sum": f"{side}_metric_sum",
            "adjustment_sum": f"{side}_adjustment_sum",
        })

    compared = aggregate(source, "source").merge(
        aggregate(result, "result"),
        on="entity_key",
        how="outer",
    )
    compared["metric_diff"] = (
        compared["result_metric_sum"].fillna(0)
        - compared["source_metric_sum"].fillna(0)
    )
    compared["event_diff"] = (
        compared["result_event_cnt"].fillna(0)
        - compared["source_event_cnt"].fillna(0)
    )
    compared["exception"] = compared.apply(
        lambda row: "missing_result" if pd.isna(row["result_metric_sum"])
        else "unexpected_result" if pd.isna(row["source_metric_sum"])
        else "count_diff" if row["event_diff"] != 0
        else "amount_diff",
        axis=1,
    )
    return compared.loc[
        (compared["metric_diff"].abs() > 0) | (compared["event_diff"] != 0)
    ].sort_values("metric_diff", key=lambda values: values.abs(), ascending=False)
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
