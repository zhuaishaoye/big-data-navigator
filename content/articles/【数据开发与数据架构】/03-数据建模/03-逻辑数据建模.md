# 逻辑数据建模

> [!abstract] 工程视角
> 如果只记住“逻辑数据建模”的定义，遇到真实数据时仍然很难行动。本文把它拆成五个可检查问题：谁在使用、流程在哪里变化、数据一行代表什么、异常如何发现、上线后用哪个指标验收。每个部分都配一个工作案例或代码片段。

## 1. 需求、SLA 与边界

“逻辑数据建模”首先是工程问题，其次才是工具选择。立项时明确：

- 谁消费数据或服务，用来做什么决策或操作。
- 数据从产生到可用允许延迟多久，失败时能否接受部分结果。
- 更新频率、保留周期、回放范围、并发和数据量级。
- 上下游依赖、权限、敏感字段、审计和成本上限。
- 正确性、完整性和一致性中，哪些必须强保证，哪些可最终一致。

数据开发与数据架构中常见的交付指标包括任务成功率、数据延迟、资源消耗。不要只写“稳定”“高效”，应定义可监测的 SLI、SLO 和错误预算。

## 2. 数据链路与模型

| 层次 | 本文建议 | 关键问题 | 验收证据 |
| --- | --- | --- | --- |
| 数据源 | 调度平台、元数据平台、数据质量平台 | 权威源、更新频率、主键和权限 | 接口或表清单 |
| 接入 | 批、流或 CDC 按业务时延选择 | 重复、顺序、断点续传和回放 | 延迟与幂等测试 |
| 存储 | 按访问模式选择数据湖、数仓或 OLAP | 分区、格式、生命周期和成本 | 容量与查询评测 |
| 计算 | SQL、Spark、Flink 或 Python 服务 | 粒度、状态、资源和失败恢复 | 压测与执行计划 |
| 治理 | 元数据、质量、血缘、权限 | 责任、规则、影响分析和审计 | 规则结果与变更记录 |
| 服务 | 指标、API、看板或应用 | SLA、缓存、限流和版本 | 监控与验收样例 |

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 数据源 | `source_id` | 需求评审 |
| 过程对象 | 数据表 | `table_id` | 源系统接入 |
| 过程对象 | 处理任务 | `job_id` | 模型设计 |
| 结果对象 | 数据服务 | `service_id` | 开发测试 |
| 结果对象 | 运行实例 | `run_id` | 发布调度 |
| 专题分析 | 逻辑数据建模 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

链路设计先明确事实粒度。例如一行代表一次事件、一条订单明细、一个每日快照还是一个任务运行实例。粒度一旦混用，后面即使加了汇总表，也会把数量和金额累计两次。

## 3. 案例一：华南某制造集团

### 案例 1：华南某制造集团的“逻辑数据建模”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“逻辑数据建模”映射到“数仓、数据湖与建模”中的一致性，而不是泛泛讨论概念。
- **触发事件**：集团数据湖接入多个工厂后，同一设备指标出现多个版本。
- **业务与数据范围**：设备、工单、工序、批次、停机、质检和能源数据。数据侧重点采集金额、行数、主键、状态和抽样明细，并与调度平台、元数据平台、数据质量平台中的时间、状态和责任人信息对齐。
- **需要回答的问题**：事实、维度和指标能否与源系统及既有报表对账。
- **关键障碍**：工厂编码不统一，设备组织关系只保留当前状态，湖表小文件过多影响查询。同时要防止重复写入把表面指标带偏。
- **处理过程**：建立设备与组织主数据映射，使用有效期维度，按业务过程拆分事实并优化分区和文件大小。实施时把“金额、数量、去重对象和状态转换都要有独立对账样例”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：复合案例同时解决口径、历史归属和查询成本，而不是只迁移存储格式。验收至少同时看主指标、金额、行数、主键、状态和抽样明细和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“先定义业务过程、事实粒度和维度有效期，再决定分层、宽表、湖仓格式与查询引擎；模型要能被复算、追溯和稳定消费。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

## 4. 代码实现：从可运行到可维护

### 专题实现代码

```sql
-- "逻辑数据建模"
-- 先声明粒度：一行 = 一个订单商品行在支付成功时形成的可加事实。
WITH paid_order AS (
  SELECT
    order_id,
    order_line_id,
    merchant_id,
    paid_at,
    quantity,
    pay_amount,
    refund_amount,
    ROW_NUMBER() OVER (PARTITION BY order_line_id ORDER BY updated_at DESC) AS rn
  FROM dwd_order_line
  WHERE dt >= DATE '2026-10-01'
    AND dt <  DATE '2026-11-01'
    AND pay_status = 'PAID'
),
dim_merchant AS (
  SELECT merchant_id, category_name, valid_from, valid_to
  FROM dim_merchant
  WHERE valid_from < DATE '2026-11-01'
    AND valid_to >= DATE '2026-10-01'
)
SELECT
  DATE(p.paid_at) AS stat_date,
  m.category_name,
  COUNT(DISTINCT p.order_id) AS order_cnt,
  SUM(p.quantity) AS item_cnt,
  SUM(p.pay_amount - p.refund_amount) AS net_gmv
FROM paid_order p
JOIN dim_merchant m
  ON p.merchant_id = m.merchant_id
 AND p.paid_at >= m.valid_from
 AND p.paid_at <  m.valid_to
WHERE p.rn = 1
GROUP BY DATE(p.paid_at), m.category_name;

-- 对账：事实主键、金额平衡、维度有效期、跨期退款和源系统抽样分别留证据。
```

### 统一口径诊断 SQL

```sql
-- 逻辑数据建模：分位对比诊断（任务类型 × 资源队列）
WITH scoped AS (
  SELECT
    source_id AS entity_key,
    event_id,
    run_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_pipeline_run
  WHERE run_time >= DATE '2026-07-01'
    AND run_time <  DATE '2026-10-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '服务可用率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

工程代码至少要满足以下要求：

1. 输入输出明确，参数来自配置或调度上下文。
2. 重跑同一分区不会产生重复结果。
3. 关键步骤记录度量，便于定位数据量和状态变化。
4. 失败可重试，但不会无限重试或放大副作用。
5. 版本、表结构和依赖变更可追踪。
6. 敏感信息不写进代码、日志和异常信息。

## 5. 测试方法与质量门禁

| 专题检查项 | 失败时会看到什么 | 首选证据 | 处理动作 |
| --- | --- | --- | --- |
| 为每个事实表写清业务过程、粒度、主键、时间字段和可加性 | 事实、维度和指标能否与源系统及既有报表对账 | 金额、行数、主键、状态和抽样明细 | 差异分类后再发布 |
| 维度保留历史有效期，跨期比较使用当时归属 | ODS、DWD、DWS、ADS 或湖仓分层各自解决什么问题 | 血缘、复用率、查询模式和成本 | 禁止用跨层直读绕过口径 |
| 金额、数量、去重对象和状态转换都要有独立对账样例 | 一行事实代表什么动作或结果，时间与金额如何记录 | 业务单据、事件日志、粒度说明和主键 | 粒度不清时停止开发 |
| 湖仓格式与分区、文件大小、元数据和生命周期必须一起评估 | 维度是否缓慢变化，历史归属按业务时间还是当前状态 | 维度有效期、代理键和源系统映射 | 跨期报表统一使用业务时间 |

### 质量门禁与失败样本

```python
# 逻辑数据建模：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "逻辑数据建模"
TOPIC_KEY = "subject"
RULE_ID = "rule_engineering_1f9jc1a"
GUIDE_CHECKS = [
    "为每个事实表写清业务过程、粒度、主键、时间字段和可加性",
    "维度保留历史有效期，跨期比较使用当时归属",
    "金额、数量、去重对象和状态转换都要有独立对账样例",
    "湖仓格式与分区、文件大小、元数据和生命周期必须一起评估"
]
RULES = {
    "required_columns": ["event_id", "source_id", "run_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "source_id",
    "time_field": "run_time",
    "max_duplicate_rate": 0.0008,
    "max_null_rate": 0.004,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：为每个事实表写清业务过程、粒度、主键、时间字段和可加性；维度保留历史有效期，跨期比较使用当时归属；金额、数量、去重对象和状态转换都要有独立对账样例；湖仓格式与分区、文件大小、元数据和生命周期必须一起评估
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

测试分为开发环境和生产前门禁。开发环境可以使用抽样数据快速验证逻辑，生产前门禁必须检查分区覆盖、主键、比例异常、上下游对账和资源消耗。数据发布后还要验证消费者能够读取、权限正确且时延在 SLA 内。

## 7. 性能、容量与成本

| 瓶颈 | 先测量 | 可选手段 | 风险 |
| --- | --- | --- | --- |
| 扫描过多 | 分区命中、文件数、字节数 | 分区裁剪、列裁剪、压缩格式 | 分区过碎 |
| Shuffle 重 | 数据量、键分布、并发 | 预聚合、盐化、调整并发 | 资源争抢 |
| 热点倾斜 | Task 时长、输入大小 | 拆分热点键、两阶段聚合 | 结果顺序变化 |
| 状态过大 | Checkpoint、状态后端 | TTL、增量 Checkpoint、拆分 | 业务语义风险 |
| 查询慢 | 执行计划、缓存命中 | 预聚合、物化视图、OLAP | 数据新鲜度 |
| 成本高 | CPU、内存、存储、调用 | 生命周期、冷热分层、弹性 | SLA 退化 |

调优必须建立基线和回归对比：执行时间、扫描量、Shuffle 量、峰值内存、失败率和成本。只展示一次“从 30 分钟到 3 分钟”不够，还要说明数据量、资源和结果是否正确。

## 9. 发布、监控与故障处理

发布流程建议包括：代码评审、配置评审、数据迁移评审、灰度、对账、可观测性检查和回滚演练。监控至少覆盖任务、数据、服务、资源和业务五层。

故障处理顺序：

1. 确认影响面和是否需要暂停下游。
2. 保存现场：任务日志、参数、版本、输入输出计数。
3. 阻断错误扩散，必要时回滚到上一个稳定版本。
4. 按源系统、接入、计算、存储、服务和消费逐层定位。
5. 修复后按受影响分区补数，并验证重复、缺失和时序。

### 案例 4：逻辑数据建模失败后如何做到可恢复

某组织希望用“逻辑数据建模”支持一次真实决策，但在取数与评审阶段发现，一次错误发布已经产生结果，团队只能凭负责人记忆寻找影响范围，补数后仍无法确认是否重复或遗漏。这个案例因此从问题定义重新开始。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 让错误输入、处理版本、影响分区和恢复结果都能被独立回放和审计。在本场景里，核心风险还包括热点倾斜，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。

- **关键异常或争议：** 一次错误发布已经产生结果，团队只能凭负责人记忆寻找影响范围，补数后仍无法确认是否重复或遗漏。初看时，数据仓库与API 网关的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 运行参数、代码版本、输入快照、输出摘要、受影响分区、回滚记录和补数对账。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“SRE”确认什么结果可以进入下一步。

- **失败路径：** 直接覆盖目标表，或者把所有分区全部重跑以求省事。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。

```sql
    AND last_altered_at >= :change_time
),
downstream_assets AS (
  SELECT
    asset_id,
    asset_name,
    asset_type,
    owner_name,
    criticality,
    last_used_at
  FROM metadata_asset_relation
  WHERE upstream_asset_id = :source_asset_id
    AND relation_status = 'active'
)
SELECT
  d.asset_id,
  d.asset_name,
  d.asset_type,
  d.owner_name,
  d.criticality,
  d.last_used_at,
  COUNT(c.column_name) AS changed_column_cnt,
  CASE
    WHEN d.criticality IN ('core', 'regulated') THEN 'block_release'
    WHEN d.last_used_at >= CURRENT_DATE - INTERVAL '7 days' THEN 'notify_owner'
    ELSE 'register_review'
  END AS required_action
FROM downstream_assets d
CROSS JOIN changed_columns c
GROUP BY d.asset_id, d.asset_name, d.asset_type, d.owner_name, d.criticality, d.last_used_at
ORDER BY
  CASE WHEN d.criticality IN ('core', 'regulated') THEN 0 ELSE 1 END,
  d.last_used_at DESC;

-- 目标：变更前识别 调度平台、元数据平台、数据质量平台 之后的所有结果与消费者。
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把逻辑数据建模的验收证据写成门禁

```python
from datetime import date
from hashlib import sha256

import pandas as pd

SUBJECT = "逻辑数据建模"
BLOCKING_RULES = ["分区覆盖完整","任务幂等","依赖无环"]


def validate_release(frame: pd.DataFrame, start: date, end: date) -> dict:
    scoped = frame.loc[
        frame["event_date"].between(pd.Timestamp(start), pd.Timestamp(end))
        & (frame["subject_key"] == "subject")
    ].copy()
    checks = {
        "has_rows": len(scoped) > 0,
        "event_id_unique": not scoped["event_id"].duplicated().any(),
        "entity_key_complete": scoped["entity_key"].notna().all(),
        "event_time_present": scoped["event_time"].notna().all(),
        "scope_matches": scoped["subject_key"].nunique() == 1,
    }
    payload = f"{SUBJECT}|{start}|{end}|{len(scoped)}|{sorted(checks.items())}"
    return {
        "subject": SUBJECT,
        "rows": len(scoped),
        "checks": checks,
        "blocking_rules": BLOCKING_RULES,
        "release_allowed": all(checks.values()),
        "evidence_hash": sha256(payload.encode("utf-8")).hexdigest(),
    }
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。

### 四个案例共用的验收清单
