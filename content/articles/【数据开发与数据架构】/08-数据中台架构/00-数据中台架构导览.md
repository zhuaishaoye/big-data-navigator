# 数据中台架构导览

> [!abstract] 企业数据能力平台实战手册
> 数据中台架构不是把所有数据集中到一个大库，而是通过业务域治理、公共能力复用、资产认证、服务目录、成本和退出机制，把分散的数据能力沉淀为可持续复用的企业资产。

## 1. 数据中台架构导览：定义、适用边界与决策出口

数据中台架构不是把所有数据集中到一个大库，而是通过业务域治理、公共能力复用、资产认证、服务目录、成本和退出机制，把分散的数据能力沉淀为可持续复用的企业资产。

**本篇的适用边界。** 本篇讨论中台的能力分层、资产准入、复用、服务与运营；不把采购某套产品、建设一个数据湖或成立一个部门自动视为中台成功。

**最常见的错误替代。** 不能用“复用率”掩盖强制调用，也不能把所有报表都迁入中台；没有业务域责任和退出机制的中心化会制造新的瓶颈。

**最终决策。** 架构委员会和业务数据负责人要判断：哪些能力进入公共层，哪些保留域内，资产是否达到认证标准，服务中心如何收费，何时拆分或退出。 因此，这篇内容不从“应该建哪张表”开始，而从业务动作、责任人和失败后果开始。只有先确定谁在什么时点做出什么决定，字段、SQL、看板和模型才有明确用途。

围绕“数据中台架构导览”，工作中至少要区分四类问题：

1. **身份问题**：对象是谁，主键能否跨系统稳定关联，合并、拆分、撤销后历史是否还看得见。
2. **时间问题**：业务发生、状态生效、数据入仓、计算完成和人员行动分别发生在哪一刻。
3. **状态问题**：当前状态是一段事件、一张快照还是最终结果，空值代表未发生、未采集还是已删除。
4. **责任问题**：谁确认口径，谁处理异常，谁有权放行或停止，谁在观察期后复盘。

## 2. 数据中台架构导览的完整业务流程

| 环节 | 要做的事 | 最小证据 | 失败后先查什么 |
| --- | --- | --- | --- |
| 业务域与能力盘点 | 识别对象、指标、服务、重复建设与共性需求 | 域模型、能力地图、现状成本和使用方 | 资产很多但无人能使用 |
| 公共资产准入 | 评估跨域复用、稳定性、合规和生命周期 | 准入申请、复用证据、责任人和 SLA | 行政命令推动所有团队调用 |
| 数据与模型分层 | 设计贴源、公共明细、公共汇总和指标服务边界 | 分层模型、粒度、血缘和版本 | 所有数据无条件复制到中心 |
| 资产开发与认证 | 完成质量、安全、性能和文档验收 | 测试、对账、权限、SLO 和资产卡 | 历史资产永久保留 |
| 服务发布与订阅 | 通过 API、数据集或指标服务向消费方提供能力 | 服务目录、契约、配额和订阅关系 | 资产很多但无人能使用 |
| 运营与成本 | 观测采用、复用、质量、时延、成本和支持负担 | 调用日志、用户反馈、成本和账单 | 行政命令推动所有团队调用 |
| 评估与退出 | 识别低价值资产、重复资产和边界变化 | 复审、迁移、下线计划和消费方通知 | 所有数据无条件复制到中心 |

把 业务域与能力盘点、公共资产准入、数据与模型分层、资产开发与认证、服务发布与订阅、运营与成本、评估与退出 串起来后可以看出，数据中台架构导览不是一个孤立字段，而是一条会跨系统、跨岗位、跨时间的证据链。流程图上每一段都应标出输入、输出、状态、时间戳、责任人和异常出口。只要其中一段只能靠口头解释，后续的统计、追责和自动化就会失去基础。

一个合格的需求说明应该写成：

> 在【授权数据范围】和【观察窗口】内，围绕“数据中台架构导览”的【业务域】，按【business_domain_id、data_product_id、service_tier、region_code】比较【有效复用域数】及其【认证资产复用率】，定位一个可干预节点；行动后同时观察主指标、样本量和护栏，任何高风险异常先阻断再调查。

## 3. 数据中台架构导览的数据对象与系统契约

| 数据对象 | 建议主键 | 一行代表什么 | 不允许混淆 |
| --- | --- | --- | --- |
| 业务域 | `business_domain_id` | 具有责任边界和统一语义的业务范围 | 对象身份与业务事件 |
| 公共数据资产 | `shared_data_asset_id` | 经准入并承诺服务水平的可复用数据能力 | 事件、状态快照和结果粒度 |
| 数据产品 | `data_product_id` | 面向明确用户和场景交付的数据、接口或指标集合 | 事件、状态快照和结果粒度 |
| 服务契约 | `service_contract_id` | SLA、字段、版本、配额和支持责任约定 | 事件、状态快照和结果粒度 |
| 订阅关系 | `subscription_id` | 消费方与资产、服务版本之间有效期关系 | 事件、状态快照和结果粒度 |
| 使用成本 | `usage_cost_id` | 存储、计算、调用和支持资源的分摊记录 | 事件、状态快照和结果粒度 |

对象表不是把所有字段塞进一张宽表。事件、状态快照和结果表应该分别保留粒度，再通过稳定主键与版本建立关联。尤其要避免三个常见混算：把一次业务事件算成多个对象、把每日快照相加当事件总量、把最新状态覆盖历史状态。

本主题的数据契约至少应包含：

- `subscription_id` 的唯一性规则、生成方式和跨系统映射。
- `observed_at` 的业务含义、时区、迟到和补录规则。
- `subscription_status` 的完整状态集合，以及删除、撤销、冻结和失效的表示方法。
- 控制对象 `platform_service_contract.service_contract_id` 与主对象的关系。
- 每次口径、规则、模型或源版本变化的影响范围和下游通知对象。
- 敏感字段、允许用途、访问角色、导出限制和审计保留时间。

## 4. 数据中台架构导览的指标、样本与验收口径

| 指标 | 公式或定义 | 口径提醒 |
| --- | --- | --- |
| 有效复用域数 | 使用认证资产的不同业务域数 | 同一域多团队重复调用不重复计数 |
| 认证资产复用率 | 被至少两个有效场景使用的认证资产数 / 认证资产数 | 强制调用和测试流量不计 |
| 服务 SLO 达标率 | 满足时延、可用性和质量 SLO 的观察窗口数 / 总观察窗口 | 分服务等级统计 |
| 单位有效请求成本 | 平台总成本 / 产生业务结果的有效请求量 | 需排除重试、扫描和测试流量 |
| 低效资产退出完成率 | 按计划下线并完成迁移的资产数 / 应退出资产数 | 下线通知、迁移证据和残留调用要核验 |

指标字典至少写到“任何人都能按同一份数据复跑”的程度：中文名、业务定义、公式、分子、分母、事实粒度、时间字段、对象范围、排除项、版本、负责人和验收样例，一个都不能少。比例指标必须同时展示分子、分母和样本量；金额或数量必须做守恒；状态指标必须能回到事件时间线。

对于“数据中台架构导览”，建议把观察分成三层：

| 层次 | 看什么 | 不能替代什么 |
| --- | --- | --- |
| 业务结果 | 有效复用域数、认证资产复用率 | 不能替代过程证据和个案回查 |
| 过程护栏 | 服务 SLO 达标率、单位有效请求成本、低效资产退出完成率 | 不能因为护栏暂时正常就跳过异常调查 |
| 数据证据 | 主键、时间、状态、版本、来源目标对账 | 不能只看任务成功或报表能打开 |

## 5. 数据中台架构导览：七个真实工作场景

以下七组场景均为公开方法结合常见工作流程构造的“脱敏复合示例”，不对应任何单一企业、患者、客户或雇员事实。场景的目的，是展示如何从现象走到证据、行动和验收，而不是虚构经营成果。

### 1. 中台资产很多但业务仍重复建设

**现场。** 平台目录有数百个资产，业务团队仍各建一套客户标签。

**怎么查。** 按资产、调用、口径和业务场景追踪，发现大量资产没有文档、责任人或可用 SLA。

**怎么处理。** 认证前要求真实消费方和复用证据；合并重复资产；未认证资产不进入公共目录首页。

**验收结论。** 资产数量不是能力。能被理解、订阅和稳定使用才算复用。

### 2. 公共层口径变化影响全公司

**现场。** 一个公共指标修改去重逻辑，多个业务看板同时变化。

**怎么查。** 查版本、订阅关系和发布通知，发现所有消费方直接引用最新视图。

**怎么处理。** 公共资产采用版本化契约；重大变更先影子发布；按订阅关系通知；保留旧版本过渡窗口。

**验收结论。** 中心化放大复用，也放大变更风险。版本和通知必须是服务的一部分。

### 3. 强制调用制造虚假复用率

**现场。** 管理要求所有报表必须走中台，复用率快速提升。

**怎么查。** 调用日志显示同一团队只是把原表复制进公共层，没有跨域使用。

**怎么处理。** 复用按独立域和真实场景核验；域内封装与跨域复用分开；管理指标不替代架构判断。

**验收结论。** 被制度推动的调用不等于有价值的能力沉淀。

### 4. 公共明细层变成巨型泥潭

**现场。** 所有源表原样复制到公共层，开发速度快但依赖混乱。

**怎么查。** 分析表依赖、重复字段、使用频率和变更记录，发现公共层没有准入标准和粒度说明。

**怎么处理。** 公共层只保留经过认证的共享对象；域内加工保留在域内；按粒度分层；定期清理无人使用资产。

**验收结论。** 公共层不是数据垃圾场。复用需要边界，不是无限集中。

### 5. 成本无法回到消费方

**现场。** 平台成本持续上升，但不知道哪些业务从中受益。

**怎么查。** 关联任务、服务、存储、请求和订阅关系，发现多个高成本任务只为一次性分析。

**怎么处理。** 建立可解释的成本分摊和预算护栏；高成本低使用资产复审；将一次性与共享工作负载区分。

**验收结论。** 没有成本信号的中心化会鼓励无限需求。

### 6. 故障时中台成为单点瓶颈

**现场。** 公共服务故障导致多个业务同时不可用。

**怎么查。** 梳理订阅关系和降级路径，发现关键业务没有本地缓存或替代数据。

**怎么处理。** 按业务重要性设计多级 SLA、隔离和降级；公共能力需要容量和故障演练；关键消费方保存应急方案。

**验收结论。** 集中复用必须同时设计中台失效时的业务连续性。

### 7. 老资产无人敢下线

**现场。** 早期数据产品已无真实用户，但每次下线都因“可能有风险”被推迟。

**怎么查。** 核对调用来源、账号状态、最后业务使用和迁移计划，区分扫描流量与真实依赖。

**怎么处理。** 设置资产生命周期和复审日期；停止新订阅；提供迁移窗口；到期按流程下线并保留归档。

**验收结论。** 没有退出机制的架构只会不断累积维护成本。

七个场景可以归成一条共同判断顺序：先确认对象和时间，再确认状态和版本；然后做总量、结构和明细三层对账；最后才讨论策略、模型或工具。若一条结论不能指出对应的原始记录、责任人和行动出口，就只能算观察，不能作为生产结论。

## 6. 数据中台架构导览的第一段 SQL：重建业务链路

下面的 SQL 用于说明对象、时间、状态、版本和分层口径如何进入同一条可复查路径。表名和部分字段是通用示例，落地时应映射到企业数据字典；SQL 方言也需按实际引擎调整。

```sql
-- 数据中台架构导览：按业务对象重建链路，避免事件、快照和结果混算
WITH ranked_subscription_id AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY subscription_id
      ORDER BY updated_at DESC
    ) AS version_no
  FROM platform_data_asset_usage
  WHERE observed_at >= TIMESTAMP '{start_time}'
    AND observed_at <  TIMESTAMP '{end_time}'
    AND subscription_status NOT IN ('deleted', 'test')
),
valid_rows AS (
  SELECT
    subscription_id,
    business_domain_id,
    data_product_id,
    service_tier,
    region_code,
    observed_at,
    subscription_status,
    ingested_at
  FROM ranked_subscription_id
  WHERE version_no = 1
)
SELECT
  business_domain_id, data_product_id, service_tier, region_code,
  COUNT(DISTINCT subscription_id) AS object_cnt,
  COUNT(DISTINCT CASE WHEN verified_business_use THEN business_domain_id END) AS numerator_value,
  COUNT(DISTINCT data_product_id) AS denominator_value,
  CAST(COUNT(DISTINCT CASE WHEN verified_business_use THEN business_domain_id END) AS DOUBLE PRECISION)
    / NULLIF(COUNT(DISTINCT data_product_id), 0) AS metric_value,
  MIN(observed_at) AS first_event_at,
  MAX(observed_at) AS last_event_at
FROM valid_rows
GROUP BY business_domain_id, data_product_id, service_tier, region_code
ORDER BY metric_value DESC, object_cnt DESC;
```

执行后至少回答六个问题：

- 同一对象是否因为多源回传产生多版本，版本保留是否符合业务要求？
- 业务时间与入仓时间是否分开，补录和迟到数据是否进入正确分区？
- 分子分母是否来自同一对象范围和同一统计窗口？
- 维度使用的是事件当时值还是当前值，跨期比较是否一致？
- 删除、撤销、冻结和测试数据是否按规则处理？
- 分组结果能否在明细中抽样复现？

## 7. 数据中台架构导览的第二段 SQL：源、控制和结果三方对账

```sql
-- 数据中台架构导览：源对象、控制对象和结果对象三方对账
WITH population AS (
  SELECT
    subscription_id,
    observed_at,
    subscription_status
  FROM platform_data_asset_usage
  WHERE observed_at >= TIMESTAMP '{start_time}'
    AND observed_at <  TIMESTAMP '{end_time}'
),
control AS (
  SELECT
    subscription_id,
    SUM(contracted_version) AS control_value,
    COUNT(DISTINCT service_contract_id) AS control_cnt,
    MAX(updated_at) AS control_updated_at
  FROM platform_service_contract
  WHERE updated_at >= TIMESTAMP '{start_time}'
  GROUP BY subscription_id
),
result AS (
  SELECT
    subscription_id,
    COUNT(*) AS result_cnt,
    MAX(calculated_at) AS calculated_at
  FROM mart_subscription_id
  WHERE business_date BETWEEN DATE '{start_date}' AND DATE '{end_date}'
  GROUP BY subscription_id
)
SELECT
  COALESCE(p.subscription_id, c.subscription_id, r.subscription_id) AS object_key,
  CASE
    WHEN p.subscription_id IS NULL THEN 'source_missing'
    WHEN c.subscription_id IS NULL THEN 'control_missing'
    WHEN r.subscription_id IS NULL THEN 'result_missing'
    WHEN ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0 THEN 'count_or_value_gap'
    ELSE 'matched'
  END AS reconciliation_status,
  p.subscription_status,
  c.control_value,
  c.control_cnt,
  r.result_cnt,
  c.control_updated_at,
  r.calculated_at
FROM population p
FULL OUTER JOIN control c ON p.subscription_id = c.subscription_id
FULL OUTER JOIN result r ON COALESCE(p.subscription_id, c.subscription_id) = r.subscription_id
WHERE p.subscription_id IS NULL
   OR c.subscription_id IS NULL
   OR r.subscription_id IS NULL
   OR ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0;
```

这段查询故意不使用“总数相差小于某个随意百分比就算通过”。它先找出缺失对象和状态差异，再检查控制值与结果值。对于数据中台架构导览，数量、金额、时长或状态任意一项无法解释，都不能用“业务波动”代替排查。

对账结果建议分成四类处理：

1. **阻断**：对象缺失、关键时间为空、状态非法、金额或数量不守恒、权限越界。
2. **严重**：比例或总量显著偏离基线，且无法由已确认的对象结构变化解释。
3. **观察**：小范围波动但来源、样本和趋势可控，进入责任人和观察窗口。
4. **探索**：只有弱信号或假设，不进入正式结论，更不直接触发业务处罚。

## 8. 数据中台架构导览的 Python 发布门禁与指标护栏

第一段代码把发布条件写成可执行对象，避免“检查过了”只存在聊天记录里：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class SubscriptionIdBatch:
    batch_id: str
    source_rows: int
    valid_rows: int
    duplicate_keys: int
    missing_required_fields: int
    reconciliation_gap: float

def release_subscription_id(batch: SubscriptionIdBatch) -> dict:
    checks = {
        "source_not_empty": batch.source_rows > 0,
        "valid_rows_in_range": 0 <= batch.valid_rows <= batch.source_rows,
        "duplicate_rate_ok": batch.duplicate_keys / max(batch.source_rows, 1) <= 0.001,
        "required_fields_ok": batch.missing_required_fields == 0,
        "reconciliation_ok": abs(batch.reconciliation_gap) <= 0.01,
    }
    return {
        "topic": "数据中台架构导览",
        "batch_id": batch.batch_id,
        "checks": checks,
        "release_allowed": all(checks.values()),
        "blocking_checks": [name for name, passed in checks.items() if not passed],
    }
```

第二段代码演示如何为比例类结果附带样本证据和小样本下界。它不是替代统计学家的模型，而是防止把少量偶然样本直接包装成稳定结论：

```python
from dataclasses import dataclass
from math import sqrt

@dataclass(frozen=True)
class SubscriptionIdObservation:
    object_id: str
    numerator: float
    denominator: float
    sample_size: int
    scope_version: str

def calculate_subscription_id(rows: list[SubscriptionIdObservation]) -> list[dict]:
    output = []
    for row in rows:
        value = row.numerator / row.denominator if row.denominator > 0 else None
        # 小样本用 Wilson 下界做护栏，不把偶然的高比例直接当稳定结果。
        z = 1.96
        p = value or 0
        n = max(row.sample_size, 1)
        center = p + z * z / (2 * n)
        margin = z * sqrt((p * (1 - p) + z * z / (4 * n)) / n)
        lower = max(0, (center - margin) / (1 + z * z / n))
        output.append({
            "object_id": row.object_id,
            "metric": "有效复用域数",
            "value": value,
            "lower_bound": lower if value is not None else None,
            "sample_size": row.sample_size,
            "scope_version": row.scope_version,
            "caution": "同一域多团队重复调用不重复计数",
        })
    return output
```

真正上线时还要补充参数配置、日志、血缘、告警级别、重跑幂等、异常样本保存和审批记录。代码通过不代表业务通过；自动检查只能证明已经定义的规则没有被违反，无法证明规则本身一定正确。

## 9. 数据中台架构导览的失败反例与上线验收

| 风险信号 | 错误做法 | 必须补齐的证据 | 发布或行动规则 |
| --- | --- | --- | --- |
| 目录数量冒充能力 | 资产很多但无人能使用 | 责任人、文档、SLA 和真实消费方 | 无消费证据不认证 |
| 强制复用 | 行政命令推动所有团队调用 | 跨域使用和场景价值 | 复用率按独立域核验 |
| 公共层无边界 | 所有数据无条件复制到中心 | 准入规则、粒度和生命周期 | 公共与域内分层治理 |
| 无法下线 | 历史资产永久保留 | 订阅、调用和迁移证据 | 设置复审和退出期限 |

上线验收不应只有一句“报表正常”。建议按下面四层验收：

| 验收对象 | 结构要求 | 测试样本 | 结果证据 |
| --- | --- | --- | --- |
| 业务域 | `business_domain_id` 能唯一定位具有责任边界和统一语义的业务范围 | 正常、重复、缺失、撤销与跨期样本 | 有效复用域数可回到原始对象 |
| 公共数据资产 | `shared_data_asset_id` 能唯一定位经准入并承诺服务水平的可复用数据能力 | 正常、重复、缺失、撤销与跨期样本 | 认证资产复用率可回到原始对象 |
| 数据产品 | `data_product_id` 能唯一定位面向明确用户和场景交付的数据、接口或指标集合 | 正常、重复、缺失、撤销与跨期样本 | 服务 SLO 达标率可回到原始对象 |
| 服务契约 | `service_contract_id` 能唯一定位SLA、字段、版本、配额和支持责任约定 | 正常、重复、缺失、撤销与跨期样本 | 单位有效请求成本可回到原始对象 |
| 订阅关系 | `subscription_id` 能唯一定位消费方与资产、服务版本之间有效期关系 | 正常、重复、缺失、撤销与跨期样本 | 低效资产退出完成率可回到原始对象 |
| 使用成本 | `usage_cost_id` 能唯一定位存储、计算、调用和支持资源的分摊记录 | 正常、重复、缺失、撤销与跨期样本 | 有效复用域数可回到原始对象 |

还应为每一次发布保留一组固定回归样本：正常对象、边界状态、重复记录、缺失字段、撤销或退款、跨期、权限拒绝和失败恢复。回归样本不是演示数据，而是以后每次改规则都能重复执行的质量资产。

## 10. 数据中台架构导览的 30 天落地与复盘

| 阶段 | 主要交付 | 通过条件 |
| --- | --- | --- |
| 第 1 周：定义 | 对象、流程、状态、指标、排除项和责任矩阵 | 业务、数据、安全或质量负责人对同一口径签字 |
| 第 2 周：打通 | 源字段、主键、时间、版本、控制对象和失败样本 | 正常与异常样本都能回到原始记录 |
| 第 3 周：验证 | 总量对账、分层对账、抽样回查、权限测试、回滚演练 | 阻断问题清零，严重问题有责任人与期限 |
| 第 4 周：发布 | 灰度、SLO、监控、行动清单、停止条件和复盘模板 | 使用者在真实场景中完成一次闭环行动 |

如果必须用 90 秒说明“数据中台架构导览”是否做对，可以按这个顺序自测：

1. 一行数据代表什么，主键是什么，哪些对象绝不能混在同一粒度？
2. 业务发生、数据可见、计算完成和行动确认分别在哪个时间点？
3. 本主题最重要的两个主指标、三个护栏和最小样本量是什么？
4. 一个异常出现时，先从原始记录、链路版本还是业务动作开始查？
5. 哪类错误必须阻断发布或停止使用，谁有权批准例外？
6. 上线后由谁在多长时间内观察，什么条件下回滚或结束？

> [!check] 完成标准
> 当另一位数据同事不看聊天记录，只根据口径卡、回归样本和代码就能复跑同一结果；当业务负责人能指出一个异常对应的原始对象、处置动作和复核证据；当系统能够阻止未授权或状态非法的数据进入下游，这篇“数据中台架构导览”才算真正落到工作里。
