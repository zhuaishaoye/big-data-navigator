# 互联网黑话词典

> [!abstract] 场景速览
> 如果只记住“互联网黑话词典”的定义，遇到真实数据时仍然很难行动。本文把它拆成五个可检查问题：谁在使用、流程在哪里变化、数据一行代表什么、异常如何发现、上线后用哪个指标验收。每个部分都配一个工作案例或代码片段。

## 1. “互联网黑话词典”在互联网商业分析业务链中的位置

互联网商业分析的核心流程可以概括为：拉新 → 激活 → 访问与互动 → 转化 → 留存 → 变现 → 召回 → 生态治理。参与角色包括用户、内容创作者、商家、平台运营、产品、算法、广告销售、财务与法务。“互联网黑话词典”通常不是一个孤立字段，而是连接业务动作、数据记录和管理决策的一层能力。

从数据团队视角，至少要回答四个问题：

1. **谁使用**：用户、内容创作者、商家、平台运营分别要用它做判断、执行还是审计。
2. **对象是什么**：一行数据代表用户、一次事件、一个批次还是一天快照。
3. **流程在哪里变化**：通过激活、访问与互动、转化、留存之间的状态和时间差定位问题。
4. **结果如何被采用**：谁在什么时间前采取行动，使用哪个指标观察改善或副作用。

一个合格的专题目标可以写成：

> 在【时间窗】和【授权数据范围】内，围绕“互联网黑话词典”，按【渠道、产品、内容类型】比较【转化率】与【留存率】，定位一个可干预流程节点，并记录行动后的变化与边界。

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 用户 | `user_id` | 拉新 |
| 过程对象 | 内容 | `content_id` | 激活 |
| 过程对象 | 会话 | `session_id` | 访问与互动 |
| 结果对象 | 订单 | `order_id` | 转化 |
| 结果对象 | 广告 | `campaign_id` | 留存 |
| 专题分析 | 互联网黑话词典 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

建模时不要先把所有系统字段堆进一张大表。更稳妥的做法是分别保留三类事实：

- **事件事实**：谁在什么时间做了动作，例如挂号、下单、开工、报警或学习。
- **状态快照**：对象在某一天的状态，例如会员等级、租约、账户余额或设备资产关系。
- **结果事实**：流程完成后的产出，例如结算金额、良品数量、签收结果或考试分数。

三者的粒度不同。把事件、快照和结果强行放在同一行，会让金额、数量和转化率在汇总时重复。若“互联网黑话词典”涉及状态变化，优先建立状态机；若涉及金额，先做借贷或收付平衡；若涉及对象归属，保留维度有效期。

## 3. 指标与口径：不要把相关数字直接当答案

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 点击率 | `COUNT(DISTINCT click_id) / COUNT(DISTINCT impression_id)`（视图字段 `ctr`） | 渠道、产品、内容类型 | 不混用测试、撤销和跨期状态；与“互联网黑话词典”相关时还要补充主题筛选 |
| 转化率 | `COUNT(DISTINCT conversion_id) / COUNT(DISTINCT eligible_session_id)`（视图字段 `cvr`） | 产品、内容类型、用户阶段 | 不混用测试、撤销和跨期状态；与“互联网黑话词典”相关时还要补充主题筛选 |
| 留存率 | `COUNT(DISTINCT retained_user_id) / COUNT(DISTINCT cohort_user_id)`（视图字段 `retention_rate`） | 内容类型、用户阶段、设备 | 不混用测试、撤销和跨期状态；与“互联网黑话词典”相关时还要补充主题筛选 |
| ARPU | `SUM(net_revenue) / COUNT(DISTINCT paying_or_active_user_id)`（视图字段 `arpu`） | 用户阶段、设备 | 不混用测试、撤销和跨期状态；与“互联网黑话词典”相关时还要补充主题筛选 |

指标字典至少应包含：中文名、英文编码、业务定义、计算公式、事实粒度、时间字段、对象范围、排除条件、负责人和验收样例。对于“互联网黑话词典”，还应注明它使用的是业务发生时间还是入仓时间，是否包含撤销、退费、测试、跨期和补录记录。

一个常见误区是看到转化率变化就立即解释业务原因。更可靠的顺序是：

1. 检查数据覆盖和延迟是否变化。
2. 检查对象范围、状态映射和维度归属是否变化。
3. 按时间、结构和分组拆解贡献。
4. 回到明细寻找能解释变化的事件。
5. 如果已经采取行动，再评估行动带来的增量，而不是事后挑一个相关指标。

## 4. 工作案例：从现象到数据处理

### 案例 1：华东某内容社区的“互联网黑话词典”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：日活增长但广告收入下降，业务希望判断是用户结构变化、内容供给还是广告库存问题。本次讨论的重点是“互联网黑话词典”，所以团队先要求把先冻结对象与时间窗写进项目目标，而不是直接开始做报表。
- **数据范围**：内容曝光、点击、停留、互动、广告请求、竞价、成交和会员订单。同时收集埋点平台、CDP、推荐系统、广告平台中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：机器流量混入曝光，多端账号未合并，广告曝光与计费口径不同。进一步检查后发现，如果不先处理埋点重复，“互联网黑话词典”很容易被一个表面相关指标替代。
- **处理过程**：建立用户-内容-广告事件模型，区分自然流量与广告流量，按内容类型和用户价值分层。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目发现低频用户占比上升和高质量内容供给不足，并调整推荐与广告频控。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“互联网黑话词典”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

这个案例最关键的动作不是“跑一条 SQL”，而是把“互联网黑话词典”对应的业务对象和上下游系统放在同一张链路图上。链路图至少要标出源系统、事件时间、关联主键、状态变化、数据负责人和消费方。

## 5. SQL 示例：在统一口径下做分层诊断

下面的查询用于展示分析结构，表名和字段需映射到实际环境。重点是去重、范围筛选、基线比较和贡献率，而不是代码本身。

### 标题专属诊断 SQL

```sql
-- 互联网黑话词典：结构贡献诊断（产品 × 用户阶段）
WITH scoped AS (
  SELECT
    user_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_internet_event
  WHERE event_time >= DATE '2026-05-01'
    AND event_time <  DATE '2026-08-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  'ARPU' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

执行后要回答四类验证题：

- 结果总量能否与源系统或既有报表在相同口径下解释差异？
- 排名前几位的分组是否由少数超长、重复或补录记录造成？
- 缺失日期表现为“未发生”还是“未采集”，是否改变分母？
- 维度使用的是当时归属还是当前归属，跨期比较是否一致？

## 7. Python 示例：把数据质量变成发布门禁

### 可执行质量门禁

```python
# 互联网黑话词典：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "互联网黑话词典"
TOPIC_KEY = "subject"
RULE_ID = "rule_internet_1d3f2os"
GUIDE_CHECKS = [
    "检查事件主键唯一",
    "检查匿名与登录身份打通",
    "检查时区一致"
]
RULES = {
    "required_columns": ["event_id", "user_id", "event_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "user_id",
    "time_field": "event_time",
    "max_duplicate_rate": 0.0006,
    "max_null_rate": 0.003,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：检查事件主键唯一；检查匿名与登录身份打通；检查时区一致
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

这段代码适合放在离线任务完成之后、指标发布之前。真实环境还应从调度平台读取分区参数、把结果写入质量平台，并在关键规则失败时阻断下游。告警不是终点，工单中要记录影响资产、发现时间、临时处理、根因、修复时间和防复发动作。

## 8. 异常排查：从指标异常回到业务事件

| 检查项 | 推荐方法 | 失败动作 | 负责人 |
| --- | --- | --- | --- |
| 事件主键唯一 | 唯一性 SQL + 抽样明细 | 阻断发布 | 用户 |
| 匿名与登录身份打通 | 时间区间与状态机校验 | 阻断发布 | 内容创作者 |
| 时区一致 | 主数据有效期关联 | 告警并登记工单 | 商家 |
| 机器流量已剔除 | 金额或数量平衡校验 | 告警并登记工单 | 平台运营 |
| 渠道归因窗口明确 | 发布前阻断 + 责任人复核 | 告警并登记工单 | 产品 |

围绕“互联网黑话词典”排查时，可以按以下顺序进行：

1. **影响面**：哪些指标、报表、接口或业务团队受影响，是否需要暂停对外发布。
2. **时间线**：源系统变更、任务发布、数据回刷、组织调整和业务活动分别发生在什么时候。
3. **数据链路**：上游是否延迟，分区是否缺失，主键是否重复，状态是否映射错误。
4. **业务证据**：抽取异常记录，与原始单据、操作日志、客服记录或现场系统核对。
5. **修复与复核**：明确补数范围、重跑粒度、回滚版本和验收样例。
6. **防复发**：把一次性排查升级为规则、监控、责任人和变更评审。

特别要注意：埋点重复；匿名身份合并错误；自然流量与付费流量归因重叠；分母口径漂移。这些问题如果不被单独标记，很容易被误写成业务趋势。

### 扩展代码一：从互联网黑话词典回到可核对明细

-- 互联网黑话词典：字段血缘与影响范围
WITH changed_columns AS (
  SELECT column_name
  FROM information_schema.columns
  WHERE table_schema = :source_schema
    AND table_name = :source_table
    AND last_altered_at >= :change_time
),
downstream_assets AS (
  SELECT
    asset_id,
    asset_name,
    asset_type,
    owner_name,
    criticality,
    last_used_at
  FROM metadata_asset_relation
  WHERE upstream_asset_id = :source_asset_id
    AND relation_status = 'active'
)
SELECT
  d.asset_id,
  d.asset_name,
  d.asset_type,
  d.owner_name,
  d.criticality,
  d.last_used_at,
  COUNT(c.column_name) AS changed_column_cnt,
  CASE
    WHEN d.criticality IN ('core', 'regulated') THEN 'block_release'
    WHEN d.last_used_at >= CURRENT_DATE - INTERVAL '7 days' THEN 'notify_owner'
    ELSE 'register_review'
  END AS required_action
FROM downstream_assets d
CROSS JOIN changed_columns c
GROUP BY d.asset_id, d.asset_name, d.asset_type, d.owner_name, d.criticality, d.last_used_at
ORDER BY
  CASE WHEN d.criticality IN ('core', 'regulated') THEN 0 ELSE 1 END,
  d.last_used_at DESC;

import json
from pathlib import Path


def build_evidence_manifest(
    subject: str,
    scope: dict,
    checks: dict,
    samples: list[dict],
    owner: str,
) -> dict:
    failed = [name for name, passed in checks.items() if not passed]
    return {
        "subject": subject,
        "scope": scope,
        "checks": checks,
        "failed_checks": failed,
        "sample_evidence": samples[:5],
        "owner": owner,
        "decision": "block" if failed else "review",
        "manual_questions": [
            "每一项失败是否已回到原始记录",
            "对象、时间和状态是否与指标字典一致",
            "回滚或修复后是否重新完成对账",
        ],
    }


manifest = build_evidence_manifest(
    subject="互联网黑话词典",
    scope={"systems": ["埋点平台","CDP","推荐系统","广告平台"]},
    checks={"definition_frozen": False, "reconciled": False},
    samples=[],
    owner="用户",
)
Path("release-evidence.json").write_text(
    json.dumps(manifest, ensure_ascii=False, indent=2),

)
