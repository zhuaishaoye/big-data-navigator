# AARRR漏斗分析

> [!tip] 分析目标
> 讨论“AARRR漏斗分析”时，最容易犯的错误是直接从工具或报表开始。更有用的顺序是：先看业务链条，再找可观察指标，随后确认数据粒度，最后才选择 SQL、模型或平台组件。本文按这个顺序给出可执行方案和常见的失败样本。

## 1. 把主题翻译成可验证的问题

“AARRR漏斗分析”不能直接等同于“做一张趋势图”。一个可执行的分析问题至少包含对象、时间、比较基准和行动：

> 在【观察周期】内，对【有效对象】按【渠道、产品、内容类型】比较【留存率】与【ARPU】，判断变化来自结构、行为还是数据口径，并验证【策略动作】是否带来可解释的增量。

在互联网商业分析场景中，用户行为、交易结果和策略曝光经常来自不同系统。先画数据流：

埋点平台 → CDP → 推荐系统 → 广告平台 → 订单系统 → 实验平台

图中至少要有三个标记：业务事件发生时间、数据可见时间、策略或行动时间。只有三者分开，后续才能判断问题发生在业务、链路还是观察窗口。

## 2. 指标定义与分母检查

| 专题观测面 | 需要回答的问题 | 关键证据 | 判定与动作 |
| --- | --- | --- | --- |
| 口径（本标题优先） | 分子分母、状态、去重和时间是否一致 | 指标字典、明细抽样、源系统对账 | 口径未冻结不比较趋势 |
| 方法 | 描述、诊断、预测、实验还是准实验 | 数据生成过程、对照组、假设和限制 | 相关结果不得写成因果 |
| 问题 | 要改变谁的行为，比较基线和成功标准是什么 | 决策记录、对象范围、时间窗口和行动负责人 | 不能转成行动的问题先澄清 |
| 行动 | 建议是否可执行，是否有护栏和观察周期 | 决策、负责人、主指标、护栏和复盘 | 没有行动与验证就不算闭环 |

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 点击率 | `COUNT(DISTINCT click_id) / COUNT(DISTINCT impression_id)`（视图字段 `ctr`） | 渠道、产品、内容类型 | 不混用测试、撤销和跨期状态；与“AARRR漏斗分析”相关时还要补充主题筛选 |
| 转化率 | `COUNT(DISTINCT conversion_id) / COUNT(DISTINCT eligible_session_id)`（视图字段 `cvr`） | 产品、内容类型、用户阶段 | 不混用测试、撤销和跨期状态；与“AARRR漏斗分析”相关时还要补充主题筛选 |
| 留存率 | `COUNT(DISTINCT retained_user_id) / COUNT(DISTINCT cohort_user_id)`（视图字段 `retention_rate`） | 内容类型、用户阶段、设备 | 不混用测试、撤销和跨期状态；与“AARRR漏斗分析”相关时还要补充主题筛选 |
| ARPU | `SUM(net_revenue) / COUNT(DISTINCT paying_or_active_user_id)`（视图字段 `arpu`） | 用户阶段、设备 | 不混用测试、撤销和跨期状态；与“AARRR漏斗分析”相关时还要补充主题筛选 |

针对“AARRR漏斗分析”，建议分别定义诊断指标、结果指标和护栏指标：

- **诊断指标**用于定位流程，例如曝光、有效访问、符合条件对象数和异常节点。
- **结果指标**用于判断是否改善，例如转化、留存、客单、毛利或处理时长。
- **护栏指标**用于防止局部优化伤害整体，例如退款、投诉、成本、公平性和长期留存。

每次计算都问四个问题：分母是谁、对象何时进入分母、例外状态怎么处理、窗口是否足够覆盖行为完成。尤其是埋点重复；匿名身份合并错误；自然流量与付费流量归因重叠，任何一项没有解释清楚，指标都可能“看起来合理但无法决策”。

## 3. 方法选择：描述、诊断、预测还是因果

| 目标 | 适合的方法 | 需要的证据 | 不要混淆 |
| --- | --- | --- | --- |
| 描述现状 | 趋势、结构、同期群 | 完整口径、稳定时间窗 | 描述不等于原因 |
| 定位异常 | 分层、贡献度、漏斗、异常检测 | 原始事件、基线和质量检查 | 排名靠前不等于因果 |
| 预测未来 | 时间序列、回归、机器学习 | 时间切分验证、误差成本 | 离线准确率不等于业务收益 |
| 评估策略 | A/B、灰度、准实验 | 对照组、样本量、护栏指标 | 上线前后对比容易混入季节和选择偏差 |

如果问题只是“发生了什么”，先别急着建模；如果问题涉及“采取某策略会怎样”，就必须讨论反事实和识别条件。围绕“AARRR漏斗分析”，应把观察分析、预测和因果评估的产出分开标注。

## 4. 案例一：华北某内容平台

### 案例 1：华北某内容平台的“AARRR漏斗分析”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“AARRR漏斗分析”映射到“分析方法、指标与实验”中的口径，而不是泛泛讨论概念。
- **触发事件**：推荐策略让人均时长增加，但次日留存和创作者多样性下降。
- **业务与数据范围**：实验组、曝光、点击、时长、留存、内容类型、创作者分布和投诉。数据侧重点采集指标字典、明细抽样、源系统对账，并与埋点平台、CDP、推荐系统中的时间、状态和责任人信息对齐。
- **需要回答的问题**：分子分母、状态、去重和时间是否一致。
- **关键障碍**：实验只看点击与时长，没有检查新奇效应、用户结构和内容供给副作用。同时要防止埋点重复把表面指标带偏。
- **处理过程**：增加分层分析、长期观察和多样性护栏，按用户活跃度评估策略差异。实施时把“分析问题写明对象、时间、比较基准、决策和行动负责人”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例项目证明主指标显著后仍需继续观察成本、体验和长期价值。验收至少同时看主指标、指标字典、明细抽样、源系统对账和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把模糊问题翻译成对象、时间、比较基准和行动，检查数据口径与偏差，再选择描述、诊断、预测或因果方法。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

落地时建议先把一个总指标拆成可行动的树：

```text
AARRR漏斗分析｜留存率结果偏离
├── 先验真伪：事件主键唯一是否有批次级证据
├── 再看规模：用户数量与ARPU是否同向变化
├── 结构定位：渠道 → 产品 → 内容类型
├── 链路时点：埋点平台 → CDP → 推荐系统
└── 行动出口：分析问题写明对象、时间、比较基准、决策和行动负责人
```

如果某一分支变化最大，再进入下一层，而不是一开始就按十几个维度切碎。每个分层结果都应同时报告样本量，避免小样本的极端比例抢走注意力。

## 5. SQL：计算趋势、结构和贡献度

### 趋势、结构与贡献度诊断

```sql
-- AARRR漏斗分析：结构贡献诊断（内容类型 × 设备）
WITH scoped AS (
  SELECT
    user_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_internet_event
  WHERE event_time >= DATE '2026-05-01'
    AND event_time <  DATE '2026-08-01'
    AND subject_key = 'aarrr'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '获客成本' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

示例 SQL 只表达计算逻辑。实际实施应加入分区条件、业务状态过滤、时区和主题范围，并在结果中保留口径版本。

当业务方要求“解释为什么下降”时，可以按下面顺序回答：

1. 先确认下降是否真实存在，排查采集、任务、维表和状态映射。
2. 把变化拆成对象数量、行为强度和结构占比。
3. 找到贡献最大的分组，但保留其他分组的抵消效应。
4. 抽取正负样本回查业务事件和操作日志。
5. 把尚不能证明的解释标为假设，并设计下一轮验证。

### 专题验证代码

```sql
-- "AARRR漏斗分析"
WITH assigned AS (
  SELECT
    user_id,
    group_name,
    DATEDIFF(DAY, exposure_time, COALESCE(first_paid_at, CURRENT_TIMESTAMP)) AS pay_delay_days,
    paid_amount,
    refund_amount,
    support_ticket_cnt
  FROM experiment_user_day
  WHERE experiment_id = 'exp_202611'
),
summary AS (
  SELECT
    group_name,
    COUNT(DISTINCT user_id) AS user_cnt,
    AVG(CASE WHEN pay_delay_days <= 7 AND paid_amount > 0 THEN 1 ELSE 0 END) AS conversion_rate,
    SUM(paid_amount - refund_amount) / COUNT(DISTINCT user_id) AS net_revenue_per_user,
    SUM(support_ticket_cnt) * 1.0 / COUNT(DISTINCT user_id) AS ticket_per_user
  FROM assigned
  GROUP BY group_name
)
SELECT *, conversion_rate - MAX(CASE WHEN group_name = 'control' THEN conversion_rate END) OVER () AS uplift
FROM summary;

## 8. 异常、偏差与常见误区

- **辛普森悖论**：总体改善但每个分组都变差，可能由对象结构变化造成。
- **幸存者偏差**：只分析完成流程的对象，忽略中途流失和中止。
- **分母漂移**：渠道口径、登录状态、版本或活动范围变化，改变可比性。
- **回传延迟**：当天数据未回补，导致近期效果被系统性低估。
- **多重比较**：反复寻找显著分组，实际只是随机波动。
- **行动偏差**：只报告支持既定方案的结果，忽略反例和护栏指标。

围绕“AARRR漏斗分析”，应预先写出至少三条反例检查。比如上线后是否有人负责观察和复盘、关键口径是否经过业务与技术共同确认，以及 异常值处理是否可能改变最终排名。

  ROUND(COUNT(*) * 1.0 / NULLIF(COUNT(DISTINCT event_id), 0), 4) AS duplication_ratio
FROM fact_internet_event
WHERE stat_date BETWEEN :start_date AND :end_date
GROUP BY stat_date
HAVING SUM(CASE WHEN event_id IS NULL THEN 1 ELSE 0 END) > 0
    OR SUM(CASE WHEN event_time < business_time THEN 1 ELSE 0 END) > 0
    OR COUNT(*) <> COUNT(DISTINCT event_id)
ORDER BY stat_date;

-- 至少人工核对一次：事件主键唯一；匿名与登录身份打通；时区一致。
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把AARRR漏斗分析的验收证据写成门禁

```python
import pandas as pd

KEY = ["entity_key", "event_id"]
AMOUNT_COLUMNS = ["metric_value", "adjustment_value"]


def reconcile(source: pd.DataFrame, result: pd.DataFrame) -> pd.DataFrame:
    def aggregate(frame: pd.DataFrame, side: str) -> pd.DataFrame:
        grouped = (
            frame.groupby("entity_key", dropna=False)
            .agg(
                event_cnt=("event_id", "nunique"),
                metric_sum=("metric_value", "sum"),
                adjustment_sum=("adjustment_value", "sum"),
            )
            .reset_index()
        )
        return grouped.rename(columns={
            "event_cnt": f"{side}_event_cnt",
            "metric_sum": f"{side}_metric_sum",
            "adjustment_sum": f"{side}_adjustment_sum",
        })

    compared = aggregate(source, "source").merge(
        aggregate(result, "result"),
        on="entity_key",
        how="outer",
    )
    compared["metric_diff"] = (
        compared["result_metric_sum"].fillna(0)
        - compared["source_metric_sum"].fillna(0)
    )
    compared["event_diff"] = (
        compared["result_event_cnt"].fillna(0)
        - compared["source_event_cnt"].fillna(0)
    )
    compared["exception"] = compared.apply(
        lambda row: "missing_result" if pd.isna(row["result_metric_sum"])
        else "unexpected_result" if pd.isna(row["source_metric_sum"])
        else "count_diff" if row["event_diff"] != 0
        else "amount_diff",
        axis=1,
    )
    return compared.loc[
        (compared["metric_diff"].abs() > 0) | (compared["event_diff"] != 0)
    ].sort_values("metric_diff", key=lambda values: values.abs(), ascending=False)
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
