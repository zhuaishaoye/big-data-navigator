# 农业行业全景解析

> [!abstract] 场景速览
> 一个关于“农业行业全景解析”的结论能不能被信任，取决于它是否能回到原始事件、明确时间和对象，并说明排除了哪些记录。下面不会用单一模板概括所有场景，而是结合农业中的多类任务，展示数据建模、代码分析和项目验收之间如何衔接。

## 1. “农业行业全景解析”在农业业务链中的位置

农业的核心流程可以概括为：选种 → 播种 → 田间管理 → 采收 → 分级 → 加工 → 仓储 → 流通 → 溯源。参与角色包括农户、合作社、农技服务、种植基地、加工企业、渠道采购、监管与质检。“农业行业全景解析”通常不是一个孤立字段，而是连接业务动作、数据记录和管理决策的一层能力。

从数据团队视角，至少要回答四个问题：

1. **谁使用**：农户、合作社、农技服务、种植基地分别要用它做判断、执行还是审计。
2. **对象是什么**：一行数据代表地块、一次事件、一个批次还是一天快照。
3. **流程在哪里变化**：通过播种、田间管理、采收、分级之间的状态和时间差定位问题。
4. **结果如何被采用**：谁在什么时间前采取行动，使用哪个指标观察改善或副作用。

一个合格的专题目标可以写成：

> 在【时间窗】和【授权数据范围】内，围绕“农业行业全景解析”，按【区域、地块、作物】比较【投入成本】与【损耗率】，定位一个可干预流程节点，并记录行动后的变化与边界。

## 2. 一张图看清角色、流程和数据

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 地块 | `plot_id` | 选种 |
| 过程对象 | 作物 | `crop_id` | 播种 |
| 过程对象 | 批次 | `batch_id` | 田间管理 |
| 结果对象 | 农事任务 | `task_id` | 采收 |
| 结果对象 | 投入品 | `input_id` | 分级 |
| 专题分析 | 农业行业全景解析 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

建模时不要先把所有系统字段堆进一张大表。更稳妥的做法是分别保留三类事实：

- **事件事实**：谁在什么时间做了动作，例如挂号、下单、开工、报警或学习。
- **状态快照**：对象在某一天的状态，例如会员等级、租约、账户余额或设备资产关系。
- **结果事实**：流程完成后的产出，例如结算金额、良品数量、签收结果或考试分数。

三者的粒度不同。把事件、快照和结果强行放在同一行，会让金额、数量和转化率在汇总时重复。若“农业行业全景解析”涉及状态变化，优先建立状态机；若涉及金额，先做借贷或收付平衡；若涉及对象归属，保留维度有效期。

## 3. 指标与口径：不要把相关数字直接当答案

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 亩产量 | `SUM(harvest_kg) / SUM(planted_mu)`（视图字段 `yield_per_mu`） | 区域、地块、作物 | 不混用测试、撤销和跨期状态；与“农业行业全景解析”相关时还要补充主题筛选 |
| 投入成本 | `SUM(seed_cost + fertilizer_cost + labor_cost + service_cost)`（视图字段 `input_cost`） | 地块、作物、批次 | 不混用测试、撤销和跨期状态；与“农业行业全景解析”相关时还要补充主题筛选 |
| 损耗率 | `(SUM(harvest_kg) - SUM(sellable_kg)) / SUM(harvest_kg)`（视图字段 `loss_rate`） | 作物、批次、农事类型 | 不混用测试、撤销和跨期状态；与“农业行业全景解析”相关时还要补充主题筛选 |
| 合格率 | `COUNT(DISTINCT passed_batch_id) / COUNT(DISTINCT inspected_batch_id)`（视图字段 `pass_rate`） | 批次、农事类型 | 不混用测试、撤销和跨期状态；与“农业行业全景解析”相关时还要补充主题筛选 |

指标字典至少应包含：中文名、英文编码、业务定义、计算公式、事实粒度、时间字段、对象范围、排除条件、负责人和验收样例。对于“农业行业全景解析”，还应注明它使用的是业务发生时间还是入仓时间，是否包含撤销、退费、测试、跨期和补录记录。

一个常见误区是看到投入成本变化就立即解释业务原因。更可靠的顺序是：

1. 检查数据覆盖和延迟是否变化。
2. 检查对象范围、状态映射和维度归属是否变化。
3. 按时间、结构和分组拆解贡献。
4. 回到明细寻找能解释变化的事件。
5. 如果已经采取行动，再评估行动带来的增量，而不是事后挑一个相关指标。

## 4. 工作案例：从现象到数据处理

### 案例 1：华南某农产品加工企业的“农业行业全景解析”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：某批次产品被渠道退回，企业需要在数小时内确认原料来源和受影响成品。本次讨论的重点是“农业行业全景解析”，所以团队先要求把先冻结对象与时间窗写进项目目标，而不是直接开始做报表。
- **数据范围**：收购、原料批次、加工投料、成品批次、质检、仓储和发货。同时收集农场管理系统、物联网平台、加工 MES、仓储系统中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：农户交售批次与内部原料批次不是一对一，手工补录导致加工时间与质检时间冲突。进一步检查后发现，如果不先处理批次追溯断链，“农业行业全景解析”很容易被一个表面相关指标替代。
- **处理过程**：建立原料-投料-成品谱系，设置追溯完整性阻断规则，保留称重、质检和发运凭证。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目把影响范围查询从跨表格人工比对变成批次谱系查询，并补齐关键节点字段。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“农业行业全景解析”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

这个案例最关键的动作不是“跑一条 SQL”，而是把“农业行业全景解析”对应的业务对象和上下游系统放在同一张链路图上。链路图至少要标出源系统、事件时间、关联主键、状态变化、数据负责人和消费方。

## 5. SQL 示例：在统一口径下做分层诊断

下面的查询用于展示分析结构，表名和字段需映射到实际环境。重点是去重、范围筛选、基线比较和贡献率，而不是代码本身。

### 标题专属诊断 SQL

```sql
-- 农业行业全景解析：同期基线诊断（地块 × 批次）
WITH scoped AS (
  SELECT
    plot_id AS entity_key,
    event_id,
    operation_date AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_agriculture_event
  WHERE operation_date >= DATE '2026-02-01'
    AND operation_date <  DATE '2026-05-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '合格率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

执行后要回答四类验证题：

- 结果总量能否与源系统或既有报表在相同口径下解释差异？
- 排名前几位的分组是否由少数超长、重复或补录记录造成？
- 缺失日期表现为“未发生”还是“未采集”，是否改变分母？
- 维度使用的是当时归属还是当前归属，跨期比较是否一致？

## 6. 第二个案例：跨系统、跨部门时怎样不失控

### 案例 2：华北某农业合作社的“农业行业全景解析”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：农资投入持续增加但亩产没有同步提高，需要评估不同服务方案的真实效果。本次讨论的重点是“农业行业全景解析”，所以团队先要求把先证明数据链路可信写进项目目标，而不是直接开始做报表。
- **数据范围**：地块、农户、农资领取、作业服务、天气、采收和成本。同时收集农场管理系统、物联网平台、加工 MES、仓储系统中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：不同地块面积单位不统一，农户自购农资未入系统，方案选择与地块条件相关导致比较偏差。进一步检查后发现，如果不先处理单位换算错误，“农业行业全景解析”很容易被一个表面相关指标替代。
- **处理过程**：统一亩制单位，建立同作物同土壤条件分组，使用种植前基线和服务记录做匹配分析。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目区分了方案效果与地块差异，避免把好地块的高产全部归因于农资。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“农业行业全景解析”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

跨部门项目最容易在三个地方返工：业务术语没有冻结、主数据映射没有版本、验收时才发现权限不足。建议在开发前让业务负责人签字确认指标定义，让数据负责人确认粒度与主键，让安全负责人确认字段范围，让运维负责人确认发布与回滚窗口。

## 7. Python 示例：把数据质量变成发布门禁

### 可执行质量门禁

```python
# 农业行业全景解析：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "农业行业全景解析"
TOPIC_KEY = "subject"
RULE_ID = "rule_agriculture_8m39dl"
GUIDE_CHECKS = [
    "检查地块边界唯一",
    "检查批次关联完整",
    "检查气象日期与农事日期对齐"
]
RULES = {
    "required_columns": ["event_id", "plot_id", "operation_date", "status"],
    "duplicate_key": "event_id",
    "entity_key": "plot_id",
    "time_field": "operation_date",
    "max_duplicate_rate": 0.001,
    "max_null_rate": 0.003,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：检查地块边界唯一；检查批次关联完整；检查气象日期与农事日期对齐
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

这段代码适合放在离线任务完成之后、指标发布之前。真实环境还应从调度平台读取分区参数、把结果写入质量平台，并在关键规则失败时阻断下游。告警不是终点，工单中要记录影响资产、发现时间、临时处理、根因、修复时间和防复发动作。

## 8. 异常排查：从指标异常回到业务事件

| 检查项 | 推荐方法 | 失败动作 | 负责人 |
| --- | --- | --- | --- |
| 地块边界唯一 | 唯一性 SQL + 抽样明细 | 阻断发布 | 农户 |
| 批次关联完整 | 时间区间与状态机校验 | 阻断发布 | 合作社 |
| 气象日期与农事日期对齐 | 主数据有效期关联 | 告警并登记工单 | 农技服务 |
| 投入品单位统一 | 金额或数量平衡校验 | 告警并登记工单 | 种植基地 |
| 采收与销售重量可核对 | 发布前阻断 + 责任人复核 | 告警并登记工单 | 加工企业 |

围绕“农业行业全景解析”排查时，可以按以下顺序进行：

1. **影响面**：哪些指标、报表、接口或业务团队受影响，是否需要暂停对外发布。
2. **时间线**：源系统变更、任务发布、数据回刷、组织调整和业务活动分别发生在什么时候。
3. **数据链路**：上游是否延迟，分区是否缺失，主键是否重复，状态是否映射错误。
4. **业务证据**：抽取异常记录，与原始单据、操作日志、客服记录或现场系统核对。
5. **修复与复核**：明确补数范围、重跑粒度、回滚版本和验收样例。
6. **防复发**：把一次性排查升级为规则、监控、责任人和变更评审。

特别要注意：批次追溯断链；单位换算错误；气象数据时空错位；重复上报农事任务。这些问题如果不被单独标记，很容易被误写成业务趋势。

## 9. 第三个案例与延伸场景

### 案例 3：华东某设施农业基地的“农业行业全景解析”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：番茄产量波动明显，基地希望判断是品种、温湿度、灌溉还是施肥方案导致。本次讨论的重点是“农业行业全景解析”，所以团队先要求把把数据和业务动作一起复盘写进项目目标，而不是直接开始做报表。
- **数据范围**：温室传感器、灌溉记录、施肥任务、批次、采收和质检。同时收集农场管理系统、物联网平台、加工 MES、仓储系统中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：传感器分钟级数据与农事按天记录粒度不同，设备离线未标记，多个温室的品种记录缺失。进一步检查后发现，如果不先处理气象数据时空错位，“农业行业全景解析”很容易被一个表面相关指标替代。
- **处理过程**：建立地块-温室-批次-农事模型，按作物阶段聚合环境指标，区分设备缺失和真实极端天气。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目识别出夜间湿度和灌溉间隔组合的风险窗口，并形成批次级种植复盘。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。

- **失败路径：** 为了压缩账单关闭质量检查，或为了刷新频率重复计算无人消费的全量结果。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“农业行业全景解析”时，先验证采收与销售重量可核对，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由农技服务在明确时限内，根据批次追溯完整率、投入成本和采收与销售重量可核对决定继续、回退、补查还是转人工。 若采收损耗与销售退货混用或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从农业行业全景解析回到可核对明细

```sql
-- 农业行业全景解析：行动前后与分组增量
WITH scoped AS (
  SELECT
    plot_id AS entity_key,
    地块 AS decision_group,
    operation_date AS event_date,
    metric_value,
    CASE
      WHEN operation_date <  :action_date THEN 'before'
      ELSE 'after'
    END AS period_label
  FROM fact_agriculture_event
  WHERE operation_date >= :analysis_start
    AND operation_date <  :analysis_end
    AND subject_key = 'subject'
),
grouped AS (
  SELECT
    decision_group,
    period_label,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    AVG(metric_value) AS metric_avg,
    SUM(metric_value) AS metric_sum
  FROM scoped
  GROUP BY decision_group, period_label
),
compared AS (
  SELECT
    decision_group,
    MAX(CASE WHEN period_label = 'before' THEN metric_avg END) AS before_avg,
    MAX(CASE WHEN period_label = 'after' THEN metric_avg END) AS after_avg,
    MAX(CASE WHEN period_label = 'before' THEN entity_cnt END) AS before_cnt,
    MAX(CASE WHEN period_label = 'after' THEN entity_cnt END) AS after_cnt
  FROM grouped
  GROUP BY decision_group
)
SELECT
  decision_group,
  before_avg,
  after_avg,
  after_avg - before_avg AS naive_delta,
  '损耗率' AS metric_name,
  '地块边界唯一' AS required_evidence
FROM compared
WHERE before_cnt >= 30 AND after_cnt >= 30
ORDER BY ABS(after_avg - before_avg) DESC;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把农业行业全景解析的验收证据写成门禁

```python
import pandas as pd

KEY = ["entity_key", "event_id"]
AMOUNT_COLUMNS = ["metric_value", "adjustment_value"]


def reconcile(source: pd.DataFrame, result: pd.DataFrame) -> pd.DataFrame:
    def aggregate(frame: pd.DataFrame, side: str) -> pd.DataFrame:
        grouped = (
            frame.groupby("entity_key", dropna=False)
            .agg(
                event_cnt=("event_id", "nunique"),
                metric_sum=("metric_value", "sum"),
                adjustment_sum=("adjustment_value", "sum"),
            )
            .reset_index()
        )
        return grouped.rename(columns={
            "event_cnt": f"{side}_event_cnt",
            "metric_sum": f"{side}_metric_sum",
            "adjustment_sum": f"{side}_adjustment_sum",
        })

    compared = aggregate(source, "source").merge(
        aggregate(result, "result"),
        on="entity_key",
        how="outer",
    )
    compared["metric_diff"] = (
        compared["result_metric_sum"].fillna(0)
        - compared["source_metric_sum"].fillna(0)
    )
    compared["event_diff"] = (
        compared["result_event_cnt"].fillna(0)
        - compared["source_event_cnt"].fillna(0)
    )
    compared["exception"] = compared.apply(
        lambda row: "missing_result" if pd.isna(row["result_metric_sum"])
        else "unexpected_result" if pd.isna(row["source_metric_sum"])
        else "count_diff" if row["event_diff"] != 0
        else "amount_diff",
        axis=1,
    )
    return compared.loc[
        (compared["metric_diff"].abs() > 0) | (compared["event_diff"] != 0)
    ].sort_values("metric_diff", key=lambda values: values.abs(), ascending=False)
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
