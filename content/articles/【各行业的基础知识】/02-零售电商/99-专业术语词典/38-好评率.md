# 好评率

> [!abstract] 评价与口碑质量实战手册
> 好评率是评价结果分布中的一个派生指标，必须同时固定评价对象、有效评价分母、评分映射、撤销与追评规则。它适合描述已购用户的满意分布，但不能单独证明商品质量、服务能力或营销效果。

## 1. 好评率：定义、适用边界与决策出口

好评率是评价结果分布中的一个派生指标，必须同时固定评价对象、有效评价分母、评分映射、撤销与追评规则。它适合描述已购用户的满意分布，但不能单独证明商品质量、服务能力或营销效果。

**本篇的适用边界。** 本篇讨论电商或服务平台的商品/订单评价好评率；不把内容点赞、客服满意度、NPS 或广告评分混成同一指标。

**最常见的错误替代。** 不能用总评价数当分母却只统计五星，不能把未验证购买评价与已购评价直接合并，也不能删除低分来提升结果。

**最终决策。** 运营和商家要判断：差评是否集中在特定批次、物流、客服或描述不符，是否需要下架、补发、改版或发起专项改善。 因此，这篇内容不从“应该建哪张表”开始，而从业务动作、责任人和失败后果开始。只有先确定谁在什么时点做出什么决定，字段、SQL、看板和模型才有明确用途。

围绕“好评率”，工作中至少要区分四类问题：

1. **身份问题**：对象是谁，主键能否跨系统稳定关联，合并、拆分、撤销后历史是否还看得见。
2. **时间问题**：业务发生、状态生效、数据入仓、计算完成和人员行动分别发生在哪一刻。
3. **状态问题**：当前状态是一段事件、一张快照还是最终结果，空值代表未发生、未采集还是已删除。
4. **责任问题**：谁确认口径，谁处理异常，谁有权放行或停止，谁在观察期后复盘。

## 2. 好评率的完整业务流程

| 环节 | 要做的事 | 最小证据 | 失败后先查什么 |
| --- | --- | --- | --- |
| 评价产生与资格校验 | 确认订单完成、购买验证、评价入口和身份 | 订单、评价、用户与商品版本 | 页面显示全部评价，指标只算已购评价 |
| 评分与文本提交 | 记录星级、维度、标签和文本 | 原始评分、提交时间、设备风控结果 | 可疑低分无证据批量清理 |
| 追评、修改与撤销 | 保留每次版本，不覆盖历史 | 评价版本号、原因和时间 | 不同 SKU 问题被合并 |
| 反作弊与有效性判定 | 识别刷评、诱导、重复和异常账号 | 风控标签、证据与人工复核 | 模板回复计入完成 |
| 聚合与展示 | 按商品和窗口计算评分分布、好评率与样本量 | 分子分母、置信区间和展示规则 | 页面显示全部评价，指标只算已购评价 |
| 差评运营与复盘 | 分类原因、响应、补偿和改善 | 工单、责任团队、解决证据和复发监控 | 可疑低分无证据批量清理 |

把 评价产生与资格校验、评分与文本提交、追评、修改与撤销、反作弊与有效性判定、聚合与展示、差评运营与复盘 串起来后可以看出，好评率不是一个孤立字段，而是一条会跨系统、跨岗位、跨时间的证据链。流程图上每一段都应标出输入、输出、状态、时间戳、责任人和异常出口。只要其中一段只能靠口头解释，后续的统计、追责和自动化就会失去基础。

一个合格的需求说明应该写成：

> 在【授权数据范围】和【观察窗口】内，围绕“好评率”的【评价】，按【subject_id、sku_id、channel_id、rating_bucket】比较【有效好评率】及其【低分集中度】，定位一个可干预节点；行动后同时观察主指标、样本量和护栏，任何高风险异常先阻断再调查。

## 3. 好评率的数据对象与系统契约

| 数据对象 | 建议主键 | 一行代表什么 | 不允许混淆 |
| --- | --- | --- | --- |
| 评价 | `review_id` | 一条评价的稳定身份 | 对象身份与业务事件 |
| 评价版本 | `review_version_id` | 修改、追评和状态变化的具体版本 | 事件、状态快照和结果粒度 |
| 评价对象 | `review_subject_id` | 商品、规格、订单行或服务单 | 事件、状态快照和结果粒度 |
| 有效购买 | `verified_purchase_id` | 评价资格对应的订单行 | 事件、状态快照和结果粒度 |
| 风控判定 | `review_risk_id` | 异常判定、证据和复核结论 | 事件、状态快照和结果粒度 |

对象表不是把所有字段塞进一张宽表。事件、状态快照和结果表应该分别保留粒度，再通过稳定主键与版本建立关联。尤其要避免三个常见混算：把一次业务事件算成多个对象、把每日快照相加当事件总量、把最新状态覆盖历史状态。

本主题的数据契约至少应包含：

- `review_version_id` 的唯一性规则、生成方式和跨系统映射。
- `submitted_at` 的业务含义、时区、迟到和补录规则。
- `validity_status` 的完整状态集合，以及删除、撤销、冻结和失效的表示方法。
- 控制对象 `review_purchase_link.verified_purchase_id` 与主对象的关系。
- 每次口径、规则、模型或源版本变化的影响范围和下游通知对象。
- 敏感字段、允许用途、访问角色、导出限制和审计保留时间。

## 4. 好评率的指标、样本与验收口径

| 指标 | 公式或定义 | 口径提醒 |
| --- | --- | --- |
| 有效好评率 | 有效评分大于等于好评阈值的评价数 / 有效评价数 | 固定阈值、时间窗、购买验证和风控规则 |
| 低分集中度 | 单一商品或批次中 1-2 星评价数 / 该对象有效评价数 | 要同时展示样本量和评价量变化 |
| 评价修改率 | 发生至少一次修改或追评的评价 / 已提交评价 | 修改不等于作弊，需区分原因 |
| 差评响应时长 | 首次有效响应时间 - 差评提交时间 | 自动回复不计为有效响应 |
| 评价异常拦截率 | 被判定无效的评价 / 触发风控评价 | 需要漏放和误杀复核 |

指标字典至少写到“任何人都能按同一份数据复跑”的程度：中文名、业务定义、公式、分子、分母、事实粒度、时间字段、对象范围、排除项、版本、负责人和验收样例，一个都不能少。比例指标必须同时展示分子、分母和样本量；金额或数量必须做守恒；状态指标必须能回到事件时间线。

对于“好评率”，建议把观察分成三层：

| 层次 | 看什么 | 不能替代什么 |
| --- | --- | --- |
| 业务结果 | 有效好评率、低分集中度 | 不能替代过程证据和个案回查 |
| 过程护栏 | 评价修改率、差评响应时长、评价异常拦截率 | 不能因为护栏暂时正常就跳过异常调查 |
| 数据证据 | 主键、时间、状态、版本、来源目标对账 | 不能只看任务成功或报表能打开 |

## 5. 好评率：七个真实工作场景

以下七组场景均为公开方法结合常见工作流程构造的“脱敏复合示例”，不对应任何单一企业、患者、客户或雇员事实。场景的目的，是展示如何从现象走到证据、行动和验收，而不是虚构经营成果。

### 1. 店铺评分上升但差评集中

**现场。** 店铺整体好评率上升，某爆款低分评价却持续增加。

**怎么查。** 按商品、规格、供应商批次、订单时段和差评标签拆分，发现新增流量带来大量未验证购买评价，稀释了已购用户差评。

**怎么处理。** 整体与已购评价分开展示；商品页增加近期有效差评率和低分原因分布。

**验收结论。** 整体平均会掩盖局部风险。评价指标必须能下钻到商品和具体问题。

### 2. 促销期出现大量五星短评

**现场。** 某活动后五星评价激增，文本高度相似且购买间隔异常。

**怎么查。** 关联账号注册时间、设备、订单、评价模板、物流和售后行为，进行规则识别与人工抽样。

**怎么处理。** 先隔离可疑评价再复核，保留原评价和判定证据；不能为了指标直接批量删除。

**验收结论。** 反作弊要保留证据链和申诉通道。异常不等于作弊，需区分误杀。

### 3. 同一商品不同规格评价混算

**现场。** 服装商品 A 规格好评率高，B 规格尺码偏差严重，但页面只展示父商品总分。

**怎么查。** 检查评价对象绑定的是父商品、SKU 还是订单行，确认规格、颜色和尺码是否可追溯。

**怎么处理。** 按最小可购买规格聚合，父商品只展示加总并允许查看子规格分布。

**验收结论。** 评价对象越粗，运营动作越难落地。规格差异不应被父商品平均掉。

### 4. 退款用户评价是否应计入

**现场。** 部分用户退款后仍给出低分，商家认为应全部剔除。

**怎么查。** 区分未发货取消、质量问题退款、仅退款、退货退款和无理由退款，并核对评价是否基于真实体验。

**怎么处理。** 按业务规则分别展示，不默认排除所有退款评价；退款原因进入问题分类。

**验收结论。** 分母规则要服务问题判断。不能只要低分就修改资格。

### 5. 差评响应率高但复购未改善

**现场。** 客服对差评几乎全部回复，但同类问题继续出现。

**怎么查。** 抽样文本和工单，发现大量模板回复，未关联根因、责任团队和修复进度。

**怎么处理。** 把“回复率”改为“有效解决率”，要求问题分类、方案、完成时间和用户确认。

**验收结论。** 响应是过程指标，解决和复发才是结果指标。

### 6. 历史评价版本被覆盖

**现场。** 用户追评后，系统只保留最新星级，导致早期物流差评消失。

**怎么查。** 检查评价版本表和展示逻辑，确认是否用最新版本覆盖了全部历史。

**怎么处理。** 保留版本链；聚合使用当前有效评分，问题分析可使用首评和追评变化。

**验收结论。** 当前结论和历史证据是两件事，不能用一个覆盖规则同时满足。

### 7. 小样本好评率的置信问题

**现场。** 新品只有 8 条评价且全部五星，被展示为 100% 好评并用于首页推荐。

**怎么查。** 评估样本量、评价来源、展示窗口和业务风险，确认 100% 对用户的误导程度。

**怎么处理。** 展示评价数并在低样本时使用置信下限或明确提示，推荐模型降低小样本权重。

**验收结论。** 比例必须带样本量。小样本的完美结果不应获得过度确定性。

七个场景可以归成一条共同判断顺序：先确认对象和时间，再确认状态和版本；然后做总量、结构和明细三层对账；最后才讨论策略、模型或工具。若一条结论不能指出对应的原始记录、责任人和行动出口，就只能算观察，不能作为生产结论。

## 6. 好评率的第一段 SQL：重建业务链路

下面的 SQL 用于说明对象、时间、状态、版本和分层口径如何进入同一条可复查路径。表名和部分字段是通用示例，落地时应映射到企业数据字典；SQL 方言也需按实际引擎调整。

```sql
-- 好评率：按业务对象重建链路，避免事件、快照和结果混算
WITH ranked_review_version_id AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY review_version_id
      ORDER BY updated_at DESC
    ) AS version_no
  FROM commerce_review_version
  WHERE submitted_at >= TIMESTAMP '{start_time}'
    AND submitted_at <  TIMESTAMP '{end_time}'
    AND validity_status NOT IN ('deleted', 'test')
),
valid_rows AS (
  SELECT
    review_version_id,
    subject_id,
    sku_id,
    channel_id,
    rating_bucket,
    submitted_at,
    validity_status,
    ingested_at
  FROM ranked_review_version_id
  WHERE version_no = 1
)
SELECT
  subject_id, sku_id, channel_id, rating_bucket,
  COUNT(DISTINCT review_version_id) AS object_cnt,
  COUNT(DISTINCT CASE WHEN rating >= 4 THEN review_id END) AS numerator_value,
  COUNT(DISTINCT CASE WHEN validity_status = 'valid' THEN review_id END) AS denominator_value,
  CAST(COUNT(DISTINCT CASE WHEN rating >= 4 THEN review_id END) AS DOUBLE PRECISION)
    / NULLIF(COUNT(DISTINCT CASE WHEN validity_status = 'valid' THEN review_id END), 0) AS metric_value,
  MIN(submitted_at) AS first_event_at,
  MAX(submitted_at) AS last_event_at
FROM valid_rows
GROUP BY subject_id, sku_id, channel_id, rating_bucket
ORDER BY metric_value DESC, object_cnt DESC;
```

执行后至少回答六个问题：

- 同一对象是否因为多源回传产生多版本，版本保留是否符合业务要求？
- 业务时间与入仓时间是否分开，补录和迟到数据是否进入正确分区？
- 分子分母是否来自同一对象范围和同一统计窗口？
- 维度使用的是事件当时值还是当前值，跨期比较是否一致？
- 删除、撤销、冻结和测试数据是否按规则处理？
- 分组结果能否在明细中抽样复现？

## 7. 好评率的第二段 SQL：源、控制和结果三方对账

```sql
-- 好评率：源对象、控制对象和结果对象三方对账
WITH population AS (
  SELECT
    review_version_id,
    submitted_at,
    validity_status
  FROM commerce_review_version
  WHERE submitted_at >= TIMESTAMP '{start_time}'
    AND submitted_at <  TIMESTAMP '{end_time}'
),
control AS (
  SELECT
    review_version_id,
    SUM(order_line_amount) AS control_value,
    COUNT(DISTINCT verified_purchase_id) AS control_cnt,
    MAX(updated_at) AS control_updated_at
  FROM review_purchase_link
  WHERE updated_at >= TIMESTAMP '{start_time}'
  GROUP BY review_version_id
),
result AS (
  SELECT
    review_version_id,
    COUNT(*) AS result_cnt,
    MAX(calculated_at) AS calculated_at
  FROM mart_review_version_id
  WHERE business_date BETWEEN DATE '{start_date}' AND DATE '{end_date}'
  GROUP BY review_version_id
)
SELECT
  COALESCE(p.review_version_id, c.review_version_id, r.review_version_id) AS object_key,
  CASE
    WHEN p.review_version_id IS NULL THEN 'source_missing'
    WHEN c.review_version_id IS NULL THEN 'control_missing'
    WHEN r.review_version_id IS NULL THEN 'result_missing'
    WHEN ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0 THEN 'count_or_value_gap'
    ELSE 'matched'
  END AS reconciliation_status,
  p.validity_status,
  c.control_value,
  c.control_cnt,
  r.result_cnt,
  c.control_updated_at,
  r.calculated_at
FROM population p
FULL OUTER JOIN control c ON p.review_version_id = c.review_version_id
FULL OUTER JOIN result r ON COALESCE(p.review_version_id, c.review_version_id) = r.review_version_id
WHERE p.review_version_id IS NULL
   OR c.review_version_id IS NULL
   OR r.review_version_id IS NULL
   OR ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0;
```

这段查询故意不使用“总数相差小于某个随意百分比就算通过”。它先找出缺失对象和状态差异，再检查控制值与结果值。对于好评率，数量、金额、时长或状态任意一项无法解释，都不能用“业务波动”代替排查。

对账结果建议分成四类处理：

1. **阻断**：对象缺失、关键时间为空、状态非法、金额或数量不守恒、权限越界。
2. **严重**：比例或总量显著偏离基线，且无法由已确认的对象结构变化解释。
3. **观察**：小范围波动但来源、样本和趋势可控，进入责任人和观察窗口。
4. **探索**：只有弱信号或假设，不进入正式结论，更不直接触发业务处罚。

## 8. 好评率的 Python 发布门禁与指标护栏

第一段代码把发布条件写成可执行对象，避免“检查过了”只存在聊天记录里：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class ReviewVersionIdBatch:
    batch_id: str
    source_rows: int
    valid_rows: int
    duplicate_keys: int
    missing_required_fields: int
    reconciliation_gap: float

def release_review_version_id(batch: ReviewVersionIdBatch) -> dict:
    checks = {
        "source_not_empty": batch.source_rows > 0,
        "valid_rows_in_range": 0 <= batch.valid_rows <= batch.source_rows,
        "duplicate_rate_ok": batch.duplicate_keys / max(batch.source_rows, 1) <= 0.001,
        "required_fields_ok": batch.missing_required_fields == 0,
        "reconciliation_ok": abs(batch.reconciliation_gap) <= 0.01,
    }
    return {
        "topic": "好评率",
        "batch_id": batch.batch_id,
        "checks": checks,
        "release_allowed": all(checks.values()),
        "blocking_checks": [name for name, passed in checks.items() if not passed],
    }
```

第二段代码演示如何为比例类结果附带样本证据和小样本下界。它不是替代统计学家的模型，而是防止把少量偶然样本直接包装成稳定结论：

```python
from dataclasses import dataclass
from math import sqrt

@dataclass(frozen=True)
class ReviewVersionIdObservation:
    object_id: str
    numerator: float
    denominator: float
    sample_size: int
    scope_version: str

def calculate_review_version_id(rows: list[ReviewVersionIdObservation]) -> list[dict]:
    output = []
    for row in rows:
        value = row.numerator / row.denominator if row.denominator > 0 else None
        # 小样本用 Wilson 下界做护栏，不把偶然的高比例直接当稳定结果。
        z = 1.96
        p = value or 0
        n = max(row.sample_size, 1)
        center = p + z * z / (2 * n)
        margin = z * sqrt((p * (1 - p) + z * z / (4 * n)) / n)
        lower = max(0, (center - margin) / (1 + z * z / n))
        output.append({
            "object_id": row.object_id,
            "metric": "有效好评率",
            "value": value,
            "lower_bound": lower if value is not None else None,
            "sample_size": row.sample_size,
            "scope_version": row.scope_version,
            "caution": "固定阈值、时间窗、购买验证和风控规则",
        })
    return output
```

真正上线时还要补充参数配置、日志、血缘、告警级别、重跑幂等、异常样本保存和审批记录。代码通过不代表业务通过；自动检查只能证明已经定义的规则没有被违反，无法证明规则本身一定正确。

## 9. 好评率的失败反例与上线验收

| 风险信号 | 错误做法 | 必须补齐的证据 | 发布或行动规则 |
| --- | --- | --- | --- |
| 分母偷换 | 页面显示全部评价，指标只算已购评价 | 分子、分母、购买验证和时间窗 | 任何展示都带同口径样本量 |
| 异常直接删除 | 可疑低分无证据批量清理 | 规则、人工复核、原值和申诉记录 | 先隔离再判定，保留证据 |
| 父商品平均掩盖规格 | 不同 SKU 问题被合并 | 评价对象到级和规格维度 | 关键质量指标至少下钻到 SKU |
| 回复率冒充解决率 | 模板回复计入完成 | 根因、行动、用户确认和复发 | 有效解决与响应分开展示 |

上线验收不应只有一句“报表正常”。建议按下面四层验收：

| 验收对象 | 结构要求 | 测试样本 | 结果证据 |
| --- | --- | --- | --- |
| 评价 | `review_id` 能唯一定位一条评价的稳定身份 | 正常、重复、缺失、撤销与跨期样本 | 有效好评率可回到原始对象 |
| 评价版本 | `review_version_id` 能唯一定位修改、追评和状态变化的具体版本 | 正常、重复、缺失、撤销与跨期样本 | 低分集中度可回到原始对象 |
| 评价对象 | `review_subject_id` 能唯一定位商品、规格、订单行或服务单 | 正常、重复、缺失、撤销与跨期样本 | 评价修改率可回到原始对象 |
| 有效购买 | `verified_purchase_id` 能唯一定位评价资格对应的订单行 | 正常、重复、缺失、撤销与跨期样本 | 差评响应时长可回到原始对象 |
| 风控判定 | `review_risk_id` 能唯一定位异常判定、证据和复核结论 | 正常、重复、缺失、撤销与跨期样本 | 评价异常拦截率可回到原始对象 |

还应为每一次发布保留一组固定回归样本：正常对象、边界状态、重复记录、缺失字段、撤销或退款、跨期、权限拒绝和失败恢复。回归样本不是演示数据，而是以后每次改规则都能重复执行的质量资产。

## 10. 好评率的 30 天落地与复盘

| 阶段 | 主要交付 | 通过条件 |
| --- | --- | --- |
| 第 1 周：定义 | 对象、流程、状态、指标、排除项和责任矩阵 | 业务、数据、安全或质量负责人对同一口径签字 |
| 第 2 周：打通 | 源字段、主键、时间、版本、控制对象和失败样本 | 正常与异常样本都能回到原始记录 |
| 第 3 周：验证 | 总量对账、分层对账、抽样回查、权限测试、回滚演练 | 阻断问题清零，严重问题有责任人与期限 |
| 第 4 周：发布 | 灰度、SLO、监控、行动清单、停止条件和复盘模板 | 使用者在真实场景中完成一次闭环行动 |

如果必须用 90 秒说明“好评率”是否做对，可以按这个顺序自测：

1. 一行数据代表什么，主键是什么，哪些对象绝不能混在同一粒度？
2. 业务发生、数据可见、计算完成和行动确认分别在哪个时间点？
3. 本主题最重要的两个主指标、三个护栏和最小样本量是什么？
4. 一个异常出现时，先从原始记录、链路版本还是业务动作开始查？
5. 哪类错误必须阻断发布或停止使用，谁有权批准例外？
6. 上线后由谁在多长时间内观察，什么条件下回滚或结束？

> [!check] 完成标准
> 当另一位数据同事不看聊天记录，只根据口径卡、回归样本和代码就能复跑同一结果；当业务负责人能指出一个异常对应的原始对象、处置动作和复核证据；当系统能够阻止未授权或状态非法的数据进入下游，这篇“好评率”才算真正落到工作里。
