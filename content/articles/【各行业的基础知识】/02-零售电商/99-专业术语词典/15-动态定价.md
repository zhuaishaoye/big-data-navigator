# 动态定价

> [!abstract] 场景速览
> “动态定价”在会议里常常只有一句话，落到数据团队却会展开成口径、主键、时间、状态、权限和交付责任。下面用一个从问题到上线的顺序展开，并穿插三个脱敏的复合案例，帮助你把标题里的知识迁移到真实项目。

## 1. “动态定价”在零售电商业务链中的位置

零售电商的核心流程可以概括为：曝光 → 点击 → 详情浏览 → 加购 → 下单 → 支付 → 履约 → 复购或流失。参与角色包括用户、商品运营、店铺运营、投放团队、供应链、客服、风控与财务。“动态定价”通常不是一个孤立字段，而是连接业务动作、数据记录和管理决策的一层能力。

从数据团队视角，至少要回答四个问题：

1. **谁使用**：用户、商品运营、店铺运营、投放团队分别要用它做判断、执行还是审计。
2. **对象是什么**：一行数据代表用户、一次事件、一个批次还是一天快照。
3. **流程在哪里变化**：通过点击、详情浏览、加购、下单之间的状态和时间差定位问题。
4. **结果如何被采用**：谁在什么时间前采取行动，使用哪个指标观察改善或副作用。

一个合格的专题目标可以写成：

> 在【时间窗】和【授权数据范围】内，围绕“动态定价”，按【渠道、品类、地区】比较【退款率】与【毛利额】，定位一个可干预流程节点，并记录行动后的变化与边界。

## 2. 一张图看清角色、流程和数据

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 用户 | `user_id` | 曝光 |
| 过程对象 | 商品 | `sku_id` | 点击 |
| 过程对象 | 会话 | `session_id` | 详情浏览 |
| 结果对象 | 订单 | `order_id` | 加购 |
| 结果对象 | 退款 | `refund_id` | 下单 |
| 专题分析 | 动态定价 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

建模时不要先把所有系统字段堆进一张大表。更稳妥的做法是分别保留三类事实：

- **事件事实**：谁在什么时间做了动作，例如挂号、下单、开工、报警或学习。
- **状态快照**：对象在某一天的状态，例如会员等级、租约、账户余额或设备资产关系。
- **结果事实**：流程完成后的产出，例如结算金额、良品数量、签收结果或考试分数。

三者的粒度不同。把事件、快照和结果强行放在同一行，会让金额、数量和转化率在汇总时重复。若“动态定价”涉及状态变化，优先建立状态机；若涉及金额，先做借贷或收付平衡；若涉及对象归属，保留维度有效期。

## 3. 指标与口径：不要把相关数字直接当答案

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 支付转化率 | `COUNT(DISTINCT paid_order_id) / COUNT(DISTINCT visit_session_id)`（视图字段 `pay_cvr`） | 渠道、品类、地区 | 不混用测试、撤销和跨期状态；与“动态定价”相关时还要补充主题筛选 |
| 客单价 | `SUM(paid_amount) / COUNT(DISTINCT paid_order_id)`（视图字段 `avg_order_value`） | 品类、地区、用户层级 | 不混用测试、撤销和跨期状态；与“动态定价”相关时还要补充主题筛选 |
| 复购率 | `COUNT(DISTINCT repeat_buyer_id) / COUNT(DISTINCT buyer_id)`（视图字段 `repurchase_rate`） | 地区、用户层级、活动 | 不混用测试、撤销和跨期状态；与“动态定价”相关时还要补充主题筛选 |
| 退款率 | `SUM(refund_amount) / SUM(paid_amount)`（视图字段 `refund_rate`） | 用户层级、活动 | 不混用测试、撤销和跨期状态；与“动态定价”相关时还要补充主题筛选 |

指标字典至少应包含：中文名、英文编码、业务定义、计算公式、事实粒度、时间字段、对象范围、排除条件、负责人和验收样例。对于“动态定价”，还应注明它使用的是业务发生时间还是入仓时间，是否包含撤销、退费、测试、跨期和补录记录。

一个常见误区是看到退款率变化就立即解释业务原因。更可靠的顺序是：

1. 检查数据覆盖和延迟是否变化。
2. 检查对象范围、状态映射和维度归属是否变化。
3. 按时间、结构和分组拆解贡献。
4. 回到明细寻找能解释变化的事件。
5. 如果已经采取行动，再评估行动带来的增量，而不是事后挑一个相关指标。

## 4. 工作案例：从现象到数据处理

### 案例 1：华南某连锁零售企业的“动态定价”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：线上订单增长，但门店库存可用率与线上显示不一致，缺货取消率持续升高。本次讨论的重点是“动态定价”，所以团队先要求把先冻结对象与时间窗写进项目目标，而不是直接开始做报表。
- **数据范围**：门店 POS、中心仓、前置仓、WMS、OMS 和即时配送订单。同时收集ERP、WMS、OMS、CRM中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：可售库存扣减存在时间差，门店盘点期间库存被错误暴露，拆单后子订单无法回溯父订单。进一步检查后发现，如果不先处理重复订单与重复退款，“动态定价”很容易被一个表面相关指标替代。
- **处理过程**：建立可售库存快照和库存事件双模型，增加安全库存缓冲，按仓店与商品分析取消原因。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目把缺货原因拆成数据延迟、真实缺货和超卖拦截，并形成库存质量日报。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“动态定价”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

这个案例最关键的动作不是“跑一条 SQL”，而是把“动态定价”对应的业务对象和上下游系统放在同一张链路图上。链路图至少要标出源系统、事件时间、关联主键、状态变化、数据负责人和消费方。

## 5. SQL 示例：在统一口径下做分层诊断

下面的查询用于展示分析结构，表名和字段需映射到实际环境。重点是去重、范围筛选、基线比较和贡献率，而不是代码本身。

### 标题专属诊断 SQL

```sql
-- 动态定价：留存同期群诊断（用户层级 × 渠道）
WITH scoped AS (
  SELECT
    user_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_retail_event
  WHERE event_time >= DATE '2026-04-01'
    AND event_time <  DATE '2026-07-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '支付转化率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

执行后要回答四类验证题：

- 结果总量能否与源系统或既有报表在相同口径下解释差异？
- 排名前几位的分组是否由少数超长、重复或补录记录造成？
- 缺失日期表现为“未发生”还是“未采集”，是否改变分母？
- 维度使用的是当时归属还是当前归属，跨期比较是否一致？

## 6. 第二个案例：跨系统、跨部门时怎样不失控

### 案例 2：西南某区域商超的“动态定价”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：会员数量增长但高价值会员贡献下降，促销预算无法判断应投向拉新、唤醒还是深度复购。本次讨论的重点是“动态定价”，所以团队先要求把先证明数据链路可信写进项目目标，而不是直接开始做报表。
- **数据范围**：会员、交易、优惠券、品类偏好、到店频次和线上到家订单。同时收集ERP、WMS、OMS、CRM中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：家庭成员共用账号，手机号变更导致一人多号，历史会员等级与当前等级混用。进一步检查后发现，如果不先处理跨渠道归因重叠，“动态定价”很容易被一个表面相关指标替代。
- **处理过程**：打通会员主数据，构建 RFM 与品类偏好组合分层，使用过去同周期基线评估券包策略。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目把会员分成待唤醒、稳定复购和高潜流失三组，并为每组设置不同触达与停止条件。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“动态定价”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

跨部门项目最容易在三个地方返工：业务术语没有冻结、主数据映射没有版本、验收时才发现权限不足。建议在开发前让业务负责人签字确认指标定义，让数据负责人确认粒度与主键，让安全负责人确认字段范围，让运维负责人确认发布与回滚窗口。

## 7. Python 示例：把数据质量变成发布门禁

### 可执行质量门禁

```python
# 动态定价：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "动态定价"
TOPIC_KEY = "subject"
RULE_ID = "rule_retail_140ne5v"
GUIDE_CHECKS = [
    "检查订单与支付金额平衡",
    "检查退款不重复冲减",
    "检查自然流量与付费流量归因唯一"
]
RULES = {
    "required_columns": ["event_id", "user_id", "event_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "user_id",
    "time_field": "event_time",
    "max_duplicate_rate": 0.0005,
    "max_null_rate": 0.005,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：检查订单与支付金额平衡；检查退款不重复冲减；检查自然流量与付费流量归因唯一
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

这段代码适合放在离线任务完成之后、指标发布之前。真实环境还应从调度平台读取分区参数、把结果写入质量平台，并在关键规则失败时阻断下游。告警不是终点，工单中要记录影响资产、发现时间、临时处理、根因、修复时间和防复发动作。

## 8. 异常排查：从指标异常回到业务事件

| 检查项 | 推荐方法 | 失败动作 | 负责人 |
| --- | --- | --- | --- |
| 订单与支付金额平衡 | 唯一性 SQL + 抽样明细 | 阻断发布 | 用户 |
| 退款不重复冲减 | 时间区间与状态机校验 | 阻断发布 | 商品运营 |
| 自然流量与付费流量归因唯一 | 主数据有效期关联 | 告警并登记工单 | 店铺运营 |
| 商品上下架时间可追溯 | 金额或数量平衡校验 | 告警并登记工单 | 投放团队 |
| 渠道和活动维度使用当时快照 | 发布前阻断 + 责任人复核 | 告警并登记工单 | 供应链 |

围绕“动态定价”排查时，可以按以下顺序进行：

1. **影响面**：哪些指标、报表、接口或业务团队受影响，是否需要暂停对外发布。
2. **时间线**：源系统变更、任务发布、数据回刷、组织调整和业务活动分别发生在什么时候。
3. **数据链路**：上游是否延迟，分区是否缺失，主键是否重复，状态是否映射错误。
4. **业务证据**：抽取异常记录，与原始单据、操作日志、客服记录或现场系统核对。
5. **修复与复核**：明确补数范围、重跑粒度、回滚版本和验收样例。
6. **防复发**：把一次性排查升级为规则、监控、责任人和变更评审。

特别要注意：重复订单与重复退款；跨渠道归因重叠；会员与匿名身份合并错误；活动价与成交价混用。这些问题如果不被单独标记，很容易被误写成业务趋势。

## 9. 第三个案例与延伸场景

### 案例 3：华东某服饰电商的“动态定价”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：大促销售额增长但毛利下降，业务方希望拆清折扣、退货、履约成本和渠道结构的影响。本次讨论的重点是“动态定价”，所以团队先要求把把数据和业务动作一起复盘写进项目目标，而不是直接开始做报表。
- **数据范围**：商品、活动、订单、支付、退款、仓储出库和优惠券核销数据。同时收集ERP、WMS、OMS、CRM中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：订单表和支付表退款状态不一致，优惠金额分摊到 SKU 时存在四舍五入差异。进一步检查后发现，如果不先处理会员与匿名身份合并错误，“动态定价”很容易被一个表面相关指标替代。
- **处理过程**：以订单行作为金额分析粒度，建立支付、退款和成本桥接表，按渠道与品类做贡献度拆解。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目发现高退货品类叠加固定履约成本是主要拖累，并推动活动门槛和运费规则调整。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。

> 最终动作不是“把报表做出来”，而是由供应链在明确时限内，根据客单价、退款率和退款不重复冲减决定继续、回退、补查还是转人工。 若跨渠道归因重叠或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从动态定价回到可核对明细

```sql
-- 动态定价：状态链与时间间隔核查
WITH ordered_events AS (
  SELECT
    user_id AS entity_key,
    event_id,
    stage_code,
    event_time AS event_time,
    LAG(stage_code) OVER (
      PARTITION BY user_id
      ORDER BY event_time, event_id
    ) AS previous_stage,
    LAG(event_time) OVER (
      PARTITION BY user_id
      ORDER BY event_time, event_id
    ) AS previous_time
  FROM fact_retail_event
  WHERE event_time >= :start_date
    AND event_time <  :end_date
    AND subject_key = 'subject'
)
SELECT
  entity_key,
  previous_stage,
  stage_code,
  event_time,
  event_time - previous_time AS elapsed,
  CASE
    WHEN event_time < previous_time THEN 'time_reversed'
    WHEN previous_stage = stage_code THEN 'duplicate_stage'
    WHEN previous_stage IS NULL THEN 'missing_prefix'
    ELSE 'candidate_delay'
  END AS exception_type
FROM ordered_events
WHERE event_time < previous_time
   OR previous_stage = stage_code
   OR event_time - previous_time > INTERVAL '1 hour'
ORDER BY exception_type, elapsed DESC;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把动态定价的验收证据写成门禁

```python
import json
from pathlib import Path


def build_evidence_manifest(
    subject: str,
    scope: dict,
    checks: dict,
    samples: list[dict],
    owner: str,
) -> dict:
    failed = [name for name, passed in checks.items() if not passed]
    return {
        "subject": subject,
        "scope": scope,
        "checks": checks,
        "failed_checks": failed,
        "sample_evidence": samples[:5],
        "owner": owner,
        "decision": "block" if failed else "review",
        "manual_questions": [
            "每一项失败是否已回到原始记录",
            "对象、时间和状态是否与指标字典一致",
            "回滚或修复后是否重新完成对账",
        ],
    }


manifest = build_evidence_manifest(
    subject="动态定价",
    scope={"systems": ["ERP","WMS","OMS","CRM"]},
    checks={"definition_frozen": False, "reconciled": False},
    samples=[],
    owner="用户",
)
Path("release-evidence.json").write_text(
    json.dumps(manifest, ensure_ascii=False, indent=2),
    encoding="utf-8",
)
print(manifest["decision"])
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
