# 支付成功率

> [!abstract] 场景速览
> 如果只记住“支付成功率”的定义，遇到真实数据时仍然很难行动。本文把它拆成五个可检查问题：谁在使用、流程在哪里变化、数据一行代表什么、异常如何发现、上线后用哪个指标验收。每个部分都配一个工作案例或代码片段。

## 1. “支付成功率”在金融行业业务链中的位置

金融行业的核心流程可以概括为：获客与准入 → 开户 → 交易或授信 → 风险监测 → 结算 → 服务 → 退出或续约。参与角色包括客户、客户经理、产品团队、风险管理、合规、运营、财务、科技与数据团队。“支付成功率”通常不是一个孤立字段，而是连接业务动作、数据记录和管理决策的一层能力。

从数据团队视角，至少要回答四个问题：

1. **谁使用**：客户、客户经理、产品团队、风险管理分别要用它做判断、执行还是审计。
2. **对象是什么**：一行数据代表客户、一次事件、一个批次还是一天快照。
3. **流程在哪里变化**：通过开户、交易或授信、风险监测、结算之间的状态和时间差定位问题。
4. **结果如何被采用**：谁在什么时间前采取行动，使用哪个指标观察改善或副作用。

一个合格的专题目标可以写成：

> 在【时间窗】和【授权数据范围】内，围绕“支付成功率”，按【机构、产品、渠道】比较【逾期率】与【风险拦截率】，定位一个可干预流程节点，并记录行动后的变化与边界。

## 2. 一张图看清角色、流程和数据

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 客户 | `customer_id` | 获客与准入 |
| 过程对象 | 账户 | `account_id` | 开户 |
| 过程对象 | 交易 | `transaction_id` | 交易或授信 |
| 结果对象 | 申请 | `application_id` | 风险监测 |
| 结果对象 | 风险事件 | `risk_event_id` | 结算 |
| 专题分析 | 支付成功率 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

建模时不要先把所有系统字段堆进一张大表。更稳妥的做法是分别保留三类事实：

- **事件事实**：谁在什么时间做了动作，例如挂号、下单、开工、报警或学习。
- **状态快照**：对象在某一天的状态，例如会员等级、租约、账户余额或设备资产关系。
- **结果事实**：流程完成后的产出，例如结算金额、良品数量、签收结果或考试分数。

三者的粒度不同。把事件、快照和结果强行放在同一行，会让金额、数量和转化率在汇总时重复。若“支付成功率”涉及状态变化，优先建立状态机；若涉及金额，先做借贷或收付平衡；若涉及对象归属，保留维度有效期。

## 3. 指标与口径：不要把相关数字直接当答案

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 活跃客户数 | `COUNT(DISTINCT active_customer_id)`（视图字段 `active_customers`） | 机构、产品、渠道 | 不混用测试、撤销和跨期状态；与“支付成功率”相关时还要补充主题筛选 |
| 资产规模 | `SUM(end_of_day_balance)`（视图字段 `aum`） | 产品、渠道、客户等级 | 不混用测试、撤销和跨期状态；与“支付成功率”相关时还要补充主题筛选 |
| 逾期率 | `SUM(overdue_principal) / SUM(outstanding_principal)`（视图字段 `overdue_rate`） | 渠道、客户等级、风险等级 | 不混用测试、撤销和跨期状态；与“支付成功率”相关时还要补充主题筛选 |
| 风险拦截率 | `COUNT(DISTINCT blocked_event_id) / COUNT(DISTINCT risk_event_id)`（视图字段 `block_rate`） | 客户等级、风险等级 | 不混用测试、撤销和跨期状态；与“支付成功率”相关时还要补充主题筛选 |

指标字典至少应包含：中文名、英文编码、业务定义、计算公式、事实粒度、时间字段、对象范围、排除条件、负责人和验收样例。对于“支付成功率”，还应注明它使用的是业务发生时间还是入仓时间，是否包含撤销、退费、测试、跨期和补录记录。

一个常见误区是看到逾期率变化就立即解释业务原因。更可靠的顺序是：

1. 检查数据覆盖和延迟是否变化。
2. 检查对象范围、状态映射和维度归属是否变化。
3. 按时间、结构和分组拆解贡献。
4. 回到明细寻找能解释变化的事件。
5. 如果已经采取行动，再评估行动带来的增量，而不是事后挑一个相关指标。

## 4. 工作案例：从现象到数据处理

### 案例 1：华北某证券公司的“支付成功率”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：财富管理客户活跃度下降，运营希望知道是行情、产品收益还是服务触达不足。本次讨论的重点是“支付成功率”，所以团队先要求把先冻结对象与时间窗写进项目目标，而不是直接开始做报表。
- **数据范围**：开户、登录、交易、持仓、产品浏览、资讯点击、客服和投顾服务。同时收集核心银行系统、信贷系统、支付清算系统、反洗钱系统中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：同一客户存在多个资金账号，机构客户与个人客户标签混用，登录事件存在机器流量。进一步检查后发现，如果不先处理敏感数据越权访问，“支付成功率”很容易被一个表面相关指标替代。
- **处理过程**：建立客户-账户-产品视图，剔除异常访问，使用同期行情分组和客户风险偏好做对照。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目形成按风险等级和产品类型的活跃诊断，不把市场普跌直接解释为服务失效。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“支付成功率”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

这个案例最关键的动作不是“跑一条 SQL”，而是把“支付成功率”对应的业务对象和上下游系统放在同一张链路图上。链路图至少要标出源系统、事件时间、关联主键、状态变化、数据负责人和消费方。

## 5. SQL 示例：在统一口径下做分层诊断

下面的查询用于展示分析结构，表名和字段需映射到实际环境。重点是去重、范围筛选、基线比较和贡献率，而不是代码本身。

### 标题专属诊断 SQL

```sql
-- 支付成功率：分位对比诊断（渠道 × 风险等级）
WITH scoped AS (
  SELECT
    customer_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_finance_event
  WHERE event_time >= DATE '2026-07-01'
    AND event_time <  DATE '2026-10-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '客户流失率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

执行后要回答四类验证题：

- 结果总量能否与源系统或既有报表在相同口径下解释差异？
- 排名前几位的分组是否由少数超长、重复或补录记录造成？
- 缺失日期表现为“未发生”还是“未采集”，是否改变分母？
- 维度使用的是当时归属还是当前归属，跨期比较是否一致？

## 6. 第二个案例：跨系统、跨部门时怎样不失控

### 案例 2：华南某消费金融公司的“支付成功率”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：逾期率上升，风险团队希望区分客群变化、准入规则和贷后触达的影响。本次讨论的重点是“支付成功率”，所以团队先要求把先证明数据链路可信写进项目目标，而不是直接开始做报表。
- **数据范围**：申请、授信、借款、还款计划、实际还款、催收和风险规则版本。同时收集核心银行系统、信贷系统、支付清算系统、反洗钱系统中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：申请件与借款件一对多，规则版本覆盖时间不完整，展期后账龄计算口径不统一。进一步检查后发现，如果不先处理授信金额与借据余额混用，“支付成功率”很容易被一个表面相关指标替代。
- **处理过程**：建立申请-借据-还款计划三级模型，固定风险规则生效区间，按账龄和放款批次做同口径分析。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目将逾期变化拆成新客结构、额度使用和早期还款行为，并建立规则回滚观察指标。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“支付成功率”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

跨部门项目最容易在三个地方返工：业务术语没有冻结、主数据映射没有版本、验收时才发现权限不足。建议在开发前让业务负责人签字确认指标定义，让数据负责人确认粒度与主键，让安全负责人确认字段范围，让运维负责人确认发布与回滚窗口。

## 7. Python 示例：把数据质量变成发布门禁

### 可执行质量门禁

```python
# 支付成功率：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "支付成功率"
TOPIC_KEY = "subject"
RULE_ID = "rule_finance_14zyv7a"
GUIDE_CHECKS = [
    "检查客户号脱敏且跨系统映射一致",
    "检查借贷与支付金额平衡",
    "检查交易时间与入账时间区分"
]
RULES = {
    "required_columns": ["event_id", "customer_id", "event_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "customer_id",
    "time_field": "event_time",
    "max_duplicate_rate": 0.0007,
    "max_null_rate": 0.004,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：检查客户号脱敏且跨系统映射一致；检查借贷与支付金额平衡；检查交易时间与入账时间区分
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

这段代码适合放在离线任务完成之后、指标发布之前。真实环境还应从调度平台读取分区参数、把结果写入质量平台，并在关键规则失败时阻断下游。告警不是终点，工单中要记录影响资产、发现时间、临时处理、根因、修复时间和防复发动作。

## 8. 异常排查：从指标异常回到业务事件

| 检查项 | 推荐方法 | 失败动作 | 负责人 |
| --- | --- | --- | --- |
| 客户号脱敏且跨系统映射一致 | 唯一性 SQL + 抽样明细 | 阻断发布 | 客户 |
| 借贷与支付金额平衡 | 时间区间与状态机校验 | 阻断发布 | 客户经理 |
| 交易时间与入账时间区分 | 主数据有效期关联 | 告警并登记工单 | 产品团队 |
| 风险标签可追溯到规则版本 | 金额或数量平衡校验 | 告警并登记工单 | 风险管理 |
| 时点快照与流水不混用 | 发布前阻断 + 责任人复核 | 告警并登记工单 | 合规 |

围绕“支付成功率”排查时，可以按以下顺序进行：

1. **影响面**：哪些指标、报表、接口或业务团队受影响，是否需要暂停对外发布。
2. **时间线**：源系统变更、任务发布、数据回刷、组织调整和业务活动分别发生在什么时候。
3. **数据链路**：上游是否延迟，分区是否缺失，主键是否重复，状态是否映射错误。
4. **业务证据**：抽取异常记录，与原始单据、操作日志、客服记录或现场系统核对。
5. **修复与复核**：明确补数范围、重跑粒度、回滚版本和验收样例。
6. **防复发**：把一次性排查升级为规则、监控、责任人和变更评审。

特别要注意：敏感数据越权访问；授信金额与借据余额混用；产品口径随组织调整无法比较；风险规则版本不可追溯。这些问题如果不被单独标记，很容易被误写成业务趋势。

## 9. 第三个案例与延伸场景

### 案例 3：华东某城市商业银行的“支付成功率”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：经营看板同时出现客户增长和资产流失，业务方无法判断是新客质量下降还是高价值客户迁移。本次讨论的重点是“支付成功率”，所以团队先要求把把数据和业务动作一起复盘写进项目目标，而不是直接开始做报表。
- **数据范围**：客户、账户、产品持仓、交易、渠道访问和客户经理服务记录。同时收集核心银行系统、信贷系统、支付清算系统、反洗钱系统中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：客户等级使用当前值回溯历史，理财产品申赎存在非交易日确认，跨行转账冲正未成对。进一步检查后发现，如果不先处理产品口径随组织调整无法比较，“支付成功率”很容易被一个表面相关指标替代。
- **处理过程**：建立客户与账户每日快照，区分交易流水和余额快照，按客户层级与产品分析资产净流入。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。

- **行动与护栏：** 保存现场并停止下游扩散，按影响边界回滚或隔离结果，使用幂等任务从最小必要范围重新计算。专题检查项“客户号脱敏且跨系统映射一致”被写成发布门禁，恢复任务没有对账、没有版本记录或无法重复执行时，不宣布故障结束。
- **失败路径：** 直接覆盖目标表，或者把所有分区全部重跑以求省事。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“支付成功率”时，先验证客户号脱敏且跨系统映射一致，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由客户经理在明确时限内，根据活跃客户数、逾期率和客户号脱敏且跨系统映射一致决定继续、回退、补查还是转人工。 若敏感数据越权访问或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

-- 支付成功率：字段血缘与影响范围
WITH changed_columns AS (
  SELECT column_name
  FROM information_schema.columns
  WHERE table_schema = :source_schema
    AND table_name = :source_table
    AND last_altered_at >= :change_time
),
downstream_assets AS (
  SELECT
    asset_id,
    asset_name,
    asset_type,
    owner_name,
    criticality,
    last_used_at
  FROM metadata_asset_relation
  WHERE upstream_asset_id = :source_asset_id
    AND relation_status = 'active'
)
SELECT
  d.asset_id,
  d.asset_name,
  d.asset_type,
  d.owner_name,
  d.criticality,
  d.last_used_at,
  COUNT(c.column_name) AS changed_column_cnt,
  CASE
    WHEN d.criticality IN ('core', 'regulated') THEN 'block_release'
    WHEN d.last_used_at >= CURRENT_DATE - INTERVAL '7 days' THEN 'notify_owner'
    ELSE 'register_review'
  END AS required_action
FROM downstream_assets d
CROSS JOIN changed_columns c
GROUP BY d.asset_id, d.asset_name, d.asset_type, d.owner_name, d.criticality, d.last_used_at
ORDER BY
  CASE WHEN d.criticality IN ('core', 'regulated') THEN 0 ELSE 1 END,
  d.last_used_at DESC;

import json
from pathlib import Path


def build_evidence_manifest(
    subject: str,
    scope: dict,
    checks: dict,
    samples: list[dict],
    owner: str,
) -> dict:
    failed = [name for name, passed in checks.items() if not passed]
    return {
        "subject": subject,
        "scope": scope,
        "checks": checks,
        "failed_checks": failed,
        "sample_evidence": samples[:5],
        "owner": owner,
        "decision": "block" if failed else "review",
        "manual_questions": [
            "每一项失败是否已回到原始记录",
            "对象、时间和状态是否与指标字典一致",
            "回滚或修复后是否重新完成对账",
        ],
    }


manifest = build_evidence_manifest(
    subject="支付成功率",
    scope={"systems": ["核心银行系统","信贷系统","支付清算系统","反洗钱系统"]},
    checks={"definition_frozen": False, "reconciled": False},
    samples=[],
    owner="客户",
)
Path("release-evidence.json").write_text(
    json.dumps(manifest, ensure_ascii=False, indent=2),
    encoding="utf-8",
)
print(manifest["decision"])
