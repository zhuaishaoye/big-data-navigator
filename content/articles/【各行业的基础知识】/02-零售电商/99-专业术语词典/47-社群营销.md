# 社群营销

> [!abstract] 私域与社群运营实战手册
> 社群营销不是把用户拉进群后反复发广告，而是围绕入群来源、成员身份、内容触达、互动、退群、转化和合规建立可解释的运营闭环。数据必须同时回答社群是否带来了真实价值，以及用户体验和退订风险是否在恶化。

## 1. 社群营销：定义、适用边界与决策出口

社群营销不是把用户拉进群后反复发广告，而是围绕入群来源、成员身份、内容触达、互动、退群、转化和合规建立可解释的运营闭环。数据必须同时回答社群是否带来了真实价值，以及用户体验和退订风险是否在恶化。

**本篇的适用边界。** 本篇讨论企业以微信群、企微群、品牌社区或同类私域社群承载用户关系的过程；不把单次群发、个人好友营销和公域广告投放混为同一对象。

**最常见的错误替代。** 不能把群成员数当作活跃用户数，也不能把群内领券、下单和成交全部归因于社群；沉默成员、重复入群和机器人账号必须单独处理。

**最终决策。** 运营团队要判断：哪些社群值得继续投入，应该发送什么内容和频率，哪些成员需要分层触达，何时停止打扰，以及异常退群是否来自内容、服务或合规问题。 因此，这篇内容不从“应该建哪张表”开始，而从业务动作、责任人和失败后果开始。只有先确定谁在什么时点做出什么决定，字段、SQL、看板和模型才有明确用途。

围绕“社群营销”，工作中至少要区分四类问题：

1. **身份问题**：对象是谁，主键能否跨系统稳定关联，合并、拆分、撤销后历史是否还看得见。
2. **时间问题**：业务发生、状态生效、数据入仓、计算完成和人员行动分别发生在哪一刻。
3. **状态问题**：当前状态是一段事件、一张快照还是最终结果，空值代表未发生、未采集还是已删除。
4. **责任问题**：谁确认口径，谁处理异常，谁有权放行或停止，谁在观察期后复盘。

## 2. 社群营销的完整业务流程

| 环节 | 要做的事 | 最小证据 | 失败后先查什么 |
| --- | --- | --- | --- |
| 来源与入群申请 | 记录渠道、邀请人、兴趣主题、 consent 和入群时间 | 渠道参数、邀请关系、同意记录、入群事件 | 累计入群次数直接作为成员数 |
| 成员身份与标签 | 建立成员、账号、群和有效期关系，区分员工、客户、达人与普通成员 | 成员主键、群主键、角色、来源和标签版本 | 所有消息回执都算活跃 |
| 内容计划与触达 | 按主题、权益、频次和目标人群编排内容 | 素材版本、发送任务、计划与实际触达 | 没有基线或对照就把订单算给群运营 |
| 互动与活跃 | 记录阅读、回复、报名、直播观看和内容领取 | 消息事件、互动事件、活动报名 | 群内可见数据直接用于短信或电话 |
| 转化与归因 | 关联领券、访问、下单、核销和复购 | 优惠凭证、订单、归因窗口和触点路径 | 累计入群次数直接作为成员数 |
| 退群与投诉 | 区分主动退出、被移出、群解散、投诉和静默 | 退群原因、操作人、投诉与处置记录 | 所有消息回执都算活跃 |
| 运营复盘 | 评估增量价值、骚扰风险、服务质量和素材效果 | 对照或基线、频次、退群率、投诉率和成本 | 没有基线或对照就把订单算给群运营 |

把 来源与入群申请、成员身份与标签、内容计划与触达、互动与活跃、转化与归因、退群与投诉、运营复盘 串起来后可以看出，社群营销不是一个孤立字段，而是一条会跨系统、跨岗位、跨时间的证据链。流程图上每一段都应标出输入、输出、状态、时间戳、责任人和异常出口。只要其中一段只能靠口头解释，后续的统计、追责和自动化就会失去基础。

一个合格的需求说明应该写成：

> 在【授权数据范围】和【观察窗口】内，围绕“社群营销”的【社群】，按【community_id、source_channel、member_role、region_code】比较【有效成员率】及其【周活跃率】，定位一个可干预节点；行动后同时观察主指标、样本量和护栏，任何高风险异常先阻断再调查。

## 3. 社群营销的数据对象与系统契约

| 数据对象 | 建议主键 | 一行代表什么 | 不允许混淆 |
| --- | --- | --- | --- |
| 社群 | `community_id` | 一个具有独立主题、规则和生命周期的人群空间 | 对象身份与业务事件 |
| 社群成员关系 | `membership_id` | 一个账号在某个社群内的一段有效关系 | 事件、状态快照和结果粒度 |
| 触达任务 | `delivery_id` | 一次面向明确人群的内容或权益发送 | 事件、状态快照和结果粒度 |
| 互动事件 | `engagement_id` | 成员对内容或活动的一次可验证行为 | 事件、状态快照和结果粒度 |
| 转化凭证 | `conversion_id` | 优惠、订单或核销与触点之间的归因记录 | 事件、状态快照和结果粒度 |
| 退群事件 | `exit_id` | 成员关系结束及对应原因 | 事件、状态快照和结果粒度 |

对象表不是把所有字段塞进一张宽表。事件、状态快照和结果表应该分别保留粒度，再通过稳定主键与版本建立关联。尤其要避免三个常见混算：把一次业务事件算成多个对象、把每日快照相加当事件总量、把最新状态覆盖历史状态。

本主题的数据契约至少应包含：

- `membership_id` 的唯一性规则、生成方式和跨系统映射。
- `occurred_at` 的业务含义、时区、迟到和补录规则。
- `membership_status` 的完整状态集合，以及删除、撤销、冻结和失效的表示方法。
- 控制对象 `crm_delivery_receipt.delivery_receipt_id` 与主对象的关系。
- 每次口径、规则、模型或源版本变化的影响范围和下游通知对象。
- 敏感字段、允许用途、访问角色、导出限制和审计保留时间。

## 4. 社群营销的指标、样本与验收口径

| 指标 | 公式或定义 | 口径提醒 |
| --- | --- | --- |
| 有效成员率 | 有效期内且非重复、非测试的成员数 / 群成员总数 | 退群和失效账号不能继续留在活跃分母 |
| 周活跃率 | 观察周发生有效互动的成员数 / 周初有效成员数 | 阅读、回复、报名要分级，不能把系统推送算互动 |
| 触达退群率 | 触达后 24 小时内退群人数 / 成功触达人数 | 必须按发送批次、频次和成员历史计算 |
| 归因转化率 | 归因窗口内完成目标动作的成员数 / 有效触达成员数 | 不能忽略自然转化和重复触点 |
| 单有效转化成本 | 社群人力、权益和渠道成本 / 有效归因转化数 | 退款、作弊和重复订单需回冲 |

指标字典至少写到“任何人都能按同一份数据复跑”的程度：中文名、业务定义、公式、分子、分母、事实粒度、时间字段、对象范围、排除项、版本、负责人和验收样例，一个都不能少。比例指标必须同时展示分子、分母和样本量；金额或数量必须做守恒；状态指标必须能回到事件时间线。

对于“社群营销”，建议把观察分成三层：

| 层次 | 看什么 | 不能替代什么 |
| --- | --- | --- |
| 业务结果 | 有效成员率、周活跃率 | 不能替代过程证据和个案回查 |
| 过程护栏 | 触达退群率、归因转化率、单有效转化成本 | 不能因为护栏暂时正常就跳过异常调查 |
| 数据证据 | 主键、时间、状态、版本、来源目标对账 | 不能只看任务成功或报表能打开 |

## 5. 社群营销：七个真实工作场景

以下七组场景均为公开方法结合常见工作流程构造的“脱敏复合示例”，不对应任何单一企业、患者、客户或雇员事实。场景的目的，是展示如何从现象走到证据、行动和验收，而不是虚构经营成果。

### 1. 渠道二维码混用导致来源失真

**现场。** 多个门店共用同一入群二维码，月报却按门店比较拉新质量。

**怎么查。** 把邀请事件、群成员、门店账号和渠道参数关联，发现部分门店使用的是总部通用码，还有员工手动拉人。

**怎么处理。** 为每个门店和活动生成独立渠道参数；无来源成员标记为未知，不强行分配；周报同时展示可归因比例。

**验收结论。** 来源缺失是数据质量问题，不能为了排名把它平均分给所有门店。

### 2. 群成员重复入群抬高规模

**现场。** 同一用户退出后再次入群，成员规模连续增长，但去重活跃人数没有变化。

**怎么查。** 按账号、手机号哈希和成员关系有效期识别反复入群，区分换群、重新加入和运营重复导入。

**怎么处理。** 群体规模按当前有效关系统计，拉新按首次有效加入统计，回流单列；重复导入的批次要求回滚并追查模板。

**验收结论。** 成员数、拉新数和回流数是三个指标，不能用一个累计值讲所有故事。

### 3. 高频群发引发集中退群

**现场。** 促销周触达次数增加后成交上升，同时退群和投诉也明显增加。

**怎么查。** 把发送任务、频次、内容类型、成员历史、退群与投诉放到同一时间线，按新客、老客和沉默成员分层。

**怎么处理。** 设置时段频次上限和敏感人群排除；退群率超过护栏时暂停后续任务；用增量成交而不是总成交评估。

**验收结论。** 短期收入不是唯一结果。退群、屏蔽和投诉必须作为同等重要的运营护栏。

### 4. 优惠券被群内重复领取

**现场。** 活动券核销率异常高，但新客订单和复购没有同步增长。

**怎么查。** 检查领券账号、设备、支付账号、收货地址和群成员关系，发现少数账号跨多个身份重复领取。

**怎么处理。** 按活动规则绑定资格和领取上限；把异常领取与正常家庭共用设备区分；建立人工复核而非直接封禁。

**验收结论。** 反作弊要有误伤控制。高风险规则先冻结权益，保留申诉和审计证据。

### 5. 达人社群成交归因过高

**现场。** 达人群内分享商品后，所有后续订单都被算作达人贡献。

**怎么查。** 比较直接点击、优惠凭证、分享关系和自然访问；延长窗口后发现大量订单来自品牌已有复购客户。

**怎么处理。** 使用触点路径、归因窗口和对照组评估增量；同时报告直接归因和增量估计，不用单一数字结算全部佣金。

**验收结论。** 最后点击不等于真实贡献。结算规则必须提前约定并保留调整机制。

### 6. 群内容很好但服务响应断链

**现场。** 阅读和互动稳定，但咨询未回复造成的负面反馈持续增加。

**怎么查。** 关联消息、客服工单、首次响应时间和问题关闭结果，发现晚间咨询无人承接。

**怎么处理。** 按群主题配置服务时段和升级路径；把未响应问题纳入运营看板；机器人回复需标记，不能计入人工解决。

**验收结论。** 内容指标不能代替服务质量。用户关系最终取决于问题是否被解决。

### 7. 跨部门数据使用边界不清

**现场。** 增长团队希望导出全部成员手机号做短信二次触达。

**怎么查。** 核对入群同意文本、用途、渠道和保存期限，发现部分成员只同意在群内接收信息。

**怎么处理。** 按用途和渠道拆分授权；导出接口拒绝无授权的数据；保留审批和访问日志；群运营与短信营销使用不同目标人群。

**验收结论。** 在群里可见不等于可以跨渠道营销。权限和同意范围必须进入数据契约。

七个场景可以归成一条共同判断顺序：先确认对象和时间，再确认状态和版本；然后做总量、结构和明细三层对账；最后才讨论策略、模型或工具。若一条结论不能指出对应的原始记录、责任人和行动出口，就只能算观察，不能作为生产结论。

## 6. 社群营销的第一段 SQL：重建业务链路

下面的 SQL 用于说明对象、时间、状态、版本和分层口径如何进入同一条可复查路径。表名和部分字段是通用示例，落地时应映射到企业数据字典；SQL 方言也需按实际引擎调整。

```sql
-- 社群营销：按业务对象重建链路，避免事件、快照和结果混算
WITH ranked_membership_id AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY membership_id
      ORDER BY updated_at DESC
    ) AS version_no
  FROM crm_community_membership_event
  WHERE occurred_at >= TIMESTAMP '{start_time}'
    AND occurred_at <  TIMESTAMP '{end_time}'
    AND membership_status NOT IN ('deleted', 'test')
),
valid_rows AS (
  SELECT
    membership_id,
    community_id,
    source_channel,
    member_role,
    region_code,
    occurred_at,
    membership_status,
    ingested_at
  FROM ranked_membership_id
  WHERE version_no = 1
)
SELECT
  community_id, source_channel, member_role, region_code,
  COUNT(DISTINCT membership_id) AS object_cnt,
  COUNT(DISTINCT CASE WHEN membership_status = 'active' THEN member_id END) AS numerator_value,
  COUNT(DISTINCT member_id) AS denominator_value,
  CAST(COUNT(DISTINCT CASE WHEN membership_status = 'active' THEN member_id END) AS DOUBLE PRECISION)
    / NULLIF(COUNT(DISTINCT member_id), 0) AS metric_value,
  MIN(occurred_at) AS first_event_at,
  MAX(occurred_at) AS last_event_at
FROM valid_rows
GROUP BY community_id, source_channel, member_role, region_code
ORDER BY metric_value DESC, object_cnt DESC;
```

执行后至少回答六个问题：

- 同一对象是否因为多源回传产生多版本，版本保留是否符合业务要求？
- 业务时间与入仓时间是否分开，补录和迟到数据是否进入正确分区？
- 分子分母是否来自同一对象范围和同一统计窗口？
- 维度使用的是事件当时值还是当前值，跨期比较是否一致？
- 删除、撤销、冻结和测试数据是否按规则处理？
- 分组结果能否在明细中抽样复现？

## 7. 社群营销的第二段 SQL：源、控制和结果三方对账

```sql
-- 社群营销：源对象、控制对象和结果对象三方对账
WITH population AS (
  SELECT
    membership_id,
    occurred_at,
    membership_status
  FROM crm_community_membership_event
  WHERE occurred_at >= TIMESTAMP '{start_time}'
    AND occurred_at <  TIMESTAMP '{end_time}'
),
control AS (
  SELECT
    membership_id,
    SUM(delivered_flag) AS control_value,
    COUNT(DISTINCT delivery_receipt_id) AS control_cnt,
    MAX(updated_at) AS control_updated_at
  FROM crm_delivery_receipt
  WHERE updated_at >= TIMESTAMP '{start_time}'
  GROUP BY membership_id
),
result AS (
  SELECT
    membership_id,
    COUNT(*) AS result_cnt,
    MAX(calculated_at) AS calculated_at
  FROM mart_membership_id
  WHERE business_date BETWEEN DATE '{start_date}' AND DATE '{end_date}'
  GROUP BY membership_id
)
SELECT
  COALESCE(p.membership_id, c.membership_id, r.membership_id) AS object_key,
  CASE
    WHEN p.membership_id IS NULL THEN 'source_missing'
    WHEN c.membership_id IS NULL THEN 'control_missing'
    WHEN r.membership_id IS NULL THEN 'result_missing'
    WHEN ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0 THEN 'count_or_value_gap'
    ELSE 'matched'
  END AS reconciliation_status,
  p.membership_status,
  c.control_value,
  c.control_cnt,
  r.result_cnt,
  c.control_updated_at,
  r.calculated_at
FROM population p
FULL OUTER JOIN control c ON p.membership_id = c.membership_id
FULL OUTER JOIN result r ON COALESCE(p.membership_id, c.membership_id) = r.membership_id
WHERE p.membership_id IS NULL
   OR c.membership_id IS NULL
   OR r.membership_id IS NULL
   OR ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0;
```

这段查询故意不使用“总数相差小于某个随意百分比就算通过”。它先找出缺失对象和状态差异，再检查控制值与结果值。对于社群营销，数量、金额、时长或状态任意一项无法解释，都不能用“业务波动”代替排查。

对账结果建议分成四类处理：

1. **阻断**：对象缺失、关键时间为空、状态非法、金额或数量不守恒、权限越界。
2. **严重**：比例或总量显著偏离基线，且无法由已确认的对象结构变化解释。
3. **观察**：小范围波动但来源、样本和趋势可控，进入责任人和观察窗口。
4. **探索**：只有弱信号或假设，不进入正式结论，更不直接触发业务处罚。

## 8. 社群营销的 Python 发布门禁与指标护栏

第一段代码把发布条件写成可执行对象，避免“检查过了”只存在聊天记录里：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class MembershipIdBatch:
    batch_id: str
    source_rows: int
    valid_rows: int
    duplicate_keys: int
    missing_required_fields: int
    reconciliation_gap: float

def release_membership_id(batch: MembershipIdBatch) -> dict:
    checks = {
        "source_not_empty": batch.source_rows > 0,
        "valid_rows_in_range": 0 <= batch.valid_rows <= batch.source_rows,
        "duplicate_rate_ok": batch.duplicate_keys / max(batch.source_rows, 1) <= 0.001,
        "required_fields_ok": batch.missing_required_fields == 0,
        "reconciliation_ok": abs(batch.reconciliation_gap) <= 0.01,
    }
    return {
        "topic": "社群营销",
        "batch_id": batch.batch_id,
        "checks": checks,
        "release_allowed": all(checks.values()),
        "blocking_checks": [name for name, passed in checks.items() if not passed],
    }
```

第二段代码演示如何为比例类结果附带样本证据和小样本下界。它不是替代统计学家的模型，而是防止把少量偶然样本直接包装成稳定结论：

```python
from dataclasses import dataclass
from math import sqrt

@dataclass(frozen=True)
class MembershipIdObservation:
    object_id: str
    numerator: float
    denominator: float
    sample_size: int
    scope_version: str

def calculate_membership_id(rows: list[MembershipIdObservation]) -> list[dict]:
    output = []
    for row in rows:
        value = row.numerator / row.denominator if row.denominator > 0 else None
        # 小样本用 Wilson 下界做护栏，不把偶然的高比例直接当稳定结果。
        z = 1.96
        p = value or 0
        n = max(row.sample_size, 1)
        center = p + z * z / (2 * n)
        margin = z * sqrt((p * (1 - p) + z * z / (4 * n)) / n)
        lower = max(0, (center - margin) / (1 + z * z / n))
        output.append({
            "object_id": row.object_id,
            "metric": "有效成员率",
            "value": value,
            "lower_bound": lower if value is not None else None,
            "sample_size": row.sample_size,
            "scope_version": row.scope_version,
            "caution": "退群和失效账号不能继续留在活跃分母",
        })
    return output
```

真正上线时还要补充参数配置、日志、血缘、告警级别、重跑幂等、异常样本保存和审批记录。代码通过不代表业务通过；自动检查只能证明已经定义的规则没有被违反，无法证明规则本身一定正确。

## 9. 社群营销的失败反例与上线验收

| 风险信号 | 错误做法 | 必须补齐的证据 | 发布或行动规则 |
| --- | --- | --- | --- |
| 成员规模虚高 | 累计入群次数直接作为成员数 | 有效成员关系、退群和重复账号 | 存量与拉新分开统计 |
| 互动被系统放大 | 所有消息回执都算活跃 | 真实回复、报名、领取和消费行为 | 互动定义分级并登记版本 |
| 成交全部归社群 | 没有基线或对照就把订单算给群运营 | 触点路径、自然转化和实验 | 归因结果与增量结果同时展示 |
| 跨渠道滥用同意 | 群内可见数据直接用于短信或电话 | 用途、渠道、同意和撤回记录 | 无授权触达默认阻断 |

上线验收不应只有一句“报表正常”。建议按下面四层验收：

| 验收对象 | 结构要求 | 测试样本 | 结果证据 |
| --- | --- | --- | --- |
| 社群 | `community_id` 能唯一定位一个具有独立主题、规则和生命周期的人群空间 | 正常、重复、缺失、撤销与跨期样本 | 有效成员率可回到原始对象 |
| 社群成员关系 | `membership_id` 能唯一定位一个账号在某个社群内的一段有效关系 | 正常、重复、缺失、撤销与跨期样本 | 周活跃率可回到原始对象 |
| 触达任务 | `delivery_id` 能唯一定位一次面向明确人群的内容或权益发送 | 正常、重复、缺失、撤销与跨期样本 | 触达退群率可回到原始对象 |
| 互动事件 | `engagement_id` 能唯一定位成员对内容或活动的一次可验证行为 | 正常、重复、缺失、撤销与跨期样本 | 归因转化率可回到原始对象 |
| 转化凭证 | `conversion_id` 能唯一定位优惠、订单或核销与触点之间的归因记录 | 正常、重复、缺失、撤销与跨期样本 | 单有效转化成本可回到原始对象 |
| 退群事件 | `exit_id` 能唯一定位成员关系结束及对应原因 | 正常、重复、缺失、撤销与跨期样本 | 有效成员率可回到原始对象 |

还应为每一次发布保留一组固定回归样本：正常对象、边界状态、重复记录、缺失字段、撤销或退款、跨期、权限拒绝和失败恢复。回归样本不是演示数据，而是以后每次改规则都能重复执行的质量资产。

## 10. 社群营销的 30 天落地与复盘

| 阶段 | 主要交付 | 通过条件 |
| --- | --- | --- |
| 第 1 周：定义 | 对象、流程、状态、指标、排除项和责任矩阵 | 业务、数据、安全或质量负责人对同一口径签字 |
| 第 2 周：打通 | 源字段、主键、时间、版本、控制对象和失败样本 | 正常与异常样本都能回到原始记录 |
| 第 3 周：验证 | 总量对账、分层对账、抽样回查、权限测试、回滚演练 | 阻断问题清零，严重问题有责任人与期限 |
| 第 4 周：发布 | 灰度、SLO、监控、行动清单、停止条件和复盘模板 | 使用者在真实场景中完成一次闭环行动 |

如果必须用 90 秒说明“社群营销”是否做对，可以按这个顺序自测：

1. 一行数据代表什么，主键是什么，哪些对象绝不能混在同一粒度？
2. 业务发生、数据可见、计算完成和行动确认分别在哪个时间点？
3. 本主题最重要的两个主指标、三个护栏和最小样本量是什么？
4. 一个异常出现时，先从原始记录、链路版本还是业务动作开始查？
5. 哪类错误必须阻断发布或停止使用，谁有权批准例外？
6. 上线后由谁在多长时间内观察，什么条件下回滚或结束？

> [!check] 完成标准
> 当另一位数据同事不看聊天记录，只根据口径卡、回归样本和代码就能复跑同一结果；当业务负责人能指出一个异常对应的原始对象、处置动作和复核证据；当系统能够阻止未授权或状态非法的数据进入下游，这篇“社群营销”才算真正落到工作里。
