# 用户获取成本

> [!tip] 分析目标
> 如果只记住“用户获取成本”的定义，遇到真实数据时仍然很难行动。本文把它拆成五个可检查问题：谁在使用、流程在哪里变化、数据一行代表什么、异常如何发现、上线后用哪个指标验收。每个部分都配一个工作案例或代码片段。

## 1. 把主题翻译成可验证的问题

“用户获取成本”不能直接等同于“做一张趋势图”。一个可执行的分析问题至少包含对象、时间、比较基准和行动：

> 在【观察周期】内，对【有效对象】按【渠道、品类、地区】比较【客单价】与【复购率】，判断变化来自结构、行为还是数据口径，并验证【策略动作】是否带来可解释的增量。

在零售电商场景中，用户行为、交易结果和策略曝光经常来自不同系统。先画数据流：

ERP → WMS → OMS → CRM → CDP → 广告投放平台

图中至少要有三个标记：业务事件发生时间、数据可见时间、策略或行动时间。只有三者分开，后续才能判断问题发生在业务、链路还是观察窗口。

## 2. 指标定义与分母检查

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 支付转化率 | `COUNT(DISTINCT paid_order_id) / COUNT(DISTINCT visit_session_id)`（视图字段 `pay_cvr`） | 渠道、品类、地区 | 不混用测试、撤销和跨期状态；与“用户获取成本”相关时还要补充主题筛选 |
| 客单价 | `SUM(paid_amount) / COUNT(DISTINCT paid_order_id)`（视图字段 `avg_order_value`） | 品类、地区、用户层级 | 不混用测试、撤销和跨期状态；与“用户获取成本”相关时还要补充主题筛选 |
| 复购率 | `COUNT(DISTINCT repeat_buyer_id) / COUNT(DISTINCT buyer_id)`（视图字段 `repurchase_rate`） | 地区、用户层级、活动 | 不混用测试、撤销和跨期状态；与“用户获取成本”相关时还要补充主题筛选 |
| 退款率 | `SUM(refund_amount) / SUM(paid_amount)`（视图字段 `refund_rate`） | 用户层级、活动 | 不混用测试、撤销和跨期状态；与“用户获取成本”相关时还要补充主题筛选 |

针对“用户获取成本”，建议分别定义诊断指标、结果指标和护栏指标：

- **诊断指标**用于定位流程，例如曝光、有效访问、符合条件对象数和异常节点。
- **结果指标**用于判断是否改善，例如转化、留存、客单、毛利或处理时长。
- **护栏指标**用于防止局部优化伤害整体，例如退款、投诉、成本、公平性和长期留存。

每次计算都问四个问题：分母是谁、对象何时进入分母、例外状态怎么处理、窗口是否足够覆盖行为完成。尤其是重复订单与重复退款；跨渠道归因重叠；会员与匿名身份合并错误，任何一项没有解释清楚，指标都可能“看起来合理但无法决策”。

## 3. 方法选择：描述、诊断、预测还是因果

| 目标 | 适合的方法 | 需要的证据 | 不要混淆 |
| --- | --- | --- | --- |
| 描述现状 | 趋势、结构、同期群 | 完整口径、稳定时间窗 | 描述不等于原因 |
| 定位异常 | 分层、贡献度、漏斗、异常检测 | 原始事件、基线和质量检查 | 排名靠前不等于因果 |
| 预测未来 | 时间序列、回归、机器学习 | 时间切分验证、误差成本 | 离线准确率不等于业务收益 |
| 评估策略 | A/B、灰度、准实验 | 对照组、样本量、护栏指标 | 上线前后对比容易混入季节和选择偏差 |

如果问题只是“发生了什么”，先别急着建模；如果问题涉及“采取某策略会怎样”，就必须讨论反事实和识别条件。围绕“用户获取成本”，应把观察分析、预测和因果评估的产出分开标注。

## 4. 案例一：西南某区域商超

### 案例 1：西南某区域商超的“用户获取成本”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：会员数量增长但高价值会员贡献下降，促销预算无法判断应投向拉新、唤醒还是深度复购。本次讨论的重点是“用户获取成本”，所以团队先要求把先冻结对象与时间窗写进项目目标，而不是直接开始做报表。
- **数据范围**：会员、交易、优惠券、品类偏好、到店频次和线上到家订单。同时收集ERP、WMS、OMS、CRM中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：家庭成员共用账号，手机号变更导致一人多号，历史会员等级与当前等级混用。进一步检查后发现，如果不先处理重复订单与重复退款，“用户获取成本”很容易被一个表面相关指标替代。
- **处理过程**：打通会员主数据，构建 RFM 与品类偏好组合分层，使用过去同周期基线评估券包策略。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目把会员分成待唤醒、稳定复购和高潜流失三组，并为每组设置不同触达与停止条件。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“用户获取成本”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

落地时建议先把一个总指标拆成可行动的树：

```text
用户获取成本｜从总量到单条证据
├── ① 同期基线：先排除节假日、活动和口径切换
├── ② 结构贡献：按渠道、品类、地区比较增量和抵消
├── ③ 状态漏斗：点击 → 详情浏览 → 加购 → 下单
├── ④ 记录回查：正常、边界、异常各抽 N 条
└── ⑤ 闭环验证：复购率与护栏指标同时恢复才算解决
```

如果某一分支变化最大，再进入下一层，而不是一开始就按十几个维度切碎。每个分层结果都应同时报告样本量，避免小样本的极端比例抢走注意力。

## 5. SQL：计算趋势、结构和贡献度

### 趋势、结构与贡献度诊断

```sql
-- 用户获取成本：分位对比诊断（品类 × 用户层级）
WITH scoped AS (
  SELECT
    user_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_retail_event
  WHERE event_time >= DATE '2026-03-01'
    AND event_time <  DATE '2026-06-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '退款率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

示例 SQL 只表达计算逻辑。实际实施应加入分区条件、业务状态过滤、时区和主题范围，并在结果中保留口径版本。

## 6. 案例二：华南某连锁零售企业

### 案例 2：华南某连锁零售企业的“用户获取成本”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：线上订单增长，但门店库存可用率与线上显示不一致，缺货取消率持续升高。本次讨论的重点是“用户获取成本”，所以团队先要求把先证明数据链路可信写进项目目标，而不是直接开始做报表。
- **数据范围**：门店 POS、中心仓、前置仓、WMS、OMS 和即时配送订单。同时收集ERP、WMS、OMS、CRM中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：可售库存扣减存在时间差，门店盘点期间库存被错误暴露，拆单后子订单无法回溯父订单。进一步检查后发现，如果不先处理跨渠道归因重叠，“用户获取成本”很容易被一个表面相关指标替代。
- **处理过程**：建立可售库存快照和库存事件双模型，增加安全库存缓冲，按仓店与商品分析取消原因。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目把缺货原因拆成数据延迟、真实缺货和超卖拦截，并形成库存质量日报。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“用户获取成本”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

当业务方要求“解释为什么下降”时，可以按下面顺序回答：

1. 先确认下降是否真实存在，排查采集、任务、维表和状态映射。
2. 把变化拆成对象数量、行为强度和结构占比。
3. 找到贡献最大的分组，但保留其他分组的抵消效应。
4. 抽取正负样本回查业务事件和操作日志。
5. 把尚不能证明的解释标为假设，并设计下一轮验证。

## 7. 代码验证：专题指标、实验或模型

### 专题验证代码

```sql
-- 主题：用户获取成本
-- 示例表名和字段名用于说明建模方法，落地时请映射到企业现有数仓。
WITH scoped AS (
  SELECT
    e.event_id,
    e.entity_id,
    e.event_time AS event_time,
    e.stage_code,
    e.dimension_value AS analysis_dim,
    e.status,
    COALESCE(e.metric_value, 0) AS metric_value,
    ROW_NUMBER() OVER (
      PARTITION BY e.event_id
      ORDER BY e.updated_at DESC
    ) AS version_no
  FROM fact_retail_event e
  WHERE e.event_time >= DATE '2026-05-01'
    AND e.event_time <  DATE '2026-08-01'
    AND e.subject_name = '用户获取成本'
    AND e.is_deleted = 0
),
dedup AS (
  SELECT *
  FROM scoped
  WHERE version_no = 1
),
baseline AS (
  SELECT
    analysis_dim,
    COUNT(DISTINCT entity_id) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    AVG(metric_value) AS avg_metric,
    MIN(event_time) AS first_seen_at,
    MAX(event_time) AS last_seen_at
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY analysis_dim
)
SELECT
  analysis_dim AS analysis_dimension,
  entity_cnt,
  event_cnt,
  ROUND(avg_metric, 4) AS avg_order_value,
  first_seen_at,
  last_seen_at,
  ROUND(event_cnt * 1.0 / NULLIF(SUM(event_cnt) OVER (), 0), 4) AS contribution_ratio
FROM baseline
ORDER BY event_cnt DESC;
```

## 8. 异常、偏差与常见误区

- **辛普森悖论**：总体改善但每个分组都变差，可能由对象结构变化造成。
- **幸存者偏差**：只分析完成流程的对象，忽略中途流失和中止。
- **分母漂移**：渠道口径、登录状态、版本或活动范围变化，改变可比性。
- **回传延迟**：当天数据未回补，导致近期效果被系统性低估。
- **多重比较**：反复寻找显著分组，实际只是随机波动。
- **行动偏差**：只报告支持既定方案的结果，忽略反例和护栏指标。

围绕“用户获取成本”，应预先写出至少三条反例检查。比如数据质量异常是否与业务变化分开、方案是否说明了成本、边界和停止条件，以及 上线后是否有人负责观察和复盘。

## 10. 交付物与工作节奏

| 交付物 | 应包含 | 质量要求 |
| --- | --- | --- |
| 问题说明 | 背景、对象、时间、成功标准 | 一句话能说明要改变什么 |
| 指标字典 | 公式、粒度、排除项、负责人 | 换人计算能得到同一结果 |
| 分析代码 | SQL/Python、参数、日志 | 可复跑，不依赖手工改数 |
| 验证记录 | 抽样、对账、边界样本 | 结论能回到原始事件 |
| 决策材料 | 结论、证据、限制、行动 | 区分事实、解释和建议 |
| 复盘记录 | 结果、副作用、下一步 | 有观察周期和停止条件 |

1. 明确“用户获取成本”服务的使用者、决策动作和不做范围，并把成功标准写成可观察指标。
2. 为用户、商品、会话分别确认主键、时间和状态，画出从源系统到结果的链路。
3. 先做字段血缘和质量画像，检查订单与支付金额平衡、退款不重复冲减、自然流量与付费流量归因唯一。
4. 用同周期基线和至少两个维度拆解问题，避免只比较一个异常周。
5. 抽取正常、异常和边界样本回查原始业务单据，记录抽样方法与结论。
6. 选择一种代码实现并保留参数、版本、执行日志和结果快照，确保别人可以复跑。
7. 上线前定义告警阈值、回滚条件和责任人；上线后按周观察主指标与护栏指标。

```python
from datetime import date
from hashlib import sha256

import pandas as pd

SUBJECT = "用户获取成本"
BLOCKING_RULES = ["订单与支付金额平衡","退款不重复冲减","自然流量与付费流量归因唯一"]


def validate_release(frame: pd.DataFrame, start: date, end: date) -> dict:
    scoped = frame.loc[
        frame["event_date"].between(pd.Timestamp(start), pd.Timestamp(end))
        & (frame["subject_key"] == "subject")
    ].copy()
    checks = {
        "has_rows": len(scoped) > 0,
        "event_id_unique": not scoped["event_id"].duplicated().any(),
        "entity_key_complete": scoped["entity_key"].notna().all(),
        "event_time_present": scoped["event_time"].notna().all(),
        "scope_matches": scoped["subject_key"].nunique() == 1,
    }
    payload = f"{SUBJECT}|{start}|{end}|{len(scoped)}|{sorted(checks.items())}"
    return {
        "subject": SUBJECT,
        "rows": len(scoped),
        "checks": checks,
        "blocking_rules": BLOCKING_RULES,
        "release_allowed": all(checks.values()),
        "evidence_hash": sha256(payload.encode("utf-8")).hexdigest(),
    }
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
