# 合规

> [!warning] 核心判断
> “合规”在会议里常常只有一句话，落到数据团队却会展开成口径、主键、时间、状态、权限和交付责任。下面用一个从问题到上线的顺序展开，并穿插三个脱敏的复合案例，帮助你把标题里的知识迁移到真实项目。

## 1. 先判断应治理什么风险

“合规”通常不是买一个平台就能解决的问题。它至少涉及制度、标准、责任、流程、技术和审计六层。开始前先把风险写成可观察事实：

| 风险问题 | 观察信号 | 可能影响 | 首先核查 |
| --- | --- | --- | --- |
| 定义不一致 | 同名指标多个 SQL、多个业务解释 | 决策冲突、返工 | 指标字典与负责人 |
| 数据不完整 | 分区缺失、关键字段空值 | 报表失真、流程中断 | 采集与任务日志 |
| 责任不清 | 问题工单长期无人认领 | 修复延迟、同类复发 | 资产责任矩阵 |
| 访问过宽 | 长期权限、共享账号、无审计 | 泄漏与合规风险 | 权限清单与访问日志 |
| 变更不可见 | 表结构或逻辑变更无通知 | 下游批量故障 | 血缘与发布记录 |

1. **敏感数据越权访问**：需要在标准、系统或组织流程中设置对应控制。
2. **授信金额与借据余额混用**：需要在标准、系统或组织流程中设置对应控制。
3. **产品口径随组织调整无法比较**：需要在标准、系统或组织流程中设置对应控制。
4. **风险规则版本不可追溯**：需要在标准、系统或组织流程中设置对应控制。
5. **冲正交易未成对处理**：需要在标准、系统或组织流程中设置对应控制。

## 2. 用 DAMA 思路拆成可执行组件

| 组件 | 本文关注对象 | 最小可执行机制 |
| --- | --- | --- |
| 数据标准 | 字段、代码、指标和业务术语；结合“合规”重点检查客户号脱敏且跨系统映射一致 | 标准登记、评审、版本与废弃 |
| 元数据 | 表、字段、任务、接口、负责人；结合“合规”重点检查借贷与支付金额平衡 | 自动采集、业务补充、变更通知 |
| 数据质量 | 完整性、唯一性、及时性、准确性；结合“合规”重点检查交易时间与入账时间区分 | 规则、阈值、工单与复盘 |
| 主数据 | 客户、商品、设备、机构等共享对象；结合“合规”重点检查风险标签可追溯到规则版本 | 源权威、去重、合并、历史关系 |
| 数据安全 | 分类分级、权限、脱敏和审计；结合“合规”重点检查时点快照与流水不混用 | 审批、最小权限、访问复核 |
| 数据血缘 | 表、字段、任务和指标关系；结合“合规”重点检查客户号脱敏且跨系统映射一致 | 影响分析、问题追踪、变更评审 |

治理不是把所有数据都按同一优先级管理。建议依据使用范围、监管要求、决策影响和故障历史划分关键资产，再决定投入。关键资产应有唯一负责人、明确消费者、质量目标、访问策略和变更通知。

## 3. 资产、标准与责任矩阵

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 客户 | `customer_id` | 获客与准入 |
| 过程对象 | 账户 | `account_id` | 开户 |
| 过程对象 | 交易 | `transaction_id` | 交易或授信 |
| 结果对象 | 申请 | `application_id` | 风险监测 |
| 结果对象 | 风险事件 | `risk_event_id` | 结算 |
| 专题分析 | 合规 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

一个可执行的数据标准至少包括：

- **业务定义**：业务人员如何理解和适用。
- **技术定义**：字段类型、长度、格式、枚举和空值语义。
- **计算口径**：时间、粒度、分子分母和排除项。
- **权威来源**：哪个系统是事实源，冲突时以谁为准。
- **生命周期**：创建、变更、废弃和归档规则。
- **责任人**：业务负责人、数据负责人、技术负责人和审批人。

资产责任可以使用 RACI：业务负责人对定义负责，数据负责人对实现与质量负责，平台团队对工具和权限负责，安全合规对访问与审计负责，消费者对使用边界负责。只有“责任人”一个字段，没有决策权和时限，问题仍会回到治理团队自己处理。

## 4. 案例一：西南某保险机构

### 案例 1：西南某保险机构的“合规”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：代理渠道保费增长但续期率下降，渠道结算与客户服务质量难以同时评估。本次讨论的重点是“合规”，所以团队先要求把先冻结对象与时间窗写进项目目标，而不是直接开始做报表。
- **数据范围**：代理人、保单、缴费、理赔、投诉、续期和渠道结算。同时收集核心银行系统、信贷系统、支付清算系统、反洗钱系统中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：保单状态与缴费状态跨系统不同步，代理人组织归属频繁变化，退保与失效口径混用。进一步检查后发现，如果不先处理敏感数据越权访问，“合规”很容易被一个表面相关指标替代。
- **处理过程**：保留代理人和机构维度有效期，按保单件与保费拆分指标，建立首年与续期分组。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目识别出高保费低继续率渠道，并推动把继续率纳入渠道质量评价。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“合规”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

治理项目应先做小范围闭环，不要一开始铺满全公司。选择一个高影响业务域，完成从资产盘点、标准确认、质量规则、问题整改到复盘的完整链路，再复制机制。

## 5. 规则与代码：让控制可执行

### 发布前规则门禁

```python
# 合规：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "合规"
TOPIC_KEY = "subject"
RULE_ID = "rule_finance_jcx991"
GUIDE_CHECKS = [
    "检查客户号脱敏且跨系统映射一致",
    "检查借贷与支付金额平衡",
    "检查交易时间与入账时间区分"
]
RULES = {
    "required_columns": ["event_id", "customer_id", "event_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "customer_id",
    "time_field": "event_time",
    "max_duplicate_rate": 0.001,
    "max_null_rate": 0.005,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})
```

### 治理对象与风险分层 SQL

```sql
-- 合规：同期基线诊断（客户等级 × 机构）
WITH scoped AS (
  SELECT
    customer_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_finance_event
  WHERE event_time >= DATE '2026-06-01'
    AND event_time <  DATE '2026-09-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '活跃客户数' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

规则设计要同时考虑三件事：能否自动执行、误报成本是否可接受、失败后谁来处理。只写“不能为空”不够，必须明确哪类对象允许为空、谁能在何种情况下豁免、豁免多久、是否需要审批和复核。

建议把规则分成四级：

1. **阻断**：涉及监管、资金、身份或核心发布，失败即停止。
2. **严重告警**：影响大但可先隔离，要求在约定时间内响应。
3. **观察告警**：可能是正常业务变化，先记录趋势。
4. **探索检查**：尚未形成稳定阈值，仅用于发现异常模式。

## 6. 案例二：华东某城市商业银行

### 案例 2：华东某城市商业银行的“合规”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：经营看板同时出现客户增长和资产流失，业务方无法判断是新客质量下降还是高价值客户迁移。本次讨论的重点是“合规”，所以团队先要求把先证明数据链路可信写进项目目标，而不是直接开始做报表。
- **数据范围**：客户、账户、产品持仓、交易、渠道访问和客户经理服务记录。同时收集核心银行系统、信贷系统、支付清算系统、反洗钱系统中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：客户等级使用当前值回溯历史，理财产品申赎存在非交易日确认，跨行转账冲正未成对。进一步检查后发现，如果不先处理授信金额与借据余额混用，“合规”很容易被一个表面相关指标替代。
- **处理过程**：建立客户与账户每日快照，区分交易流水和余额快照，按客户层级与产品分析资产净流入。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目定位到短期理财到期集中流出，并增加到期前触达与产品承接分析。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“合规”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

治理指标不要只统计“生成了多少文档、接入了多少资产”。更值得观察的是规则覆盖的关键资产、问题发现前移比例、问题复发率、变更影响分析耗时和业务是否愿意使用。

## 7. 权限、安全与审计

围绕“合规”，权限治理至少应回答：

- 谁能申请、谁审批、审批依据是什么？
- 权限是否按角色、数据级别和用途最小化？
- 临时权限何时收回，离职和转岗是否自动处理？
- 查询、下载和导出是否留痕，异常访问如何发现？
- 脱敏、加密、水印和审计日志是否与数据类型匹配？

敏感字段不应通过“复制一份测试数据”绕过问题。更合适的做法是分级脱敏、合成数据或受控计算环境。所有示例和代码都不应包含真实身份、账号、密钥、客户名单或未公开经营数据。

## 8. 第三个案例：华南某消费金融公司

### 案例 3：华南某消费金融公司的“合规”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：逾期率上升，风险团队希望区分客群变化、准入规则和贷后触达的影响。本次讨论的重点是“合规”，所以团队先要求把把数据和业务动作一起复盘写进项目目标，而不是直接开始做报表。
- **数据范围**：申请、授信、借款、还款计划、实际还款、催收和风险规则版本。同时收集核心银行系统、信贷系统、支付清算系统、反洗钱系统中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：申请件与借款件一对多，规则版本覆盖时间不完整，展期后账龄计算口径不统一。进一步检查后发现，如果不先处理产品口径随组织调整无法比较，“合规”很容易被一个表面相关指标替代。
- **处理过程**：建立申请-借据-还款计划三级模型，固定风险规则生效区间，按账龄和放款批次做同口径分析。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目将逾期变化拆成新客结构、额度使用和早期还款行为，并建立规则回滚观察指标。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“合规”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

## 9. 90 天落地路线

| 时间 | 重点 | 输出 | 验收 |
| --- | --- | --- | --- |
| 第 1-2 周 | 访谈、资产盘点、风险分级 | 关键资产清单、问题基线 | 每个资产有负责人 |
| 第 3-4 周 | 标准与指标口径 | 标准草案、指标字典 | 业务和技术共同确认 |
| 第 5-7 周 | 规则、权限和血缘接入 | 自动规则、访问矩阵、影响分析 | 关键故障能被提前发现 |
| 第 8-10 周 | 问题闭环与试点 | 工单流程、复盘记录 | 问题有分级、时限与复核 |
| 第 11-12 周 | 复制与成熟度评估 | 推广清单、下一阶段路线 | 用数据证明有效而非只报接入量 |

1. 明确“合规”服务的使用者、决策动作和不做范围，并把成功标准写成可观察指标。
2. 为客户、账户、交易分别确认主键、时间和状态，画出从源系统到结果的链路。
3. 先做字段血缘和质量画像，检查客户号脱敏且跨系统映射一致、借贷与支付金额平衡、交易时间与入账时间区分。
4. 用同周期基线和至少两个维度拆解问题，避免只比较一个异常周。
5. 抽取正常、异常和边界样本回查原始业务单据，记录抽样方法与结论。
6. 选择一种代码实现并保留参数、版本、执行日志和结果快照，确保别人可以复跑。
7. 上线前定义告警阈值、回滚条件和责任人；上线后按周观察主指标与护栏指标。
8. 复盘时区分数据问题、业务变化、方案偏差和外部因素，并把改进项转成有时限的任务。

## 10. 检查清单与自测

### 扩展代码一：从合规回到可核对明细

```sql
-- 合规：状态链与时间间隔核查
WITH ordered_events AS (
  SELECT
    customer_id AS entity_key,
    event_id,
    stage_code,
    event_time AS event_time,
    LAG(stage_code) OVER (
      PARTITION BY customer_id
      ORDER BY event_time, event_id
    ) AS previous_stage,
    LAG(event_time) OVER (
      PARTITION BY customer_id
      ORDER BY event_time, event_id
    ) AS previous_time
  FROM fact_finance_event
  WHERE event_time >= :start_date
    AND event_time <  :end_date
    AND subject_key = 'subject'
)
SELECT
  entity_key,
  previous_stage,
  stage_code,
  event_time,
  event_time - previous_time AS elapsed,
  CASE
    WHEN event_time < previous_time THEN 'time_reversed'
    WHEN previous_stage = stage_code THEN 'duplicate_stage'
    WHEN previous_stage IS NULL THEN 'missing_prefix'
    ELSE 'candidate_delay'
  END AS exception_type
FROM ordered_events
WHERE event_time < previous_time
   OR previous_stage = stage_code
   OR event_time - previous_time > INTERVAL '1 hour'
ORDER BY exception_type, elapsed DESC;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

```python
Path("release-evidence.json").write_text(
    json.dumps(manifest, ensure_ascii=False, indent=2),
    encoding="utf-8",
)
print(manifest["decision"])
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
