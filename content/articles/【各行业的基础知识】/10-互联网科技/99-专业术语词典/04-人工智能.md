# 人工智能

> [!abstract] 场景速览
> 一个关于“人工智能”的结论能不能被信任，取决于它是否能回到原始事件、明确时间和对象，并说明排除了哪些记录。下面不会用单一模板概括所有场景，而是结合互联网科技中的多类任务，展示数据建模、代码分析和项目验收之间如何衔接。

## 1. “人工智能”在互联网科技业务链中的位置

互联网科技的核心流程可以概括为：获客 → 注册 → 激活 → 功能使用 → 付费 → 续费 → 支持 → 流失或升级。参与角色包括用户、产品经理、研发、SRE、数据分析、销售与客户成功、安全与合规。“人工智能”通常不是一个孤立字段，而是连接业务动作、数据记录和管理决策的一层能力。

从数据团队视角，至少要回答四个问题：

1. **谁使用**：用户、产品经理、研发、SRE分别要用它做判断、执行还是审计。
2. **对象是什么**：一行数据代表账号、一次事件、一个批次还是一天快照。
3. **流程在哪里变化**：通过注册、激活、功能使用、付费之间的状态和时间差定位问题。
4. **结果如何被采用**：谁在什么时间前采取行动，使用哪个指标观察改善或副作用。

一个合格的专题目标可以写成：

> 在【时间窗】和【授权数据范围】内，围绕“人工智能”，按【产品、功能、版本】比较【功能渗透率】与【续费率】，定位一个可干预流程节点，并记录行动后的变化与边界。

## 2. 一张图看清角色、流程和数据

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 账号 | `account_id` | 获客 |
| 过程对象 | 设备 | `device_id` | 注册 |
| 过程对象 | 功能 | `feature_id` | 激活 |
| 结果对象 | 会话 | `session_id` | 功能使用 |
| 结果对象 | 订阅 | `subscription_id` | 付费 |
| 专题分析 | 人工智能 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

建模时不要先把所有系统字段堆进一张大表。更稳妥的做法是分别保留三类事实：

- **事件事实**：谁在什么时间做了动作，例如挂号、下单、开工、报警或学习。
- **状态快照**：对象在某一天的状态，例如会员等级、租约、账户余额或设备资产关系。
- **结果事实**：流程完成后的产出，例如结算金额、良品数量、签收结果或考试分数。

三者的粒度不同。把事件、快照和结果强行放在同一行，会让金额、数量和转化率在汇总时重复。若“人工智能”涉及状态变化，优先建立状态机；若涉及金额，先做借贷或收付平衡；若涉及对象归属，保留维度有效期。

## 3. 指标与口径：不要把相关数字直接当答案

| 专题观测面 | 需要回答的问题 | 关键证据 | 判定与动作 |
| --- | --- | --- | --- |
| 部署（本标题优先） | 模型版本、漂移、延迟、成本、回滚和人工接管 | 监控、灰度、日志和事故演练 | 无回滚不进入关键流程 |
| 任务 | 问题是分类、预测、生成、检索还是动作决策 | 输入输出、成功标准、失败成本 | 无需 AI 时优先规则或简单模型 |
| 评估 | 离线、上线和人工评估是否一致 | 基线、时间切分、分群、任务完成和风险 | 高风险错误单独设门槛 |
| 数据 | 样本是否代表业务、是否泄漏、是否获授权 | 数据卡、标签、分群、版本和来源 | 数据不合格不先调模型 |

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 活跃率 | `COUNT(DISTINCT active_account_id) / COUNT(DISTINCT eligible_account_id)`（视图字段 `active_rate`） | 产品、功能、版本 | 不混用测试、撤销和跨期状态；与“人工智能”相关时还要补充主题筛选 |
| 功能渗透率 | `COUNT(DISTINCT account_using_feature_id) / COUNT(DISTINCT active_account_id)`（视图字段 `feature_adoption`） | 功能、版本、地区 | 不混用测试、撤销和跨期状态；与“人工智能”相关时还要补充主题筛选 |
| 续费率 | `COUNT(DISTINCT renewed_subscription_id) / COUNT(DISTINCT renewable_subscription_id)`（视图字段 `renewal_rate`） | 版本、地区、客户层级 | 不混用测试、撤销和跨期状态；与“人工智能”相关时还要补充主题筛选 |
| 故障影响面 | `COUNT(DISTINCT affected_account_id) / COUNT(DISTINCT active_account_id)`（视图字段 `incident_impact`） | 地区、客户层级 | 不混用测试、撤销和跨期状态；与“人工智能”相关时还要补充主题筛选 |

指标字典至少应包含：中文名、英文编码、业务定义、计算公式、事实粒度、时间字段、对象范围、排除条件、负责人和验收样例。对于“人工智能”，还应注明它使用的是业务发生时间还是入仓时间，是否包含撤销、退费、测试、跨期和补录记录。

一个常见误区是看到功能渗透率变化就立即解释业务原因。更可靠的顺序是：

1. 检查数据覆盖和延迟是否变化。
2. 检查对象范围、状态映射和维度归属是否变化。
3. 按时间、结构和分组拆解贡献。
4. 回到明细寻找能解释变化的事件。
5. 如果已经采取行动，再评估行动带来的增量，而不是事后挑一个相关指标。

## 4. 工作案例：从现象到数据处理

### 案例 1：华东某内容平台的“人工智能”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“人工智能”映射到“人工智能基础、方法与业务应用”中的部署，而不是泛泛讨论概念。
- **触发事件**：模型离线准确率提升，但线上推荐点击与用户留存没有改善。
- **业务与数据范围**：样本、特征、时间切分、曝光、点击、留存、成本和实验分组。数据侧重点采集监控、灰度、日志和事故演练，并与埋点平台、账号系统、订阅计费中的时间、状态和责任人信息对齐。
- **需要回答的问题**：模型版本、漂移、延迟、成本、回滚和人工接管。
- **关键障碍**：训练数据使用未来信息，评估只看总体准确率，没有覆盖冷启动与内容多样性。同时要防止机器流量误计把表面指标带偏。
- **处理过程**：重建时间外评测，加入业务护栏和线上对照，按用户分层分析收益与副作用。实施时把“部署具备版本、监控、漂移、回滚和人工接管”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例评估把模型指标、业务动作和长期价值分开验证。验收至少同时看主指标、监控、灰度、日志和事故演练和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“从任务、数据、基线、模型、评估、部署和风险理解 AI 能力，避免把模型热度等同于业务价值。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

这个案例最关键的动作不是“跑一条 SQL”，而是把“人工智能”对应的业务对象和上下游系统放在同一张链路图上。链路图至少要标出源系统、事件时间、关联主键、状态变化、数据负责人和消费方。

## 5. SQL 示例：在统一口径下做分层诊断

下面的查询用于展示分析结构，表名和字段需映射到实际环境。重点是去重、范围筛选、基线比较和贡献率，而不是代码本身。

### 标题专属诊断 SQL

```sql
-- 人工智能：留存同期群诊断（功能 × 地区）
WITH scoped AS (
  SELECT
    account_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_product_event
  WHERE event_time >= DATE '2026-08-01'
    AND event_time <  DATE '2026-11-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '故障影响面' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

执行后要回答四类验证题：

- 结果总量能否与源系统或既有报表在相同口径下解释差异？
- 排名前几位的分组是否由少数超长、重复或补录记录造成？
- 缺失日期表现为“未发生”还是“未采集”，是否改变分母？
- 维度使用的是当时归属还是当前归属，跨期比较是否一致？

## 6. 第二个案例：跨系统、跨部门时怎样不失控

### 案例 2：华北某移动工具产品的“人工智能”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“人工智能”映射到“人工智能基础、方法与业务应用”中的任务，而不是泛泛讨论概念。
- **触发事件**：新版本上线后活跃下降，产品团队无法判断是用户结构、功能改动还是埋点变化。
- **业务与数据范围**：版本、安装、升级、启动、功能点击、崩溃、设备与渠道。数据侧重点采集输入输出、成功标准、失败成本，并与埋点平台、账号系统、订阅计费中的时间、状态和责任人信息对齐。
- **需要回答的问题**：问题是分类、预测、生成、检索还是动作决策。
- **关键障碍**：新旧版本并行且升级用户不是随机分组，埋点在新版本改名，崩溃事件采样率变化。同时要防止多版本并行把表面指标带偏。
- **处理过程**：保留事件字典和版本映射，按升级前后用户做同体对照，把功能行为与崩溃分开分析。实施时把“用简单基线和业务价值证明需要 AI”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例项目发现启动链路崩溃与某渠道安装包有关，并建立版本级质量门禁。验收至少同时看主指标、输入输出、成功标准、失败成本和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“从任务、数据、基线、模型、评估、部署和风险理解 AI 能力，避免把模型热度等同于业务价值。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

跨部门项目最容易在三个地方返工：业务术语没有冻结、主数据映射没有版本、验收时才发现权限不足。建议在开发前让业务负责人签字确认指标定义，让数据负责人确认粒度与主键，让安全负责人确认字段范围，让运维负责人确认发布与回滚窗口。

## 7. Python 示例：把数据质量变成发布门禁

### 可执行质量门禁

```python
# 人工智能：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "人工智能"
TOPIC_KEY = "subject"
RULE_ID = "rule_technology_tl8a53"
GUIDE_CHECKS = [
    "用简单基线和业务价值证明需要 AI",
    "训练、验证和测试按时间或实体隔离并检查泄漏",
    "离线、线上、人工和风险指标共同构成评估",
    "部署具备版本、监控、漂移、回滚和人工接管"
]
RULES = {
    "required_columns": ["event_id", "account_id", "event_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "account_id",
    "time_field": "event_time",
    "max_duplicate_rate": 0.001,
    "max_null_rate": 0.003,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：用简单基线和业务价值证明需要 AI；训练、验证和测试按时间或实体隔离并检查泄漏；离线、线上、人工和风险指标共同构成评估；部署具备版本、监控、漂移、回滚和人工接管
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

这段代码适合放在离线任务完成之后、指标发布之前。真实环境还应从调度平台读取分区参数、把结果写入质量平台，并在关键规则失败时阻断下游。告警不是终点，工单中要记录影响资产、发现时间、临时处理、根因、修复时间和防复发动作。

## 8. 异常排查：从指标异常回到业务事件

| 专题检查项 | 失败时会看到什么 | 首选证据 | 处理动作 |
| --- | --- | --- | --- |
| 用简单基线和业务价值证明需要 AI | 模型版本、漂移、延迟、成本、回滚和人工接管 | 监控、灰度、日志和事故演练 | 无回滚不进入关键流程 |
| 训练、验证和测试按时间或实体隔离并检查泄漏 | 问题是分类、预测、生成、检索还是动作决策 | 输入输出、成功标准、失败成本 | 无需 AI 时优先规则或简单模型 |
| 离线、线上、人工和风险指标共同构成评估 | 离线、上线和人工评估是否一致 | 基线、时间切分、分群、任务完成和风险 | 高风险错误单独设门槛 |
| 部署具备版本、监控、漂移、回滚和人工接管 | 样本是否代表业务、是否泄漏、是否获授权 | 数据卡、标签、分群、版本和来源 | 数据不合格不先调模型 |

围绕“人工智能”排查时，可以按以下顺序进行：

1. **影响面**：哪些指标、报表、接口或业务团队受影响，是否需要暂停对外发布。
2. **时间线**：源系统变更、任务发布、数据回刷、组织调整和业务活动分别发生在什么时候。
3. **数据链路**：上游是否延迟，分区是否缺失，主键是否重复，状态是否映射错误。
4. **业务证据**：抽取异常记录，与原始单据、操作日志、客服记录或现场系统核对。
5. **修复与复核**：明确补数范围、重跑粒度、回滚版本和验收样例。
6. **防复发**：把一次性排查升级为规则、监控、责任人和变更评审。

特别要注意：机器流量误计；多版本并行；订阅时点口径混淆；故障影响面低估。这些问题如果不被单独标记，很容易被误写成业务趋势。

## 9. 第三个案例与延伸场景

### 案例 3：华南某金融机构的“人工智能”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“人工智能”映射到“人工智能基础、方法与业务应用”中的评估，而不是泛泛讨论概念。
- **触发事件**：智能客服上线后解决率一般，高风险问题却偶尔给出过度确定回答。
- **业务与数据范围**：真实会话、意图、知识来源、人工转接、错误成本和模型日志。数据侧重点采集基线、时间切分、分群、任务完成和风险，并与埋点平台、账号系统、订阅计费中的时间、状态和责任人信息对齐。
- **需要回答的问题**：离线、上线和人工评估是否一致。
- **关键障碍**：评测集以常见问题为主，没有拒答、越权和复杂问题样本。同时要防止订阅时点口径混淆把表面指标带偏。
- **处理过程**：按意图与风险分层建立评测，低置信度澄清或转人工，关键答案强制引用。实施时把“训练、验证和测试按时间或实体隔离并检查泄漏”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例门禁以任务完成、引用支持、风险拦截和人工采纳评估。验收至少同时看主指标、基线、时间切分、分群、任务完成和风险和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“从任务、数据、基线、模型、评估、部署和风险理解 AI 能力，避免把模型热度等同于业务价值。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

另外两个适合继续拆分的工作场景是：

- **华东某 SaaS 公司**：客户数量增长但净收入留存下降，管理层需要区分降级、流失和新客结构。可以先从账号、席位、订阅、账单、功能使用、工单和客户健康度建立最小数据闭环，再围绕“人工智能”检查一个客户存在多个租户，席位变更与账单生效时间不同，降级未正确冲减。
- **华南某云服务商**：服务可用率看似达标，但客户投诉集中在短时高峰和部分区域。可以先从API 调用、错误码、延迟、可用区、客户等级、工单和故障公告建立最小数据闭环，再围绕“人工智能”检查平均可用率掩盖小客户长尾，重试请求放大调用量，故障和工单缺少统一事件号。

### 案例 4：人工智能的口径冲突与双轨对账

一个看似普通的“人工智能”需求，在跨系统核验后变成了围绕“对象与口径争议”的专项排查。触发排查的不是一次严重事故，而是连续几次解释不清的数据差异。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 在开发报表或模型前，把对象、粒度、时间、状态和排除条件形成可执行的共同定义。在本场景里，核心风险还包括多版本并行，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：账号、设备及其在流失或升级前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注account_id与device_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 两个团队都声称在统计同一主题，但一行数据代表的业务对象不同，时间字段也不同。初看时，CRM与埋点平台的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 指标字典版本、源系统样例、两条计算链路、差异清单和业务确认记录。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“安全与合规”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“人工智能”的当前定义并记录版本；第二步用账号明细核对CRM到埋点平台的关联；第三步按功能与地区做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察功能渗透率和护栏指标故障影响面。
- **行动与护栏：** 先冻结本期对象范围，再分别按源系统口径和目标口径重算，对每一类差异写明原因和暂定处理。专题检查项“用简单基线和业务价值证明需要 AI”被写成发布门禁，口径未确认时只发布差异分析，不把任一结果包装成正式经营指标。
- **失败路径：** 用平均值掩盖差异，或直接把对不上的明细删掉。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“人工智能”时，先验证监控、灰度、日志和事故演练，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由安全与合规在明确时限内，根据功能渗透率、故障影响面和版本字段完整决定继续、回退、补查还是转人工。 若多版本并行或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 案例 7：人工智能上线前的质量门禁

某组织希望用“人工智能”支持一次真实决策，但在取数与评审阶段发现，常规日期下结果看起来正常，一旦遇到空值、重复、跨期、撤销或历史归属，报表口径便无法解释。这个案例因此从问题定义重新开始。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 把关键质量规则、阈值、例外审批、阻断动作和复核人写入发布流程。在本场景里，核心风险还包括产品事件缺少版本上下文，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：会话、订阅及其在激活前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注session_id与subscription_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 常规日期下结果看起来正常，一旦遇到空值、重复、跨期、撤销或历史归属，报表口径便无法解释。初看时，订阅计费与工单系统的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 五类边界样本、规则命中率、趋势对比、豁免记录、责任人、阻断结果和复盘工单。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“研发”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“人工智能”的当前定义并记录版本；第二步用会话明细核对订阅计费到工单系统的关联；第三步按客户层级与功能做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察工单解决时长和护栏指标功能渗透率。
- **行动与护栏：** 从阻断、严重、观察三级建立规则，先修数据和逻辑，再决定是否允许有期限的业务例外。专题检查项“部署具备版本、监控、漂移、回滚和人工接管”被写成发布门禁，影响资金、安全、监管或核心经营判断的关键规则失败时停止发布。
- **失败路径：** 一直调低阈值让报表通过，却没有处理规则为何持续失败。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“人工智能”时，先验证数据卡、标签、分群、版本和来源，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由研发在明确时限内，根据工单解决时长、功能渗透率和故障与工单可关联决定继续、回退、补查还是转人工。 若产品事件缺少版本上下文或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从人工智能回到可核对明细

```sql
-- 人工智能：行动前后与分组增量
WITH scoped AS (
  SELECT
    account_id AS entity_key,
    功能 AS decision_group,
    event_time AS event_date,
    metric_value,
    CASE
      WHEN event_time <  :action_date THEN 'before'
      ELSE 'after'
    END AS period_label
  FROM fact_product_event
  WHERE event_time >= :analysis_start
    AND event_time <  :analysis_end
    AND subject_key = 'subject'
),
grouped AS (
  SELECT
    decision_group,
    period_label,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    AVG(metric_value) AS metric_avg,
    SUM(metric_value) AS metric_sum
  FROM scoped
  GROUP BY decision_group, period_label
),
compared AS (
  SELECT
    decision_group,
    MAX(CASE WHEN period_label = 'before' THEN metric_avg END) AS before_avg,
    MAX(CASE WHEN period_label = 'after' THEN metric_avg END) AS after_avg,
    MAX(CASE WHEN period_label = 'before' THEN entity_cnt END) AS before_cnt,
    MAX(CASE WHEN period_label = 'after' THEN entity_cnt END) AS after_cnt
  FROM grouped
  GROUP BY decision_group
)
SELECT
  decision_group,
  before_avg,
  after_avg,
  after_avg - before_avg AS naive_delta,
  '续费率' AS metric_name,
  '用简单基线和业务价值证明需要 AI' AS required_evidence
FROM compared
WHERE before_cnt >= 30 AND after_cnt >= 30
ORDER BY ABS(after_avg - before_avg) DESC;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把人工智能的验收证据写成门禁

```python
import json
from pathlib import Path


def build_evidence_manifest(
    subject: str,
    scope: dict,
    checks: dict,
    samples: list[dict],
    owner: str,
) -> dict:
    failed = [name for name, passed in checks.items() if not passed]
    return {
        "subject": subject,
        "scope": scope,
        "checks": checks,
        "failed_checks": failed,
        "sample_evidence": samples[:5],
        "owner": owner,
        "decision": "block" if failed else "review",
        "manual_questions": [
            "每一项失败是否已回到原始记录",
            "对象、时间和状态是否与指标字典一致",
            "回滚或修复后是否重新完成对账",
        ],
    }


manifest = build_evidence_manifest(
    subject="人工智能",
    scope={"systems": ["埋点平台","账号系统","订阅计费","工单系统"]},
    checks={"definition_frozen": False, "reconciled": False},
    samples=[],
    owner="用户",
)
Path("release-evidence.json").write_text(
    json.dumps(manifest, ensure_ascii=False, indent=2),
    encoding="utf-8",
)
print(manifest["decision"])
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。

### 四个案例共用的验收清单

| 验证面 | 发布前问题 | 证据 | 不通过时 |
| --- | --- | --- | --- |
