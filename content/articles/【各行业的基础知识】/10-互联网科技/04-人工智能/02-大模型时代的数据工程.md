# 大模型时代的数据工程

> [!tip] 核心原则
> 讨论“大模型时代的数据工程”时，最容易犯的错误是直接从工具或报表开始。更有用的顺序是：先看业务链条，再找可观察指标，随后确认数据粒度，最后才选择 SQL、模型或平台组件。本文按这个顺序给出可执行方案和常见的失败样本。

## 1. 从业务任务定义 AI 能力

围绕“大模型时代的数据工程”，先把任务写成输入、输出、成功标准和失败边界。不要从“上一套模型”或“接一个聊天框”开始。

| 设计项 | 必须回答的问题 | 错误示例 | 更好做法 |
| --- | --- | --- | --- |
| 用户 | 谁使用，谁复核，谁承担后果 | 所有人都能用 | 按角色和权限明确使用边界 |
| 输入 | 文本、表格、图片还是工具调用 | 把所有数据都塞进上下文 | 只提供任务所需且获授权的数据 |
| 输出 | 分类、生成、检索、SQL 还是动作 | 只要求“回答准确” | 定义可检查的输出结构 |
| 成功 | 任务完成、采纳、质量、时延和成本 | 只看离线准确率 | 离线 + 线上 + 人工复核 |
| 失败 | 无答案、拒答、转人工还是回滚 | 失败也生成看似合理内容 | 明确置信阈值和降级路径 |

## 2. 数据、知识库与版本

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 账号 | `account_id` | 获客 |
| 过程对象 | 设备 | `device_id` | 注册 |
| 过程对象 | 功能 | `feature_id` | 激活 |
| 结果对象 | 会话 | `session_id` | 功能使用 |
| 结果对象 | 订阅 | `subscription_id` | 付费 |
| 专题分析 | 大模型时代的数据工程 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

AI 项目的数据治理比传统报表更强调版本和来源。至少记录：

- 数据集和知识文档的来源、授权、时间、负责人和版本。
- 样本标注规则、标注人、抽检结果和争议处理。
- 训练、验证、测试与线上反馈是否隔离。
- 提示词、模型、温度、检索参数和工具权限的版本。
- 输入中的个人信息、商业秘密和敏感字段是否脱敏。

如果“大模型时代的数据工程”使用 RAG，文档切片应尊重标题、章节、表格和条款结构；如果使用微调，先证明提示词、检索或流程优化不足；如果使用 Agent，先限制工具白名单和最大执行步数。

## 3. 评估：不要只看一个准确率

| 评估层 | 指标 | 说明 |
| --- | --- | --- |
| 检索 | Hit@K、MRR、版本正确率、权限过滤 | 正确内容是否被召回且可用 |
| 生成 | 引用支持率、事实一致性、完整性 | 回答是否有证据、是否遗漏关键条件 |
| 任务 | 完成率、转人工率、采纳率、重复澄清 | 用户问题是否真的解决 |
| 安全 | 越权、注入、敏感输出、违规动作 | 是否突破权限与安全边界 |
| 工程 | P50/P95 延迟、错误率、并发、成本 | 能否稳定且经济地服务 |
| 业务 | 节省时间、转化、质量、投诉 | 是否带来可解释价值 |

离线集要包含高频问题、长尾问题、边界问题、对抗问题和“应该拒答”的问题。线上评估要按用户、任务和风险等级分层，避免总体平均掩盖高危错误。

## 4. 案例一：华北某金融科技公司

### 案例 1：华北某金融科技公司的“大模型时代的数据工程”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“大模型时代的数据工程”映射到“大模型、Prompt 与评估工程”中的运营，而不是泛泛讨论概念。
- **触发事件**：生成式摘要成本快速增加，但业务只使用其中少量结果。
- **业务与数据范围**：请求类型、输入长度、模型路由、缓存、人工采纳和单任务成本。数据侧重点采集版本、trace、P95、单任务成本和回滚，并与埋点平台、账号系统、订阅计费中的时间、状态和责任人信息对齐。
- **需要回答的问题**：模型、Prompt、参数、成本和故障是否可追踪。
- **关键障碍**：所有请求都走同一大模型和长上下文，没有模板、缓存或小模型路由。同时要防止机器流量误计把表面指标带偏。
- **处理过程**：按任务复杂度和风险分层路由，常见问题模板化，长文档先检索压缩，再记录采纳反馈。实施时把“离线指标必须与线上任务完成、人工采纳、成本和风险关联”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例运营在质量护栏内降低单位成本，并对模型降级做 A/B 验证。验收至少同时看主指标、版本、trace、P95、单任务成本和回滚和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“先证明任务需要大模型，再用版本化 Prompt、评测集、人工反馈、成本与安全门禁管理迭代，避免只凭少数演示判断效果。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

## 5. Python：检索与任务评估

### 检索、Agent 或模型任务实现

```python
from dataclasses import dataclass
from statistics import mean

@dataclass
class EvalCase:
    case_id: str
    expected: str
    risk: str

def score_case(case: EvalCase, output: str, cited: bool, refused: bool) -> dict:
    checks = {
        "contains_expected": case.expected in output,
        "citation_supported": cited,
        "safe_refusal": refused if case.risk == "high" else True,
    }
    return {"case_id": case.case_id, "score": mean(checks.values()), "checks": checks}

eval_cases = [
    EvalCase("e1", "标准答案", "low"),
    EvalCase("e2", "需要澄清", "medium"),
    EvalCase("e3", "应转人工", "high"),
]

# 主题："大模型时代的数据工程"
# 覆盖常规、长尾、边界、对抗和拒答；模型、Prompt、知识库、工具和参数全部版本化。
```

### 标题专属数据与失败分层 SQL

```sql
-- 大模型时代的数据工程：分位对比诊断（版本 × 客户层级）
WITH scoped AS (
  SELECT
    account_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_product_event
  WHERE event_time >= DATE '2026-07-01'
    AND event_time <  DATE '2026-10-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '工单解决时长' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

示例代码只展示可测试结构。真实系统还需要模型服务、向量库、权限、日志、缓存、限流、敏感检查和人工反馈，不应把安全完全交给提示词。

## 6. 案例二：华东某 SaaS 客服团队

### 案例 2：华东某 SaaS 客服团队的“大模型时代的数据工程”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“大模型时代的数据工程”映射到“大模型、Prompt 与评估工程”中的评测，而不是泛泛讨论概念。
- **触发事件**：模型升级后离线准确率提升，但线上转人工率没有下降。
- **业务与数据范围**：真实会话、意图、回答、解决状态、人工标注、模型版本和成本。数据侧重点采集准确、引用、完整、拒答、采纳和任务完成，并与埋点平台、账号系统、订阅计费中的时间、状态和责任人信息对齐。
- **需要回答的问题**：离线、线上、人工和业务指标是否一致。
- **关键障碍**：评测集来自早期样本，标注只看流畅度，没有衡量问题是否真正解决。同时要防止多版本并行把表面指标带偏。
- **处理过程**：按意图和用户阶段重建评测集，加入任务完成、澄清轮次、转人工、引用和安全门槛。实施时把“模型更新保留灰度、对照、回滚和人工接管”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例评测发现复杂退款问题存在过度自信，并加入低置信度澄清与转人工。验收至少同时看主指标、准确、引用、完整、拒答、采纳和任务完成和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“先证明任务需要大模型，再用版本化 Prompt、评测集、人工反馈、成本与安全门禁管理迭代，避免只凭少数演示判断效果。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

## 7. 架构与工程链路

| 层次 | 本文建议 | 关键问题 | 验收证据 |
| --- | --- | --- | --- |
| 数据源 | 埋点平台、账号系统、订阅计费 | 权威源、更新频率、主键和权限 | 接口或表清单 |
| 接入 | 批、流或 CDC 按业务时延选择 | 重复、顺序、断点续传和回放 | 延迟与幂等测试 |
| 存储 | 按访问模式选择数据湖、数仓或 OLAP | 分区、格式、生命周期和成本 | 容量与查询评测 |
| 计算 | SQL、Spark、Flink 或 Python 服务 | 粒度、状态、资源和失败恢复 | 压测与执行计划 |
| 治理 | 元数据、质量、血缘、权限 | 责任、规则、影响分析和审计 | 规则结果与变更记录 |
| 服务 | 指标、API、看板或应用 | SLA、缓存、限流和版本 | 监控与验收样例 |

推荐把链路拆成六层：数据与知识准备、检索或特征、模型调用、工具执行、评估与审核、监控与反馈。每层都要有版本、日志和失败处理。Agent 工具调用应在服务端校验参数与权限，不能只依赖模型“自觉”。

## 8. 监控、成本与安全

- 监控请求量、延迟、错误码、超时、重试和缓存命中。
- 记录检索文档版本、模型版本、提示词版本和关键参数。
- 对失败分类：检索缺失、上下文过长、工具失败、权限拒绝、模型拒答、结果不合规。
- 设置单位任务成本、每租户预算和异常调用告警。
- 对提示注入、越权、敏感信息和危险动作做专门测试。
- 保留人工复核、转人工、回滚到旧模型和关闭工具的开关。

## 9. 第三个案例与上线验收

### 案例 3：华南某云服务商的“大模型时代的数据工程”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“大模型时代的数据工程”映射到“大模型、Prompt 与评估工程”中的任务，而不是泛泛讨论概念。
- **触发事件**：服务可用率看似达标，但客户投诉集中在短时高峰和部分区域。
- **业务与数据范围**：API 调用、错误码、延迟、可用区、客户等级、工单和故障公告。数据侧重点采集输入结构、输出结构、成功标准和失败路径，并与埋点平台、账号系统、订阅计费中的时间、状态和责任人信息对齐。
- **需要回答的问题**：模型输出是分类、生成、抽取、改写还是决策建议。
- **关键障碍**：平均可用率掩盖小客户长尾，重试请求放大调用量，故障和工单缺少统一事件号。同时要防止订阅时点口径混淆把表面指标带偏。
- **处理过程**：建立请求级 SLI 和客户影响面模型，按分位数、区域和客户层级监控，关联故障与工单。实施时把“评测集覆盖高频、长尾、边界、对抗、拒答和真实失败样本”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例项目识别出重试风暴和区域网络抖动，并调整告警阈值与降级策略。验收至少同时看主指标、输入结构、输出结构、成功标准和失败路径和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“先证明任务需要大模型，再用版本化 Prompt、评测集、人工反馈、成本与安全门禁管理迭代，避免只凭少数演示判断效果。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

| 验收项 | 最低要求 | 证据 |
| --- | --- | --- |
| 任务定义 | 输入输出和失败路径明确 | 产品说明、评测集 |
| 数据授权 | 来源、用途和权限可追溯 | 数据卡、授权记录 |
| 离线评估 | 覆盖常规、边界和拒答 | 评测报告 |
| 线上灰度 | 有对照组和护栏指标 | 实验或灰度记录 |
| 安全 | 越权、注入和敏感输出已测试 | 红队与审计报告 |
| 成本 | 单位请求预算和上限明确 | 账单与调用日志 |
| 运营 | 有反馈、复盘和回滚 | 周报、事故演练 |

1. 先写清“大模型时代的数据工程”的目标：先证明任务需要大模型，再用版本化 Prompt、评测集、人工反馈、成本与安全门禁管理迭代，避免只凭少数演示判断效果。
2. 专题检查：评测集覆盖高频、长尾、边界、对抗、拒答和真实失败样本
3. 专题检查：Prompt、模型、参数、知识、工具和代码全部版本化
4. 专题检查：离线指标必须与线上任务完成、人工采纳、成本和风险关联
5. 专题检查：模型更新保留灰度、对照、回滚和人工接管
6. 明确“大模型时代的数据工程”服务的使用者、决策动作和不做范围，并把成功标准写成可观察指标。
7. 为账号、设备、功能分别确认主键、时间和状态，画出从源系统到结果的链路。
8. 先做字段血缘和质量画像，检查账号设备映射有效、版本字段完整、机器流量剔除。
9. 用同周期基线和至少两个维度拆解问题，避免只比较一个异常周。
10. 抽取正常、异常和边界样本回查原始业务单据，记录抽样方法与结论。
11. 选择一种代码实现并保留参数、版本、执行日志和结果快照，确保别人可以复跑。
12. 上线前定义告警阈值、回滚条件和责任人；上线后按周观察主指标与护栏指标。
13. 复盘时区分数据问题、业务变化、方案偏差和外部因素，并把改进项转成有时限的任务。

```sql
  'subject' AS subject_key,
  stat_date,
  COUNT(*) AS row_cnt,
  COUNT(DISTINCT event_id) AS distinct_event_cnt,
  SUM(CASE WHEN event_id IS NULL THEN 1 ELSE 0 END) AS null_event_cnt,
  SUM(CASE WHEN event_time < business_time THEN 1 ELSE 0 END) AS time_reverse_cnt,
```

```python
from hashlib import sha256

import pandas as pd

SUBJECT = "大模型时代的数据工程"
BLOCKING_RULES = ["账号设备映射有效","版本字段完整","机器流量剔除"]


def validate_release(frame: pd.DataFrame, start: date, end: date) -> dict:
    scoped = frame.loc[
        frame["event_date"].between(pd.Timestamp(start), pd.Timestamp(end))
        & (frame["subject_key"] == "subject")
    ].copy()
    checks = {
        "has_rows": len(scoped) > 0,
        "event_id_unique": not scoped["event_id"].duplicated().any(),

        "event_time_present": scoped["event_time"].notna().all(),
        "scope_matches": scoped["subject_key"].nunique() == 1,
    }
    payload = f"{SUBJECT}|{start}|{end}|{len(scoped)}|{sorted(checks.items())}"
    return {
        "subject": SUBJECT,
        "rows": len(scoped),
        "checks": checks,
        "blocking_rules": BLOCKING_RULES,
        "release_allowed": all(checks.values()),
        "evidence_hash": sha256(payload.encode("utf-8")).hexdigest(),
    }
```
