# 学习数据分析与挖掘

> [!tip] 学习目标
> 把“学习数据分析与挖掘”放进招生线索、课程报名、学习行为、作业考试、续费退费、就业与教学质量管理，真正困难的通常不是解释名词，而是把它变成一条能被核对、能被复现、也能推动行动的工程链路。本文不追求堆满概念，而是围绕这个主题拆出业务对象、数据粒度、典型故障、代码验证和验收方式。

## 1. 先诊断，不要从收藏课程开始

围绕“学习数据分析与挖掘”，把当前水平分成四层：

| 层级 | 你应该能做到 | 自测方式 | 常见缺口 |
| --- | --- | --- | --- |
| 知道 | 用自己的话解释概念和边界 | 不看资料讲 2 分钟 | 只会背定义 |
| 会用 | 跟随示例跑通最小闭环 | 从原始数据得到结果 | 依赖复制代码 |
| 会判断 | 发现异常、解释取舍和限制 | 处理缺失、重复和边界样本 | 不知道何时不适用 |
| 会交付 | 独立完成项目并被别人复跑 | 写文档、代码和验收 | 没有质量与复盘 |

给自己打 0-3 分，并选择最低的一项作为第一周重点。不要同时学十个工具，先把学员、线索、课程与线索、试听、报名、开课之间的关系画出来。

## 2. 六周学习地图

| 周期 | 学习重点 | 最小交付 | 验收标准 |
| --- | --- | --- | --- |
| 第 1 周 | 概念、业务链路、术语 | 一张流程图和术语表 | 能解释“学习数据分析与挖掘”解决什么问题 |
| 第 2 周 | 数据模型与最小 SQL/Python | 可从原始数据算出两个指标 | 主键、时间、粒度能说明 |
| 第 3 周 | 质量与异常 | 三条规则和三类样例 | 能发现并解释一次错误 |
| 第 4 周 | 分析或工程实践 | 一个完整专题或小管道 | 结果能回到明细 |
| 第 5 周 | 性能、权限与发布 | 监控、成本或安全检查 | 知道失败后怎么处理 |

如果每天只有 45 分钟，可以拉长为 8-10 周，但每周都必须留下可检查的产物。阅读时间是输入，代码、验证和复盘才是掌握证据。

## 4. 练习项目：做一个可复现的闭环

项目题目可以定为：**在教育培训的脱敏数据中，围绕“学习数据分析与挖掘”分析一个流程问题，提出并验证一个改进假设。**

第一版只选择两个指标，例如线索转化率和到课率。按渠道、课程、班级拆分，要求：

1. 说明一行业务数据代表什么。
2. 写出指标和排除项。
3. 至少处理重复、缺失和时间边界。
4. 输出趋势、结构和一个异常案例。
5. 给出行动、负责人、观察周期和停止条件。

### 练习题：标题专属分析代码

```sql
-- 学习数据分析与挖掘：分位对比诊断（地区 × 渠道）
WITH scoped AS (
  SELECT
    student_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_education_event
  WHERE event_time >= DATE '2026-03-01'
    AND event_time <  DATE '2026-06-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '线索转化率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

### 练习题：质量检查

```python
# 学习数据分析与挖掘：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "学习数据分析与挖掘"
TOPIC_KEY = "subject"
RULE_ID = "rule_education_1yoig2i"
GUIDE_CHECKS = [
    "检查试听与正式课分开统计",
    "检查一人多号已合并",
    "检查刷课时长已剔除"
]
RULES = {
    "required_columns": ["event_id", "student_id", "event_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "student_id",
    "time_field": "event_time",
    "max_duplicate_rate": 0.0005,
    "max_null_rate": 0.005,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：检查试听与正式课分开统计；检查一人多号已合并；检查刷课时长已剔除
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

不要只运行代码。请故意破坏三件事：重复一个主键、删除一段日期、把状态改成未知值，确认质量检查能发现。再思考：数据量扩大十倍时，分组是否倾斜、查询是否全表扫描、日志是否足够、重跑是否幂等。

## 6. 工作案例一：华南某在线教育平台

### 案例 1：华南某在线教育平台的“学习数据分析与挖掘”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：课程完课率下降但用户投诉不多，产品团队怀疑课程难度和提醒策略有问题。本次讨论的重点是“学习数据分析与挖掘”，所以团队先要求把先冻结对象与时间窗写进项目目标，而不是直接开始做报表。
- **数据范围**：报名、直播观看、回放、作业提交、测验、教师反馈和续费。同时收集CRM、LMS、SIS、教务系统中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：后台播放时长包含挂机，课程章节中途改版，退费学员仍进入续费分母。进一步检查后发现，如果不先处理试听行为混入正式转化，“学习数据分析与挖掘”很容易被一个表面相关指标替代。
- **处理过程**：用有效播放与交互行为共同定义学习时长，建立课程版本和学员进度表，按章节分析流失点。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目定位到第 3 章作业难度和提醒频率不当，并建立章节级学习健康度预警。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“学习数据分析与挖掘”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

从案例中提取一个练习：用表中的检查项和 SQL 结构，写出你所在场景的对象、时间和指标。即使没有企业数据，也可以用公开数据集或合成数据完成，但必须说明数据来源和使用边界。

## 8. 反馈与复盘机制

学习不能只靠自我感觉。每周至少安排一次外部反馈：

- 让另一个人不看解释运行你的代码或打开作品。
- 请熟悉业务的人检查指标定义是否符合实际。
- 请工程同学检查数据量、成本、权限和失败处理。
- 用“结论能否回到明细”挑战你的分析。

| 复盘问题 | 记录方式 | 下一步 |
| --- | --- | --- |
| 哪一步卡住最久 | 时间日志 | 补概念还是补环境 |
| 哪个错误重复出现 | 错误清单 | 写成检查项或脚本 |
| 哪个结论无法验证 | 证据清单 | 补样本或改结论 |
| 哪个部分依赖复制 | 代码审查 | 从空白重写一次 |
| 哪个交付别人看不懂 | 同伴反馈 | 改文档和示例 |

- **和本主题的联系**：在“学习数据分析与挖掘”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

## 10. 作品集与能力证明

作品首页不要从工具列表开始，而要先写清问题和对象。推荐结构：背景与范围、数据与权限、流程图、关键代码、质量检查、结果与限制、复盘与下一步。每张图都应有标题和口径，每段结论都要能指出证据。

可以在简历中这样表达：

> 围绕【真实问题】完成“学习数据分析与挖掘”学习项目，使用【脱敏数据】建立【对象/粒度/指标】，实现【SQL/Python/质量规则】，通过【验证方法】发现【具体问题】，并沉淀【可复跑文档和看板】。

1. 明确“学习数据分析与挖掘”服务的使用者、决策动作和不做范围，并把成功标准写成可观察指标。
2. 为学员、线索、课程分别确认主键、时间和状态，画出从源系统到结果的链路。
3. 先做字段血缘和质量画像，检查试听与正式课分开统计、一人多号已合并、刷课时长已剔除。
4. 用同周期基线和至少两个维度拆解问题，避免只比较一个异常周。
5. 抽取正常、异常和边界样本回查原始业务单据，记录抽样方法与结论。
6. 选择一种代码实现并保留参数、版本、执行日志和结果快照，确保别人可以复跑。
7. 上线前定义告警阈值、回滚条件和责任人；上线后按周观察主指标与护栏指标。
8. 复盘时区分数据问题、业务变化、方案偏差和外部因素，并把改进项转成有时限的任务。

## 扩展实战：学习数据分析与挖掘的四个可执行案例

> [!info] 内容说明
> 以下内容围绕“学习数据分析与挖掘”补充四个相互独立的工作场景，分别落在权限、隐私与审计、链路断点与延迟、成本、质量与时效取舍、质量门禁与例外治理。它们使用公开方法、常见系统边界和脱敏数据构造，重点展示怎样从现象回到对象、流程、代码、行动与验收，而不是给出一个可以套用所有企业的标准答案。

| 案例 | 观察角度 | 首要对象 | 关键证据 | 失败时先停什么 |
| --- | --- | --- | --- | --- |
| 案例 4 | 权限、隐私与审计 | 学员 / 线索 | 分类分级、授权记录、字段血缘 | 高风险字段缺少授权、脱敏或审计时不进入分析环境，紧急访问必须到期自动回收 |
| 案例 5 | 链路断点与延迟 | 线索 / 课程 | 源端操作日志、CDC/批次水位、分区清单 | 无法证明数据完整的链路不进入正式发布，优先保留旧版本供下游读取 |
| 案例 6 | 成本、质量与时效取舍 | 课程 / 班级 | 执行计划、扫描量、文件数 | 任何优化都必须同时通过结果对账、延迟目标与成本预算，不能只展示一次最快执行 |
| 案例 7 | 质量门禁与例外治理 | 班级 / 学习事件 | 五类边界样本、规则命中率、趋势对比 | 影响资金、安全、监管或核心经营判断的关键规则失败时停止发布 |

这四个案例共享一条底线：先证明数据对象和链路能够解释，再讨论优化或决策。任何涉及资金、医疗安全、用户隐私、监管报送或核心权限的结果，都需要保留人工复核、阻断条件和回滚路径。

### 案例 4：学习数据分析与挖掘的最小权限与越权核查

一个看似普通的“学习数据分析与挖掘”需求，在跨系统核验后变成了围绕“权限、隐私与审计”的专项排查。触发排查的不是一次严重事故，而是连续几次解释不清的数据差异。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 让数据用途、最小字段、访问角色、加工产物、保存期限和撤回机制都可追溯。在本场景里，核心风险还包括退费后仍计入续费，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：学员、线索及其在报名前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注student_id与lead_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 分析结果本身可以访问，但派生字段、导出文件和临时表扩大了敏感数据范围，现有流程没有及时识别。初看时，LMS与SIS的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 分类分级、授权记录、字段血缘、访问日志、导出清单、脱敏规则和过期清理记录。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“销售顾问”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“学习数据分析与挖掘”的当前定义并记录版本；第二步用学员明细核对LMS到SIS的关联；第三步按地区与渠道做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察续费率和护栏指标线索转化率。
- **行动与护栏：** 按任务拆分数据集与角色，使用最小字段和临时授权，发布前检查派生表与导出是否出现敏感扩散。专题检查项“退费与订单状态一致”被写成发布门禁，高风险字段缺少授权、脱敏或审计时不进入分析环境，紧急访问必须到期自动回收。
- **失败路径：** 把“内网可访问”当成“业务已授权”，或者用永久大权限账号支撑临时分析。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“学习数据分析与挖掘”时，先验证退费与订单状态一致，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由销售顾问在明确时限内，根据续费率、线索转化率和退费与订单状态一致决定继续、回退、补查还是转人工。 若退费后仍计入续费或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。
### 案例 5：学习数据分析与挖掘从源事件到结果的长链路核查

一个看似普通的“学习数据分析与挖掘”需求，在跨系统核验后变成了围绕“链路断点与延迟”的专项排查。触发排查的不是一次严重事故，而是连续几次解释不清的数据差异。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 把业务发生时间、数据可见时间、任务完成时间和下游消费时间放到同一条证据链。在本场景里，核心风险还包括课程版本变化导致成绩不可比，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：线索、课程及其在开课前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注lead_id与course_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 结果表出现缺失或延迟，单看调度状态却显示成功，无法判断问题发生在源端、接入、计算还是服务层。初看时，SIS与教务系统的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 源端操作日志、CDC/批次水位、分区清单、任务参数、血缘关系、下游请求日志。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“班主任”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“学习数据分析与挖掘”的当前定义并记录版本；第二步用线索明细核对SIS到教务系统的关联；第三步按学员阶段与课程做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察学习时长和护栏指标到课率。
- **行动与护栏：** 按时间轴核对每一跳的输入输出计数与水位，先阻断错误结果扩散，再确定重跑范围和补数窗口。专题检查项“课程和班级历史关系可追溯”被写成发布门禁，无法证明数据完整的链路不进入正式发布，优先保留旧版本供下游读取。
- **失败路径：** 看到任务成功就立即补数，却没有确认重复、乱序和迟到事件。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“学习数据分析与挖掘”时，先验证课程和班级历史关系可追溯，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由班主任在明确时限内，根据学习时长、到课率和课程和班级历史关系可追溯决定继续、回退、补查还是转人工。 若课程版本变化导致成绩不可比或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。
### 案例 6：学习数据分析与挖掘的三方取舍实验

一个看似普通的“学习数据分析与挖掘”需求，在跨系统核验后变成了围绕“成本、质量与时效取舍”的专项排查。触发排查的不是一次严重事故，而是连续几次解释不清的数据差异。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 把新鲜度、正确性和成本分别量化，找到满足真实决策节奏的最低必要资源。在本场景里，核心风险还包括试听行为混入正式转化，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：课程、班级及其在学习前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注course_id与class_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 为追求更快结果不断增加资源，账单和重复计算同步上升，但业务真正使用的时效并没有显著改善。初看时，教务系统与直播课堂的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 执行计划、扫描量、文件数、峰值资源、单位产出成本、业务截止时间和质量门禁。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“讲师”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“学习数据分析与挖掘”的当前定义并记录版本；第二步用课程明细核对教务系统到直播课堂的关联；第三步按渠道与班级做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察线索转化率和护栏指标完课率。
- **行动与护栏：** 先按使用场景和截止时间分级，再比较预聚合、增量计算、缓存、并发调整和生命周期策略。专题检查项“试听与正式课分开统计”被写成发布门禁，任何优化都必须同时通过结果对账、延迟目标与成本预算，不能只展示一次最快执行。
- **失败路径：** 为了压缩账单关闭质量检查，或为了刷新频率重复计算无人消费的全量结果。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“学习数据分析与挖掘”时，先验证试听与正式课分开统计，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由讲师在明确时限内，根据线索转化率、完课率和试听与正式课分开统计决定继续、回退、补查还是转人工。 若试听行为混入正式转化或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。
### 案例 7：学习数据分析与挖掘上线前的质量门禁

一个看似普通的“学习数据分析与挖掘”需求，在跨系统核验后变成了围绕“质量门禁与例外治理”的专项排查。触发排查的不是一次严重事故，而是连续几次解释不清的数据差异。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 把关键质量规则、阈值、例外审批、阻断动作和复核人写入发布流程。在本场景里，核心风险还包括自动播放造成虚假学习时长，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：班级、学习事件及其在考试前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注class_id与learning_event_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 常规日期下结果看起来正常，一旦遇到空值、重复、跨期、撤销或历史归属，报表口径便无法解释。初看时，直播课堂与订单与支付系统的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 五类边界样本、规则命中率、趋势对比、豁免记录、责任人、阻断结果和复盘工单。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“教研”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“学习数据分析与挖掘”的当前定义并记录版本；第二步用班级明细核对直播课堂到订单与支付系统的关联；第三步按课程与地区做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察到课率和护栏指标续费率。
- **行动与护栏：** 从阻断、严重、观察三级建立规则，先修数据和逻辑，再决定是否允许有期限的业务例外。专题检查项“一人多号已合并”被写成发布门禁，影响资金、安全、监管或核心经营判断的关键规则失败时停止发布。
- **失败路径：** 一直调低阈值让报表通过，却没有处理规则为何持续失败。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“学习数据分析与挖掘”时，先验证一人多号已合并，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由教研在明确时限内，根据到课率、续费率和一人多号已合并决定继续、回退、补查还是转人工。 若自动播放造成虚假学习时长或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从学习数据分析与挖掘回到可核对明细

```sql
-- 学习数据分析与挖掘：源表与结果表按对象对账
WITH source_side AS (
  SELECT
    student_id AS entity_key,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum
  FROM fact_education_event
  WHERE event_time >= :start_date
    AND event_time <  :end_date
    AND subject_key = 'subject'
    AND is_deleted = 0
  GROUP BY student_id
),
result_side AS (
  SELECT
    student_id AS entity_key,
    event_cnt,
    metric_sum
  FROM fact_education_event_result
  WHERE stat_date BETWEEN :start_date AND :end_date
    AND subject_key = 'subject'
)
SELECT
  COALESCE(s.entity_key, r.entity_key) AS entity_key,
  s.event_cnt AS source_event_cnt,
  r.event_cnt AS result_event_cnt,
  s.metric_sum AS source_metric_sum,
  r.metric_sum AS result_metric_sum,
  COALESCE(r.metric_sum, 0) - COALESCE(s.metric_sum, 0) AS metric_diff
FROM source_side s
FULL OUTER JOIN result_side r USING (entity_key)
WHERE ABS(COALESCE(r.metric_sum, 0) - COALESCE(s.metric_sum, 0)) > 0
   OR COALESCE(s.event_cnt, 0) <> COALESCE(r.event_cnt, 0)
ORDER BY ABS(metric_diff) DESC;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把学习数据分析与挖掘的验收证据写成门禁

```python
import json
from pathlib import Path


def build_evidence_manifest(
    subject: str,
    scope: dict,
    checks: dict,
    samples: list[dict],
    owner: str,
) -> dict:
    failed = [name for name, passed in checks.items() if not passed]
    return {
        "subject": subject,
        "scope": scope,
        "checks": checks,
        "failed_checks": failed,
        "sample_evidence": samples[:5],
        "owner": owner,
        "decision": "block" if failed else "review",
        "manual_questions": [
            "每一项失败是否已回到原始记录",
            "对象、时间和状态是否与指标字典一致",
            "回滚或修复后是否重新完成对账",
        ],
    }


manifest = build_evidence_manifest(
    subject="学习数据分析与挖掘",
    scope={"systems": ["CRM","LMS","SIS","教务系统"]},
    checks={"definition_frozen": False, "reconciled": False},
    samples=[],
    owner="学员",
)
Path("release-evidence.json").write_text(
    json.dumps(manifest, ensure_ascii=False, indent=2),
    encoding="utf-8",
)
print(manifest["decision"])
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
