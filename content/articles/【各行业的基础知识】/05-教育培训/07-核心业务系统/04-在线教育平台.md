# 在线教育平台

> [!abstract] 场景速览
> “在线教育平台”在会议里常常只有一句话，落到数据团队却会展开成口径、主键、时间、状态、权限和交付责任。下面用一个从问题到上线的顺序展开，并穿插三个脱敏的复合案例，帮助你把标题里的知识迁移到真实项目。

## 1. “在线教育平台”在教育培训业务链中的位置

教育培训的核心流程可以概括为：线索 → 试听 → 报名 → 开课 → 学习 → 考试 → 续费 → 退费或毕业。参与角色包括学员、家长、销售顾问、班主任、讲师、教研、教务、产品与数据分析。“在线教育平台”通常不是一个孤立字段，而是连接业务动作、数据记录和管理决策的一层能力。

从数据团队视角，至少要回答四个问题：

1. **谁使用**：学员、家长、销售顾问、班主任分别要用它做判断、执行还是审计。
2. **对象是什么**：一行数据代表学员、一次事件、一个批次还是一天快照。
3. **流程在哪里变化**：通过试听、报名、开课、学习之间的状态和时间差定位问题。
4. **结果如何被采用**：谁在什么时间前采取行动，使用哪个指标观察改善或副作用。

一个合格的专题目标可以写成：

> 在【时间窗】和【授权数据范围】内，围绕“在线教育平台”，按【渠道、课程、班级】比较【学习时长】与【线索转化率】，定位一个可干预流程节点，并记录行动后的变化与边界。

## 2. 一张图看清角色、流程和数据

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 学员 | `student_id` | 线索 |
| 过程对象 | 线索 | `lead_id` | 试听 |
| 过程对象 | 课程 | `course_id` | 报名 |
| 结果对象 | 班级 | `class_id` | 开课 |
| 结果对象 | 学习事件 | `learning_event_id` | 学习 |
| 专题分析 | 在线教育平台 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

建模时不要先把所有系统字段堆进一张大表。更稳妥的做法是分别保留三类事实：

- **事件事实**：谁在什么时间做了动作，例如挂号、下单、开工、报警或学习。
- **状态快照**：对象在某一天的状态，例如会员等级、租约、账户余额或设备资产关系。
- **结果事实**：流程完成后的产出，例如结算金额、良品数量、签收结果或考试分数。

三者的粒度不同。把事件、快照和结果强行放在同一行，会让金额、数量和转化率在汇总时重复。若“在线教育平台”涉及状态变化，优先建立状态机；若涉及金额，先做借贷或收付平衡；若涉及对象归属，保留维度有效期。

## 3. 指标与口径：不要把相关数字直接当答案

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 线索转化率 | `COUNT(DISTINCT paid_student_id) / COUNT(DISTINCT valid_lead_id)`（视图字段 `lead_cvr`） | 渠道、课程、班级 | 不混用测试、撤销和跨期状态；与“在线教育平台”相关时还要补充主题筛选 |
| 到课率 | `COUNT(DISTINCT attended_session_id) / COUNT(DISTINCT scheduled_session_id)`（视图字段 `attendance_rate`） | 课程、班级、地区 | 不混用测试、撤销和跨期状态；与“在线教育平台”相关时还要补充主题筛选 |
| 完课率 | `COUNT(DISTINCT completed_student_id) / COUNT(DISTINCT enrolled_student_id)`（视图字段 `completion_rate`） | 班级、地区、学员阶段 | 不混用测试、撤销和跨期状态；与“在线教育平台”相关时还要补充主题筛选 |
| 续费率 | `COUNT(DISTINCT renewed_student_id) / COUNT(DISTINCT renewable_student_id)`（视图字段 `renewal_rate`） | 地区、学员阶段 | 不混用测试、撤销和跨期状态；与“在线教育平台”相关时还要补充主题筛选 |

指标字典至少应包含：中文名、英文编码、业务定义、计算公式、事实粒度、时间字段、对象范围、排除条件、负责人和验收样例。对于“在线教育平台”，还应注明它使用的是业务发生时间还是入仓时间，是否包含撤销、退费、测试、跨期和补录记录。

一个常见误区是看到学习时长变化就立即解释业务原因。更可靠的顺序是：

1. 检查数据覆盖和延迟是否变化。
2. 检查对象范围、状态映射和维度归属是否变化。
3. 按时间、结构和分组拆解贡献。
4. 回到明细寻找能解释变化的事件。
5. 如果已经采取行动，再评估行动带来的增量，而不是事后挑一个相关指标。

## 4. 工作案例：从现象到数据处理

### 案例 1：华东某职业教育机构的“在线教育平台”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：招生线索增长但报名转化下降，销售认为线索质量变差，市场团队认为跟进不及时。本次讨论的重点是“在线教育平台”，所以团队先要求把先冻结对象与时间窗写进项目目标，而不是直接开始做报表。
- **数据范围**：广告渠道、线索分配、首次联系、试听预约、试听到课、报价和支付。同时收集CRM、LMS、SIS、教务系统中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：重复线索未去重，销售首次联系时间存在手工修改，试听取消未回写 CRM。进一步检查后发现，如果不先处理试听行为混入正式转化，“在线教育平台”很容易被一个表面相关指标替代。
- **处理过程**：统一有效线索定义，建立线索-试听-订单事件链，按渠道、响应时长和顾问分组做转化分析。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目识别出响应超时和高意向课程错配两类问题，并形成线索质量与跟进质量双看板。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“在线教育平台”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

这个案例最关键的动作不是“跑一条 SQL”，而是把“在线教育平台”对应的业务对象和上下游系统放在同一张链路图上。链路图至少要标出源系统、事件时间、关联主键、状态变化、数据负责人和消费方。

## 5. SQL 示例：在统一口径下做分层诊断

下面的查询用于展示分析结构，表名和字段需映射到实际环境。重点是去重、范围筛选、基线比较和贡献率，而不是代码本身。

### 标题专属诊断 SQL

```sql
-- 在线教育平台：留存同期群诊断（学员阶段 × 课程）
WITH scoped AS (
  SELECT
    student_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_education_event
  WHERE event_time >= DATE '2026-04-01'
    AND event_time <  DATE '2026-07-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '到课率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

执行后要回答四类验证题：

- 结果总量能否与源系统或既有报表在相同口径下解释差异？
- 排名前几位的分组是否由少数超长、重复或补录记录造成？
- 缺失日期表现为“未发生”还是“未采集”，是否改变分母？
- 维度使用的是当时归属还是当前归属，跨期比较是否一致？

## 6. 第二个案例：跨系统、跨部门时怎样不失控

### 案例 2：华南某在线教育平台的“在线教育平台”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：课程完课率下降但用户投诉不多，产品团队怀疑课程难度和提醒策略有问题。本次讨论的重点是“在线教育平台”，所以团队先要求把先证明数据链路可信写进项目目标，而不是直接开始做报表。
- **数据范围**：报名、直播观看、回放、作业提交、测验、教师反馈和续费。同时收集CRM、LMS、SIS、教务系统中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：后台播放时长包含挂机，课程章节中途改版，退费学员仍进入续费分母。进一步检查后发现，如果不先处理自动播放造成虚假学习时长，“在线教育平台”很容易被一个表面相关指标替代。
- **处理过程**：用有效播放与交互行为共同定义学习时长，建立课程版本和学员进度表，按章节分析流失点。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目定位到第 3 章作业难度和提醒频率不当，并建立章节级学习健康度预警。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“在线教育平台”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

跨部门项目最容易在三个地方返工：业务术语没有冻结、主数据映射没有版本、验收时才发现权限不足。建议在开发前让业务负责人签字确认指标定义，让数据负责人确认粒度与主键，让安全负责人确认字段范围，让运维负责人确认发布与回滚窗口。

## 7. Python 示例：把数据质量变成发布门禁

### 可执行质量门禁

```python
# 在线教育平台：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "在线教育平台"
TOPIC_KEY = "subject"
RULE_ID = "rule_education_g9j13v"
GUIDE_CHECKS = [
    "检查试听与正式课分开统计",
    "检查一人多号已合并",
    "检查刷课时长已剔除"
]
RULES = {
    "required_columns": ["event_id", "student_id", "event_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "student_id",
    "time_field": "event_time",
    "max_duplicate_rate": 0.0006,
    "max_null_rate": 0.006,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：检查试听与正式课分开统计；检查一人多号已合并；检查刷课时长已剔除
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

这段代码适合放在离线任务完成之后、指标发布之前。真实环境还应从调度平台读取分区参数、把结果写入质量平台，并在关键规则失败时阻断下游。告警不是终点，工单中要记录影响资产、发现时间、临时处理、根因、修复时间和防复发动作。

## 8. 异常排查：从指标异常回到业务事件

| 检查项 | 推荐方法 | 失败动作 | 负责人 |
| --- | --- | --- | --- |
| 试听与正式课分开统计 | 唯一性 SQL + 抽样明细 | 阻断发布 | 学员 |
| 一人多号已合并 | 时间区间与状态机校验 | 阻断发布 | 家长 |
| 刷课时长已剔除 | 主数据有效期关联 | 告警并登记工单 | 销售顾问 |
| 退费与订单状态一致 | 金额或数量平衡校验 | 告警并登记工单 | 班主任 |
| 课程和班级历史关系可追溯 | 发布前阻断 + 责任人复核 | 告警并登记工单 | 讲师 |

围绕“在线教育平台”排查时，可以按以下顺序进行：

1. **影响面**：哪些指标、报表、接口或业务团队受影响，是否需要暂停对外发布。
2. **时间线**：源系统变更、任务发布、数据回刷、组织调整和业务活动分别发生在什么时候。
3. **数据链路**：上游是否延迟，分区是否缺失，主键是否重复，状态是否映射错误。
4. **业务证据**：抽取异常记录，与原始单据、操作日志、客服记录或现场系统核对。
5. **修复与复核**：明确补数范围、重跑粒度、回滚版本和验收样例。
6. **防复发**：把一次性排查升级为规则、监控、责任人和变更评审。

特别要注意：试听行为混入正式转化；自动播放造成虚假学习时长；同一学员多平台账号重复；退费后仍计入续费。这些问题如果不被单独标记，很容易被误写成业务趋势。

## 9. 第三个案例与延伸场景

### 案例 3：华北某 K12 教育集团的“在线教育平台”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：校区续费率差异明显，管理者希望区分教学质量、服务频次和学员基础的影响。本次讨论的重点是“在线教育平台”，所以团队先要求把把数据和业务动作一起复盘写进项目目标，而不是直接开始做报表。
- **数据范围**：入学测评、到课、作业、阶段考试、家长沟通、投诉和续费。同时收集CRM、LMS、SIS、教务系统中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：不同校区测评试卷不同，教师更换记录缺失，续费窗口按自然月而非课程结束日。进一步检查后发现，如果不先处理同一学员多平台账号重复，“在线教育平台”很容易被一个表面相关指标替代。
- **处理过程**：统一标准化成绩增量，建立学员-班级-教师关系有效期，按续费窗口比较同年级同班型。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目把续费差异拆成学习进步、出勤、服务触达和价格敏感四类因素。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。

### 扩展代码一：从在线教育平台回到可核对明细

```sql
-- 在线教育平台：状态链与时间间隔核查
WITH ordered_events AS (
  SELECT
    student_id AS entity_key,
    event_id,
    stage_code,
    event_time AS event_time,
    LAG(stage_code) OVER (
      PARTITION BY student_id
      ORDER BY event_time, event_id
    ) AS previous_stage,
    LAG(event_time) OVER (
      PARTITION BY student_id
      ORDER BY event_time, event_id
    ) AS previous_time
  FROM fact_education_event
  WHERE event_time >= :start_date
    AND event_time <  :end_date
    AND subject_key = 'subject'
)
SELECT
  entity_key,
  previous_stage,
  stage_code,
  event_time,
  event_time - previous_time AS elapsed,
  CASE
    WHEN event_time < previous_time THEN 'time_reversed'
    WHEN previous_stage = stage_code THEN 'duplicate_stage'
    WHEN previous_stage IS NULL THEN 'missing_prefix'
    ELSE 'candidate_delay'
  END AS exception_type
FROM ordered_events
WHERE event_time < previous_time
   OR previous_stage = stage_code
   OR event_time - previous_time > INTERVAL '1 hour'
ORDER BY exception_type, elapsed DESC;
```

### 扩展代码二：把在线教育平台的验收证据写成门禁

```python
import pandas as pd

KEY = ["entity_key", "event_id"]
AMOUNT_COLUMNS = ["metric_value", "adjustment_value"]


def reconcile(source: pd.DataFrame, result: pd.DataFrame) -> pd.DataFrame:
    def aggregate(frame: pd.DataFrame, side: str) -> pd.DataFrame:
        grouped = (
            frame.groupby("entity_key", dropna=False)
            .agg(
                event_cnt=("event_id", "nunique"),
                metric_sum=("metric_value", "sum"),
                adjustment_sum=("adjustment_value", "sum"),
            )
            .reset_index()
        )
        return grouped.rename(columns={
            "event_cnt": f"{side}_event_cnt",
            "metric_sum": f"{side}_metric_sum",
            "adjustment_sum": f"{side}_adjustment_sum",
        })

    compared = aggregate(source, "source").merge(
        aggregate(result, "result"),
        on="entity_key",
        how="outer",
    )
    compared["metric_diff"] = (
        compared["result_metric_sum"].fillna(0)
        - compared["source_metric_sum"].fillna(0)
    )
    compared["event_diff"] = (
        compared["result_event_cnt"].fillna(0)
        - compared["source_event_cnt"].fillna(0)
    )
    compared["exception"] = compared.apply(
        lambda row: "missing_result" if pd.isna(row["result_metric_sum"])
        else "unexpected_result" if pd.isna(row["source_metric_sum"])
        else "count_diff" if row["event_diff"] != 0
        else "amount_diff",
        axis=1,
    )
    return compared.loc[
        (compared["metric_diff"].abs() > 0) | (compared["event_diff"] != 0)
    ].sort_values("metric_diff", key=lambda values: values.abs(), ascending=False)
```
