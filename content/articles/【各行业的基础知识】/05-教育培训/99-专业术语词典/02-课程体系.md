# 课程体系

> [!abstract] 场景速览
> 讨论“课程体系”时，最容易犯的错误是直接从工具或报表开始。更有用的顺序是：先看业务链条，再找可观察指标，随后确认数据粒度，最后才选择 SQL、模型或平台组件。本文按这个顺序给出可执行方案和常见的失败样本。

## 1. “课程体系”在教育培训业务链中的位置

教育培训的核心流程可以概括为：线索 → 试听 → 报名 → 开课 → 学习 → 考试 → 续费 → 退费或毕业。参与角色包括学员、家长、销售顾问、班主任、讲师、教研、教务、产品与数据分析。“课程体系”通常不是一个孤立字段，而是连接业务动作、数据记录和管理决策的一层能力。

从数据团队视角，至少要回答四个问题：

1. **谁使用**：学员、家长、销售顾问、班主任分别要用它做判断、执行还是审计。
2. **对象是什么**：一行数据代表学员、一次事件、一个批次还是一天快照。
3. **流程在哪里变化**：通过试听、报名、开课、学习之间的状态和时间差定位问题。
4. **结果如何被采用**：谁在什么时间前采取行动，使用哪个指标观察改善或副作用。

一个合格的专题目标可以写成：

> 在【时间窗】和【授权数据范围】内，围绕“课程体系”，按【渠道、课程、班级】比较【线索转化率】与【到课率】，定位一个可干预流程节点，并记录行动后的变化与边界。

## 2. 一张图看清角色、流程和数据

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 学员 | `student_id` | 线索 |
| 过程对象 | 线索 | `lead_id` | 试听 |
| 过程对象 | 课程 | `course_id` | 报名 |
| 结果对象 | 班级 | `class_id` | 开课 |
| 结果对象 | 学习事件 | `learning_event_id` | 学习 |
| 专题分析 | 课程体系 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

建模时不要先把所有系统字段堆进一张大表。更稳妥的做法是分别保留三类事实：

- **事件事实**：谁在什么时间做了动作，例如挂号、下单、开工、报警或学习。
- **状态快照**：对象在某一天的状态，例如会员等级、租约、账户余额或设备资产关系。
- **结果事实**：流程完成后的产出，例如结算金额、良品数量、签收结果或考试分数。

三者的粒度不同。把事件、快照和结果强行放在同一行，会让金额、数量和转化率在汇总时重复。若“课程体系”涉及状态变化，优先建立状态机；若涉及金额，先做借贷或收付平衡；若涉及对象归属，保留维度有效期。

## 3. 指标与口径：不要把相关数字直接当答案

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 线索转化率 | `COUNT(DISTINCT paid_student_id) / COUNT(DISTINCT valid_lead_id)`（视图字段 `lead_cvr`） | 渠道、课程、班级 | 不混用测试、撤销和跨期状态；与“课程体系”相关时还要补充主题筛选 |
| 到课率 | `COUNT(DISTINCT attended_session_id) / COUNT(DISTINCT scheduled_session_id)`（视图字段 `attendance_rate`） | 课程、班级、地区 | 不混用测试、撤销和跨期状态；与“课程体系”相关时还要补充主题筛选 |
| 完课率 | `COUNT(DISTINCT completed_student_id) / COUNT(DISTINCT enrolled_student_id)`（视图字段 `completion_rate`） | 班级、地区、学员阶段 | 不混用测试、撤销和跨期状态；与“课程体系”相关时还要补充主题筛选 |
| 续费率 | `COUNT(DISTINCT renewed_student_id) / COUNT(DISTINCT renewable_student_id)`（视图字段 `renewal_rate`） | 地区、学员阶段 | 不混用测试、撤销和跨期状态；与“课程体系”相关时还要补充主题筛选 |

指标字典至少应包含：中文名、英文编码、业务定义、计算公式、事实粒度、时间字段、对象范围、排除条件、负责人和验收样例。对于“课程体系”，还应注明它使用的是业务发生时间还是入仓时间，是否包含撤销、退费、测试、跨期和补录记录。

一个常见误区是看到线索转化率变化就立即解释业务原因。更可靠的顺序是：

1. 检查数据覆盖和延迟是否变化。
2. 检查对象范围、状态映射和维度归属是否变化。
3. 按时间、结构和分组拆解贡献。
4. 回到明细寻找能解释变化的事件。
5. 如果已经采取行动，再评估行动带来的增量，而不是事后挑一个相关指标。

## 4. 工作案例：从现象到数据处理

### 案例 1：华东某职业教育机构的“课程体系”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：招生线索增长但报名转化下降，销售认为线索质量变差，市场团队认为跟进不及时。本次讨论的重点是“课程体系”，所以团队先要求把先冻结对象与时间窗写进项目目标，而不是直接开始做报表。
- **数据范围**：广告渠道、线索分配、首次联系、试听预约、试听到课、报价和支付。同时收集CRM、LMS、SIS、教务系统中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：重复线索未去重，销售首次联系时间存在手工修改，试听取消未回写 CRM。进一步检查后发现，如果不先处理试听行为混入正式转化，“课程体系”很容易被一个表面相关指标替代。
- **处理过程**：统一有效线索定义，建立线索-试听-订单事件链，按渠道、响应时长和顾问分组做转化分析。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目识别出响应超时和高意向课程错配两类问题，并形成线索质量与跟进质量双看板。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“课程体系”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

这个案例最关键的动作不是“跑一条 SQL”，而是把“课程体系”对应的业务对象和上下游系统放在同一张链路图上。链路图至少要标出源系统、事件时间、关联主键、状态变化、数据负责人和消费方。

## 5. SQL 示例：在统一口径下做分层诊断

下面的查询用于展示分析结构，表名和字段需映射到实际环境。重点是去重、范围筛选、基线比较和贡献率，而不是代码本身。

### 标题专属诊断 SQL

```sql
-- 课程体系：结构贡献诊断（渠道 × 班级）
WITH scoped AS (
  SELECT
    student_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_education_event
  WHERE event_time >= DATE '2026-01-01'
    AND event_time <  DATE '2026-04-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '完课率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

执行后要回答四类验证题：

- 结果总量能否与源系统或既有报表在相同口径下解释差异？
- 排名前几位的分组是否由少数超长、重复或补录记录造成？
- 缺失日期表现为“未发生”还是“未采集”，是否改变分母？
- 维度使用的是当时归属还是当前归属，跨期比较是否一致？

## 6. 第二个案例：跨系统、跨部门时怎样不失控

### 案例 2：华南某在线教育平台的“课程体系”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：课程完课率下降但用户投诉不多，产品团队怀疑课程难度和提醒策略有问题。本次讨论的重点是“课程体系”，所以团队先要求把先证明数据链路可信写进项目目标，而不是直接开始做报表。
- **数据范围**：报名、直播观看、回放、作业提交、测验、教师反馈和续费。同时收集CRM、LMS、SIS、教务系统中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：后台播放时长包含挂机，课程章节中途改版，退费学员仍进入续费分母。进一步检查后发现，如果不先处理自动播放造成虚假学习时长，“课程体系”很容易被一个表面相关指标替代。
- **处理过程**：用有效播放与交互行为共同定义学习时长，建立课程版本和学员进度表，按章节分析流失点。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目定位到第 3 章作业难度和提醒频率不当，并建立章节级学习健康度预警。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“课程体系”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

跨部门项目最容易在三个地方返工：业务术语没有冻结、主数据映射没有版本、验收时才发现权限不足。建议在开发前让业务负责人签字确认指标定义，让数据负责人确认粒度与主键，让安全负责人确认字段范围，让运维负责人确认发布与回滚窗口。

## 7. Python 示例：把数据质量变成发布门禁

### 可执行质量门禁

```python
# 课程体系：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "课程体系"
TOPIC_KEY = "subject"
RULE_ID = "rule_education_rjnew"
GUIDE_CHECKS = [
    "检查试听与正式课分开统计",
    "检查一人多号已合并",
    "检查刷课时长已剔除"
]
RULES = {
    "required_columns": ["event_id", "student_id", "event_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "student_id",
    "time_field": "event_time",
    "max_duplicate_rate": 0.0007,
    "max_null_rate": 0.002,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：检查试听与正式课分开统计；检查一人多号已合并；检查刷课时长已剔除
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

这段代码适合放在离线任务完成之后、指标发布之前。真实环境还应从调度平台读取分区参数、把结果写入质量平台，并在关键规则失败时阻断下游。告警不是终点，工单中要记录影响资产、发现时间、临时处理、根因、修复时间和防复发动作。

## 8. 异常排查：从指标异常回到业务事件

| 检查项 | 推荐方法 | 失败动作 | 负责人 |
| --- | --- | --- | --- |
| 试听与正式课分开统计 | 唯一性 SQL + 抽样明细 | 阻断发布 | 学员 |
| 一人多号已合并 | 时间区间与状态机校验 | 阻断发布 | 家长 |
| 刷课时长已剔除 | 主数据有效期关联 | 告警并登记工单 | 销售顾问 |
| 退费与订单状态一致 | 金额或数量平衡校验 | 告警并登记工单 | 班主任 |
| 课程和班级历史关系可追溯 | 发布前阻断 + 责任人复核 | 告警并登记工单 | 讲师 |

围绕“课程体系”排查时，可以按以下顺序进行：

1. **影响面**：哪些指标、报表、接口或业务团队受影响，是否需要暂停对外发布。
2. **时间线**：源系统变更、任务发布、数据回刷、组织调整和业务活动分别发生在什么时候。
3. **数据链路**：上游是否延迟，分区是否缺失，主键是否重复，状态是否映射错误。
4. **业务证据**：抽取异常记录，与原始单据、操作日志、客服记录或现场系统核对。
5. **修复与复核**：明确补数范围、重跑粒度、回滚版本和验收样例。
6. **防复发**：把一次性排查升级为规则、监控、责任人和变更评审。

特别要注意：试听行为混入正式转化；自动播放造成虚假学习时长；同一学员多平台账号重复；退费后仍计入续费。这些问题如果不被单独标记，很容易被误写成业务趋势。

## 9. 第三个案例与延伸场景

### 案例 3：西南某高校继续教育平台的“课程体系”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：线上培训项目报名人数多，但证书完成率和企业满意度偏低。本次讨论的重点是“课程体系”，所以团队先要求把把数据和业务动作一起复盘写进项目目标，而不是直接开始做报表。
- **数据范围**：企业报名、学员账号、课程资源、考试、证书、学习支持和满意度问卷。同时收集CRM、LMS、SIS、教务系统中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：企业管理员替员工报名导致身份错配，考试补考次数未记录，满意度样本严重偏斜。进一步检查后发现，如果不先处理同一学员多平台账号重复，“课程体系”很容易被一个表面相关指标替代。
- **处理过程**：建立企业项目-学员-课程三级模型，拆分首次通过和补考通过，补充分层抽样回访。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目发现移动端兼容和考试提醒不足是主要完成障碍，并推动课程包重构。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“课程体系”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

另外两个适合继续拆分的工作场景是：

- **华北某 K12 教育集团**：校区续费率差异明显，管理者希望区分教学质量、服务频次和学员基础的影响。可以先从入学测评、到课、作业、阶段考试、家长沟通、投诉和续费建立最小数据闭环，再围绕“课程体系”检查不同校区测评试卷不同，教师更换记录缺失，续费窗口按自然月而非课程结束日。

### 案例 4：课程体系失败后如何做到可恢复

某组织希望用“课程体系”支持一次真实决策，但在取数与评审阶段发现，一次错误发布已经产生结果，团队只能凭负责人记忆寻找影响范围，补数后仍无法确认是否重复或遗漏。这个案例因此从问题定义重新开始。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 让错误输入、处理版本、影响分区和恢复结果都能被独立回放和审计。在本场景里，核心风险还包括试听行为混入正式转化，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：学员、线索及其在线索前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注student_id与lead_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 一次错误发布已经产生结果，团队只能凭负责人记忆寻找影响范围，补数后仍无法确认是否重复或遗漏。初看时，教务系统与直播课堂的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 运行参数、代码版本、输入快照、输出摘要、受影响分区、回滚记录和补数对账。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“学员”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“课程体系”的当前定义并记录版本；第二步用学员明细核对教务系统到直播课堂的关联；第三步按渠道与班级做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察线索转化率和护栏指标完课率。

- **失败路径：** 直接覆盖目标表，或者把所有分区全部重跑以求省事。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“课程体系”时，先验证试听与正式课分开统计，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

### 扩展代码一：从课程体系回到可核对明细

```sql
-- 课程体系：发布前质量画像
SELECT
  'subject' AS subject_key,
  stat_date,
  COUNT(*) AS row_cnt,
  COUNT(DISTINCT event_id) AS distinct_event_cnt,
  SUM(CASE WHEN event_id IS NULL THEN 1 ELSE 0 END) AS null_event_cnt,
  SUM(CASE WHEN event_time < business_time THEN 1 ELSE 0 END) AS time_reverse_cnt,
  SUM(CASE WHEN status NOT IN ('valid', 'completed', 'cancelled') THEN 1 ELSE 0 END) AS invalid_status_cnt,
  ROUND(COUNT(*) * 1.0 / NULLIF(COUNT(DISTINCT event_id), 0), 4) AS duplication_ratio
FROM fact_education_event
WHERE stat_date BETWEEN :start_date AND :end_date
GROUP BY stat_date
HAVING SUM(CASE WHEN event_id IS NULL THEN 1 ELSE 0 END) > 0
    OR SUM(CASE WHEN event_time < business_time THEN 1 ELSE 0 END) > 0
    OR COUNT(*) <> COUNT(DISTINCT event_id)
ORDER BY stat_date;

-- 至少人工核对一次：试听与正式课分开统计；一人多号已合并；刷课时长已剔除。
```

### 扩展代码二：把课程体系的验收证据写成门禁

```python
from datetime import date
from hashlib import sha256

import pandas as pd

SUBJECT = "课程体系"
BLOCKING_RULES = ["试听与正式课分开统计","一人多号已合并","刷课时长已剔除"]


def validate_release(frame: pd.DataFrame, start: date, end: date) -> dict:
    scoped = frame.loc[
        frame["event_date"].between(pd.Timestamp(start), pd.Timestamp(end))
        & (frame["subject_key"] == "subject")
    ].copy()
    checks = {
        "has_rows": len(scoped) > 0,
        "event_id_unique": not scoped["event_id"].duplicated().any(),
        "entity_key_complete": scoped["entity_key"].notna().all(),
        "event_time_present": scoped["event_time"].notna().all(),
        "scope_matches": scoped["subject_key"].nunique() == 1,
    }
    payload = f"{SUBJECT}|{start}|{end}|{len(scoped)}|{sorted(checks.items())}"
    return {
        "subject": SUBJECT,
        "rows": len(scoped),
        "checks": checks,
        "blocking_rules": BLOCKING_RULES,
        "release_allowed": all(checks.values()),
        "evidence_hash": sha256(payload.encode("utf-8")).hexdigest(),
    }
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
