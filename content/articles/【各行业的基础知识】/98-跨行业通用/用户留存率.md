# 用户留存率

> [!tip] 分析目标
> 讨论“用户留存率”时，最容易犯的错误是直接从工具或报表开始。更有用的顺序是：先看业务链条，再找可观察指标，随后确认数据粒度，最后才选择 SQL、模型或平台组件。本文按这个顺序给出可执行方案和常见的失败样本。

## 1. 把主题翻译成可验证的问题

“用户留存率”不能直接等同于“做一张趋势图”。一个可执行的分析问题至少包含对象、时间、比较基准和行动：

> 在【观察周期】内，对【有效对象】按【时间、业务类型、地区】比较【转化率】与【处理时长】，判断变化来自结构、行为还是数据口径，并验证【策略动作】是否带来可解释的增量。

在跨行业通用场景中，用户行为、交易结果和策略曝光经常来自不同系统。先画数据流：

业务系统 → CRM → ERP → 数据仓库 → 调度平台 → BI

图中至少要有三个标记：业务事件发生时间、数据可见时间、策略或行动时间。只有三者分开，后续才能判断问题发生在业务、链路还是观察窗口。

## 2. 指标定义与分母检查

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 业务量 | `COUNT(DISTINCT event_id)`（视图字段 `event_cnt`） | 时间、业务类型、地区 | 不混用测试、撤销和跨期状态；与“用户留存率”相关时还要补充主题筛选 |
| 转化率 | `COUNT(DISTINCT success_id) / COUNT(DISTINCT eligible_id)`（视图字段 `conversion_rate`） | 业务类型、地区、对象层级 | 不混用测试、撤销和跨期状态；与“用户留存率”相关时还要补充主题筛选 |
| 处理时长 | `AVG(completed_at - started_at)`（视图字段 `processing_time`） | 地区、对象层级、来源渠道 | 不混用测试、撤销和跨期状态；与“用户留存率”相关时还要补充主题筛选 |
| 质量率 | `COUNT(DISTINCT valid_id) / COUNT(DISTINCT checked_id)`（视图字段 `quality_rate`） | 对象层级、来源渠道 | 不混用测试、撤销和跨期状态；与“用户留存率”相关时还要补充主题筛选 |

针对“用户留存率”，建议分别定义诊断指标、结果指标和护栏指标：

- **诊断指标**用于定位流程，例如曝光、有效访问、符合条件对象数和异常节点。
- **结果指标**用于判断是否改善，例如转化、留存、客单、毛利或处理时长。
- **护栏指标**用于防止局部优化伤害整体，例如退款、投诉、成本、公平性和长期留存。

每次计算都问四个问题：分母是谁、对象何时进入分母、例外状态怎么处理、窗口是否足够覆盖行为完成。尤其是口径未冻结；主数据不一致；异常值未处理，任何一项没有解释清楚，指标都可能“看起来合理但无法决策”。

## 3. 方法选择：描述、诊断、预测还是因果

| 目标 | 适合的方法 | 需要的证据 | 不要混淆 |
| --- | --- | --- | --- |
| 描述现状 | 趋势、结构、同期群 | 完整口径、稳定时间窗 | 描述不等于原因 |
| 定位异常 | 分层、贡献度、漏斗、异常检测 | 原始事件、基线和质量检查 | 排名靠前不等于因果 |
| 预测未来 | 时间序列、回归、机器学习 | 时间切分验证、误差成本 | 离线准确率不等于业务收益 |
| 评估策略 | A/B、灰度、准实验 | 对照组、样本量、护栏指标 | 上线前后对比容易混入季节和选择偏差 |

如果问题只是“发生了什么”，先别急着建模；如果问题涉及“采取某策略会怎样”，就必须讨论反事实和识别条件。围绕“用户留存率”，应把观察分析、预测和因果评估的产出分开标注。

## 4. 案例一：某全国连锁服务企业

### 案例 1：某全国连锁服务企业的“用户留存率”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：管理层发现营业额增长但利润下降，跨部门对原因判断不一致。本次讨论的重点是“用户留存率”，所以团队先要求把先冻结对象与时间窗写进项目目标，而不是直接开始做报表。
- **数据范围**：门店、订单、客户、活动、成本、人员和工单数据。同时收集业务系统、CRM、ERP、数据仓库中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：收入与成本时间归属不同，活动优惠分摊不完整，组织调整导致门店历史归属变化。进一步检查后发现，如果不先处理口径未冻结，“用户留存率”很容易被一个表面相关指标替代。
- **处理过程**：统一经营分析粒度，建立收入成本桥接和门店维度有效期，按地区、业态和活动拆解。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目把利润变化拆成价格、数量、成本和结构四部分，并形成月度复盘模板。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“用户留存率”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

落地时建议先把一个总指标拆成可行动的树：

```text
用户留存率｜转化率结果偏离
├── 先验真伪：主键唯一是否有批次级证据
├── 再看规模：业务对象数量与处理时长是否同向变化
├── 结构定位：时间 → 业务类型 → 地区
├── 链路时点：业务系统 → CRM → ERP
└── 行动出口：由业务负责人确认口径并安排回查
```

如果某一分支变化最大，再进入下一层，而不是一开始就按十几个维度切碎。每个分层结果都应同时报告样本量，避免小样本的极端比例抢走注意力。

## 5. SQL：计算趋势、结构和贡献度

### 趋势、结构与贡献度诊断

```sql
-- 用户留存率：结构贡献诊断（业务类型 × 对象层级）
WITH scoped AS (
  SELECT
    entity_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_business_event
  WHERE event_time >= DATE '2026-01-01'
    AND event_time <  DATE '2026-04-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '质量率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

示例 SQL 只表达计算逻辑。实际实施应加入分区条件、业务状态过滤、时区和主题范围，并在结果中保留口径版本。

- **关键障碍**：问题只有告警没有分级，跨团队责任边界不清，同类问题没有根因标签。进一步检查后发现，如果不先处理主数据不一致，“用户留存率”很容易被一个表面相关指标替代。

当业务方要求“解释为什么下降”时，可以按下面顺序回答：

1. 先确认下降是否真实存在，排查采集、任务、维表和状态映射。
2. 把变化拆成对象数量、行为强度和结构占比。
3. 找到贡献最大的分组，但保留其他分组的抵消效应。
4. 抽取正负样本回查业务事件和操作日志。
5. 把尚不能证明的解释标为假设，并设计下一轮验证。

## 7. 代码验证：专题指标、实验或模型

### 专题验证代码

```sql
-- 主题：用户留存率
-- 示例表名和字段名用于说明建模方法，落地时请映射到企业现有数仓。
WITH scoped AS (
  SELECT
    e.event_id,
    e.entity_id,
    e.event_time AS event_time,
    e.stage_code,
    e.dimension_value AS analysis_dim,
    e.status,
    COALESCE(e.metric_value, 0) AS metric_value,
    ROW_NUMBER() OVER (
      PARTITION BY e.event_id
      ORDER BY e.updated_at DESC
    ) AS version_no
  FROM fact_business_event e
  WHERE e.event_time >= DATE '2026-03-01'
    AND e.event_time <  DATE '2026-06-01'
    AND e.subject_name = '用户留存率'
    AND e.is_deleted = 0
),
dedup AS (
  SELECT *
  FROM scoped
  WHERE version_no = 1
),
baseline AS (
  SELECT
    analysis_dim,
    COUNT(DISTINCT entity_id) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    AVG(metric_value) AS avg_metric,
    MIN(event_time) AS first_seen_at,
    MAX(event_time) AS last_seen_at
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY analysis_dim
)
SELECT
  analysis_dim AS analysis_dimension,
  entity_cnt,
  event_cnt,
  ROUND(avg_metric, 4) AS conversion_rate,
  first_seen_at,
  last_seen_at,
  ROUND(event_cnt * 1.0 / NULLIF(SUM(event_cnt) OVER (), 0), 4) AS contribution_ratio
FROM baseline
ORDER BY event_cnt DESC;
```

## 8. 异常、偏差与常见误区

- **辛普森悖论**：总体改善但每个分组都变差，可能由对象结构变化造成。
- **幸存者偏差**：只分析完成流程的对象，忽略中途流失和中止。
- **分母漂移**：渠道口径、登录状态、版本或活动范围变化，改变可比性。
- **回传延迟**：当天数据未回补，导致近期效果被系统性低估。
- **多重比较**：反复寻找显著分组，实际只是随机波动。
- **行动偏差**：只报告支持既定方案的结果，忽略反例和护栏指标。

围绕“用户留存率”，应预先写出至少三条反例检查。比如结论是否能回到明细、指标是否在同一对象和同一时间窗内计算，以及 数据质量异常是否与业务变化分开。

## 10. 交付物与工作节奏

| 交付物 | 应包含 | 质量要求 |
| --- | --- | --- |
| 问题说明 | 背景、对象、时间、成功标准 | 一句话能说明要改变什么 |
| 指标字典 | 公式、粒度、排除项、负责人 | 换人计算能得到同一结果 |
| 分析代码 | SQL/Python、参数、日志 | 可复跑，不依赖手工改数 |
| 验证记录 | 抽样、对账、边界样本 | 结论能回到原始事件 |
| 决策材料 | 结论、证据、限制、行动 | 区分事实、解释和建议 |
| 复盘记录 | 结果、副作用、下一步 | 有观察周期和停止条件 |

1. 明确“用户留存率”服务的使用者、决策动作和不做范围，并把成功标准写成可观察指标。
2. 为业务对象、事件、流程分别确认主键、时间和状态，画出从源系统到结果的链路。
3. 先做字段血缘和质量画像，检查主键唯一、时间完整、枚举受控。
4. 用同周期基线和至少两个维度拆解问题，避免只比较一个异常周。
5. 抽取正常、异常和边界样本回查原始业务单据，记录抽样方法与结论。
6. 选择一种代码实现并保留参数、版本、执行日志和结果快照，确保别人可以复跑。
7. 上线前定义告警阈值、回滚条件和责任人；上线后按周观察主指标与护栏指标。
8. 复盘时区分数据问题、业务变化、方案偏差和外部因素，并把改进项转成有时限的任务。

### 扩展代码一：从用户留存率回到可核对明细

```sql
-- 用户留存率：发布前质量画像
SELECT
  'subject' AS subject_key,
  stat_date,
  COUNT(*) AS row_cnt,
  COUNT(DISTINCT event_id) AS distinct_event_cnt,
  SUM(CASE WHEN event_id IS NULL THEN 1 ELSE 0 END) AS null_event_cnt,
  SUM(CASE WHEN event_time < business_time THEN 1 ELSE 0 END) AS time_reverse_cnt,
  SUM(CASE WHEN status NOT IN ('valid', 'completed', 'cancelled') THEN 1 ELSE 0 END) AS invalid_status_cnt,
  ROUND(COUNT(*) * 1.0 / NULLIF(COUNT(DISTINCT event_id), 0), 4) AS duplication_ratio
FROM fact_business_event
WHERE stat_date BETWEEN :start_date AND :end_date
GROUP BY stat_date
HAVING SUM(CASE WHEN event_id IS NULL THEN 1 ELSE 0 END) > 0
    OR SUM(CASE WHEN event_time < business_time THEN 1 ELSE 0 END) > 0
    OR COUNT(*) <> COUNT(DISTINCT event_id)
ORDER BY stat_date;

-- 至少人工核对一次：主键唯一；时间完整；枚举受控。
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把用户留存率的验收证据写成门禁

```python
import pandas as pd

KEY = ["entity_key", "event_id"]
AMOUNT_COLUMNS = ["metric_value", "adjustment_value"]


def reconcile(source: pd.DataFrame, result: pd.DataFrame) -> pd.DataFrame:
    def aggregate(frame: pd.DataFrame, side: str) -> pd.DataFrame:
        grouped = (
            frame.groupby("entity_key", dropna=False)
            .agg(
                event_cnt=("event_id", "nunique"),
                metric_sum=("metric_value", "sum"),
                adjustment_sum=("adjustment_value", "sum"),
            )
            .reset_index()
        )
        return grouped.rename(columns={
            "event_cnt": f"{side}_event_cnt",
            "metric_sum": f"{side}_metric_sum",
            "adjustment_sum": f"{side}_adjustment_sum",
        })

    compared = aggregate(source, "source").merge(
        aggregate(result, "result"),
        on="entity_key",
        how="outer",
    )
    compared["metric_diff"] = (
        compared["result_metric_sum"].fillna(0)
        - compared["source_metric_sum"].fillna(0)
    )
    compared["event_diff"] = (
        compared["result_event_cnt"].fillna(0)
        - compared["source_event_cnt"].fillna(0)
    )
    compared["exception"] = compared.apply(
        lambda row: "missing_result" if pd.isna(row["result_metric_sum"])
        else "unexpected_result" if pd.isna(row["source_metric_sum"])
        else "count_diff" if row["event_diff"] != 0
        else "amount_diff",
        axis=1,
    )
    return compared.loc[
        (compared["metric_diff"].abs() > 0) | (compared["event_diff"] != 0)
    ].sort_values("metric_diff", key=lambda values: values.abs(), ascending=False)
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。

| 验证面 | 发布前问题 | 证据 | 不通过时 |
