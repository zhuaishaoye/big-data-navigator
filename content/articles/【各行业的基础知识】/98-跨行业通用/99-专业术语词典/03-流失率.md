# 流失率

> [!abstract] 场景速览
> “流失率”既可能是业务概念，也可能是技术方案，还可能是岗位能力。判断学习是否有效，要看能否在需求澄清、业务事件采集、指标计算、经营分析、流程优化和结果复盘中做出一个可复现的小闭环。本文用多个案例展示从需求到数据结果，再回到业务行动和复盘的完整路径。

## 1. “流失率”在跨行业通用业务链中的位置

跨行业通用的核心流程可以概括为：需求 → 采集 → 加工 → 分析 → 决策 → 行动 → 复盘。参与角色包括业务负责人、产品与运营、数据开发、数据分析、财务、风控、技术运维。“流失率”通常不是一个孤立字段，而是连接业务动作、数据记录和管理决策的一层能力。

从数据团队视角，至少要回答四个问题：

1. **谁使用**：业务负责人、产品与运营、数据开发、数据分析分别要用它做判断、执行还是审计。
2. **对象是什么**：一行数据代表业务对象、一次事件、一个批次还是一天快照。
3. **流程在哪里变化**：通过采集、加工、分析、决策之间的状态和时间差定位问题。
4. **结果如何被采用**：谁在什么时间前采取行动，使用哪个指标观察改善或副作用。

一个合格的专题目标可以写成：

> 在【时间窗】和【授权数据范围】内，围绕“流失率”，按【时间、业务类型、地区】比较【转化率】与【处理时长】，定位一个可干预流程节点，并记录行动后的变化与边界。

## 2. 一张图看清角色、流程和数据

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 业务对象 | `entity_id` | 需求 |
| 过程对象 | 事件 | `event_id` | 采集 |
| 过程对象 | 流程 | `process_id` | 加工 |
| 结果对象 | 组织 | `org_id` | 分析 |
| 结果对象 | 指标结果 | `metric_id` | 决策 |
| 专题分析 | 流失率 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

建模时不要先把所有系统字段堆进一张大表。更稳妥的做法是分别保留三类事实：

- **事件事实**：谁在什么时间做了动作，例如挂号、下单、开工、报警或学习。
- **状态快照**：对象在某一天的状态，例如会员等级、租约、账户余额或设备资产关系。
- **结果事实**：流程完成后的产出，例如结算金额、良品数量、签收结果或考试分数。

三者的粒度不同。把事件、快照和结果强行放在同一行，会让金额、数量和转化率在汇总时重复。若“流失率”涉及状态变化，优先建立状态机；若涉及金额，先做借贷或收付平衡；若涉及对象归属，保留维度有效期。

## 3. 指标与口径：不要把相关数字直接当答案

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 业务量 | `COUNT(DISTINCT event_id)`（视图字段 `event_cnt`） | 时间、业务类型、地区 | 不混用测试、撤销和跨期状态；与“流失率”相关时还要补充主题筛选 |
| 转化率 | `COUNT(DISTINCT success_id) / COUNT(DISTINCT eligible_id)`（视图字段 `conversion_rate`） | 业务类型、地区、对象层级 | 不混用测试、撤销和跨期状态；与“流失率”相关时还要补充主题筛选 |
| 处理时长 | `AVG(completed_at - started_at)`（视图字段 `processing_time`） | 地区、对象层级、来源渠道 | 不混用测试、撤销和跨期状态；与“流失率”相关时还要补充主题筛选 |
| 质量率 | `COUNT(DISTINCT valid_id) / COUNT(DISTINCT checked_id)`（视图字段 `quality_rate`） | 对象层级、来源渠道 | 不混用测试、撤销和跨期状态；与“流失率”相关时还要补充主题筛选 |

指标字典至少应包含：中文名、英文编码、业务定义、计算公式、事实粒度、时间字段、对象范围、排除条件、负责人和验收样例。对于“流失率”，还应注明它使用的是业务发生时间还是入仓时间，是否包含撤销、退费、测试、跨期和补录记录。

一个常见误区是看到转化率变化就立即解释业务原因。更可靠的顺序是：

1. 检查数据覆盖和延迟是否变化。
2. 检查对象范围、状态映射和维度归属是否变化。
3. 按时间、结构和分组拆解贡献。
4. 回到明细寻找能解释变化的事件。
5. 如果已经采取行动，再评估行动带来的增量，而不是事后挑一个相关指标。

## 4. 工作案例：从现象到数据处理

### 案例 1：某集团数据治理办公室的“流失率”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：多个业务域的数据质量问题反复出现，但整改责任和优先级难以落实。本次讨论的重点是“流失率”，所以团队先要求把先冻结对象与时间窗写进项目目标，而不是直接开始做报表。
- **数据范围**：数据资产、质量问题、责任团队、工单、修复记录和影响范围。同时收集业务系统、CRM、ERP、数据仓库中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：问题只有告警没有分级，跨团队责任边界不清，同类问题没有根因标签。进一步检查后发现，如果不先处理口径未冻结，“流失率”很容易被一个表面相关指标替代。
- **处理过程**：建立问题分级、根因分类、负责人和时限，按影响范围和复发率排序。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目把治理从工具告警变成闭环机制，并为季度评审提供可量化依据。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“流失率”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

这个案例最关键的动作不是“跑一条 SQL”，而是把“流失率”对应的业务对象和上下游系统放在同一张链路图上。链路图至少要标出源系统、事件时间、关联主键、状态变化、数据负责人和消费方。

## 5. SQL 示例：在统一口径下做分层诊断

下面的查询用于展示分析结构，表名和字段需映射到实际环境。重点是去重、范围筛选、基线比较和贡献率，而不是代码本身。

### 标题专属诊断 SQL

```sql
-- 流失率：留存同期群诊断（业务类型 × 对象层级）
WITH scoped AS (
  SELECT
    entity_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_business_event
  WHERE event_time >= DATE '2026-08-01'
    AND event_time <  DATE '2026-11-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '质量率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

执行后要回答四类验证题：

- 结果总量能否与源系统或既有报表在相同口径下解释差异？
- 排名前几位的分组是否由少数超长、重复或补录记录造成？
- 缺失日期表现为“未发生”还是“未采集”，是否改变分母？
- 维度使用的是当时归属还是当前归属，跨期比较是否一致？

## 6. 第二个案例：跨系统、跨部门时怎样不失控

### 案例 2：某全国连锁服务企业的“流失率”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：管理层发现营业额增长但利润下降，跨部门对原因判断不一致。本次讨论的重点是“流失率”，所以团队先要求把先证明数据链路可信写进项目目标，而不是直接开始做报表。
- **数据范围**：门店、订单、客户、活动、成本、人员和工单数据。同时收集业务系统、CRM、ERP、数据仓库中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：收入与成本时间归属不同，活动优惠分摊不完整，组织调整导致门店历史归属变化。进一步检查后发现，如果不先处理主数据不一致，“流失率”很容易被一个表面相关指标替代。
- **处理过程**：统一经营分析粒度，建立收入成本桥接和门店维度有效期，按地区、业态和活动拆解。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目把利润变化拆成价格、数量、成本和结构四部分，并形成月度复盘模板。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“流失率”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

跨部门项目最容易在三个地方返工：业务术语没有冻结、主数据映射没有版本、验收时才发现权限不足。建议在开发前让业务负责人签字确认指标定义，让数据负责人确认粒度与主键，让安全负责人确认字段范围，让运维负责人确认发布与回滚窗口。

## 7. Python 示例：把数据质量变成发布门禁

### 可执行质量门禁

```python
# 流失率：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "流失率"
TOPIC_KEY = "subject"
RULE_ID = "rule_general_ptlikn"
GUIDE_CHECKS = [
    "检查主键唯一",
    "检查时间完整",
    "检查枚举受控"
]
RULES = {
    "required_columns": ["event_id", "entity_id", "event_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "entity_id",
    "time_field": "event_time",
    "max_duplicate_rate": 0.0007,
    "max_null_rate": 0.003,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：检查主键唯一；检查时间完整；检查枚举受控
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

这段代码适合放在离线任务完成之后、指标发布之前。真实环境还应从调度平台读取分区参数、把结果写入质量平台，并在关键规则失败时阻断下游。告警不是终点，工单中要记录影响资产、发现时间、临时处理、根因、修复时间和防复发动作。

## 8. 异常排查：从指标异常回到业务事件

| 检查项 | 推荐方法 | 失败动作 | 负责人 |
| --- | --- | --- | --- |
| 主键唯一 | 唯一性 SQL + 抽样明细 | 阻断发布 | 业务负责人 |
| 时间完整 | 时间区间与状态机校验 | 阻断发布 | 产品与运营 |
| 枚举受控 | 主数据有效期关联 | 告警并登记工单 | 数据开发 |
| 金额与数量关系合理 | 金额或数量平衡校验 | 告警并登记工单 | 数据分析 |
| 指标口径版本可追溯 | 发布前阻断 + 责任人复核 | 告警并登记工单 | 财务 |

围绕“流失率”排查时，可以按以下顺序进行：

1. **影响面**：哪些指标、报表、接口或业务团队受影响，是否需要暂停对外发布。
2. **时间线**：源系统变更、任务发布、数据回刷、组织调整和业务活动分别发生在什么时候。
3. **数据链路**：上游是否延迟，分区是否缺失，主键是否重复，状态是否映射错误。
4. **业务证据**：抽取异常记录，与原始单据、操作日志、客服记录或现场系统核对。
5. **修复与复核**：明确补数范围、重跑粒度、回滚版本和验收样例。
6. **防复发**：把一次性排查升级为规则、监控、责任人和变更评审。

特别要注意：口径未冻结；主数据不一致；异常值未处理；上下游延迟。这些问题如果不被单独标记，很容易被误写成业务趋势。

## 9. 第三个案例与延伸场景

### 案例 3：某快速扩张的运营团队的“流失率”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：新策略上线后短期指标提升，但两个月后用户投诉和退款增加。本次讨论的重点是“流失率”，所以团队先要求把把数据和业务动作一起复盘写进项目目标，而不是直接开始做报表。
- **数据范围**：策略曝光、用户分层、转化、留存、退款、投诉和客服记录。同时收集业务系统、CRM、ERP、数据仓库中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：只观察短期转化，没有设置对照组，退款和投诉没有纳入长期目标。进一步检查后发现，如果不先处理异常值未处理，“流失率”很容易被一个表面相关指标替代。
- **处理过程**：补充同周期对照和护栏指标，把成功标准写成主指标、护栏指标和停止条件。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目避免了仅凭短期增长扩大策略，并形成试验评审与退出机制。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“流失率”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

另外两个适合继续拆分的工作场景是：

- **某大型企业数据平台团队**：报表数量增长但业务仍反馈找不到可信数据，数据团队交付压力持续上升。可以先从表、任务、指标、血缘、质量规则、查询日志和问题工单建立最小数据闭环，再围绕“流失率”检查同一指标多个 SQL 版本，血缘只覆盖部分任务，资产没有明确负责人。

如果要把本专题扩展成一个完整作品或项目，建议至少保留以下材料：

- 一页业务流程图，标注角色、系统、事件和异常分支。
- 一份指标字典，记录定义、粒度、边界和负责人。
- 一张事实与维度关系图，说明主键、时间和历史归属。
- 一套 SQL 或 Python 代码，包含参数、质量检查和执行说明。
- 三组验证样例：正常对象、边界对象和异常对象。

### 扩展代码一：从流失率回到可核对明细

```sql
-- 流失率：恢复后缺失、重复与跨期检查
WITH expected_keys AS (
  SELECT DISTINCT entity_id AS entity_key, event_id
  FROM fact_business_event
  WHERE event_time >= :restore_start
    AND event_time <  :restore_end
    AND subject_key = 'subject'
),
restored_keys AS (
  SELECT entity_id AS entity_key, event_id, load_version, loaded_at
  FROM fact_business_event
  WHERE event_time >= :restore_start
    AND event_time <  :restore_end
    AND subject_key = 'subject'
    AND load_version = :restore_version
),
coverage AS (
  SELECT
    (SELECT COUNT(*) FROM expected_keys) AS expected_cnt,
    (SELECT COUNT(*) FROM restored_keys) AS restored_cnt,
    (SELECT COUNT(*) FROM (
      SELECT entity_key, event_id
      FROM restored_keys
      GROUP BY entity_key, event_id
      HAVING COUNT(*) > 1
    ) duplicate_keys) AS duplicated_cnt,
    (SELECT COUNT(*) FROM (
      SELECT e.entity_key, e.event_id
      FROM expected_keys e
      LEFT JOIN restored_keys r USING (entity_key, event_id)
      WHERE r.entity_key IS NULL
    ) missing_keys) AS missing_cnt
)
SELECT *,
  CASE
    WHEN expected_cnt <> restored_cnt OR duplicated_cnt > 0 OR missing_cnt > 0
      THEN 'reject_release'
    ELSE 'accept_restore'
  END AS gate_result
FROM coverage;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把流失率的验收证据写成门禁

```python
from dataclasses import dataclass
from datetime import datetime


@dataclass(frozen=True)
class ReleaseEvidence:
    subject: str
    source_watermark: datetime
    output_watermark: datetime
    source_rows: int
    output_rows: int
    duplicate_rows: int
    blocked_rows: int
    code_version: str
    parameter_version: str


def release_gate(evidence: ReleaseEvidence) -> tuple[bool, list[str]]:
    reasons = []
    if evidence.source_watermark != evidence.output_watermark:
        reasons.append("watermark_mismatch")
    if evidence.source_rows != evidence.output_rows:
        reasons.append("row_count_mismatch")
    if evidence.duplicate_rows:
        reasons.append("duplicate_keys")
    if evidence.blocked_rows:
        reasons.append("blocking_quality_rule_failed")
    if not evidence.code_version or not evidence.parameter_version:
        reasons.append("release_provenance_missing")
    return not reasons, reasons


evidence = ReleaseEvidence(
    subject="流失率",
    source_watermark=datetime.fromisoformat("2026-11-06T02:00:00"),
    output_watermark=datetime.fromisoformat("2026-11-06T02:00:00"),
    source_rows=0,
    output_rows=0,
    duplicate_rows=0,
    blocked_rows=0,
    code_version="demo-v1",
    parameter_version="scope-v1",
)
print(release_gate(evidence))
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
