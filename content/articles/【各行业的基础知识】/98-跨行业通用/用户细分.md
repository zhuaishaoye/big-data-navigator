# 用户细分

> [!tip] 分析目标
> 把“用户细分”放进需求澄清、业务事件采集、指标计算、经营分析、流程优化和结果复盘，真正困难的通常不是解释名词，而是把它变成一条能被核对、能被复现、也能推动行动的工程链路。本文不追求堆满概念，而是围绕这个主题拆出业务对象、数据粒度、典型故障、代码验证和验收方式。

## 1. 把主题翻译成可验证的问题

“用户细分”不能直接等同于“做一张趋势图”。一个可执行的分析问题至少包含对象、时间、比较基准和行动：

> 在【观察周期】内，对【有效对象】按【时间、业务类型、地区】比较【质量率】与【成本】，判断变化来自结构、行为还是数据口径，并验证【策略动作】是否带来可解释的增量。

在跨行业通用场景中，用户行为、交易结果和策略曝光经常来自不同系统。先画数据流：

业务系统 → CRM → ERP → 数据仓库 → 调度平台 → BI

图中至少要有三个标记：业务事件发生时间、数据可见时间、策略或行动时间。只有三者分开，后续才能判断问题发生在业务、链路还是观察窗口。

## 2. 指标定义与分母检查

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 业务量 | `COUNT(DISTINCT event_id)`（视图字段 `event_cnt`） | 时间、业务类型、地区 | 不混用测试、撤销和跨期状态；与“用户细分”相关时还要补充主题筛选 |
| 转化率 | `COUNT(DISTINCT success_id) / COUNT(DISTINCT eligible_id)`（视图字段 `conversion_rate`） | 业务类型、地区、对象层级 | 不混用测试、撤销和跨期状态；与“用户细分”相关时还要补充主题筛选 |
| 处理时长 | `AVG(completed_at - started_at)`（视图字段 `processing_time`） | 地区、对象层级、来源渠道 | 不混用测试、撤销和跨期状态；与“用户细分”相关时还要补充主题筛选 |
| 质量率 | `COUNT(DISTINCT valid_id) / COUNT(DISTINCT checked_id)`（视图字段 `quality_rate`） | 对象层级、来源渠道 | 不混用测试、撤销和跨期状态；与“用户细分”相关时还要补充主题筛选 |

针对“用户细分”，建议分别定义诊断指标、结果指标和护栏指标：

- **诊断指标**用于定位流程，例如曝光、有效访问、符合条件对象数和异常节点。
- **结果指标**用于判断是否改善，例如转化、留存、客单、毛利或处理时长。
- **护栏指标**用于防止局部优化伤害整体，例如退款、投诉、成本、公平性和长期留存。

每次计算都问四个问题：分母是谁、对象何时进入分母、例外状态怎么处理、窗口是否足够覆盖行为完成。尤其是口径未冻结；主数据不一致；异常值未处理，任何一项没有解释清楚，指标都可能“看起来合理但无法决策”。

## 3. 方法选择：描述、诊断、预测还是因果

| 目标 | 适合的方法 | 需要的证据 | 不要混淆 |
| --- | --- | --- | --- |
| 描述现状 | 趋势、结构、同期群 | 完整口径、稳定时间窗 | 描述不等于原因 |
| 定位异常 | 分层、贡献度、漏斗、异常检测 | 原始事件、基线和质量检查 | 排名靠前不等于因果 |
| 预测未来 | 时间序列、回归、机器学习 | 时间切分验证、误差成本 | 离线准确率不等于业务收益 |
| 评估策略 | A/B、灰度、准实验 | 对照组、样本量、护栏指标 | 上线前后对比容易混入季节和选择偏差 |

如果问题只是“发生了什么”，先别急着建模；如果问题涉及“采取某策略会怎样”，就必须讨论反事实和识别条件。围绕“用户细分”，应把观察分析、预测和因果评估的产出分开标注。

## 4. 案例一：某大型企业数据平台团队

### 案例 1：某大型企业数据平台团队的“用户细分”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：报表数量增长但业务仍反馈找不到可信数据，数据团队交付压力持续上升。本次讨论的重点是“用户细分”，所以团队先要求把先冻结对象与时间窗写进项目目标，而不是直接开始做报表。
- **数据范围**：表、任务、指标、血缘、质量规则、查询日志和问题工单。同时收集业务系统、CRM、ERP、数据仓库中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：同一指标多个 SQL 版本，血缘只覆盖部分任务，资产没有明确负责人。进一步检查后发现，如果不先处理口径未冻结，“用户细分”很容易被一个表面相关指标替代。
- **处理过程**：盘点核心指标和资产，建立责任人和版本机制，把质量规则和影响分析接入发布流程。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目减少重复取数问题，并为高影响指标建立变更通知和回滚清单。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“用户细分”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

落地时建议先把一个总指标拆成可行动的树：

```text
用户细分｜从总量到单条证据
├── ① 同期基线：先排除节假日、活动和口径切换
├── ② 结构贡献：按时间、业务类型、地区比较增量和抵消
├── ③ 状态漏斗：采集 → 加工 → 分析 → 决策
├── ④ 记录回查：正常、边界、异常各抽 N 条
└── ⑤ 闭环验证：成本与护栏指标同时恢复才算解决
```

如果某一分支变化最大，再进入下一层，而不是一开始就按十几个维度切碎。每个分层结果都应同时报告样本量，避免小样本的极端比例抢走注意力。

## 5. SQL：计算趋势、结构和贡献度

### 趋势、结构与贡献度诊断

```sql
-- 用户细分：分位对比诊断（对象层级 × 时间）
WITH scoped AS (
  SELECT
    entity_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_business_event
  WHERE event_time >= DATE '2026-07-01'
    AND event_time <  DATE '2026-10-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '业务量' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

示例 SQL 只表达计算逻辑。实际实施应加入分区条件、业务状态过滤、时区和主题范围，并在结果中保留口径版本。

## 6. 案例二：某快速扩张的运营团队

### 案例 2：某快速扩张的运营团队的“用户细分”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：新策略上线后短期指标提升，但两个月后用户投诉和退款增加。本次讨论的重点是“用户细分”，所以团队先要求把先证明数据链路可信写进项目目标，而不是直接开始做报表。
- **数据范围**：策略曝光、用户分层、转化、留存、退款、投诉和客服记录。同时收集业务系统、CRM、ERP、数据仓库中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：只观察短期转化，没有设置对照组，退款和投诉没有纳入长期目标。进一步检查后发现，如果不先处理主数据不一致，“用户细分”很容易被一个表面相关指标替代。
- **处理过程**：补充同周期对照和护栏指标，把成功标准写成主指标、护栏指标和停止条件。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目避免了仅凭短期增长扩大策略，并形成试验评审与退出机制。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“用户细分”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

当业务方要求“解释为什么下降”时，可以按下面顺序回答：

1. 先确认下降是否真实存在，排查采集、任务、维表和状态映射。
2. 把变化拆成对象数量、行为强度和结构占比。
3. 找到贡献最大的分组，但保留其他分组的抵消效应。
4. 抽取正负样本回查业务事件和操作日志。
5. 把尚不能证明的解释标为假设，并设计下一轮验证。

## 7. 代码验证：专题指标、实验或模型

### 专题验证代码

```sql
-- 主题：用户细分
-- 示例表名和字段名用于说明建模方法，落地时请映射到企业现有数仓。
WITH scoped AS (
  SELECT
    e.event_id,
    e.entity_id,
    e.event_time AS event_time,
    e.stage_code,
    e.dimension_value AS analysis_dim,
    e.status,
    COALESCE(e.metric_value, 0) AS metric_value,
    ROW_NUMBER() OVER (
      PARTITION BY e.event_id
      ORDER BY e.updated_at DESC
    ) AS version_no
  FROM fact_business_event e
  WHERE e.event_time >= DATE '2026-01-01'
    AND e.event_time <  DATE '2026-04-01'
    AND e.subject_name = '用户细分'
    AND e.is_deleted = 0
),
dedup AS (
  SELECT *
  FROM scoped
  WHERE version_no = 1
),
baseline AS (
  SELECT
    analysis_dim,
    COUNT(DISTINCT entity_id) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    AVG(metric_value) AS avg_metric,
    MIN(event_time) AS first_seen_at,
    MAX(event_time) AS last_seen_at
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY analysis_dim
)
SELECT
  analysis_dim AS analysis_dimension,
  entity_cnt,
  event_cnt,
  ROUND(avg_metric, 4) AS quality_rate,
  first_seen_at,
  last_seen_at,
  ROUND(event_cnt * 1.0 / NULLIF(SUM(event_cnt) OVER (), 0), 4) AS contribution_ratio
FROM baseline
ORDER BY event_cnt DESC;
```

## 8. 异常、偏差与常见误区

- **辛普森悖论**：总体改善但每个分组都变差，可能由对象结构变化造成。
- **幸存者偏差**：只分析完成流程的对象，忽略中途流失和中止。
- **分母漂移**：渠道口径、登录状态、版本或活动范围变化，改变可比性。
- **回传延迟**：当天数据未回补，导致近期效果被系统性低估。
- **多重比较**：反复寻找显著分组，实际只是随机波动。
- **行动偏差**：只报告支持既定方案的结果，忽略反例和护栏指标。

围绕“用户细分”，应预先写出至少三条反例检查。比如异常值处理是否可能改变最终排名、权限和敏感信息是否遵循最小必要原则，以及 结论是否能回到明细。

## 10. 交付物与工作节奏

| 交付物 | 应包含 | 质量要求 |
| --- | --- | --- |
| 问题说明 | 背景、对象、时间、成功标准 | 一句话能说明要改变什么 |
| 指标字典 | 公式、粒度、排除项、负责人 | 换人计算能得到同一结果 |
| 分析代码 | SQL/Python、参数、日志 | 可复跑，不依赖手工改数 |
| 验证记录 | 抽样、对账、边界样本 | 结论能回到原始事件 |
| 决策材料 | 结论、证据、限制、行动 | 区分事实、解释和建议 |
| 复盘记录 | 结果、副作用、下一步 | 有观察周期和停止条件 |

1. 明确“用户细分”服务的使用者、决策动作和不做范围，并把成功标准写成可观察指标。
2. 为业务对象、事件、流程分别确认主键、时间和状态，画出从源系统到结果的链路。
3. 先做字段血缘和质量画像，检查主键唯一、时间完整、枚举受控。
4. 用同周期基线和至少两个维度拆解问题，避免只比较一个异常周。
5. 抽取正常、异常和边界样本回查原始业务单据，记录抽样方法与结论。
6. 选择一种代码实现并保留参数、版本、执行日志和结果快照，确保别人可以复跑。
7. 上线前定义告警阈值、回滚条件和责任人；上线后按周观察主指标与护栏指标。
8. 复盘时区分数据问题、业务变化、方案偏差和外部因素，并把改进项转成有时限的任务。

> 以下内容围绕“用户细分”补充四个相互独立的工作场景，分别落在链路断点与延迟、对象与口径争议、故障恢复与可回放、权限、隐私与审计。它们使用公开方法、常见系统边界和脱敏数据构造，重点展示怎样从现象回到对象、流程、代码、行动与验收，而不是给出一个可以套用所有企业的标准答案。

| 案例 | 观察角度 | 首要对象 | 关键证据 | 失败时先停什么 |
| --- | --- | --- | --- | --- |
| 案例 4 | 链路断点与延迟 | 业务对象 / 事件 | 源端操作日志、CDC/批次水位、分区清单 | 无法证明数据完整的链路不进入正式发布，优先保留旧版本供下游读取 |
| 案例 5 | 对象与口径争议 | 事件 / 流程 | 指标字典版本、源系统样例、两条计算链路 | 口径未确认时只发布差异分析，不把任一结果包装成正式经营指标 |
| 案例 6 | 故障恢复与可回放 | 流程 / 组织 | 运行参数、代码版本、输入快照 | 恢复任务没有对账、没有版本记录或无法重复执行时，不宣布故障结束 |
| 案例 7 | 权限、隐私与审计 | 组织 / 指标结果 | 分类分级、授权记录、字段血缘 | 高风险字段缺少授权、脱敏或审计时不进入分析环境，紧急访问必须到期自动回收 |

这四个案例共享一条底线：先证明数据对象和链路能够解释，再讨论优化或决策。任何涉及资金、医疗安全、用户隐私、监管报送或核心权限的结果，都需要保留人工复核、阻断条件和回滚路径。

### 案例 4：用户细分从源事件到结果的长链路核查

一个看似普通的“用户细分”需求，在跨系统核验后变成了围绕“链路断点与延迟”的专项排查。触发排查的不是一次严重事故，而是连续几次解释不清的数据差异。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 把业务发生时间、数据可见时间、任务完成时间和下游消费时间放到同一条证据链。在本场景里，核心风险还包括上下游延迟，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：业务对象、事件及其在复盘前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注entity_id与event_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 结果表出现缺失或延迟，单看调度状态却显示成功，无法判断问题发生在源端、接入、计算还是服务层。初看时，工单系统与业务系统的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 源端操作日志、CDC/批次水位、分区清单、任务参数、血缘关系、下游请求日志。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“技术运维”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“用户细分”的当前定义并记录版本；第二步用业务对象明细核对工单系统到业务系统的关联；第三步按对象层级与时间做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察质量率和护栏指标业务量。
- **行动与护栏：** 按时间轴核对每一跳的输入输出计数与水位，先阻断错误结果扩散，再确定重跑范围和补数窗口。专题检查项“金额与数量关系合理”被写成发布门禁，无法证明数据完整的链路不进入正式发布，优先保留旧版本供下游读取。
- **失败路径：** 看到任务成功就立即补数，却没有确认重复、乱序和迟到事件。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“用户细分”时，先验证金额与数量关系合理，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由技术运维在明确时限内，根据质量率、业务量和金额与数量关系合理决定继续、回退、补查还是转人工。 若上下游延迟或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

- **可迁移结论：** 处理“用户细分”时，先验证指标口径版本可追溯，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由业务负责人在明确时限内，根据成本、转化率和指标口径版本可追溯决定继续、回退、补查还是转人工。 若分析结论无法落地或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从用户细分回到可核对明细

```sql
-- 用户细分：源表与结果表按对象对账
WITH source_side AS (
  SELECT
    entity_id AS entity_key,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum
  FROM fact_business_event
  WHERE event_time >= :start_date
    AND event_time <  :end_date
    AND subject_key = 'subject'
    AND is_deleted = 0
  GROUP BY entity_id
),
result_side AS (
  SELECT
    entity_id AS entity_key,
    event_cnt,
    metric_sum
  FROM fact_business_event_result
  WHERE stat_date BETWEEN :start_date AND :end_date
    AND subject_key = 'subject'
)
SELECT
  COALESCE(s.entity_key, r.entity_key) AS entity_key,
  s.event_cnt AS source_event_cnt,
  r.event_cnt AS result_event_cnt,
  s.metric_sum AS source_metric_sum,
  r.metric_sum AS result_metric_sum,
  COALESCE(r.metric_sum, 0) - COALESCE(s.metric_sum, 0) AS metric_diff
FROM source_side s
FULL OUTER JOIN result_side r USING (entity_key)
WHERE ABS(COALESCE(r.metric_sum, 0) - COALESCE(s.metric_sum, 0)) > 0
   OR COALESCE(s.event_cnt, 0) <> COALESCE(r.event_cnt, 0)
ORDER BY ABS(metric_diff) DESC;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把用户细分的验收证据写成门禁

```python
from dataclasses import dataclass
from datetime import datetime


@dataclass(frozen=True)
class ReleaseEvidence:
    subject: str
    source_watermark: datetime
    output_watermark: datetime
    source_rows: int
    output_rows: int
    duplicate_rows: int
    blocked_rows: int
    code_version: str
    parameter_version: str


def release_gate(evidence: ReleaseEvidence) -> tuple[bool, list[str]]:
    reasons = []
    if evidence.source_watermark != evidence.output_watermark:
        reasons.append("watermark_mismatch")
    if evidence.source_rows != evidence.output_rows:
        reasons.append("row_count_mismatch")
    if evidence.duplicate_rows:
        reasons.append("duplicate_keys")
    if evidence.blocked_rows:
        reasons.append("blocking_quality_rule_failed")
    if not evidence.code_version or not evidence.parameter_version:
        reasons.append("release_provenance_missing")
    return not reasons, reasons


evidence = ReleaseEvidence(
    subject="用户细分",
    source_watermark=datetime.fromisoformat("2026-11-06T02:00:00"),
    output_watermark=datetime.fromisoformat("2026-11-06T02:00:00"),
    source_rows=0,
    output_rows=0,
    duplicate_rows=0,
    blocked_rows=0,
    code_version="demo-v1",
    parameter_version="scope-v1",
)
print(release_gate(evidence))
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。

### 四个案例共用的验收清单

| 验证面 | 发布前问题 | 证据 | 不通过时 |
| --- | --- | --- | --- |
| 对象与粒度 | 一行数据代表业务对象、事件、快照还是结果 | 主键、版本、有效时间和边界样本 | 阻断 |
| 时间语义 | 业务发生、数据可见、决策采用是否混用 | event_time、入仓时间、行动时间轴 | 阻断 |
| 指标口径 | 业务量的分子、分母和排除项是否冻结 | 指标字典、SQL、对账结果 | 阻断正式指标 |
| 状态与关联 | 需求 → 采集 → 加工 → 分析是否可达且可追溯 | 状态机、明细、操作日志 | 阻断关键链路 |
| 权限与最小字段 | 派生表、导出和临时授权是否扩大访问范围 | 分类分级、字段血缘、访问日志 | 阻断导出 |
| 恢复与审计 | 失败后能否定位影响范围并幂等重跑 | 参数、版本、分区清单、补数对账 | 阻断发布 |

### 如果要把案例继续做深

1. **补一张真实但脱敏的链路图：** 标出业务系统、CRM、ERP、数据仓库、调度平台之间的主键、时间、状态、版本、责任人和失败动作。
2. **补一份指标或规则字典：** 说明业务量、转化率、处理时长的定义、粒度、排除项、负责人和验收样例。
3. **补一组代码证据：** 保留 SQL/Python、执行参数、输入输出计数、质量结果和一次失败回放，证明代码不只展示成功路径。
4. **补一次业务评审：** 让业务负责人、产品与运营、数据开发、数据分析分别说明结果会改变什么动作，以及哪些结论仍缺少证据。
5. **补一次复盘：** 记录口径未冻结、主数据不一致、异常值未处理是否发生、护栏是否生效、哪些处理应进入下一版标准。
