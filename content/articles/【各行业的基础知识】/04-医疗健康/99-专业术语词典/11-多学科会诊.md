# 11-多学科会诊

> [!abstract] 快速理解
> “多学科会诊”不是一个孤立概念。放到门诊、住院、检查、用药、随访和支付结算的真实工作里，它最终要回答三个问题：谁受影响、变化发生在哪一步、团队下一步应该做什么。本文按可直接落地的数据项目展开，而不是停留在名词解释。

## 一、业务场景与问题定义

在门诊、住院、检查、用药、随访和支付结算中，患者、就诊记录、医嘱、检查检验、药品和医疗费用会持续产生记录。围绕“多学科会诊”，建议先把一个模糊需求拆成可验证的问题：

- **对象**：分析哪类患者，是否排除测试、撤销和重复记录。
- **时间**：采用自然日、自然月还是滚动窗口，时区是否统一。
- **粒度**：一行代表一次事件、一天快照，还是一个业务对象。
- **动作**：结果提供给运营、产品、风控、供应链还是管理层，谁负责跟进。

一个可用的目标句式是：

> 在【时间范围】内，按【业务维度】比较【对象范围】的【按时随访率】与【复诊率】，定位变化最大的环节，并验证【行动方案】是否带来改善。

先保证数据可用，再追求模型复杂和报表丰富。这一步应在编码前完成，否则后续很容易出现“数字都能算出来，但没人知道该怎么用”的情况。

## 二、核心概念、指标与口径

“多学科会诊”在实际项目中通常同时涉及业务定义和数据定义。业务定义回答“这个现象是什么”，数据定义回答“如何从表中稳定得到它”。两者都写进指标字典，才能避免同名不同义。

| 口径项 | 本文建议 |
| --- | --- |
| 统计对象 | 去重后的有效患者 |
| 默认时间 | 以 `visit_date` 为准，并明确时区 |
| 成功状态 | 只统计已确认完成的状态，测试和撤销记录不计入 |
| 分子分母 | 分子与分母必须来自同一时间窗和同一对象范围 |
| 缺失值 | 区分“业务未发生”“系统未采集”和“采集失败” |

| 指标 | 建议定义 | 常用维度 | 用途 |
| --- | --- | --- | --- |
| 就诊人次 | 在明确统计周期和对象范围后，用不重复业务主键计数或汇总 | 院区、科室、病种 | 判断整体规模与趋势 |
| 复诊率 | 用同一粒度的分子除以可解释的分母，并排除测试与撤销记录 | 科室、病种、人群 | 判断流程效率或质量 |
| 人均费用 | 将“多学科会诊”相关的状态变化落到事件或快照口径 | 病种、人群、支付方式 | 支撑专题分析和行动追踪 |

建议为每个指标至少保留：名称、英文编码、一句话定义、计算公式、统计粒度、时间字段、排除条件、负责人、更新频率和验收样例。仅写一个公式截图，后续很难维护。

## 三、数据模型与关键字段

一个便于验证的最小模型可以包含事实表、维度表和时间字段。下面的表名是示例，落地时应映射到现有数仓分层。

| 层 | 示例对象 | 关键字段 | 作用 |
| --- | --- | --- | --- |
| ODS | `ods_*_log` | 业务主键、原始状态、事件时间、更新时间 | 保留原始记录，便于回溯 |
| DWD | `fact_medical_visit` | fact_medical_visit.id、fact_medical_visit.visit_date、fact_medical_visit.entity_id、fact_medical_visit.status、fact_medical_visit.amount、dim_patient.name | 统一粒度、清洗无效记录 |
| DIM | `dim_patient` | 实体主键、名称、分类、生效时间 | 提供一致的分析维度 |
| ADS | `ads_topic_summary` | 日期、维度、指标 | 面向报表和专题分析 |

建模时重点检查两件事。第一，事实表是否只有一个清晰粒度；如果订单、订单明细和退款记录混在同一张表，金额和数量会被重复累计。第二，维度表是否支持缓慢变化；组织、区域、设备和产品分类都会变化，历史报表应明确使用“当时归属”还是“当前归属”。

## 四、可执行的 SQL 分析模板

以下 SQL 使用通用语法，可直接改造成 Hive、Spark SQL、PostgreSQL、ClickHouse 或 Doris 版本。运行前先确认时间字段类型和分区字段，避免全表扫描。

```sql
WITH base AS (
  SELECT
    f.id,
    f.visit_date AS event_date,
    f.entity_id,
    f.status,
    COALESCE(f.amount, 0) AS amount,
    d.name AS entity_name
  FROM fact_medical_visit f
  LEFT JOIN dim_patient d
    ON f.entity_id = d.id
  WHERE f.visit_date >= DATE '2026-01-01'
    AND f.visit_date <  DATE '2026-04-01'
    AND COALESCE(f.is_deleted, 0) = 0
)
SELECT
  DATE_TRUNC('month', event_date) AS month,
  COUNT(DISTINCT id) AS event_count,
  COUNT(DISTINCT entity_id) AS entity_count,
  ROUND(SUM(amount), 2) AS total_amount,
  ROUND(AVG(amount), 2) AS avg_amount
FROM base
GROUP BY 1
ORDER BY 1;
```

如果要定位变化发生在哪一步，不要只看总量，可以按同一粒度做环比和分层：

```sql
WITH monthly AS (
  SELECT
    DATE_TRUNC('month', visit_date) AS month,
    entity_id,
    COUNT(DISTINCT id) AS event_count
  FROM fact_medical_visit
  WHERE visit_date >= DATE '2026-01-01'
    AND COALESCE(is_deleted, 0) = 0
  GROUP BY 1, 2
),
compared AS (
  SELECT
    month,
    event_count,
    LAG(event_count, 1) OVER (
      PARTITION BY entity_id ORDER BY month
    ) AS previous_count
  FROM monthly
)
SELECT
  month,
  entity_id,
  event_count,
  previous_count,
  ROUND(
    (event_count - previous_count) * 1.0
    / NULLIF(previous_count, 0),
    4
  ) AS month_over_month_rate
FROM compared
ORDER BY month, entity_id;
```

## 五、真实落地步骤

1. **冻结问题与口径**：把需求写成一句可验证的话，确认对象、时间、维度和成功标准。
2. **检查数据可用性**：统计主键重复率、时间空值率、状态枚举、分区覆盖和上下游延迟。
3. **建立基线**：选择过去 8 至 12 周或同季节周期，避免只用异常周作比较。
4. **做分层诊断**：先看整体，再按院区、科室、病种、人群、支付方式拆分，定位贡献最大的分组。
5. **回到明细验证**：抽取正向和反向样本，确认数字与业务事件一致。
6. **给出行动方案**：把结论写成“对象、动作、负责人、观察周期和停止条件”。
7. **建立监控**：为数据量、空值率、重复率、指标波动和更新延迟设置阈值。

## 六、数据质量与异常排查

| 检查项 | 推荐规则 | 异常时的处理 |
| --- | --- | --- |
| 唯一性 | 业务主键重复率为 0，事件流水允许重复时必须先去重 | 找到上游幂等或重复写入原因 |
| 完整性 | 患者标识脱敏；就诊时间完整；诊断编码有效；费用与明细可核对 | 阻断下游发布并通知数据负责人 |
| 一致性 | 状态、金额、数量与业务系统对账 | 以原始业务单据为准修正 |
| 及时性 | 核心分区在约定 SLA 前就绪 | 标注延迟，不使用半成品数据出结论 |
| 合理性 | 指标波动超过历史区间时触发告警 | 先排查数据问题，再解释业务变化 |

常见误区包括：只看总量不看结构、分母基数变化却不说明、用累计快照计算新增、把缺失值直接当 0、在多个系统使用不同实体编码。围绕“多学科会诊”出问题时，应优先回到粒度、主键、状态和时间这四个维度排查。

## 七、结果解释与工作产出

一份可复用的交付不应只有一张图。建议同时提交：

- 一页问题说明：背景、范围和不在本次范围内的事项。
- 一份指标口径：公式、排除规则和负责人。
- 一张主看板：趋势、结构、异常和行动状态。
- 一组验证样例：正常对象、异常对象和边界对象。
- 一份复盘记录：医疗数据的隐私保护、临床口径确认和合规使用的控制措施。

向业务方汇报时，先给结论和影响范围，再给证据。例如：“按时随访率下降主要来自院区中的科室分组，排除数据缺失后仍成立；建议先处理 A 环节，观察两周，以复诊率是否回升作为验收指标。”

## 八、练习与自测

用你自己的业务数据完成下面四项练习：

1. 写出“多学科会诊”的数据粒度，并说明一行代表什么。
2. 为“按时随访率”写一份包含排除条件的指标定义。
3. 找一个指标下降案例，分别从数据质量和业务变化两方面给出证据。
4. 将上面的 SQL 改写为适配当前数仓方言的版本，并记录扫描分区和执行耗时。

> [!check] 完成标准
> 能向不熟悉数据的同事解释口径；能从报表追溯到明细；能在没有新增数据的情况下说明结论边界；能把分析结果转成有负责人和验收时间的行动项。

## 九、公开资料与方法依据

本文采用公开数据治理、指标管理和分析实践中的通用方法：先定义业务对象与粒度，再明确指标口径，最后通过明细抽样、分层对比和持续监控验证结论。行业场景还受内部制度、监管要求和系统现状影响，正式上线前应由业务、数据、安全与合规负责人共同确认。
