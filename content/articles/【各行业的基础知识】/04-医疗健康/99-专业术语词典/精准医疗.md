# 精准医疗

> [!abstract] 场景速览
> 讨论“精准医疗”时，最容易犯的错误是直接从工具或报表开始。更有用的顺序是：先看业务链条，再找可观察指标，随后确认数据粒度，最后才选择 SQL、模型或平台组件。本文按这个顺序给出可执行方案和常见的失败样本。

## 1. “精准医疗”在医疗健康业务链中的位置

医疗健康的核心流程可以概括为：预约与挂号 → 接诊与分诊 → 检查检验 → 诊断与治疗 → 出院与结算 → 随访与质量复盘。参与角色包括患者、临床科室、护理团队、医技科室、医务管理、医保与财务、信息中心。“精准医疗”通常不是一个孤立字段，而是连接业务动作、数据记录和管理决策的一层能力。

从数据团队视角，至少要回答四个问题：

1. **谁使用**：患者、临床科室、护理团队、医技科室分别要用它做判断、执行还是审计。
2. **对象是什么**：一行数据代表患者、一次事件、一个批次还是一天快照。
3. **流程在哪里变化**：通过接诊与分诊、检查检验、诊断与治疗、出院与结算之间的状态和时间差定位问题。
4. **结果如何被采用**：谁在什么时间前采取行动，使用哪个指标观察改善或副作用。

一个合格的专题目标可以写成：

> 在【时间窗】和【授权数据范围】内，围绕“精准医疗”，按【院区、科室、病种】比较【平均住院日】与【复诊率】，定位一个可干预流程节点，并记录行动后的变化与边界。

## 2. 一张图看清角色、流程和数据

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 患者 | `patient_id` | 预约与挂号 |
| 过程对象 | 就诊 | `visit_id` | 接诊与分诊 |
| 过程对象 | 医嘱 | `order_id` | 检查检验 |
| 结果对象 | 检查检验 | `report_id` | 诊断与治疗 |
| 结果对象 | 费用 | `settlement_id` | 出院与结算 |
| 专题分析 | 精准医疗 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

建模时不要先把所有系统字段堆进一张大表。更稳妥的做法是分别保留三类事实：

- **事件事实**：谁在什么时间做了动作，例如挂号、下单、开工、报警或学习。
- **状态快照**：对象在某一天的状态，例如会员等级、租约、账户余额或设备资产关系。
- **结果事实**：流程完成后的产出，例如结算金额、良品数量、签收结果或考试分数。

三者的粒度不同。把事件、快照和结果强行放在同一行，会让金额、数量和转化率在汇总时重复。若“精准医疗”涉及状态变化，优先建立状态机；若涉及金额，先做借贷或收付平衡；若涉及对象归属，保留维度有效期。

## 3. 指标与口径：不要把相关数字直接当答案

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 门急诊人次 | `COUNT(DISTINCT visit_id)`（视图字段 `visit_cnt`） | 院区、科室、病种 | 不混用测试、撤销和跨期状态；与“精准医疗”相关时还要补充主题筛选 |
| 平均住院日 | `SUM(discharge_days) / COUNT(DISTINCT inpatient_visit_id)`（视图字段 `avg_los`） | 科室、病种、人群 | 不混用测试、撤销和跨期状态；与“精准医疗”相关时还要补充主题筛选 |
| 复诊率 | `COUNT(DISTINCT revisit_patient_id) / COUNT(DISTINCT index_patient_id)`（视图字段 `revisit_rate`） | 病种、人群、支付方式 | 不混用测试、撤销和跨期状态；与“精准医疗”相关时还要补充主题筛选 |
| 异常检验占比 | `COUNT(DISTINCT abnormal_report_id) / COUNT(DISTINCT report_id)`（视图字段 `abnormal_rate`） | 人群、支付方式 | 不混用测试、撤销和跨期状态；与“精准医疗”相关时还要补充主题筛选 |

指标字典至少应包含：中文名、英文编码、业务定义、计算公式、事实粒度、时间字段、对象范围、排除条件、负责人和验收样例。对于“精准医疗”，还应注明它使用的是业务发生时间还是入仓时间，是否包含撤销、退费、测试、跨期和补录记录。

一个常见误区是看到平均住院日变化就立即解释业务原因。更可靠的顺序是：

1. 检查数据覆盖和延迟是否变化。
2. 检查对象范围、状态映射和维度归属是否变化。
3. 按时间、结构和分组拆解贡献。
4. 回到明细寻找能解释变化的事件。
5. 如果已经采取行动，再评估行动带来的增量，而不是事后挑一个相关指标。

## 4. 工作案例：从现象到数据处理

### 案例 1：华东某三甲医院的“精准医疗”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：门诊高峰期投诉增加，管理层希望判断问题来自号源、接诊、检查还是报告回传。本次讨论的重点是“精准医疗”，所以团队先要求把先冻结对象与时间窗写进项目目标，而不是直接开始做报表。
- **数据范围**：3 个院区 18 个月挂号、报到、叫号、医嘱、检查、报告和结算事件。同时收集HIS、EMR、LIS、RIS中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：各系统用就诊号、住院号和申请单号交叉关联，报告回传时间缺少统一时区。进一步检查后发现，如果不先处理患者隐私泄露，“精准医疗”很容易被一个表面相关指标替代。
- **处理过程**：建立患者主索引和就诊主键，把门诊流程拆成 8 个事件节点，按院区、科室和时段做分层基线。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目把流程断点定位从人工拉取多个系统缩短到一张小时级监控，并形成报告超时催办规则。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“精准医疗”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

这个案例最关键的动作不是“跑一条 SQL”，而是把“精准医疗”对应的业务对象和上下游系统放在同一张链路图上。链路图至少要标出源系统、事件时间、关联主键、状态变化、数据负责人和消费方。

## 5. SQL 示例：在统一口径下做分层诊断

下面的查询用于展示分析结构，表名和字段需映射到实际环境。重点是去重、范围筛选、基线比较和贡献率，而不是代码本身。

### 标题专属诊断 SQL

```sql
-- 精准医疗：结构贡献诊断（科室 × 人群）
WITH scoped AS (
  SELECT
    patient_id AS entity_key,
    event_id,
    event_date AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_medical_event
  WHERE event_date >= DATE '2026-05-01'
    AND event_date <  DATE '2026-08-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '异常检验占比' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

执行后要回答四类验证题：

- 结果总量能否与源系统或既有报表在相同口径下解释差异？
- 排名前几位的分组是否由少数超长、重复或补录记录造成？
- 缺失日期表现为“未发生”还是“未采集”，是否改变分母？
- 维度使用的是当时归属还是当前归属，跨期比较是否一致？

## 6. 第二个案例：跨系统、跨部门时怎样不失控

### 案例 2：华中某互联网医院的“精准医疗”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：在线问诊订单增长但完成率下降，运营团队无法判断是医生供给、消息触达还是支付环节问题。本次讨论的重点是“精准医疗”，所以团队先要求把先证明数据链路可信写进项目目标，而不是直接开始做报表。
- **数据范围**：问诊下单、支付、医生接诊、图文消息、处方审核、药品配送和退款事件。同时收集HIS、EMR、LIS、RIS中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：匿名咨询与登录账号未打通，超时未接诊被误判为取消，退款事件重复上报。进一步检查后发现，如果不先处理多院区患者主索引重复，“精准医疗”很容易被一个表面相关指标替代。
- **处理过程**：建立用户、问诊单和支付单三级粒度，对超时、取消、退款和重新下单分别建模，补充漏斗诊断。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目定位到夜间接诊供给缺口，并建立了分时段排班与超时预警看板。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“精准医疗”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

跨部门项目最容易在三个地方返工：业务术语没有冻结、主数据映射没有版本、验收时才发现权限不足。建议在开发前让业务负责人签字确认指标定义，让数据负责人确认粒度与主键，让安全负责人确认字段范围，让运维负责人确认发布与回滚窗口。

## 7. Python 示例：把数据质量变成发布门禁

### 可执行质量门禁

```python
# 精准医疗：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "精准医疗"
TOPIC_KEY = "subject"
RULE_ID = "rule_healthcare_ec1vp8"
GUIDE_CHECKS = [
    "检查患者主索引跨院区唯一",
    "检查就诊时间与医嘱时间有序",
    "检查诊断编码在有效版本内"
]
RULES = {
    "required_columns": ["event_id", "patient_id", "event_date", "status"],
    "duplicate_key": "event_id",
    "entity_key": "patient_id",
    "time_field": "event_date",
    "max_duplicate_rate": 0.0004,
    "max_null_rate": 0.003,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：检查患者主索引跨院区唯一；检查就诊时间与医嘱时间有序；检查诊断编码在有效版本内
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

这段代码适合放在离线任务完成之后、指标发布之前。真实环境还应从调度平台读取分区参数、把结果写入质量平台，并在关键规则失败时阻断下游。告警不是终点，工单中要记录影响资产、发现时间、临时处理、根因、修复时间和防复发动作。

## 8. 异常排查：从指标异常回到业务事件

| 检查项 | 推荐方法 | 失败动作 | 负责人 |
| --- | --- | --- | --- |
| 患者主索引跨院区唯一 | 唯一性 SQL + 抽样明细 | 阻断发布 | 患者 |
| 就诊时间与医嘱时间有序 | 时间区间与状态机校验 | 阻断发布 | 临床科室 |
| 诊断编码在有效版本内 | 主数据有效期关联 | 告警并登记工单 | 护理团队 |
| 检验结果带单位与参考区间 | 金额或数量平衡校验 | 告警并登记工单 | 医技科室 |
| 费用明细与结算总额可对账 | 发布前阻断 + 责任人复核 | 告警并登记工单 | 医务管理 |

围绕“精准医疗”排查时，可以按以下顺序进行：

1. **影响面**：哪些指标、报表、接口或业务团队受影响，是否需要暂停对外发布。
2. **时间线**：源系统变更、任务发布、数据回刷、组织调整和业务活动分别发生在什么时候。
3. **数据链路**：上游是否延迟，分区是否缺失，主键是否重复，状态是否映射错误。
4. **业务证据**：抽取异常记录，与原始单据、操作日志、客服记录或现场系统核对。
5. **修复与复核**：明确补数范围、重跑粒度、回滚版本和验收样例。
6. **防复发**：把一次性排查升级为规则、监控、责任人和变更评审。

特别要注意：患者隐私泄露；多院区患者主索引重复；临床时间与计费时间混用；检验单位不统一。这些问题如果不被单独标记，很容易被误写成业务趋势。

## 9. 第三个案例与延伸场景

### 案例 3：华南某区域医疗集团的“精准医疗”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：集团合并报表中同一患者的跨院区就诊被重复计算，重点专科服务量口径长期不一致。本次讨论的重点是“精准医疗”，所以团队先要求把把数据和业务动作一起复盘写进项目目标，而不是直接开始做报表。
- **数据范围**：5 家成员医院患者、机构、科室、诊断、就诊和费用数据。同时收集HIS、EMR、LIS、RIS中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：患者证件号存在空值，院内卡号不能跨院使用，科室历史组织架构多次调整。进一步检查后发现，如果不先处理临床时间与计费时间混用，“精准医疗”很容易被一个表面相关指标替代。
- **处理过程**：设计患者、机构、科室三套主数据映射，保留维度有效期，建立指标口径评审和责任签字机制。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目把服务量差异拆成重复患者、跨期结算和科室归属三类，并形成月结对账流程。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。

- **可迁移结论：** 处理“精准医疗”时，先验证费用明细与结算总额可对账，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由医技科室在明确时限内，根据费用偏差率、平均住院日和费用明细与结算总额可对账决定继续、回退、补查还是转人工。 若历史诊断编码版本失效或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从精准医疗回到可核对明细

```sql
-- 精准医疗：发布前质量画像
SELECT
  'subject' AS subject_key,
  stat_date,
  COUNT(*) AS row_cnt,
  COUNT(DISTINCT event_id) AS distinct_event_cnt,
  SUM(CASE WHEN event_id IS NULL THEN 1 ELSE 0 END) AS null_event_cnt,
  SUM(CASE WHEN event_date < business_time THEN 1 ELSE 0 END) AS time_reverse_cnt,
  SUM(CASE WHEN status NOT IN ('valid', 'completed', 'cancelled') THEN 1 ELSE 0 END) AS invalid_status_cnt,
  ROUND(COUNT(*) * 1.0 / NULLIF(COUNT(DISTINCT event_id), 0), 4) AS duplication_ratio
FROM fact_medical_event
WHERE stat_date BETWEEN :start_date AND :end_date
GROUP BY stat_date
HAVING SUM(CASE WHEN event_id IS NULL THEN 1 ELSE 0 END) > 0
    OR SUM(CASE WHEN event_date < business_time THEN 1 ELSE 0 END) > 0
    OR COUNT(*) <> COUNT(DISTINCT event_id)
ORDER BY stat_date;

-- 至少人工核对一次：患者主索引跨院区唯一；就诊时间与医嘱时间有序；诊断编码在有效版本内。
```

### 扩展代码二：把精准医疗的验收证据写成门禁

```python
from datetime import date
from hashlib import sha256

import pandas as pd

SUBJECT = "精准医疗"
BLOCKING_RULES = ["患者主索引跨院区唯一","就诊时间与医嘱时间有序","诊断编码在有效版本内"]


def validate_release(frame: pd.DataFrame, start: date, end: date) -> dict:
    scoped = frame.loc[
        frame["event_date"].between(pd.Timestamp(start), pd.Timestamp(end))
        & (frame["subject_key"] == "subject")
    ].copy()
    checks = {
        "has_rows": len(scoped) > 0,
        "event_id_unique": not scoped["event_id"].duplicated().any(),
        "entity_key_complete": scoped["entity_key"].notna().all(),
        "event_time_present": scoped["event_time"].notna().all(),
        "scope_matches": scoped["subject_key"].nunique() == 1,
    }
    payload = f"{SUBJECT}|{start}|{end}|{len(scoped)}|{sorted(checks.items())}"
    return {
        "subject": SUBJECT,
        "rows": len(scoped),
        "checks": checks,
        "blocking_rules": BLOCKING_RULES,
        "release_allowed": all(checks.values()),
        "evidence_hash": sha256(payload.encode("utf-8")).hexdigest(),
    }
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
