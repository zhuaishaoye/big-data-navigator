# 仿制药

> [!abstract] 仿制药注册与一致性评价实战手册
> 仿制药不是“照着原研药复制配方”，而是以参比制剂为比较基础，通过药学、生物等效性和生产质量证据证明其安全有效且质量可控的独立产品。数据分析要围绕产品身份、参比关系、处方工艺、生物等效性、批次放行和上市后质量展开。

## 1. 仿制药：定义、适用边界与决策出口

仿制药不是“照着原研药复制配方”，而是以参比制剂为比较基础，通过药学、生物等效性和生产质量证据证明其安全有效且质量可控的独立产品。数据分析要围绕产品身份、参比关系、处方工艺、生物等效性、批次放行和上市后质量展开。

**本篇的适用边界。** 本篇覆盖仿制药注册、一致性评价和商业化质量数据；不讨论未经批准的个人配制，也不把价格低、成分相同直接等同于临床可替代。

**最常见的错误替代。** 不能用原研药商品名代替参比制剂，也不能只用平均血药浓度判断生物等效性。

**最终决策。** 团队需要判断：处方和工艺是否稳定、试验是否符合方案、批次能否放行、市场替代是否需要监管与临床条件。 因此，这篇内容不从“应该建哪张表”开始，而从业务动作、责任人和失败后果开始。只有先确定谁在什么时点做出什么决定，字段、SQL、看板和模型才有明确用途。

围绕“仿制药”，工作中至少要区分四类问题：

1. **身份问题**：对象是谁，主键能否跨系统稳定关联，合并、拆分、撤销后历史是否还看得见。
2. **时间问题**：业务发生、状态生效、数据入仓、计算完成和人员行动分别发生在哪一刻。
3. **状态问题**：当前状态是一段事件、一张快照还是最终结果，空值代表未发生、未采集还是已删除。
4. **责任问题**：谁确认口径，谁处理异常，谁有权放行或停止，谁在观察期后复盘。

## 2. 仿制药的完整业务流程

| 环节 | 要做的事 | 最小证据 | 失败后先查什么 |
| --- | --- | --- | --- |
| 参比制剂与目标产品确认 | 固定参比来源、规格、批次和批准信息 | 参比制剂目录、采购与检验记录 | 只记录原研商品名，不记录具体规格和来源 |
| 处方与工艺开发 | 研究关键质量属性、辅料和放大风险 | 处方版本、工艺参数、稳定性 | 排除标准随结果变化 |
| 生物等效性研究 | 验证关键药代参数及个体差异 | 方案、受试者、采样、分析方法和统计报告 | 辅料或设备变更未经评估直接生产 |
| 注册申报 | 提交药学、非临床和生物等效性证据 | 申报资料、发补问题和批准范围 | 仅按价格把所有同成分产品视为可互换 |
| 商业化生产 | 按验证工艺生产并检验放行 | 批记录、偏差、OOS、设备清洁 | 只记录原研商品名，不记录具体规格和来源 |
| 上市后质量与替代 | 监测投诉、召回、疗效反馈和供应 | 反馈、留样、稳定性、市场数据 | 排除标准随结果变化 |

把 参比制剂与目标产品确认、处方与工艺开发、生物等效性研究、注册申报、商业化生产、上市后质量与替代 串起来后可以看出，仿制药不是一个孤立字段，而是一条会跨系统、跨岗位、跨时间的证据链。流程图上每一段都应标出输入、输出、状态、时间戳、责任人和异常出口。只要其中一段只能靠口头解释，后续的统计、追责和自动化就会失去基础。

一个合格的需求说明应该写成：

> 在【授权数据范围】和【观察窗口】内，围绕“仿制药”的【仿制产品】，按【generic_product_id、site_id、formulation_version、batch_size_band】比较【生物等效性研究完成率】及其【关键药代参数可评估率】，定位一个可干预节点；行动后同时观察主指标、样本量和护栏，任何高风险异常先阻断再调查。

## 3. 仿制药的数据对象与系统契约

| 数据对象 | 建议主键 | 一行代表什么 | 不允许混淆 |
| --- | --- | --- | --- |
| 仿制产品 | `generic_product_id` | 活性成分、剂型、规格和批准持有人 | 对象身份与业务事件 |
| 参比关系 | `reference_product_id` | 具体参比制剂、来源和有效版本 | 事件、状态快照和结果粒度 |
| 处方工艺 | `formulation_version_id` | 批次、辅料来源和关键参数 | 事件、状态快照和结果粒度 |
| 生物等效性研究 | `be_study_id` | 设计、人群、采样和统计方案 | 事件、状态快照和结果粒度 |
| 商业批次 | `generic_batch_id` | 生产、检验和放行记录 | 事件、状态快照和结果粒度 |
| 质量反馈 | `product_quality_case_id` | 投诉、留样复核和召回影响 | 事件、状态快照和结果粒度 |

对象表不是把所有字段塞进一张宽表。事件、状态快照和结果表应该分别保留粒度，再通过稳定主键与版本建立关联。尤其要避免三个常见混算：把一次业务事件算成多个对象、把每日快照相加当事件总量、把最新状态覆盖历史状态。

本主题的数据契约至少应包含：

- `generic_batch_id` 的唯一性规则、生成方式和跨系统映射。
- `manufactured_at` 的业务含义、时区、迟到和补录规则。
- `release_status` 的完整状态集合，以及删除、撤销、冻结和失效的表示方法。
- 控制对象 `be_subject_profile.be_subject_id` 与主对象的关系。
- 每次口径、规则、模型或源版本变化的影响范围和下游通知对象。
- 敏感字段、允许用途、访问角色、导出限制和审计保留时间。

## 4. 仿制药的指标、样本与验收口径

| 指标 | 公式或定义 | 口径提醒 |
| --- | --- | --- |
| 生物等效性研究完成率 | 完成全部计划采样和分析的受试者 / 计划受试者 | 退出、呕吐、异常采样和方案偏离要分开 |
| 关键药代参数可评估率 | 达到方案要求的可评估受试者 / 随机化受试者 | 不能只报最终纳入统计的人数 |
| 商业批次一次放行率 | 首次放行合格的批次 / 呈报放行批次 | OOS、偏差和文档缺陷要分类 |
| 溶出曲线可比率 | 在规定条件下满足比较标准的批次或时间点 | 不能只看单一时间点 |
| 投诉批次闭环率 | 完成调查和处置的质量投诉 / 应调查投诉 | 调查完成不等于问题已纠正 |

指标字典至少写到“任何人都能按同一份数据复跑”的程度：中文名、业务定义、公式、分子、分母、事实粒度、时间字段、对象范围、排除项、版本、负责人和验收样例，一个都不能少。比例指标必须同时展示分子、分母和样本量；金额或数量必须做守恒；状态指标必须能回到事件时间线。

对于“仿制药”，建议把观察分成三层：

| 层次 | 看什么 | 不能替代什么 |
| --- | --- | --- |
| 业务结果 | 生物等效性研究完成率、关键药代参数可评估率 | 不能替代过程证据和个案回查 |
| 过程护栏 | 商业批次一次放行率、溶出曲线可比率、投诉批次闭环率 | 不能因为护栏暂时正常就跳过异常调查 |
| 数据证据 | 主键、时间、状态、版本、来源目标对账 | 不能只看任务成功或报表能打开 |

## 5. 仿制药：七个真实工作场景

以下七组场景均为公开方法结合常见工作流程构造的“脱敏复合示例”，不对应任何单一企业、患者、客户或雇员事实。场景的目的，是展示如何从现象走到证据、行动和验收，而不是虚构经营成果。

### 1. 生物等效性研究出现空腹与餐后差异

**现场。** 空腹结果通过评价标准，餐后结果接近边界，团队希望合并两组证明总体通过。

**怎么查。** 核对研究设计、给药条件、采样时间、受试者分配、分析方法和统计模型，确认两组是不同条件下的独立问题。

**怎么处理。** 按预先定义分别报告，不合并成一个“总体通过”；对接近边界的结果进行敏感性分析和方案偏差核查。

**验收结论。** 预先定义的统计口径不能被结果反向修改。研究条件不同的数据不能为了显著性强行合并。

### 2. 辅料供应商变更后的溶出波动

**现场。** 更换辅料供应商后，多个批次的溶出曲线出现尾部差异。

**怎么查。** 关联辅料型号、粒径、供应商批次、处方版本、制粒参数和设备，比较关键质量属性。

**怎么处理。** 先判断变更是否达到需要注册或验证的等级；未完成评估前不把新批次与旧批次视为完全可比。

**验收结论。** “化学名相同”的辅料可能功能不同，变更管理必须连接物料属性和工艺结果。

### 3. OOS 与稳定性时间点异常

**现场。** 长期稳定性某个时间点含量下降，复测结果又回到合格。

**怎么查。** 保留原值并检查样品、方法、设备、标准品、温湿度和检验员，区分实验室异常与产品趋势。

**怎么处理。** 按 OOS/OOT 流程调查，不删掉异常点；同时看多个批次和多时间点，而不是只挑合格复测值。

**验收结论。** 趋势分析的价值在于发现缓慢变化。只保留最终合格值会掩盖产品风险。

### 4. 多规格产品在采购系统被合并

**现场。** 医院采购把不同规格或不同批准文号的产品合并成一个编码，导致替代分析失真。

**怎么查。** 核对批准文号、剂型、规格、包装、供应商和医保支付编码，建立产品多级身份。

**怎么处理。** 采购、药房和监管数据使用统一产品主数据；替代分析必须按具体规格和批准范围。

**验收结论。** 成分相同不代表可直接替换，商业与监管身份必须保持到最小可开方单位。

### 5. 偏差批次是否可放行

**现场。** 某批生产过程中制粒时间超出验证范围，但成品检验仍合格。

**怎么查。** 判断这是否为关键参数、影响哪些质量属性、是否在验证空间内，并检查设备和操作记录。

**怎么处理。** 质量部门依据风险评估和法规要求决定放行、返工或拒绝；数据团队提供完整参数和样品链。

**验收结论。** 成品合格不能自动消除过程偏差，放行结论要同时考虑参数、风险和批准范围。

### 6. 上市后疗效反馈与批次信号

**现场。** 多个医疗机构反馈某一批次效果不佳，但没有明确的不良事件报告。

**怎么查。** 先确认产品、批号、贮存和患者使用的可比性；核对投诉时间、留样检验和同产品其他批次趋势。

**怎么处理。** 建立批次级反馈率和快速冻结规则，质量、医学和监管共同评估是否需要进一步调查。

**验收结论。** 疗效反馈不等于因果结论，但集中出现的批次信号不能只被归类为“主观感受”。

### 7. 集中采购后的供应连续性

**现场。** 中标后短期内订单快速增长，部分规格出现缺货，同时库存周转异常。

**怎么查。** 区分在产、在检、待放行、在途、配送中和真实可用库存，结合产能与放行周期。

**怎么处理。** 建立供应风险看板，优先保障临床必需规格，并对扩产或委托生产变更执行质量评估。

**验收结论。** 供应改善不能绕过质量与注册边界。库存、放行和需求必须在同一口径下管理。

七个场景可以归成一条共同判断顺序：先确认对象和时间，再确认状态和版本；然后做总量、结构和明细三层对账；最后才讨论策略、模型或工具。若一条结论不能指出对应的原始记录、责任人和行动出口，就只能算观察，不能作为生产结论。

## 6. 仿制药的第一段 SQL：重建业务链路

下面的 SQL 用于说明对象、时间、状态、版本和分层口径如何进入同一条可复查路径。表名和部分字段是通用示例，落地时应映射到企业数据字典；SQL 方言也需按实际引擎调整。

```sql
-- 仿制药：按业务对象重建链路，避免事件、快照和结果混算
WITH ranked_generic_batch_id AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY generic_batch_id
      ORDER BY updated_at DESC
    ) AS version_no
  FROM generic_batch_release
  WHERE manufactured_at >= TIMESTAMP '{start_time}'
    AND manufactured_at <  TIMESTAMP '{end_time}'
    AND release_status NOT IN ('deleted', 'test')
),
valid_rows AS (
  SELECT
    generic_batch_id,
    generic_product_id,
    site_id,
    formulation_version,
    batch_size_band,
    manufactured_at,
    release_status,
    ingested_at
  FROM ranked_generic_batch_id
  WHERE version_no = 1
)
SELECT
  generic_product_id, site_id, formulation_version, batch_size_band,
  COUNT(DISTINCT generic_batch_id) AS object_cnt,
  SUM(CASE WHEN first_release_pass THEN 1 ELSE 0 END) AS numerator_value,
  COUNT(DISTINCT generic_batch_id) AS denominator_value,
  CAST(SUM(CASE WHEN first_release_pass THEN 1 ELSE 0 END) AS DOUBLE PRECISION)
    / NULLIF(COUNT(DISTINCT generic_batch_id), 0) AS metric_value,
  MIN(manufactured_at) AS first_event_at,
  MAX(manufactured_at) AS last_event_at
FROM valid_rows
GROUP BY generic_product_id, site_id, formulation_version, batch_size_band
ORDER BY metric_value DESC, object_cnt DESC;
```

执行后至少回答六个问题：

- 同一对象是否因为多源回传产生多版本，版本保留是否符合业务要求？
- 业务时间与入仓时间是否分开，补录和迟到数据是否进入正确分区？
- 分子分母是否来自同一对象范围和同一统计窗口？
- 维度使用的是事件当时值还是当前值，跨期比较是否一致？
- 删除、撤销、冻结和测试数据是否按规则处理？
- 分组结果能否在明细中抽样复现？

## 7. 仿制药的第二段 SQL：源、控制和结果三方对账

```sql
-- 仿制药：源对象、控制对象和结果对象三方对账
WITH population AS (
  SELECT
    generic_batch_id,
    manufactured_at,
    release_status
  FROM generic_batch_release
  WHERE manufactured_at >= TIMESTAMP '{start_time}'
    AND manufactured_at <  TIMESTAMP '{end_time}'
),
control AS (
  SELECT
    generic_batch_id,
    SUM(evaluable_flag) AS control_value,
    COUNT(DISTINCT be_subject_id) AS control_cnt,
    MAX(updated_at) AS control_updated_at
  FROM be_subject_profile
  WHERE updated_at >= TIMESTAMP '{start_time}'
  GROUP BY generic_batch_id
),
result AS (
  SELECT
    generic_batch_id,
    COUNT(*) AS result_cnt,
    MAX(calculated_at) AS calculated_at
  FROM mart_generic_batch_id
  WHERE business_date BETWEEN DATE '{start_date}' AND DATE '{end_date}'
  GROUP BY generic_batch_id
)
SELECT
  COALESCE(p.generic_batch_id, c.generic_batch_id, r.generic_batch_id) AS object_key,
  CASE
    WHEN p.generic_batch_id IS NULL THEN 'source_missing'
    WHEN c.generic_batch_id IS NULL THEN 'control_missing'
    WHEN r.generic_batch_id IS NULL THEN 'result_missing'
    WHEN ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0 THEN 'count_or_value_gap'
    ELSE 'matched'
  END AS reconciliation_status,
  p.release_status,
  c.control_value,
  c.control_cnt,
  r.result_cnt,
  c.control_updated_at,
  r.calculated_at
FROM population p
FULL OUTER JOIN control c ON p.generic_batch_id = c.generic_batch_id
FULL OUTER JOIN result r ON COALESCE(p.generic_batch_id, c.generic_batch_id) = r.generic_batch_id
WHERE p.generic_batch_id IS NULL
   OR c.generic_batch_id IS NULL
   OR r.generic_batch_id IS NULL
   OR ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0;
```

这段查询故意不使用“总数相差小于某个随意百分比就算通过”。它先找出缺失对象和状态差异，再检查控制值与结果值。对于仿制药，数量、金额、时长或状态任意一项无法解释，都不能用“业务波动”代替排查。

对账结果建议分成四类处理：

1. **阻断**：对象缺失、关键时间为空、状态非法、金额或数量不守恒、权限越界。
2. **严重**：比例或总量显著偏离基线，且无法由已确认的对象结构变化解释。
3. **观察**：小范围波动但来源、样本和趋势可控，进入责任人和观察窗口。
4. **探索**：只有弱信号或假设，不进入正式结论，更不直接触发业务处罚。

## 8. 仿制药的 Python 发布门禁与指标护栏

第一段代码把发布条件写成可执行对象，避免“检查过了”只存在聊天记录里：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class GenericBatchIdBatch:
    batch_id: str
    source_rows: int
    valid_rows: int
    duplicate_keys: int
    missing_required_fields: int
    reconciliation_gap: float

def release_generic_batch_id(batch: GenericBatchIdBatch) -> dict:
    checks = {
        "source_not_empty": batch.source_rows > 0,
        "valid_rows_in_range": 0 <= batch.valid_rows <= batch.source_rows,
        "duplicate_rate_ok": batch.duplicate_keys / max(batch.source_rows, 1) <= 0.001,
        "required_fields_ok": batch.missing_required_fields == 0,
        "reconciliation_ok": abs(batch.reconciliation_gap) <= 0.01,
    }
    return {
        "topic": "仿制药",
        "batch_id": batch.batch_id,
        "checks": checks,
        "release_allowed": all(checks.values()),
        "blocking_checks": [name for name, passed in checks.items() if not passed],
    }
```

第二段代码演示如何为比例类结果附带样本证据和小样本下界。它不是替代统计学家的模型，而是防止把少量偶然样本直接包装成稳定结论：

```python
from dataclasses import dataclass
from math import sqrt

@dataclass(frozen=True)
class GenericBatchIdObservation:
    object_id: str
    numerator: float
    denominator: float
    sample_size: int
    scope_version: str

def calculate_generic_batch_id(rows: list[GenericBatchIdObservation]) -> list[dict]:
    output = []
    for row in rows:
        value = row.numerator / row.denominator if row.denominator > 0 else None
        # 小样本用 Wilson 下界做护栏，不把偶然的高比例直接当稳定结果。
        z = 1.96
        p = value or 0
        n = max(row.sample_size, 1)
        center = p + z * z / (2 * n)
        margin = z * sqrt((p * (1 - p) + z * z / (4 * n)) / n)
        lower = max(0, (center - margin) / (1 + z * z / n))
        output.append({
            "object_id": row.object_id,
            "metric": "生物等效性研究完成率",
            "value": value,
            "lower_bound": lower if value is not None else None,
            "sample_size": row.sample_size,
            "scope_version": row.scope_version,
            "caution": "退出、呕吐、异常采样和方案偏离要分开",
        })
    return output
```

真正上线时还要补充参数配置、日志、血缘、告警级别、重跑幂等、异常样本保存和审批记录。代码通过不代表业务通过；自动检查只能证明已经定义的规则没有被违反，无法证明规则本身一定正确。

## 9. 仿制药的失败反例与上线验收

| 风险信号 | 错误做法 | 必须补齐的证据 | 发布或行动规则 |
| --- | --- | --- | --- |
| 参比关系模糊 | 只记录原研商品名，不记录具体规格和来源 | 参比制剂目录、来源批次与批准版本 | 无明确参比关系不得开展比较 |
| BE 口径被反复挑选 | 排除标准随结果变化 | 方案、分析集、排除原因和统计代码 | 分析方案冻结后才看分组结果 |
| 变更等级低估 | 辅料或设备变更未经评估直接生产 | 变更单、验证批次和质量属性 | 达到阈值必须走注册或验证流程 |
| 市场替代越界 | 仅按价格把所有同成分产品视为可互换 | 批准、支付与临床可替代规则 | 替代清单必须有专业批准 |

上线验收不应只有一句“报表正常”。建议按下面四层验收：

| 验收对象 | 结构要求 | 测试样本 | 结果证据 |
| --- | --- | --- | --- |
| 仿制产品 | `generic_product_id` 能唯一定位活性成分、剂型、规格和批准持有人 | 正常、重复、缺失、撤销与跨期样本 | 生物等效性研究完成率可回到原始对象 |
| 参比关系 | `reference_product_id` 能唯一定位具体参比制剂、来源和有效版本 | 正常、重复、缺失、撤销与跨期样本 | 关键药代参数可评估率可回到原始对象 |
| 处方工艺 | `formulation_version_id` 能唯一定位批次、辅料来源和关键参数 | 正常、重复、缺失、撤销与跨期样本 | 商业批次一次放行率可回到原始对象 |
| 生物等效性研究 | `be_study_id` 能唯一定位设计、人群、采样和统计方案 | 正常、重复、缺失、撤销与跨期样本 | 溶出曲线可比率可回到原始对象 |
| 商业批次 | `generic_batch_id` 能唯一定位生产、检验和放行记录 | 正常、重复、缺失、撤销与跨期样本 | 投诉批次闭环率可回到原始对象 |
| 质量反馈 | `product_quality_case_id` 能唯一定位投诉、留样复核和召回影响 | 正常、重复、缺失、撤销与跨期样本 | 生物等效性研究完成率可回到原始对象 |

还应为每一次发布保留一组固定回归样本：正常对象、边界状态、重复记录、缺失字段、撤销或退款、跨期、权限拒绝和失败恢复。回归样本不是演示数据，而是以后每次改规则都能重复执行的质量资产。

| 阶段 | 主要交付 | 通过条件 |

如果必须用 90 秒说明“仿制药”是否做对，可以按这个顺序自测：

1. 一行数据代表什么，主键是什么，哪些对象绝不能混在同一粒度？
2. 业务发生、数据可见、计算完成和行动确认分别在哪个时间点？
3. 本主题最重要的两个主指标、三个护栏和最小样本量是什么？
4. 一个异常出现时，先从原始记录、链路版本还是业务动作开始查？
5. 哪类错误必须阻断发布或停止使用，谁有权批准例外？
6. 上线后由谁在多长时间内观察，什么条件下回滚或结束？
