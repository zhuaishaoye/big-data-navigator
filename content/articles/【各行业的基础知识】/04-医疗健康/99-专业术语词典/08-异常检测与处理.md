# 异常检测与处理

> [!tip] 分析目标
> 如果只记住“异常检测与处理”的定义，遇到真实数据时仍然很难行动。本文把它拆成五个可检查问题：谁在使用、流程在哪里变化、数据一行代表什么、异常如何发现、上线后用哪个指标验收。每个部分都配一个工作案例或代码片段。

## 1. 把主题翻译成可验证的问题

“异常检测与处理”不能直接等同于“做一张趋势图”。一个可执行的分析问题至少包含对象、时间、比较基准和行动：

> 在【观察周期】内，对【有效对象】按【院区、科室、病种】比较【费用偏差率】与【门急诊人次】，判断变化来自结构、行为还是数据口径，并验证【策略动作】是否带来可解释的增量。

在医疗健康场景中，用户行为、交易结果和策略曝光经常来自不同系统。先画数据流：

HIS → EMR → LIS → RIS → PACS → 医保结算系统

图中至少要有三个标记：业务事件发生时间、数据可见时间、策略或行动时间。只有三者分开，后续才能判断问题发生在业务、链路还是观察窗口。

## 2. 指标定义与分母检查

| 专题观测面 | 需要回答的问题 | 关键证据 | 判定与动作 |
| --- | --- | --- | --- |
| 闭环（本标题优先） | 谁在何时处理，是否复发，修复是否验证 | 工单、根因、修复时长、复发率和复核记录 | 只告警不闭环的规则应下线重做 |
| 准确性 | 值与业务事实、源系统或计算规则是否一致 | 抽样单据、金额平衡、枚举与公式复核 | 差异分类后登记工单 |
| 及时性 | 数据何时可用，是否满足消费者 SLA | 分区完成时间、端到端延迟和告警时间 | 超 SLA 自动通知并标记影响 |
| 完整性 | 分区、记录和关键字段是否缺失 | 覆盖日期、行数基线、空值率和源目标计数 | 关键资产缺失时阻断发布 |

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 门急诊人次 | `COUNT(DISTINCT visit_id)`（视图字段 `visit_cnt`） | 院区、科室、病种 | 不混用测试、撤销和跨期状态；与“异常检测与处理”相关时还要补充主题筛选 |
| 平均住院日 | `SUM(discharge_days) / COUNT(DISTINCT inpatient_visit_id)`（视图字段 `avg_los`） | 科室、病种、人群 | 不混用测试、撤销和跨期状态；与“异常检测与处理”相关时还要补充主题筛选 |
| 复诊率 | `COUNT(DISTINCT revisit_patient_id) / COUNT(DISTINCT index_patient_id)`（视图字段 `revisit_rate`） | 病种、人群、支付方式 | 不混用测试、撤销和跨期状态；与“异常检测与处理”相关时还要补充主题筛选 |
| 异常检验占比 | `COUNT(DISTINCT abnormal_report_id) / COUNT(DISTINCT report_id)`（视图字段 `abnormal_rate`） | 人群、支付方式 | 不混用测试、撤销和跨期状态；与“异常检测与处理”相关时还要补充主题筛选 |

针对“异常检测与处理”，建议分别定义诊断指标、结果指标和护栏指标：

- **诊断指标**用于定位流程，例如曝光、有效访问、符合条件对象数和异常节点。
- **结果指标**用于判断是否改善，例如转化、留存、客单、毛利或处理时长。
- **护栏指标**用于防止局部优化伤害整体，例如退款、投诉、成本、公平性和长期留存。

每次计算都问四个问题：分母是谁、对象何时进入分母、例外状态怎么处理、窗口是否足够覆盖行为完成。尤其是患者隐私泄露；多院区患者主索引重复；临床时间与计费时间混用，任何一项没有解释清楚，指标都可能“看起来合理但无法决策”。

## 3. 方法选择：描述、诊断、预测还是因果

| 目标 | 适合的方法 | 需要的证据 | 不要混淆 |
| --- | --- | --- | --- |
| 描述现状 | 趋势、结构、同期群 | 完整口径、稳定时间窗 | 描述不等于原因 |
| 定位异常 | 分层、贡献度、漏斗、异常检测 | 原始事件、基线和质量检查 | 排名靠前不等于因果 |
| 预测未来 | 时间序列、回归、机器学习 | 时间切分验证、误差成本 | 离线准确率不等于业务收益 |
| 评估策略 | A/B、灰度、准实验 | 对照组、样本量、护栏指标 | 上线前后对比容易混入季节和选择偏差 |

如果问题只是“发生了什么”，先别急着建模；如果问题涉及“采取某策略会怎样”，就必须讨论反事实和识别条件。围绕“异常检测与处理”，应把观察分析、预测和因果评估的产出分开标注。

## 4. 案例一：华北某医学影像中心

### 案例 1：华北某医学影像中心的“异常检测与处理”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“异常检测与处理”映射到“数据质量规则、监控与闭环”中的闭环，而不是泛泛讨论概念。
- **触发事件**：影像检查量持续增长，但报告及时率波动明显，疑似与设备、检查部位和审核流程有关。
- **业务与数据范围**：检查申请、排队、扫描、图像归档、初诊、复审和报告发布日志。数据侧重点采集工单、根因、修复时长、复发率和复核记录，并与HIS、EMR、LIS中的时间、状态和责任人信息对齐。
- **需要回答的问题**：谁在何时处理，是否复发，修复是否验证。
- **关键障碍**：PACS 与 RIS 状态含义不同，设备停机时间没有进入分析链路，节假日排班缺失。同时要防止患者隐私泄露把表面指标带偏。
- **处理过程**：统一检查状态机，补充设备日历和人员排班，按检查部位、设备型号与班次分析报告时延。实施时把“关键规则必须绑定资产、负责人、严重等级、失败动作和复核时限”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例项目将问题拆分为设备等待、初诊积压和复审返工三类，并建立分位数时延监控。验收至少同时看主指标、工单、根因、修复时长、复发率和复核记录和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把质量规则绑定到关键资产、严重等级、责任人和失败动作，通过样本回查和趋势监控区分数据问题与业务变化。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

落地时建议先把一个总指标拆成可行动的树：

```text
异常检测与处理｜费用偏差率结果偏离
├── 先验真伪：患者主索引跨院区唯一是否有批次级证据
├── 再看规模：患者数量与门急诊人次是否同向变化
├── 结构定位：院区 → 科室 → 病种
├── 链路时点：HIS → EMR → LIS
└── 行动出口：关键规则必须绑定资产、负责人、严重等级、失败动作和复核时限
```

如果某一分支变化最大，再进入下一层，而不是一开始就按十几个维度切碎。每个分层结果都应同时报告样本量，避免小样本的极端比例抢走注意力。

## 5. SQL：计算趋势、结构和贡献度

### 趋势、结构与贡献度诊断

```sql
-- 异常检测与处理：结构贡献诊断（支付方式 × 科室）
WITH scoped AS (
  SELECT
    patient_id AS entity_key,
    event_id,
    event_date AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_medical_event
  WHERE event_date >= DATE '2026-01-01'
    AND event_date <  DATE '2026-04-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '平均住院日' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

示例 SQL 只表达计算逻辑。实际实施应加入分区条件、业务状态过滤、时区和主题范围，并在结果中保留口径版本。

## 6. 案例二：华南某零售会员团队

### 案例 2：华南某零售会员团队的“异常检测与处理”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“异常检测与处理”映射到“数据质量规则、监控与闭环”中的准确性，而不是泛泛讨论概念。
- **触发事件**：会员分层结果一周内多次变化，运营无法确定触达名单。
- **业务与数据范围**：会员主数据、订单、退款、标签版本、更新时间和分层规则。数据侧重点采集抽样单据、金额平衡、枚举与公式复核，并与HIS、EMR、LIS中的时间、状态和责任人信息对齐。
- **需要回答的问题**：值与业务事实、源系统或计算规则是否一致。
- **关键障碍**：测试会员未排除，退款未冲减，标签规则更新没有版本记录。同时要防止多院区患者主索引重复把表面指标带偏。
- **处理过程**：增加业务对象范围检查、历史回放和版本对比，先隔离异常会员再发布名单。实施时把“同时覆盖完整性、唯一性、准确性、及时性和一致性，不只查空值”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：复合案例将问题拆成输入质量、规则变更和正常行为变化。验收至少同时看主指标、抽样单据、金额平衡、枚举与公式复核和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把质量规则绑定到关键资产、严重等级、责任人和失败动作，通过样本回查和趋势监控区分数据问题与业务变化。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

当业务方要求“解释为什么下降”时，可以按下面顺序回答：

1. 先确认下降是否真实存在，排查采集、任务、维表和状态映射。
2. 把变化拆成对象数量、行为强度和结构占比。
3. 找到贡献最大的分组，但保留其他分组的抵消效应。
4. 抽取正负样本回查业务事件和操作日志。
5. 把尚不能证明的解释标为假设，并设计下一轮验证。

## 8. 异常、偏差与常见误区

- **辛普森悖论**：总体改善但每个分组都变差，可能由对象结构变化造成。
- **幸存者偏差**：只分析完成流程的对象，忽略中途流失和中止。
- **分母漂移**：渠道口径、登录状态、版本或活动范围变化，改变可比性。
- **回传延迟**：当天数据未回补，导致近期效果被系统性低估。
- **多重比较**：反复寻找显著分组，实际只是随机波动。
- **行动偏差**：只报告支持既定方案的结果，忽略反例和护栏指标。

围绕“异常检测与处理”，应预先写出至少三条反例检查。比如结论是否能回到明细、指标是否在同一对象和同一时间窗内计算，以及 数据质量异常是否与业务变化分开。

## 9. 第三个案例：华中某互联网医院

### 案例 3：华中某互联网医院的“异常检测与处理”现场

## 10. 交付物与工作节奏

### 案例 4：异常检测与处理从源事件到结果的长链路核查

一次例行发布后，负责“异常检测与处理”的小组收到下游反馈：数字和源系统对不上，但任务本身全部成功。团队决定围绕“链路断点与延迟”做一次完整回放。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 把业务发生时间、数据可见时间、任务完成时间和下游消费时间放到同一条证据链。在本场景里，核心风险还包括历史诊断编码版本失效，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：患者、就诊及其在出院与结算前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注patient_id与visit_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 结果表出现缺失或延迟，单看调度状态却显示成功，无法判断问题发生在源端、接入、计算还是服务层。初看时，RIS与PACS的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 源端操作日志、CDC/批次水位、分区清单、任务参数、血缘关系、下游请求日志。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“医技科室”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“异常检测与处理”的当前定义并记录版本；第二步用患者明细核对RIS到PACS的关联；第三步按支付方式与科室做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察费用偏差率和护栏指标平均住院日。
- **行动与护栏：** 按时间轴核对每一跳的输入输出计数与水位，先阻断错误结果扩散，再确定重跑范围和补数窗口。专题检查项“关键规则必须绑定资产、负责人、严重等级、失败动作和复核时限”被写成发布门禁，无法证明数据完整的链路不进入正式发布，优先保留旧版本供下游读取。
- **失败路径：** 看到任务成功就立即补数，却没有确认重复、乱序和迟到事件。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“异常检测与处理”时，先验证工单、根因、修复时长、复发率和复核记录，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由医技科室在明确时限内，根据费用偏差率、平均住院日和费用明细与结算总额可对账决定继续、回退、补查还是转人工。 若历史诊断编码版本失效或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

- **处理步骤：** 第一步先冻结“异常检测与处理”的当前定义并记录版本；第二步用检查检验明细核对随访平台到HIS的关联；第三步按病种与支付方式做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察复诊率和护栏指标费用偏差率。
- **行动与护栏：** 组织上游生产、数据开发、消费方和安全人员做一次契约评审，把模糊责任改成可执行的检查项。专题检查项“用发现前移、误报率、闭环时长和复发率衡量治理效果”被写成发布门禁，业务定义、粒度或状态语义发生破坏性变化时，未通知消费者不得直接发布。
- **失败路径：** 只建立群聊和文档链接，却没有版本、负责人、失败动作和下线流程。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“异常检测与处理”时，先验证覆盖日期、行数基线、空值率和源目标计数，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由信息中心在明确时限内，根据复诊率、费用偏差率和诊断编码在有效版本内决定继续、回退、补查还是转人工。 若临床时间与计费时间混用或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从异常检测与处理回到可核对明细

```sql
-- 异常检测与处理：字段血缘与影响范围
WITH changed_columns AS (
  SELECT column_name
  FROM information_schema.columns
  WHERE table_schema = :source_schema
    AND table_name = :source_table
    AND last_altered_at >= :change_time
),
downstream_assets AS (
  SELECT
    asset_id,
    asset_name,
    asset_type,
    owner_name,
    criticality,
    last_used_at
  FROM metadata_asset_relation
  WHERE upstream_asset_id = :source_asset_id
    AND relation_status = 'active'
)
SELECT
  d.asset_id,
  d.asset_name,
  d.asset_type,
  d.owner_name,
  d.criticality,
  d.last_used_at,
  COUNT(c.column_name) AS changed_column_cnt,
  CASE
    WHEN d.criticality IN ('core', 'regulated') THEN 'block_release'
    WHEN d.last_used_at >= CURRENT_DATE - INTERVAL '7 days' THEN 'notify_owner'
    ELSE 'register_review'
  END AS required_action
FROM downstream_assets d
CROSS JOIN changed_columns c
GROUP BY d.asset_id, d.asset_name, d.asset_type, d.owner_name, d.criticality, d.last_used_at
ORDER BY
  CASE WHEN d.criticality IN ('core', 'regulated') THEN 0 ELSE 1 END,
  d.last_used_at DESC;

-- 目标：变更前识别 HIS、EMR、LIS 之后的所有结果与消费者。
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把异常检测与处理的验收证据写成门禁

```python
import json
from pathlib import Path


def build_evidence_manifest(
    subject: str,
    scope: dict,
    checks: dict,
    samples: list[dict],
    owner: str,
) -> dict:
    failed = [name for name, passed in checks.items() if not passed]
    return {
        "subject": subject,
        "scope": scope,
        "checks": checks,
        "failed_checks": failed,
        "sample_evidence": samples[:5],
        "owner": owner,
        "decision": "block" if failed else "review",
        "manual_questions": [
            "每一项失败是否已回到原始记录",
            "对象、时间和状态是否与指标字典一致",
            "回滚或修复后是否重新完成对账",
        ],
    }


manifest = build_evidence_manifest(
    subject="异常检测与处理",
    scope={"systems": ["HIS","EMR","LIS","RIS"]},
    checks={"definition_frozen": False, "reconciled": False},
    samples=[],
    owner="患者",
)
Path("release-evidence.json").write_text(
    json.dumps(manifest, ensure_ascii=False, indent=2),
    encoding="utf-8",
)
print(manifest["decision"])
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。

### 四个案例共用的验收清单

| 验证面 | 发布前问题 | 证据 | 不通过时 |
| --- | --- | --- | --- |
