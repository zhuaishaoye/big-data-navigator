# 原研药

> [!abstract] 创新药与原创产品实战手册
> 原研药的核心是首个完成完整研发和注册证据链、获得上市批准的原创药品。数据工作不能只记录商品名和价格，而要把化合物或生物制品、适应证、临床试验、批准范围、批次、安全性、专利与市场准入放在同一条生命周期中。

## 1. 原研药：定义、适用边界与决策出口

原研药的核心是首个完成完整研发和注册证据链、获得上市批准的原创药品。数据工作不能只记录商品名和价格，而要把化合物或生物制品、适应证、临床试验、批准范围、批次、安全性、专利与市场准入放在同一条生命周期中。

**本篇的适用边界。** 本篇把原研药视为具有原创研发和监管批准证据的产品，不把任何先上市的品牌药、进口药或高价格药自动认定为原研药。

**最常见的错误替代。** 不能用商品名唯一识别产品，也不能仅凭专利到期、价格高低或市场份额判断其原研属性。

**最终决策。** 研发、医学、准入和供应团队要判断：证据是否支持继续研发、注册和适应证扩展，产品能否在特定市场供应，以及安全性信号是否需要更新说明。 因此，这篇内容不从“应该建哪张表”开始，而从业务动作、责任人和失败后果开始。只有先确定谁在什么时点做出什么决定，字段、SQL、看板和模型才有明确用途。

围绕“原研药”，工作中至少要区分四类问题：

1. **身份问题**：对象是谁，主键能否跨系统稳定关联，合并、拆分、撤销后历史是否还看得见。
2. **时间问题**：业务发生、状态生效、数据入仓、计算完成和人员行动分别发生在哪一刻。
3. **状态问题**：当前状态是一段事件、一张快照还是最终结果，空值代表未发生、未采集还是已删除。
4. **责任问题**：谁确认口径，谁处理异常，谁有权放行或停止，谁在观察期后复盘。

## 2. 原研药的完整业务流程

| 环节 | 要做的事 | 最小证据 | 失败后先查什么 |
| --- | --- | --- | --- |
| 靶点与候选物评估 | 形成作用机制、成药性和差异化假设 | 研究方案、实验记录、候选物版本 | 换包装后历史轨迹断裂 |
| 非临床研究 | 完成药理、毒理和药代等证据 | 研究报告、动物批次、质量数据 | 自发报告增加被解释为风险增加 |
| 临床试验申请与实施 | 按阶段验证安全性、剂量和有效性 | 方案版本、入排、受试者、不良事件和偏离 | 跨版本终点和人群直接比较 |
| 注册申报与审评 | 提交质量、非临床和临床证据并回应问询 | 申报包、审评问题、批准范围 | 受试者级数据被复制到个人环境 |
| 商业化生产与供应 | 确认工艺验证、批放行和供应链连续性 | 批记录、放行、稳定性、库存 | 换包装后历史轨迹断裂 |
| 上市后安全与生命周期 | 持续监测不良反应、新证据和适应证变化 | 个例报告、信号、说明书版本 | 自发报告增加被解释为风险增加 |

把 靶点与候选物评估、非临床研究、临床试验申请与实施、注册申报与审评、商业化生产与供应、上市后安全与生命周期 串起来后可以看出，原研药不是一个孤立字段，而是一条会跨系统、跨岗位、跨时间的证据链。流程图上每一段都应标出输入、输出、状态、时间戳、责任人和异常出口。只要其中一段只能靠口头解释，后续的统计、追责和自动化就会失去基础。

一个合格的需求说明应该写成：

> 在【授权数据范围】和【观察窗口】内，围绕“原研药”的【药品主数据】，按【trial_id、site_id、country_code、study_arm】比较【试验入组达成率】及其【方案偏离发生率】，定位一个可干预节点；行动后同时观察主指标、样本量和护栏，任何高风险异常先阻断再调查。

## 3. 原研药的数据对象与系统契约

| 数据对象 | 建议主键 | 一行代表什么 | 不允许混淆 |
| --- | --- | --- | --- |
| 药品主数据 | `medicinal_product_id` | 活性成分、剂型、规格和批准持有人 | 对象身份与业务事件 |
| 临床试验 | `clinical_trial_id` | 方案版本、阶段、适应证和研究中心 | 事件、状态快照和结果粒度 |
| 受试者暴露 | `subject_exposure_id` | 受试者在某阶段的实际用药暴露 | 事件、状态快照和结果粒度 |
| 批准与说明书 | `regulatory_approval_id` | 国家、适应证、版本和有效期 | 事件、状态快照和结果粒度 |
| 商业批次 | `commercial_batch_id` | 生产、放行和供应批次 | 事件、状态快照和结果粒度 |
| 安全事件 | `safety_case_id` | 个例安全报告及因果关系评估 | 事件、状态快照和结果粒度 |

对象表不是把所有字段塞进一张宽表。事件、状态快照和结果表应该分别保留粒度，再通过稳定主键与版本建立关联。尤其要避免三个常见混算：把一次业务事件算成多个对象、把每日快照相加当事件总量、把最新状态覆盖历史状态。

本主题的数据契约至少应包含：

- `subject_visit_id` 的唯一性规则、生成方式和跨系统映射。
- `visit_date` 的业务含义、时区、迟到和补录规则。
- `visit_status` 的完整状态集合，以及删除、撤销、冻结和失效的表示方法。
- 控制对象 `clinical_subject_exposure.subject_exposure_id` 与主对象的关系。
- 每次口径、规则、模型或源版本变化的影响范围和下游通知对象。
- 敏感字段、允许用途、访问角色、导出限制和审计保留时间。

## 4. 原研药的指标、样本与验收口径

| 指标 | 公式或定义 | 口径提醒 |
| --- | --- | --- |
| 试验入组达成率 | 实际入组合格受试者数 / 计划入组数 | 必须按中心、阶段和时点，不用筛选人数代替 |
| 方案偏离发生率 | 发生至少一次重要方案偏离的受试者数 / 已入组受试者数 | 偏离严重程度和是否影响主要终点要单列 |
| 批放行一次通过率 | 首次放行合格的商业批次 / 提交放行的批次 | 稳定性、检验和文档缺陷要分类 |
| 安全报告按时率 | 在监管时限内提交的有效个例报告 / 应提交报告 | 起算时间与报告完整性要同时检查 |
| 适应证覆盖完整率 | 已映射到标准适应证和批准版本的记录 / 应映射记录 | 不能用自由文本直接做跨市场比较 |

指标字典至少写到“任何人都能按同一份数据复跑”的程度：中文名、业务定义、公式、分子、分母、事实粒度、时间字段、对象范围、排除项、版本、负责人和验收样例，一个都不能少。比例指标必须同时展示分子、分母和样本量；金额或数量必须做守恒；状态指标必须能回到事件时间线。

对于“原研药”，建议把观察分成三层：

| 层次 | 看什么 | 不能替代什么 |
| --- | --- | --- |
| 业务结果 | 试验入组达成率、方案偏离发生率 | 不能替代过程证据和个案回查 |
| 过程护栏 | 批放行一次通过率、安全报告按时率、适应证覆盖完整率 | 不能因为护栏暂时正常就跳过异常调查 |
| 数据证据 | 主键、时间、状态、版本、来源目标对账 | 不能只看任务成功或报表能打开 |

## 5. 原研药：七个真实工作场景

以下七组场景均为公开方法结合常见工作流程构造的“脱敏复合示例”，不对应任何单一企业、患者、客户或雇员事实。场景的目的，是展示如何从现象走到证据、行动和验收，而不是虚构经营成果。

### 1. 全球试验与本地注册口径不一致

**现场。** 总部试验数据库和本地注册资料中的适应证名称、剂量组和主要终点定义不一致。

**怎么查。** 建立试验、方案版本、国家、监管词典和批准适应证映射，逐项比较版本生效时间。

**怎么处理。** 保留原始值和标准映射值；任何注册结论都引用具体方案版本和监管词典版本。

**验收结论。** 同名不一定是同定义。跨市场分析先确认版本和适用人群，再比较结果。

### 2. 入组速度看似正常但合格率下降

**现场。** 某中心月度入组数达标，但随机化后退出和方案偏离上升。

**怎么查。** 把筛选、合格、入组、暴露、随访和退出分层，发现筛查标准执行偏差集中在少数研究团队。

**怎么处理。** 将入组和质量指标并列，补充中心培训与源数据核查；不按总人数奖励导致质量下降。

**验收结论。** 只考核数量会诱导错误行为。研发指标必须带质量护栏。

### 3. 批次供应链事件

**现场。** 某商业批次出现包装缺陷，供应团队需要判断受影响市场与替代库存。

**怎么查。** 按批次、包装线、放行市场、库存位置和发货记录建立正向与反向追溯。

**怎么处理。** 冻结相关批次，区分仍可安全使用、需要召回和仅标签整改的范围，并同步医学与监管沟通。

**验收结论。** 供应链数据必须能回答“这一批去了哪里、哪些患者可能暴露、还有哪些替代库存”。

### 4. 说明书版本更新后的历史数据比较

**现场。** 说明书新增安全性信息后，运营仍用旧适应证范围统计使用量。

**怎么查。** 为说明书和批准适应证建立有效期，按事件发生时间关联当时版本。

**怎么处理。** 所有安全和使用分析使用时点正确版本，并标记跨版本不可直接比较的区间。

**验收结论。** 监管文本也是维度。用当前说明书回溯历史，会产生看似精确但语义错误的结论。

### 5. 安全信号回顾中的分母问题

**现场。** 某不良事件报告数增加，被误判为风险显著上升。

**怎么查。** 同时核对暴露人数、报告来源、报告完整度、上市时间和媒体关注；区分报告率与真实发生率。

**怎么处理。** 建立报告来源和时间趋势分层，注明自发报告无法直接计算发生率，交由药物警戒专业评估。

**验收结论。** 报告数不是发生率。数据团队必须阻止把被动报告直接包装成因果关系。

### 6. 专利到期后的产品识别

**现场。** 采购数据用商品名变化判断原研药是否被仿制药替代。

**怎么查。** 核对活性成分、批准持有人、批准文号、剂型规格和医保支付规则，而非只看名称。

**怎么处理。** 建立产品-批准-商品名-包装多级映射，并保留时间有效期。

**验收结论。** 商业名称会变，产品与监管身份不能随之丢失。

### 7. 研究数据共享与隐私边界

**现场。** 跨机构分析希望直接共享受试者级原始数据。

**怎么查。** 确认知情同意范围、数据使用协议、去标识化程度、跨境要求和最小必要字段。

**怎么处理。** 优先使用汇总或受控环境分析；申请流程、访问日志和销毁规则进入数据契约。

**验收结论。** 能分析不等于能复制。受试者数据共享必须由授权、用途和审计共同限定。

七个场景可以归成一条共同判断顺序：先确认对象和时间，再确认状态和版本；然后做总量、结构和明细三层对账；最后才讨论策略、模型或工具。若一条结论不能指出对应的原始记录、责任人和行动出口，就只能算观察，不能作为生产结论。

## 6. 原研药的第一段 SQL：重建业务链路

下面的 SQL 用于说明对象、时间、状态、版本和分层口径如何进入同一条可复查路径。表名和部分字段是通用示例，落地时应映射到企业数据字典；SQL 方言也需按实际引擎调整。

```sql
-- 原研药：按业务对象重建链路，避免事件、快照和结果混算
WITH ranked_subject_visit_id AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY subject_visit_id
      ORDER BY updated_at DESC
    ) AS version_no
  FROM clinical_subject_visit
  WHERE visit_date >= TIMESTAMP '{start_time}'
    AND visit_date <  TIMESTAMP '{end_time}'
    AND visit_status NOT IN ('deleted', 'test')
),
valid_rows AS (
  SELECT
    subject_visit_id,
    trial_id,
    site_id,
    country_code,
    study_arm,
    visit_date,
    visit_status,
    ingested_at
  FROM ranked_subject_visit_id
  WHERE version_no = 1
)
SELECT
  trial_id, site_id, country_code, study_arm,
  COUNT(DISTINCT subject_visit_id) AS object_cnt,
  COUNT(DISTINCT CASE WHEN visit_status = 'completed' THEN subject_id END) AS numerator_value,
  COUNT(DISTINCT subject_id) AS denominator_value,
  CAST(COUNT(DISTINCT CASE WHEN visit_status = 'completed' THEN subject_id END) AS DOUBLE PRECISION)
    / NULLIF(COUNT(DISTINCT subject_id), 0) AS metric_value,
  MIN(visit_date) AS first_event_at,
  MAX(visit_date) AS last_event_at
FROM valid_rows
GROUP BY trial_id, site_id, country_code, study_arm
ORDER BY metric_value DESC, object_cnt DESC;
```

执行后至少回答六个问题：

- 同一对象是否因为多源回传产生多版本，版本保留是否符合业务要求？
- 业务时间与入仓时间是否分开，补录和迟到数据是否进入正确分区？
- 分子分母是否来自同一对象范围和同一统计窗口？
- 维度使用的是事件当时值还是当前值，跨期比较是否一致？
- 删除、撤销、冻结和测试数据是否按规则处理？
- 分组结果能否在明细中抽样复现？

## 7. 原研药的第二段 SQL：源、控制和结果三方对账

```sql
-- 原研药：源对象、控制对象和结果对象三方对账
WITH population AS (
  SELECT
    subject_visit_id,
    visit_date,
    visit_status
  FROM clinical_subject_visit
  WHERE visit_date >= TIMESTAMP '{start_time}'
    AND visit_date <  TIMESTAMP '{end_time}'
),
control AS (
  SELECT
    subject_visit_id,
    SUM(exposure_dose) AS control_value,
    COUNT(DISTINCT subject_exposure_id) AS control_cnt,
    MAX(updated_at) AS control_updated_at
  FROM clinical_subject_exposure
  WHERE updated_at >= TIMESTAMP '{start_time}'
  GROUP BY subject_visit_id
),
result AS (
  SELECT
    subject_visit_id,
    COUNT(*) AS result_cnt,
    MAX(calculated_at) AS calculated_at
  FROM mart_subject_visit_id
  WHERE business_date BETWEEN DATE '{start_date}' AND DATE '{end_date}'
  GROUP BY subject_visit_id
)
SELECT
  COALESCE(p.subject_visit_id, c.subject_visit_id, r.subject_visit_id) AS object_key,
  CASE
    WHEN p.subject_visit_id IS NULL THEN 'source_missing'
    WHEN c.subject_visit_id IS NULL THEN 'control_missing'
    WHEN r.subject_visit_id IS NULL THEN 'result_missing'
    WHEN ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0 THEN 'count_or_value_gap'
    ELSE 'matched'
  END AS reconciliation_status,
  p.visit_status,
  c.control_value,
  c.control_cnt,
  r.result_cnt,
  c.control_updated_at,
  r.calculated_at
FROM population p
FULL OUTER JOIN control c ON p.subject_visit_id = c.subject_visit_id
FULL OUTER JOIN result r ON COALESCE(p.subject_visit_id, c.subject_visit_id) = r.subject_visit_id
WHERE p.subject_visit_id IS NULL
   OR c.subject_visit_id IS NULL
   OR r.subject_visit_id IS NULL
   OR ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0;
```

这段查询故意不使用“总数相差小于某个随意百分比就算通过”。它先找出缺失对象和状态差异，再检查控制值与结果值。对于原研药，数量、金额、时长或状态任意一项无法解释，都不能用“业务波动”代替排查。

对账结果建议分成四类处理：

1. **阻断**：对象缺失、关键时间为空、状态非法、金额或数量不守恒、权限越界。
2. **严重**：比例或总量显著偏离基线，且无法由已确认的对象结构变化解释。
3. **观察**：小范围波动但来源、样本和趋势可控，进入责任人和观察窗口。
4. **探索**：只有弱信号或假设，不进入正式结论，更不直接触发业务处罚。

## 8. 原研药的 Python 发布门禁与指标护栏

第一段代码把发布条件写成可执行对象，避免“检查过了”只存在聊天记录里：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class SubjectVisitIdBatch:
    batch_id: str
    source_rows: int
    valid_rows: int
    duplicate_keys: int
    missing_required_fields: int
    reconciliation_gap: float

def release_subject_visit_id(batch: SubjectVisitIdBatch) -> dict:
    checks = {
        "source_not_empty": batch.source_rows > 0,
        "valid_rows_in_range": 0 <= batch.valid_rows <= batch.source_rows,
        "duplicate_rate_ok": batch.duplicate_keys / max(batch.source_rows, 1) <= 0.001,
        "required_fields_ok": batch.missing_required_fields == 0,
        "reconciliation_ok": abs(batch.reconciliation_gap) <= 0.01,
    }
    return {
        "topic": "原研药",
        "batch_id": batch.batch_id,
        "checks": checks,
        "release_allowed": all(checks.values()),
        "blocking_checks": [name for name, passed in checks.items() if not passed],
    }
```

第二段代码演示如何为比例类结果附带样本证据和小样本下界。它不是替代统计学家的模型，而是防止把少量偶然样本直接包装成稳定结论：

```python
from dataclasses import dataclass
from math import sqrt

@dataclass(frozen=True)
class SubjectVisitIdObservation:
    object_id: str
    numerator: float
    denominator: float
    sample_size: int
    scope_version: str

def calculate_subject_visit_id(rows: list[SubjectVisitIdObservation]) -> list[dict]:
    output = []
    for row in rows:
        value = row.numerator / row.denominator if row.denominator > 0 else None
        # 小样本用 Wilson 下界做护栏，不把偶然的高比例直接当稳定结果。
        z = 1.96
        p = value or 0
        n = max(row.sample_size, 1)
        center = p + z * z / (2 * n)
        margin = z * sqrt((p * (1 - p) + z * z / (4 * n)) / n)
        lower = max(0, (center - margin) / (1 + z * z / n))
        output.append({
            "object_id": row.object_id,
            "metric": "试验入组达成率",
            "value": value,
            "lower_bound": lower if value is not None else None,
            "sample_size": row.sample_size,
            "scope_version": row.scope_version,
            "caution": "必须按中心、阶段和时点，不用筛选人数代替",
        })
    return output
```

真正上线时还要补充参数配置、日志、血缘、告警级别、重跑幂等、异常样本保存和审批记录。代码通过不代表业务通过；自动检查只能证明已经定义的规则没有被违反，无法证明规则本身一定正确。

## 9. 原研药的失败反例与上线验收

| 风险信号 | 错误做法 | 必须补齐的证据 | 发布或行动规则 |
| --- | --- | --- | --- |
| 商品名代替产品 | 换包装后历史轨迹断裂 | 批准文号、持有人的有效期与别名表 | 产品身份以监管主数据为准 |
| 报告数当发生率 | 自发报告增加被解释为风险增加 | 暴露分母、来源和报告完整度 | 禁止无分母的因果结论 |
| 方案版本混用 | 跨版本终点和人群直接比较 | 方案、词典和分析集版本 | 版本变化进入可比性声明 |
| 安全数据越权 | 受试者级数据被复制到个人环境 | 授权用途、最小字段和访问日志 | 未授权数据不得离开受控环境 |

上线验收不应只有一句“报表正常”。建议按下面四层验收：

| 验收对象 | 结构要求 | 测试样本 | 结果证据 |
| --- | --- | --- | --- |
| 药品主数据 | `medicinal_product_id` 能唯一定位活性成分、剂型、规格和批准持有人 | 正常、重复、缺失、撤销与跨期样本 | 试验入组达成率可回到原始对象 |
| 临床试验 | `clinical_trial_id` 能唯一定位方案版本、阶段、适应证和研究中心 | 正常、重复、缺失、撤销与跨期样本 | 方案偏离发生率可回到原始对象 |
| 受试者暴露 | `subject_exposure_id` 能唯一定位受试者在某阶段的实际用药暴露 | 正常、重复、缺失、撤销与跨期样本 | 批放行一次通过率可回到原始对象 |
| 批准与说明书 | `regulatory_approval_id` 能唯一定位国家、适应证、版本和有效期 | 正常、重复、缺失、撤销与跨期样本 | 安全报告按时率可回到原始对象 |
| 商业批次 | `commercial_batch_id` 能唯一定位生产、放行和供应批次 | 正常、重复、缺失、撤销与跨期样本 | 适应证覆盖完整率可回到原始对象 |
| 安全事件 | `safety_case_id` 能唯一定位个例安全报告及因果关系评估 | 正常、重复、缺失、撤销与跨期样本 | 试验入组达成率可回到原始对象 |

还应为每一次发布保留一组固定回归样本：正常对象、边界状态、重复记录、缺失字段、撤销或退款、跨期、权限拒绝和失败恢复。回归样本不是演示数据，而是以后每次改规则都能重复执行的质量资产。

## 10. 原研药的 30 天落地与复盘

| 阶段 | 主要交付 | 通过条件 |
| --- | --- | --- |
| 第 1 周：定义 | 对象、流程、状态、指标、排除项和责任矩阵 | 业务、数据、安全或质量负责人对同一口径签字 |
| 第 2 周：打通 | 源字段、主键、时间、版本、控制对象和失败样本 | 正常与异常样本都能回到原始记录 |
| 第 3 周：验证 | 总量对账、分层对账、抽样回查、权限测试、回滚演练 | 阻断问题清零，严重问题有责任人与期限 |
| 第 4 周：发布 | 灰度、SLO、监控、行动清单、停止条件和复盘模板 | 使用者在真实场景中完成一次闭环行动 |

如果必须用 90 秒说明“原研药”是否做对，可以按这个顺序自测：

1. 一行数据代表什么，主键是什么，哪些对象绝不能混在同一粒度？
2. 业务发生、数据可见、计算完成和行动确认分别在哪个时间点？
3. 本主题最重要的两个主指标、三个护栏和最小样本量是什么？
4. 一个异常出现时，先从原始记录、链路版本还是业务动作开始查？
5. 哪类错误必须阻断发布或停止使用，谁有权批准例外？
6. 上线后由谁在多长时间内观察，什么条件下回滚或结束？

> [!check] 完成标准
> 当另一位数据同事不看聊天记录，只根据口径卡、回归样本和代码就能复跑同一结果；当业务负责人能指出一个异常对应的原始对象、处置动作和复核证据；当系统能够阻止未授权或状态非法的数据进入下游，这篇“原研药”才算真正落到工作里。
