# 院内制剂

> [!abstract] 医疗机构制剂实战手册
> 院内制剂不是普通的“医院自制药品”，而是由医疗机构依据临床需要、经过准入与配制管理、按批次检验放行，并只在规定使用范围内流转的制剂产品。数据工作的重点，是让处方、原辅料、配制过程、检验结果、放行结论和临床使用能够按批次互相追溯。

## 1. 院内制剂：定义、适用边界与决策出口

院内制剂不是普通的“医院自制药品”，而是由医疗机构依据临床需要、经过准入与配制管理、按批次检验放行，并只在规定使用范围内流转的制剂产品。数据工作的重点，是让处方、原辅料、配制过程、检验结果、放行结论和临床使用能够按批次互相追溯。

**本篇的适用边界。** 纳入本篇的对象是取得相应资质后为本机构或规定范围配制和使用的制剂；不把院内协定处方、临方炮制、普通药品采购和未经批准的跨机构销售混在一起。

**最常见的错误替代。** 不能把制剂批号当成普通商品 SKU，也不能用药品采购入库量代替实际配制、放行和临床使用量。

**最终决策。** 业务最终要决定的是：这一批能否放行、是否允许继续使用、是否需要召回或限制科室领用，以及哪个环节必须补充调查。 因此，这篇内容不从“应该建哪张表”开始，而从业务动作、责任人和失败后果开始。只有先确定谁在什么时点做出什么决定，字段、SQL、看板和模型才有明确用途。

围绕“院内制剂”，工作中至少要区分四类问题：

1. **身份问题**：对象是谁，主键能否跨系统稳定关联，合并、拆分、撤销后历史是否还看得见。
2. **时间问题**：业务发生、状态生效、数据入仓、计算完成和人员行动分别发生在哪一刻。
3. **状态问题**：当前状态是一段事件、一张快照还是最终结果，空值代表未发生、未采集还是已删除。
4. **责任问题**：谁确认口径，谁处理异常，谁有权放行或停止，谁在观察期后复盘。

## 2. 院内制剂的完整业务流程

| 环节 | 要做的事 | 最小证据 | 失败后先查什么 |
| --- | --- | --- | --- |
| 临床需求与品种准入 | 提出临床需求、处方依据、适用人群和风险说明 | 品种准入表、处方依据、伦理或药事审议记录 | 只维护药品名称，不维护允许机构和用途 |
| 配制资质与备案/批准核对 | 核对机构、制剂室、配制范围和批准状态 | 批准或备案凭证、品种目录、有效期 | 数据库只保留最终合格值 |
| 原辅料与包材准入 | 确认供应商、批号、检验报告、贮存条件和有效期 | 来料验收、供应商证照、物料放行记录 | 冻结、留样和待检库存仍参与领用 |
| 配制与批记录 | 按处方工艺执行称量、配制、灌装或分装并留痕 | 批生产记录、设备参数、操作人复核人 | 原辅料、配制、检验使用不同编号 |
| 检验与质量放行 | 按标准完成鉴别、含量、微生物或装量等检验 | 取样记录、检验原始数据、OOS/OOT 调查 | 只维护药品名称，不维护允许机构和用途 |
| 标签包装与储存 | 核对品名、规格、批号、有效期和使用范围 | 标签样张、包装复核、库房温湿度 | 数据库只保留最终合格值 |
| 临床使用与反馈 | 限定科室、用途和观察要求，收集不良反应与质量问题 | 领用记录、医嘱关联、反馈和召回记录 | 冻结、留样和待检库存仍参与领用 |

把 临床需求与品种准入、配制资质与备案/批准核对、原辅料与包材准入、配制与批记录、检验与质量放行、标签包装与储存、临床使用与反馈 串起来后可以看出，院内制剂不是一个孤立字段，而是一条会跨系统、跨岗位、跨时间的证据链。流程图上每一段都应标出输入、输出、状态、时间戳、责任人和异常出口。只要其中一段只能靠口头解释，后续的统计、追责和自动化就会失去基础。

一个合格的需求说明应该写成：

> 在【授权数据范围】和【观察窗口】内，围绕“院内制剂”的【制剂品种】，按【preparation_id、preparation_room_id、dosage_form、batch_no】比较【批次首次检验合格率】及其【批次放行及时率】，定位一个可干预节点；行动后同时观察主指标、样本量和护栏，任何高风险异常先阻断再调查。

## 3. 院内制剂的数据对象与系统契约

| 数据对象 | 建议主键 | 一行代表什么 | 不允许混淆 |
| --- | --- | --- | --- |
| 制剂品种 | `preparation_master_id` | 一个获批或备案的处方、规格与用途组合 | 对象身份与业务事件 |
| 配制批次 | `preparation_batch_id` | 一次完整配制过程及对应批记录 | 事件、状态快照和结果粒度 |
| 原辅料批号 | `material_lot_id` | 供应商批次与内部验收批次的映射 | 事件、状态快照和结果粒度 |
| 检验样本 | `qc_sample_id` | 一次取样、检验方法和结果版本 | 事件、状态快照和结果粒度 |
| 放行记录 | `release_id` | 允许或拒绝用于指定范围的质量结论 | 事件、状态快照和结果粒度 |
| 临床领用 | `dispense_id` | 科室或患者使用数量及批号关联 | 事件、状态快照和结果粒度 |

对象表不是把所有字段塞进一张宽表。事件、状态快照和结果表应该分别保留粒度，再通过稳定主键与版本建立关联。尤其要避免三个常见混算：把一次业务事件算成多个对象、把每日快照相加当事件总量、把最新状态覆盖历史状态。

本主题的数据契约至少应包含：

- `preparation_batch_id` 的唯一性规则、生成方式和跨系统映射。
- `compounded_at` 的业务含义、时区、迟到和补录规则。
- `release_status` 的完整状态集合，以及删除、撤销、冻结和失效的表示方法。
- 控制对象 `preparation_material_lot.material_lot_id` 与主对象的关系。
- 每次口径、规则、模型或源版本变化的影响范围和下游通知对象。
- 敏感字段、允许用途、访问角色、导出限制和审计保留时间。

## 4. 院内制剂的指标、样本与验收口径

| 指标 | 公式或定义 | 口径提醒 |
| --- | --- | --- |
| 批次首次检验合格率 | 首次检验合格批次数 / 已检验批次数 | 首次检验与复验必须分开，OOS 不能直接删除 |
| 批次放行及时率 | 在承诺时限内完成质量放行的批次数 / 应放行批次数 | 起止时间要统一到配制结束和放行批准 |
| 批记录完整率 | 关键字段和双人复核完整的批次 / 应检查批次 | 电子签名、补录和纸质扫描要区分 |
| 有效期内报废率 | 非质量原因报废数量 / 期初加本期配制的可用数量 | 不能把召回、检验消耗和正常留样混入报废 |
| 不良反应关联及时率 | 在规定时限内完成批次回查的反馈数 / 需关联批次的反馈数 | 只有时间、患者和批次均能关联时才计为完成 |

指标字典至少写到“任何人都能按同一份数据复跑”的程度：中文名、业务定义、公式、分子、分母、事实粒度、时间字段、对象范围、排除项、版本、负责人和验收样例，一个都不能少。比例指标必须同时展示分子、分母和样本量；金额或数量必须做守恒；状态指标必须能回到事件时间线。

对于“院内制剂”，建议把观察分成三层：

| 层次 | 看什么 | 不能替代什么 |
| --- | --- | --- |
| 业务结果 | 批次首次检验合格率、批次放行及时率 | 不能替代过程证据和个案回查 |
| 过程护栏 | 批记录完整率、有效期内报废率、不良反应关联及时率 | 不能因为护栏暂时正常就跳过异常调查 |
| 数据证据 | 主键、时间、状态、版本、来源目标对账 | 不能只看任务成功或报表能打开 |

## 5. 院内制剂：七个真实工作场景

以下七组场景均为公开方法结合常见工作流程构造的“脱敏复合示例”，不对应任何单一企业、患者、客户或雇员事实。场景的目的，是展示如何从现象走到证据、行动和验收，而不是虚构经营成果。

### 1. 新增品种从临床申请到首批放行

**现场。** 临床科室提出一个常用协定处方的配制需求，信息系统中只有药品通用名，没有独立品种编码。

**怎么查。** 药事管理、制剂室和质量部门把处方依据、配制范围、规格、包装材料、检验项目和标签样张逐项对齐，并将批准状态设为使用前置条件。

**怎么处理。** 建立品种主数据与版本表；首批配制使用专批记录模板，原辅料、设备清洁、称量复核、取样和检验结果都以批次键关联。

**验收结论。** 首批放行不是“检验合格”四个字，而是批准范围、物料、工艺、标签和检验证据全部满足；任何一项缺失都应阻断领用。

### 2. 同一原辅料供应商换批后含量波动

**现场。** 连续两个配制批次的含量接近下限，但每批检验都被判为合格。

**怎么查。** 将原辅料供应商批次、实际投料量、水分、配制设备、操作班组、检验方法版本和库存贮存时长放在同一批次视图，发现来料含水量偏高且库龄较长。

**怎么处理。** 把供应商批次和内部验收批号绑定；对含水量建立收窄的预警区间；在工艺参数未变时先复核物料与贮存条件，不直接调整成品标准。

**验收结论。** 趋势贴限不等于合格即可忽略。统计预警和质量放行要并行，不能为了减少偏差把所有波动写进“正常范围”。

### 3. 检验结果为 OOS 时的批次链条回放

**现场。** 某批微生物检验不合格，现场认为可能是取样问题，要求复验后直接放行。

**怎么查。** 先冻结批次和关联原辅料，回查取样环境、样品运输、培养基批次、检验设备、对照结果和历史趋势，并区分实验室差错与产品质量问题。

**怎么处理。** 禁止用复验覆盖原结果；建立 OOS 调查对象、原因分类、影响范围和最终处置。只有调查结论、质量负责人批准和纠正措施均完成才允许改变批次状态。

**验收结论。** 复验可以补充证据，但不能替原结果“改分”。数据表必须保留原值、复验值和调查版本。

### 4. 标签规格相近造成领用风险

**现场。** 两个不同规格制剂的包装标签颜色和文字非常接近，门诊药房反馈容易拿错。

**怎么查。** 把品种、规格、批号、包装版本、库位、标签样张和实际领用记录关联，检查人工选码、扫码和复核节点。

**怎么处理。** 从数据侧增加品种规格组合唯一约束和扫码校验；标签版本变更进入审批；对高风险相似品种设置物理隔离和双人复核。

**验收结论。** 标签错误不是单纯界面问题，最终要看是否能把错误标签追溯到具体批次、库位和领用环节，并阻断在患者使用前。

### 5. 临期批次与科室领用不均

**现场。** 库房出现多批临期制剂，同时部分科室反映领用不足。

**怎么查。** 区分可放行库存、已预留库存、检验留样、冻结批次和实际消耗；按品种、批号、有效期和科室计算可领用天数。

**怎么处理。** 建立近效期预警和先进先出建议，但不自动把冻结或未放行库存算作可用库存；科室调拨需保留原因和批准。

**验收结论。** 库存周转改善不能以使用临期或不合格批次为代价。数据必须同时展示可用量、缺货风险和报废风险。

### 6. 临床反馈与批次追溯断链

**现场。** 临床报告疑似不适反应，但反馈表只记录制剂名称，无法确认患者实际使用了哪个批次。

**怎么查。** 回到领用单、药房发药、护理执行、患者用药记录和批号标签，判断是业务未采集还是数据未关联。

**怎么处理。** 将反馈的必填项改为品种加批号，补充无法追溯的原因码；质量团队按批次统计反馈率，并设置集中爆发的调查触发规则。

**验收结论。** 不良反应反馈的核心不是“有没有登记”，而是能否在可控时间内冻结相关批次、通知使用科室并判断是否需要扩大回查。

### 7. 跨院区需求与合规边界

**现场。** 集团内另一院区希望共享某制剂，要求把库存和处方数据直接打通。

**怎么查。** 先核对双方机构资质、制剂批准使用范围、处方与标签是否一致、运输储存条件和质量责任，再讨论数据接口。

**怎么处理。** 在品种主数据中记录允许使用的机构范围；接口只提供经批准的目录与可调剂库存，跨范围请求默认拒绝并留审计记录。

**验收结论。** 系统能传输不等于业务允许。合规范围必须成为数据规则和接口契约的一部分，而不是靠操作人员记忆。

七个场景可以归成一条共同判断顺序：先确认对象和时间，再确认状态和版本；然后做总量、结构和明细三层对账；最后才讨论策略、模型或工具。若一条结论不能指出对应的原始记录、责任人和行动出口，就只能算观察，不能作为生产结论。

## 6. 院内制剂的第一段 SQL：重建业务链路

下面的 SQL 用于说明对象、时间、状态、版本和分层口径如何进入同一条可复查路径。表名和部分字段是通用示例，落地时应映射到企业数据字典；SQL 方言也需按实际引擎调整。

```sql
-- 院内制剂：按业务对象重建链路，避免事件、快照和结果混算
WITH ranked_preparation_batch_id AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY preparation_batch_id
      ORDER BY updated_at DESC
    ) AS version_no
  FROM hospital_preparation_batch
  WHERE compounded_at >= TIMESTAMP '{start_time}'
    AND compounded_at <  TIMESTAMP '{end_time}'
    AND release_status NOT IN ('deleted', 'test')
),
valid_rows AS (
  SELECT
    preparation_batch_id,
    preparation_id,
    preparation_room_id,
    dosage_form,
    batch_no,
    compounded_at,
    release_status,
    ingested_at
  FROM ranked_preparation_batch_id
  WHERE version_no = 1
)
SELECT
  preparation_id, preparation_room_id, dosage_form, batch_no,
  COUNT(DISTINCT preparation_batch_id) AS object_cnt,
  SUM(CASE WHEN first_pass_qc THEN 1 ELSE 0 END) AS numerator_value,
  COUNT(DISTINCT preparation_batch_id) AS denominator_value,
  CAST(SUM(CASE WHEN first_pass_qc THEN 1 ELSE 0 END) AS DOUBLE PRECISION)
    / NULLIF(COUNT(DISTINCT preparation_batch_id), 0) AS metric_value,
  MIN(compounded_at) AS first_event_at,
  MAX(compounded_at) AS last_event_at
FROM valid_rows
GROUP BY preparation_id, preparation_room_id, dosage_form, batch_no
ORDER BY metric_value DESC, object_cnt DESC;
```

执行后至少回答六个问题：

- 同一对象是否因为多源回传产生多版本，版本保留是否符合业务要求？
- 业务时间与入仓时间是否分开，补录和迟到数据是否进入正确分区？
- 分子分母是否来自同一对象范围和同一统计窗口？
- 维度使用的是事件当时值还是当前值，跨期比较是否一致？
- 删除、撤销、冻结和测试数据是否按规则处理？
- 分组结果能否在明细中抽样复现？

## 7. 院内制剂的第二段 SQL：源、控制和结果三方对账

```sql
-- 院内制剂：源对象、控制对象和结果对象三方对账
WITH population AS (
  SELECT
    preparation_batch_id,
    compounded_at,
    release_status
  FROM hospital_preparation_batch
  WHERE compounded_at >= TIMESTAMP '{start_time}'
    AND compounded_at <  TIMESTAMP '{end_time}'
),
control AS (
  SELECT
    preparation_batch_id,
    SUM(qualified_qty) AS control_value,
    COUNT(DISTINCT material_lot_id) AS control_cnt,
    MAX(updated_at) AS control_updated_at
  FROM preparation_material_lot
  WHERE updated_at >= TIMESTAMP '{start_time}'
  GROUP BY preparation_batch_id
),
result AS (
  SELECT
    preparation_batch_id,
    COUNT(*) AS result_cnt,
    MAX(calculated_at) AS calculated_at
  FROM mart_preparation_batch_id
  WHERE business_date BETWEEN DATE '{start_date}' AND DATE '{end_date}'
  GROUP BY preparation_batch_id
)
SELECT
  COALESCE(p.preparation_batch_id, c.preparation_batch_id, r.preparation_batch_id) AS object_key,
  CASE
    WHEN p.preparation_batch_id IS NULL THEN 'source_missing'
    WHEN c.preparation_batch_id IS NULL THEN 'control_missing'
    WHEN r.preparation_batch_id IS NULL THEN 'result_missing'
    WHEN ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0 THEN 'count_or_value_gap'
    ELSE 'matched'
  END AS reconciliation_status,
  p.release_status,
  c.control_value,
  c.control_cnt,
  r.result_cnt,
  c.control_updated_at,
  r.calculated_at
FROM population p
FULL OUTER JOIN control c ON p.preparation_batch_id = c.preparation_batch_id
FULL OUTER JOIN result r ON COALESCE(p.preparation_batch_id, c.preparation_batch_id) = r.preparation_batch_id
WHERE p.preparation_batch_id IS NULL
   OR c.preparation_batch_id IS NULL
   OR r.preparation_batch_id IS NULL
   OR ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0;
```

这段查询故意不使用“总数相差小于某个随意百分比就算通过”。它先找出缺失对象和状态差异，再检查控制值与结果值。对于院内制剂，数量、金额、时长或状态任意一项无法解释，都不能用“业务波动”代替排查。

对账结果建议分成四类处理：

1. **阻断**：对象缺失、关键时间为空、状态非法、金额或数量不守恒、权限越界。
2. **严重**：比例或总量显著偏离基线，且无法由已确认的对象结构变化解释。
3. **观察**：小范围波动但来源、样本和趋势可控，进入责任人和观察窗口。
4. **探索**：只有弱信号或假设，不进入正式结论，更不直接触发业务处罚。

## 8. 院内制剂的 Python 发布门禁与指标护栏

第一段代码把发布条件写成可执行对象，避免“检查过了”只存在聊天记录里：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class PreparationBatchIdBatch:
    batch_id: str
    source_rows: int
    valid_rows: int
    duplicate_keys: int
    missing_required_fields: int
    reconciliation_gap: float

def release_preparation_batch_id(batch: PreparationBatchIdBatch) -> dict:
    checks = {
        "source_not_empty": batch.source_rows > 0,
        "valid_rows_in_range": 0 <= batch.valid_rows <= batch.source_rows,
        "duplicate_rate_ok": batch.duplicate_keys / max(batch.source_rows, 1) <= 0.001,
        "required_fields_ok": batch.missing_required_fields == 0,
        "reconciliation_ok": abs(batch.reconciliation_gap) <= 0.01,
    }
    return {
        "topic": "院内制剂",
        "batch_id": batch.batch_id,
        "checks": checks,
        "release_allowed": all(checks.values()),
        "blocking_checks": [name for name, passed in checks.items() if not passed],
    }
```

第二段代码演示如何为比例类结果附带样本证据和小样本下界。它不是替代统计学家的模型，而是防止把少量偶然样本直接包装成稳定结论：

```python
from dataclasses import dataclass
from math import sqrt

@dataclass(frozen=True)
class PreparationBatchIdObservation:
    object_id: str
    numerator: float
    denominator: float
    sample_size: int
    scope_version: str

def calculate_preparation_batch_id(rows: list[PreparationBatchIdObservation]) -> list[dict]:
    output = []
    for row in rows:
        value = row.numerator / row.denominator if row.denominator > 0 else None
        # 小样本用 Wilson 下界做护栏，不把偶然的高比例直接当稳定结果。
        z = 1.96
        p = value or 0
        n = max(row.sample_size, 1)
        center = p + z * z / (2 * n)
        margin = z * sqrt((p * (1 - p) + z * z / (4 * n)) / n)
        lower = max(0, (center - margin) / (1 + z * z / n))
        output.append({
            "object_id": row.object_id,
            "metric": "批次首次检验合格率",
            "value": value,
            "lower_bound": lower if value is not None else None,
            "sample_size": row.sample_size,
            "scope_version": row.scope_version,
            "caution": "首次检验与复验必须分开，OOS 不能直接删除",
        })
    return output
```

真正上线时还要补充参数配置、日志、血缘、告警级别、重跑幂等、异常样本保存和审批记录。代码通过不代表业务通过；自动检查只能证明已经定义的规则没有被违反，无法证明规则本身一定正确。

## 9. 院内制剂的失败反例与上线验收

| 风险信号 | 错误做法 | 必须补齐的证据 | 发布或行动规则 |
| --- | --- | --- | --- |
| 批准范围未进入系统 | 只维护药品名称，不维护允许机构和用途 | 审批文件与品种主数据版本 | 范围外请求默认阻断 |
| 原结果被复验覆盖 | 数据库只保留最终合格值 | 原始值、复验值、OOS 调查和签字 | 保留全部版本并记录放行依据 |
| 可用库存虚高 | 冻结、留样和待检库存仍参与领用 | 按状态拆分的库存快照 | 未放行批次不得释放库存 |
| 批次断链 | 原辅料、配制、检验使用不同编号 | 批次谱系与来源目标计数 | 无法追溯时停止放行并回查 |

上线验收不应只有一句“报表正常”。建议按下面四层验收：

| 验收对象 | 结构要求 | 测试样本 | 结果证据 |
| --- | --- | --- | --- |
| 制剂品种 | `preparation_master_id` 能唯一定位一个获批或备案的处方、规格与用途组合 | 正常、重复、缺失、撤销与跨期样本 | 批次首次检验合格率可回到原始对象 |
| 配制批次 | `preparation_batch_id` 能唯一定位一次完整配制过程及对应批记录 | 正常、重复、缺失、撤销与跨期样本 | 批次放行及时率可回到原始对象 |
| 原辅料批号 | `material_lot_id` 能唯一定位供应商批次与内部验收批次的映射 | 正常、重复、缺失、撤销与跨期样本 | 批记录完整率可回到原始对象 |
| 检验样本 | `qc_sample_id` 能唯一定位一次取样、检验方法和结果版本 | 正常、重复、缺失、撤销与跨期样本 | 有效期内报废率可回到原始对象 |
| 放行记录 | `release_id` 能唯一定位允许或拒绝用于指定范围的质量结论 | 正常、重复、缺失、撤销与跨期样本 | 不良反应关联及时率可回到原始对象 |
| 临床领用 | `dispense_id` 能唯一定位科室或患者使用数量及批号关联 | 正常、重复、缺失、撤销与跨期样本 | 批次首次检验合格率可回到原始对象 |

还应为每一次发布保留一组固定回归样本：正常对象、边界状态、重复记录、缺失字段、撤销或退款、跨期、权限拒绝和失败恢复。回归样本不是演示数据，而是以后每次改规则都能重复执行的质量资产。
