# HIPAA合规与医疗数据安全指南

> [!warning] 核心判断
> 讨论“HIPAA合规与医疗数据安全指南”时，最容易犯的错误是直接从工具或报表开始。更有用的顺序是：先看业务链条，再找可观察指标，随后确认数据粒度，最后才选择 SQL、模型或平台组件。本文按这个顺序给出可执行方案和常见的失败样本。

## 1. 先判断应治理什么风险

“HIPAA合规与医疗数据安全指南”通常不是买一个平台就能解决的问题。它至少涉及制度、标准、责任、流程、技术和审计六层。开始前先把风险写成可观察事实：

| 风险问题 | 观察信号 | 可能影响 | 首先核查 |
| --- | --- | --- | --- |
| 定义不一致 | 同名指标多个 SQL、多个业务解释 | 决策冲突、返工 | 指标字典与负责人 |
| 数据不完整 | 分区缺失、关键字段空值 | 报表失真、流程中断 | 采集与任务日志 |
| 责任不清 | 问题工单长期无人认领 | 修复延迟、同类复发 | 资产责任矩阵 |
| 访问过宽 | 长期权限、共享账号、无审计 | 泄漏与合规风险 | 权限清单与访问日志 |
| 变更不可见 | 表结构或逻辑变更无通知 | 下游批量故障 | 血缘与发布记录 |

1. **患者隐私泄露**：需要在标准、系统或组织流程中设置对应控制。
2. **多院区患者主索引重复**：需要在标准、系统或组织流程中设置对应控制。
3. **临床时间与计费时间混用**：需要在标准、系统或组织流程中设置对应控制。
4. **检验单位不统一**：需要在标准、系统或组织流程中设置对应控制。
5. **历史诊断编码版本失效**：需要在标准、系统或组织流程中设置对应控制。

治理不是把所有数据都按同一优先级管理。建议依据使用范围、监管要求、决策影响和故障历史划分关键资产，再决定投入。关键资产应有唯一负责人、明确消费者、质量目标、访问策略和变更通知。

## 3. 资产、标准与责任矩阵

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 患者 | `patient_id` | 预约与挂号 |
| 过程对象 | 就诊 | `visit_id` | 接诊与分诊 |
| 过程对象 | 医嘱 | `order_id` | 检查检验 |
| 结果对象 | 检查检验 | `report_id` | 诊断与治疗 |
| 结果对象 | 费用 | `settlement_id` | 出院与结算 |
| 专题分析 | HIPAA合规与医疗数据安全指南 | `topic_key = 'hipaa'` | 用于把通用事件收窄到本主题 |

一个可执行的数据标准至少包括：

- **业务定义**：业务人员如何理解和适用。
- **技术定义**：字段类型、长度、格式、枚举和空值语义。
- **计算口径**：时间、粒度、分子分母和排除项。
- **权威来源**：哪个系统是事实源，冲突时以谁为准。
- **生命周期**：创建、变更、废弃和归档规则。
- **责任人**：业务负责人、数据负责人、技术负责人和审批人。

资产责任可以使用 RACI：业务负责人对定义负责，数据负责人对实现与质量负责，平台团队对工具和权限负责，安全合规对访问与审计负责，消费者对使用边界负责。只有“责任人”一个字段，没有决策权和时限，问题仍会回到治理团队自己处理。

## 4. 案例一：华北某 AI 公司

### 案例 1：华北某 AI 公司的“HIPAA合规与医疗数据安全指南”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“HIPAA合规与医疗数据安全指南”映射到“数据安全、合规与权限治理”中的审计，而不是泛泛讨论概念。
- **触发事件**：客服大模型测试时出现内部制度和个人信息片段。
- **业务与数据范围**：训练语料、检索知识、用户问题、输出日志、脱敏规则和模型版本。数据侧重点采集身份、时间、对象、动作、结果和审批链，并与HIS、EMR、LIS中的时间、状态和责任人信息对齐。
- **需要回答的问题**：能否还原谁在何时访问了什么、做了什么。
- **关键障碍**：训练与生产数据边界不清，提示注入和越权检索没有专门测试。同时要防止患者隐私泄露把表面指标带偏。
- **处理过程**：建立数据卡与模型卡，训练前去标识化，检索前做权限过滤，输出侧增加敏感检查和红队集。实施时把“先分类分级和确认用途，再谈开放哪些字段与操作”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例项目把安全测试、人工复核和可回滚发布纳入模型上线门禁。验收至少同时看主指标、身份、时间、对象、动作、结果和审批链和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“按数据类型、用途、角色和风险设置最小权限、脱敏、审计和生命周期控制，让每次访问与共享都有依据、可追踪、可回收。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

治理项目应先做小范围闭环，不要一开始铺满全公司。选择一个高影响业务域，完成从资产盘点、标准确认、质量规则、问题整改到复盘的完整链路，再复制机制。

## 5. 规则与代码：让控制可执行

### 发布前规则门禁

```python
# HIPAA合规与医疗数据安全指南：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "HIPAA合规与医疗数据安全指南"
TOPIC_KEY = "hipaa"
RULE_ID = "rule_healthcare_xnwcak"
GUIDE_CHECKS = [
    "先分类分级和确认用途，再谈开放哪些字段与操作",
    "权限必须绑定角色、项目、用途和有效期，并能自动回收",
    "查询、下载、训练、共享和模型输出都需要审计证据",
    "高风险场景准备脱敏、拒绝、转人工、回滚和事故响应路径"
]
RULES = {
    "required_columns": ["event_id", "patient_id", "event_date", "status"],
    "duplicate_key": "event_id",
    "entity_key": "patient_id",
    "time_field": "event_date",
    "max_duplicate_rate": 0.0008,
    "max_null_rate": 0.002,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：先分类分级和确认用途，再谈开放哪些字段与操作；权限必须绑定角色、项目、用途和有效期，并能自动回收；查询、下载、训练、共享和模型输出都需要审计证据；高风险场景准备脱敏、拒绝、转人工、回滚和事故响应路径
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

from dataclasses import dataclass

@dataclass(frozen=True)
class AccessRequest:
    role: str
    purpose: str
    columns: set[str]

POLICY = {
    "research": {
        "allowed_columns": {"patient_id_hash", "age_band", "diagnosis_code"},
        "forbidden_purposes": {"marketing"},
    }
}

def authorize(request: AccessRequest) -> tuple[bool, str]:
    policy = POLICY.get(request.role)
    if not policy:
        return False, "role_not_approved"
    if request.purpose in policy["forbidden_purposes"]:
        return False, "purpose_not_allowed"
    if not request.columns <= policy["allowed_columns"]:
        return False, "sensitive_column_requested"
    return True, "approved_with_mask_and_audit"

### 治理对象与风险分层 SQL

```sql
-- HIPAA合规与医疗数据安全指南：结构贡献诊断（院区 × 病种）
WITH scoped AS (
  SELECT
    patient_id AS entity_key,
    event_id,
    event_date AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_medical_event
  WHERE event_date >= DATE '2026-05-01'
    AND event_date <  DATE '2026-08-01'
    AND subject_key = 'hipaa'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '复诊率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

规则设计要同时考虑三件事：能否自动执行、误报成本是否可接受、失败后谁来处理。只写“不能为空”不够，必须明确哪类对象允许为空、谁能在何种情况下豁免、豁免多久、是否需要审批和复核。

建议把规则分成四级：

1. **阻断**：涉及监管、资金、身份或核心发布，失败即停止。
2. **严重告警**：影响大但可先隔离，要求在约定时间内响应。
3. **观察告警**：可能是正常业务变化，先记录趋势。
4. **探索检查**：尚未形成稳定阈值，仅用于发现异常模式。

## 6. 案例二：华东某医疗数据平台

### 案例 2：华东某医疗数据平台的“HIPAA合规与医疗数据安全指南”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“HIPAA合规与医疗数据安全指南”映射到“数据安全、合规与权限治理”中的使用，而不是泛泛讨论概念。
- **触发事件**：研究团队需要分析病历数据，但直接导出会包含患者身份和敏感诊断信息。
- **业务与数据范围**：患者主索引、就诊、诊断、检验、授权目的、字段分级和导出范围。数据侧重点采集脱敏策略、水印、审计日志和异常访问，并与HIS、EMR、LIS中的时间、状态和责任人信息对齐。
- **需要回答的问题**：查询、导出、训练和共享是否遵循最小必要。
- **关键障碍**：权限按部门授予，无法区分研究用途和临床用途，脱敏规则又只在部分视图生效。同时要防止多院区患者主索引重复把表面指标带偏。
- **处理过程**：按用途建立受控数据空间，身份字段不可逆脱敏，敏感诊断按最小集授权，导出需审批和水印。实施时把“权限必须绑定角色、项目、用途和有效期，并能自动回收”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例方案以授权可追踪、最小字段和访问审计为上线条件。验收至少同时看主指标、脱敏策略、水印、审计日志和异常访问和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“按数据类型、用途、角色和风险设置最小权限、脱敏、审计和生命周期控制，让每次访问与共享都有依据、可追踪、可回收。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

治理指标不要只统计“生成了多少文档、接入了多少资产”。更值得观察的是规则覆盖的关键资产、问题发现前移比例、问题复发率、变更影响分析耗时和业务是否愿意使用。

## 7. 权限、安全与审计

围绕“HIPAA合规与医疗数据安全指南”，权限治理至少应回答：

- 谁能申请、谁审批、审批依据是什么？
- 权限是否按角色、数据级别和用途最小化？
- 临时权限何时收回，离职和转岗是否自动处理？
- 查询、下载和导出是否留痕，异常访问如何发现？
- 脱敏、加密、水印和审计日志是否与数据类型匹配？

敏感字段不应通过“复制一份测试数据”绕过问题。更合适的做法是分级脱敏、合成数据或受控计算环境。所有示例和代码都不应包含真实身份、账号、密钥、客户名单或未公开经营数据。

## 8. 第三个案例：华东某三甲医院

### 案例 3：华东某三甲医院的“HIPAA合规与医疗数据安全指南”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“HIPAA合规与医疗数据安全指南”映射到“数据安全、合规与权限治理”中的分类，而不是泛泛讨论概念。
- **触发事件**：门诊高峰期投诉增加，管理层希望判断问题来自号源、接诊、检查还是报告回传。
- **业务与数据范围**：3 个院区 18 个月挂号、报到、叫号、医嘱、检查、报告和结算事件。数据侧重点采集字段清单、分级标签、业务用途和授权依据，并与HIS、EMR、LIS中的时间、状态和责任人信息对齐。
- **需要回答的问题**：数据包含什么主体、敏感程度和监管属性。
- **关键障碍**：各系统用就诊号、住院号和申请单号交叉关联，报告回传时间缺少统一时区。同时要防止临床时间与计费时间混用把表面指标带偏。
- **处理过程**：建立患者主索引和就诊主键，把门诊流程拆成 8 个事件节点，按院区、科室和时段做分层基线。实施时把“查询、下载、训练、共享和模型输出都需要审计证据”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例项目把流程断点定位从人工拉取多个系统缩短到一张小时级监控，并形成报告超时催办规则。验收至少同时看主指标、字段清单、分级标签、业务用途和授权依据和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“按数据类型、用途、角色和风险设置最小权限、脱敏、审计和生命周期控制，让每次访问与共享都有依据、可追踪、可回收。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

### 案例 4：HIPAA合规与医疗数据安全指南的最小权限与越权核查

一次例行发布后，负责“HIPAA合规与医疗数据安全指南”的小组收到下游反馈：数字和源系统对不上，但任务本身全部成功。团队决定围绕“权限、隐私与审计”做一次完整回放。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 让数据用途、最小字段、访问角色、加工产物、保存期限和撤回机制都可追溯。在本场景里，核心风险还包括患者隐私泄露，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：患者、就诊及其在检查检验前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注patient_id与visit_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 分析结果本身可以访问，但派生字段、导出文件和临时表扩大了敏感数据范围，现有流程没有及时识别。初看时，PACS与医保结算系统的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 分类分级、授权记录、字段血缘、访问日志、导出清单、脱敏规则和过期清理记录。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“医务管理”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“HIPAA合规与医疗数据安全指南”的当前定义并记录版本；第二步用患者明细核对PACS到医保结算系统的关联；第三步按院区与病种做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察门急诊人次和护栏指标复诊率。
- **行动与护栏：** 按任务拆分数据集与角色，使用最小字段和临时授权，发布前检查派生表与导出是否出现敏感扩散。专题检查项“先分类分级和确认用途，再谈开放哪些字段与操作”被写成发布门禁，高风险字段缺少授权、脱敏或审计时不进入分析环境，紧急访问必须到期自动回收。
- **失败路径：** 把“内网可访问”当成“业务已授权”，或者用永久大权限账号支撑临时分析。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“HIPAA合规与医疗数据安全指南”时，先验证身份、时间、对象、动作、结果和审批链，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由医务管理在明确时限内，根据门急诊人次、复诊率和患者主索引跨院区唯一决定继续、回退、补查还是转人工。 若患者隐私泄露或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 案例 7：HIPAA合规与医疗数据安全指南的三方取舍实验

一个看似普通的“HIPAA合规与医疗数据安全指南”需求，在跨系统核验后变成了围绕“成本、质量与时效取舍”的专项排查。触发排查的不是一次严重事故，而是连续几次解释不清的数据差异。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 把新鲜度、正确性和成本分别量化，找到满足真实决策节奏的最低必要资源。在本场景里，核心风险还包括检验单位不统一，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：检查检验、费用及其在随访与质量复盘前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注report_id与settlement_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 为追求更快结果不断增加资源，账单和重复计算同步上升，但业务真正使用的时效并没有显著改善。初看时，HIS与EMR的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 执行计划、扫描量、文件数、峰值资源、单位产出成本、业务截止时间和质量门禁。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“患者”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“HIPAA合规与医疗数据安全指南”的当前定义并记录版本；第二步用检查检验明细核对HIS到EMR的关联；第三步按人群与院区做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察异常检验占比和护栏指标门急诊人次。
- **行动与护栏：** 先按使用场景和截止时间分级，再比较预聚合、增量计算、缓存、并发调整和生命周期策略。专题检查项“高风险场景准备脱敏、拒绝、转人工、回滚和事故响应路径”被写成发布门禁，任何优化都必须同时通过结果对账、延迟目标与成本预算，不能只展示一次最快执行。
- **失败路径：** 为了压缩账单关闭质量检查，或为了刷新频率重复计算无人消费的全量结果。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“HIPAA合规与医疗数据安全指南”时，先验证角色、用途、审批、临时权限和回收记录，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由患者在明确时限内，根据异常检验占比、门急诊人次和检验结果带单位与参考区间决定继续、回退、补查还是转人工。 若检验单位不统一或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从HIPAA合规与医疗数据安全指南回到可核对明细

```sql
-- HIPAA合规与医疗数据安全指南：发布前质量画像
SELECT
  'hipaa' AS subject_key,
  stat_date,
  COUNT(*) AS row_cnt,
  COUNT(DISTINCT event_id) AS distinct_event_cnt,
  SUM(CASE WHEN event_id IS NULL THEN 1 ELSE 0 END) AS null_event_cnt,
  SUM(CASE WHEN event_date < business_time THEN 1 ELSE 0 END) AS time_reverse_cnt,
  SUM(CASE WHEN status NOT IN ('valid', 'completed', 'cancelled') THEN 1 ELSE 0 END) AS invalid_status_cnt,
  ROUND(COUNT(*) * 1.0 / NULLIF(COUNT(DISTINCT event_id), 0), 4) AS duplication_ratio
FROM fact_medical_event
WHERE stat_date BETWEEN :start_date AND :end_date
GROUP BY stat_date
HAVING SUM(CASE WHEN event_id IS NULL THEN 1 ELSE 0 END) > 0
    OR SUM(CASE WHEN event_date < business_time THEN 1 ELSE 0 END) > 0
    OR COUNT(*) <> COUNT(DISTINCT event_id)
ORDER BY stat_date;

-- 至少人工核对一次：患者主索引跨院区唯一；就诊时间与医嘱时间有序；诊断编码在有效版本内。
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把HIPAA合规与医疗数据安全指南的验收证据写成门禁

```python
from datetime import date
from hashlib import sha256

import pandas as pd

SUBJECT = "HIPAA合规与医疗数据安全指南"
BLOCKING_RULES = ["患者主索引跨院区唯一","就诊时间与医嘱时间有序","诊断编码在有效版本内"]


def validate_release(frame: pd.DataFrame, start: date, end: date) -> dict:
    scoped = frame.loc[
        frame["event_date"].between(pd.Timestamp(start), pd.Timestamp(end))
        & (frame["subject_key"] == "hipaa")
    ].copy()
    checks = {
        "has_rows": len(scoped) > 0,
        "event_id_unique": not scoped["event_id"].duplicated().any(),
        "entity_key_complete": scoped["entity_key"].notna().all(),
        "event_time_present": scoped["event_time"].notna().all(),
        "scope_matches": scoped["subject_key"].nunique() == 1,
    }
    payload = f"{SUBJECT}|{start}|{end}|{len(scoped)}|{sorted(checks.items())}"
    return {
        "subject": SUBJECT,
        "rows": len(scoped),
        "checks": checks,
        "blocking_rules": BLOCKING_RULES,
        "release_allowed": all(checks.values()),
        "evidence_hash": sha256(payload.encode("utf-8")).hexdigest(),
    }
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。

### 四个案例共用的验收清单

| 验证面 | 发布前问题 | 证据 | 不通过时 |
| --- | --- | --- | --- |
| 对象与粒度 | 一行数据代表患者、事件、快照还是结果 | 主键、版本、有效时间和边界样本 | 阻断 |
| 时间语义 | 业务发生、数据可见、决策采用是否混用 | event_date、入仓时间、行动时间轴 | 阻断 |
