# 生产周期

> [!abstract] 场景速览
> 如果只记住“生产周期”的定义，遇到真实数据时仍然很难行动。本文把它拆成五个可检查问题：谁在使用、流程在哪里变化、数据一行代表什么、异常如何发现、上线后用哪个指标验收。每个部分都配一个工作案例或代码片段。

## 1. “生产周期”在制造业业务链中的位置

制造业的核心流程可以概括为：需求计划 → 排产 → 备料 → 工单执行 → 质量检验 → 入库 → 发运 → 售后追溯。参与角色包括计划、采购、工艺、生产、设备、质量、仓储、交付与财务。“生产周期”通常不是一个孤立字段，而是连接业务动作、数据记录和管理决策的一层能力。

从数据团队视角，至少要回答四个问题：

1. **谁使用**：计划、采购、工艺、生产分别要用它做判断、执行还是审计。
2. **对象是什么**：一行数据代表工厂、一次事件、一个批次还是一天快照。
3. **流程在哪里变化**：通过排产、备料、工单执行、质量检验之间的状态和时间差定位问题。
4. **结果如何被采用**：谁在什么时间前采取行动，使用哪个指标观察改善或副作用。

一个合格的专题目标可以写成：

> 在【时间窗】和【授权数据范围】内，围绕“生产周期”，按【工厂、产线、产品】比较【单位制造成本】与【准时交付率】，定位一个可干预流程节点，并记录行动后的变化与边界。

## 2. 一张图看清角色、流程和数据

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 工厂 | `plant_id` | 需求计划 |
| 过程对象 | 产线 | `line_id` | 排产 |
| 过程对象 | 设备 | `equipment_id` | 备料 |
| 结果对象 | 工单 | `work_order_id` | 工单执行 |
| 结果对象 | 批次 | `batch_id` | 质量检验 |
| 专题分析 | 生产周期 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

建模时不要先把所有系统字段堆进一张大表。更稳妥的做法是分别保留三类事实：

- **事件事实**：谁在什么时间做了动作，例如挂号、下单、开工、报警或学习。
- **状态快照**：对象在某一天的状态，例如会员等级、租约、账户余额或设备资产关系。
- **结果事实**：流程完成后的产出，例如结算金额、良品数量、签收结果或考试分数。

三者的粒度不同。把事件、快照和结果强行放在同一行，会让金额、数量和转化率在汇总时重复。若“生产周期”涉及状态变化，优先建立状态机；若涉及金额，先做借贷或收付平衡；若涉及对象归属，保留维度有效期。

## 3. 指标与口径：不要把相关数字直接当答案

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 良品率 | `SUM(good_qty) / SUM(produced_qty)`（视图字段 `yield_rate`） | 工厂、产线、产品 | 不混用测试、撤销和跨期状态；与“生产周期”相关时还要补充主题筛选 |
| 设备稼动率 | `SUM(run_minutes) / SUM(planned_minutes)`（视图字段 `availability`） | 产线、产品、班组 | 不混用测试、撤销和跨期状态；与“生产周期”相关时还要补充主题筛选 |
| 计划达成率 | `SUM(completed_plan_qty) / SUM(planned_qty)`（视图字段 `plan_attainment`） | 产品、班组、设备类型 | 不混用测试、撤销和跨期状态；与“生产周期”相关时还要补充主题筛选 |
| 单位制造成本 | `SUM(conversion_cost) / SUM(good_qty)`（视图字段 `unit_cost`） | 班组、设备类型 | 不混用测试、撤销和跨期状态；与“生产周期”相关时还要补充主题筛选 |

指标字典至少应包含：中文名、英文编码、业务定义、计算公式、事实粒度、时间字段、对象范围、排除条件、负责人和验收样例。对于“生产周期”，还应注明它使用的是业务发生时间还是入仓时间，是否包含撤销、退费、测试、跨期和补录记录。

一个常见误区是看到单位制造成本变化就立即解释业务原因。更可靠的顺序是：

1. 检查数据覆盖和延迟是否变化。
2. 检查对象范围、状态映射和维度归属是否变化。
3. 按时间、结构和分组拆解贡献。
4. 回到明细寻找能解释变化的事件。
5. 如果已经采取行动，再评估行动带来的增量，而不是事后挑一个相关指标。

## 4. 工作案例：从现象到数据处理

### 案例 1：华东某汽车零部件工厂的“生产周期”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：订单准时交付率下降，但生产能力数据看起来仍有富余，管理层无法判断瓶颈位置。本次讨论的重点是“生产周期”，所以团队先要求把先冻结对象与时间窗写进项目目标，而不是直接开始做报表。
- **数据范围**：销售订单、主生产计划、工单、设备状态、停机和质检记录。同时收集ERP、MES、PLM、QMS中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：计划达成率按工单数量统计，无法反映不同产品工时；设备停机原因存在人工重复录入。进一步检查后发现，如果不先处理设备与工单编码变化导致断链，“生产周期”很容易被一个表面相关指标替代。
- **处理过程**：统一工单、工序、设备和批次粒度，用标准工时转换产能，建立停机区间合并与瓶颈工序分析。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目识别出换型损失和某工序返工积压，并建立按周滚动产能与交付风险清单。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“生产周期”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

这个案例最关键的动作不是“跑一条 SQL”，而是把“生产周期”对应的业务对象和上下游系统放在同一张链路图上。链路图至少要标出源系统、事件时间、关联主键、状态变化、数据负责人和消费方。

## 5. SQL 示例：在统一口径下做分层诊断

下面的查询用于展示分析结构，表名和字段需映射到实际环境。重点是去重、范围筛选、基线比较和贡献率，而不是代码本身。

### 标题专属诊断 SQL

```sql
-- 生产周期：结构贡献诊断（班组 × 工厂）
WITH scoped AS (
  SELECT
    plant_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_manufacturing_event
  WHERE event_time >= DATE '2026-05-01'
    AND event_time <  DATE '2026-08-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '良品率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

执行后要回答四类验证题：

- 结果总量能否与源系统或既有报表在相同口径下解释差异？
- 排名前几位的分组是否由少数超长、重复或补录记录造成？
- 缺失日期表现为“未发生”还是“未采集”，是否改变分母？
- 维度使用的是当时归属还是当前归属，跨期比较是否一致？

## 6. 第二个案例：跨系统、跨部门时怎样不失控

### 案例 2：华南某电子制造企业的“生产周期”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：良品率短期波动，质量团队怀疑供应商批次，但生产记录与来料检验无法快速关联。本次讨论的重点是“生产周期”，所以团队先要求把先证明数据链路可信写进项目目标，而不是直接开始做报表。
- **数据范围**：供应商、来料批次、投料记录、设备参数、工序质检和售后返修。同时收集ERP、MES、PLM、QMS中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：同一物料存在供应商编码、内部料号和制造商料号三套标识，批次追溯在手工补录处断开。进一步检查后发现，如果不先处理停机时长重复计算，“生产周期”很容易被一个表面相关指标替代。
- **处理过程**：建立物料主数据映射和批次谱系，按供应商批次、设备、班组和参数窗口做交叉分析。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目把异常批次追溯从数天缩短到小时级，并增加了参数越界与批次隔离规则。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“生产周期”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

跨部门项目最容易在三个地方返工：业务术语没有冻结、主数据映射没有版本、验收时才发现权限不足。建议在开发前让业务负责人签字确认指标定义，让数据负责人确认粒度与主键，让安全负责人确认字段范围，让运维负责人确认发布与回滚窗口。

## 7. Python 示例：把数据质量变成发布门禁

### 可执行质量门禁

```python
# 生产周期：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "生产周期"
TOPIC_KEY = "subject"
RULE_ID = "rule_manufacturing_1afig44"
GUIDE_CHECKS = [
    "检查工单与批次关系完整",
    "检查停机区间不重叠",
    "检查质检结果可追到工序"
]
RULES = {
    "required_columns": ["event_id", "plant_id", "event_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "plant_id",
    "time_field": "event_time",
    "max_duplicate_rate": 0.0009,
    "max_null_rate": 0.005,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：检查工单与批次关系完整；检查停机区间不重叠；检查质检结果可追到工序
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

这段代码适合放在离线任务完成之后、指标发布之前。真实环境还应从调度平台读取分区参数、把结果写入质量平台，并在关键规则失败时阻断下游。告警不是终点，工单中要记录影响资产、发现时间、临时处理、根因、修复时间和防复发动作。

## 8. 异常排查：从指标异常回到业务事件

| 检查项 | 推荐方法 | 失败动作 | 负责人 |
| --- | --- | --- | --- |
| 工单与批次关系完整 | 唯一性 SQL + 抽样明细 | 阻断发布 | 计划 |
| 停机区间不重叠 | 时间区间与状态机校验 | 阻断发布 | 采购 |
| 质检结果可追到工序 | 主数据有效期关联 | 告警并登记工单 | 工艺 |
| 物料编码单位统一 | 金额或数量平衡校验 | 告警并登记工单 | 生产 |
| 设备组织关系保留有效期 | 发布前阻断 + 责任人复核 | 告警并登记工单 | 设备 |

围绕“生产周期”排查时，可以按以下顺序进行：

1. **影响面**：哪些指标、报表、接口或业务团队受影响，是否需要暂停对外发布。
2. **时间线**：源系统变更、任务发布、数据回刷、组织调整和业务活动分别发生在什么时候。
3. **数据链路**：上游是否延迟，分区是否缺失，主键是否重复，状态是否映射错误。
4. **业务证据**：抽取异常记录，与原始单据、操作日志、客服记录或现场系统核对。
5. **修复与复核**：明确补数范围、重跑粒度、回滚版本和验收样例。
6. **防复发**：把一次性排查升级为规则、监控、责任人和变更评审。

特别要注意：设备与工单编码变化导致断链；停机时长重复计算；质检抽样不能代表整批；计划版本与执行版本混用。这些问题如果不被单独标记，很容易被误写成业务趋势。

## 9. 第三个案例与延伸场景

### 案例 3：西南某食品加工企业的“生产周期”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：多工厂成本和损耗口径不同，集团无法比较不同产线的真实改善效果。本次讨论的重点是“生产周期”，所以团队先要求把把数据和业务动作一起复盘写进项目目标，而不是直接开始做报表。
- **数据范围**：工单投入产出、物料领用、能源、人工、报废、返工和成品入库。同时收集ERP、MES、PLM、QMS中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：月末盘点差异被平均分摊到所有批次，能源表计读数跨日切分不一致。进一步检查后发现，如果不先处理质检抽样不能代表整批，“生产周期”很容易被一个表面相关指标替代。
- **处理过程**：建立投入产出平衡、能源分摊和标准成本桥接，统一损耗定义与关账流程。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目将成本差异拆成价格、用量、良率和产量结构，并形成每周可行动清单。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“生产周期”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

另外两个适合继续拆分的工作场景是：

- **华北某新能源装备工厂**：设备预测性维护项目告警很多，但真正停机次数没有明显下降，现场对模型失去信任。可以先从振动、温度、电流、报警、维修工单、备件更换和停机记录建立最小数据闭环，再围绕“生产周期”检查传感器时间未统一，报警只记录触发不记录恢复，维修工单与设备状态缺少关联。

```sql
    AND relation_status = 'active'
)
SELECT
  d.asset_id,
  d.asset_name,
  d.asset_type,
  d.owner_name,
  d.criticality,
  d.last_used_at,
  COUNT(c.column_name) AS changed_column_cnt,
  CASE
    WHEN d.criticality IN ('core', 'regulated') THEN 'block_release'
    WHEN d.last_used_at >= CURRENT_DATE - INTERVAL '7 days' THEN 'notify_owner'
    ELSE 'register_review'
  END AS required_action
FROM downstream_assets d
CROSS JOIN changed_columns c
GROUP BY d.asset_id, d.asset_name, d.asset_type, d.owner_name, d.criticality, d.last_used_at
ORDER BY
  CASE WHEN d.criticality IN ('core', 'regulated') THEN 0 ELSE 1 END,
  d.last_used_at DESC;

-- 目标：变更前识别 ERP、MES、PLM 之后的所有结果与消费者。
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把生产周期的验收证据写成门禁

```python
from datetime import date
from hashlib import sha256

import pandas as pd

SUBJECT = "生产周期"
BLOCKING_RULES = ["工单与批次关系完整","停机区间不重叠","质检结果可追到工序"]


def validate_release(frame: pd.DataFrame, start: date, end: date) -> dict:
    scoped = frame.loc[
        frame["event_date"].between(pd.Timestamp(start), pd.Timestamp(end))
        & (frame["subject_key"] == "subject")
    ].copy()
    checks = {
        "has_rows": len(scoped) > 0,
        "event_id_unique": not scoped["event_id"].duplicated().any(),
        "entity_key_complete": scoped["entity_key"].notna().all(),
        "event_time_present": scoped["event_time"].notna().all(),
        "scope_matches": scoped["subject_key"].nunique() == 1,
    }
    payload = f"{SUBJECT}|{start}|{end}|{len(scoped)}|{sorted(checks.items())}"
    return {
        "subject": SUBJECT,
        "rows": len(scoped),
        "checks": checks,
        "blocking_rules": BLOCKING_RULES,
        "release_allowed": all(checks.values()),
        "evidence_hash": sha256(payload.encode("utf-8")).hexdigest(),
    }
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
