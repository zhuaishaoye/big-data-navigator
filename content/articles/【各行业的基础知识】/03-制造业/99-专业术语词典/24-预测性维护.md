# 预测性维护

> [!abstract] 设备可靠性与工业数据实战手册
> 预测性维护不是预测未来某天一定会故障的魔法模型，而是结合设备、传感器、工况、历史故障、维修工单和停机成本，提前识别风险并给出可执行检查动作。模型价值取决于告警是否可解释、误报成本是否可接受、维护资源是否跟得上。

## 1. 预测性维护：定义、适用边界与决策出口

预测性维护不是预测未来某天一定会故障的魔法模型，而是结合设备、传感器、工况、历史故障、维修工单和停机成本，提前识别风险并给出可执行检查动作。模型价值取决于告警是否可解释、误报成本是否可接受、维护资源是否跟得上。

**本篇的适用边界。** 本篇覆盖旋转设备、泵阀、电机和产线关键设备的传感器监测与维护决策；不把基于固定周期的大修简单包装成预测性维护。

**最常见的错误替代。** 不能用故障标签含糊的历史工单直接训练模型，也不能只看准确率；漏报、误报、提前期、停机和人工确认必须分别评估。

**最终决策。** 设备团队要判断：哪些设备需要提前检修，何时停机最合适，告警是否可信，备件和人员是否齐备，以及某次告警应该自动派单还是人工复核。 因此，这篇内容不从“应该建哪张表”开始，而从业务动作、责任人和失败后果开始。只有先确定谁在什么时点做出什么决定，字段、SQL、看板和模型才有明确用途。

围绕“预测性维护”，工作中至少要区分四类问题：

1. **身份问题**：对象是谁，主键能否跨系统稳定关联，合并、拆分、撤销后历史是否还看得见。
2. **时间问题**：业务发生、状态生效、数据入仓、计算完成和人员行动分别发生在哪一刻。
3. **状态问题**：当前状态是一段事件、一张快照还是最终结果，空值代表未发生、未采集还是已删除。
4. **责任问题**：谁确认口径，谁处理异常，谁有权放行或停止，谁在观察期后复盘。

## 2. 预测性维护的完整业务流程

| 环节 | 要做的事 | 最小证据 | 失败后先查什么 |
| --- | --- | --- | --- |
| 设备与测点建档 | 登记设备层级、部件、传感器、量程和安装位置 | 设备台账、测点表、校准记录 | 传感器停更仍沿用最后一个值 |
| 工况与事件采集 | 持续采集振动、温度、电流、压力和运行状态 | 时序数据、采样频率、时钟和缺失区间 | 所有工单都被视为设备故障 |
| 特征窗口 | 按设备状态和固定时间窗构造趋势、波动和异常特征 | 窗口版本、聚合函数、设备负载分层 | 误报导致停机成本却未计入评估 |
| 故障与维修标注 | 从工单、停机、备件和检查结果建立可验证标签 | 故障代码、检查结论、停机原因和维修时间 | 提示很多但没有工单、备件和停机窗口 |
| 风险评分 | 输出健康分、异常概率或剩余可用时间假设 | 模型版本、阈值、特征重要性和置信区间 | 传感器停更仍沿用最后一个值 |
| 告警与处置 | 将风险转换为复核、巡检、检修或停机建议 | 告警接收、确认、工单和处置结果 | 所有工单都被视为设备故障 |
| 效果评估 | 评估提前期、漏报、误报、停机和维护成本 | 基线、回放、工单闭环和模型监控 | 误报导致停机成本却未计入评估 |

把 设备与测点建档、工况与事件采集、特征窗口、故障与维修标注、风险评分、告警与处置、效果评估 串起来后可以看出，预测性维护不是一个孤立字段，而是一条会跨系统、跨岗位、跨时间的证据链。流程图上每一段都应标出输入、输出、状态、时间戳、责任人和异常出口。只要其中一段只能靠口头解释，后续的统计、追责和自动化就会失去基础。

一个合格的需求说明应该写成：

> 在【授权数据范围】和【观察窗口】内，围绕“预测性维护”的【设备】，按【asset_id、component_id、operating_mode、shift_code】比较【有效预警提前期】及其【告警精确率】，定位一个可干预节点；行动后同时观察主指标、样本量和护栏，任何高风险异常先阻断再调查。

## 3. 预测性维护的数据对象与系统契约

| 数据对象 | 建议主键 | 一行代表什么 | 不允许混淆 |
| --- | --- | --- | --- |
| 设备 | `asset_id` | 具有独立台账和维护策略的物理设备 | 对象身份与业务事件 |
| 部件 | `component_id` | 设备中可独立检测、维修或更换的部件 | 事件、状态快照和结果粒度 |
| 测点 | `sensor_tag_id` | 一个传感器在设备上的具体测量通道 | 事件、状态快照和结果粒度 |
| 监测窗口 | `monitor_window_id` | 固定时间、设备状态和特征版本下的观测窗口 | 事件、状态快照和结果粒度 |
| 告警 | `maintenance_alert_id` | 模型或规则产生的一次风险提示 | 事件、状态快照和结果粒度 |
| 维修工单 | `work_order_id` | 检查、维修、更换和停机执行记录 | 事件、状态快照和结果粒度 |

对象表不是把所有字段塞进一张宽表。事件、状态快照和结果表应该分别保留粒度，再通过稳定主键与版本建立关联。尤其要避免三个常见混算：把一次业务事件算成多个对象、把每日快照相加当事件总量、把最新状态覆盖历史状态。

本主题的数据契约至少应包含：

- `monitor_window_id` 的唯一性规则、生成方式和跨系统映射。
- `window_end_at` 的业务含义、时区、迟到和补录规则。
- `window_quality_status` 的完整状态集合，以及删除、撤销、冻结和失效的表示方法。
- 控制对象 `maintenance_work_order.work_order_id` 与主对象的关系。
- 每次口径、规则、模型或源版本变化的影响范围和下游通知对象。
- 敏感字段、允许用途、访问角色、导出限制和审计保留时间。

## 4. 预测性维护的指标、样本与验收口径

| 指标 | 公式或定义 | 口径提醒 |
| --- | --- | --- |
| 有效预警提前期 | 从告警到实际停机的可用小时数 / 有效告警数 | 提前期过短无法组织维修，过长可能失去时效 |
| 告警精确率 | 经检查确认的告警数 / 已处置告警数 | 必须说明由谁确认、在多长时间内确认 |
| 漏报率 | 未在故障前告警的故障事件数 / 可预警故障事件数 | 不可预警故障要单列，不能混算 |
| 误报处理成本 | 误报导致的检查工时和停机损失 / 误报数 | 按设备和班组分层 |
| 预警到工单闭环率 | 完成工单处置且记录结果的告警数 / 已发送告警数 | 通知不等于处置，处置不等于验证 |

指标字典至少写到“任何人都能按同一份数据复跑”的程度：中文名、业务定义、公式、分子、分母、事实粒度、时间字段、对象范围、排除项、版本、负责人和验收样例，一个都不能少。比例指标必须同时展示分子、分母和样本量；金额或数量必须做守恒；状态指标必须能回到事件时间线。

对于“预测性维护”，建议把观察分成三层：

| 层次 | 看什么 | 不能替代什么 |
| --- | --- | --- |
| 业务结果 | 有效预警提前期、告警精确率 | 不能替代过程证据和个案回查 |
| 过程护栏 | 漏报率、误报处理成本、预警到工单闭环率 | 不能因为护栏暂时正常就跳过异常调查 |
| 数据证据 | 主键、时间、状态、版本、来源目标对账 | 不能只看任务成功或报表能打开 |

## 5. 预测性维护：七个真实工作场景

以下七组场景均为公开方法结合常见工作流程构造的“脱敏复合示例”，不对应任何单一企业、患者、客户或雇员事实。场景的目的，是展示如何从现象走到证据、行动和验收，而不是虚构经营成果。

### 1. 传感器缺失被误判为设备正常

**现场。** 某设备健康分稳定，但现场巡检发现温度异常。

**怎么查。** 检查时序数据发现测点连续数小时没有新值，平台把最后值填充后继续计算。

**怎么处理。** 增加测点新鲜度和缺失率门禁；缺数据输出未知而不是正常；告警路由到数据负责人和现场巡检。

**验收结论。** 未知状态不能被健康模型填成安全结论。

### 2. 工单文本无法作为故障标签

**现场。** 维修记录只有“已处理”三个字，团队准备将全部工单视为故障。

**怎么查。** 抽样工单、备件和停机数据，区分计划保养、误操作、点检和真实部件失效。

**怎么处理。** 重写故障分类和关闭字段；只有检查结论和部件更换能支撑的工单才作为标签；无标签样本单列。

**验收结论。** 标签质量决定模型上限。把所有维修都算故障只会训练出保养日历。

### 3. 负载变化造成大量误报

**现场。** 同一设备在高负荷班次频繁告警，低负荷时一切正常。

**怎么查。** 把负载、转速、环境温度、产品规格和传感器基线放入分层分析，发现模型使用全厂统一阈值。

**怎么处理。** 按工况建立基线；输出相对当前工况的风险；告警附上最相关特征和最近相似历史。

**验收结论。** 异常必须相对于工况，不是相对于一条全厂平均曲线。

### 4. 告警太多导致现场忽略

**现场。** 模型上线后每天产生数百条提示，巡检人员开始批量关闭。

**怎么查。** 分析告警优先级、重复率、确认时间和处置结果，发现同一故障持续重复触发。

**怎么处理。** 设置冷却窗口和事件合并；先按风险与可执行性排序；把不可行动告警留在观察层，不生成工单。

**验收结论。** 告警是一种稀缺注意力资源。不能行动的提示不应打扰现场。

### 5. 检修资源没有随预测排程

**现场。** 系统提前发现风险，但关键备件缺货，停机窗口也无法安排。

**怎么查。** 关联告警、备件库存、人员班次和产线计划，发现预测与供应链、排产系统脱节。

**怎么处理。** 告警处置流程纳入备件可用性和生产计划；低库存关键备件提前触发补货；无法停机时输出临时监控方案。

**验收结论。** 预测准确不等于维护完成。决策链路必须包含资源和时间约束。

### 6. 故障后没有反馈模型

**现场。** 某次严重故障发生前没有预警，团队只在线下复盘。

**怎么查。** 回放故障前数周的传感器、工况和维护事件，判断是信号缺失、特征漂移、标签错误还是模型阈值问题。

**怎么处理。** 把复盘结论写入回归样本和模型版本；补充负样本和边界样本；再训练前先修复数据与流程。

**验收结论。** 故障回放是模型资产，不是一次性会议材料。

### 7. 跨工厂复制模型水土不服

**现场。** 总部模型在一个新工厂直接上线后精确率明显下降。

**怎么查。** 比较设备型号、工况、采样频率、维护质量、故障定义和产品节拍，发现新工厂缺少稳定标签。

**怎么处理。** 先在目标工厂做影子运行和人工对照；校准测点与标签；达到门槛后再进入告警流程。

**验收结论。** 模型跨域迁移需要证据。相同设备名称不代表相同数据分布。

七个场景可以归成一条共同判断顺序：先确认对象和时间，再确认状态和版本；然后做总量、结构和明细三层对账；最后才讨论策略、模型或工具。若一条结论不能指出对应的原始记录、责任人和行动出口，就只能算观察，不能作为生产结论。

## 6. 预测性维护的第一段 SQL：重建业务链路

下面的 SQL 用于说明对象、时间、状态、版本和分层口径如何进入同一条可复查路径。表名和部分字段是通用示例，落地时应映射到企业数据字典；SQL 方言也需按实际引擎调整。

```sql
-- 预测性维护：按业务对象重建链路，避免事件、快照和结果混算
WITH ranked_monitor_window_id AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY monitor_window_id
      ORDER BY updated_at DESC
    ) AS version_no
  FROM iot_equipment_sensor_window
  WHERE window_end_at >= TIMESTAMP '{start_time}'
    AND window_end_at <  TIMESTAMP '{end_time}'
    AND window_quality_status NOT IN ('deleted', 'test')
),
valid_rows AS (
  SELECT
    monitor_window_id,
    asset_id,
    component_id,
    operating_mode,
    shift_code,
    window_end_at,
    window_quality_status,
    ingested_at
  FROM ranked_monitor_window_id
  WHERE version_no = 1
)
SELECT
  asset_id, component_id, operating_mode, shift_code,
  COUNT(DISTINCT monitor_window_id) AS object_cnt,
  COUNT(DISTINCT CASE WHEN alert_confirmed THEN alert_id END) AS numerator_value,
  COUNT(DISTINCT alert_id) AS denominator_value,
  CAST(COUNT(DISTINCT CASE WHEN alert_confirmed THEN alert_id END) AS DOUBLE PRECISION)
    / NULLIF(COUNT(DISTINCT alert_id), 0) AS metric_value,
  MIN(window_end_at) AS first_event_at,
  MAX(window_end_at) AS last_event_at
FROM valid_rows
GROUP BY asset_id, component_id, operating_mode, shift_code
ORDER BY metric_value DESC, object_cnt DESC;
```

执行后至少回答六个问题：

- 同一对象是否因为多源回传产生多版本，版本保留是否符合业务要求？
- 业务时间与入仓时间是否分开，补录和迟到数据是否进入正确分区？
- 分子分母是否来自同一对象范围和同一统计窗口？
- 维度使用的是事件当时值还是当前值，跨期比较是否一致？
- 删除、撤销、冻结和测试数据是否按规则处理？
- 分组结果能否在明细中抽样复现？

## 7. 预测性维护的第二段 SQL：源、控制和结果三方对账

```sql
-- 预测性维护：源对象、控制对象和结果对象三方对账
WITH population AS (
  SELECT
    monitor_window_id,
    window_end_at,
    window_quality_status
  FROM iot_equipment_sensor_window
  WHERE window_end_at >= TIMESTAMP '{start_time}'
    AND window_end_at <  TIMESTAMP '{end_time}'
),
control AS (
  SELECT
    monitor_window_id,
    SUM(closed_flag) AS control_value,
    COUNT(DISTINCT work_order_id) AS control_cnt,
    MAX(updated_at) AS control_updated_at
  FROM maintenance_work_order
  WHERE updated_at >= TIMESTAMP '{start_time}'
  GROUP BY monitor_window_id
),
result AS (
  SELECT
    monitor_window_id,
    COUNT(*) AS result_cnt,
    MAX(calculated_at) AS calculated_at
  FROM mart_monitor_window_id
  WHERE business_date BETWEEN DATE '{start_date}' AND DATE '{end_date}'
  GROUP BY monitor_window_id
)
SELECT
  COALESCE(p.monitor_window_id, c.monitor_window_id, r.monitor_window_id) AS object_key,
  CASE
    WHEN p.monitor_window_id IS NULL THEN 'source_missing'
    WHEN c.monitor_window_id IS NULL THEN 'control_missing'
    WHEN r.monitor_window_id IS NULL THEN 'result_missing'
    WHEN ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0 THEN 'count_or_value_gap'
    ELSE 'matched'
  END AS reconciliation_status,
  p.window_quality_status,
  c.control_value,
  c.control_cnt,
  r.result_cnt,
  c.control_updated_at,
  r.calculated_at
FROM population p
FULL OUTER JOIN control c ON p.monitor_window_id = c.monitor_window_id
FULL OUTER JOIN result r ON COALESCE(p.monitor_window_id, c.monitor_window_id) = r.monitor_window_id
WHERE p.monitor_window_id IS NULL
   OR c.monitor_window_id IS NULL
   OR r.monitor_window_id IS NULL
   OR ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0;
```

这段查询故意不使用“总数相差小于某个随意百分比就算通过”。它先找出缺失对象和状态差异，再检查控制值与结果值。对于预测性维护，数量、金额、时长或状态任意一项无法解释，都不能用“业务波动”代替排查。

对账结果建议分成四类处理：

1. **阻断**：对象缺失、关键时间为空、状态非法、金额或数量不守恒、权限越界。
2. **严重**：比例或总量显著偏离基线，且无法由已确认的对象结构变化解释。
3. **观察**：小范围波动但来源、样本和趋势可控，进入责任人和观察窗口。
4. **探索**：只有弱信号或假设，不进入正式结论，更不直接触发业务处罚。

## 8. 预测性维护的 Python 发布门禁与指标护栏

第一段代码把发布条件写成可执行对象，避免“检查过了”只存在聊天记录里：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class MonitorWindowIdBatch:
    batch_id: str
    source_rows: int
    valid_rows: int
    duplicate_keys: int
    missing_required_fields: int
    reconciliation_gap: float

def release_monitor_window_id(batch: MonitorWindowIdBatch) -> dict:
    checks = {
        "source_not_empty": batch.source_rows > 0,
        "valid_rows_in_range": 0 <= batch.valid_rows <= batch.source_rows,
        "duplicate_rate_ok": batch.duplicate_keys / max(batch.source_rows, 1) <= 0.001,
        "required_fields_ok": batch.missing_required_fields == 0,
        "reconciliation_ok": abs(batch.reconciliation_gap) <= 0.01,
    }
    return {
        "topic": "预测性维护",
        "batch_id": batch.batch_id,
        "checks": checks,
        "release_allowed": all(checks.values()),
        "blocking_checks": [name for name, passed in checks.items() if not passed],
    }
```

第二段代码演示如何为比例类结果附带样本证据和小样本下界。它不是替代统计学家的模型，而是防止把少量偶然样本直接包装成稳定结论：

```python
from dataclasses import dataclass
from math import sqrt

@dataclass(frozen=True)
class MonitorWindowIdObservation:
    object_id: str
    numerator: float
    denominator: float
    sample_size: int
    scope_version: str

def calculate_monitor_window_id(rows: list[MonitorWindowIdObservation]) -> list[dict]:
    output = []
    for row in rows:
        value = row.numerator / row.denominator if row.denominator > 0 else None
        # 小样本用 Wilson 下界做护栏，不把偶然的高比例直接当稳定结果。
        z = 1.96
        p = value or 0
        n = max(row.sample_size, 1)
        center = p + z * z / (2 * n)
        margin = z * sqrt((p * (1 - p) + z * z / (4 * n)) / n)
        lower = max(0, (center - margin) / (1 + z * z / n))
        output.append({
            "object_id": row.object_id,
            "metric": "有效预警提前期",
            "value": value,
            "lower_bound": lower if value is not None else None,
            "sample_size": row.sample_size,
            "scope_version": row.scope_version,
            "caution": "提前期过短无法组织维修，过长可能失去时效",
        })
    return output
```

真正上线时还要补充参数配置、日志、血缘、告警级别、重跑幂等、异常样本保存和审批记录。代码通过不代表业务通过；自动检查只能证明已经定义的规则没有被违反，无法证明规则本身一定正确。

## 9. 预测性维护的失败反例与上线验收

| 风险信号 | 错误做法 | 必须补齐的证据 | 发布或行动规则 |
| --- | --- | --- | --- |
| 缺数据被填成正常 | 传感器停更仍沿用最后一个值 | 数据新鲜度、覆盖率和未知状态 | 无有效数据不输出正常结论 |
| 故障标签含糊 | 所有工单都被视为设备故障 | 故障代码、检查结论和部件更换 | 标签不足时先做规则或人工标注 |
| 只看模型准确率 | 误报导致停机成本却未计入评估 | 告警精确率、提前期和处置成本 | 模型指标与业务成本联合验收 |
| 告警无行动出口 | 提示很多但没有工单、备件和停机窗口 | 接收人、工单、资源和处置结果 | 不可行动告警不进入正式派单 |

上线验收不应只有一句“报表正常”。建议按下面四层验收：

| 验收对象 | 结构要求 | 测试样本 | 结果证据 |
| --- | --- | --- | --- |
| 设备 | `asset_id` 能唯一定位具有独立台账和维护策略的物理设备 | 正常、重复、缺失、撤销与跨期样本 | 有效预警提前期可回到原始对象 |
| 部件 | `component_id` 能唯一定位设备中可独立检测、维修或更换的部件 | 正常、重复、缺失、撤销与跨期样本 | 告警精确率可回到原始对象 |
| 测点 | `sensor_tag_id` 能唯一定位一个传感器在设备上的具体测量通道 | 正常、重复、缺失、撤销与跨期样本 | 漏报率可回到原始对象 |
| 监测窗口 | `monitor_window_id` 能唯一定位固定时间、设备状态和特征版本下的观测窗口 | 正常、重复、缺失、撤销与跨期样本 | 误报处理成本可回到原始对象 |
| 告警 | `maintenance_alert_id` 能唯一定位模型或规则产生的一次风险提示 | 正常、重复、缺失、撤销与跨期样本 | 预警到工单闭环率可回到原始对象 |
| 维修工单 | `work_order_id` 能唯一定位检查、维修、更换和停机执行记录 | 正常、重复、缺失、撤销与跨期样本 | 有效预警提前期可回到原始对象 |

还应为每一次发布保留一组固定回归样本：正常对象、边界状态、重复记录、缺失字段、撤销或退款、跨期、权限拒绝和失败恢复。回归样本不是演示数据，而是以后每次改规则都能重复执行的质量资产。

## 10. 预测性维护的 30 天落地与复盘

| 阶段 | 主要交付 | 通过条件 |
| --- | --- | --- |
| 第 1 周：定义 | 对象、流程、状态、指标、排除项和责任矩阵 | 业务、数据、安全或质量负责人对同一口径签字 |
| 第 2 周：打通 | 源字段、主键、时间、版本、控制对象和失败样本 | 正常与异常样本都能回到原始记录 |
| 第 3 周：验证 | 总量对账、分层对账、抽样回查、权限测试、回滚演练 | 阻断问题清零，严重问题有责任人与期限 |
| 第 4 周：发布 | 灰度、SLO、监控、行动清单、停止条件和复盘模板 | 使用者在真实场景中完成一次闭环行动 |

如果必须用 90 秒说明“预测性维护”是否做对，可以按这个顺序自测：

1. 一行数据代表什么，主键是什么，哪些对象绝不能混在同一粒度？
2. 业务发生、数据可见、计算完成和行动确认分别在哪个时间点？
3. 本主题最重要的两个主指标、三个护栏和最小样本量是什么？
4. 一个异常出现时，先从原始记录、链路版本还是业务动作开始查？
5. 哪类错误必须阻断发布或停止使用，谁有权批准例外？
6. 上线后由谁在多长时间内观察，什么条件下回滚或结束？

> [!check] 完成标准
> 当另一位数据同事不看聊天记录，只根据口径卡、回归样本和代码就能复跑同一结果；当业务负责人能指出一个异常对应的原始对象、处置动作和复核证据；当系统能够阻止未授权或状态非法的数据进入下游，这篇“预测性维护”才算真正落到工作里。
