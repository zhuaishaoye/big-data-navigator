# 智能制造转型

> [!abstract] 制造企业数字化升级实战手册
> 智能制造转型不是购买几台机器人或上线一个 MES，而是围绕产品、订单、工艺、设备、质量、供应链和组织能力进行分阶段改造。数据工作要能证明试点解决了什么业务问题、改造边界在哪里、投资和停机风险是否可控，以及规模化复制需要什么条件。

## 1. 智能制造转型：定义、适用边界与决策出口

智能制造转型不是购买几台机器人或上线一个 MES，而是围绕产品、订单、工艺、设备、质量、供应链和组织能力进行分阶段改造。数据工作要能证明试点解决了什么业务问题、改造边界在哪里、投资和停机风险是否可控，以及规模化复制需要什么条件。

**本篇的适用边界。** 本篇讨论离散或流程制造企业从传统生产向数据驱动、柔性化和协同化升级的规划与评估；不把单一自动化设备、单点看板或软件采购等同于转型完成。

**最常见的错误替代。** 不能用系统上线数量衡量转型，也不能在基础主数据、设备联网和现场执行尚不稳定时直接追求无人工厂。

**最终决策。** 经营层和工厂团队要判断：先改哪条产线，试点是否通过，是否扩展到多工厂，投资如何回收，组织与岗位如何调整，以及何时暂停或退出。 因此，这篇内容不从“应该建哪张表”开始，而从业务动作、责任人和失败后果开始。只有先确定谁在什么时点做出什么决定，字段、SQL、看板和模型才有明确用途。

围绕“智能制造转型”，工作中至少要区分四类问题：

1. **身份问题**：对象是谁，主键能否跨系统稳定关联，合并、拆分、撤销后历史是否还看得见。
2. **时间问题**：业务发生、状态生效、数据入仓、计算完成和人员行动分别发生在哪一刻。
3. **状态问题**：当前状态是一段事件、一张快照还是最终结果，空值代表未发生、未采集还是已删除。
4. **责任问题**：谁确认口径，谁处理异常，谁有权放行或停止，谁在观察期后复盘。

## 2. 智能制造转型的完整业务流程

| 环节 | 要做的事 | 最小证据 | 失败后先查什么 |
| --- | --- | --- | --- |
| 战略与现状评估 | 明确质量、成本、交付、柔性和能耗目标并建立基线 | 经营目标、产线现状、瓶颈、投资约束 | 设备接入很多但业务指标不可用 |
| 产品与工艺标准化 | 梳理 BOM、工艺路线、工时、质量和设备参数 | 主数据、工艺版本、标准和变更记录 | 单站效率提高但总产出未变 |
| 设备联网与现场采集 | 连接 PLC、SCADA、传感器和工单执行 | 设备台账、采集点、事件和质量状态 | 报工完成即认定工单完成 |
| 系统与流程集成 | 打通 ERP、MES、WMS、QMS 和设备系统 | 接口契约、工单、库存、质量和报工 | 把自然增长算作项目收益 |
| 试点产线改造 | 在有限范围实施自动化、排产或质量优化 | 改造范围、基线、并行运行和风险控制 | 设备接入很多但业务指标不可用 |
| 人员与组织调整 | 重新定义岗位、技能、排班和责任边界 | 培训、实操、岗位变化和采用证据 | 单站效率提高但总产出未变 |
| 评估与规模化 | 验证财务和非财务收益，形成复制和退出条件 | 投资回收、OEE、质量、交付和复盘 | 报工完成即认定工单完成 |

把 战略与现状评估、产品与工艺标准化、设备联网与现场采集、系统与流程集成、试点产线改造、人员与组织调整、评估与规模化 串起来后可以看出，智能制造转型不是一个孤立字段，而是一条会跨系统、跨岗位、跨时间的证据链。流程图上每一段都应标出输入、输出、状态、时间戳、责任人和异常出口。只要其中一段只能靠口头解释，后续的统计、追责和自动化就会失去基础。

一个合格的需求说明应该写成：

> 在【授权数据范围】和【观察窗口】内，围绕“智能制造转型”的【转型举措】，按【factory_id、production_line_id、product_family、shift_code】比较【设备综合效率 OEE】及其【订单准交率】，定位一个可干预节点；行动后同时观察主指标、样本量和护栏，任何高风险异常先阻断再调查。

## 3. 智能制造转型的数据对象与系统契约

| 数据对象 | 建议主键 | 一行代表什么 | 不允许混淆 |
| --- | --- | --- | --- |
| 转型举措 | `transformation_initiative_id` | 一个具有目标、范围、预算和阶段门禁的改造 | 对象身份与业务事件 |
| 工厂与产线 | `production_line_id` | 改造涉及的物理生产和组织单元 | 事件、状态快照和结果粒度 |
| 产品与工艺路线 | `routing_version_id` | 某产品在有效期内的工序、设备和标准参数 | 事件、状态快照和结果粒度 |
| 设备与工单 | `work_order_id` | 生产执行与设备状态关联的最小业务过程 | 事件、状态快照和结果粒度 |
| 试点改造 | `pilot_id` | 限定产品、产线和周期内的方案验证 | 事件、状态快照和结果粒度 |
| 收益证据 | `benefit_evidence_id` | 成本、质量、交付、能耗或柔性改善的可复核记录 | 事件、状态快照和结果粒度 |

对象表不是把所有字段塞进一张宽表。事件、状态快照和结果表应该分别保留粒度，再通过稳定主键与版本建立关联。尤其要避免三个常见混算：把一次业务事件算成多个对象、把每日快照相加当事件总量、把最新状态覆盖历史状态。

本主题的数据契约至少应包含：

- `factory_kpi_snapshot_id` 的唯一性规则、生成方式和跨系统映射。
- `snapshot_at` 的业务含义、时区、迟到和补录规则。
- `data_quality_status` 的完整状态集合，以及删除、撤销、冻结和失效的表示方法。
- 控制对象 `mes_work_order_execution.work_order_execution_id` 与主对象的关系。
- 每次口径、规则、模型或源版本变化的影响范围和下游通知对象。
- 敏感字段、允许用途、访问角色、导出限制和审计保留时间。

## 4. 智能制造转型的指标、样本与验收口径

| 指标 | 公式或定义 | 口径提醒 |
| --- | --- | --- |
| 设备综合效率 OEE | 可用率 × 性能率 × 良品率 | 三项都要展示，不能只报一个乘积 |
| 订单准交率 | 按承诺时间完整交付的订单数 / 应交付订单数 | 改期、拆单和部分交付需登记 |
| 一次合格率 | 首次检验合格的产出数 / 首次检验总数 | 返工和复检结果单列 |
| 单位产品制造成本 | 制造成本 / 合格产出数量 | 需固定产品结构和核算范围 |
| 试点收益达成率 | 已验证收益 / 立项承诺收益 | 区分硬收益、软收益和尚未验证收益 |

指标字典至少写到“任何人都能按同一份数据复跑”的程度：中文名、业务定义、公式、分子、分母、事实粒度、时间字段、对象范围、排除项、版本、负责人和验收样例，一个都不能少。比例指标必须同时展示分子、分母和样本量；金额或数量必须做守恒；状态指标必须能回到事件时间线。

对于“智能制造转型”，建议把观察分成三层：

| 层次 | 看什么 | 不能替代什么 |
| --- | --- | --- |
| 业务结果 | 设备综合效率 OEE、订单准交率 | 不能替代过程证据和个案回查 |
| 过程护栏 | 一次合格率、单位产品制造成本、试点收益达成率 | 不能因为护栏暂时正常就跳过异常调查 |
| 数据证据 | 主键、时间、状态、版本、来源目标对账 | 不能只看任务成功或报表能打开 |

## 5. 智能制造转型：七个真实工作场景

以下七组场景均为公开方法结合常见工作流程构造的“脱敏复合示例”，不对应任何单一企业、患者、客户或雇员事实。场景的目的，是展示如何从现象走到证据、行动和验收，而不是虚构经营成果。

### 1. 设备联网率很高但 OEE 仍不可信

**现场。** 多个工厂展示联网率超过 95%，管理层无法比较 OEE。

**怎么查。** 抽查设备状态、停机原因、标准节拍和良品数量，发现各厂对计划停机和换型时间定义不同。

**怎么处理。** 统一 OEE 口径和停机分类；联网率只作为数据覆盖指标；按产品和产线验证三项分指标。

**验收结论。** 连接设备不是终点。没有统一业务状态，联网只会更快地产生不可比数字。

### 2. 自动化设备没有解决瓶颈工序

**现场。** 某产线增加机器人后整体产出提升有限。

**怎么查。** 做工序能力、在制品、等待和换型分析，发现机器人工序不是瓶颈，前后物料配送才限制产出。

**怎么处理。** 重新做瓶颈识别；调整试点范围；同步改造物流和排产；用端到端产出而不是单站节拍验收。

**验收结论。** 局部自动化可能只是把等待转移到别处。转型必须看整条价值流。

### 3. 系统数据与现场实际不一致

**现场。** MES 显示工单完成，仓库仍缺成品。

**怎么查。** 关联报工、质检、入库、批次和接口日志，发现报工通过后质量放行和仓库过账未完成。

**怎么处理。** 定义端到端工单状态；区分生产完成、质量放行和可发货；异常工单进入人工核对。

**验收结论。** 系统完成不等于业务完成。状态链必须覆盖下游真实动作。

### 4. 试点收益来自产量自然增长

**现场。** 改造后单位成本下降，项目被认定成功。

**怎么查。** 比较产品结构、产量、原料价格、班次和可比产线，发现高毛利产品占比上升。

**怎么处理。** 固定产品结构和核算范围；设置对照产线或基线期；收益验证延长完整经营周期。

**验收结论。** 结果改善不一定来自项目。转型评估必须处理混杂因素。

### 5. 新系统增加一线负担

**现场。** 管理层看到流程在线率上升，现场人员却使用纸单再补录。

**怎么查。** 观察实际任务时长、补录率、错误和访谈反馈，发现移动端网络和字段设计不适合现场。

**怎么处理。** 让一线参与流程设计；先优化高频任务；减少重复录入；采用率按无纸实际完成而非登录次数统计。

**验收结论。** 系统登录不等于采用。数字化不能把成本从办公室转给现场。

### 6. 规模化复制忽略工厂差异

**现场。** 单厂试点成功后在集团复制，多个工厂延误。

**怎么查。** 比较产品、工艺、设备年代、组织、网络和本地系统，发现试点依赖定制接口和高技能团队。

**怎么处理。** 产品化标准能力与本地适配分开；建立复制评估清单；每厂先做小范围影子运行和差距整改。

**验收结论。** 试点是验证假设，规模化是验证可复制性。

### 7. 转型项目没有停止条件

**现场。** 投资持续增加，关键指标仍未达到阶段目标。

**怎么查。** 检查阶段门禁、收益证据和范围变更，发现每次延期都以“智能制造需要长期投入”解释。

**怎么处理。** 在立项时写明阶段目标、预算上限、止损和转向条件；重大范围变化重新审批；保留阶段性退出方案。

**验收结论。** 长期方向正确不代表每个项目都应无限继续。

七个场景可以归成一条共同判断顺序：先确认对象和时间，再确认状态和版本；然后做总量、结构和明细三层对账；最后才讨论策略、模型或工具。若一条结论不能指出对应的原始记录、责任人和行动出口，就只能算观察，不能作为生产结论。

## 6. 智能制造转型的第一段 SQL：重建业务链路

下面的 SQL 用于说明对象、时间、状态、版本和分层口径如何进入同一条可复查路径。表名和部分字段是通用示例，落地时应映射到企业数据字典；SQL 方言也需按实际引擎调整。

```sql
-- 智能制造转型：按业务对象重建链路，避免事件、快照和结果混算
WITH ranked_factory_kpi_snapshot_id AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY factory_kpi_snapshot_id
      ORDER BY updated_at DESC
    ) AS version_no
  FROM mfg_smart_factory_kpi
  WHERE snapshot_at >= TIMESTAMP '{start_time}'
    AND snapshot_at <  TIMESTAMP '{end_time}'
    AND data_quality_status NOT IN ('deleted', 'test')
),
valid_rows AS (
  SELECT
    factory_kpi_snapshot_id,
    factory_id,
    production_line_id,
    product_family,
    shift_code,
    snapshot_at,
    data_quality_status,
    ingested_at
  FROM ranked_factory_kpi_snapshot_id
  WHERE version_no = 1
)
SELECT
  factory_id, production_line_id, product_family, shift_code,
  COUNT(DISTINCT factory_kpi_snapshot_id) AS object_cnt,
  SUM(good_output_qty) AS numerator_value,
  SUM(planned_output_qty) AS denominator_value,
  CAST(SUM(good_output_qty) AS DOUBLE PRECISION)
    / NULLIF(SUM(planned_output_qty), 0) AS metric_value,
  MIN(snapshot_at) AS first_event_at,
  MAX(snapshot_at) AS last_event_at
FROM valid_rows
GROUP BY factory_id, production_line_id, product_family, shift_code
ORDER BY metric_value DESC, object_cnt DESC;
```

执行后至少回答六个问题：

- 同一对象是否因为多源回传产生多版本，版本保留是否符合业务要求？
- 业务时间与入仓时间是否分开，补录和迟到数据是否进入正确分区？
- 分子分母是否来自同一对象范围和同一统计窗口？
- 维度使用的是事件当时值还是当前值，跨期比较是否一致？
- 删除、撤销、冻结和测试数据是否按规则处理？
- 分组结果能否在明细中抽样复现？

## 7. 智能制造转型的第二段 SQL：源、控制和结果三方对账

```sql
-- 智能制造转型：源对象、控制对象和结果对象三方对账
WITH population AS (
  SELECT
    factory_kpi_snapshot_id,
    snapshot_at,
    data_quality_status
  FROM mfg_smart_factory_kpi
  WHERE snapshot_at >= TIMESTAMP '{start_time}'
    AND snapshot_at <  TIMESTAMP '{end_time}'
),
control AS (
  SELECT
    factory_kpi_snapshot_id,
    SUM(confirmed_output_qty) AS control_value,
    COUNT(DISTINCT work_order_execution_id) AS control_cnt,
    MAX(updated_at) AS control_updated_at
  FROM mes_work_order_execution
  WHERE updated_at >= TIMESTAMP '{start_time}'
  GROUP BY factory_kpi_snapshot_id
),
result AS (
  SELECT
    factory_kpi_snapshot_id,
    COUNT(*) AS result_cnt,
    MAX(calculated_at) AS calculated_at
  FROM mart_factory_kpi_snapshot_id
  WHERE business_date BETWEEN DATE '{start_date}' AND DATE '{end_date}'
  GROUP BY factory_kpi_snapshot_id
)
SELECT
  COALESCE(p.factory_kpi_snapshot_id, c.factory_kpi_snapshot_id, r.factory_kpi_snapshot_id) AS object_key,
  CASE
    WHEN p.factory_kpi_snapshot_id IS NULL THEN 'source_missing'
    WHEN c.factory_kpi_snapshot_id IS NULL THEN 'control_missing'
    WHEN r.factory_kpi_snapshot_id IS NULL THEN 'result_missing'
    WHEN ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0 THEN 'count_or_value_gap'
    ELSE 'matched'
  END AS reconciliation_status,
  p.data_quality_status,
  c.control_value,
  c.control_cnt,
  r.result_cnt,
  c.control_updated_at,
  r.calculated_at
FROM population p
FULL OUTER JOIN control c ON p.factory_kpi_snapshot_id = c.factory_kpi_snapshot_id
FULL OUTER JOIN result r ON COALESCE(p.factory_kpi_snapshot_id, c.factory_kpi_snapshot_id) = r.factory_kpi_snapshot_id
WHERE p.factory_kpi_snapshot_id IS NULL
   OR c.factory_kpi_snapshot_id IS NULL
   OR r.factory_kpi_snapshot_id IS NULL
   OR ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0;
```

这段查询故意不使用“总数相差小于某个随意百分比就算通过”。它先找出缺失对象和状态差异，再检查控制值与结果值。对于智能制造转型，数量、金额、时长或状态任意一项无法解释，都不能用“业务波动”代替排查。

对账结果建议分成四类处理：

1. **阻断**：对象缺失、关键时间为空、状态非法、金额或数量不守恒、权限越界。
2. **严重**：比例或总量显著偏离基线，且无法由已确认的对象结构变化解释。
3. **观察**：小范围波动但来源、样本和趋势可控，进入责任人和观察窗口。
4. **探索**：只有弱信号或假设，不进入正式结论，更不直接触发业务处罚。

## 8. 智能制造转型的 Python 发布门禁与指标护栏

第一段代码把发布条件写成可执行对象，避免“检查过了”只存在聊天记录里：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class FactoryKpiSnapshotIdBatch:
    batch_id: str
    source_rows: int
    valid_rows: int
    duplicate_keys: int
    missing_required_fields: int
    reconciliation_gap: float

def release_factory_kpi_snapshot_id(batch: FactoryKpiSnapshotIdBatch) -> dict:
    checks = {
        "source_not_empty": batch.source_rows > 0,
        "valid_rows_in_range": 0 <= batch.valid_rows <= batch.source_rows,
        "duplicate_rate_ok": batch.duplicate_keys / max(batch.source_rows, 1) <= 0.001,
        "required_fields_ok": batch.missing_required_fields == 0,
        "reconciliation_ok": abs(batch.reconciliation_gap) <= 0.01,
    }
    return {
        "topic": "智能制造转型",
        "batch_id": batch.batch_id,
        "checks": checks,
        "release_allowed": all(checks.values()),
        "blocking_checks": [name for name, passed in checks.items() if not passed],
    }
```

第二段代码演示如何为比例类结果附带样本证据和小样本下界。它不是替代统计学家的模型，而是防止把少量偶然样本直接包装成稳定结论：

```python
from dataclasses import dataclass
from math import sqrt

@dataclass(frozen=True)
class FactoryKpiSnapshotIdObservation:
    object_id: str
    numerator: float
    denominator: float
    sample_size: int
    scope_version: str

def calculate_factory_kpi_snapshot_id(rows: list[FactoryKpiSnapshotIdObservation]) -> list[dict]:
    output = []
    for row in rows:
        value = row.numerator / row.denominator if row.denominator > 0 else None
        # 小样本用 Wilson 下界做护栏，不把偶然的高比例直接当稳定结果。
        z = 1.96
        p = value or 0
        n = max(row.sample_size, 1)
        center = p + z * z / (2 * n)
        margin = z * sqrt((p * (1 - p) + z * z / (4 * n)) / n)
        lower = max(0, (center - margin) / (1 + z * z / n))
        output.append({
            "object_id": row.object_id,
            "metric": "设备综合效率 OEE",
            "value": value,
            "lower_bound": lower if value is not None else None,
            "sample_size": row.sample_size,
            "scope_version": row.scope_version,
            "caution": "三项都要展示，不能只报一个乘积",
        })
    return output
```

真正上线时还要补充参数配置、日志、血缘、告警级别、重跑幂等、异常样本保存和审批记录。代码通过不代表业务通过；自动检查只能证明已经定义的规则没有被违反，无法证明规则本身一定正确。

## 9. 智能制造转型的失败反例与上线验收

| 风险信号 | 错误做法 | 必须补齐的证据 | 发布或行动规则 |
| --- | --- | --- | --- |
| 联网率冒充转型 | 设备接入很多但业务指标不可用 | 设备状态、业务事件和收益证据 | 联网率只作基础覆盖指标 |
| 局部优化转移瓶颈 | 单站效率提高但总产出未变 | 端到端节拍、在制品和等待 | 按价值流验收 |
| 系统状态不闭环 | 报工完成即认定工单完成 | 质检、入库和发货状态 | 端到端状态才可确认交付 |
| 收益无法归因 | 把自然增长算作项目收益 | 基线、对照和结构变化 | 收益证据带口径与观察周期 |

上线验收不应只有一句“报表正常”。建议按下面四层验收：

| 验收对象 | 结构要求 | 测试样本 | 结果证据 |
| --- | --- | --- | --- |
| 转型举措 | `transformation_initiative_id` 能唯一定位一个具有目标、范围、预算和阶段门禁的改造 | 正常、重复、缺失、撤销与跨期样本 | 设备综合效率 OEE可回到原始对象 |
| 工厂与产线 | `production_line_id` 能唯一定位改造涉及的物理生产和组织单元 | 正常、重复、缺失、撤销与跨期样本 | 订单准交率可回到原始对象 |
| 产品与工艺路线 | `routing_version_id` 能唯一定位某产品在有效期内的工序、设备和标准参数 | 正常、重复、缺失、撤销与跨期样本 | 一次合格率可回到原始对象 |
| 设备与工单 | `work_order_id` 能唯一定位生产执行与设备状态关联的最小业务过程 | 正常、重复、缺失、撤销与跨期样本 | 单位产品制造成本可回到原始对象 |
| 试点改造 | `pilot_id` 能唯一定位限定产品、产线和周期内的方案验证 | 正常、重复、缺失、撤销与跨期样本 | 试点收益达成率可回到原始对象 |
| 收益证据 | `benefit_evidence_id` 能唯一定位成本、质量、交付、能耗或柔性改善的可复核记录 | 正常、重复、缺失、撤销与跨期样本 | 设备综合效率 OEE可回到原始对象 |

还应为每一次发布保留一组固定回归样本：正常对象、边界状态、重复记录、缺失字段、撤销或退款、跨期、权限拒绝和失败恢复。回归样本不是演示数据，而是以后每次改规则都能重复执行的质量资产。

## 10. 智能制造转型的 30 天落地与复盘

| 阶段 | 主要交付 | 通过条件 |
| --- | --- | --- |
| 第 1 周：定义 | 对象、流程、状态、指标、排除项和责任矩阵 | 业务、数据、安全或质量负责人对同一口径签字 |
| 第 2 周：打通 | 源字段、主键、时间、版本、控制对象和失败样本 | 正常与异常样本都能回到原始记录 |
| 第 3 周：验证 | 总量对账、分层对账、抽样回查、权限测试、回滚演练 | 阻断问题清零，严重问题有责任人与期限 |
| 第 4 周：发布 | 灰度、SLO、监控、行动清单、停止条件和复盘模板 | 使用者在真实场景中完成一次闭环行动 |

如果必须用 90 秒说明“智能制造转型”是否做对，可以按这个顺序自测：

1. 一行数据代表什么，主键是什么，哪些对象绝不能混在同一粒度？
2. 业务发生、数据可见、计算完成和行动确认分别在哪个时间点？
3. 本主题最重要的两个主指标、三个护栏和最小样本量是什么？
4. 一个异常出现时，先从原始记录、链路版本还是业务动作开始查？
5. 哪类错误必须阻断发布或停止使用，谁有权批准例外？
6. 上线后由谁在多长时间内观察，什么条件下回滚或结束？

> [!check] 完成标准
> 当另一位数据同事不看聊天记录，只根据口径卡、回归样本和代码就能复跑同一结果；当业务负责人能指出一个异常对应的原始对象、处置动作和复核证据；当系统能够阻止未授权或状态非法的数据进入下游，这篇“智能制造转型”才算真正落到工作里。
