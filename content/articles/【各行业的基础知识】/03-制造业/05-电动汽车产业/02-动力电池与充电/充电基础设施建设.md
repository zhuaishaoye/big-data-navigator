# 充电基础设施建设

> [!abstract] 场景速览
> “充电基础设施建设”在会议里常常只有一句话，落到数据团队却会展开成口径、主键、时间、状态、权限和交付责任。下面用一个从问题到上线的顺序展开，并穿插三个脱敏的复合案例，帮助你把标题里的知识迁移到真实项目。

## 1. “充电基础设施建设”在制造业业务链中的位置

制造业的核心流程可以概括为：需求计划 → 排产 → 备料 → 工单执行 → 质量检验 → 入库 → 发运 → 售后追溯。参与角色包括计划、采购、工艺、生产、设备、质量、仓储、交付与财务。“充电基础设施建设”通常不是一个孤立字段，而是连接业务动作、数据记录和管理决策的一层能力。

从数据团队视角，至少要回答四个问题：

1. **谁使用**：计划、采购、工艺、生产分别要用它做判断、执行还是审计。
2. **对象是什么**：一行数据代表工厂、一次事件、一个批次还是一天快照。
3. **流程在哪里变化**：通过排产、备料、工单执行、质量检验之间的状态和时间差定位问题。
4. **结果如何被采用**：谁在什么时间前采取行动，使用哪个指标观察改善或副作用。

一个合格的专题目标可以写成：

> 在【时间窗】和【授权数据范围】内，围绕“充电基础设施建设”，按【工厂、产线、产品】比较【计划达成率】与【单位制造成本】，定位一个可干预流程节点，并记录行动后的变化与边界。

## 2. 一张图看清角色、流程和数据

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 工厂 | `plant_id` | 需求计划 |
| 过程对象 | 产线 | `line_id` | 排产 |
| 过程对象 | 设备 | `equipment_id` | 备料 |
| 结果对象 | 工单 | `work_order_id` | 工单执行 |
| 结果对象 | 批次 | `batch_id` | 质量检验 |
| 专题分析 | 充电基础设施建设 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

建模时不要先把所有系统字段堆进一张大表。更稳妥的做法是分别保留三类事实：

- **事件事实**：谁在什么时间做了动作，例如挂号、下单、开工、报警或学习。
- **状态快照**：对象在某一天的状态，例如会员等级、租约、账户余额或设备资产关系。
- **结果事实**：流程完成后的产出，例如结算金额、良品数量、签收结果或考试分数。

三者的粒度不同。把事件、快照和结果强行放在同一行，会让金额、数量和转化率在汇总时重复。若“充电基础设施建设”涉及状态变化，优先建立状态机；若涉及金额，先做借贷或收付平衡；若涉及对象归属，保留维度有效期。

## 3. 指标与口径：不要把相关数字直接当答案

| 专题观测面 | 需要回答的问题 | 关键证据 | 判定与动作 |
| --- | --- | --- | --- |
| 数据流（本标题优先） | 批、流、CDC、共享与服务之间如何衔接 | 源系统、粒度、频率、容量和延迟 | 每条链路要有唯一责任边界 |
| 非功能 | 可用性、扩展性、一致性、安全和成本如何取舍 | SLO、压测、故障演练、账单和权限矩阵 | 关键指标必须有基线 |
| 演进 | 旧系统如何迁移，数据和接口怎样兼容回滚 | 版本、双写/双读、灰度和回滚方案 | 迁移期间保留可对账双链路 |
| 业务能力 | 架构到底支撑哪些决策、流程和数据产品 | 能力地图、用例、消费方和现状痛点 | 没有业务约束不做平台堆叠 |

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 良品率 | `SUM(good_qty) / SUM(produced_qty)`（视图字段 `yield_rate`） | 工厂、产线、产品 | 不混用测试、撤销和跨期状态；与“充电基础设施建设”相关时还要补充主题筛选 |
| 设备稼动率 | `SUM(run_minutes) / SUM(planned_minutes)`（视图字段 `availability`） | 产线、产品、班组 | 不混用测试、撤销和跨期状态；与“充电基础设施建设”相关时还要补充主题筛选 |
| 计划达成率 | `SUM(completed_plan_qty) / SUM(planned_qty)`（视图字段 `plan_attainment`） | 产品、班组、设备类型 | 不混用测试、撤销和跨期状态；与“充电基础设施建设”相关时还要补充主题筛选 |
| 单位制造成本 | `SUM(conversion_cost) / SUM(good_qty)`（视图字段 `unit_cost`） | 班组、设备类型 | 不混用测试、撤销和跨期状态；与“充电基础设施建设”相关时还要补充主题筛选 |

指标字典至少应包含：中文名、英文编码、业务定义、计算公式、事实粒度、时间字段、对象范围、排除条件、负责人和验收样例。对于“充电基础设施建设”，还应注明它使用的是业务发生时间还是入仓时间，是否包含撤销、退费、测试、跨期和补录记录。

一个常见误区是看到计划达成率变化就立即解释业务原因。更可靠的顺序是：

1. 检查数据覆盖和延迟是否变化。
2. 检查对象范围、状态映射和维度归属是否变化。
3. 按时间、结构和分组拆解贡献。
4. 回到明细寻找能解释变化的事件。
5. 如果已经采取行动，再评估行动带来的增量，而不是事后挑一个相关指标。

## 4. 工作案例：从现象到数据处理

### 案例 1：华北某新能源装备工厂的“充电基础设施建设”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“充电基础设施建设”映射到“数据架构、平台与云原生基础设施”中的数据流，而不是泛泛讨论概念。
- **触发事件**：设备预测性维护项目告警很多，但真正停机次数没有明显下降，现场对模型失去信任。
- **业务与数据范围**：振动、温度、电流、报警、维修工单、备件更换和停机记录。数据侧重点采集源系统、粒度、频率、容量和延迟，并与ERP、MES、PLM中的时间、状态和责任人信息对齐。
- **需要回答的问题**：批、流、CDC、共享与服务之间如何衔接。
- **关键障碍**：传感器时间未统一，报警只记录触发不记录恢复，维修工单与设备状态缺少关联。同时要防止设备与工单编码变化导致断链把表面指标带偏。
- **处理过程**：先补事件状态机和标签质量，再建立提前预警窗口，按设备型号评估召回率和误报成本。实施时把“架构决策同时评估 SLA、一致性、安全、容量、成本和可运维性”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例项目把模型目标从单一准确率改为提前时长、有效召回和维修资源可承受度。验收至少同时看主指标、源系统、粒度、频率、容量和延迟和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“从业务能力、数据流、访问模式、一致性、SLA、安全和成本出发拆分组件，并用可验证的非功能指标约束演进。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

这个案例最关键的动作不是“跑一条 SQL”，而是把“充电基础设施建设”对应的业务对象和上下游系统放在同一张链路图上。链路图至少要标出源系统、事件时间、关联主键、状态变化、数据负责人和消费方。

## 5. SQL 示例：在统一口径下做分层诊断

下面的查询用于展示分析结构，表名和字段需映射到实际环境。重点是去重、范围筛选、基线比较和贡献率，而不是代码本身。

### 标题专属诊断 SQL

```sql
-- 充电基础设施建设：同期基线诊断（产品 × 设备类型）
WITH scoped AS (
  SELECT
    plant_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_manufacturing_event
  WHERE event_time >= DATE '2026-02-01'
    AND event_time <  DATE '2026-05-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '准时交付率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

执行后要回答四类验证题：

- 结果总量能否与源系统或既有报表在相同口径下解释差异？
- 排名前几位的分组是否由少数超长、重复或补录记录造成？
- 缺失日期表现为“未发生”还是“未采集”，是否改变分母？
- 维度使用的是当时归属还是当前归属，跨期比较是否一致？

## 6. 第二个案例：跨系统、跨部门时怎样不失控

### 案例 2：华南某金融机构的“充电基础设施建设”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“充电基础设施建设”映射到“数据架构、平台与云原生基础设施”中的非功能，而不是泛泛讨论概念。
- **触发事件**：核心系统迁移到云上后，跨域链路时延和权限边界比预期更复杂。
- **业务与数据范围**：系统调用、网络、数据分区、密钥、身份、审计、SLO 和迁移批次。数据侧重点采集SLO、压测、故障演练、账单和权限矩阵，并与ERP、MES、PLM中的时间、状态和责任人信息对齐。
- **需要回答的问题**：可用性、扩展性、一致性、安全和成本如何取舍。
- **关键障碍**：只迁移计算和存储，没有同步治理身份、网络域、数据分级与故障隔离。同时要防止停机时长重复计算把表面指标带偏。
- **处理过程**：拆分受控数据域，建立统一身份与最小权限，按业务链路做双跑对照和故障演练。实施时把“跨域数据流有契约、主键、版本、权限和故障隔离”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例迁移以功能、数据、权限、性能和回滚五类证据分批放行。验收至少同时看主指标、SLO、压测、故障演练、账单和权限矩阵和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“从业务能力、数据流、访问模式、一致性、SLA、安全和成本出发拆分组件，并用可验证的非功能指标约束演进。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

跨部门项目最容易在三个地方返工：业务术语没有冻结、主数据映射没有版本、验收时才发现权限不足。建议在开发前让业务负责人签字确认指标定义，让数据负责人确认粒度与主键，让安全负责人确认字段范围，让运维负责人确认发布与回滚窗口。

## 7. Python 示例：把数据质量变成发布门禁

### 可执行质量门禁

```python
# 充电基础设施建设：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "充电基础设施建设"
TOPIC_KEY = "subject"
RULE_ID = "rule_manufacturing_1dcvqbd"
GUIDE_CHECKS = [
    "每个组件都对应明确业务能力、数据流和消费方，而非只为技术栈完整",
    "架构决策同时评估 SLA、一致性、安全、容量、成本和可运维性",
    "跨域数据流有契约、主键、版本、权限和故障隔离",
    "迁移方案包含双跑对账、灰度、数据校验和可执行回滚"
]
RULES = {
    "required_columns": ["event_id", "plant_id", "event_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "plant_id",
    "time_field": "event_time",
    "max_duplicate_rate": 0.0006,
    "max_null_rate": 0.004,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：每个组件都对应明确业务能力、数据流和消费方，而非只为技术栈完整；架构决策同时评估 SLA、一致性、安全、容量、成本和可运维性；跨域数据流有契约、主键、版本、权限和故障隔离；迁移方案包含双跑对账、灰度、数据校验和可执行回滚
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

这段代码适合放在离线任务完成之后、指标发布之前。真实环境还应从调度平台读取分区参数、把结果写入质量平台，并在关键规则失败时阻断下游。告警不是终点，工单中要记录影响资产、发现时间、临时处理、根因、修复时间和防复发动作。

## 8. 异常排查：从指标异常回到业务事件

围绕“充电基础设施建设”排查时，可以按以下顺序进行：

1. **影响面**：哪些指标、报表、接口或业务团队受影响，是否需要暂停对外发布。
2. **时间线**：源系统变更、任务发布、数据回刷、组织调整和业务活动分别发生在什么时候。
3. **数据链路**：上游是否延迟，分区是否缺失，主键是否重复，状态是否映射错误。
4. **业务证据**：抽取异常记录，与原始单据、操作日志、客服记录或现场系统核对。
5. **修复与复核**：明确补数范围、重跑粒度、回滚版本和验收样例。
6. **防复发**：把一次性排查升级为规则、监控、责任人和变更评审。

特别要注意：设备与工单编码变化导致断链；停机时长重复计算；质检抽样不能代表整批；计划版本与执行版本混用。这些问题如果不被单独标记，很容易被误写成业务趋势。

### 扩展代码一：从充电基础设施建设回到可核对明细

```sql
-- 充电基础设施建设：状态链与时间间隔核查
WITH ordered_events AS (
  SELECT
    plant_id AS entity_key,
    event_id,
    stage_code,
    event_time AS event_time,
    LAG(stage_code) OVER (
      PARTITION BY plant_id
      ORDER BY event_time, event_id
    ) AS previous_stage,
    LAG(event_time) OVER (
      PARTITION BY plant_id
      ORDER BY event_time, event_id
    ) AS previous_time
  FROM fact_manufacturing_event
  WHERE event_time >= :start_date
    AND event_time <  :end_date
    AND subject_key = 'subject'
)
SELECT
  entity_key,
  previous_stage,
  stage_code,
  event_time,
  event_time - previous_time AS elapsed,
  CASE
    WHEN event_time < previous_time THEN 'time_reversed'
    WHEN previous_stage = stage_code THEN 'duplicate_stage'
    WHEN previous_stage IS NULL THEN 'missing_prefix'
    ELSE 'candidate_delay'
  END AS exception_type
FROM ordered_events
WHERE event_time < previous_time
   OR previous_stage = stage_code
   OR event_time - previous_time > INTERVAL '1 hour'
ORDER BY exception_type, elapsed DESC;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把充电基础设施建设的验收证据写成门禁

```python
import pandas as pd

KEY = ["entity_key", "event_id"]
AMOUNT_COLUMNS = ["metric_value", "adjustment_value"]


def reconcile(source: pd.DataFrame, result: pd.DataFrame) -> pd.DataFrame:
    def aggregate(frame: pd.DataFrame, side: str) -> pd.DataFrame:
        grouped = (
            frame.groupby("entity_key", dropna=False)
            .agg(
                event_cnt=("event_id", "nunique"),
                metric_sum=("metric_value", "sum"),
                adjustment_sum=("adjustment_value", "sum"),
            )
            .reset_index()
        )
        return grouped.rename(columns={
            "event_cnt": f"{side}_event_cnt",
            "metric_sum": f"{side}_metric_sum",
            "adjustment_sum": f"{side}_adjustment_sum",
        })

    compared = aggregate(source, "source").merge(
        aggregate(result, "result"),
        on="entity_key",
        how="outer",
    )
    compared["metric_diff"] = (
        compared["result_metric_sum"].fillna(0)
        - compared["source_metric_sum"].fillna(0)
    )
    compared["event_diff"] = (
        compared["result_event_cnt"].fillna(0)
        - compared["source_event_cnt"].fillna(0)
    )
    compared["exception"] = compared.apply(
        lambda row: "missing_result" if pd.isna(row["result_metric_sum"])
        else "unexpected_result" if pd.isna(row["source_metric_sum"])
        else "count_diff" if row["event_diff"] != 0
        else "amount_diff",
        axis=1,
    )
    return compared.loc[
        (compared["metric_diff"].abs() > 0) | (compared["event_diff"] != 0)
    ].sort_values("metric_diff", key=lambda values: values.abs(), ascending=False)
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
