# 协同制造网络

> [!abstract] 多工厂与供应链协同实战手册
> 协同制造网络让多个工厂、供应商、物流伙伴和客户围绕订单、产能、物料、质量和交付进行跨组织协同。数据重点是节点身份、接口契约、订单状态、产能承诺、库存所有权、异常事件和跨组织责任，而不是把所有企业的内部数据无限集中。

## 1. 协同制造网络：定义、适用边界与决策出口

协同制造网络让多个工厂、供应商、物流伙伴和客户围绕订单、产能、物料、质量和交付进行跨组织协同。数据重点是节点身份、接口契约、订单状态、产能承诺、库存所有权、异常事件和跨组织责任，而不是把所有企业的内部数据无限集中。

**本篇的适用边界。** 本篇讨论多工厂和多供应商之间的订单、产能、物料与交付协同；不把 EDI 或 API 连通本身视为协同能力，也不默认所有合作方数据都可共享。

**最常见的错误替代。** 不能用单一工厂口径代表网络，不能把供应商确认交期当作实际交付，也不能忽略跨组织数据的主权、用途和最小必要。

**最终决策。** 供应链与制造网络负责人要判断：订单应分配给哪个节点，交期风险如何预警，出现缺料或质量问题由谁处理，哪些伙伴需要升级协同，以及网络是否需要调整。 因此，这篇内容不从“应该建哪张表”开始，而从业务动作、责任人和失败后果开始。只有先确定谁在什么时点做出什么决定，字段、SQL、看板和模型才有明确用途。

围绕“协同制造网络”，工作中至少要区分四类问题：

1. **身份问题**：对象是谁，主键能否跨系统稳定关联，合并、拆分、撤销后历史是否还看得见。
2. **时间问题**：业务发生、状态生效、数据入仓、计算完成和人员行动分别发生在哪一刻。
3. **状态问题**：当前状态是一段事件、一张快照还是最终结果，空值代表未发生、未采集还是已删除。
4. **责任问题**：谁确认口径，谁处理异常，谁有权放行或停止，谁在观察期后复盘。

## 2. 协同制造网络的完整业务流程

| 环节 | 要做的事 | 最小证据 | 失败后先查什么 |
| --- | --- | --- | --- |
| 网络节点与能力建模 | 登记工厂、供应商、仓、承运商和能力边界 | 节点主数据、认证、产能和地理信息 | 网络响应 200 即显示订单已确认 |
| 需求与订单协同 | 汇总客户需求、预测和订单承诺 | 需求版本、订单行、承诺与变更 | 多个工厂使用各自快照分配同一物料 |
| 产能与物料匹配 | 将订单与可用产能、库存和在途物料匹配 | 产能日历、库存、采购和替代规则 | 历史承诺被最新日期覆盖 |
| 跨组织计划发布 | 下发生产、采购和物流计划并接收确认 | 计划版本、确认、偏差和接口回执 | 合作方索要超出用途的内部数据 |
| 执行状态同步 | 跟踪生产、质检、发货、运输和签收 | 工单、批次、ASN、轨迹和回执 | 网络响应 200 即显示订单已确认 |
| 异常协同 | 缺料、延期、质量、运力和地址异常跨节点处理 | 事件、责任人、升级和替代方案 | 多个工厂使用各自快照分配同一物料 |
| 网络绩效复盘 | 评估交付、成本、库存、质量和韧性 | 节点绩效、网络基线和服务约束 | 历史承诺被最新日期覆盖 |

把 网络节点与能力建模、需求与订单协同、产能与物料匹配、跨组织计划发布、执行状态同步、异常协同、网络绩效复盘 串起来后可以看出，协同制造网络不是一个孤立字段，而是一条会跨系统、跨岗位、跨时间的证据链。流程图上每一段都应标出输入、输出、状态、时间戳、责任人和异常出口。只要其中一段只能靠口头解释，后续的统计、追责和自动化就会失去基础。

一个合格的需求说明应该写成：

> 在【授权数据范围】和【观察窗口】内，围绕“协同制造网络”的【网络节点】，按【network_node_id、product_family、destination_region、commitment_week】比较【订单承诺达成率】及其【网络准交率】，定位一个可干预节点；行动后同时观察主指标、样本量和护栏，任何高风险异常先阻断再调查。

## 3. 协同制造网络的数据对象与系统契约

| 数据对象 | 建议主键 | 一行代表什么 | 不允许混淆 |
| --- | --- | --- | --- |
| 网络节点 | `network_node_id` | 参与协同的工厂、供应商、仓或承运商 | 对象身份与业务事件 |
| 协同订单 | `collaboration_order_id` | 跨组织和节点的订单协同过程 | 事件、状态快照和结果粒度 |
| 产能承诺 | `capacity_commitment_id` | 节点在时间窗口内承诺提供的产能或物料 | 事件、状态快照和结果粒度 |
| 物料批次 | `material_lot_id` | 在供应链中流转并需追溯的物料批次 | 事件、状态快照和结果粒度 |
| 运输通知 | `shipment_notice_id` | 发货、包装、承运和预计到达信息 | 事件、状态快照和结果粒度 |
| 协同异常 | `network_exception_id` | 跨节点无法按计划完成的缺口与处置 | 事件、状态快照和结果粒度 |

对象表不是把所有字段塞进一张宽表。事件、状态快照和结果表应该分别保留粒度，再通过稳定主键与版本建立关联。尤其要避免三个常见混算：把一次业务事件算成多个对象、把每日快照相加当事件总量、把最新状态覆盖历史状态。

本主题的数据契约至少应包含：

- `capacity_commitment_id` 的唯一性规则、生成方式和跨系统映射。
- `committed_at` 的业务含义、时区、迟到和补录规则。
- `commitment_status` 的完整状态集合，以及删除、撤销、冻结和失效的表示方法。
- 控制对象 `supply_shipment_notice.shipment_notice_id` 与主对象的关系。
- 每次口径、规则、模型或源版本变化的影响范围和下游通知对象。
- 敏感字段、允许用途、访问角色、导出限制和审计保留时间。

## 4. 协同制造网络的指标、样本与验收口径

| 指标 | 公式或定义 | 口径提醒 |
| --- | --- | --- |
| 订单承诺达成率 | 按承诺数量和时间交付的订单行数 / 已承诺订单行数 | 承诺变更需保留历史 |
| 网络准交率 | 最终按期完整交付的订单数 / 应交付订单数 | 不能只看单个节点是否准时 |
| 产能承诺偏差 | 实际可用产能 / 已承诺产能 | 按节点、周期和产品族统计 |
| 跨节点异常恢复时长 | 异常关闭时间 - 发现时间 | 区分发现、响应、解决和验证 |
| 批次追溯完整率 | 可追溯到来源和去向的物料批次节点数 / 应追溯节点数 | 断链批次必须隔离 |

指标字典至少写到“任何人都能按同一份数据复跑”的程度：中文名、业务定义、公式、分子、分母、事实粒度、时间字段、对象范围、排除项、版本、负责人和验收样例，一个都不能少。比例指标必须同时展示分子、分母和样本量；金额或数量必须做守恒；状态指标必须能回到事件时间线。

对于“协同制造网络”，建议把观察分成三层：

| 层次 | 看什么 | 不能替代什么 |
| --- | --- | --- |
| 业务结果 | 订单承诺达成率、网络准交率 | 不能替代过程证据和个案回查 |
| 过程护栏 | 产能承诺偏差、跨节点异常恢复时长、批次追溯完整率 | 不能因为护栏暂时正常就跳过异常调查 |
| 数据证据 | 主键、时间、状态、版本、来源目标对账 | 不能只看任务成功或报表能打开 |

## 5. 协同制造网络：七个真实工作场景

以下七组场景均为公开方法结合常见工作流程构造的“脱敏复合示例”，不对应任何单一企业、患者、客户或雇员事实。场景的目的，是展示如何从现象走到证据、行动和验收，而不是虚构经营成果。

### 1. 接口连通但双方订单状态不同

**现场。** 协同平台显示已确认，供应商系统仍为待评审。

**怎么查。** 检查接口请求、应用回执、人工审批和状态映射，发现平台把网络成功当作业务确认。

**怎么处理。** 状态以双方业务确认为准；接口保存请求与回执；长时间未知进入人工协调。

**验收结论。** 接口成功不等于伙伴承诺。跨组织状态必须由业务事件确认。

### 2. 多工厂争抢同一关键物料

**现场。** 两个工厂分别显示物料已分配，集团总量不足。

**怎么查。** 按物料批次、库存所有权、预留和承诺时间重建分配链路，发现各自使用本地快照。

**怎么处理。** 关键物料由网络级可用量统一分配；本地预留有优先级和到期时间；冲突进入升级。

**验收结论。** 局部可用不等于网络可用。共享资源需要共享约束。

### 3. 供应商承诺交期很好但到货波动大

**现场。** 供应商确认率很高，工厂仍频繁缺料。

**怎么查。** 比较承诺时间、ASN、实际发货、运输和在途偏差，发现供应商长期临近交期才调整。

**怎么处理。** 把承诺稳定性与到货可靠性一起考核；提前预警窗口；关键物料要求分阶段进度回执。

**验收结论。** 承诺数量不代表承诺质量。时间偏差和变更历史同样重要。

### 4. 质量异常无法定位受影响客户

**现场。** 某供应商批次出现问题，网络内多地使用。

**怎么查。** 沿采购批次、生产工单、成品批次、仓库和客户订单追踪，发现部分工厂未回传消耗关系。

**怎么处理。** 批次消耗和去向必须进入协同契约；断链批次暂停使用；召回或替换范围由多节点共同确认。

**验收结论。** 追溯链必须覆盖跨组织边界，不能只在集团内部完整。

### 5. 物流轨迹与签收状态冲突

**现场。** 承运商显示已签收，收货工厂没有入库。

**怎么查。** 关联运输节点、签收人、卸货预约、验收和入库事件，发现签收只是到达门岗。

**怎么处理。** 区分到达、签收、验收和入库；异常订单不自动关闭；明确各方确认责任。

**验收结论。** 节点状态名称相同不代表业务含义相同，接口契约要附定义。

### 6. 协同网络数据过度共享

**现场。** 平台要求供应商上传全部成本和客户订单。

**怎么查。** 核对协同目标、最小字段和合同授权，发现采购计划只需数量、时间和质量要求。

**怎么处理。** 按用途提供最小数据集；敏感字段脱敏或聚合；访问和导出审计；伙伴退出后按约定清理。

**验收结论。** 网络协同不能以牺牲伙伴数据主权为代价。

### 7. 网络优化降低单点成本却增加风险

**现场。** 集中到低成本节点后运输成本下降，但任一节点故障影响大量订单。

**怎么查。** 按节点、替代能力、库存、交期和故障场景模拟影响范围。

**怎么处理。** 设置关键能力备份和产能上限；保留替代路径；网络绩效同时评估效率和韧性。

**验收结论。** 最低成本网络不一定是最可靠网络。冗余需要基于业务影响设计。

七个场景可以归成一条共同判断顺序：先确认对象和时间，再确认状态和版本；然后做总量、结构和明细三层对账；最后才讨论策略、模型或工具。若一条结论不能指出对应的原始记录、责任人和行动出口，就只能算观察，不能作为生产结论。

## 6. 协同制造网络的第一段 SQL：重建业务链路

下面的 SQL 用于说明对象、时间、状态、版本和分层口径如何进入同一条可复查路径。表名和部分字段是通用示例，落地时应映射到企业数据字典；SQL 方言也需按实际引擎调整。

```sql
-- 协同制造网络：按业务对象重建链路，避免事件、快照和结果混算
WITH ranked_capacity_commitment_id AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY capacity_commitment_id
      ORDER BY updated_at DESC
    ) AS version_no
  FROM supply_network_order_commitment
  WHERE committed_at >= TIMESTAMP '{start_time}'
    AND committed_at <  TIMESTAMP '{end_time}'
    AND commitment_status NOT IN ('deleted', 'test')
),
valid_rows AS (
  SELECT
    capacity_commitment_id,
    network_node_id,
    product_family,
    destination_region,
    commitment_week,
    committed_at,
    commitment_status,
    ingested_at
  FROM ranked_capacity_commitment_id
  WHERE version_no = 1
)
SELECT
  network_node_id, product_family, destination_region, commitment_week,
  COUNT(DISTINCT capacity_commitment_id) AS object_cnt,
  SUM(CASE WHEN delivered_on_time_qty >= committed_qty THEN 1 ELSE 0 END) AS numerator_value,
  COUNT(DISTINCT collaboration_order_id) AS denominator_value,
  CAST(SUM(CASE WHEN delivered_on_time_qty >= committed_qty THEN 1 ELSE 0 END) AS DOUBLE PRECISION)
    / NULLIF(COUNT(DISTINCT collaboration_order_id), 0) AS metric_value,
  MIN(committed_at) AS first_event_at,
  MAX(committed_at) AS last_event_at
FROM valid_rows
GROUP BY network_node_id, product_family, destination_region, commitment_week
ORDER BY metric_value DESC, object_cnt DESC;
```

执行后至少回答六个问题：

- 同一对象是否因为多源回传产生多版本，版本保留是否符合业务要求？
- 业务时间与入仓时间是否分开，补录和迟到数据是否进入正确分区？
- 分子分母是否来自同一对象范围和同一统计窗口？
- 维度使用的是事件当时值还是当前值，跨期比较是否一致？
- 删除、撤销、冻结和测试数据是否按规则处理？
- 分组结果能否在明细中抽样复现？

## 7. 协同制造网络的第二段 SQL：源、控制和结果三方对账

```sql
-- 协同制造网络：源对象、控制对象和结果对象三方对账
WITH population AS (
  SELECT
    capacity_commitment_id,
    committed_at,
    commitment_status
  FROM supply_network_order_commitment
  WHERE committed_at >= TIMESTAMP '{start_time}'
    AND committed_at <  TIMESTAMP '{end_time}'
),
control AS (
  SELECT
    capacity_commitment_id,
    SUM(received_qty) AS control_value,
    COUNT(DISTINCT shipment_notice_id) AS control_cnt,
    MAX(updated_at) AS control_updated_at
  FROM supply_shipment_notice
  WHERE updated_at >= TIMESTAMP '{start_time}'
  GROUP BY capacity_commitment_id
),
result AS (
  SELECT
    capacity_commitment_id,
    COUNT(*) AS result_cnt,
    MAX(calculated_at) AS calculated_at
  FROM mart_capacity_commitment_id
  WHERE business_date BETWEEN DATE '{start_date}' AND DATE '{end_date}'
  GROUP BY capacity_commitment_id
)
SELECT
  COALESCE(p.capacity_commitment_id, c.capacity_commitment_id, r.capacity_commitment_id) AS object_key,
  CASE
    WHEN p.capacity_commitment_id IS NULL THEN 'source_missing'
    WHEN c.capacity_commitment_id IS NULL THEN 'control_missing'
    WHEN r.capacity_commitment_id IS NULL THEN 'result_missing'
    WHEN ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0 THEN 'count_or_value_gap'
    ELSE 'matched'
  END AS reconciliation_status,
  p.commitment_status,
  c.control_value,
  c.control_cnt,
  r.result_cnt,
  c.control_updated_at,
  r.calculated_at
FROM population p
FULL OUTER JOIN control c ON p.capacity_commitment_id = c.capacity_commitment_id
FULL OUTER JOIN result r ON COALESCE(p.capacity_commitment_id, c.capacity_commitment_id) = r.capacity_commitment_id
WHERE p.capacity_commitment_id IS NULL
   OR c.capacity_commitment_id IS NULL
   OR r.capacity_commitment_id IS NULL
   OR ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0;
```

这段查询故意不使用“总数相差小于某个随意百分比就算通过”。它先找出缺失对象和状态差异，再检查控制值与结果值。对于协同制造网络，数量、金额、时长或状态任意一项无法解释，都不能用“业务波动”代替排查。

对账结果建议分成四类处理：

1. **阻断**：对象缺失、关键时间为空、状态非法、金额或数量不守恒、权限越界。
2. **严重**：比例或总量显著偏离基线，且无法由已确认的对象结构变化解释。
3. **观察**：小范围波动但来源、样本和趋势可控，进入责任人和观察窗口。
4. **探索**：只有弱信号或假设，不进入正式结论，更不直接触发业务处罚。

## 8. 协同制造网络的 Python 发布门禁与指标护栏

第一段代码把发布条件写成可执行对象，避免“检查过了”只存在聊天记录里：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class CapacityCommitmentIdBatch:
    batch_id: str
    source_rows: int
    valid_rows: int
    duplicate_keys: int
    missing_required_fields: int
    reconciliation_gap: float

def release_capacity_commitment_id(batch: CapacityCommitmentIdBatch) -> dict:
    checks = {
        "source_not_empty": batch.source_rows > 0,
        "valid_rows_in_range": 0 <= batch.valid_rows <= batch.source_rows,
        "duplicate_rate_ok": batch.duplicate_keys / max(batch.source_rows, 1) <= 0.001,
        "required_fields_ok": batch.missing_required_fields == 0,
        "reconciliation_ok": abs(batch.reconciliation_gap) <= 0.01,
    }
    return {
        "topic": "协同制造网络",
        "batch_id": batch.batch_id,
        "checks": checks,
        "release_allowed": all(checks.values()),
        "blocking_checks": [name for name, passed in checks.items() if not passed],
    }
```

第二段代码演示如何为比例类结果附带样本证据和小样本下界。它不是替代统计学家的模型，而是防止把少量偶然样本直接包装成稳定结论：

```python
from dataclasses import dataclass
from math import sqrt

@dataclass(frozen=True)
class CapacityCommitmentIdObservation:
    object_id: str
    numerator: float
    denominator: float
    sample_size: int
    scope_version: str

def calculate_capacity_commitment_id(rows: list[CapacityCommitmentIdObservation]) -> list[dict]:
    output = []
    for row in rows:
        value = row.numerator / row.denominator if row.denominator > 0 else None
        # 小样本用 Wilson 下界做护栏，不把偶然的高比例直接当稳定结果。
        z = 1.96
        p = value or 0
        n = max(row.sample_size, 1)
        center = p + z * z / (2 * n)
        margin = z * sqrt((p * (1 - p) + z * z / (4 * n)) / n)
        lower = max(0, (center - margin) / (1 + z * z / n))
        output.append({
            "object_id": row.object_id,
            "metric": "订单承诺达成率",
            "value": value,
            "lower_bound": lower if value is not None else None,
            "sample_size": row.sample_size,
            "scope_version": row.scope_version,
            "caution": "承诺变更需保留历史",
        })
    return output
```

真正上线时还要补充参数配置、日志、血缘、告警级别、重跑幂等、异常样本保存和审批记录。代码通过不代表业务通过；自动检查只能证明已经定义的规则没有被违反，无法证明规则本身一定正确。

## 9. 协同制造网络的失败反例与上线验收

| 风险信号 | 错误做法 | 必须补齐的证据 | 发布或行动规则 |
| --- | --- | --- | --- |
| 接口成功冒充业务确认 | 网络响应 200 即显示订单已确认 | 双方业务状态和回执 | 未知状态进入人工协同 |
| 本地库存重复承诺 | 多个工厂使用各自快照分配同一物料 | 网络级预留和所有权 | 共享资源统一校验 |
| 交期只有一个快照 | 历史承诺被最新日期覆盖 | 承诺版本和变更原因 | 保留每次变更及影响 |
| 协同字段无限扩张 | 合作方索要超出用途的内部数据 | 最小必要和合同范围 | 超范围接口拒绝 |

上线验收不应只有一句“报表正常”。建议按下面四层验收：

| 验收对象 | 结构要求 | 测试样本 | 结果证据 |
| --- | --- | --- | --- |
| 网络节点 | `network_node_id` 能唯一定位参与协同的工厂、供应商、仓或承运商 | 正常、重复、缺失、撤销与跨期样本 | 订单承诺达成率可回到原始对象 |
| 协同订单 | `collaboration_order_id` 能唯一定位跨组织和节点的订单协同过程 | 正常、重复、缺失、撤销与跨期样本 | 网络准交率可回到原始对象 |
| 产能承诺 | `capacity_commitment_id` 能唯一定位节点在时间窗口内承诺提供的产能或物料 | 正常、重复、缺失、撤销与跨期样本 | 产能承诺偏差可回到原始对象 |
| 物料批次 | `material_lot_id` 能唯一定位在供应链中流转并需追溯的物料批次 | 正常、重复、缺失、撤销与跨期样本 | 跨节点异常恢复时长可回到原始对象 |
| 运输通知 | `shipment_notice_id` 能唯一定位发货、包装、承运和预计到达信息 | 正常、重复、缺失、撤销与跨期样本 | 批次追溯完整率可回到原始对象 |
| 协同异常 | `network_exception_id` 能唯一定位跨节点无法按计划完成的缺口与处置 | 正常、重复、缺失、撤销与跨期样本 | 订单承诺达成率可回到原始对象 |

还应为每一次发布保留一组固定回归样本：正常对象、边界状态、重复记录、缺失字段、撤销或退款、跨期、权限拒绝和失败恢复。回归样本不是演示数据，而是以后每次改规则都能重复执行的质量资产。

## 10. 协同制造网络的 30 天落地与复盘

| 阶段 | 主要交付 | 通过条件 |
| --- | --- | --- |
| 第 1 周：定义 | 对象、流程、状态、指标、排除项和责任矩阵 | 业务、数据、安全或质量负责人对同一口径签字 |
| 第 2 周：打通 | 源字段、主键、时间、版本、控制对象和失败样本 | 正常与异常样本都能回到原始记录 |
| 第 3 周：验证 | 总量对账、分层对账、抽样回查、权限测试、回滚演练 | 阻断问题清零，严重问题有责任人与期限 |
| 第 4 周：发布 | 灰度、SLO、监控、行动清单、停止条件和复盘模板 | 使用者在真实场景中完成一次闭环行动 |

如果必须用 90 秒说明“协同制造网络”是否做对，可以按这个顺序自测：

1. 一行数据代表什么，主键是什么，哪些对象绝不能混在同一粒度？
2. 业务发生、数据可见、计算完成和行动确认分别在哪个时间点？
3. 本主题最重要的两个主指标、三个护栏和最小样本量是什么？
4. 一个异常出现时，先从原始记录、链路版本还是业务动作开始查？
5. 哪类错误必须阻断发布或停止使用，谁有权批准例外？
6. 上线后由谁在多长时间内观察，什么条件下回滚或结束？

> [!check] 完成标准
> 当另一位数据同事不看聊天记录，只根据口径卡、回归样本和代码就能复跑同一结果；当业务负责人能指出一个异常对应的原始对象、处置动作和复核证据；当系统能够阻止未授权或状态非法的数据进入下游，这篇“协同制造网络”才算真正落到工作里。
