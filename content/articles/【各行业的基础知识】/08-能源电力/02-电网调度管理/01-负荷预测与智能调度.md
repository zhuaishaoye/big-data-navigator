# 负荷预测与智能调度

> [!abstract] 工程视角
> “负荷预测与智能调度”在会议里常常只有一句话，落到数据团队却会展开成口径、主键、时间、状态、权限和交付责任。下面用一个从问题到上线的顺序展开，并穿插三个脱敏的复合案例，帮助你把标题里的知识迁移到真实项目。

## 1. 需求、SLA 与边界

“负荷预测与智能调度”首先是工程问题，其次才是工具选择。立项时明确：

- 谁消费数据或服务，用来做什么决策或操作。
- 数据从产生到可用允许延迟多久，失败时能否接受部分结果。
- 更新频率、保留周期、回放范围、并发和数据量级。
- 上下游依赖、权限、敏感字段、审计和成本上限。
- 正确性、完整性和一致性中，哪些必须强保证，哪些可最终一致。

能源电力中常见的交付指标包括负荷率、用电量、线损率。不要只写“稳定”“高效”，应定义可监测的 SLI、SLO 和错误预算。

## 2. 数据链路与模型

| 层次 | 本文建议 | 关键问题 | 验收证据 |
| --- | --- | --- | --- |
| 数据源 | SCADA、EMS、DMS | 权威源、更新频率、主键和权限 | 接口或表清单 |
| 接入 | 批、流或 CDC 按业务时延选择 | 重复、顺序、断点续传和回放 | 延迟与幂等测试 |
| 存储 | 按访问模式选择数据湖、数仓或 OLAP | 分区、格式、生命周期和成本 | 容量与查询评测 |
| 计算 | SQL、Spark、Flink 或 Python 服务 | 粒度、状态、资源和失败恢复 | 压测与执行计划 |
| 治理 | 元数据、质量、血缘、权限 | 责任、规则、影响分析和审计 | 规则结果与变更记录 |
| 服务 | 指标、API、看板或应用 | SLA、缓存、限流和版本 | 监控与验收样例 |

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |

链路设计先明确事实粒度。例如一行代表一次事件、一条订单明细、一个每日快照还是一个任务运行实例。粒度一旦混用，后面即使加了汇总表，也会把数量和金额累计两次。

## 3. 案例一：西北某综合能源服务公司

### 案例 1：西北某综合能源服务公司的“负荷预测与智能调度”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：园区用能成本上涨，客户希望判断节能改造和负荷转移的真实收益。本次讨论的重点是“负荷预测与智能调度”，所以团队先要求把先冻结对象与时间窗写进项目目标，而不是直接开始做报表。
- **数据范围**：分项计量、生产班次、天气、电价、储能充放电和设备运行。同时收集SCADA、EMS、DMS、计量自动化系统中的状态、时间和负责人信息，避免分析只停留在结果表。
- **关键障碍**：总表与分表口径不一致，电价尖峰平谷跨月，节能量没有基线调整。进一步检查后发现，如果不先处理采集频率不一致，“负荷预测与智能调度”很容易被一个表面相关指标替代。
- **处理过程**：建立总表-分表平衡和基线模型，区分价格变化、产量变化与改造节能效果。团队把需求拆成对象、粒度、指标、质量、发布五个检查点，并为每个检查点指定原始证据。
- **结果与边界**：示例项目形成改造前后同产量同温度对比，并给出储能与负荷转移的收益测算。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。
- **和本主题的联系**：在“负荷预测与智能调度”上，最有价值的产出不是一张漂亮的总览图，而是能从异常分组下钻到事件明细，并明确下一步由谁在什么时间前处理。

### 统一口径诊断 SQL

```sql
-- 负荷预测与智能调度：留存同期群诊断（用户类型 × 区域）
WITH scoped AS (
  SELECT
    station_id AS entity_key,
    event_id,
    reading_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_energy_event
  WHERE reading_time >= DATE '2026-04-01'
    AND reading_time <  DATE '2026-07-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '负荷率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

工程代码至少要满足以下要求：

1. 输入输出明确，参数来自配置或调度上下文。
2. 重跑同一分区不会产生重复结果。
3. 关键步骤记录度量，便于定位数据量和状态变化。
4. 失败可重试，但不会无限重试或放大副作用。
5. 版本、表结构和依赖变更可追踪。
6. 敏感信息不写进代码、日志和异常信息。

### 质量门禁与失败样本

```python
# 负荷预测与智能调度：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "负荷预测与智能调度"
TOPIC_KEY = "subject"
RULE_ID = "rule_energy_sa4l6j"
GUIDE_CHECKS = [
    "检查表码读数单调",
    "检查采集频率与时区一致",
    "检查缺失点已标记"
]
RULES = {
    "required_columns": ["event_id", "station_id", "reading_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "station_id",
    "time_field": "reading_time",
    "max_duplicate_rate": 0.0008,
    "max_null_rate": 0.005,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：检查表码读数单调；检查采集频率与时区一致；检查缺失点已标记
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

测试分为开发环境和生产前门禁。开发环境可以使用抽样数据快速验证逻辑，生产前门禁必须检查分区覆盖、主键、比例异常、上下游对账和资源消耗。数据发布后还要验证消费者能够读取、权限正确且时延在 SLA 内。

### 案例 2：南方某城市供电局的“负荷预测与智能调度”问题

这是一个脱敏后的复合场景，不代表任何单一客户的事实数据。

- **触发事件**：设备告警数量持续增长，但真正故障处理资源有限，运维团队需要确定优先级。本次讨论的重点是“负荷预测与智能调度”，所以团队先要求把先证明数据链路可信写进项目目标，而不是直接开始做报表。

- **结果与边界**：示例项目减少重复告警干扰，并把高风险设备和重要用户纳入优先巡检清单。这组示例说明方法与行动之间的关系，真实项目仍应以本企业口径、样本和验收记录为准。

## 7. 性能、容量与成本

| 瓶颈 | 先测量 | 可选手段 | 风险 |
| --- | --- | --- | --- |
| 扫描过多 | 分区命中、文件数、字节数 | 分区裁剪、列裁剪、压缩格式 | 分区过碎 |
| Shuffle 重 | 数据量、键分布、并发 | 预聚合、盐化、调整并发 | 资源争抢 |
| 热点倾斜 | Task 时长、输入大小 | 拆分热点键、两阶段聚合 | 结果顺序变化 |
| 状态过大 | Checkpoint、状态后端 | TTL、增量 Checkpoint、拆分 | 业务语义风险 |
| 查询慢 | 执行计划、缓存命中 | 预聚合、物化视图、OLAP | 数据新鲜度 |
| 成本高 | CPU、内存、存储、调用 | 生命周期、冷热分层、弹性 | SLA 退化 |

调优必须建立基线和回归对比：执行时间、扫描量、Shuffle 量、峰值内存、失败率和成本。只展示一次“从 30 分钟到 3 分钟”不够，还要说明数据量、资源和结果是否正确。

## 9. 发布、监控与故障处理

发布流程建议包括：代码评审、配置评审、数据迁移评审、灰度、对账、可观测性检查和回滚演练。监控至少覆盖任务、数据、服务、资源和业务五层。

故障处理顺序：

1. 确认影响面和是否需要暂停下游。
2. 保存现场：任务日志、参数、版本、输入输出计数。
3. 阻断错误扩散，必要时回滚到上一个稳定版本。
4. 按源系统、接入、计算、存储、服务和消费逐层定位。
5. 修复后按受影响分区补数，并验证重复、缺失和时序。
6. 完成问题时间线、根因、影响、改进和复核。

## 10. 验收清单

- 表结构、主键、分区、生命周期和负责人已登记。
- 关键任务具备幂等、重试、超时、告警和回滚。
- 质量规则接入发布门禁，阈值有业务依据。
- 核心链路有端到端 SLA 监控。
- 配置和密钥与代码分离，访问遵循最小权限。
- 容量和成本有基线，扩容与优化都有测量依据。
- 文档包含数据流、依赖、口径、故障处理和联系人。

1. 明确“负荷预测与智能调度”服务的使用者、决策动作和不做范围，并把成功标准写成可观察指标。
2. 为场站、设备、表计分别确认主键、时间和状态，画出从源系统到结果的链路。
3. 先做字段血缘和质量画像，检查表码读数单调、采集频率与时区一致、缺失点已标记。
4. 用同周期基线和至少两个维度拆解问题，避免只比较一个异常周。
5. 抽取正常、异常和边界样本回查原始业务单据，记录抽样方法与结论。
6. 选择一种代码实现并保留参数、版本、执行日志和结果快照，确保别人可以复跑。
7. 上线前定义告警阈值、回滚条件和责任人；上线后按周观察主指标与护栏指标。
8. 复盘时区分数据问题、业务变化、方案偏差和外部因素，并把改进项转成有时限的任务。

### 扩展代码一：从负荷预测与智能调度回到可核对明细

```sql
-- 负荷预测与智能调度：状态链与时间间隔核查
WITH ordered_events AS (
  SELECT
    station_id AS entity_key,
    event_id,
    stage_code,
    reading_time AS event_time,
    LAG(stage_code) OVER (
      PARTITION BY station_id
      ORDER BY reading_time, event_id
    ) AS previous_stage,
    LAG(reading_time) OVER (
      PARTITION BY station_id
      ORDER BY reading_time, event_id
    ) AS previous_time
  FROM fact_energy_event
  WHERE reading_time >= :start_date
    AND reading_time <  :end_date
    AND subject_key = 'subject'
)
SELECT
  entity_key,
  previous_stage,
  stage_code,
  event_time,
  event_time - previous_time AS elapsed,
  CASE
    WHEN event_time < previous_time THEN 'time_reversed'
    WHEN previous_stage = stage_code THEN 'duplicate_stage'
    WHEN previous_stage IS NULL THEN 'missing_prefix'
    ELSE 'candidate_delay'
  END AS exception_type
FROM ordered_events
WHERE event_time < previous_time
   OR previous_stage = stage_code
   OR event_time - previous_time > INTERVAL '1 hour'
ORDER BY exception_type, elapsed DESC;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把负荷预测与智能调度的验收证据写成门禁

```python
from datetime import date
from hashlib import sha256

import pandas as pd

SUBJECT = "负荷预测与智能调度"
BLOCKING_RULES = ["表码读数单调","采集频率与时区一致","缺失点已标记"]


def validate_release(frame: pd.DataFrame, start: date, end: date) -> dict:
    scoped = frame.loc[
        frame["event_date"].between(pd.Timestamp(start), pd.Timestamp(end))
        & (frame["subject_key"] == "subject")
    ].copy()
    checks = {
        "has_rows": len(scoped) > 0,
        "event_id_unique": not scoped["event_id"].duplicated().any(),
        "entity_key_complete": scoped["entity_key"].notna().all(),
        "event_time_present": scoped["event_time"].notna().all(),
        "scope_matches": scoped["subject_key"].nunique() == 1,
    }
    payload = f"{SUBJECT}|{start}|{end}|{len(scoped)}|{sorted(checks.items())}"
    return {
        "subject": SUBJECT,
        "rows": len(scoped),
        "checks": checks,
        "blocking_rules": BLOCKING_RULES,
        "release_allowed": all(checks.values()),
        "evidence_hash": sha256(payload.encode("utf-8")).hexdigest(),
    }
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
