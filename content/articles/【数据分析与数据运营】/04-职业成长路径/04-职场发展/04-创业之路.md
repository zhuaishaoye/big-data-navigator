# 创业之路

> [!tip] 使用方式
> 把“创业之路”放进经营监控、用户增长、活动复盘、用户分层、实验评估和策略迭代，真正困难的通常不是解释名词，而是把它变成一条能被核对、能被复现、也能推动行动的工程链路。本文不追求堆满概念，而是围绕这个主题拆出业务对象、数据粒度、典型故障、代码验证和验收方式。

## 1. 岗位到底在解决什么问题

围绕“创业之路”，数据分析相关岗位的价值不是掌握多少工具名称，而是能在经营监控、用户增长、活动复盘、用户分层、实验评估和策略迭代中把模糊问题转成可验证交付。看岗位 JD 时，把要求分成四层：

| 层级 | JD 常见表述 | 面试官真正想确认 | 可提供的证据 |
| --- | --- | --- | --- |
| 业务 | 理解业务、推动增长、支持决策 | 能否找到问题和行动 | 场景、口径、决策与复盘 |
| 方法 | 指标体系、实验、建模、治理 | 是否会选择合适方法 | 方案对比、假设、反例 |
| 工程 | SQL、Python、平台、调度、质量 | 能否稳定交付和排障 | 代码、监控、回滚记录 |
| 协作 | 跨团队、沟通、项目管理 | 是否能把事情推进完 | 争议、决策、责任和时间线 |

“创业之路”在面试中不能只回答定义。准备一个真实案例，说明为什么做、你个人做了什么、如何验证、结果怎样、如果重做会改什么。团队成果和个人贡献要明确分开。

## 2. 能力地图：从知道到能交付

| 能力项 | 合格表现 | 进阶表现 | 证据 |
| --- | --- | --- | --- |
| 业务理解 | 能说明“创业之路”服务谁、影响什么决策 | 能识别错误问题和隐藏约束 | 访谈记录、问题说明 |
| 指标口径 | 能定义对象、粒度、时间和排除项 | 能处理历史变更、实验和护栏指标 | 指标字典、对账样例 |
| 数据处理 | 能写可运行的 SQL/Python 并验证质量 | 能设计增量、幂等、监控和回滚 | 代码、执行日志 |
| 分析判断 | 能分层定位并回到明细 | 能区分描述、预测和因果 | 专题分析、反例清单 |
| 工程意识 | 知道时延、成本、权限和稳定性边界 | 能做方案取舍与容量评估 | 架构图、压测或故障复盘 |
| 协作推动 | 能记录争议、结论和负责人 | 能把一次性项目沉淀为机制 | 评审纪要、上线复盘 |
| 岗位迁移 | 能针对不同 JD 调整证据顺序 | 能解释长期能力与行业选择 | 定制简历、作品集 |

建议每个能力项准备三份材料：一页知识笔记、一段可运行代码或分析、一条项目证据。没有项目证据的内容可以保留在学习清单，但不要写成“精通”。

## 3. 案例一：用业务问题讲清技术选择

### 案例 1：华东某互联网公司面试小组的“创业之路”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“创业之路”映射到“数据岗位求职与面试表达”中的技术，而不是泛泛讨论概念。
- **触发事件**：候选人简历写了多个大数据项目，但追问吞吐、延迟和故障恢复时回答空泛。
- **业务与数据范围**：简历要点、项目背景、架构、指标、个人职责、故障记录和追问表现。数据侧重点采集架构图、执行计划、事故复盘和替代方案，并与埋点平台、CRM、订单系统中的时间、状态和责任人信息对齐。
- **需要回答的问题**：是否理解原理、取舍、故障和边界。
- **关键障碍**：项目均以工具清单描述，没有基线、取舍、验证和个人边界。同时要防止埋点重复把表面指标带偏。
- **处理过程**：按 STAR 重写两个核心项目，补充容量、SLA、失败案例和替代方案，并进行三轮模拟追问。实施时把“每个岗位准备两到三个与 JD 最相关且有证据的项目”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例准备把表达从“做了什么”转为“为什么这样做、如何证明有效”。验收至少同时看主指标、架构图、执行计划、事故复盘和替代方案和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把岗位要求拆成可验证能力，用真实项目证据回答业务、技术、协作和反思问题，并清楚说明个人贡献与结果边界。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

面试表达可以压缩成 90 秒：

> 背景是【候选人简历写了多个大数据项目，但追问吞吐、延迟和故障恢复时回答空泛】。我负责【对象、范围、数据与方案】。先处理【主键、时间、状态或权限】，再用【方法】验证。最终交付【表/指标/服务/规则】，业务采取【行动】。结果是【有口径的改善】，但仍有【限制】，下一版会【改进】。

数字要能回答来源、时间窗、计算方法和你的贡献，不要使用无法解释的百分比。

## 4. 案例二：故障与复盘如何讲

### 案例 2：华南某金融科技公司招聘团队的“创业之路”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“创业之路”映射到“数据岗位求职与面试表达”中的证据，而不是泛泛讨论概念。
- **触发事件**：候选人技术题答得不错，但业务沟通和风险意识未达到高级岗位要求。
- **业务与数据范围**：案例面试记录、指标定义、权限、合规、协作冲突和复盘表现。数据侧重点采集需求记录、代码、指标、上线、复盘和他人反馈，并与埋点平台、CRM、订单系统中的时间、状态和责任人信息对齐。
- **需要回答的问题**：项目是否有问题、动作、结果、验证和个人贡献。
- **关键障碍**：候选人只关注计算实现，没有说明消费者、口径、权限和上线风险。同时要防止分母漂移把表面指标带偏。
- **处理过程**：补充业务访谈式练习，要求每次方案先写对象、决策、SLA、风险和验收。实施时把“回答包含背景、个人任务、关键动作、验证结果、限制和反思”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：复合案例用结构化评分而非单一算法题判断岗位匹配。验收至少同时看主指标、需求记录、代码、指标、上线、复盘和他人反馈和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把岗位要求拆成可验证能力，用真实项目证据回答业务、技术、协作和反思问题，并清楚说明个人贡献与结果边界。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

故障题按“影响、止血、定位、修复、复核、防复发”回答。比如数据异常时，先判断是否阻断发布和通知消费者，再检查源系统、任务、分区、口径、代码和维度映射。修复后要保留问题时间线、影响资产、根因和自动化措施。

from dataclasses import dataclass, field

@dataclass
class Evidence:
    capability: str
    artifact: str
    verified_by: str
    result: str
    limitation: str

@dataclass
class CapabilityPlan:
    target_role: str
    topic: str = "\"创业之路\""
    evidence: list[Evidence] = field(default_factory=list)

    def gaps(self) -> list[str]:
        required = {"SQL", "数据质量", "工程交付", "业务表达"}
        return sorted(required - {item.capability for item in self.evidence})

plan = CapabilityPlan(
    target_role="数据开发工程师",
    evidence=[
        Evidence("SQL", "可复跑窗口函数项目", "逐行口头解释", "结果与样例对账", "仅一个业务域"),
        Evidence("数据质量", "质量规则与失败样本", "同伴代码评审", "发现重复与缺失", "样本规模有限"),
    ],
)
print({"gaps": plan.gaps(), "claim_policy": "只有证据才写成熟练"})

### 质量验证与发布门禁

```python
# 创业之路：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "创业之路"
TOPIC_KEY = "subject"
RULE_ID = "rule_analytics_1xqpxdo"
GUIDE_CHECKS = [
    "每个岗位准备两到三个与 JD 最相关且有证据的项目",
    "回答包含背景、个人任务、关键动作、验证结果、限制和反思",
    "技术追问能解释原理、替代方案、故障和取舍",
    "所有数字、职责和成果都能回到真实材料"
]
RULES = {
    "required_columns": ["event_id", "user_id", "event_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "user_id",
    "time_field": "event_time",
    "max_duplicate_rate": 0.0005,
    "max_null_rate": 0.002,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：每个岗位准备两到三个与 JD 最相关且有证据的项目；回答包含背景、个人任务、关键动作、验证结果、限制和反思；技术追问能解释原理、替代方案、故障和取舍；所有数字、职责和成果都能回到真实材料
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

现场回答代码题时，建议边写边讲：

1. 先确认表粒度、状态定义和时间字段。
2. 说明去重策略及为什么选择该窗口。
3. 指出可能全表扫描、数据倾斜或空值影响。

5. 说明数据量扩大十倍时先测什么，而不是直接说加机器。

## 6. 高频追问与回答骨架

**问：你如何定义“创业之路”的成功？**

答：同时给出业务结果、过程诊断和护栏指标。业务结果说明是否改善，过程指标解释改善来自哪里，护栏指标防止成本、投诉、风险或长期价值恶化。

**问：指标下降了怎么办？**

答：先确认数据是否真实完整，再按对象、结构、行为和外部因素拆分，抽取正负样本回查，最后给出行动和验证方式。事件主键唯一、分子分母同口径、匿名与登录身份已打通。

**问：为什么选择这个方案？**

答：说明约束和目标，再比较至少两个替代方案。回答应包括开发成本、维护成本、时延、准确性、扩展性和失败后的影响。

**问：最大的困难是什么？**

答：选择一个可复现的技术或协作问题，例如“埋点重复”，讲清你如何定位、谁参与、采取了什么折中和最终防复发措施。

**问：如果重做会改什么？**

答：优先说可验证的改进，例如更早冻结口径、增加质量门禁、用小范围灰度、补充长期护栏指标或减少手工依赖。

## 7. 简历和作品集怎么写

弱表达：

> 使用 SQL 和 Python 完成“创业之路”相关数据分析，制作报表并优化流程。

更可信的表达：

> 负责【业务域】的“创业之路”专题，统一【对象/时间/状态】口径，完成【模型、代码、规则或服务】；通过【验证方法】定位【具体问题】，推动【业务动作】；沉淀【指标字典、监控或复用方案】，并使用【可解释的效率、质量、时效或范围指标】验收。

作品集至少包含背景、数据范围、架构或分析流程、关键代码、质量验证、结果限制和复盘。不能披露公司数据时，使用合成数据和脱敏边界，不要为了好看虚构业务增长。

## 8. 案例三：把岗位要求转成可验证练习

### 案例 3：华北某转行学习者的“创业之路”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“创业之路”映射到“数据岗位求职与面试表达”中的岗位，而不是泛泛讨论概念。
- **触发事件**：作品集包含多个教程项目，投递后很少获得面试。
- **业务与数据范围**：目标 JD、作品问题、数据来源、代码、结果、文档和招聘方反馈。数据侧重点采集职责、技术栈、业务域、交付对象和面试流程，并与埋点平台、CRM、订单系统中的时间、状态和责任人信息对齐。
- **需要回答的问题**：JD 真正要求解决什么问题、面对什么数据和约束。
- **关键障碍**：项目彼此重复，没有真实问题、验证和质量控制。同时要防止把相关性误写成因果把表面指标带偏。
- **处理过程**：只保留两个有业务闭环的项目，补充数据卡、质量规则、失败样本、复盘和可复跑说明。实施时把“技术追问能解释原理、替代方案、故障和取舍”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例求职材料用问题深度和证据质量替代项目数量。验收至少同时看主指标、职责、技术栈、业务域、交付对象和面试流程和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把岗位要求拆成可验证能力，用真实项目证据回答业务、技术、协作和反思问题，并清楚说明个人贡献与结果边界。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

把案例改写成练习时，不要直接复述团队成果。先列出你个人能复跑的部分，例如定义一行数据、写出三个指标、实现一个质量检查、解释一次失败回滚，再为每个部分找评审人或可验证结果。面试中的“熟悉”必须能落到这些证据上。

### 扩展代码一：从创业之路回到可核对明细

```sql
-- 创业之路：源表与结果表按对象对账
WITH source_side AS (
  SELECT
    user_id AS entity_key,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum
  FROM fact_analysis_event
  WHERE event_time >= :start_date
    AND event_time <  :end_date
    AND subject_key = 'subject'
    AND is_deleted = 0
  GROUP BY user_id
),
result_side AS (
  SELECT
    user_id AS entity_key,
    event_cnt,
    metric_sum
  FROM fact_analysis_event_result
  WHERE stat_date BETWEEN :start_date AND :end_date
    AND subject_key = 'subject'
)
SELECT
  COALESCE(s.entity_key, r.entity_key) AS entity_key,
  s.event_cnt AS source_event_cnt,
  r.event_cnt AS result_event_cnt,
  s.metric_sum AS source_metric_sum,
  r.metric_sum AS result_metric_sum,
  COALESCE(r.metric_sum, 0) - COALESCE(s.metric_sum, 0) AS metric_diff
FROM source_side s
FULL OUTER JOIN result_side r USING (entity_key)
WHERE ABS(COALESCE(r.metric_sum, 0) - COALESCE(s.metric_sum, 0)) > 0
   OR COALESCE(s.event_cnt, 0) <> COALESCE(r.event_cnt, 0)
ORDER BY ABS(metric_diff) DESC;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把创业之路的验收证据写成门禁

```python
from datetime import date
from hashlib import sha256

import pandas as pd

SUBJECT = "创业之路"
BLOCKING_RULES = ["事件主键唯一","分子分母同口径","匿名与登录身份已打通"]


def validate_release(frame: pd.DataFrame, start: date, end: date) -> dict:
    scoped = frame.loc[
        frame["event_date"].between(pd.Timestamp(start), pd.Timestamp(end))
        & (frame["subject_key"] == "subject")
    ].copy()
    checks = {
        "has_rows": len(scoped) > 0,
        "event_id_unique": not scoped["event_id"].duplicated().any(),
        "entity_key_complete": scoped["entity_key"].notna().all(),
        "event_time_present": scoped["event_time"].notna().all(),
        "scope_matches": scoped["subject_key"].nunique() == 1,
    }
    payload = f"{SUBJECT}|{start}|{end}|{len(scoped)}|{sorted(checks.items())}"
    return {
        "subject": SUBJECT,
        "rows": len(scoped),
        "checks": checks,
        "blocking_rules": BLOCKING_RULES,
        "release_allowed": all(checks.values()),
        "evidence_hash": sha256(payload.encode("utf-8")).hexdigest(),
    }
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。

### 四个案例共用的验收清单

| 验证面 | 发布前问题 | 证据 | 不通过时 |
| --- | --- | --- | --- |
| 对象与粒度 | 一行数据代表用户、事件、快照还是结果 | 主键、版本、有效时间和边界样本 | 阻断 |
| 时间语义 | 业务发生、数据可见、决策采用是否混用 | event_time、入仓时间、行动时间轴 | 阻断 |
| 指标口径 | 转化率的分子、分母和排除项是否冻结 | 指标字典、SQL、对账结果 | 阻断正式指标 |
| 状态与关联 | 业务问题 → 指标定义 → 数据准备 → 探索分析是否可达且可追溯 | 状态机、明细、操作日志 | 阻断关键链路 |
| 权限与最小字段 | 派生表、导出和临时授权是否扩大访问范围 | 分类分级、字段血缘、访问日志 | 阻断导出 |
| 恢复与审计 | 失败后能否定位影响范围并幂等重跑 | 参数、版本、分区清单、补数对账 | 阻断发布 |
