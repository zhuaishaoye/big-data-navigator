# 转化率

> [!abstract] 场景速览
> 如果只记住“转化率”的定义，遇到真实数据时仍然很难行动。本文把它拆成五个可检查问题：谁在使用、流程在哪里变化、数据一行代表什么、异常如何发现、上线后用哪个指标验收。每个部分都配一个工作案例或代码片段。

## 1. “转化率”在数据分析与数据运营业务链中的位置

数据分析与数据运营的核心流程可以概括为：业务问题 → 指标定义 → 数据准备 → 探索分析 → 策略设计 → 实验或灰度 → 结果复盘。参与角色包括业务负责人、产品、运营、数据分析、数据开发、财务、客服。“转化率”通常不是一个孤立字段，而是连接业务动作、数据记录和管理决策的一层能力。

从数据团队视角，至少要回答四个问题：

1. **谁使用**：业务负责人、产品、运营、数据分析分别要用它做判断、执行还是审计。
2. **对象是什么**：一行数据代表用户、一次事件、一个批次还是一天快照。
3. **流程在哪里变化**：通过指标定义、数据准备、探索分析、策略设计之间的状态和时间差定位问题。
4. **结果如何被采用**：谁在什么时间前采取行动，使用哪个指标观察改善或副作用。

一个合格的专题目标可以写成：

> 在【时间窗】和【授权数据范围】内，围绕“转化率”，按【渠道、用户分层、活动】比较【复购率】与【增量收益】，定位一个可干预流程节点，并记录行动后的变化与边界。

## 2. 一张图看清角色、流程和数据

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 用户 | `user_id` | 业务问题 |
| 过程对象 | 会话 | `session_id` | 指标定义 |
| 过程对象 | 行为事件 | `event_id` | 数据准备 |
| 结果对象 | 订单 | `order_id` | 探索分析 |
| 结果对象 | 策略 | `strategy_id` | 策略设计 |
| 专题分析 | 转化率 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

建模时不要先把所有系统字段堆进一张大表。更稳妥的做法是分别保留三类事实：

- **事件事实**：谁在什么时间做了动作，例如挂号、下单、开工、报警或学习。
- **状态快照**：对象在某一天的状态，例如会员等级、租约、账户余额或设备资产关系。
- **结果事实**：流程完成后的产出，例如结算金额、良品数量、签收结果或考试分数。

三者的粒度不同。把事件、快照和结果强行放在同一行，会让金额、数量和转化率在汇总时重复。若“转化率”涉及状态变化，优先建立状态机；若涉及金额，先做借贷或收付平衡；若涉及对象归属，保留维度有效期。

## 3. 指标与口径：不要把相关数字直接当答案

| 专题观测面 | 需要回答的问题 | 关键证据 | 判定与动作 |
| --- | --- | --- | --- |
| 行动（本标题优先） | 建议是否可执行，是否有护栏和观察周期 | 决策、负责人、主指标、护栏和复盘 | 没有行动与验证就不算闭环 |
| 口径 | 分子分母、状态、去重和时间是否一致 | 指标字典、明细抽样、源系统对账 | 口径未冻结不比较趋势 |
| 问题 | 要改变谁的行为，比较基线和成功标准是什么 | 决策记录、对象范围、时间窗口和行动负责人 | 不能转成行动的问题先澄清 |
| 方法 | 描述、诊断、预测、实验还是准实验 | 数据生成过程、对照组、假设和限制 | 相关结果不得写成因果 |

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 转化率 | `COUNT(DISTINCT conversion_id) / COUNT(DISTINCT eligible_id)`（视图字段 `cvr`） | 渠道、用户分层、活动 | 不混用测试、撤销和跨期状态；与“转化率”相关时还要补充主题筛选 |
| 留存率 | `COUNT(DISTINCT retained_user_id) / COUNT(DISTINCT cohort_user_id)`（视图字段 `retention_rate`） | 用户分层、活动、产品 | 不混用测试、撤销和跨期状态；与“转化率”相关时还要补充主题筛选 |
| 客单价 | `SUM(paid_amount) / COUNT(DISTINCT paid_order_id)`（视图字段 `avg_order_value`） | 活动、产品、地区 | 不混用测试、撤销和跨期状态；与“转化率”相关时还要补充主题筛选 |
| 复购率 | `COUNT(DISTINCT repeat_buyer_id) / COUNT(DISTINCT buyer_id)`（视图字段 `repurchase_rate`） | 产品、地区 | 不混用测试、撤销和跨期状态；与“转化率”相关时还要补充主题筛选 |

指标字典至少应包含：中文名、英文编码、业务定义、计算公式、事实粒度、时间字段、对象范围、排除条件、负责人和验收样例。对于“转化率”，还应注明它使用的是业务发生时间还是入仓时间，是否包含撤销、退费、测试、跨期和补录记录。

一个常见误区是看到复购率变化就立即解释业务原因。更可靠的顺序是：

1. 检查数据覆盖和延迟是否变化。
2. 检查对象范围、状态映射和维度归属是否变化。
3. 按时间、结构和分组拆解贡献。
4. 回到明细寻找能解释变化的事件。
5. 如果已经采取行动，再评估行动带来的增量，而不是事后挑一个相关指标。

## 4. 工作案例：从现象到数据处理

### 案例 1：华南某 SaaS 运营团队的“转化率”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“转化率”映射到“分析方法、指标与实验”中的行动，而不是泛泛讨论概念。
- **触发事件**：总体续费率稳定，但多个客户分层续费率都在下降。
- **业务与数据范围**：客户规模、行业、合同期、产品使用、工单、续费和流失原因。数据侧重点采集决策、负责人、主指标、护栏和复盘，并与埋点平台、CRM、订单系统中的时间、状态和责任人信息对齐。
- **需要回答的问题**：建议是否可执行，是否有护栏和观察周期。
- **关键障碍**：高价值大客户占比上升掩盖小客户流失，形成辛普森悖论。同时要防止埋点重复把表面指标带偏。
- **处理过程**：按客户分层和合同期拆解结构贡献，回到增购、降级和工单记录验证原因。实施时把“描述、预测和因果结论分别命名并说明证据边界”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：复合案例用结构变化、分组率和样本量解释总体指标。验收至少同时看主指标、决策、负责人、主指标、护栏和复盘和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把模糊问题翻译成对象、时间、比较基准和行动，检查数据口径与偏差，再选择描述、诊断、预测或因果方法。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

这个案例最关键的动作不是“跑一条 SQL”，而是把“转化率”对应的业务对象和上下游系统放在同一张链路图上。链路图至少要标出源系统、事件时间、关联主键、状态变化、数据负责人和消费方。

## 5. SQL 示例：在统一口径下做分层诊断

下面的查询用于展示分析结构，表名和字段需映射到实际环境。重点是去重、范围筛选、基线比较和贡献率，而不是代码本身。

### 标题专属诊断 SQL

```sql
-- 转化率：分位对比诊断（产品 × 渠道）
WITH scoped AS (
  SELECT
    user_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_analysis_event
  WHERE event_time >= DATE '2026-07-01'
    AND event_time <  DATE '2026-10-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '转化率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

执行后要回答四类验证题：

- 结果总量能否与源系统或既有报表在相同口径下解释差异？
- 排名前几位的分组是否由少数超长、重复或补录记录造成？
- 缺失日期表现为“未发生”还是“未采集”，是否改变分母？
- 维度使用的是当时归属还是当前归属，跨期比较是否一致？

## 6. 第二个案例：跨系统、跨部门时怎样不失控

### 案例 2：华北某内容平台的“转化率”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“转化率”映射到“分析方法、指标与实验”中的口径，而不是泛泛讨论概念。
- **触发事件**：推荐策略让人均时长增加，但次日留存和创作者多样性下降。
- **业务与数据范围**：实验组、曝光、点击、时长、留存、内容类型、创作者分布和投诉。数据侧重点采集指标字典、明细抽样、源系统对账，并与埋点平台、CRM、订单系统中的时间、状态和责任人信息对齐。
- **需要回答的问题**：分子分母、状态、去重和时间是否一致。
- **关键障碍**：实验只看点击与时长，没有检查新奇效应、用户结构和内容供给副作用。同时要防止分母漂移把表面指标带偏。
- **处理过程**：增加分层分析、长期观察和多样性护栏，按用户活跃度评估策略差异。实施时把“报告同时保留反例、样本量、护栏指标和停止条件”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例项目证明主指标显著后仍需继续观察成本、体验和长期价值。验收至少同时看主指标、指标字典、明细抽样、源系统对账和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把模糊问题翻译成对象、时间、比较基准和行动，检查数据口径与偏差，再选择描述、诊断、预测或因果方法。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

跨部门项目最容易在三个地方返工：业务术语没有冻结、主数据映射没有版本、验收时才发现权限不足。建议在开发前让业务负责人签字确认指标定义，让数据负责人确认粒度与主键，让安全负责人确认字段范围，让运维负责人确认发布与回滚窗口。

## 7. Python 示例：把数据质量变成发布门禁

### 可执行质量门禁

```python
# 转化率：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "转化率"
TOPIC_KEY = "subject"
RULE_ID = "rule_analytics_kno9am"
GUIDE_CHECKS = [
    "分析问题写明对象、时间、比较基准、决策和行动负责人",
    "所有指标检查分母、状态、时间、去重和排除条件",
    "描述、预测和因果结论分别命名并说明证据边界",
    "报告同时保留反例、样本量、护栏指标和停止条件"
]
RULES = {
    "required_columns": ["event_id", "user_id", "event_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "user_id",
    "time_field": "event_time",
    "max_duplicate_rate": 0.0007,
    "max_null_rate": 0.005,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：分析问题写明对象、时间、比较基准、决策和行动负责人；所有指标检查分母、状态、时间、去重和排除条件；描述、预测和因果结论分别命名并说明证据边界；报告同时保留反例、样本量、护栏指标和停止条件
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

这段代码适合放在离线任务完成之后、指标发布之前。真实环境还应从调度平台读取分区参数、把结果写入质量平台，并在关键规则失败时阻断下游。告警不是终点，工单中要记录影响资产、发现时间、临时处理、根因、修复时间和防复发动作。

## 8. 异常排查：从指标异常回到业务事件

| 专题检查项 | 失败时会看到什么 | 首选证据 | 处理动作 |
| --- | --- | --- | --- |
| 分析问题写明对象、时间、比较基准、决策和行动负责人 | 建议是否可执行，是否有护栏和观察周期 | 决策、负责人、主指标、护栏和复盘 | 没有行动与验证就不算闭环 |
| 所有指标检查分母、状态、时间、去重和排除条件 | 分子分母、状态、去重和时间是否一致 | 指标字典、明细抽样、源系统对账 | 口径未冻结不比较趋势 |
| 描述、预测和因果结论分别命名并说明证据边界 | 要改变谁的行为，比较基线和成功标准是什么 | 决策记录、对象范围、时间窗口和行动负责人 | 不能转成行动的问题先澄清 |
| 报告同时保留反例、样本量、护栏指标和停止条件 | 描述、诊断、预测、实验还是准实验 | 数据生成过程、对照组、假设和限制 | 相关结果不得写成因果 |

围绕“转化率”排查时，可以按以下顺序进行：

1. **影响面**：哪些指标、报表、接口或业务团队受影响，是否需要暂停对外发布。
2. **时间线**：源系统变更、任务发布、数据回刷、组织调整和业务活动分别发生在什么时候。
3. **数据链路**：上游是否延迟，分区是否缺失，主键是否重复，状态是否映射错误。
4. **业务证据**：抽取异常记录，与原始单据、操作日志、客服记录或现场系统核对。
5. **修复与复核**：明确补数范围、重跑粒度、回滚版本和验收样例。
6. **防复发**：把一次性排查升级为规则、监控、责任人和变更评审。

特别要注意：埋点重复；分母漂移；把相关性误写成因果；活动归因重叠。这些问题如果不被单独标记，很容易被误写成业务趋势。

## 9. 第三个案例与延伸场景

### 案例 3：华东某电商增长团队的“转化率”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“转化率”映射到“分析方法、指标与实验”中的问题，而不是泛泛讨论概念。
- **触发事件**：新人券上线后首日转化提升，但一周后复购和毛利下降。
- **业务与数据范围**：曝光、领券、下单、支付、退款、复购、渠道和用户分层。数据侧重点采集决策记录、对象范围、时间窗口和行动负责人，并与埋点平台、CRM、订单系统中的时间、状态和责任人信息对齐。
- **需要回答的问题**：要改变谁的行为，比较基线和成功标准是什么。
- **关键障碍**：只比较活动前后，没有对照组；自然流量和付费流量归因重叠。同时要防止把相关性误写成因果把表面指标带偏。
- **处理过程**：按用户分层做对照实验，主指标看新增贡献，加入退款、毛利和长期留存护栏。实施时把“分析问题写明对象、时间、比较基准、决策和行动负责人”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例分析把短期提升与长期收益分开，并给出扩大或停止条件。验收至少同时看主指标、决策记录、对象范围、时间窗口和行动负责人和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把模糊问题翻译成对象、时间、比较基准和行动，检查数据口径与偏差，再选择描述、诊断、预测或因果方法。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

另外两个适合继续拆分的工作场景是：

- **华东某内容社区**：日活增长但广告收入下降，业务希望判断是用户结构变化、内容供给还是广告库存问题。可以先从内容曝光、点击、停留、互动、广告请求、竞价、成交和会员订单建立最小数据闭环，再围绕“转化率”检查机器流量混入曝光，多端账号未合并，广告曝光与计费口径不同。
- **华南某本地生活平台**：补贴增加但订单和商家留存没有同步改善，需要评估补贴投向和生态健康度。可以先从用户曝光、领券、下单、核销、退款、商家经营、配送和补贴成本建立最小数据闭环，再围绕“转化率”检查领券用户跨设备识别失败，核销与退款跨日，商家营业状态未进入推荐链路。

如果要把本专题扩展成一个完整作品或项目，建议至少保留以下材料：

- 一页业务流程图，标注角色、系统、事件和异常分支。
- 一份指标字典，记录定义、粒度、边界和负责人。
- 一张事实与维度关系图，说明主键、时间和历史归属。
- 一套 SQL 或 Python 代码，包含参数、质量检查和执行说明。
- 三组验证样例：正常对象、边界对象和异常对象。
- 一份上线后复盘，记录行动、结果、副作用和下一步。

### 案例 4：转化率上线前的质量门禁

某组织希望用“转化率”支持一次真实决策，但在取数与评审阶段发现，常规日期下结果看起来正常，一旦遇到空值、重复、跨期、撤销或历史归属，报表口径便无法解释。这个案例因此从问题定义重新开始。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 把关键质量规则、阈值、例外审批、阻断动作和复核人写入发布流程。在本场景里，核心风险还包括活动归因重叠，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：用户、会话及其在探索分析前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注user_id与session_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 常规日期下结果看起来正常，一旦遇到空值、重复、跨期、撤销或历史归属，报表口径便无法解释。初看时，实验平台与BI的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 五类边界样本、规则命中率、趋势对比、豁免记录、责任人、阻断结果和复盘工单。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“数据分析”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“转化率”的当前定义并记录版本；第二步用用户明细核对实验平台到BI的关联；第三步按产品与渠道做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察复购率和护栏指标转化率。
- **行动与护栏：** 从阻断、严重、观察三级建立规则，先修数据和逻辑，再决定是否允许有期限的业务例外。专题检查项“分析问题写明对象、时间、比较基准、决策和行动负责人”被写成发布门禁，影响资金、安全、监管或核心经营判断的关键规则失败时停止发布。
- **失败路径：** 一直调低阈值让报表通过，却没有处理规则为何持续失败。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“转化率”时，先验证决策、负责人、主指标、护栏和复盘，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由数据分析在明确时限内，根据复购率、转化率和时区一致决定继续、回退、补查还是转人工。 若活动归因重叠或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。
### 案例 5：转化率失败后如何做到可恢复

团队准备把“转化率”从个人分析脚本升级为多人共用的数据能力。第一次评审就暴露出：一次错误发布已经产生结果，团队只能凭负责人记忆寻找影响范围，补数后仍无法确认是否重复或遗漏。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 让错误输入、处理版本、影响分区和恢复结果都能被独立回放和审计。在本场景里，核心风险还包括只观察短期指标，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：会话、行为事件及其在策略设计前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注session_id与event_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 一次错误发布已经产生结果，团队只能凭负责人记忆寻找影响范围，补数后仍无法确认是否重复或遗漏。初看时，BI与客服工单的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 运行参数、代码版本、输入快照、输出摘要、受影响分区、回滚记录和补数对账。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“数据开发”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“转化率”的当前定义并记录版本；第二步用会话明细核对BI到客服工单的关联；第三步按地区与用户分层做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察增量收益和护栏指标留存率。
- **行动与护栏：** 保存现场并停止下游扩散，按影响边界回滚或隔离结果，使用幂等任务从最小必要范围重新计算。专题检查项“所有指标检查分母、状态、时间、去重和排除条件”被写成发布门禁，恢复任务没有对账、没有版本记录或无法重复执行时，不宣布故障结束。
- **失败路径：** 直接覆盖目标表，或者把所有分区全部重跑以求省事。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“转化率”时，先验证指标字典、明细抽样、源系统对账，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由数据开发在明确时限内，根据增量收益、留存率和退款与撤销已冲减决定继续、回退、补查还是转人工。 若只观察短期指标或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

> 最终动作不是“把报表做出来”，而是由财务在明确时限内，根据转化率、客单价和事件主键唯一决定继续、回退、补查还是转人工。 若埋点重复或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。
### 案例 7：转化率上线后的增量验证

某组织希望用“转化率”支持一次真实决策，但在取数与评审阶段发现，方案上线后主指标出现变化，但同期还有活动、季节性和渠道结构调整，无法证明变化来自本次动作。这个案例因此从问题定义重新开始。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 把观察结果与可执行动作分开，判断方案是否带来可解释增量，并明确停止或扩大的条件。在本场景里，核心风险还包括分母漂移，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：订单、策略及其在结果复盘前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注order_id与strategy_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 方案上线后主指标出现变化，但同期还有活动、季节性和渠道结构调整，无法证明变化来自本次动作。初看时，数据仓库与埋点平台的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 基线、对照或趋势拟合、分组分配、主指标、护栏指标、动作时间和成本记录。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“客服”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“转化率”的当前定义并记录版本；第二步用订单明细核对数据仓库到埋点平台的关联；第三步按用户分层与产品做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察留存率和护栏指标复购率。
- **行动与护栏：** 在行动前冻结观察窗口与分组规则，上线后同时报告总体结果、分层结果、置信区间和反例。专题检查项“报告同时保留反例、样本量、护栏指标和停止条件”被写成发布门禁，收益只在少数子组出现且护栏恶化时，不扩大全量使用。
- **失败路径：** 用上线前后两张趋势图直接宣称方案有效，忽略选择偏差与自然增长。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“转化率”时，先验证数据生成过程、对照组、假设和限制，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由客服在明确时限内，根据留存率、复购率和分子分母同口径决定继续、回退、补查还是转人工。 若分母漂移或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从转化率回到可核对明细

```sql
-- 转化率：字段血缘与影响范围
WITH changed_columns AS (
  SELECT column_name
  FROM information_schema.columns
  WHERE table_schema = :source_schema
    AND table_name = :source_table
    AND last_altered_at >= :change_time
),
downstream_assets AS (
  SELECT
    asset_id,
    asset_name,
    asset_type,
    owner_name,
    criticality,
    last_used_at
  FROM metadata_asset_relation
  WHERE upstream_asset_id = :source_asset_id
    AND relation_status = 'active'
)
SELECT
  d.asset_id,
  d.asset_name,
  d.asset_type,
  d.owner_name,
  d.criticality,
  d.last_used_at,
  COUNT(c.column_name) AS changed_column_cnt,
  CASE
    WHEN d.criticality IN ('core', 'regulated') THEN 'block_release'
    WHEN d.last_used_at >= CURRENT_DATE - INTERVAL '7 days' THEN 'notify_owner'
    ELSE 'register_review'
  END AS required_action
FROM downstream_assets d
CROSS JOIN changed_columns c
GROUP BY d.asset_id, d.asset_name, d.asset_type, d.owner_name, d.criticality, d.last_used_at
ORDER BY
  CASE WHEN d.criticality IN ('core', 'regulated') THEN 0 ELSE 1 END,
  d.last_used_at DESC;

-- 目标：变更前识别 埋点平台、CRM、订单系统 之后的所有结果与消费者。
```

### 扩展代码二：把转化率的验收证据写成门禁

```python
import pandas as pd

KEY = ["entity_key", "event_id"]
AMOUNT_COLUMNS = ["metric_value", "adjustment_value"]


def reconcile(source: pd.DataFrame, result: pd.DataFrame) -> pd.DataFrame:
    def aggregate(frame: pd.DataFrame, side: str) -> pd.DataFrame:
        grouped = (
            frame.groupby("entity_key", dropna=False)
            .agg(
                event_cnt=("event_id", "nunique"),
                metric_sum=("metric_value", "sum"),
                adjustment_sum=("adjustment_value", "sum"),
            )
            .reset_index()
        )
        return grouped.rename(columns={
            "event_cnt": f"{side}_event_cnt",
            "metric_sum": f"{side}_metric_sum",
            "adjustment_sum": f"{side}_adjustment_sum",
        })

    compared = aggregate(source, "source").merge(
        aggregate(result, "result"),
        on="entity_key",
        how="outer",
    )
    compared["metric_diff"] = (
        compared["result_metric_sum"].fillna(0)
        - compared["source_metric_sum"].fillna(0)
    )
    compared["event_diff"] = (
        compared["result_event_cnt"].fillna(0)
        - compared["source_event_cnt"].fillna(0)
    )
    compared["exception"] = compared.apply(
        lambda row: "missing_result" if pd.isna(row["result_metric_sum"])
        else "unexpected_result" if pd.isna(row["source_metric_sum"])
        else "count_diff" if row["event_diff"] != 0
        else "amount_diff",
        axis=1,
    )
    return compared.loc[
        (compared["metric_diff"].abs() > 0) | (compared["event_diff"] != 0)
    ].sort_values("metric_diff", key=lambda values: values.abs(), ascending=False)
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。

### 四个案例共用的验收清单

| 验证面 | 发布前问题 | 证据 | 不通过时 |
| --- | --- | --- | --- |
| 对象与粒度 | 一行数据代表用户、事件、快照还是结果 | 主键、版本、有效时间和边界样本 | 阻断 |
| 时间语义 | 业务发生、数据可见、决策采用是否混用 | event_time、入仓时间、行动时间轴 | 阻断 |
