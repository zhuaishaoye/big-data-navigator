# 营销活动分析

> [!abstract] 营销投放与活动评估实战手册
> 营销活动分析要区分目标人群、成功触达、自然转化和由活动带来的增量。曝光、点击、领券和下单属于不同阶段，活动效果必须结合对照、成本、频次、售后和长期用户价值判断。

## 1. 营销活动分析：定义、适用边界与决策出口

营销活动分析要区分目标人群、成功触达、自然转化和由活动带来的增量。曝光、点击、领券和下单属于不同阶段，活动效果必须结合对照、成本、频次、售后和长期用户价值判断。

**本篇的适用边界。** 本篇覆盖站内外广告、内容营销、优惠券和会员活动的一次活动或连续活动评估；不把品牌广告的长期价值强行压缩成单次最后点击转化。

**最常见的错误替代。** 不能把活动期所有订单都算作活动成果，不能忽略渠道同时调整和自然增长，也不能用优惠依赖用户的短期订单证明长期价值。

**最终决策。** 营销、财务和数据分析团队要判断：活动是否触达目标人群，是否产生可解释增量，投放到什么频次应停止，预算如何调整，售后和品牌风险是否可接受。 因此，这篇内容不从“应该建哪张表”开始，而从业务动作、责任人和失败后果开始。只有先确定谁在什么时点做出什么决定，字段、SQL、看板和模型才有明确用途。

围绕“营销活动分析”，工作中至少要区分四类问题：

1. **身份问题**：对象是谁，主键能否跨系统稳定关联，合并、拆分、撤销后历史是否还看得见。
2. **时间问题**：业务发生、状态生效、数据入仓、计算完成和人员行动分别发生在哪一刻。
3. **状态问题**：当前状态是一段事件、一张快照还是最终结果，空值代表未发生、未采集还是已删除。
4. **责任问题**：谁确认口径，谁处理异常，谁有权放行或停止，谁在观察期后复盘。

## 2. 营销活动分析的完整业务流程

| 环节 | 要做的事 | 最小证据 | 失败后先查什么 |
| --- | --- | --- | --- |
| 目标与人群 | 定义业务目标、目标对象、排除人群和成功时限 | 活动 brief、人群规则和基线 | 没有对照和触点规则 |
| 触达与频次 | 记录渠道、素材、发送、可见曝光和成本 | 投放任务、请求、回执和频次上限 | 预算按最后点击分配 |
| 行为响应 | 关联点击、访问、领券、加购和咨询 | 触点路径、设备与活动参数 | 退款投诉未进入护栏 |
| 交易与售后 | 记录订单、支付、退款、退货和投诉 | 归因订单、售后事件和观察窗口 | 每个渠道单独限额 |
| 增量评估 | 通过对照、实验或准实验识别活动效果 | 分组、样本量、主指标和护栏 | 没有对照和触点规则 |
| 成本与价值 | 汇总媒体、权益、人力和技术成本 | 成本单、预算和单位增量成本 | 预算按最后点击分配 |
| 复盘与停止 | 判断扩量、调频、换人群或结束活动 | 批准记录、经验库和下一轮假设 | 退款投诉未进入护栏 |

把 目标与人群、触达与频次、行为响应、交易与售后、增量评估、成本与价值、复盘与停止 串起来后可以看出，营销活动分析不是一个孤立字段，而是一条会跨系统、跨岗位、跨时间的证据链。流程图上每一段都应标出输入、输出、状态、时间戳、责任人和异常出口。只要其中一段只能靠口头解释，后续的统计、追责和自动化就会失去基础。

一个合格的需求说明应该写成：

> 在【授权数据范围】和【观察窗口】内，围绕“营销活动分析”的【活动】，按【campaign_id、channel、creative_id、audience_segment】比较【有效触达率】及其【增量转化率】，定位一个可干预节点；行动后同时观察主指标、样本量和护栏，任何高风险异常先阻断再调查。

## 3. 营销活动分析的数据对象与系统契约

| 数据对象 | 建议主键 | 一行代表什么 | 不允许混淆 |
| --- | --- | --- | --- |
| 活动 | `campaign_id` | 一个有明确目标、时间和预算的营销项目 | 对象身份与业务事件 |
| 目标人群 | `audience_id` | 按规则计算且在生效时点冻结的人群集合 | 事件、状态快照和结果粒度 |
| 投放触点 | `touchpoint_id` | 一次渠道与素材在特定版位的投放 | 事件、状态快照和结果粒度 |
| 触达回执 | `delivery_id` | 目标对象实际收到或看到曝光的记录 | 事件、状态快照和结果粒度 |
| 响应事件 | `response_id` | 点击、领券、访问、咨询等行为 | 事件、状态快照和结果粒度 |
| 归因订单 | `attributed_order_id` | 按既定规则关联到触点的订单及其售后状态 | 事件、状态快照和结果粒度 |

对象表不是把所有字段塞进一张宽表。事件、状态快照和结果表应该分别保留粒度，再通过稳定主键与版本建立关联。尤其要避免三个常见混算：把一次业务事件算成多个对象、把每日快照相加当事件总量、把最新状态覆盖历史状态。

本主题的数据契约至少应包含：

- `delivery_id` 的唯一性规则、生成方式和跨系统映射。
- `delivered_at` 的业务含义、时区、迟到和补录规则。
- `response_status` 的完整状态集合，以及删除、撤销、冻结和失效的表示方法。
- 控制对象 `marketing_cost_ledger.cost_entry_id` 与主对象的关系。
- 每次口径、规则、模型或源版本变化的影响范围和下游通知对象。
- 敏感字段、允许用途、访问角色、导出限制和审计保留时间。

## 4. 营销活动分析的指标、样本与验收口径

| 指标 | 公式或定义 | 口径提醒 |
| --- | --- | --- |
| 有效触达率 | 有效触达人数 / 目标人群人数 | 发送成功不等于可见或有效触达 |
| 增量转化率 | 处理组转化率 - 有效对照组转化率 | 需报告置信区间和样本量 |
| 单位增量转化成本 | 活动总成本 / 估计增量转化数 | 退款、作弊和重复订单要回冲 |
| 频次超限率 | 超过频次上限的触达数 / 有效触达数 | 目标是零，并区分设备与身份 |
| 售后恶化率 | 活动归因订单退款退货投诉率 - 对照基线 | 必须用同窗口和同商品结构比较 |

指标字典至少写到“任何人都能按同一份数据复跑”的程度：中文名、业务定义、公式、分子、分母、事实粒度、时间字段、对象范围、排除项、版本、负责人和验收样例，一个都不能少。比例指标必须同时展示分子、分母和样本量；金额或数量必须做守恒；状态指标必须能回到事件时间线。

对于“营销活动分析”，建议把观察分成三层：

| 层次 | 看什么 | 不能替代什么 |
| --- | --- | --- |
| 业务结果 | 有效触达率、增量转化率 | 不能替代过程证据和个案回查 |
| 过程护栏 | 单位增量转化成本、频次超限率、售后恶化率 | 不能因为护栏暂时正常就跳过异常调查 |
| 数据证据 | 主键、时间、状态、版本、来源目标对账 | 不能只看任务成功或报表能打开 |

## 5. 营销活动分析：七个真实工作场景

以下七组场景均为公开方法结合常见工作流程构造的“脱敏复合示例”，不对应任何单一企业、患者、客户或雇员事实。场景的目的，是展示如何从现象走到证据、行动和验收，而不是虚构经营成果。

### 1. 全站订单都算活动成果

**现场。** 首页横幅上线当天订单增长，活动报告直接归因全部订单。

**怎么查。** 检查曝光资格、活动参数、优惠凭证和自然访问，发现大多数订单来自原本高意向用户。

**怎么处理。** 设置曝光组和未曝光对照组；区分直接响应与自然转化；结果同时报告归因订单和增量估计。

**验收结论。** 活动归因回答谁接触过，增量回答活动改变了什么。两者不能混用。

### 2. 优惠券重复领取抬高转化

**现场。** 券领取量很高，但支付订单和复购没有增长。

**怎么查。** 关联账号、设备、支付、收货地址和领取规则，发现小规模批量领取。

**怎么处理。** 资格规则冻结在活动时点；按身份、设备和支付建立风险分层；高风险领取先冻结权益，保留申诉。

**验收结论。** 反作弊要精确到权益动作，不能用强规则误伤正常家庭或企业账号。

### 3. 多渠道同时投放无法判断预算效果

**现场。** 品牌、信息流和私域同一周上线，总转化增长但渠道互相抢功。

**怎么查。** 检查各渠道时间、受众重叠和触点路径，发现同一批用户多渠道被触达且预算同时变化。

**怎么处理。** 采用地理或用户级对照；错开重大变量；对重叠人群单独建模；预算按边际增量而不是最后点击分配。

**验收结论。** 最后点击会奖励最靠近成交的渠道，却忽略真正推动认知和意向的触点。

### 4. 活动提升短期订单却拉高退款

**现场。** 活动期间支付增长，三周后退款和投诉明显上升。

**怎么查。** 按素材、优惠力度、商品、用户历史和物流时效比较，发现夸大承诺吸引错位人群。

**怎么处理。** 暂停高风险素材；调整人群和预期表达；以净收入、退款和投诉作为停止规则；重新设计小流量实验。

**验收结论。** 营销指标必须延伸到售后和长期价值，支付不是最终收益。

### 5. 频次过高造成用户疲劳

**现场。** 同用户一天多次看到活动，短期点击上升，随后屏蔽和取消订阅增加。

**怎么查。** 按身份合并跨渠道曝光，检查频次上限执行和素材重复度。

**怎么处理。** 按用户设置跨渠道统一频次；对非活跃和高风险人群主动降频；疲劳护栏触发时停止后续投放。

**验收结论。** 渠道各自限额不等于用户级限频，必须按人统一管理。

### 6. 预算集中在高响应人群导致边际收益下降

**现场。** 多次投放同一高意向人群，早期 ROI 高，后来逐步下降。

**怎么查。** 按曝光次数、历史购买、饱和度和增量成本分层，发现重复触达边际收益快速降低。

**怎么处理。** 使用预算曲线和饱和分析；把增量成本低的人群放在前面；给控制组保留自然转化证据。

**验收结论。** 平均 ROI 会掩盖边际变化。预算决策要看下一单位投入带来什么。

### 7. 活动结束用户价值迅速回落

**现场。** 新客首单增长，但 30 天复购低于自然新客。

**怎么查。** 比较用户来源、首购商品、优惠深度、体验和售后，判断是否吸引一次优惠型人群。

**怎么处理。** 将 30/90 天复购、毛利和投诉纳入验收；调整优惠门槛和商品匹配；不把首单 ROI 当作全部价值。

**验收结论。** 活动目标是业务增量而不是领券次数。长期价值和售后必须进入护栏。

七个场景可以归成一条共同判断顺序：先确认对象和时间，再确认状态和版本；然后做总量、结构和明细三层对账；最后才讨论策略、模型或工具。若一条结论不能指出对应的原始记录、责任人和行动出口，就只能算观察，不能作为生产结论。

## 6. 营销活动分析的第一段 SQL：重建业务链路

下面的 SQL 用于说明对象、时间、状态、版本和分层口径如何进入同一条可复查路径。表名和部分字段是通用示例，落地时应映射到企业数据字典；SQL 方言也需按实际引擎调整。

```sql
-- 营销活动分析：按业务对象重建链路，避免事件、快照和结果混算
WITH ranked_delivery_id AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY delivery_id
      ORDER BY updated_at DESC
    ) AS version_no
  FROM marketing_campaign_response
  WHERE delivered_at >= TIMESTAMP '{start_time}'
    AND delivered_at <  TIMESTAMP '{end_time}'
    AND response_status NOT IN ('deleted', 'test')
),
valid_rows AS (
  SELECT
    delivery_id,
    campaign_id,
    channel,
    creative_id,
    audience_segment,
    delivered_at,
    response_status,
    ingested_at
  FROM ranked_delivery_id
  WHERE version_no = 1
)
SELECT
  campaign_id, channel, creative_id, audience_segment,
  COUNT(DISTINCT delivery_id) AS object_cnt,
  COUNT(DISTINCT CASE WHEN converted THEN user_key END) AS numerator_value,
  COUNT(DISTINCT user_key) AS denominator_value,
  CAST(COUNT(DISTINCT CASE WHEN converted THEN user_key END) AS DOUBLE PRECISION)
    / NULLIF(COUNT(DISTINCT user_key), 0) AS metric_value,
  MIN(delivered_at) AS first_event_at,
  MAX(delivered_at) AS last_event_at
FROM valid_rows
GROUP BY campaign_id, channel, creative_id, audience_segment
ORDER BY metric_value DESC, object_cnt DESC;
```

执行后至少回答六个问题：

- 同一对象是否因为多源回传产生多版本，版本保留是否符合业务要求？
- 业务时间与入仓时间是否分开，补录和迟到数据是否进入正确分区？
- 分子分母是否来自同一对象范围和同一统计窗口？
- 维度使用的是事件当时值还是当前值，跨期比较是否一致？
- 删除、撤销、冻结和测试数据是否按规则处理？
- 分组结果能否在明细中抽样复现？

## 7. 营销活动分析的第二段 SQL：源、控制和结果三方对账

```sql
-- 营销活动分析：源对象、控制对象和结果对象三方对账
WITH population AS (
  SELECT
    delivery_id,
    delivered_at,
    response_status
  FROM marketing_campaign_response
  WHERE delivered_at >= TIMESTAMP '{start_time}'
    AND delivered_at <  TIMESTAMP '{end_time}'
),
control AS (
  SELECT
    delivery_id,
    SUM(allocated_cost) AS control_value,
    COUNT(DISTINCT cost_entry_id) AS control_cnt,
    MAX(updated_at) AS control_updated_at
  FROM marketing_cost_ledger
  WHERE updated_at >= TIMESTAMP '{start_time}'
  GROUP BY delivery_id
),
result AS (
  SELECT
    delivery_id,
    COUNT(*) AS result_cnt,
    MAX(calculated_at) AS calculated_at
  FROM mart_delivery_id
  WHERE business_date BETWEEN DATE '{start_date}' AND DATE '{end_date}'
  GROUP BY delivery_id
)
SELECT
  COALESCE(p.delivery_id, c.delivery_id, r.delivery_id) AS object_key,
  CASE
    WHEN p.delivery_id IS NULL THEN 'source_missing'
    WHEN c.delivery_id IS NULL THEN 'control_missing'
    WHEN r.delivery_id IS NULL THEN 'result_missing'
    WHEN ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0 THEN 'count_or_value_gap'
    ELSE 'matched'
  END AS reconciliation_status,
  p.response_status,
  c.control_value,
  c.control_cnt,
  r.result_cnt,
  c.control_updated_at,
  r.calculated_at
FROM population p
FULL OUTER JOIN control c ON p.delivery_id = c.delivery_id
FULL OUTER JOIN result r ON COALESCE(p.delivery_id, c.delivery_id) = r.delivery_id
WHERE p.delivery_id IS NULL
   OR c.delivery_id IS NULL
   OR r.delivery_id IS NULL
   OR ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0;
```

这段查询故意不使用“总数相差小于某个随意百分比就算通过”。它先找出缺失对象和状态差异，再检查控制值与结果值。对于营销活动分析，数量、金额、时长或状态任意一项无法解释，都不能用“业务波动”代替排查。

对账结果建议分成四类处理：

1. **阻断**：对象缺失、关键时间为空、状态非法、金额或数量不守恒、权限越界。
2. **严重**：比例或总量显著偏离基线，且无法由已确认的对象结构变化解释。
3. **观察**：小范围波动但来源、样本和趋势可控，进入责任人和观察窗口。
4. **探索**：只有弱信号或假设，不进入正式结论，更不直接触发业务处罚。

## 8. 营销活动分析的 Python 发布门禁与指标护栏

第一段代码把发布条件写成可执行对象，避免“检查过了”只存在聊天记录里：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class DeliveryIdBatch:
    batch_id: str
    source_rows: int
    valid_rows: int
    duplicate_keys: int
    missing_required_fields: int
    reconciliation_gap: float

def release_delivery_id(batch: DeliveryIdBatch) -> dict:
    checks = {
        "source_not_empty": batch.source_rows > 0,
        "valid_rows_in_range": 0 <= batch.valid_rows <= batch.source_rows,
        "duplicate_rate_ok": batch.duplicate_keys / max(batch.source_rows, 1) <= 0.001,
        "required_fields_ok": batch.missing_required_fields == 0,
        "reconciliation_ok": abs(batch.reconciliation_gap) <= 0.01,
    }
    return {
        "topic": "营销活动分析",
        "batch_id": batch.batch_id,
        "checks": checks,
        "release_allowed": all(checks.values()),
        "blocking_checks": [name for name, passed in checks.items() if not passed],
    }
```

第二段代码演示如何为比例类结果附带样本证据和小样本下界。它不是替代统计学家的模型，而是防止把少量偶然样本直接包装成稳定结论：

```python
from dataclasses import dataclass
from math import sqrt

@dataclass(frozen=True)
class DeliveryIdObservation:
    object_id: str
    numerator: float
    denominator: float
    sample_size: int
    scope_version: str

def calculate_delivery_id(rows: list[DeliveryIdObservation]) -> list[dict]:
    output = []
    for row in rows:
        value = row.numerator / row.denominator if row.denominator > 0 else None
        # 小样本用 Wilson 下界做护栏，不把偶然的高比例直接当稳定结果。
        z = 1.96
        p = value or 0
        n = max(row.sample_size, 1)
        center = p + z * z / (2 * n)
        margin = z * sqrt((p * (1 - p) + z * z / (4 * n)) / n)
        lower = max(0, (center - margin) / (1 + z * z / n))
        output.append({
            "object_id": row.object_id,
            "metric": "有效触达率",
            "value": value,
            "lower_bound": lower if value is not None else None,
            "sample_size": row.sample_size,
            "scope_version": row.scope_version,
            "caution": "发送成功不等于可见或有效触达",
        })
    return output
```

真正上线时还要补充参数配置、日志、血缘、告警级别、重跑幂等、异常样本保存和审批记录。代码通过不代表业务通过；自动检查只能证明已经定义的规则没有被违反，无法证明规则本身一定正确。

## 9. 营销活动分析的失败反例与上线验收

| 风险信号 | 错误做法 | 必须补齐的证据 | 发布或行动规则 |
| --- | --- | --- | --- |
| 活动期订单全归因 | 没有对照和触点规则 | 人群、曝光、触点路径和基线 | 归因与增量分开报告 |
| 渠道重复抢功 | 预算按最后点击分配 | 重叠受众、路径和边际实验 | 按增量与边际成本决策 |
| 只看到支付 | 退款投诉未进入护栏 | 同商品同窗口售后比较 | 净收入不足则停止扩量 |
| 身份限频失效 | 每个渠道单独限额 | 跨渠道统一身份和频次日志 | 按用户设置总频次 |

上线验收不应只有一句“报表正常”。建议按下面四层验收：

| 验收对象 | 结构要求 | 测试样本 | 结果证据 |
| --- | --- | --- | --- |
| 活动 | `campaign_id` 能唯一定位一个有明确目标、时间和预算的营销项目 | 正常、重复、缺失、撤销与跨期样本 | 有效触达率可回到原始对象 |
| 目标人群 | `audience_id` 能唯一定位按规则计算且在生效时点冻结的人群集合 | 正常、重复、缺失、撤销与跨期样本 | 增量转化率可回到原始对象 |
| 投放触点 | `touchpoint_id` 能唯一定位一次渠道与素材在特定版位的投放 | 正常、重复、缺失、撤销与跨期样本 | 单位增量转化成本可回到原始对象 |
| 触达回执 | `delivery_id` 能唯一定位目标对象实际收到或看到曝光的记录 | 正常、重复、缺失、撤销与跨期样本 | 频次超限率可回到原始对象 |
| 响应事件 | `response_id` 能唯一定位点击、领券、访问、咨询等行为 | 正常、重复、缺失、撤销与跨期样本 | 售后恶化率可回到原始对象 |
| 归因订单 | `attributed_order_id` 能唯一定位按既定规则关联到触点的订单及其售后状态 | 正常、重复、缺失、撤销与跨期样本 | 有效触达率可回到原始对象 |

还应为每一次发布保留一组固定回归样本：正常对象、边界状态、重复记录、缺失字段、撤销或退款、跨期、权限拒绝和失败恢复。回归样本不是演示数据，而是以后每次改规则都能重复执行的质量资产。

## 10. 营销活动分析的 30 天落地与复盘

| 阶段 | 主要交付 | 通过条件 |
| --- | --- | --- |
| 第 1 周：定义 | 对象、流程、状态、指标、排除项和责任矩阵 | 业务、数据、安全或质量负责人对同一口径签字 |
| 第 2 周：打通 | 源字段、主键、时间、版本、控制对象和失败样本 | 正常与异常样本都能回到原始记录 |
| 第 3 周：验证 | 总量对账、分层对账、抽样回查、权限测试、回滚演练 | 阻断问题清零，严重问题有责任人与期限 |
| 第 4 周：发布 | 灰度、SLO、监控、行动清单、停止条件和复盘模板 | 使用者在真实场景中完成一次闭环行动 |

如果必须用 90 秒说明“营销活动分析”是否做对，可以按这个顺序自测：

1. 一行数据代表什么，主键是什么，哪些对象绝不能混在同一粒度？
2. 业务发生、数据可见、计算完成和行动确认分别在哪个时间点？
3. 本主题最重要的两个主指标、三个护栏和最小样本量是什么？
4. 一个异常出现时，先从原始记录、链路版本还是业务动作开始查？
5. 哪类错误必须阻断发布或停止使用，谁有权批准例外？
6. 上线后由谁在多长时间内观察，什么条件下回滚或结束？

> [!check] 完成标准
> 当另一位数据同事不看聊天记录，只根据口径卡、回归样本和代码就能复跑同一结果；当业务负责人能指出一个异常对应的原始对象、处置动作和复核证据；当系统能够阻止未授权或状态非法的数据进入下游，这篇“营销活动分析”才算真正落到工作里。
