# 用户行为分析

> [!abstract] 产品行为与用户旅程实战手册
> 用户行为分析不是把点击做成漏斗，而是用事件字典、用户身份、会话、页面和业务结果重建用户在一段时间内的行为旅程。分析结论必须区分观察、假设和因果，并保护行为数据中的身份与隐私边界。

## 1. 用户行为分析：定义、适用边界与决策出口

用户行为分析不是把点击做成漏斗，而是用事件字典、用户身份、会话、页面和业务结果重建用户在一段时间内的行为旅程。分析结论必须区分观察、假设和因果，并保护行为数据中的身份与隐私边界。

**本篇的适用边界。** 本篇覆盖产品、内容和交易场景中的行为事件、会话、漏斗、留存、路径与异常识别；不把曝光日志等同于用户意图，也不监控用户设备之外的私人活动。

**最常见的错误替代。** 不能用页面浏览量代表用户价值，不能忽略同一用户的跨设备身份，也不能把埋点缺失解释成用户流失。

**最终决策。** 产品、数据和运营团队要判断：哪个行为节点造成阻塞，变化来自人群结构、功能体验还是埋点质量，下一步做何实验，以及哪些敏感行为不应采集。 因此，这篇内容不从“应该建哪张表”开始，而从业务动作、责任人和失败后果开始。只有先确定谁在什么时点做出什么决定，字段、SQL、看板和模型才有明确用途。

围绕“用户行为分析”，工作中至少要区分四类问题：

1. **身份问题**：对象是谁，主键能否跨系统稳定关联，合并、拆分、撤销后历史是否还看得见。
2. **时间问题**：业务发生、状态生效、数据入仓、计算完成和人员行动分别发生在哪一刻。
3. **状态问题**：当前状态是一段事件、一张快照还是最终结果，空值代表未发生、未采集还是已删除。
4. **责任问题**：谁确认口径，谁处理异常，谁有权放行或停止，谁在观察期后复盘。

## 2. 用户行为分析的完整业务流程

| 环节 | 要做的事 | 最小证据 | 失败后先查什么 |
| --- | --- | --- | --- |
| 事件字典 | 定义事件、属性、触发时机、版本和责任人 | 字段说明、样例、重复与缺失规则 | 改触发点后历史直接拼接 |
| 身份与会话 | 区分匿名、登录、设备和家庭共用关系 | 身份映射、会话切分和冲突样本 | 仅按手机号合并登录与匿名行为 |
| 旅程重建 | 按业务时间和事件顺序还原曝光、访问、动作与结果 | 事件序列、页面上下文和回传延迟 | 自动刷新计入活跃用户 |
| 指标与分层 | 定义漏斗、留存、频次、路径和护栏 | 分子分母、观察窗口和样本人群 | 采集广泛字段备用 |
| 异常与假设 | 区分采集、版本、结构变化和真实行为 | 质量画像、分组贡献和会话回查 | 改触发点后历史直接拼接 |
| 实验与验证 | 用对照、灰度和准实验检验行动增量 | 分组、样本量、主指标和长期护栏 | 仅按手机号合并登录与匿名行为 |
| 隐私与治理 | 按目的最小化采集、使用、保留和导出 | 同意、权限、脱敏和审计记录 | 自动刷新计入活跃用户 |

把 事件字典、身份与会话、旅程重建、指标与分层、异常与假设、实验与验证、隐私与治理 串起来后可以看出，用户行为分析不是一个孤立字段，而是一条会跨系统、跨岗位、跨时间的证据链。流程图上每一段都应标出输入、输出、状态、时间戳、责任人和异常出口。只要其中一段只能靠口头解释，后续的统计、追责和自动化就会失去基础。

一个合格的需求说明应该写成：

> 在【授权数据范围】和【观察窗口】内，围绕“用户行为分析”的【匿名设备】，按【event_name、event_version、platform、entry_channel】比较【有效访问率】及其【步骤转化率】，定位一个可干预节点；行动后同时观察主指标、样本量和护栏，任何高风险异常先阻断再调查。

## 3. 用户行为分析的数据对象与系统契约

| 数据对象 | 建议主键 | 一行代表什么 | 不允许混淆 |
| --- | --- | --- | --- |
| 匿名设备 | `anonymous_device_id` | 未登录状态下可观察的设备或浏览器实例 | 对象身份与业务事件 |
| 用户身份 | `user_id` | 经授权确认的自然人或产品账户 | 事件、状态快照和结果粒度 |
| 行为事件 | `behavior_event_id` | 一次有明确触发规则的曝光、点击、浏览或提交 | 事件、状态快照和结果粒度 |
| 会话 | `session_id` | 在规则下连续发生的一组交互 | 事件、状态快照和结果粒度 |
| 业务流程实例 | `journey_id` | 围绕一个目标形成的行为链 | 事件、状态快照和结果粒度 |
| 实验分配 | `experiment_assignment_id` | 用户或对象进入实验组与观察组的关系 | 事件、状态快照和结果粒度 |

对象表不是把所有字段塞进一张宽表。事件、状态快照和结果表应该分别保留粒度，再通过稳定主键与版本建立关联。尤其要避免三个常见混算：把一次业务事件算成多个对象、把每日快照相加当事件总量、把最新状态覆盖历史状态。

本主题的数据契约至少应包含：

- `behavior_event_id` 的唯一性规则、生成方式和跨系统映射。
- `event_time` 的业务含义、时区、迟到和补录规则。
- `event_status` 的完整状态集合，以及删除、撤销、冻结和失效的表示方法。
- 控制对象 `product_session.session_id` 与主对象的关系。
- 每次口径、规则、模型或源版本变化的影响范围和下游通知对象。
- 敏感字段、允许用途、访问角色、导出限制和审计保留时间。

## 4. 用户行为分析的指标、样本与验收口径

| 指标 | 公式或定义 | 口径提醒 |
| --- | --- | --- |
| 有效访问率 | 发生至少一个有效内容或功能互动的会话数 / 有效进入会话数 | 自动跳转和失败页不能算有效互动 |
| 步骤转化率 | 完成目标步骤且满足顺序的对象数 / 到达起始步骤的有效对象数 | 重复事件按业务键去重 |
| N 日留存率 | 首日后第 N 日仍有有效行为的对象数 / 首日新增有效对象数 | 设备、账号和回流必须分开 |
| 路径异常率 | 出现越级、逆序或缺失前置步骤的旅程数 / 有效旅程数 | 先确认事件定义版本 |
| 隐私暴露事件数 | 未授权采集、导出或访问的行为数据事件数 | 目标是零，任何发生都要复盘 |

指标字典至少写到“任何人都能按同一份数据复跑”的程度：中文名、业务定义、公式、分子、分母、事实粒度、时间字段、对象范围、排除项、版本、负责人和验收样例，一个都不能少。比例指标必须同时展示分子、分母和样本量；金额或数量必须做守恒；状态指标必须能回到事件时间线。

对于“用户行为分析”，建议把观察分成三层：

| 层次 | 看什么 | 不能替代什么 |
| --- | --- | --- |
| 业务结果 | 有效访问率、步骤转化率 | 不能替代过程证据和个案回查 |
| 过程护栏 | N 日留存率、路径异常率、隐私暴露事件数 | 不能因为护栏暂时正常就跳过异常调查 |
| 数据证据 | 主键、时间、状态、版本、来源目标对账 | 不能只看任务成功或报表能打开 |

## 5. 用户行为分析：七个真实工作场景

以下七组场景均为公开方法结合常见工作流程构造的“脱敏复合示例”，不对应任何单一企业、患者、客户或雇员事实。场景的目的，是展示如何从现象走到证据、行动和验收，而不是虚构经营成果。

### 1. 新增用户下降但老用户活跃稳定

**现场。** 产品周报显示新增访问连续下降，运营准备加大投放。

**怎么查。** 检查埋点版本、入口渠道和匿名身份，发现新版本首屏事件延迟触发且部分页面未上报。

**怎么处理。** 先修复事件版本和触发时机；对缺失页面设为不可比较；按渠道检查真实注册与内容消费，再决定是否加投放。

**验收结论。** 行为指标异常的第一步是验证数据产生过程，不是立即解释用户心理。

### 2. 跨设备登录导致留存被低估

**现场。** 用户手机和电脑切换后被视为两个新用户，次日留存偏低。

**怎么查。** 比较匿名设备、登录账号、合并时间和设备共用情况，发现登录后没有回填历史行为。

**怎么处理。** 允许在获得授权后把登录前会话与账号关联；保留原始匿名关系；对家庭共用设备和无法确认的映射不强行合并。

**验收结论。** 身份合并提高可观测性，也会扩大隐私风险。合并规则必须可解释、可撤回。

### 3. 漏斗中间步骤下降来自版本结构变化

**现场。** 商品详情到支付的转化突然下降，页面点击也同步下降。

**怎么查。** 按客户端版本、页面结构和按钮曝光拆分，发现新版把按钮拆成两个事件但旧漏斗只识别其中一个。

**怎么处理。** 为事件建立语义版本和兼容映射；新旧版本并行期分别计算；回归样本覆盖主路径和异常路径。

**验收结论。** 埋点改名不是简单技术变更。指标历史必须先评估断点。

### 4. 高频曝光把活跃率抬高

**现场。** 推荐模块自动刷新后，大量用户被动曝光，活跃率明显上升。

**怎么查。** 区分自动曝光、可见曝光、点击、停留和后续消费，检查频次与用户分层。

**怎么处理。** 活跃定义改为有效互动；曝光只作为触达；对自动刷新设置频次上限，并同时观察停留、投诉和消费。

**验收结论。** 系统展示不等于用户行为。指标必须尽量接近真实意图。

### 5. 用户路径分析得到看似热门但无价值路径

**现场。** 路径图显示大量用户在多个页面来回跳转，团队准备复制该路径。

**怎么查。** 回查会话质量、错误页、重复提交和用户反馈，发现频繁跳转来自加载失败。

**怎么处理。** 把错误、重试和返回标记为路径状态；区分成功路径与故障路径；先修复稳定性，再讨论导航优化。

**验收结论。** 路径频次高不代表路径有价值，可能是用户受困。

### 6. A/B 实验只提升点击却增加投诉

**现场。** 新版引导按钮点击率提升，团队计划全量发布。

**怎么查。** 检查实验分配、样本比例、主指标、停留时间、投诉和取消率，发现诱导文案让用户误入设置页。

**怎么处理。** 保持原版本；修改文案和信息层级；以任务完成和投诉为护栏重做实验；显著点击不能覆盖体验损害。

**验收结论。** 点击是过程指标。产品决策必须同时看任务完成、长期留存和负面反馈。

### 7. 行为数据被过度采集

**现场。** 为分析推荐效果，客户端计划采集剪贴板和设备应用列表。

**怎么查。** 评审分析目的、必要性、同意文本、存储期限和访问角色，确认这些数据与核心问题不成比例。

**怎么处理。** 改用页面内曝光、点击和明确反馈；敏感数据默认不采集；新增字段需隐私评审和用途登记，导出受限。

**验收结论。** 能采集不等于应该采集。行为分析必须遵守最小必要原则。

七个场景可以归成一条共同判断顺序：先确认对象和时间，再确认状态和版本；然后做总量、结构和明细三层对账；最后才讨论策略、模型或工具。若一条结论不能指出对应的原始记录、责任人和行动出口，就只能算观察，不能作为生产结论。

## 6. 用户行为分析的第一段 SQL：重建业务链路

下面的 SQL 用于说明对象、时间、状态、版本和分层口径如何进入同一条可复查路径。表名和部分字段是通用示例，落地时应映射到企业数据字典；SQL 方言也需按实际引擎调整。

```sql
-- 用户行为分析：按业务对象重建链路，避免事件、快照和结果混算
WITH ranked_behavior_event_id AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY behavior_event_id
      ORDER BY updated_at DESC
    ) AS version_no
  FROM product_behavior_event
  WHERE event_time >= TIMESTAMP '{start_time}'
    AND event_time <  TIMESTAMP '{end_time}'
    AND event_status NOT IN ('deleted', 'test')
),
valid_rows AS (
  SELECT
    behavior_event_id,
    event_name,
    event_version,
    platform,
    entry_channel,
    event_time,
    event_status,
    ingested_at
  FROM ranked_behavior_event_id
  WHERE version_no = 1
)
SELECT
  event_name, event_version, platform, entry_channel,
  COUNT(DISTINCT behavior_event_id) AS object_cnt,
  COUNT(DISTINCT CASE WHEN event_status = 'valid' THEN user_key END) AS numerator_value,
  COUNT(DISTINCT CASE WHEN is_eligible THEN user_key END) AS denominator_value,
  CAST(COUNT(DISTINCT CASE WHEN event_status = 'valid' THEN user_key END) AS DOUBLE PRECISION)
    / NULLIF(COUNT(DISTINCT CASE WHEN is_eligible THEN user_key END), 0) AS metric_value,
  MIN(event_time) AS first_event_at,
  MAX(event_time) AS last_event_at
FROM valid_rows
GROUP BY event_name, event_version, platform, entry_channel
ORDER BY metric_value DESC, object_cnt DESC;
```

执行后至少回答六个问题：

- 同一对象是否因为多源回传产生多版本，版本保留是否符合业务要求？
- 业务时间与入仓时间是否分开，补录和迟到数据是否进入正确分区？
- 分子分母是否来自同一对象范围和同一统计窗口？
- 维度使用的是事件当时值还是当前值，跨期比较是否一致？
- 删除、撤销、冻结和测试数据是否按规则处理？
- 分组结果能否在明细中抽样复现？

## 7. 用户行为分析的第二段 SQL：源、控制和结果三方对账

```sql
-- 用户行为分析：源对象、控制对象和结果对象三方对账
WITH population AS (
  SELECT
    behavior_event_id,
    event_time,
    event_status
  FROM product_behavior_event
  WHERE event_time >= TIMESTAMP '{start_time}'
    AND event_time <  TIMESTAMP '{end_time}'
),
control AS (
  SELECT
    behavior_event_id,
    SUM(valid_event_count) AS control_value,
    COUNT(DISTINCT session_id) AS control_cnt,
    MAX(updated_at) AS control_updated_at
  FROM product_session
  WHERE updated_at >= TIMESTAMP '{start_time}'
  GROUP BY behavior_event_id
),
result AS (
  SELECT
    behavior_event_id,
    COUNT(*) AS result_cnt,
    MAX(calculated_at) AS calculated_at
  FROM mart_behavior_event_id
  WHERE business_date BETWEEN DATE '{start_date}' AND DATE '{end_date}'
  GROUP BY behavior_event_id
)
SELECT
  COALESCE(p.behavior_event_id, c.behavior_event_id, r.behavior_event_id) AS object_key,
  CASE
    WHEN p.behavior_event_id IS NULL THEN 'source_missing'
    WHEN c.behavior_event_id IS NULL THEN 'control_missing'
    WHEN r.behavior_event_id IS NULL THEN 'result_missing'
    WHEN ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0 THEN 'count_or_value_gap'
    ELSE 'matched'
  END AS reconciliation_status,
  p.event_status,
  c.control_value,
  c.control_cnt,
  r.result_cnt,
  c.control_updated_at,
  r.calculated_at
FROM population p
FULL OUTER JOIN control c ON p.behavior_event_id = c.behavior_event_id
FULL OUTER JOIN result r ON COALESCE(p.behavior_event_id, c.behavior_event_id) = r.behavior_event_id
WHERE p.behavior_event_id IS NULL
   OR c.behavior_event_id IS NULL
   OR r.behavior_event_id IS NULL
   OR ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0;
```

这段查询故意不使用“总数相差小于某个随意百分比就算通过”。它先找出缺失对象和状态差异，再检查控制值与结果值。对于用户行为分析，数量、金额、时长或状态任意一项无法解释，都不能用“业务波动”代替排查。

对账结果建议分成四类处理：

1. **阻断**：对象缺失、关键时间为空、状态非法、金额或数量不守恒、权限越界。
2. **严重**：比例或总量显著偏离基线，且无法由已确认的对象结构变化解释。
3. **观察**：小范围波动但来源、样本和趋势可控，进入责任人和观察窗口。
4. **探索**：只有弱信号或假设，不进入正式结论，更不直接触发业务处罚。

## 8. 用户行为分析的 Python 发布门禁与指标护栏

第一段代码把发布条件写成可执行对象，避免“检查过了”只存在聊天记录里：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class BehaviorEventIdBatch:
    batch_id: str
    source_rows: int
    valid_rows: int
    duplicate_keys: int
    missing_required_fields: int
    reconciliation_gap: float

def release_behavior_event_id(batch: BehaviorEventIdBatch) -> dict:
    checks = {
        "source_not_empty": batch.source_rows > 0,
        "valid_rows_in_range": 0 <= batch.valid_rows <= batch.source_rows,
        "duplicate_rate_ok": batch.duplicate_keys / max(batch.source_rows, 1) <= 0.001,
        "required_fields_ok": batch.missing_required_fields == 0,
        "reconciliation_ok": abs(batch.reconciliation_gap) <= 0.01,
    }
    return {
        "topic": "用户行为分析",
        "batch_id": batch.batch_id,
        "checks": checks,
        "release_allowed": all(checks.values()),
        "blocking_checks": [name for name, passed in checks.items() if not passed],
    }
```

第二段代码演示如何为比例类结果附带样本证据和小样本下界。它不是替代统计学家的模型，而是防止把少量偶然样本直接包装成稳定结论：

```python
from dataclasses import dataclass
from math import sqrt

@dataclass(frozen=True)
class BehaviorEventIdObservation:
    object_id: str
    numerator: float
    denominator: float
    sample_size: int
    scope_version: str

def calculate_behavior_event_id(rows: list[BehaviorEventIdObservation]) -> list[dict]:
    output = []
    for row in rows:
        value = row.numerator / row.denominator if row.denominator > 0 else None
        # 小样本用 Wilson 下界做护栏，不把偶然的高比例直接当稳定结果。
        z = 1.96
        p = value or 0
        n = max(row.sample_size, 1)
        center = p + z * z / (2 * n)
        margin = z * sqrt((p * (1 - p) + z * z / (4 * n)) / n)
        lower = max(0, (center - margin) / (1 + z * z / n))
        output.append({
            "object_id": row.object_id,
            "metric": "有效访问率",
            "value": value,
            "lower_bound": lower if value is not None else None,
            "sample_size": row.sample_size,
            "scope_version": row.scope_version,
            "caution": "自动跳转和失败页不能算有效互动",
        })
    return output
```

真正上线时还要补充参数配置、日志、血缘、告警级别、重跑幂等、异常样本保存和审批记录。代码通过不代表业务通过；自动检查只能证明已经定义的规则没有被违反，无法证明规则本身一定正确。

## 9. 用户行为分析的失败反例与上线验收

| 风险信号 | 错误做法 | 必须补齐的证据 | 发布或行动规则 |
| --- | --- | --- | --- |
| 事件定义无版本 | 改触发点后历史直接拼接 | 事件版本、触发规则和兼容映射 | 语义变更必须断点或映射 |
| 身份强行合并 | 仅按手机号合并登录与匿名行为 | 多设备证据、授权和可撤销关系 | 弱标识不直接视为同一人 |
| 曝光等同活跃 | 自动刷新计入活跃用户 | 可见、点击、停留和投诉证据 | 活跃定义靠近真实互动 |
| 隐私目的不清 | 采集广泛字段备用 | 用途、必要性、同意和保留 | 无明确目的不采集 |

上线验收不应只有一句“报表正常”。建议按下面四层验收：

| 验收对象 | 结构要求 | 测试样本 | 结果证据 |
| --- | --- | --- | --- |
| 匿名设备 | `anonymous_device_id` 能唯一定位未登录状态下可观察的设备或浏览器实例 | 正常、重复、缺失、撤销与跨期样本 | 有效访问率可回到原始对象 |
| 用户身份 | `user_id` 能唯一定位经授权确认的自然人或产品账户 | 正常、重复、缺失、撤销与跨期样本 | 步骤转化率可回到原始对象 |
| 行为事件 | `behavior_event_id` 能唯一定位一次有明确触发规则的曝光、点击、浏览或提交 | 正常、重复、缺失、撤销与跨期样本 | N 日留存率可回到原始对象 |
| 会话 | `session_id` 能唯一定位在规则下连续发生的一组交互 | 正常、重复、缺失、撤销与跨期样本 | 路径异常率可回到原始对象 |
| 业务流程实例 | `journey_id` 能唯一定位围绕一个目标形成的行为链 | 正常、重复、缺失、撤销与跨期样本 | 隐私暴露事件数可回到原始对象 |
| 实验分配 | `experiment_assignment_id` 能唯一定位用户或对象进入实验组与观察组的关系 | 正常、重复、缺失、撤销与跨期样本 | 有效访问率可回到原始对象 |

还应为每一次发布保留一组固定回归样本：正常对象、边界状态、重复记录、缺失字段、撤销或退款、跨期、权限拒绝和失败恢复。回归样本不是演示数据，而是以后每次改规则都能重复执行的质量资产。

## 10. 用户行为分析的 30 天落地与复盘

| 阶段 | 主要交付 | 通过条件 |
| --- | --- | --- |
| 第 1 周：定义 | 对象、流程、状态、指标、排除项和责任矩阵 | 业务、数据、安全或质量负责人对同一口径签字 |
| 第 2 周：打通 | 源字段、主键、时间、版本、控制对象和失败样本 | 正常与异常样本都能回到原始记录 |
| 第 3 周：验证 | 总量对账、分层对账、抽样回查、权限测试、回滚演练 | 阻断问题清零，严重问题有责任人与期限 |
| 第 4 周：发布 | 灰度、SLO、监控、行动清单、停止条件和复盘模板 | 使用者在真实场景中完成一次闭环行动 |

如果必须用 90 秒说明“用户行为分析”是否做对，可以按这个顺序自测：

1. 一行数据代表什么，主键是什么，哪些对象绝不能混在同一粒度？
2. 业务发生、数据可见、计算完成和行动确认分别在哪个时间点？
3. 本主题最重要的两个主指标、三个护栏和最小样本量是什么？
4. 一个异常出现时，先从原始记录、链路版本还是业务动作开始查？
5. 哪类错误必须阻断发布或停止使用，谁有权批准例外？
6. 上线后由谁在多长时间内观察，什么条件下回滚或结束？

> [!check] 完成标准
> 当另一位数据同事不看聊天记录，只根据口径卡、回归样本和代码就能复跑同一结果；当业务负责人能指出一个异常对应的原始对象、处置动作和复核证据；当系统能够阻止未授权或状态非法的数据进入下游，这篇“用户行为分析”才算真正落到工作里。
