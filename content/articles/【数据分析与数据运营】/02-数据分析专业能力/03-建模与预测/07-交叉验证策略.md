# 交叉验证策略

> [!abstract] 模型评估与泛化验证实战手册
> 交叉验证策略是根据数据结构和业务使用方式安排训练、验证与测试的方法。随机 K 折不是默认答案；时间序列、用户分组、设备分组、类别不平衡和线上漂移都要求不同的切分方式。

## 1. 交叉验证策略：定义、适用边界与决策出口

交叉验证策略是根据数据结构和业务使用方式安排训练、验证与测试的方法。随机 K 折不是默认答案；时间序列、用户分组、设备分组、类别不平衡和线上漂移都要求不同的切分方式。

**本篇的适用边界。** 本篇讨论表格、行为和业务预测模型中的数据切分、泄漏检查、指标稳定性和上线前验证；不展开所有模型算法，也不把一次交叉验证分数当作生产效果证明。

**最常见的错误替代。** 不能把同一用户或同一时间段的数据同时放在训练和验证中，不能反复使用测试集调参，也不能用随机切分处理明显的时间趋势。

**最终决策。** 建模团队要判断：预测在什么时点、对什么对象、用什么决策阈值使用，哪些切分最接近真实场景，指标波动是否可接受，模型何时需要重新训练或停用。 因此，这篇内容不从“应该建哪张表”开始，而从业务动作、责任人和失败后果开始。只有先确定谁在什么时点做出什么决定，字段、SQL、看板和模型才有明确用途。

围绕“交叉验证策略”，工作中至少要区分四类问题：

1. **身份问题**：对象是谁，主键能否跨系统稳定关联，合并、拆分、撤销后历史是否还看得见。
2. **时间问题**：业务发生、状态生效、数据入仓、计算完成和人员行动分别发生在哪一刻。
3. **状态问题**：当前状态是一段事件、一张快照还是最终结果，空值代表未发生、未采集还是已删除。
4. **责任问题**：谁确认口径，谁处理异常，谁有权放行或停止，谁在观察期后复盘。

## 2. 交叉验证策略的完整业务流程

| 环节 | 要做的事 | 最小证据 | 失败后先查什么 |
| --- | --- | --- | --- |
| 预测用途定义 | 明确预测时点、对象、标签和决策动作 | 场景说明、标签字典和成本矩阵 | 未来信息进入训练 |
| 数据边界检查 | 识别用户、设备、商家、时间和来源依赖 | 实体关系、时间范围和数据血缘 | 同一用户或设备泄漏 |
| 切分方案设计 | 选择时间、分组、分层或嵌套验证 | 切分图、样本量和代表性测试 | 最终分数过度乐观 |
| 泄漏排查 | 检查标签未来信息、重复实体和预处理顺序 | 泄漏用例、特征时间和流水线审查 | 准确率上升但收益下降 |
| 指标与不确定性 | 选择主指标、成本指标和置信区间 | 折间波动、校准和子组表现 | 未来信息进入训练 |
| 最终测试 | 锁住未见测试集并在接近线上条件评估 | 测试集版本、一次性评估和决策记录 | 同一用户或设备泄漏 |
| 上线监控 | 持续观察数据漂移、效果和阈值稳定性 | 监控面板、重训规则和停用条件 | 最终分数过度乐观 |

把 预测用途定义、数据边界检查、切分方案设计、泄漏排查、指标与不确定性、最终测试、上线监控 串起来后可以看出，交叉验证策略不是一个孤立字段，而是一条会跨系统、跨岗位、跨时间的证据链。流程图上每一段都应标出输入、输出、状态、时间戳、责任人和异常出口。只要其中一段只能靠口头解释，后续的统计、追责和自动化就会失去基础。

一个合格的需求说明应该写成：

> 在【授权数据范围】和【观察窗口】内，围绕“交叉验证策略”的【训练样本】，按【model_version、split_strategy、entity_type、test_period】比较【折间主指标标准差】及其【实体泄漏率】，定位一个可干预节点；行动后同时观察主指标、样本量和护栏，任何高风险异常先阻断再调查。

## 3. 交叉验证策略的数据对象与系统契约

| 数据对象 | 建议主键 | 一行代表什么 | 不允许混淆 |
| --- | --- | --- | --- |
| 训练样本 | `training_sample_id` | 在预测时点之前可用于学习的一条对象记录 | 对象身份与业务事件 |
| 验证折 | `validation_fold_id` | 用于模型选择的一段样本边界 | 事件、状态快照和结果粒度 |
| 测试集 | `holdout_test_id` | 在最终决策前不参与调参的独立样本 | 事件、状态快照和结果粒度 |
| 实体分组 | `entity_group_id` | 在切分中必须保持隔离的用户、设备或商家分组 | 事件、状态快照和结果粒度 |
| 模型版本 | `model_version_id` | 包含特征、参数、数据和阈值的一次可复现模型 | 事件、状态快照和结果粒度 |
| 漂移窗口 | `drift_window_id` | 用于比较训练与线上分布的一段时间和对象范围 | 事件、状态快照和结果粒度 |

对象表不是把所有字段塞进一张宽表。事件、状态快照和结果表应该分别保留粒度，再通过稳定主键与版本建立关联。尤其要避免三个常见混算：把一次业务事件算成多个对象、把每日快照相加当事件总量、把最新状态覆盖历史状态。

本主题的数据契约至少应包含：

- `fold_result_id` 的唯一性规则、生成方式和跨系统映射。
- `evaluated_at` 的业务含义、时区、迟到和补录规则。
- `validation_status` 的完整状态集合，以及删除、撤销、冻结和失效的表示方法。
- 控制对象 `model_training_snapshot.training_snapshot_id` 与主对象的关系。
- 每次口径、规则、模型或源版本变化的影响范围和下游通知对象。
- 敏感字段、允许用途、访问角色、导出限制和审计保留时间。

## 4. 交叉验证策略的指标、样本与验收口径

| 指标 | 公式或定义 | 口径提醒 |
| --- | --- | --- |
| 折间主指标标准差 | 各验证折主指标的样本标准差 | 同时报告最小值、最大值和样本量 |
| 实体泄漏率 | 训练与验证共享同一实体的样本对比例 | 目标是零，时间邻近仍需单独检查 |
| 校准误差 | 预测概率与实际发生率的差异 | 按概率区间和重要子组报告 |
| 时间外推下降 | 历史测试主指标 - 时间外测试主指标 | 用于判断趋势和概念漂移 |
| 决策收益稳定性 | 各折按业务成本计算的净收益波动 | 比单纯准确率更接近实际使用 |

指标字典至少写到“任何人都能按同一份数据复跑”的程度：中文名、业务定义、公式、分子、分母、事实粒度、时间字段、对象范围、排除项、版本、负责人和验收样例，一个都不能少。比例指标必须同时展示分子、分母和样本量；金额或数量必须做守恒；状态指标必须能回到事件时间线。

对于“交叉验证策略”，建议把观察分成三层：

| 层次 | 看什么 | 不能替代什么 |
| --- | --- | --- |
| 业务结果 | 折间主指标标准差、实体泄漏率 | 不能替代过程证据和个案回查 |
| 过程护栏 | 校准误差、时间外推下降、决策收益稳定性 | 不能因为护栏暂时正常就跳过异常调查 |
| 数据证据 | 主键、时间、状态、版本、来源目标对账 | 不能只看任务成功或报表能打开 |

## 5. 交叉验证策略：七个真实工作场景

以下七组场景均为公开方法结合常见工作流程构造的“脱敏复合示例”，不对应任何单一企业、患者、客户或雇员事实。场景的目的，是展示如何从现象走到证据、行动和验收，而不是虚构经营成果。

### 1. 随机切分让同一用户同时出现在训练和验证

**现场。** 推荐模型离线 AUC 很高，上线后效果明显下降。

**怎么查。** 按用户分组检查发现同一用户多行行为被分到训练和验证，模型记住用户偏好。

**怎么处理。** 使用 GroupKFold 或时间分组切分；预处理只在训练折拟合；最终测试按上线时间和用户隔离。

**验收结论。** 同一实体的重复记录会造成信息泄漏，离线分数越漂亮越危险。

### 2. 时间序列使用随机 K 折

**现场。** 销量模型随机验证表现稳定，预测未来月份误差很大。

**怎么查。** 检查切分后发现验证包含训练之后的未来促销和趋势信息。

**怎么处理。** 使用滚动时间验证；训练窗口始终早于验证；保留最终未来 holdout；把促销和供应变化放入场景分析。

**验收结论。** 时间序列必须模拟“只能使用过去预测未来”。

### 3. 类别不平衡只看准确率

**现场。** 欺诈识别模型准确率 99%，但几乎抓不到欺诈。

**怎么查。** 比较少数类召回、精确率、PR-AUC 和业务成本，发现多数类主导指标。

**怎么处理。** 使用分层切分和 PR 指标；按调查能力选择阈值；报告每千次误报和漏报成本；保留时间外验证。

**验收结论。** 不平衡场景的准确率会掩盖业务失败，阈值要结合人工处理容量。

### 4. 预处理在切分前完成造成泄漏

**现场。** 缺失值用全量均值填补，模型离线结果略好。

**怎么查。** 审查流水线发现验证集统计量参与训练预处理，且目标编码使用全量标签。

**怎么处理。** 将填补、缩放和目标编码放入只在训练折拟合的 Pipeline；折内完成特征工程；重复材料必须按实体隔离。

**验收结论。** 数据泄漏不只在切分，也常藏在预处理和特征选择里。

### 5. 反复调参消耗测试集

**现场。** 团队根据测试集结果改了几十轮，最终分数被管理层当真。

**怎么查。** 检查实验记录、版本和测试集使用次数，发现测试集已经成为隐式验证集。

**怎么处理。** 固定测试集只在最终批准时使用；模型选择在验证折完成；所有尝试记录在实验管理系统中。

**验收结论。** 测试集用一次是估计，用很多次就变成训练反馈。

### 6. 线上分布漂移但没有停用条件

**现场。** 新渠道用户进入后，模型输入分布变化，效果持续下降。

**怎么查。** 按渠道、时间和特征比较训练与线上 PSI、缺失率和校准，发现新增枚举被错误编码。

**怎么处理。** 建立漂移监控和分级响应；未知类别安全降级；达到阈值触发重评或停用；重训需通过时间外测试。

**验收结论。** 模型不是发布后自动长期有效，上线监控和退出条件同样是验证的一部分。

### 7. 交叉验证很好但业务收益为负

**现场。** 模型准确率提升，按预测排序投放后利润下降。

**怎么查。** 把预测概率、阈值、客单价、成本和人工处理能力带入净收益模拟，发现高概率用户只买低毛利商品。

**怎么处理。** 以净收益和预算约束作为模型选择指标；分人群评估；设置保守阈值并做小流量实验。

**验收结论。** 统计指标不是决策指标。验证必须连接真实动作和成本。

七个场景可以归成一条共同判断顺序：先确认对象和时间，再确认状态和版本；然后做总量、结构和明细三层对账；最后才讨论策略、模型或工具。若一条结论不能指出对应的原始记录、责任人和行动出口，就只能算观察，不能作为生产结论。

## 6. 交叉验证策略的第一段 SQL：重建业务链路

下面的 SQL 用于说明对象、时间、状态、版本和分层口径如何进入同一条可复查路径。表名和部分字段是通用示例，落地时应映射到企业数据字典；SQL 方言也需按实际引擎调整。

```sql
-- 交叉验证策略：按业务对象重建链路，避免事件、快照和结果混算
WITH ranked_fold_result_id AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY fold_result_id
      ORDER BY updated_at DESC
    ) AS version_no
  FROM model_validation_fold_result
  WHERE evaluated_at >= TIMESTAMP '{start_time}'
    AND evaluated_at <  TIMESTAMP '{end_time}'
    AND validation_status NOT IN ('deleted', 'test')
),
valid_rows AS (
  SELECT
    fold_result_id,
    model_version,
    split_strategy,
    entity_type,
    test_period,
    evaluated_at,
    validation_status,
    ingested_at
  FROM ranked_fold_result_id
  WHERE version_no = 1
)
SELECT
  model_version, split_strategy, entity_type, test_period,
  COUNT(DISTINCT fold_result_id) AS object_cnt,
  AVG(primary_metric) AS numerator_value,
  COUNT(DISTINCT validation_fold_id) AS denominator_value,
  CAST(AVG(primary_metric) AS DOUBLE PRECISION)
    / NULLIF(COUNT(DISTINCT validation_fold_id), 0) AS metric_value,
  MIN(evaluated_at) AS first_event_at,
  MAX(evaluated_at) AS last_event_at
FROM valid_rows
GROUP BY model_version, split_strategy, entity_type, test_period
ORDER BY metric_value DESC, object_cnt DESC;
```

执行后至少回答六个问题：

- 同一对象是否因为多源回传产生多版本，版本保留是否符合业务要求？
- 业务时间与入仓时间是否分开，补录和迟到数据是否进入正确分区？
- 分子分母是否来自同一对象范围和同一统计窗口？
- 维度使用的是事件当时值还是当前值，跨期比较是否一致？
- 删除、撤销、冻结和测试数据是否按规则处理？
- 分组结果能否在明细中抽样复现？

## 7. 交叉验证策略的第二段 SQL：源、控制和结果三方对账

```sql
-- 交叉验证策略：源对象、控制对象和结果对象三方对账
WITH population AS (
  SELECT
    fold_result_id,
    evaluated_at,
    validation_status
  FROM model_validation_fold_result
  WHERE evaluated_at >= TIMESTAMP '{start_time}'
    AND evaluated_at <  TIMESTAMP '{end_time}'
),
control AS (
  SELECT
    fold_result_id,
    SUM(training_sample_count) AS control_value,
    COUNT(DISTINCT training_snapshot_id) AS control_cnt,
    MAX(updated_at) AS control_updated_at
  FROM model_training_snapshot
  WHERE updated_at >= TIMESTAMP '{start_time}'
  GROUP BY fold_result_id
),
result AS (
  SELECT
    fold_result_id,
    COUNT(*) AS result_cnt,
    MAX(calculated_at) AS calculated_at
  FROM mart_fold_result_id
  WHERE business_date BETWEEN DATE '{start_date}' AND DATE '{end_date}'
  GROUP BY fold_result_id
)
SELECT
  COALESCE(p.fold_result_id, c.fold_result_id, r.fold_result_id) AS object_key,
  CASE
    WHEN p.fold_result_id IS NULL THEN 'source_missing'
    WHEN c.fold_result_id IS NULL THEN 'control_missing'
    WHEN r.fold_result_id IS NULL THEN 'result_missing'
    WHEN ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0 THEN 'count_or_value_gap'
    ELSE 'matched'
  END AS reconciliation_status,
  p.validation_status,
  c.control_value,
  c.control_cnt,
  r.result_cnt,
  c.control_updated_at,
  r.calculated_at
FROM population p
FULL OUTER JOIN control c ON p.fold_result_id = c.fold_result_id
FULL OUTER JOIN result r ON COALESCE(p.fold_result_id, c.fold_result_id) = r.fold_result_id
WHERE p.fold_result_id IS NULL
   OR c.fold_result_id IS NULL
   OR r.fold_result_id IS NULL
   OR ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0;
```

这段查询故意不使用“总数相差小于某个随意百分比就算通过”。它先找出缺失对象和状态差异，再检查控制值与结果值。对于交叉验证策略，数量、金额、时长或状态任意一项无法解释，都不能用“业务波动”代替排查。

对账结果建议分成四类处理：

1. **阻断**：对象缺失、关键时间为空、状态非法、金额或数量不守恒、权限越界。
2. **严重**：比例或总量显著偏离基线，且无法由已确认的对象结构变化解释。
3. **观察**：小范围波动但来源、样本和趋势可控，进入责任人和观察窗口。
4. **探索**：只有弱信号或假设，不进入正式结论，更不直接触发业务处罚。

## 8. 交叉验证策略的 Python 发布门禁与指标护栏

第一段代码把发布条件写成可执行对象，避免“检查过了”只存在聊天记录里：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class FoldResultIdBatch:
    batch_id: str
    source_rows: int
    valid_rows: int
    duplicate_keys: int
    missing_required_fields: int
    reconciliation_gap: float

def release_fold_result_id(batch: FoldResultIdBatch) -> dict:
    checks = {
        "source_not_empty": batch.source_rows > 0,
        "valid_rows_in_range": 0 <= batch.valid_rows <= batch.source_rows,
        "duplicate_rate_ok": batch.duplicate_keys / max(batch.source_rows, 1) <= 0.001,
        "required_fields_ok": batch.missing_required_fields == 0,
        "reconciliation_ok": abs(batch.reconciliation_gap) <= 0.01,
    }
    return {
        "topic": "交叉验证策略",
        "batch_id": batch.batch_id,
        "checks": checks,
        "release_allowed": all(checks.values()),
        "blocking_checks": [name for name, passed in checks.items() if not passed],
    }
```

第二段代码演示如何为比例类结果附带样本证据和小样本下界。它不是替代统计学家的模型，而是防止把少量偶然样本直接包装成稳定结论：

```python
from dataclasses import dataclass
from math import sqrt

@dataclass(frozen=True)
class FoldResultIdObservation:
    object_id: str
    numerator: float
    denominator: float
    sample_size: int
    scope_version: str

def calculate_fold_result_id(rows: list[FoldResultIdObservation]) -> list[dict]:
    output = []
    for row in rows:
        value = row.numerator / row.denominator if row.denominator > 0 else None
        # 小样本用 Wilson 下界做护栏，不把偶然的高比例直接当稳定结果。
        z = 1.96
        p = value or 0
        n = max(row.sample_size, 1)
        center = p + z * z / (2 * n)
        margin = z * sqrt((p * (1 - p) + z * z / (4 * n)) / n)
        lower = max(0, (center - margin) / (1 + z * z / n))
        output.append({
            "object_id": row.object_id,
            "metric": "折间主指标标准差",
            "value": value,
            "lower_bound": lower if value is not None else None,
            "sample_size": row.sample_size,
            "scope_version": row.scope_version,
            "caution": "同时报告最小值、最大值和样本量",
        })
    return output
```

真正上线时还要补充参数配置、日志、血缘、告警级别、重跑幂等、异常样本保存和审批记录。代码通过不代表业务通过；自动检查只能证明已经定义的规则没有被违反，无法证明规则本身一定正确。

## 9. 交叉验证策略的失败反例与上线验收

| 风险信号 | 错误做法 | 必须补齐的证据 | 发布或行动规则 |
| --- | --- | --- | --- |
| 随机切分时间数据 | 未来信息进入训练 | 时间边界和滚动验证 | 时间序列必须按时间切分 |
| 实体跨折重复 | 同一用户或设备泄漏 | 实体分组和重叠检查 | 分组切分并核查预处理 |
| 测试集反复调参 | 最终分数过度乐观 | 测试次数和版本记录 | 测试集只用于最终评估 |
| 指标脱离成本 | 准确率上升但收益下降 | 混淆矩阵、成本矩阵和净收益 | 以业务决策指标验收 |

上线验收不应只有一句“报表正常”。建议按下面四层验收：

| 验收对象 | 结构要求 | 测试样本 | 结果证据 |
| --- | --- | --- | --- |
| 训练样本 | `training_sample_id` 能唯一定位在预测时点之前可用于学习的一条对象记录 | 正常、重复、缺失、撤销与跨期样本 | 折间主指标标准差可回到原始对象 |
| 验证折 | `validation_fold_id` 能唯一定位用于模型选择的一段样本边界 | 正常、重复、缺失、撤销与跨期样本 | 实体泄漏率可回到原始对象 |
| 测试集 | `holdout_test_id` 能唯一定位在最终决策前不参与调参的独立样本 | 正常、重复、缺失、撤销与跨期样本 | 校准误差可回到原始对象 |
| 实体分组 | `entity_group_id` 能唯一定位在切分中必须保持隔离的用户、设备或商家分组 | 正常、重复、缺失、撤销与跨期样本 | 时间外推下降可回到原始对象 |
| 模型版本 | `model_version_id` 能唯一定位包含特征、参数、数据和阈值的一次可复现模型 | 正常、重复、缺失、撤销与跨期样本 | 决策收益稳定性可回到原始对象 |
| 漂移窗口 | `drift_window_id` 能唯一定位用于比较训练与线上分布的一段时间和对象范围 | 正常、重复、缺失、撤销与跨期样本 | 折间主指标标准差可回到原始对象 |

还应为每一次发布保留一组固定回归样本：正常对象、边界状态、重复记录、缺失字段、撤销或退款、跨期、权限拒绝和失败恢复。回归样本不是演示数据，而是以后每次改规则都能重复执行的质量资产。

## 10. 交叉验证策略的 30 天落地与复盘

| 阶段 | 主要交付 | 通过条件 |
| --- | --- | --- |
| 第 1 周：定义 | 对象、流程、状态、指标、排除项和责任矩阵 | 业务、数据、安全或质量负责人对同一口径签字 |
| 第 2 周：打通 | 源字段、主键、时间、版本、控制对象和失败样本 | 正常与异常样本都能回到原始记录 |
| 第 3 周：验证 | 总量对账、分层对账、抽样回查、权限测试、回滚演练 | 阻断问题清零，严重问题有责任人与期限 |
| 第 4 周：发布 | 灰度、SLO、监控、行动清单、停止条件和复盘模板 | 使用者在真实场景中完成一次闭环行动 |

如果必须用 90 秒说明“交叉验证策略”是否做对，可以按这个顺序自测：

1. 一行数据代表什么，主键是什么，哪些对象绝不能混在同一粒度？
2. 业务发生、数据可见、计算完成和行动确认分别在哪个时间点？
3. 本主题最重要的两个主指标、三个护栏和最小样本量是什么？
4. 一个异常出现时，先从原始记录、链路版本还是业务动作开始查？
5. 哪类错误必须阻断发布或停止使用，谁有权批准例外？
6. 上线后由谁在多长时间内观察，什么条件下回滚或结束？

> [!check] 完成标准
> 当另一位数据同事不看聊天记录，只根据口径卡、回归样本和代码就能复跑同一结果；当业务负责人能指出一个异常对应的原始对象、处置动作和复核证据；当系统能够阻止未授权或状态非法的数据进入下游，这篇“交叉验证策略”才算真正落到工作里。
