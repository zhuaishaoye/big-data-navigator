# 模型可解释性分析

> [!tip] 核心原则
> 如果只记住“模型可解释性分析”的定义，遇到真实数据时仍然很难行动。本文把它拆成五个可检查问题：谁在使用、流程在哪里变化、数据一行代表什么、异常如何发现、上线后用哪个指标验收。每个部分都配一个工作案例或代码片段。

## 1. 从业务任务定义 AI 能力

围绕“模型可解释性分析”，先把任务写成输入、输出、成功标准和失败边界。不要从“上一套模型”或“接一个聊天框”开始。

| 设计项 | 必须回答的问题 | 错误示例 | 更好做法 |
| --- | --- | --- | --- |
| 用户 | 谁使用，谁复核，谁承担后果 | 所有人都能用 | 按角色和权限明确使用边界 |
| 输入 | 文本、表格、图片还是工具调用 | 把所有数据都塞进上下文 | 只提供任务所需且获授权的数据 |
| 输出 | 分类、生成、检索、SQL 还是动作 | 只要求“回答准确” | 定义可检查的输出结构 |
| 成功 | 任务完成、采纳、质量、时延和成本 | 只看离线准确率 | 离线 + 线上 + 人工复核 |
| 失败 | 无答案、拒答、转人工还是回滚 | 失败也生成看似合理内容 | 明确置信阈值和降级路径 |

## 2. 数据、知识库与版本

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 用户 | `user_id` | 业务问题 |
| 过程对象 | 会话 | `session_id` | 指标定义 |
| 过程对象 | 行为事件 | `event_id` | 数据准备 |
| 结果对象 | 订单 | `order_id` | 探索分析 |
| 结果对象 | 策略 | `strategy_id` | 策略设计 |
| 专题分析 | 模型可解释性分析 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

AI 项目的数据治理比传统报表更强调版本和来源。至少记录：

- 数据集和知识文档的来源、授权、时间、负责人和版本。
- 样本标注规则、标注人、抽检结果和争议处理。
- 训练、验证、测试与线上反馈是否隔离。
- 提示词、模型、温度、检索参数和工具权限的版本。
- 输入中的个人信息、商业秘密和敏感字段是否脱敏。

如果“模型可解释性分析”使用 RAG，文档切片应尊重标题、章节、表格和条款结构；如果使用微调，先证明提示词、检索或流程优化不足；如果使用 Agent，先限制工具白名单和最大执行步数。

## 3. 评估：不要只看一个准确率

| 评估层 | 指标 | 说明 |
| --- | --- | --- |
| 检索 | Hit@K、MRR、版本正确率、权限过滤 | 正确内容是否被召回且可用 |
| 生成 | 引用支持率、事实一致性、完整性 | 回答是否有证据、是否遗漏关键条件 |
| 任务 | 完成率、转人工率、采纳率、重复澄清 | 用户问题是否真的解决 |
| 安全 | 越权、注入、敏感输出、违规动作 | 是否突破权限与安全边界 |
| 工程 | P50/P95 延迟、错误率、并发、成本 | 能否稳定且经济地服务 |
| 业务 | 节省时间、转化、质量、投诉 | 是否带来可解释价值 |

离线集要包含高频问题、长尾问题、边界问题、对抗问题和“应该拒答”的问题。线上评估要按用户、任务和风险等级分层，避免总体平均掩盖高危错误。

## 4. 案例一：华南某客服 AI 团队

### 案例 1：华南某客服 AI 团队的“模型可解释性分析”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“模型可解释性分析”映射到“AI 数据治理、合规与可解释性”中的版本，而不是泛泛讨论概念。
- **触发事件**：模型升级后回答质量波动，无法确认是数据、Prompt 还是检索变化。
- **业务与数据范围**：训练与评测数据、Prompt、检索索引、模型、请求日志和反馈。数据侧重点采集版本标识、变更记录、回放和血缘，并与埋点平台、CRM、订单系统中的时间、状态和责任人信息对齐。
- **需要回答的问题**：数据、Prompt、特征、模型和评测能否互相对应。
- **关键障碍**：各组件独立发布，没有统一版本和回放能力。同时要防止埋点重复把表面指标带偏。
- **处理过程**：为每次请求记录数据、索引、Prompt、模型和代码版本，建立可重放评测与一键回滚。实施时把“数据、Prompt、特征、索引、模型和评测版本可以互相对应和回放”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：复合案例缩短问题定位时间，并支持影响范围分析。验收至少同时看主指标、版本标识、变更记录、回放和血缘和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“为 AI 数据建立来源、授权、质量、版本、偏差、隐私、血缘和使用反馈的控制链，让模型效果与风险都能解释和追溯。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

### 标题专属数据与失败分层 SQL

```sql
-- 模型可解释性分析：分位对比诊断（用户分层 × 产品）
WITH scoped AS (
  SELECT
    user_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_analysis_event
  WHERE event_time >= DATE '2026-07-01'
    AND event_time <  DATE '2026-10-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '复购率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

示例代码只展示可测试结构。真实系统还需要模型服务、向量库、权限、日志、缓存、限流、敏感检查和人工反馈，不应把安全完全交给提示词。

## 6. 案例二：华北某政务问答团队

### 案例 2：华北某政务问答团队的“模型可解释性分析”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“模型可解释性分析”映射到“AI 数据治理、合规与可解释性”中的质量，而不是泛泛讨论概念。
- **触发事件**：生成式问答引用了过期政策，并可能包含个人信息。
- **业务与数据范围**：政策版本、权限、问题、检索片段、输出、敏感检测和人工反馈。数据侧重点采集抽样审核、标注一致性、分群覆盖和反例，并与埋点平台、CRM、订单系统中的时间、状态和责任人信息对齐。
- **需要回答的问题**：样本是否代表目标人群，标注是否一致，偏差在哪里。
- **关键障碍**：知识更新没有失效机制，日志中保存了原始敏感文本。同时要防止分母漂移把表面指标带偏。

- **验证方式**：示例项目以引用正确率、过期命中率、敏感输出率和转人工率评估。验收至少同时看主指标、抽样审核、标注一致性、分群覆盖和反例和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“为 AI 数据建立来源、授权、质量、版本、偏差、隐私、血缘和使用反馈的控制链，让模型效果与风险都能解释和追溯。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

## 7. 架构与工程链路

| 层次 | 本文建议 | 关键问题 | 验收证据 |
| --- | --- | --- | --- |
| 数据源 | 埋点平台、CRM、订单系统 | 权威源、更新频率、主键和权限 | 接口或表清单 |
| 接入 | 批、流或 CDC 按业务时延选择 | 重复、顺序、断点续传和回放 | 延迟与幂等测试 |
| 存储 | 按访问模式选择数据湖、数仓或 OLAP | 分区、格式、生命周期和成本 | 容量与查询评测 |
| 计算 | SQL、Spark、Flink 或 Python 服务 | 粒度、状态、资源和失败恢复 | 压测与执行计划 |
| 治理 | 元数据、质量、血缘、权限 | 责任、规则、影响分析和审计 | 规则结果与变更记录 |
| 服务 | 指标、API、看板或应用 | SLA、缓存、限流和版本 | 监控与验收样例 |

推荐把链路拆成六层：数据与知识准备、检索或特征、模型调用、工具执行、评估与审核、监控与反馈。每层都要有版本、日志和失败处理。Agent 工具调用应在服务端校验参数与权限，不能只依赖模型“自觉”。

## 8. 监控、成本与安全

- 监控请求量、延迟、错误码、超时、重试和缓存命中。
- 记录检索文档版本、模型版本、提示词版本和关键参数。
- 对失败分类：检索缺失、上下文过长、工具失败、权限拒绝、模型拒答、结果不合规。
- 设置单位任务成本、每租户预算和异常调用告警。
- 对提示注入、越权、敏感信息和危险动作做专门测试。
- 保留人工复核、转人工、回滚到旧模型和关闭工具的开关。

## 9. 第三个案例与上线验收

### 案例 3：华东某医疗 AI 团队的“模型可解释性分析”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“模型可解释性分析”映射到“AI 数据治理、合规与可解释性”中的来源，而不是泛泛讨论概念。
- **触发事件**：模型在总体测试集表现良好，但老年与罕见病人群错误率明显更高。
- **业务与数据范围**：影像、病历、年龄、疾病亚型、标注来源、训练版本和分群评估结果。数据侧重点采集数据卡、授权依据、采集时间和用途，并与埋点平台、CRM、订单系统中的时间、状态和责任人信息对齐。
- **需要回答的问题**：数据从哪里来、是否授权、能否用于训练或评测。
- **关键障碍**：评测集人群结构失衡，数据卡没有记录排除标准。同时要防止把相关性误写成因果把表面指标带偏。
- **处理过程**：补充分群样本和专家复核，建立数据卡与模型卡，发布前检查弱势群体指标和错误类型。实施时把“训练、评测和生产数据记录来源、授权、用途、版本和负责人”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例治理将总体准确率改为分群效果、风险差异和人工复核共同验收。验收至少同时看主指标、数据卡、授权依据、采集时间和用途和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“为 AI 数据建立来源、授权、质量、版本、偏差、隐私、血缘和使用反馈的控制链，让模型效果与风险都能解释和追溯。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

| 验收项 | 最低要求 | 证据 |
| --- | --- | --- |
| 任务定义 | 输入输出和失败路径明确 | 产品说明、评测集 |
| 数据授权 | 来源、用途和权限可追溯 | 数据卡、授权记录 |
| 离线评估 | 覆盖常规、边界和拒答 | 评测报告 |
| 线上灰度 | 有对照组和护栏指标 | 实验或灰度记录 |
| 安全 | 越权、注入和敏感输出已测试 | 红队与审计报告 |
| 成本 | 单位请求预算和上限明确 | 账单与调用日志 |
| 运营 | 有反馈、复盘和回滚 | 周报、事故演练 |

1. 先写清“模型可解释性分析”的目标：为 AI 数据建立来源、授权、质量、版本、偏差、隐私、血缘和使用反馈的控制链，让模型效果与风险都能解释和追溯。
2. 专题检查：训练、评测和生产数据记录来源、授权、用途、版本和负责人
3. 专题检查：按人群、场景和风险等级评估质量与偏差，不只报告总体平均
4. 专题检查：数据、Prompt、特征、索引、模型和评测版本可以互相对应和回放
5. 专题检查：建立隐私、越权、错误信息、滥用和人工复核控制
6. 明确“模型可解释性分析”服务的使用者、决策动作和不做范围，并把成功标准写成可观察指标。
7. 为用户、会话、行为事件分别确认主键、时间和状态，画出从源系统到结果的链路。
8. 先做字段血缘和质量画像，检查事件主键唯一、分子分母同口径、匿名与登录身份已打通。
9. 用同周期基线和至少两个维度拆解问题，避免只比较一个异常周。
10. 抽取正常、异常和边界样本回查原始业务单据，记录抽样方法与结论。
11. 选择一种代码实现并保留参数、版本、执行日志和结果快照，确保别人可以复跑。
12. 上线前定义告警阈值、回滚条件和责任人；上线后按周观察主指标与护栏指标。
13. 复盘时区分数据问题、业务变化、方案偏差和外部因素，并把改进项转成有时限的任务。

## 扩展实战：模型可解释性分析的四个可执行案例

> [!info] 内容说明
> 以下内容围绕“模型可解释性分析”补充四个相互独立的工作场景，分别落在成本、质量与时效取舍、故障恢复与可回放、质量门禁与例外治理、权限、隐私与审计。它们使用公开方法、常见系统边界和脱敏数据构造，重点展示怎样从现象回到对象、流程、代码、行动与验收，而不是给出一个可以套用所有企业的标准答案。

| 案例 | 观察角度 | 首要对象 | 关键证据 | 失败时先停什么 |
| --- | --- | --- | --- | --- |
| 案例 4 | 成本、质量与时效取舍 | 用户 / 会话 | 执行计划、扫描量、文件数 | 任何优化都必须同时通过结果对账、延迟目标与成本预算，不能只展示一次最快执行 |

### 扩展代码一：从模型可解释性分析回到可核对明细

```sql
-- 模型可解释性分析：字段血缘与影响范围
WITH changed_columns AS (
  SELECT column_name
  FROM information_schema.columns
  WHERE table_schema = :source_schema
    AND table_name = :source_table
    AND last_altered_at >= :change_time
),
downstream_assets AS (
  SELECT
    asset_id,
    asset_name,
    asset_type,
    owner_name,
    criticality,
    last_used_at
  FROM metadata_asset_relation
  WHERE upstream_asset_id = :source_asset_id
    AND relation_status = 'active'
)
SELECT
  d.asset_id,
  d.asset_name,
  d.asset_type,
  d.owner_name,
  d.criticality,
  d.last_used_at,
  COUNT(c.column_name) AS changed_column_cnt,
  CASE
    WHEN d.criticality IN ('core', 'regulated') THEN 'block_release'
    WHEN d.last_used_at >= CURRENT_DATE - INTERVAL '7 days' THEN 'notify_owner'
    ELSE 'register_review'
  END AS required_action
FROM downstream_assets d
CROSS JOIN changed_columns c
GROUP BY d.asset_id, d.asset_name, d.asset_type, d.owner_name, d.criticality, d.last_used_at
ORDER BY
  CASE WHEN d.criticality IN ('core', 'regulated') THEN 0 ELSE 1 END,
  d.last_used_at DESC;
```

### 扩展代码二：把模型可解释性分析的验收证据写成门禁

```python
from dataclasses import dataclass
from datetime import datetime


@dataclass(frozen=True)
class ReleaseEvidence:
    subject: str
    source_watermark: datetime
    output_watermark: datetime
    source_rows: int
    output_rows: int
    duplicate_rows: int
    blocked_rows: int
    code_version: str
    parameter_version: str


def release_gate(evidence: ReleaseEvidence) -> tuple[bool, list[str]]:
    reasons = []
    if evidence.source_watermark != evidence.output_watermark:
        reasons.append("watermark_mismatch")
    if evidence.source_rows != evidence.output_rows:
        reasons.append("row_count_mismatch")
    if evidence.duplicate_rows:
        reasons.append("duplicate_keys")
    if evidence.blocked_rows:
        reasons.append("blocking_quality_rule_failed")
    if not evidence.code_version or not evidence.parameter_version:
        reasons.append("release_provenance_missing")
    return not reasons, reasons


evidence = ReleaseEvidence(
    subject="模型可解释性分析",
    source_watermark=datetime.fromisoformat("2026-11-06T02:00:00"),
    output_watermark=datetime.fromisoformat("2026-11-06T02:00:00"),
    source_rows=0,
    output_rows=0,
    duplicate_rows=0,
    blocked_rows=0,
    code_version="demo-v1",
    parameter_version="scope-v1",
)
print(release_gate(evidence))
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。

| 时间语义 | 业务发生、数据可见、决策采用是否混用 | event_time、入仓时间、行动时间轴 | 阻断 |
| 指标口径 | 转化率的分子、分母和排除项是否冻结 | 指标字典、SQL、对账结果 | 阻断正式指标 |
| 状态与关联 | 业务问题 → 指标定义 → 数据准备 → 探索分析是否可达且可追溯 | 状态机、明细、操作日志 | 阻断关键链路 |
| 权限与最小字段 | 派生表、导出和临时授权是否扩大访问范围 | 分类分级、字段血缘、访问日志 | 阻断导出 |
| 恢复与审计 | 失败后能否定位影响范围并幂等重跑 | 参数、版本、分区清单、补数对账 | 阻断发布 |

### 如果要把案例继续做深

1. **补一张真实但脱敏的链路图：** 标出埋点平台、CRM、订单系统、实验平台、BI之间的主键、时间、状态、版本、责任人和失败动作。
2. **补一份指标或规则字典：** 说明转化率、留存率、客单价的定义、粒度、排除项、负责人和验收样例。
3. **补一组代码证据：** 保留 SQL/Python、执行参数、输入输出计数、质量结果和一次失败回放，证明代码不只展示成功路径。
4. **补一次业务评审：** 让业务负责人、产品、运营、数据分析分别说明结果会改变什么动作，以及哪些结论仍缺少证据。
5. **补一次复盘：** 记录埋点重复、分母漂移、把相关性误写成因果是否发生、护栏是否生效、哪些处理应进入下一版标准。
