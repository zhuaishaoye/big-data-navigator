# 模型评估指标体系

> [!tip] 分析目标
> 把“模型评估指标体系”放进经营监控、用户增长、活动复盘、用户分层、实验评估和策略迭代，真正困难的通常不是解释名词，而是把它变成一条能被核对、能被复现、也能推动行动的工程链路。本文不追求堆满概念，而是围绕这个主题拆出业务对象、数据粒度、典型故障、代码验证和验收方式。

## 1. 把主题翻译成可验证的问题

“模型评估指标体系”不能直接等同于“做一张趋势图”。一个可执行的分析问题至少包含对象、时间、比较基准和行动：

> 在【观察周期】内，对【有效对象】按【渠道、用户分层、活动】比较【复购率】与【增量收益】，判断变化来自结构、行为还是数据口径，并验证【策略动作】是否带来可解释的增量。

在数据分析与数据运营场景中，用户行为、交易结果和策略曝光经常来自不同系统。先画数据流：

埋点平台 → CRM → 订单系统 → 实验平台 → BI → 客服工单

图中至少要有三个标记：业务事件发生时间、数据可见时间、策略或行动时间。只有三者分开，后续才能判断问题发生在业务、链路还是观察窗口。

## 2. 指标定义与分母检查

| 专题观测面 | 需要回答的问题 | 关键证据 | 判定与动作 |
| --- | --- | --- | --- |
| 运营（本标题优先） | 模型、Prompt、参数、成本和故障是否可追踪 | 版本、trace、P95、单任务成本和回滚 | 每次发布保留对照结果 |
| 评测 | 离线、线上、人工和业务指标是否一致 | 准确、引用、完整、拒答、采纳和任务完成 | 高风险错误单独设门槛 |
| 任务 | 模型输出是分类、生成、抽取、改写还是决策建议 | 输入结构、输出结构、成功标准和失败路径 | 能用规则解决的问题不先上模型 |
| 数据 | 训练、评测和线上反馈是否分离且覆盖边界 | 数据卡、标注规则、去重、授权和漂移 | 污染或不代表线上时暂停评估 |

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 转化率 | `COUNT(DISTINCT conversion_id) / COUNT(DISTINCT eligible_id)`（视图字段 `cvr`） | 渠道、用户分层、活动 | 不混用测试、撤销和跨期状态；与“模型评估指标体系”相关时还要补充主题筛选 |
| 留存率 | `COUNT(DISTINCT retained_user_id) / COUNT(DISTINCT cohort_user_id)`（视图字段 `retention_rate`） | 用户分层、活动、产品 | 不混用测试、撤销和跨期状态；与“模型评估指标体系”相关时还要补充主题筛选 |
| 客单价 | `SUM(paid_amount) / COUNT(DISTINCT paid_order_id)`（视图字段 `avg_order_value`） | 活动、产品、地区 | 不混用测试、撤销和跨期状态；与“模型评估指标体系”相关时还要补充主题筛选 |
| 复购率 | `COUNT(DISTINCT repeat_buyer_id) / COUNT(DISTINCT buyer_id)`（视图字段 `repurchase_rate`） | 产品、地区 | 不混用测试、撤销和跨期状态；与“模型评估指标体系”相关时还要补充主题筛选 |

针对“模型评估指标体系”，建议分别定义诊断指标、结果指标和护栏指标：

- **诊断指标**用于定位流程，例如曝光、有效访问、符合条件对象数和异常节点。
- **结果指标**用于判断是否改善，例如转化、留存、客单、毛利或处理时长。
- **护栏指标**用于防止局部优化伤害整体，例如退款、投诉、成本、公平性和长期留存。

每次计算都问四个问题：分母是谁、对象何时进入分母、例外状态怎么处理、窗口是否足够覆盖行为完成。尤其是埋点重复；分母漂移；把相关性误写成因果，任何一项没有解释清楚，指标都可能“看起来合理但无法决策”。

## 3. 方法选择：描述、诊断、预测还是因果

| 目标 | 适合的方法 | 需要的证据 | 不要混淆 |
| --- | --- | --- | --- |
| 描述现状 | 趋势、结构、同期群 | 完整口径、稳定时间窗 | 描述不等于原因 |
| 定位异常 | 分层、贡献度、漏斗、异常检测 | 原始事件、基线和质量检查 | 排名靠前不等于因果 |
| 预测未来 | 时间序列、回归、机器学习 | 时间切分验证、误差成本 | 离线准确率不等于业务收益 |
| 评估策略 | A/B、灰度、准实验 | 对照组、样本量、护栏指标 | 上线前后对比容易混入季节和选择偏差 |

如果问题只是“发生了什么”，先别急着建模；如果问题涉及“采取某策略会怎样”，就必须讨论反事实和识别条件。围绕“模型评估指标体系”，应把观察分析、预测和因果评估的产出分开标注。

## 4. 案例一：华东某 SaaS 客服团队

### 案例 1：华东某 SaaS 客服团队的“模型评估指标体系”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“模型评估指标体系”映射到“大模型、Prompt 与评估工程”中的运营，而不是泛泛讨论概念。
- **触发事件**：模型升级后离线准确率提升，但线上转人工率没有下降。
- **业务与数据范围**：真实会话、意图、回答、解决状态、人工标注、模型版本和成本。数据侧重点采集版本、trace、P95、单任务成本和回滚，并与埋点平台、CRM、订单系统中的时间、状态和责任人信息对齐。
- **需要回答的问题**：模型、Prompt、参数、成本和故障是否可追踪。
- **关键障碍**：评测集来自早期样本，标注只看流畅度，没有衡量问题是否真正解决。同时要防止埋点重复把表面指标带偏。
- **处理过程**：按意图和用户阶段重建评测集，加入任务完成、澄清轮次、转人工、引用和安全门槛。实施时把“评测集覆盖高频、长尾、边界、对抗、拒答和真实失败样本”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例评测发现复杂退款问题存在过度自信，并加入低置信度澄清与转人工。验收至少同时看主指标、版本、trace、P95、单任务成本和回滚和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“先证明任务需要大模型，再用版本化 Prompt、评测集、人工反馈、成本与安全门禁管理迭代，避免只凭少数演示判断效果。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

落地时建议先把一个总指标拆成可行动的树：

```text
模型评估指标体系｜复购率结果偏离
├── 先验真伪：事件主键唯一是否有批次级证据
├── 再看规模：用户数量与增量收益是否同向变化
├── 结构定位：渠道 → 用户分层 → 活动
├── 链路时点：埋点平台 → CRM → 订单系统
└── 行动出口：评测集覆盖高频、长尾、边界、对抗、拒答和真实失败样本
```

如果某一分支变化最大，再进入下一层，而不是一开始就按十几个维度切碎。每个分层结果都应同时报告样本量，避免小样本的极端比例抢走注意力。

## 5. SQL：计算趋势、结构和贡献度

### 趋势、结构与贡献度诊断

```sql
-- 模型评估指标体系：结构贡献诊断（产品 × 渠道）
WITH scoped AS (
  SELECT
    user_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_analysis_event
  WHERE event_time >= DATE '2026-05-01'
    AND event_time <  DATE '2026-08-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '转化率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

示例 SQL 只表达计算逻辑。实际实施应加入分区条件、业务状态过滤、时区和主题范围，并在结果中保留口径版本。

## 6. 案例二：华南某制造文档团队

### 案例 2：华南某制造文档团队的“模型评估指标体系”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“模型评估指标体系”映射到“大模型、Prompt 与评估工程”中的评测，而不是泛泛讨论概念。
- **触发事件**：团队尝试微调模型解释设备手册，但更新型号后效果迅速下降。
- **业务与数据范围**：手册版本、问答样本、型号、检索结果、微调数据和生产失败案例。数据侧重点采集准确、引用、完整、拒答、采纳和任务完成，并与埋点平台、CRM、订单系统中的时间、状态和责任人信息对齐。
- **需要回答的问题**：离线、线上、人工和业务指标是否一致。
- **关键障碍**：知识更新频率高，微调把旧事实写入参数，缺少检索与版本控制。同时要防止分母漂移把表面指标带偏。
- **处理过程**：先优化检索和结构化输出，只把稳定语言能力留给微调，新知识由版本化知识库提供。实施时把“Prompt、模型、参数、知识、工具和代码全部版本化”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：复合案例用更新时效、引用正确率和回归成本比较微调与 RAG。验收至少同时看主指标、准确、引用、完整、拒答、采纳和任务完成和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“先证明任务需要大模型，再用版本化 Prompt、评测集、人工反馈、成本与安全门禁管理迭代，避免只凭少数演示判断效果。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

当业务方要求“解释为什么下降”时，可以按下面顺序回答：

1. 先确认下降是否真实存在，排查采集、任务、维表和状态映射。
2. 把变化拆成对象数量、行为强度和结构占比。
3. 找到贡献最大的分组，但保留其他分组的抵消效应。
4. 抽取正负样本回查业务事件和操作日志。
5. 把尚不能证明的解释标为假设，并设计下一轮验证。

## 7. 代码验证：专题指标、实验或模型

### 专题验证代码

```python
from dataclasses import dataclass
from statistics import mean

@dataclass
class EvalCase:
    case_id: str
    expected: str
    risk: str

def score_case(case: EvalCase, output: str, cited: bool, refused: bool) -> dict:
    checks = {
        "contains_expected": case.expected in output,
        "citation_supported": cited,
        "safe_refusal": refused if case.risk == "high" else True,
    }
    return {"case_id": case.case_id, "score": mean(checks.values()), "checks": checks}

eval_cases = [
    EvalCase("e1", "标准答案", "low"),
    EvalCase("e2", "需要澄清", "medium"),
    EvalCase("e3", "应转人工", "high"),
]

# 主题："模型评估指标体系"
# 覆盖常规、长尾、边界、对抗和拒答；模型、Prompt、知识库、工具和参数全部版本化。
# 线下平均分提升不足以发布，还要看任务完成、人工采纳、P95、单位成本和风险事件。
```

## 8. 异常、偏差与常见误区

- **辛普森悖论**：总体改善但每个分组都变差，可能由对象结构变化造成。
- **幸存者偏差**：只分析完成流程的对象，忽略中途流失和中止。
- **分母漂移**：渠道口径、登录状态、版本或活动范围变化，改变可比性。
- **回传延迟**：当天数据未回补，导致近期效果被系统性低估。
- **多重比较**：反复寻找显著分组，实际只是随机波动。
- **行动偏差**：只报告支持既定方案的结果，忽略反例和护栏指标。

围绕“模型评估指标体系”，应预先写出至少三条反例检查。比如上线后是否有人负责观察和复盘、关键口径是否经过业务与技术共同确认，以及 异常值处理是否可能改变最终排名。

## 10. 交付物与工作节奏

| 交付物 | 应包含 | 质量要求 |
| --- | --- | --- |

```sql
  WHERE event_time >= :start_date
    AND event_time <  :end_date
    AND subject_key = 'subject'
    AND is_deleted = 0
  GROUP BY user_id
),
result_side AS (
  SELECT
    user_id AS entity_key,
    event_cnt,
    metric_sum
  FROM fact_analysis_event_result
  WHERE stat_date BETWEEN :start_date AND :end_date
    AND subject_key = 'subject'
)
SELECT
  COALESCE(s.entity_key, r.entity_key) AS entity_key,
  s.event_cnt AS source_event_cnt,
  r.event_cnt AS result_event_cnt,
  s.metric_sum AS source_metric_sum,
  r.metric_sum AS result_metric_sum,
  COALESCE(r.metric_sum, 0) - COALESCE(s.metric_sum, 0) AS metric_diff
FROM source_side s
FULL OUTER JOIN result_side r USING (entity_key)
WHERE ABS(COALESCE(r.metric_sum, 0) - COALESCE(s.metric_sum, 0)) > 0
   OR COALESCE(s.event_cnt, 0) <> COALESCE(r.event_cnt, 0)
ORDER BY ABS(metric_diff) DESC;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把模型评估指标体系的验收证据写成门禁

```python
from datetime import date
from hashlib import sha256

import pandas as pd

SUBJECT = "模型评估指标体系"
BLOCKING_RULES = ["事件主键唯一","分子分母同口径","匿名与登录身份已打通"]


def validate_release(frame: pd.DataFrame, start: date, end: date) -> dict:
    scoped = frame.loc[
        frame["event_date"].between(pd.Timestamp(start), pd.Timestamp(end))
        & (frame["subject_key"] == "subject")
    ].copy()
    checks = {
        "has_rows": len(scoped) > 0,
        "event_id_unique": not scoped["event_id"].duplicated().any(),
        "entity_key_complete": scoped["entity_key"].notna().all(),
        "event_time_present": scoped["event_time"].notna().all(),
        "scope_matches": scoped["subject_key"].nunique() == 1,
    }
    payload = f"{SUBJECT}|{start}|{end}|{len(scoped)}|{sorted(checks.items())}"
    return {
        "subject": SUBJECT,
        "rows": len(scoped),
        "checks": checks,
        "blocking_rules": BLOCKING_RULES,
        "release_allowed": all(checks.values()),
        "evidence_hash": sha256(payload.encode("utf-8")).hexdigest(),
    }
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。

### 四个案例共用的验收清单

| 验证面 | 发布前问题 | 证据 | 不通过时 |
| --- | --- | --- | --- |
| 对象与粒度 | 一行数据代表用户、事件、快照还是结果 | 主键、版本、有效时间和边界样本 | 阻断 |
| 时间语义 | 业务发生、数据可见、决策采用是否混用 | event_time、入仓时间、行动时间轴 | 阻断 |
| 指标口径 | 转化率的分子、分母和排除项是否冻结 | 指标字典、SQL、对账结果 | 阻断正式指标 |
| 状态与关联 | 业务问题 → 指标定义 → 数据准备 → 探索分析是否可达且可追溯 | 状态机、明细、操作日志 | 阻断关键链路 |
