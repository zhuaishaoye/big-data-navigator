# 归因分析方法

> [!abstract] 多触点归因与增量评估实战手册
> 归因分析是在多个触点、多个设备和多个时间窗之间分配结果贡献的方法。任何归因结果都依赖身份、触点、路径、模型和窗口假设；它能解释分配，但不能自动证明因果增量。

## 1. 归因分析方法：定义、适用边界与决策出口

归因分析是在多个触点、多个设备和多个时间窗之间分配结果贡献的方法。任何归因结果都依赖身份、触点、路径、模型和窗口假设；它能解释分配，但不能自动证明因果增量。

**本篇的适用边界。** 本篇讨论广告、内容、私域和站内推荐等数字触点的事后归因，并与实验或准实验增量评估配合使用；不把归因分数直接当作预算因果结论。

**最常见的错误替代。** 不能只用最后点击，也不能在触点缺失、跨设备未关联或窗口任意拉长时声称方法先进；不同模型结果不一致不等于其中一个必然正确。

**最终决策。** 营销、数据和财务负责人要判断：哪些触点应当记账，身份和会话如何关联，采用什么模型及窗口，何时用实验校准，预算调整依据是什么。 因此，这篇内容不从“应该建哪张表”开始，而从业务动作、责任人和失败后果开始。只有先确定谁在什么时点做出什么决定，字段、SQL、看板和模型才有明确用途。

围绕“归因分析方法”，工作中至少要区分四类问题：

1. **身份问题**：对象是谁，主键能否跨系统稳定关联，合并、拆分、撤销后历史是否还看得见。
2. **时间问题**：业务发生、状态生效、数据入仓、计算完成和人员行动分别发生在哪一刻。
3. **状态问题**：当前状态是一段事件、一张快照还是最终结果，空值代表未发生、未采集还是已删除。
4. **责任问题**：谁确认口径，谁处理异常，谁有权放行或停止，谁在观察期后复盘。

## 2. 归因分析方法的完整业务流程

| 环节 | 要做的事 | 最小证据 | 失败后先查什么 |
| --- | --- | --- | --- |
| 结果对象定义 | 确定订单、线索、激活或留存等要分配的结果 | 业务键、有效状态和售后回冲规则 | 按贡献直接宣布预算有效 |
| 触点采集 | 记录曝光、点击、访问、内容和成本 | 触点 ID、来源、时间和素材版本 | 家庭设备被当作同一人 |
| 身份与路径 | 在授权前提下关联跨设备和跨渠道路径 | 映射证据、有效窗口和不可关联标记 | 长期自然复购归给旧广告 |
| 归因模型 | 选择规则、时间衰减、位置或数据驱动方法 | 模型假设、训练范围、版本和验证 | 成熟渠道持续获得更多预算 |
| 增量校准 | 通过实验、地理对照或准实验验证贡献 | 对照、样本量、置信区间和偏差评估 | 按贡献直接宣布预算有效 |
| 预算应用 | 把归因、边际成本、长期价值和护栏结合 | 预算场景、阈值和审批记录 | 家庭设备被当作同一人 |
| 复盘与迭代 | 比较预测与实际、识别漏触点和模型漂移 | 误差、漂移、策略和下一轮实验 | 长期自然复购归给旧广告 |

把 结果对象定义、触点采集、身份与路径、归因模型、增量校准、预算应用、复盘与迭代 串起来后可以看出，归因分析方法不是一个孤立字段，而是一条会跨系统、跨岗位、跨时间的证据链。流程图上每一段都应标出输入、输出、状态、时间戳、责任人和异常出口。只要其中一段只能靠口头解释，后续的统计、追责和自动化就会失去基础。

一个合格的需求说明应该写成：

> 在【授权数据范围】和【观察窗口】内，围绕“归因分析方法”的【触点】，按【model_version、channel、campaign_id、identity_confidence】比较【有效触点覆盖率】及其【跨设备关联率】，定位一个可干预节点；行动后同时观察主指标、样本量和护栏，任何高风险异常先阻断再调查。

## 3. 归因分析方法的数据对象与系统契约

| 数据对象 | 建议主键 | 一行代表什么 | 不允许混淆 |
| --- | --- | --- | --- |
| 触点 | `touchpoint_id` | 一次可识别的曝光、点击或内容接触 | 对象身份与业务事件 |
| 身份映射 | `identity_link_id` | 匿名设备与授权账户之间的一段关联证据 | 事件、状态快照和结果粒度 |
| 转化路径 | `conversion_path_id` | 围绕一个结果对象按时间排列的有效触点集合 | 事件、状态快照和结果粒度 |
| 归因权重 | `attribution_weight_id` | 某触点在一个模型和窗口下获得的贡献份额 | 事件、状态快照和结果粒度 |
| 增量实验 | `incrementality_test_id` | 用于估计策略或渠道真实增量的对照安排 | 事件、状态快照和结果粒度 |
| 模型版本 | `attribution_model_version_id` | 包含规则、窗口、身份和训练数据的可复现版本 | 事件、状态快照和结果粒度 |

对象表不是把所有字段塞进一张宽表。事件、状态快照和结果表应该分别保留粒度，再通过稳定主键与版本建立关联。尤其要避免三个常见混算：把一次业务事件算成多个对象、把每日快照相加当事件总量、把最新状态覆盖历史状态。

本主题的数据契约至少应包含：

- `touchpoint_id` 的唯一性规则、生成方式和跨系统映射。
- `touchpoint_time` 的业务含义、时区、迟到和补录规则。
- `touchpoint_status` 的完整状态集合，以及删除、撤销、冻结和失效的表示方法。
- 控制对象 `incrementality_experiment_result.experiment_result_id` 与主对象的关系。
- 每次口径、规则、模型或源版本变化的影响范围和下游通知对象。
- 敏感字段、允许用途、访问角色、导出限制和审计保留时间。

## 4. 归因分析方法的指标、样本与验收口径

| 指标 | 公式或定义 | 口径提醒 |
| --- | --- | --- |
| 有效触点覆盖率 | 含至少一个有效触点的转化数 / 可归因转化数 | 缺失触点和未授权影响要单列 |
| 跨设备关联率 | 有可靠身份映射的转化数 / 可关联转化数 | 不把无法确认的映射强行补齐 |
| 模型稳定性 | 相同历史输入在不同重跑下结果一致的对象数 / 对象数 | 数据驱动模型还需记录随机种子 |
| 归因与实验偏差 | 归因份额 - 实验估计增量 | 按渠道和人群报告方向与置信区间 |
| 单位增量贡献成本 | 渠道总成本 / 实验估计增量结果 | 售后和长期价值纳入结果口径 |

指标字典至少写到“任何人都能按同一份数据复跑”的程度：中文名、业务定义、公式、分子、分母、事实粒度、时间字段、对象范围、排除项、版本、负责人和验收样例，一个都不能少。比例指标必须同时展示分子、分母和样本量；金额或数量必须做守恒；状态指标必须能回到事件时间线。

对于“归因分析方法”，建议把观察分成三层：

| 层次 | 看什么 | 不能替代什么 |
| --- | --- | --- |
| 业务结果 | 有效触点覆盖率、跨设备关联率 | 不能替代过程证据和个案回查 |
| 过程护栏 | 模型稳定性、归因与实验偏差、单位增量贡献成本 | 不能因为护栏暂时正常就跳过异常调查 |
| 数据证据 | 主键、时间、状态、版本、来源目标对账 | 不能只看任务成功或报表能打开 |

## 5. 归因分析方法：七个真实工作场景

以下七组场景均为公开方法结合常见工作流程构造的“脱敏复合示例”，不对应任何单一企业、患者、客户或雇员事实。场景的目的，是展示如何从现象走到证据、行动和验收，而不是虚构经营成果。

### 1. 品牌广告长期没有最后点击

**现场。** 品牌投放后用户通过搜索下单，预算却全部奖励搜索渠道。

**怎么查。** 还原用户首次曝光、搜索点击和直接访问路径，并设计品牌覆盖地区或人群对照。

**怎么处理。** 同时报告位置归因、路径贡献和实验增量；把品牌认知指标作为过程证据；预算不只看最后点击。

**验收结论。** 最后点击解释短路径分配，不等于品牌广告没有价值。

### 2. 跨设备身份关联扩大归因范围

**现场。** 把家庭 Wi-Fi 下多台设备合并后，归因转化大幅增加。

**怎么查。** 抽查设备、登录、收货和支付证据，发现家庭成员共用网络被错误合并。

**怎么处理。** 采用分层身份置信度；高置信登录关系可直接关联，弱信号只做概率匹配；无法确认的保留为未归因。

**验收结论。** 归因范围扩大不等于真实提升。错误身份会同时放大触点和结果。

### 3. 不同归因模型排名完全相反

**现场。** 首触、末触和线性模型给渠道完全不同的预算建议。

**怎么查。** 比较各模型的窗口、触点覆盖、重复路径和成本，再抽渠道做增量实验。

**怎么处理。** 不以某个模型作为唯一真相；把模型差异作为不确定性；在可实验渠道校准，不能实验的渠道降低决策权重。

**验收结论。** 模型是分配视角。预算最终需要因果证据和业务约束。

### 4. 长归因窗口把自然复购算给旧广告

**现场。** 把点击窗口从 7 天延长到 90 天后，品牌渠道贡献迅速上升。

**怎么查。** 观察用户自然复购周期、触点密度和窗口内无触点订单，并用对照估计基线。

**怎么处理。** 按业务购买周期选择窗口；超过窗口保留观察但不默认归因；报告自然转化和回冲。

**验收结论。** 窗口越长覆盖越多，但因果关系越弱。窗口必须由业务周期和证据决定。

### 5. 线下门店与线上广告无法关联

**现场。** 线上广告后到店成交，数字报表完全看不到贡献。

**怎么查。** 结合活动区域、门店扫码、优惠凭证和地理对照，区分可识别到店和整体区域提升。

**怎么处理。** 对可识别路径做个体归因；对不可识别部分使用区域聚合或实验；不把未识别订单强行分配到个人。

**验收结论。** 归因精度受数据连接能力限制。聚合方法可以评估整体，但不能制造个人关系。

### 6. 数据驱动模型在新渠道上失灵

**现场。** 模型按历史路径把大部分预算给成熟渠道，新渠道没有机会获得数据。

**怎么查。** 检查训练数据覆盖、探索预算和选择偏差，发现新渠道历史触点极少。

**怎么处理。** 保留固定探索预算；用实验获取新渠道增量；模型只在覆盖足够后参与决策；监控冷启动误差。

**验收结论。** 历史归因会强化已有渠道。需要探索机制避免预算被反馈循环锁死。

### 7. 财务要求归因收入与账单对账

**现场。** 营销平台报告收入与财务净收入长期不一致。

**怎么查。** 按订单状态、退款、税费、归因窗口和币种逐步对账，发现营销使用支付口径且未回冲售后。

**怎么处理。** 建立共用结果口径；支付、净收入、毛利分别发布；归因权重随订单状态更新并保留历史版本。

**验收结论。** 归因结果必须能回到财务对象和状态变化，不能只是一张营销平台报表。

七个场景可以归成一条共同判断顺序：先确认对象和时间，再确认状态和版本；然后做总量、结构和明细三层对账；最后才讨论策略、模型或工具。若一条结论不能指出对应的原始记录、责任人和行动出口，就只能算观察，不能作为生产结论。

## 6. 归因分析方法的第一段 SQL：重建业务链路

下面的 SQL 用于说明对象、时间、状态、版本和分层口径如何进入同一条可复查路径。表名和部分字段是通用示例，落地时应映射到企业数据字典；SQL 方言也需按实际引擎调整。

```sql
-- 归因分析方法：按业务对象重建链路，避免事件、快照和结果混算
WITH ranked_touchpoint_id AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY touchpoint_id
      ORDER BY updated_at DESC
    ) AS version_no
  FROM attribution_touchpoint
  WHERE touchpoint_time >= TIMESTAMP '{start_time}'
    AND touchpoint_time <  TIMESTAMP '{end_time}'
    AND touchpoint_status NOT IN ('deleted', 'test')
),
valid_rows AS (
  SELECT
    touchpoint_id,
    model_version,
    channel,
    campaign_id,
    identity_confidence,
    touchpoint_time,
    touchpoint_status,
    ingested_at
  FROM ranked_touchpoint_id
  WHERE version_no = 1
)
SELECT
  model_version, channel, campaign_id, identity_confidence,
  COUNT(DISTINCT touchpoint_id) AS object_cnt,
  SUM(attributed_conversion_value) AS numerator_value,
  SUM(allocated_cost) AS denominator_value,
  CAST(SUM(attributed_conversion_value) AS DOUBLE PRECISION)
    / NULLIF(SUM(allocated_cost), 0) AS metric_value,
  MIN(touchpoint_time) AS first_event_at,
  MAX(touchpoint_time) AS last_event_at
FROM valid_rows
GROUP BY model_version, channel, campaign_id, identity_confidence
ORDER BY metric_value DESC, object_cnt DESC;
```

执行后至少回答六个问题：

- 同一对象是否因为多源回传产生多版本，版本保留是否符合业务要求？
- 业务时间与入仓时间是否分开，补录和迟到数据是否进入正确分区？
- 分子分母是否来自同一对象范围和同一统计窗口？
- 维度使用的是事件当时值还是当前值，跨期比较是否一致？
- 删除、撤销、冻结和测试数据是否按规则处理？
- 分组结果能否在明细中抽样复现？

## 7. 归因分析方法的第二段 SQL：源、控制和结果三方对账

```sql
-- 归因分析方法：源对象、控制对象和结果对象三方对账
WITH population AS (
  SELECT
    touchpoint_id,
    touchpoint_time,
    touchpoint_status
  FROM attribution_touchpoint
  WHERE touchpoint_time >= TIMESTAMP '{start_time}'
    AND touchpoint_time <  TIMESTAMP '{end_time}'
),
control AS (
  SELECT
    touchpoint_id,
    SUM(verified_incremental_value) AS control_value,
    COUNT(DISTINCT experiment_result_id) AS control_cnt,
    MAX(updated_at) AS control_updated_at
  FROM incrementality_experiment_result
  WHERE updated_at >= TIMESTAMP '{start_time}'
  GROUP BY touchpoint_id
),
result AS (
  SELECT
    touchpoint_id,
    COUNT(*) AS result_cnt,
    MAX(calculated_at) AS calculated_at
  FROM mart_touchpoint_id
  WHERE business_date BETWEEN DATE '{start_date}' AND DATE '{end_date}'
  GROUP BY touchpoint_id
)
SELECT
  COALESCE(p.touchpoint_id, c.touchpoint_id, r.touchpoint_id) AS object_key,
  CASE
    WHEN p.touchpoint_id IS NULL THEN 'source_missing'
    WHEN c.touchpoint_id IS NULL THEN 'control_missing'
    WHEN r.touchpoint_id IS NULL THEN 'result_missing'
    WHEN ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0 THEN 'count_or_value_gap'
    ELSE 'matched'
  END AS reconciliation_status,
  p.touchpoint_status,
  c.control_value,
  c.control_cnt,
  r.result_cnt,
  c.control_updated_at,
  r.calculated_at
FROM population p
FULL OUTER JOIN control c ON p.touchpoint_id = c.touchpoint_id
FULL OUTER JOIN result r ON COALESCE(p.touchpoint_id, c.touchpoint_id) = r.touchpoint_id
WHERE p.touchpoint_id IS NULL
   OR c.touchpoint_id IS NULL
   OR r.touchpoint_id IS NULL
   OR ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0;
```

这段查询故意不使用“总数相差小于某个随意百分比就算通过”。它先找出缺失对象和状态差异，再检查控制值与结果值。对于归因分析方法，数量、金额、时长或状态任意一项无法解释，都不能用“业务波动”代替排查。

对账结果建议分成四类处理：

1. **阻断**：对象缺失、关键时间为空、状态非法、金额或数量不守恒、权限越界。
2. **严重**：比例或总量显著偏离基线，且无法由已确认的对象结构变化解释。
3. **观察**：小范围波动但来源、样本和趋势可控，进入责任人和观察窗口。
4. **探索**：只有弱信号或假设，不进入正式结论，更不直接触发业务处罚。

## 8. 归因分析方法的 Python 发布门禁与指标护栏

第一段代码把发布条件写成可执行对象，避免“检查过了”只存在聊天记录里：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class TouchpointIdBatch:
    batch_id: str
    source_rows: int
    valid_rows: int
    duplicate_keys: int
    missing_required_fields: int
    reconciliation_gap: float

def release_touchpoint_id(batch: TouchpointIdBatch) -> dict:
    checks = {
        "source_not_empty": batch.source_rows > 0,
        "valid_rows_in_range": 0 <= batch.valid_rows <= batch.source_rows,
        "duplicate_rate_ok": batch.duplicate_keys / max(batch.source_rows, 1) <= 0.001,
        "required_fields_ok": batch.missing_required_fields == 0,
        "reconciliation_ok": abs(batch.reconciliation_gap) <= 0.01,
    }
    return {
        "topic": "归因分析方法",
        "batch_id": batch.batch_id,
        "checks": checks,
        "release_allowed": all(checks.values()),
        "blocking_checks": [name for name, passed in checks.items() if not passed],
    }
```

第二段代码演示如何为比例类结果附带样本证据和小样本下界。它不是替代统计学家的模型，而是防止把少量偶然样本直接包装成稳定结论：

```python
from dataclasses import dataclass
from math import sqrt

@dataclass(frozen=True)
class TouchpointIdObservation:
    object_id: str
    numerator: float
    denominator: float
    sample_size: int
    scope_version: str

def calculate_touchpoint_id(rows: list[TouchpointIdObservation]) -> list[dict]:
    output = []
    for row in rows:
        value = row.numerator / row.denominator if row.denominator > 0 else None
        # 小样本用 Wilson 下界做护栏，不把偶然的高比例直接当稳定结果。
        z = 1.96
        p = value or 0
        n = max(row.sample_size, 1)
        center = p + z * z / (2 * n)
        margin = z * sqrt((p * (1 - p) + z * z / (4 * n)) / n)
        lower = max(0, (center - margin) / (1 + z * z / n))
        output.append({
            "object_id": row.object_id,
            "metric": "有效触点覆盖率",
            "value": value,
            "lower_bound": lower if value is not None else None,
            "sample_size": row.sample_size,
            "scope_version": row.scope_version,
            "caution": "缺失触点和未授权影响要单列",
        })
    return output
```

真正上线时还要补充参数配置、日志、血缘、告警级别、重跑幂等、异常样本保存和审批记录。代码通过不代表业务通过；自动检查只能证明已经定义的规则没有被违反，无法证明规则本身一定正确。

## 9. 归因分析方法的失败反例与上线验收

| 风险信号 | 错误做法 | 必须补齐的证据 | 发布或行动规则 |
| --- | --- | --- | --- |
| 把归因当归因果 | 按贡献直接宣布预算有效 | 实验或准实验增量 | 归因与增量并列展示 |
| 身份低置信合并 | 家庭设备被当作同一人 | 登录、支付和授权证据 | 低置信不直接合并 |
| 窗口任意延长 | 长期自然复购归给旧广告 | 购买周期和自然转化基线 | 窗口需版本化并由业务确认 |
| 训练数据自我强化 | 成熟渠道持续获得更多预算 | 探索预算和冷启动误差 | 保留实验与探索空间 |

上线验收不应只有一句“报表正常”。建议按下面四层验收：

| 验收对象 | 结构要求 | 测试样本 | 结果证据 |
| --- | --- | --- | --- |
| 触点 | `touchpoint_id` 能唯一定位一次可识别的曝光、点击或内容接触 | 正常、重复、缺失、撤销与跨期样本 | 有效触点覆盖率可回到原始对象 |
| 身份映射 | `identity_link_id` 能唯一定位匿名设备与授权账户之间的一段关联证据 | 正常、重复、缺失、撤销与跨期样本 | 跨设备关联率可回到原始对象 |
| 转化路径 | `conversion_path_id` 能唯一定位围绕一个结果对象按时间排列的有效触点集合 | 正常、重复、缺失、撤销与跨期样本 | 模型稳定性可回到原始对象 |
| 归因权重 | `attribution_weight_id` 能唯一定位某触点在一个模型和窗口下获得的贡献份额 | 正常、重复、缺失、撤销与跨期样本 | 归因与实验偏差可回到原始对象 |
| 增量实验 | `incrementality_test_id` 能唯一定位用于估计策略或渠道真实增量的对照安排 | 正常、重复、缺失、撤销与跨期样本 | 单位增量贡献成本可回到原始对象 |
| 模型版本 | `attribution_model_version_id` 能唯一定位包含规则、窗口、身份和训练数据的可复现版本 | 正常、重复、缺失、撤销与跨期样本 | 有效触点覆盖率可回到原始对象 |

还应为每一次发布保留一组固定回归样本：正常对象、边界状态、重复记录、缺失字段、撤销或退款、跨期、权限拒绝和失败恢复。回归样本不是演示数据，而是以后每次改规则都能重复执行的质量资产。

## 10. 归因分析方法的 30 天落地与复盘

| 阶段 | 主要交付 | 通过条件 |
| --- | --- | --- |
| 第 1 周：定义 | 对象、流程、状态、指标、排除项和责任矩阵 | 业务、数据、安全或质量负责人对同一口径签字 |
| 第 2 周：打通 | 源字段、主键、时间、版本、控制对象和失败样本 | 正常与异常样本都能回到原始记录 |
| 第 3 周：验证 | 总量对账、分层对账、抽样回查、权限测试、回滚演练 | 阻断问题清零，严重问题有责任人与期限 |
| 第 4 周：发布 | 灰度、SLO、监控、行动清单、停止条件和复盘模板 | 使用者在真实场景中完成一次闭环行动 |

如果必须用 90 秒说明“归因分析方法”是否做对，可以按这个顺序自测：

1. 一行数据代表什么，主键是什么，哪些对象绝不能混在同一粒度？
2. 业务发生、数据可见、计算完成和行动确认分别在哪个时间点？
3. 本主题最重要的两个主指标、三个护栏和最小样本量是什么？
4. 一个异常出现时，先从原始记录、链路版本还是业务动作开始查？
5. 哪类错误必须阻断发布或停止使用，谁有权批准例外？
6. 上线后由谁在多长时间内观察，什么条件下回滚或结束？

> [!check] 完成标准
> 当另一位数据同事不看聊天记录，只根据口径卡、回归样本和代码就能复跑同一结果；当业务负责人能指出一个异常对应的原始对象、处置动作和复核证据；当系统能够阻止未授权或状态非法的数据进入下游，这篇“归因分析方法”才算真正落到工作里。
