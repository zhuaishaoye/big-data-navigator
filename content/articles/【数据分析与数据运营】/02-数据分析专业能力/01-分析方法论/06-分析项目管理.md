# 分析项目管理

> [!abstract] 项目视角
> 把“分析项目管理”放进经营监控、用户增长、活动复盘、用户分层、实验评估和策略迭代，真正困难的通常不是解释名词，而是把它变成一条能被核对、能被复现、也能推动行动的工程链路。本文不追求堆满概念，而是围绕这个主题拆出业务对象、数据粒度、典型故障、代码验证和验收方式。

## 1. 项目背景与边界

“分析项目管理”作为项目，必须同时定义业务目标、数据范围、技术边界和验收方式。建议在立项材料里写清：

- **业务目标**：改善哪个流程、服务哪个角色、影响什么决策。
- **现状基线**：当前耗时、错误率、覆盖率、成本或用户反馈，不能只写“比较落后”。
- **范围**：覆盖业务域、系统、表、指标和团队；明确不做什么。
- **约束**：数据权限、上线窗口、依赖系统、预算、合规和人员。
- **成功标准**：主指标、护栏指标、验收样例和观察周期。

一个合格目标示例：

> 在【时间】前，为【用户】交付“分析项目管理”能力，使【转化率】达到【可解释目标】，同时保证事件主键唯一、分子分母同口径、匿名与登录身份已打通，上线后由【负责人】按周复盘。

## 2. 现状诊断与数据资产盘点

先梳理埋点平台、CRM、订单系统、实验平台、BI、客服工单之间的数据流，记录源系统、接口、表、任务、负责人和延迟。不要用一张“系统架构图”掩盖数据质量问题，必须把主键、时间、状态和数量关系标出来。

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 用户 | `user_id` | 业务问题 |
| 过程对象 | 会话 | `session_id` | 指标定义 |
| 过程对象 | 行为事件 | `event_id` | 数据准备 |
| 结果对象 | 订单 | `order_id` | 探索分析 |
| 结果对象 | 策略 | `strategy_id` | 策略设计 |
| 专题分析 | 分析项目管理 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

盘点阶段至少输出：资产清单、接口清单、指标基线、质量问题清单、权限清单和依赖矩阵。对每个问题标记影响范围、发生频率、现有临时方案和根本原因。

## 3. 目标架构与方案取舍

| 层次 | 本文建议 | 关键问题 | 验收证据 |
| --- | --- | --- | --- |
| 数据源 | 埋点平台、CRM、订单系统 | 权威源、更新频率、主键和权限 | 接口或表清单 |
| 接入 | 批、流或 CDC 按业务时延选择 | 重复、顺序、断点续传和回放 | 延迟与幂等测试 |
| 存储 | 按访问模式选择数据湖、数仓或 OLAP | 分区、格式、生命周期和成本 | 容量与查询评测 |
| 计算 | SQL、Spark、Flink 或 Python 服务 | 粒度、状态、资源和失败恢复 | 压测与执行计划 |
| 治理 | 元数据、质量、血缘、权限 | 责任、规则、影响分析和审计 | 规则结果与变更记录 |
| 服务 | 指标、API、看板或应用 | SLA、缓存、限流和版本 | 监控与验收样例 |

方案评审至少比较两种选择。例如批处理与实时处理、现成工具与自研、集中式平台与数据网格。比较维度包括交付速度、时延、成本、可维护性、权限边界、扩展性和失败恢复，而不是只比较功能清单。

## 4. 数据模型与指标口径

| 专题观测面 | 需要回答的问题 | 关键证据 | 判定与动作 |
| --- | --- | --- | --- |
| 上线（本标题优先） | 权限、质量、监控、培训和回滚是否就绪 | 上线清单、演练、验收和责任人 | 关键风险未关闭不发布 |
| 采用与收益 | 谁在使用，是否改变决策，副作用如何 | 使用日志、主指标、护栏和复盘 | 上线数量不等于项目成功 |
| 方案与证据 | 为什么选择当前方案，关键假设如何验证 | 替代方案、原型、数据和评审记录 | 重大假设必须有试验 |
| 问题与范围 | 项目改变什么行为，边界和不做什么是什么 | 决策记录、需求说明和现状基线 | 范围不清时先做诊断 |

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 转化率 | `COUNT(DISTINCT conversion_id) / COUNT(DISTINCT eligible_id)`（视图字段 `cvr`） | 渠道、用户分层、活动 | 不混用测试、撤销和跨期状态；与“分析项目管理”相关时还要补充主题筛选 |
| 留存率 | `COUNT(DISTINCT retained_user_id) / COUNT(DISTINCT cohort_user_id)`（视图字段 `retention_rate`） | 用户分层、活动、产品 | 不混用测试、撤销和跨期状态；与“分析项目管理”相关时还要补充主题筛选 |
| 客单价 | `SUM(paid_amount) / COUNT(DISTINCT paid_order_id)`（视图字段 `avg_order_value`） | 活动、产品、地区 | 不混用测试、撤销和跨期状态；与“分析项目管理”相关时还要补充主题筛选 |
| 复购率 | `COUNT(DISTINCT repeat_buyer_id) / COUNT(DISTINCT buyer_id)`（视图字段 `repurchase_rate`） | 产品、地区 | 不混用测试、撤销和跨期状态；与“分析项目管理”相关时还要补充主题筛选 |

模型设计优先保证粒度清晰和可重算。事实表负责事件或结果，维度表负责对象属性与历史归属，汇总表负责稳定消费。对于“分析项目管理”，如果既有事件又有状态，应分别建模，避免用最新状态覆盖历史。

## 5. 案例一：华东某零售数据项目组

### 案例 1：华东某零售数据项目组的“分析项目管理”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“分析项目管理”映射到“数据项目交付、验收与运营”中的上线，而不是泛泛讨论概念。
- **触发事件**：项目按期上线看板，但业务仍用 Excel 决策，数据团队无法证明价值。
- **业务与数据范围**：需求访谈、用户任务、使用日志、指标口径、决策记录和反馈。数据侧重点采集上线清单、演练、验收和责任人，并与埋点平台、CRM、订单系统中的时间、状态和责任人信息对齐。
- **需要回答的问题**：权限、质量、监控、培训和回滚是否就绪。
- **关键障碍**：项目只定义功能范围，没有定义采用动作和决策改变。同时要防止埋点重复把表面指标带偏。
- **处理过程**：把关键决策、使用场景和验收样例写入范围，按业务角色灰度并跟踪真实查询与行动。实施时把“项目目标包含业务行为、主指标、护栏指标和观察周期”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例验收以采用率、决策闭环、口径争议和人工步骤变化评估。验收至少同时看主指标、上线清单、演练、验收和责任人和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“从问题、范围、基线、方案、数据、上线、采用和复盘管理项目，确保交付的是可验证的业务能力而不是一次性材料。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

项目里最重要的一次评审通常发生在写代码之前。把对象、粒度、时间和成功标准画在白板上，让业务、数据、安全和运维共同指出歧义，往往比上线后修复便宜得多。

```python
from dataclasses import dataclass
from datetime import date

TOPIC = "分析项目管理"
PROJECT_ID = "g_project_delivery_1lplw3c"

@dataclass
class Milestone:
    name: str
    owner: str
    due: date
    evidence: str
    gate_passed: bool = False

milestones = [
    Milestone("问题与范围", "业务负责人", date(2026, 11, 8), "决策记录与基线"),
    Milestone("数据与权限", "数据负责人", date(2026, 11, 15), "接口、契约和授权矩阵"),
    Milestone("质量与灰度", "开发负责人", date(2026, 11, 22), "对账、回滚与演练"),
    Milestone("采用与复盘", "产品负责人", date(2026, 12, 6), "使用日志、主指标与护栏"),
]

required_checks = [
    "项目目标包含业务行为、主指标、护栏指标和观察周期",
    "范围明确数据、系统、团队、权限和不在本期处理的事项",
    "上线前完成质量、权限、监控、培训和回滚验收"
]

def release_gate(items: list[Milestone], checks: list[str]) -> dict:
    blockers = [item.name for item in items if not item.gate_passed]
    return {
        "project_id": PROJECT_ID,
        "topic": TOPIC,
        "blocked_by": blockers,
        "checks": checks,
        "release_allowed": not blockers and len(checks) >= 3,
    }

print(release_gate(milestones, required_checks))

# 项目管理以可验收能力为单位，不以代码提交、文档页数或看板数量代替结果。
# 变更必须同步评估范围、口径、权限、依赖、上线窗口和回滚成本。
```

### 上线前质量门禁

```python
# 分析项目管理：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "分析项目管理"
TOPIC_KEY = "subject"
RULE_ID = "rule_analytics_1lplw3c"
GUIDE_CHECKS = [
    "项目目标包含业务行为、主指标、护栏指标和观察周期",
    "范围明确数据、系统、团队、权限和不在本期处理的事项",
    "上线前完成质量、权限、监控、培训和回滚验收",
    "项目复盘同时衡量采用、收益、副作用和可复制性"
]
RULES = {
    "required_columns": ["event_id", "user_id", "event_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "user_id",
    "time_field": "event_time",
    "max_duplicate_rate": 0.0007,
    "max_null_rate": 0.002,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：项目目标包含业务行为、主指标、护栏指标和观察周期；范围明确数据、系统、团队、权限和不在本期处理的事项；上线前完成质量、权限、监控、培训和回滚验收；项目复盘同时衡量采用、收益、副作用和可复制性
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

代码交付要求：

- 参数化日期、环境和业务范围，不在代码里硬编码生产密钥。
- 任务可重复运行，重复执行不会产生重复数据。
- 关键步骤记录输入行数、输出行数、过滤行数和质量结果。
- 失败时保留日志和中间状态，支持按分区重跑。
- 代码、配置和表结构纳入版本管理，并有变更记录。

## 8. 测试、灰度与上线

| 测试类型 | 检查内容 | 通过标准 |
| --- | --- | --- |
| 单元测试 | 字段映射、计算逻辑、边界条件 | 用例覆盖正常、异常和极端值 |
| 集成测试 | 上下游接口、主键关联、权限 | 端到端能跑通 |
| 数据测试 | 唯一、完整、及时、平衡 | 关键规则通过并留存结果 |
| 性能测试 | 扫描量、执行时长、并发和资源 | 在容量预算内且可扩展 |
| 灰度 | 小范围业务与新旧结果对照 | 差异可解释，问题可回滚 |
| 验收 | 业务样例、指标和操作流程 | 验收人签字或有系统记录 |

灰度阶段应保留新旧链路对照。差异不能简单要求“完全一致”，因为修复本身可能改变结果；正确做法是对每类差异给出原因、影响和审批。

## 9. 第三个案例：华北某制造数据治理项目

### 案例 3：华北某制造数据治理项目的“分析项目管理”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“分析项目管理”映射到“数据项目交付、验收与运营”中的方案与证据，而不是泛泛讨论概念。
- **触发事件**：试点质量问题改善明显，但推广到更多工厂后效果迅速衰减。
- **业务与数据范围**：试点机制、责任人、规则、工单、培训和复制成本。数据侧重点采集替代方案、原型、数据和评审记录，并与埋点平台、CRM、订单系统中的时间、状态和责任人信息对齐。
- **需要回答的问题**：为什么选择当前方案，关键假设如何验证。
- **关键障碍**：项目依赖少数专家手工推动，没有形成角色、模板和自动化。同时要防止把相关性误写成因果把表面指标带偏。
- **处理过程**：把试点拆成可复制资产，建立本地负责人、规则模板、培训认证和月度复核。实施时把“上线前完成质量、权限、监控、培训和回滚验收”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例推广以复制周期、规则复用、问题复发和本地自治能力评估。验收至少同时看主指标、替代方案、原型、数据和评审记录和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“从问题、范围、基线、方案、数据、上线、采用和复盘管理项目，确保交付的是可验证的业务能力而不是一次性材料。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

## 10. 运营、验收与复盘

上线不是项目结束，而是运营开始。建议建立：

- 日监控：任务成功、延迟、数据量、关键规则和接口错误。
- 周复盘：主指标、护栏指标、业务使用、问题和行动。
- 月评估：成本、容量、复用、缺陷和需求变化。
- 变更评审：表结构、口径、依赖、权限和下游通知。

| 验收项 | 证据 | 负责人 |
| --- | --- | --- |
| 业务范围与口径确认 | 评审记录、指标字典 | 业务负责人 |

| 收益与副作用 | 主指标、护栏指标、复盘 | 项目负责人 |

1. 先写清“分析项目管理”的目标：从问题、范围、基线、方案、数据、上线、采用和复盘管理项目，确保交付的是可验证的业务能力而不是一次性材料。
2. 专题检查：项目目标包含业务行为、主指标、护栏指标和观察周期
3. 专题检查：范围明确数据、系统、团队、权限和不在本期处理的事项
4. 专题检查：上线前完成质量、权限、监控、培训和回滚验收
5. 专题检查：项目复盘同时衡量采用、收益、副作用和可复制性
6. 明确“分析项目管理”服务的使用者、决策动作和不做范围，并把成功标准写成可观察指标。
7. 为用户、会话、行为事件分别确认主键、时间和状态，画出从源系统到结果的链路。
8. 先做字段血缘和质量画像，检查事件主键唯一、分子分母同口径、匿名与登录身份已打通。
9. 用同周期基线和至少两个维度拆解问题，避免只比较一个异常周。
10. 抽取正常、异常和边界样本回查原始业务单据，记录抽样方法与结论。
11. 选择一种代码实现并保留参数、版本、执行日志和结果快照，确保别人可以复跑。
12. 上线前定义告警阈值、回滚条件和责任人；上线后按周观察主指标与护栏指标。
13. 复盘时区分数据问题、业务变化、方案偏差和外部因素，并把改进项转成有时限的任务。

## 扩展实战：分析项目管理的四个可执行案例

> [!info] 内容说明
> 以下内容围绕“分析项目管理”补充四个相互独立的工作场景，分别落在对象与口径争议、成本、质量与时效取舍、链路断点与延迟、决策增量与反事实。它们使用公开方法、常见系统边界和脱敏数据构造，重点展示怎样从现象回到对象、流程、代码、行动与验收，而不是给出一个可以套用所有企业的标准答案。

| 案例 | 观察角度 | 首要对象 | 关键证据 | 失败时先停什么 |
| --- | --- | --- | --- | --- |
| 案例 4 | 对象与口径争议 | 用户 / 会话 | 指标字典版本、源系统样例、两条计算链路 | 口径未确认时只发布差异分析，不把任一结果包装成正式经营指标 |

### 案例 4：分析项目管理的口径冲突与双轨对账

一个看似普通的“分析项目管理”需求，在跨系统核验后变成了围绕“对象与口径争议”的专项排查。触发排查的不是一次严重事故，而是连续几次解释不清的数据差异。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 在开发报表或模型前，把对象、粒度、时间、状态和排除条件形成可执行的共同定义。在本场景里，核心风险还包括埋点重复，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：用户、会话及其在探索分析前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注user_id与session_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 两个团队都声称在统计同一主题，但一行数据代表的业务对象不同，时间字段也不同。初看时，实验平台与BI的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 指标字典版本、源系统样例、两条计算链路、差异清单和业务确认记录。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“数据分析”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“分析项目管理”的当前定义并记录版本；第二步用用户明细核对实验平台到BI的关联；第三步按渠道与活动做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察转化率和护栏指标客单价。
- **行动与护栏：** 先冻结本期对象范围，再分别按源系统口径和目标口径重算，对每一类差异写明原因和暂定处理。专题检查项“项目目标包含业务行为、主指标、护栏指标和观察周期”被写成发布门禁，口径未确认时只发布差异分析，不把任一结果包装成正式经营指标。
- **失败路径：** 用平均值掩盖差异，或直接把对不上的明细删掉。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“分析项目管理”时，先验证上线清单、演练、验收和责任人，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由数据分析在明确时限内，根据转化率、客单价和事件主键唯一决定继续、回退、补查还是转人工。 若埋点重复或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

- **行动与护栏：** 在行动前冻结观察窗口与分组规则，上线后同时报告总体结果、分层结果、置信区间和反例。专题检查项“项目复盘同时衡量采用、收益、副作用和可复制性”被写成发布门禁，收益只在少数子组出现且护栏恶化时，不扩大全量使用。
- **失败路径：** 用上线前后两张趋势图直接宣称方案有效，忽略选择偏差与自然增长。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“分析项目管理”时，先验证决策记录、需求说明和现状基线，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由客服在明确时限内，根据复购率、转化率和时区一致决定继续、回退、补查还是转人工。 若活动归因重叠或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从分析项目管理回到可核对明细

```sql
-- 分析项目管理：源表与结果表按对象对账
WITH source_side AS (
  SELECT
    user_id AS entity_key,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum
  FROM fact_analysis_event
  WHERE event_time >= :start_date
    AND event_time <  :end_date
    AND subject_key = 'subject'
    AND is_deleted = 0
  GROUP BY user_id
),
result_side AS (
  SELECT
    user_id AS entity_key,
    event_cnt,
    metric_sum
  FROM fact_analysis_event_result
  WHERE stat_date BETWEEN :start_date AND :end_date
    AND subject_key = 'subject'
)
SELECT
  COALESCE(s.entity_key, r.entity_key) AS entity_key,
  s.event_cnt AS source_event_cnt,
  r.event_cnt AS result_event_cnt,
  s.metric_sum AS source_metric_sum,
  r.metric_sum AS result_metric_sum,
  COALESCE(r.metric_sum, 0) - COALESCE(s.metric_sum, 0) AS metric_diff
FROM source_side s
FULL OUTER JOIN result_side r USING (entity_key)
WHERE ABS(COALESCE(r.metric_sum, 0) - COALESCE(s.metric_sum, 0)) > 0
   OR COALESCE(s.event_cnt, 0) <> COALESCE(r.event_cnt, 0)
ORDER BY ABS(metric_diff) DESC;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把分析项目管理的验收证据写成门禁

```python
from dataclasses import dataclass
from datetime import datetime


@dataclass(frozen=True)
class ReleaseEvidence:
    subject: str
    source_watermark: datetime
    output_watermark: datetime
    source_rows: int
    output_rows: int
    duplicate_rows: int
    blocked_rows: int
    code_version: str
    parameter_version: str


def release_gate(evidence: ReleaseEvidence) -> tuple[bool, list[str]]:
    reasons = []
    if evidence.source_watermark != evidence.output_watermark:
        reasons.append("watermark_mismatch")
    if evidence.source_rows != evidence.output_rows:
        reasons.append("row_count_mismatch")
    if evidence.duplicate_rows:
        reasons.append("duplicate_keys")
    if evidence.blocked_rows:
        reasons.append("blocking_quality_rule_failed")
    if not evidence.code_version or not evidence.parameter_version:
        reasons.append("release_provenance_missing")
    return not reasons, reasons


evidence = ReleaseEvidence(
    subject="分析项目管理",
    source_watermark=datetime.fromisoformat("2026-11-06T02:00:00"),
    output_watermark=datetime.fromisoformat("2026-11-06T02:00:00"),
    source_rows=0,
    output_rows=0,
    duplicate_rows=0,
    blocked_rows=0,
    code_version="demo-v1",
    parameter_version="scope-v1",
)
print(release_gate(evidence))
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。

### 四个案例共用的验收清单

| 验证面 | 发布前问题 | 证据 | 不通过时 |
| --- | --- | --- | --- |
| 对象与粒度 | 一行数据代表用户、事件、快照还是结果 | 主键、版本、有效时间和边界样本 | 阻断 |
| 时间语义 | 业务发生、数据可见、决策采用是否混用 | event_time、入仓时间、行动时间轴 | 阻断 |
| 指标口径 | 转化率的分子、分母和排除项是否冻结 | 指标字典、SQL、对账结果 | 阻断正式指标 |
| 状态与关联 | 业务问题 → 指标定义 → 数据准备 → 探索分析是否可达且可追溯 | 状态机、明细、操作日志 | 阻断关键链路 |
