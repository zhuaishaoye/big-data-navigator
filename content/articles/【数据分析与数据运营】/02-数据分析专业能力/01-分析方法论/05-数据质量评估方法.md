# 数据质量评估方法

> [!warning] 核心判断
> 一个关于“数据质量评估方法”的结论能不能被信任，取决于它是否能回到原始事件、明确时间和对象，并说明排除了哪些记录。下面不会用单一模板概括所有场景，而是结合数据分析与数据运营中的多类任务，展示数据建模、代码分析和项目验收之间如何衔接。

## 1. 先判断应治理什么风险

“数据质量评估方法”通常不是买一个平台就能解决的问题。它至少涉及制度、标准、责任、流程、技术和审计六层。开始前先把风险写成可观察事实：

| 风险问题 | 观察信号 | 可能影响 | 首先核查 |
| --- | --- | --- | --- |
| 定义不一致 | 同名指标多个 SQL、多个业务解释 | 决策冲突、返工 | 指标字典与负责人 |
| 数据不完整 | 分区缺失、关键字段空值 | 报表失真、流程中断 | 采集与任务日志 |
| 责任不清 | 问题工单长期无人认领 | 修复延迟、同类复发 | 资产责任矩阵 |
| 访问过宽 | 长期权限、共享账号、无审计 | 泄漏与合规风险 | 权限清单与访问日志 |
| 变更不可见 | 表结构或逻辑变更无通知 | 下游批量故障 | 血缘与发布记录 |

1. **埋点重复**：需要在标准、系统或组织流程中设置对应控制。
2. **分母漂移**：需要在标准、系统或组织流程中设置对应控制。
3. **把相关性误写成因果**：需要在标准、系统或组织流程中设置对应控制。
4. **活动归因重叠**：需要在标准、系统或组织流程中设置对应控制。
5. **只观察短期指标**：需要在标准、系统或组织流程中设置对应控制。

## 2. 用 DAMA 思路拆成可执行组件

| 组件 | 本文关注对象 | 最小可执行机制 |
| --- | --- | --- |
| 数据标准 | 字段、代码、指标和业务术语；结合“数据质量评估方法”重点检查事件主键唯一 | 标准登记、评审、版本与废弃 |
| 元数据 | 表、字段、任务、接口、负责人；结合“数据质量评估方法”重点检查分子分母同口径 | 自动采集、业务补充、变更通知 |
| 数据质量 | 完整性、唯一性、及时性、准确性；结合“数据质量评估方法”重点检查匿名与登录身份已打通 | 规则、阈值、工单与复盘 |
| 主数据 | 客户、商品、设备、机构等共享对象；结合“数据质量评估方法”重点检查时区一致 | 源权威、去重、合并、历史关系 |
| 数据安全 | 分类分级、权限、脱敏和审计；结合“数据质量评估方法”重点检查退款与撤销已冲减 | 审批、最小权限、访问复核 |
| 数据血缘 | 表、字段、任务和指标关系；结合“数据质量评估方法”重点检查事件主键唯一 | 影响分析、问题追踪、变更评审 |

治理不是把所有数据都按同一优先级管理。建议依据使用范围、监管要求、决策影响和故障历史划分关键资产，再决定投入。关键资产应有唯一负责人、明确消费者、质量目标、访问策略和变更通知。

## 3. 资产、标准与责任矩阵

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 用户 | `user_id` | 业务问题 |
| 过程对象 | 会话 | `session_id` | 指标定义 |
| 过程对象 | 行为事件 | `event_id` | 数据准备 |
| 结果对象 | 订单 | `order_id` | 探索分析 |
| 结果对象 | 策略 | `strategy_id` | 策略设计 |
| 专题分析 | 数据质量评估方法 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

一个可执行的数据标准至少包括：

- **业务定义**：业务人员如何理解和适用。
- **技术定义**：字段类型、长度、格式、枚举和空值语义。
- **计算口径**：时间、粒度、分子分母和排除项。
- **权威来源**：哪个系统是事实源，冲突时以谁为准。
- **生命周期**：创建、变更、废弃和归档规则。
- **责任人**：业务负责人、数据负责人、技术负责人和审批人。

资产责任可以使用 RACI：业务负责人对定义负责，数据负责人对实现与质量负责，平台团队对工具和权限负责，安全合规对访问与审计负责，消费者对使用边界负责。只有“责任人”一个字段，没有决策权和时限，问题仍会回到治理团队自己处理。

## 4. 案例一：华东某银行数据治理团队

### 案例 1：华东某银行数据治理团队的“数据质量评估方法”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“数据质量评估方法”映射到“数据质量规则、监控与闭环”中的及时性，而不是泛泛讨论概念。
- **触发事件**：核心指标在月末出现异常波动，业务先怀疑营销活动，后发现源系统批量延迟。
- **业务与数据范围**：源表分区、入仓时间、金额平衡、状态枚举、指标趋势和业务活动日历。数据侧重点采集分区完成时间、端到端延迟和告警时间，并与埋点平台、CRM、订单系统中的时间、状态和责任人信息对齐。
- **需要回答的问题**：数据何时可用，是否满足消费者 SLA。
- **关键障碍**：质量规则只看空值，没有检查分区完整性和跨系统金额平衡。同时要防止埋点重复把表面指标带偏。
- **处理过程**：为核心资产增加行数与金额对账、分区 SLA 和状态机检查，并按严重等级绑定阻断与工单。实施时把“同时覆盖完整性、唯一性、准确性、及时性和一致性，不只查空值”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例治理把发现时间前移到发布前，并用误报率、闭环时长和复发率评估规则。验收至少同时看主指标、分区完成时间、端到端延迟和告警时间和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把质量规则绑定到关键资产、严重等级、责任人和失败动作，通过样本回查和趋势监控区分数据问题与业务变化。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

治理项目应先做小范围闭环，不要一开始铺满全公司。选择一个高影响业务域，完成从资产盘点、标准确认、质量规则、问题整改到复盘的完整链路，再复制机制。

## 5. 规则与代码：让控制可执行

### 发布前规则门禁

```python
# 数据质量评估方法：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "数据质量评估方法"
TOPIC_KEY = "subject"
RULE_ID = "rule_analytics_1mkthe9"
GUIDE_CHECKS = [
    "关键规则必须绑定资产、负责人、严重等级、失败动作和复核时限",
    "同时覆盖完整性、唯一性、准确性、及时性和一致性，不只查空值",
    "异常结果保留样本与上下文，便于业务回查原始单据",
    "用发现前移、误报率、闭环时长和复发率衡量治理效果"
]
RULES = {
    "required_columns": ["event_id", "user_id", "event_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "user_id",
    "time_field": "event_time",
    "max_duplicate_rate": 0.0004,
    "max_null_rate": 0.004,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：关键规则必须绑定资产、负责人、严重等级、失败动作和复核时限；同时覆盖完整性、唯一性、准确性、及时性和一致性，不只查空值；异常结果保留样本与上下文，便于业务回查原始单据；用发现前移、误报率、闭环时长和复发率衡量治理效果
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

### 治理对象与风险分层 SQL

```sql
-- 数据质量评估方法：同期基线诊断（活动 × 地区）
WITH scoped AS (
  SELECT
    user_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_analysis_event
  WHERE event_time >= DATE '2026-02-01'
    AND event_time <  DATE '2026-05-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '增量收益' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

规则设计要同时考虑三件事：能否自动执行、误报成本是否可接受、失败后谁来处理。只写“不能为空”不够，必须明确哪类对象允许为空、谁能在何种情况下豁免、豁免多久、是否需要审批和复核。

建议把规则分成四级：

1. **阻断**：涉及监管、资金、身份或核心发布，失败即停止。
2. **严重告警**：影响大但可先隔离，要求在约定时间内响应。
3. **观察告警**：可能是正常业务变化，先记录趋势。
4. **探索检查**：尚未形成稳定阈值，仅用于发现异常模式。

## 6. 案例二：华南某零售会员团队

### 案例 2：华南某零售会员团队的“数据质量评估方法”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“数据质量评估方法”映射到“数据质量规则、监控与闭环”中的准确性，而不是泛泛讨论概念。
- **触发事件**：会员分层结果一周内多次变化，运营无法确定触达名单。
- **业务与数据范围**：会员主数据、订单、退款、标签版本、更新时间和分层规则。数据侧重点采集抽样单据、金额平衡、枚举与公式复核，并与埋点平台、CRM、订单系统中的时间、状态和责任人信息对齐。
- **需要回答的问题**：值与业务事实、源系统或计算规则是否一致。
- **关键障碍**：测试会员未排除，退款未冲减，标签规则更新没有版本记录。同时要防止分母漂移把表面指标带偏。
- **处理过程**：增加业务对象范围检查、历史回放和版本对比，先隔离异常会员再发布名单。实施时把“异常结果保留样本与上下文，便于业务回查原始单据”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：复合案例将问题拆成输入质量、规则变更和正常行为变化。验收至少同时看主指标、抽样单据、金额平衡、枚举与公式复核和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把质量规则绑定到关键资产、严重等级、责任人和失败动作，通过样本回查和趋势监控区分数据问题与业务变化。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

治理指标不要只统计“生成了多少文档、接入了多少资产”。更值得观察的是规则覆盖的关键资产、问题发现前移比例、问题复发率、变更影响分析耗时和业务是否愿意使用。

## 7. 权限、安全与审计

围绕“数据质量评估方法”，权限治理至少应回答：

- 谁能申请、谁审批、审批依据是什么？
- 权限是否按角色、数据级别和用途最小化？
- 临时权限何时收回，离职和转岗是否自动处理？
- 查询、下载和导出是否留痕，异常访问如何发现？
- 脱敏、加密、水印和审计日志是否与数据类型匹配？

敏感字段不应通过“复制一份测试数据”绕过问题。更合适的做法是分级脱敏、合成数据或受控计算环境。所有示例和代码都不应包含真实身份、账号、密钥、客户名单或未公开经营数据。

## 8. 第三个案例：华北某制造质量平台

### 案例 3：华北某制造质量平台的“数据质量评估方法”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“数据质量评估方法”映射到“数据质量规则、监控与闭环”中的完整性，而不是泛泛讨论概念。
- **触发事件**：良品率日报偶尔超过 100%，现场对数据看板失去信任。
- **业务与数据范围**：工单投入、产出、报废、返工、质检、设备状态和批次记录。数据侧重点采集覆盖日期、行数基线、空值率和源目标计数，并与埋点平台、CRM、订单系统中的时间、状态和责任人信息对齐。
- **需要回答的问题**：分区、记录和关键字段是否缺失。
- **关键障碍**：投入与产出时间窗错位，返工数量被重复计入良品，部分离线补录没有来源。同时要防止把相关性误写成因果把表面指标带偏。
- **处理过程**：建立投入产出平衡、批次去重和补录来源检查，异常时展示影响明细而不是只显示红灯。实施时把“用发现前移、误报率、闭环时长和复发率衡量治理效果”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例项目将质量规则、业务解释和现场处置合并到同一页面。验收至少同时看主指标、覆盖日期、行数基线、空值率和源目标计数和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把质量规则绑定到关键资产、严重等级、责任人和失败动作，通过样本回查和趋势监控区分数据问题与业务变化。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

## 扩展实战：数据质量评估方法的四个可执行案例

> [!info] 内容说明
> 以下内容围绕“数据质量评估方法”补充四个相互独立的工作场景，分别落在跨团队交接与责任、成本、质量与时效取舍、链路断点与延迟、故障恢复与可回放。它们使用公开方法、常见系统边界和脱敏数据构造，重点展示怎样从现象回到对象、流程、代码、行动与验收，而不是给出一个可以套用所有企业的标准答案。

| 案例 | 观察角度 | 首要对象 | 关键证据 | 失败时先停什么 |
| --- | --- | --- | --- | --- |
| 案例 4 | 跨团队交接与责任 | 用户 / 会话 | 数据契约版本、字段语义、接口样例 | 业务定义、粒度或状态语义发生破坏性变化时，未通知消费者不得直接发布 |

这四个案例共享一条底线：先证明数据对象和链路能够解释，再讨论优化或决策。任何涉及资金、医疗安全、用户隐私、监管报送或核心权限的结果，都需要保留人工复核、阻断条件和回滚路径。

### 案例 4：数据质量评估方法跨团队交接的契约缺口

某数据分析与数据运营团队在季度复盘时重新讨论“数据质量评估方法”。讨论并没有从工具选型开始，而是先追问一个更基础的问题：上游认为字段已经交付，下游却持续遇到状态含义、历史归属和异常处理不一致，问题在群聊中反复流转。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 把数据定义、变更通知、失败动作、服务时限和责任人写成可测试的运行契约。在本场景里，核心风险还包括把相关性误写成因果，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：用户、会话及其在业务问题前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注user_id与session_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 上游认为字段已经交付，下游却持续遇到状态含义、历史归属和异常处理不一致，问题在群聊中反复流转。初看时，埋点平台与CRM的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 数据契约版本、字段语义、接口样例、变更记录、工单时效、消费者验收和升级路径。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“业务负责人”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“数据质量评估方法”的当前定义并记录版本；第二步用用户明细核对埋点平台到CRM的关联；第三步按活动与地区做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察客单价和护栏指标增量收益。
- **行动与护栏：** 组织上游生产、数据开发、消费方和安全人员做一次契约评审，把模糊责任改成可执行的检查项。专题检查项“关键规则必须绑定资产、负责人、严重等级、失败动作和复核时限”被写成发布门禁，业务定义、粒度或状态语义发生破坏性变化时，未通知消费者不得直接发布。
- **失败路径：** 只建立群聊和文档链接，却没有版本、负责人、失败动作和下线流程。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“数据质量评估方法”时，先验证分区完成时间、端到端延迟和告警时间，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由业务负责人在明确时限内，根据客单价、增量收益和匿名与登录身份已打通决定继续、回退、补查还是转人工。 若把相关性误写成因果或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。
### 案例 5：数据质量评估方法的三方取舍实验

- **为什么要做：** 把新鲜度、正确性和成本分别量化，找到满足真实决策节奏的最低必要资源。在本场景里，核心风险还包括活动归因重叠，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。

- **关键异常或争议：** 一次错误发布已经产生结果，团队只能凭负责人记忆寻找影响范围，补数后仍无法确认是否重复或遗漏。初看时，实验平台与BI的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 运行参数、代码版本、输入快照、输出摘要、受影响分区、回滚记录和补数对账。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“数据分析”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“数据质量评估方法”的当前定义并记录版本；第二步用订单明细核对实验平台到BI的关联；第三步按渠道与活动做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察转化率和护栏指标客单价。
- **行动与护栏：** 保存现场并停止下游扩散，按影响边界回滚或隔离结果，使用幂等任务从最小必要范围重新计算。专题检查项“用发现前移、误报率、闭环时长和复发率衡量治理效果”被写成发布门禁，恢复任务没有对账、没有版本记录或无法重复执行时，不宣布故障结束。
- **失败路径：** 直接覆盖目标表，或者把所有分区全部重跑以求省事。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“数据质量评估方法”时，先验证工单、根因、修复时长、复发率和复核记录，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由数据分析在明确时限内，根据转化率、客单价和事件主键唯一决定继续、回退、补查还是转人工。 若埋点重复或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从数据质量评估方法回到可核对明细

```sql
-- 数据质量评估方法：行动前后与分组增量
WITH scoped AS (
  SELECT
    user_id AS entity_key,
    活动 AS decision_group,
    event_time AS event_date,
    metric_value,
    CASE
      WHEN event_time <  :action_date THEN 'before'
      ELSE 'after'
    END AS period_label
  FROM fact_analysis_event
  WHERE event_time >= :analysis_start
    AND event_time <  :analysis_end
    AND subject_key = 'subject'
),
grouped AS (
  SELECT
    decision_group,
    period_label,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    AVG(metric_value) AS metric_avg,
    SUM(metric_value) AS metric_sum
  FROM scoped
  GROUP BY decision_group, period_label
),
compared AS (
  SELECT
    decision_group,
    MAX(CASE WHEN period_label = 'before' THEN metric_avg END) AS before_avg,
    MAX(CASE WHEN period_label = 'after' THEN metric_avg END) AS after_avg,
    MAX(CASE WHEN period_label = 'before' THEN entity_cnt END) AS before_cnt,
    MAX(CASE WHEN period_label = 'after' THEN entity_cnt END) AS after_cnt
  FROM grouped
  GROUP BY decision_group
)
SELECT
  decision_group,
  before_avg,
  after_avg,
  after_avg - before_avg AS naive_delta,
  '复购率' AS metric_name,
  '关键规则必须绑定资产、负责人、严重等级、失败动作和复核时限' AS required_evidence
FROM compared
WHERE before_cnt >= 30 AND after_cnt >= 30
ORDER BY ABS(after_avg - before_avg) DESC;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把数据质量评估方法的验收证据写成门禁

```python
import pandas as pd

KEY = ["entity_key", "event_id"]
AMOUNT_COLUMNS = ["metric_value", "adjustment_value"]


def reconcile(source: pd.DataFrame, result: pd.DataFrame) -> pd.DataFrame:
    def aggregate(frame: pd.DataFrame, side: str) -> pd.DataFrame:
        grouped = (
            frame.groupby("entity_key", dropna=False)
            .agg(
                event_cnt=("event_id", "nunique"),
                metric_sum=("metric_value", "sum"),
                adjustment_sum=("adjustment_value", "sum"),
            )
            .reset_index()
        )
        return grouped.rename(columns={
            "event_cnt": f"{side}_event_cnt",
            "metric_sum": f"{side}_metric_sum",
            "adjustment_sum": f"{side}_adjustment_sum",
        })

    compared = aggregate(source, "source").merge(
        aggregate(result, "result"),
        on="entity_key",
        how="outer",
    )
    compared["metric_diff"] = (
        compared["result_metric_sum"].fillna(0)
        - compared["source_metric_sum"].fillna(0)
    )
    compared["event_diff"] = (
        compared["result_event_cnt"].fillna(0)
        - compared["source_event_cnt"].fillna(0)
    )
    compared["exception"] = compared.apply(
        lambda row: "missing_result" if pd.isna(row["result_metric_sum"])
        else "unexpected_result" if pd.isna(row["source_metric_sum"])
        else "count_diff" if row["event_diff"] != 0
        else "amount_diff",
        axis=1,
    )
    return compared.loc[
        (compared["metric_diff"].abs() > 0) | (compared["event_diff"] != 0)
    ].sort_values("metric_diff", key=lambda values: values.abs(), ascending=False)
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。

### 四个案例共用的验收清单

| 验证面 | 发布前问题 | 证据 | 不通过时 |
| --- | --- | --- | --- |
| 对象与粒度 | 一行数据代表用户、事件、快照还是结果 | 主键、版本、有效时间和边界样本 | 阻断 |
| 时间语义 | 业务发生、数据可见、决策采用是否混用 | event_time、入仓时间、行动时间轴 | 阻断 |
| 指标口径 | 转化率的分子、分母和排除项是否冻结 | 指标字典、SQL、对账结果 | 阻断正式指标 |
| 状态与关联 | 业务问题 → 指标定义 → 数据准备 → 探索分析是否可达且可追溯 | 状态机、明细、操作日志 | 阻断关键链路 |
| 权限与最小字段 | 派生表、导出和临时授权是否扩大访问范围 | 分类分级、字段血缘、访问日志 | 阻断导出 |
| 恢复与审计 | 失败后能否定位影响范围并幂等重跑 | 参数、版本、分区清单、补数对账 | 阻断发布 |
