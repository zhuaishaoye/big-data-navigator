# Text-to-SQL与语义层协同

> [!tip] 核心原则
> 一个关于“Text-to-SQL与语义层协同”的结论能不能被信任，取决于它是否能回到原始事件、明确时间和对象，并说明排除了哪些记录。下面不会用单一模板概括所有场景，而是结合数据分析与数据运营中的多类任务，展示数据建模、代码分析和项目验收之间如何衔接。

## 1. 从业务任务定义 AI 能力

围绕“Text-to-SQL与语义层协同”，先把任务写成输入、输出、成功标准和失败边界。不要从“上一套模型”或“接一个聊天框”开始。

| 设计项 | 必须回答的问题 | 错误示例 | 更好做法 |
| --- | --- | --- | --- |
| 用户 | 谁使用，谁复核，谁承担后果 | 所有人都能用 | 按角色和权限明确使用边界 |
| 输入 | 文本、表格、图片还是工具调用 | 把所有数据都塞进上下文 | 只提供任务所需且获授权的数据 |
| 输出 | 分类、生成、检索、SQL 还是动作 | 只要求“回答准确” | 定义可检查的输出结构 |
| 成功 | 任务完成、采纳、质量、时延和成本 | 只看离线准确率 | 离线 + 线上 + 人工复核 |
| 失败 | 无答案、拒答、转人工还是回滚 | 失败也生成看似合理内容 | 明确置信阈值和降级路径 |

| 专题分析 | Text-to-SQL与语义层协同 | `topic_key = 'text_to_sql'` | 用于把通用事件收窄到本主题 |

AI 项目的数据治理比传统报表更强调版本和来源。至少记录：

- 数据集和知识文档的来源、授权、时间、负责人和版本。
- 样本标注规则、标注人、抽检结果和争议处理。
- 训练、验证、测试与线上反馈是否隔离。
- 提示词、模型、温度、检索参数和工具权限的版本。
- 输入中的个人信息、商业秘密和敏感字段是否脱敏。

如果“Text-to-SQL与语义层协同”使用 RAG，文档切片应尊重标题、章节、表格和条款结构；如果使用微调，先证明提示词、检索或流程优化不足；如果使用 Agent，先限制工具白名单和最大执行步数。

## 3. 评估：不要只看一个准确率

| 评估层 | 指标 | 说明 |
| --- | --- | --- |
| 检索 | Hit@K、MRR、版本正确率、权限过滤 | 正确内容是否被召回且可用 |
| 生成 | 引用支持率、事实一致性、完整性 | 回答是否有证据、是否遗漏关键条件 |
| 任务 | 完成率、转人工率、采纳率、重复澄清 | 用户问题是否真的解决 |
| 安全 | 越权、注入、敏感输出、违规动作 | 是否突破权限与安全边界 |
| 工程 | P50/P95 延迟、错误率、并发、成本 | 能否稳定且经济地服务 |
| 业务 | 节省时间、转化、质量、投诉 | 是否带来可解释价值 |

离线集要包含高频问题、长尾问题、边界问题、对抗问题和“应该拒答”的问题。线上评估要按用户、任务和风险等级分层，避免总体平均掩盖高危错误。

## 4. 案例一：华东某零售集团

### 案例 1：华东某零售集团的“Text-to-SQL与语义层协同”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“Text-to-SQL与语义层协同”映射到“数据标准、指标口径与主数据”中的编码，而不是泛泛讨论概念。
- **触发事件**：会员数量与财务、门店、线上渠道各自口径不同，董事会无法判断真实用户规模。
- **业务与数据范围**：手机号、会员卡、设备、登录账号、匿名行为、合并关系和历史等级。数据侧重点采集源系统字段、映射表、历史版本和样例，并与埋点平台、CRM、订单系统中的时间、状态和责任人信息对齐。
- **需要回答的问题**：类型、长度、枚举、单位和空值语义。
- **关键障碍**：手机号空值与变更造成误合并，匿名与登录身份未建立可信关联。同时要防止埋点重复把表面指标带偏。
- **处理过程**：定义会员唯一标识、候选匹配和人工复核规则，保留合并前后关系，指标区分注册、活跃和可触达会员。实施时把“标准变更执行影响分析、评审、通知、验证和回滚”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例项目用重复率、误合并率、覆盖率和跨期一致性评估 OneID。验收至少同时看主指标、源系统字段、映射表、历史版本和样例和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把业务定义、编码、主键、指标公式、权威源和责任人变成可执行标准，并通过版本、评审和对账控制变更。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

## 5. Python：检索与任务评估

### 检索、Agent 或模型任务实现

```sql
-- "Text-to-SQL与语义层协同"
-- 主数据候选匹配：确定性规则优先，模糊结果进入人工复核。
WITH normalized AS (
  SELECT
    source_system,
    source_id,
    REGEXP_REPLACE(LOWER(TRIM(entity_name)), '\\s+', '') AS normalized_name,
    COALESCE(unified_social_credit_code, business_license_no) AS strong_key
  FROM ods_master_entity
  WHERE dt = DATE '2026-11-05'
)
SELECT
  a.source_system AS left_source,
  a.source_id AS left_id,
  b.source_system AS right_source,
  b.source_id AS right_id,
  CASE WHEN a.strong_key IS NOT NULL THEN 'strong_key' ELSE 'name_review' END AS match_type,
  CASE WHEN a.strong_key IS NOT NULL THEN 1.0 ELSE 0.8 END AS confidence
FROM normalized a
JOIN normalized b
  ON (
    a.strong_key = b.strong_key
    OR (a.strong_key IS NULL AND b.strong_key IS NULL AND a.normalized_name = b.normalized_name)
  )
 AND (a.source_system <> b.source_system OR a.source_id < b.source_id);

-- 合并前评估重复率、误合并率、覆盖率、有效期和历史关系；保留来源、规则版本与人工复核。
```

### 标题专属数据与失败分层 SQL

```sql
-- Text-to-SQL与语义层协同：留存同期群诊断（产品 × 渠道）
WITH scoped AS (
  SELECT
    user_id AS entity_key,
    event_id,
    event_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_analysis_event
  WHERE event_time >= DATE '2026-04-01'
    AND event_time <  DATE '2026-07-01'
    AND subject_key = 'text_to_sql'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '转化率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

示例代码只展示可测试结构。真实系统还需要模型服务、向量库、权限、日志、缓存、限流、敏感检查和人工反馈，不应把安全完全交给提示词。

## 6. 案例二：华南某制造集团

### 案例 2：华南某制造集团的“Text-to-SQL与语义层协同”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“Text-to-SQL与语义层协同”映射到“数据标准、指标口径与主数据”中的变更，而不是泛泛讨论概念。
- **触发事件**：同一物料在采购、生产、仓储和财务使用不同编码，集团分析经常断链。
- **业务与数据范围**：供应商料号、内部料号、制造商料号、单位、批次和有效期。数据侧重点采集版本记录、影响分析、回滚和下游确认，并与埋点平台、CRM、订单系统中的时间、状态和责任人信息对齐。
- **需要回答的问题**：谁提出、谁评审、谁批准、何时生效。
- **关键障碍**：各单位独立维护编码，单位换算和停用状态没有统一标准。同时要防止分母漂移把表面指标带偏。
- **处理过程**：建立物料主数据权威源、映射与清洗规则，保留历史编码和有效期，关键变更需跨域评审。实施时把“标准必须包含业务定义、技术定义、权威源、负责人、版本和生效时间”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：复合案例让采购、生产和财务能够围绕同一主数据对账。验收至少同时看主指标、版本记录、影响分析、回滚和下游确认和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把业务定义、编码、主键、指标公式、权威源和责任人变成可执行标准，并通过版本、评审和对账控制变更。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

## 7. 架构与工程链路

| 层次 | 本文建议 | 关键问题 | 验收证据 |
| --- | --- | --- | --- |
| 数据源 | 埋点平台、CRM、订单系统 | 权威源、更新频率、主键和权限 | 接口或表清单 |
| 接入 | 批、流或 CDC 按业务时延选择 | 重复、顺序、断点续传和回放 | 延迟与幂等测试 |
| 存储 | 按访问模式选择数据湖、数仓或 OLAP | 分区、格式、生命周期和成本 | 容量与查询评测 |
| 计算 | SQL、Spark、Flink 或 Python 服务 | 粒度、状态、资源和失败恢复 | 压测与执行计划 |
| 治理 | 元数据、质量、血缘、权限 | 责任、规则、影响分析和审计 | 规则结果与变更记录 |
| 服务 | 指标、API、看板或应用 | SLA、缓存、限流和版本 | 监控与验收样例 |

推荐把链路拆成六层：数据与知识准备、检索或特征、模型调用、工具执行、评估与审核、监控与反馈。每层都要有版本、日志和失败处理。Agent 工具调用应在服务端校验参数与权限，不能只依赖模型“自觉”。

## 8. 监控、成本与安全

- 监控请求量、延迟、错误码、超时、重试和缓存命中。
- 记录检索文档版本、模型版本、提示词版本和关键参数。
- 对失败分类：检索缺失、上下文过长、工具失败、权限拒绝、模型拒答、结果不合规。
- 设置单位任务成本、每租户预算和异常调用告警。
- 对提示注入、越权、敏感信息和危险动作做专门测试。
- 保留人工复核、转人工、回滚到旧模型和关闭工具的开关。

## 9. 第三个案例与上线验收

### 案例 3：华北某互联网平台的“Text-to-SQL与语义层协同”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“Text-to-SQL与语义层协同”映射到“数据标准、指标口径与主数据”中的主键，而不是泛泛讨论概念。
- **触发事件**：不同团队对活跃用户和留存率有十几个版本，实验结论相互冲突。
- **业务与数据范围**：指标名称、公式、粒度、时间窗、排除条件、版本和下游使用清单。数据侧重点采集重复率、误合并率、有效期和跨系统映射，并与埋点平台、CRM、订单系统中的时间、状态和责任人信息对齐。
- **需要回答的问题**：唯一标识、合并、拆分和历史关系如何处理。
- **关键障碍**：指标只存在于 SQL 和文档，变更没有负责人和下游通知。同时要防止把相关性误写成因果把表面指标带偏。
- **处理过程**：建立原子指标与派生指标分层，公式版本化，关键口径进入语义层并通过单测。实施时把“主数据合并保留来源、规则、置信度和人工复核记录”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例治理用口径争议数、重复开发量、变更影响时间和使用覆盖率衡量。验收至少同时看主指标、重复率、误合并率、有效期和跨系统映射和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把业务定义、编码、主键、指标公式、权威源和责任人变成可执行标准，并通过版本、评审和对账控制变更。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

| 验收项 | 最低要求 | 证据 |
| --- | --- | --- |
| 任务定义 | 输入输出和失败路径明确 | 产品说明、评测集 |
| 数据授权 | 来源、用途和权限可追溯 | 数据卡、授权记录 |
| 离线评估 | 覆盖常规、边界和拒答 | 评测报告 |
| 线上灰度 | 有对照组和护栏指标 | 实验或灰度记录 |
| 安全 | 越权、注入和敏感输出已测试 | 红队与审计报告 |
| 成本 | 单位请求预算和上限明确 | 账单与调用日志 |
| 运营 | 有反馈、复盘和回滚 | 周报、事故演练 |

1. 先写清“Text-to-SQL与语义层协同”的目标：把业务定义、编码、主键、指标公式、权威源和责任人变成可执行标准，并通过版本、评审和对账控制变更。
2. 专题检查：标准必须包含业务定义、技术定义、权威源、负责人、版本和生效时间
3. 专题检查：主数据合并保留来源、规则、置信度和人工复核记录
4. 专题检查：指标公式与粒度进入语义层，不允许散落在个人 SQL 中
5. 专题检查：标准变更执行影响分析、评审、通知、验证和回滚
6. 明确“Text-to-SQL与语义层协同”服务的使用者、决策动作和不做范围，并把成功标准写成可观察指标。
7. 为用户、会话、行为事件分别确认主键、时间和状态，画出从源系统到结果的链路。
8. 先做字段血缘和质量画像，检查事件主键唯一、分子分母同口径、匿名与登录身份已打通。
9. 用同周期基线和至少两个维度拆解问题，避免只比较一个异常周。
10. 抽取正常、异常和边界样本回查原始业务单据，记录抽样方法与结论。
11. 选择一种代码实现并保留参数、版本、执行日志和结果快照，确保别人可以复跑。
12. 上线前定义告警阈值、回滚条件和责任人；上线后按周观察主指标与护栏指标。
13. 复盘时区分数据问题、业务变化、方案偏差和外部因素，并把改进项转成有时限的任务。

## 扩展实战：Text-to-SQL与语义层协同的四个可执行案例

> [!info] 内容说明

### 扩展代码一：从Text-to-SQL与语义层协同回到可核对明细

```sql
-- Text-to-SQL与语义层协同：行动前后与分组增量
WITH scoped AS (
  SELECT
    user_id AS entity_key,
    产品 AS decision_group,
    event_time AS event_date,
    metric_value,
    CASE
      WHEN event_time <  :action_date THEN 'before'
      ELSE 'after'
    END AS period_label
  FROM fact_analysis_event
  WHERE event_time >= :analysis_start
    AND event_time <  :analysis_end
    AND subject_key = 'text_to_sql'
),
grouped AS (
  SELECT
    decision_group,
    period_label,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    AVG(metric_value) AS metric_avg,
    SUM(metric_value) AS metric_sum
  FROM scoped
  GROUP BY decision_group, period_label
),
compared AS (
  SELECT
    decision_group,
    MAX(CASE WHEN period_label = 'before' THEN metric_avg END) AS before_avg,
    MAX(CASE WHEN period_label = 'after' THEN metric_avg END) AS after_avg,
    MAX(CASE WHEN period_label = 'before' THEN entity_cnt END) AS before_cnt,
    MAX(CASE WHEN period_label = 'after' THEN entity_cnt END) AS after_cnt
  FROM grouped
  GROUP BY decision_group
)
SELECT
  decision_group,
  before_avg,
  after_avg,
  after_avg - before_avg AS naive_delta,
  '增量收益' AS metric_name,
  '标准必须包含业务定义、技术定义、权威源、负责人、版本和生效时间' AS required_evidence
FROM compared
WHERE before_cnt >= 30 AND after_cnt >= 30
ORDER BY ABS(after_avg - before_avg) DESC;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把Text-to-SQL与语义层协同的验收证据写成门禁

```python
from datetime import date
from hashlib import sha256

import pandas as pd

SUBJECT = "Text-to-SQL与语义层协同"
BLOCKING_RULES = ["事件主键唯一","分子分母同口径","匿名与登录身份已打通"]


def validate_release(frame: pd.DataFrame, start: date, end: date) -> dict:
    scoped = frame.loc[
        frame["event_date"].between(pd.Timestamp(start), pd.Timestamp(end))
        & (frame["subject_key"] == "text_to_sql")
    ].copy()
    checks = {
        "has_rows": len(scoped) > 0,
        "event_id_unique": not scoped["event_id"].duplicated().any(),
        "entity_key_complete": scoped["entity_key"].notna().all(),
        "event_time_present": scoped["event_time"].notna().all(),
        "scope_matches": scoped["subject_key"].nunique() == 1,
    }
    payload = f"{SUBJECT}|{start}|{end}|{len(scoped)}|{sorted(checks.items())}"
    return {
        "subject": SUBJECT,
        "rows": len(scoped),
        "checks": checks,
        "blocking_rules": BLOCKING_RULES,
        "release_allowed": all(checks.values()),
        "evidence_hash": sha256(payload.encode("utf-8")).hexdigest(),
    }
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。

| 对象与粒度 | 一行数据代表用户、事件、快照还是结果 | 主键、版本、有效时间和边界样本 | 阻断 |
| 时间语义 | 业务发生、数据可见、决策采用是否混用 | event_time、入仓时间、行动时间轴 | 阻断 |
| 指标口径 | 转化率的分子、分母和排除项是否冻结 | 指标字典、SQL、对账结果 | 阻断正式指标 |
| 状态与关联 | 业务问题 → 指标定义 → 数据准备 → 探索分析是否可达且可追溯 | 状态机、明细、操作日志 | 阻断关键链路 |
| 权限与最小字段 | 派生表、导出和临时授权是否扩大访问范围 | 分类分级、字段血缘、访问日志 | 阻断导出 |
| 恢复与审计 | 失败后能否定位影响范围并幂等重跑 | 参数、版本、分区清单、补数对账 | 阻断发布 |
