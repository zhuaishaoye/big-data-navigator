## 🔍 索引技术定义

**数据库索引**（Database Index）是一种独立的数据结构，用于加速数据检索操作，通过维护索引键到数据记录的访问结构来减少检索成本；树索引通常维护有序键，Hash索引则采用哈希组织，是否避免全表扫描取决于查询与执行计划。以平衡树索引的键定位为例，查找通常可达到O(log n)复杂度；完整查询成本还取决于匹配行数、回表、排序及执行计划，并非所有索引或查询都具有这一复杂度。

### 核心工作机制

#### B-Tree索引结构原理
```json
       [50]
      /    \
   [25]    [75]
   /  \    /  \
[10][35][60][90]
```

索引内部工作流程：
1. **索引构建阶段**：
   - 扫描表数据，提取索引列值
   - 按列值排序并构建B-Tree结构
   - 叶子节点内容取决于存储引擎和索引类型：可能包含行定位符、InnoDB二级索引中的主键值，或聚簇索引中的数据行

2. **查询执行阶段**：
   - 解析WHERE条件中的索引列
   - 从根节点开始进行二分查找
   - 定位到叶子节点获取行指针
   - 根据行指针回表获取完整数据

3. **存储层面**：
   - 非聚簇索引通常使用独立索引页；聚簇索引的叶子页本身存储数据行
   - 使用页分裂和合并维护平衡性
   - 通过缓冲池管理热点索引页

## 🏗️ 索引类型与特性

### 1. 聚簇索引（Clustered Index）
**技术特性**：数据行按索引键顺序物理存储，索引的叶子节点直接包含数据行，每个表只能有一个聚簇索引

```sql
-- MySQL InnoDB 主键自动创建聚簇索引
CREATE TABLE users (
    user_id INT PRIMARY KEY AUTO_INCREMENT,  -- 聚簇索引
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 查看聚簇索引信息
SHOW INDEX FROM users WHERE Key_name = 'PRIMARY';
```

**性能特点**：
- 范围查询性能优异（ORDER BY主键字段）
- 插入数据可能产生页分裂
- 主键查询无需回表操作

### 2. 非聚簇索引（Non-Clustered Index）
**技术特性**：非聚簇索引的行定位方式依赖存储引擎；例如MySQL InnoDB二级索引的叶子记录包含索引键值和主键值，通过主键访问聚簇索引获取未覆盖的列。

```sql
-- 创建非聚簇索引用于高频查询字段
CREATE INDEX idx_username ON users(username) 
USING BTREE 
COMMENT '用户名查询索引';

CREATE INDEX idx_email ON users(email)
USING BTREE
COMMENT '邮箱查询索引';

-- 查看索引统计信息
ANALYZE TABLE users;
SHOW INDEX FROM users WHERE Key_name = 'idx_username';
```

**回表查询示例**：
```sql
-- 需要回表的查询（索引覆盖不了所有字段）
EXPLAIN SELECT user_id, username, email, created_at 
FROM users WHERE username = 'john_doe';
```

### 3. 复合索引（Composite Index）
**技术特性**：多个字段组合的索引，遵循最左前缀匹配原则，索引列顺序影响查询优化效果

```sql
-- 复合索引设计：高选择性字段在前
CREATE INDEX idx_user_query ON users(status, created_at, username)
COMMENT '用户查询复合索引';

-- 支持的查询模式
SELECT * FROM users WHERE status = 'active';                    -- ✅ 使用索引
SELECT * FROM users WHERE status = 'active' AND created_at > '2024-01-01';  -- ✅ 使用索引
SELECT * FROM users WHERE status = 'active' AND created_at > '2024-01-01' AND username LIKE 'john%';  -- 可利用status和created_at定位范围；username能否用于索引条件过滤等优化需结合执行计划判断，不能据此认定所有列都参与范围定位

-- 不支持的查询模式
SELECT * FROM users WHERE created_at > '2024-01-01';            -- 缺少最左列条件，通常不能按常规最左前缀进行范围定位；是否采用索引扫描或其他访问方式需查看执行计划
SELECT * FROM users WHERE username = 'john';                    -- 跳过前缀字段，通常不能按常规最左前缀进行范围定位；是否使用索引仍由优化器结合数据和查询决定
```

### 4. 唯一索引（Unique Index）
**技术特性**：在提供查询优化的同时，在索引层面强制字段值唯一性约束

```sql
-- 业务唯一性约束索引
CREATE UNIQUE INDEX idx_unique_email ON users(email)
COMMENT '邮箱唯一性索引';

CREATE UNIQUE INDEX idx_unique_phone ON users(phone)
COMMENT '手机号唯一性索引';

-- 复合唯一索引
CREATE UNIQUE INDEX idx_unique_user_tenant ON users(username, tenant_id)
COMMENT '多租户用户名唯一性索引';
```

### 5. 部分索引（Partial Index）
**技术特性**：仅对满足特定WHERE条件的行建立索引，减少索引大小和维护开销

```sql
-- PostgreSQL 部分索引
CREATE INDEX idx_active_users ON users(username, email)
WHERE status = 'active' AND deleted_at IS NULL;
COMMENT ON INDEX idx_active_users IS '活跃用户部分索引';

-- 设计设想：仅索引近30天订单。
-- 以下表达式包含NOW()，不能用于MySQL函数索引，也不能形成自动滚动的时间窗口：
-- CREATE INDEX idx_recent_orders ON orders((CASE WHEN created_at > DATE_SUB(NOW(), INTERVAL 30 DAY) THEN user_id END));
-- MySQL函数索引要求8.0.13+；近30天查询应另行评估普通复合索引、分区或由业务维护的标记字段。
```

### 6. Hash索引
**技术特性**：基于哈希算法，等值查询性能O(1)，不支持范围查询

```sql
-- MySQL Memory引擎支持Hash索引
CREATE TABLE user_sessions (
    session_id VARCHAR(64) NOT NULL,
    user_id INT NOT NULL,
    data VARCHAR(1024),
    INDEX idx_session_hash (session_id) USING HASH
) ENGINE=MEMORY;
```

### 7. 全文索引（Full-Text Index）
**技术特性**：专门用于文本搜索的倒排索引结构

```sql
-- 创建全文索引
CREATE TABLE articles (
    id INT PRIMARY KEY AUTO_INCREMENT,
    title VARCHAR(200),
    content TEXT,
    FULLTEXT idx_content_search (title, content) WITH PARSER ngram
);

-- 全文搜索查询
SELECT * FROM articles 
WHERE MATCH(title, content) AGAINST('数据库索引优化' IN BOOLEAN MODE);
```

## ⚡ 索引管理与操作

### 企业级索引创建策略

#### 1. 索引选择性分析
```sql
-- 计算字段选择性（不同值占比）
SELECT 
    COUNT(DISTINCT status) / COUNT(*) AS status_selectivity,
    COUNT(DISTINCT email) / COUNT(*) AS email_selectivity,
    COUNT(DISTINCT created_at) / COUNT(*) AS date_selectivity
FROM users;

-- 不同值占比不能单独决定是否建索引；需结合值分布、查询过滤比例、排序需求、查询频率及执行计划评估
```

#### 2. 基于查询模式的索引设计
```sql
-- 分析慢查询日志确定索引需求
-- 高频等值查询：单字段索引
CREATE INDEX idx_user_status ON users(status) 
WHERE status IN ('active', 'pending', 'suspended');

-- 多条件复合查询：复合索引（选择性高的字段在前）
CREATE INDEX idx_order_query ON orders(status, user_id, created_date)
COMMENT '订单查询复合索引：状态+用户+时间';

-- 覆盖索引：避免回表查询
CREATE INDEX idx_user_profile_cover ON users(user_id, username, email, status)
COMMENT '用户资料覆盖索引';
```

#### 3. 在线索引创建（生产环境）
```sql
-- MySQL 8.0+ 在线DDL操作
CREATE INDEX idx_username ON users(username)
COMMENT '用户名查询索引'
ALGORITHM=INPLACE LOCK=NONE;

-- PostgreSQL 并发索引创建
CREATE INDEX CONCURRENTLY idx_email ON users(email);

-- SQL Server 在线索引重建
ALTER INDEX idx_username ON users REBUILD WITH (ONLINE = ON);
```

### 索引监控与维护

#### 1. 索引使用统计查询
```sql
-- MySQL 索引使用情况
SELECT 
    t.table_name,
    t.index_name,
    t.non_unique,
    t.cardinality,
    s.table_rows,
    ROUND(t.cardinality / s.table_rows * 100, 2) AS selectivity_percent
FROM information_schema.statistics t
JOIN information_schema.tables s ON t.table_name = s.table_name AND t.table_schema = s.table_schema
WHERE t.table_schema = 'your_database'
AND t.index_name != 'PRIMARY'
ORDER BY selectivity_percent DESC;

-- 查看未使用的索引
SELECT 
    object_schema AS database_name,
    object_name AS table_name,
    index_name,
    count_star AS index_usage_count
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE index_name IS NOT NULL
AND count_star = 0
AND object_schema = 'your_database'
ORDER BY object_name;
```

#### 2. 索引碎片分析和维护
```sql
-- MySQL InnoDB 索引碎片查询
SELECT 
    table_name,
    data_length,
    index_length,
    data_free,
    ROUND(data_free / (data_length + index_length) * 100, 2) AS fragmentation_percent
FROM information_schema.tables
WHERE table_schema = 'your_database'
AND data_free > 0
ORDER BY fragmentation_percent DESC;

-- 索引重建和优化
OPTIMIZE TABLE users;  -- MySQL
REINDEX INDEX idx_username;  -- PostgreSQL
ALTER INDEX idx_username REBUILD;  -- SQL Server
```

#### 3. 索引大小和性能监控
```sql
-- 查看索引占用空间
SELECT 
    table_name,
    index_name,
    ROUND(stat_value * @@innodb_page_size / 1024 / 1024, 2) AS size_mb
FROM mysql.innodb_index_stats
WHERE stat_name = 'size'
AND database_name = 'your_database'
ORDER BY size_mb DESC;

-- 查看索引扫描统计
SHOW ENGINE INNODB STATUS\G
```

## ⚠️ 索引设计最佳实践与注意事项

### 索引设计核心原则

#### 1. 查询驱动索引设计
```sql
-- 基于实际查询模式设计索引，而非盲目创建
-- 分析慢查询日志，识别高频查询模式

-- 示例：电商订单查询分析
-- 查询1：用户查看自己的订单列表
SELECT order_id, status, total_amount, created_at 
FROM orders 
WHERE user_id = 12345 
ORDER BY created_at DESC 
LIMIT 20;

-- 对应索引设计
CREATE INDEX idx_orders_user_created ON orders(user_id, created_at DESC)
COMMENT '支持用户订单列表查询的复合索引';
```

#### 2. 索引选择性评估
```sql
-- 计算字段选择性，选择性 = 不同值数量 / 总行数
SELECT 
    'gender' AS field_name,
    COUNT(DISTINCT gender) AS distinct_values,
    COUNT(*) AS total_rows,
    ROUND(COUNT(DISTINCT gender) / COUNT(*), 4) AS selectivity
FROM users
UNION ALL
SELECT 
    'email' AS field_name,
    COUNT(DISTINCT email),
    COUNT(*),
    ROUND(COUNT(DISTINCT email) / COUNT(*), 4)
FROM users;

-- 选择性评估说明：
-- 0.1和0.01不是通用建索引阈值；不同值占比需与实际值分布和查询条件结合分析
-- 低不同值占比字段也可能因稀有值过滤、排序或覆盖查询而具有索引价值
```

#### 3. 复合索引字段排序策略
```sql
-- 复合索引字段排序原则：
-- 1. 等值查询字段在前
-- 2. 范围查询字段在后
-- 3. 高选择性字段在前
-- 4. 考虑ORDER BY字段

-- 优化前：低效的索引设计
CREATE INDEX idx_orders_bad ON orders(created_at, user_id, status);

-- 优化后：基于查询模式的索引设计
-- 查询：SELECT * FROM orders WHERE user_id = ? AND status = ? ORDER BY created_at DESC
CREATE INDEX idx_orders_optimized ON orders(user_id, status, created_at DESC);
```

### 避免索引设计误区

#### 1. 过度索引问题
```sql

CREATE INDEX idx_users_status ON users(status);        -- 四值字段：按本文定义，选择性为不同值数量/总行数；各值的实际分布需另行统计

-- ✅ 正确：基于实际查询需求合并索引
```

```sql
CREATE PROCEDURE CleanupUnusedIndexes()
BEGIN
    DECLARE done INT DEFAULT FALSE;
    DECLARE table_name VARCHAR(64);
    DECLARE index_name VARCHAR(64);
    
    DECLARE unused_cursor CURSOR FOR 
        SELECT object_name, index_name
        FROM performance_schema.table_io_waits_summary_by_index_usage
        WHERE count_star = 0 
        AND index_name IS NOT NULL 
        AND object_schema = DATABASE();
    
    DECLARE CONTINUE HANDLER FOR NOT FOUND SET done = TRUE;
    
    OPEN unused_cursor;
    cleanup_loop: LOOP
        FETCH unused_cursor INTO table_name, index_name;
        IF done THEN
            LEAVE cleanup_loop;
        END IF;

        INSERT INTO index_cleanup_log (table_name, index_name, cleanup_date)
        VALUES (table_name, index_name, CURDATE());
        
    END LOOP;
    CLOSE unused_cursor;
END //
```

#### 索引性能报告生成
```sql
-- 创建索引性能监控视图
CREATE VIEW v_index_performance_report AS
SELECT 
    t.table_name,
    t.index_name,
    t.cardinality,
    ROUND(t.cardinality / tab.table_rows * 100, 2) AS selectivity_percent,
    tio.count_read,
    tio.count_write,
    ROUND(tio.sum_timer_read / 1000000000000, 3) AS total_read_seconds,
    ROUND(tio.sum_timer_write / 1000000000000, 3) AS total_write_seconds,
    ROUND(
        (SELECT SUM(stat_value * @@innodb_page_size) 
         FROM mysql.innodb_index_stats 
         WHERE database_name = t.table_schema 
         AND table_name = t.table_name 
         AND index_name = t.index_name 
         AND stat_name = 'size') / 1024 / 1024, 2
    ) AS index_size_mb,
    CASE 
        WHEN tio.count_read = 0 THEN 'UNUSED'
        WHEN tio.count_read < 100 THEN 'LOW_USAGE'  
        WHEN tio.count_read < 1000 THEN 'MEDIUM_USAGE'
        ELSE 'HIGH_USAGE'
    END AS usage_category
FROM information_schema.statistics t
JOIN information_schema.tables tab ON t.table_name = tab.table_name AND t.table_schema = tab.table_schema
LEFT JOIN performance_schema.table_io_waits_summary_by_index_usage tio 
    ON tio.object_name = t.table_name AND tio.index_name = t.index_name
WHERE t.table_schema = 'your_database'
AND t.index_name != 'PRIMARY';

-- 生成索引优化建议报告
SELECT 
    table_name,
    index_name,
    index_size_mb,
    usage_category,
    CASE 
        WHEN usage_category = 'UNUSED' THEN 'Consider dropping this index'
        WHEN usage_category = 'LOW_USAGE' AND index_size_mb > 100 THEN 'Review index necessity'
        WHEN selectivity_percent < 1 THEN 'Low selectivity, consider composite index'
        ELSE 'Index performing well'
    END AS optimization_suggestion
FROM v_index_performance_report
WHERE usage_category IN ('UNUSED', 'LOW_USAGE') OR selectivity_percent < 1
ORDER BY index_size_mb DESC;
```

```sql
AND status IN ('paid', 'delivered');

-- 4. 分区维护脚本
-- 分区扩展思路示例：下列ADD PARTITION过程不适用于已有MAXVALUE分区的orders_large；该表需重组p_future分区后才能增加具体年份分区
DELIMITER //
CREATE PROCEDURE CreateNewPartition(IN partition_year INT)
BEGIN
    SET @sql = CONCAT(
        'ALTER TABLE orders_large ADD PARTITION (',
        'PARTITION p', partition_year, ' VALUES LESS THAN (', partition_year + 1, '))'
    );
    PREPARE stmt FROM @sql;
    EXECUTE stmt;
    DEALLOCATE PREPARE stmt;
END //
DELIMITER ;
```

## 📝 索引设计最佳实践总结

### 设计原则
1. **查询驱动设计**：基于实际查询模式设计索引，避免盲目创建
2. **选择性评估**：结合过滤比例、值分布、查询频率和执行计划评估索引；选择性 > 0.1不能作为通用建索引门槛
3. **复合索引排序**：等值查询字段在前，范围查询字段在后
4. **覆盖索引应用**：包含查询所需字段，减少回表操作

### 维护策略
1. **定期监控**：使用performance_schema监控索引使用情况
2. **清理无效索引**：定期清理未使用或低效的索引
3. **在线维护**：在数据库、版本和操作支持的条件下使用在线DDL降低影响；仍需评估元数据锁、资源占用和失败风险，不能保证业务不中断
4. **碎片整理**：定期重建高碎片率的索引

### 性能权衡
1. **读写平衡**：权衡查询性能提升与写入性能损失
2. **存储成本**：按工作负载、容量和维护成本评估索引空间；索引总大小不超过表数据大小的50%不是通用限制
3. **内存使用**：关注索引在缓冲池中的内存占用
4. **维护开销**：避免创建过多或过复杂的索引

**专家建议 💡**
- 生产环境索引变更必须经过充分测试和性能评估
- 建立索引设计评审机制，避免重复或冲突的索引
- 使用索引监控工具建立自动化的性能报告体系
- 制定明确的索引命名规范和生命周期管理流程
