## 🔍 事务技术定义

**数据库事务**（Database Transaction）是数据库管理系统中的一个逻辑工作单元，由一组相关的数据库操作组成。事务确保这些操作作为一个不可分割的整体执行，即要么全部成功提交，要么全部失败回滚。

### 核心技术特性（ACID）

#### 1. 原子性（Atomicity）
事务中的所有操作作为一个不可分割的单元，要么全部执行成功，要么全部撤销。
```sql
-- 转账事务示例：两个操作必须都成功
BEGIN TRANSACTION;
UPDATE accounts SET balance = balance - 1000 WHERE account_id = 'A001';
UPDATE accounts SET balance = balance + 1000 WHERE account_id = 'A002';
COMMIT;  -- 或者 ROLLBACK 回滚
```

#### 2. 一致性（Consistency）
事务执行前后，数据库必须从一个一致性状态转移到另一个一致性状态。
```sql
-- 保证业务规则一致性：账户余额不能为负
BEGIN TRANSACTION;
-- 检查余额是否足够
SELECT balance FROM accounts WHERE account_id = 'A001' FOR UPDATE;
-- 仅在余额足够时才执行转账
UPDATE accounts SET balance = balance - 1000 
WHERE account_id = 'A001' AND balance >= 1000;
COMMIT;
```

#### 3. 隔离性（Isolation）
隔离性规定并发事务之间的数据可见性与相互影响边界；具体允许哪些并发现象取决于隔离级别和数据库实现，不能将所有隔离级别都理解为完全互不干扰。
```sql
-- 事务A
BEGIN TRANSACTION;
SELECT balance FROM accounts WHERE account_id = 'A001';
-- ... 其他操作
COMMIT;

-- 事务B（并发执行）
BEGIN TRANSACTION;
UPDATE accounts SET balance = balance + 500 WHERE account_id = 'A001';
COMMIT;
```

#### 4. 持久性（Durability）
持久性要求成功提交的事务结果在数据库所承诺的故障模型内能够恢复；实际保证取决于存储引擎、日志持久化配置及存储系统，不能将所有配置下的COMMIT都视为崩溃后绝不丢失。
```sql
-- 提交后的持久化保证取决于存储引擎、日志持久化配置及存储系统
BEGIN TRANSACTION;
INSERT INTO audit_log (action, timestamp) VALUES ('transfer', NOW());
COMMIT;  -- 提交事务；是否已同步持久化到存储介质取决于数据库配置
```

## 🏗️ 事务控制语法

### 基本事务操作
```sql
-- 显式开始事务
START TRANSACTION;  -- MySQL、PostgreSQL；SQL Server使用BEGIN TRANSACTION

-- 执行事务操作
INSERT INTO orders (customer_id, amount) VALUES (1001, 299.99);
UPDATE inventory SET quantity = quantity - 1 WHERE product_id = 'P001';
INSERT INTO order_items (order_id, product_id, quantity) VALUES (LAST_INSERT_ID(), 'P001', 1);

-- 提交事务
COMMIT;
```

### 事务回滚操作
```sql
-- 开始事务
BEGIN TRANSACTION;

-- 执行操作
UPDATE accounts SET balance = balance - 5000 WHERE account_id = 'A001';

-- 检查业务逻辑
SELECT balance FROM accounts WHERE account_id = 'A001';

-- 如果余额不足，回滚事务
IF (balance < 0) THEN
    ROLLBACK;
ELSE
    COMMIT;
END IF;
```

### 保存点（Savepoint）机制
```sql
-- 复杂事务中的部分回滚
BEGIN TRANSACTION;

-- 第一阶段操作
INSERT INTO customers (name, email) VALUES ('John Doe', 'john@example.com');
SAVEPOINT customer_created;

-- 第二阶段操作（可能失败）
INSERT INTO orders (customer_id, amount) VALUES (LAST_INSERT_ID(), 999.99);
SAVEPOINT order_created;

-- 第三阶段操作（失败）
INSERT INTO payments (order_id, amount) VALUES (LAST_INSERT_ID(), 999.99);
-- 如果这里失败，只回滚到订单创建后
ROLLBACK TO order_created;

-- 最终提交成功的部分
COMMIT;
```

### 自动提交控制
```sql
-- 关闭自动提交（MySQL）
SET AUTOCOMMIT = 0;

-- 执行多个操作
UPDATE products SET price = price * 1.1 WHERE category = 'electronics';
UPDATE products SET price = price * 1.05 WHERE category = 'books';

-- 手动提交
COMMIT;

-- 重新开启自动提交
SET AUTOCOMMIT = 1;
```

## 🔐 事务隔离级别

### SQL标准隔离级别

#### 1. READ UNCOMMITTED（未提交读）
**特性**：允许读取未提交的数据，可能出现脏读
```sql
-- 设置隔离级别
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

-- 事务A：修改但未提交
BEGIN TRANSACTION;
UPDATE accounts SET balance = 10000 WHERE account_id = 'A001';
-- 未 COMMIT

-- 事务B：可以读到未提交的数据（脏读）
SELECT balance FROM accounts WHERE account_id = 'A001';  -- 返回 10000
```

#### 2. READ COMMITTED（已提交读）
**特性**：只能读取已提交的数据，避免脏读，但可能出现不可重复读
```sql
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- 事务A
BEGIN TRANSACTION;
SELECT balance FROM accounts WHERE account_id = 'A001';  -- 第一次读取：5000
-- ... 其他操作

-- 事务B（并发执行）
UPDATE accounts SET balance = 8000 WHERE account_id = 'A001';
COMMIT;

-- 事务A 继续
SELECT balance FROM accounts WHERE account_id = 'A001';  -- 第二次读取：8000
COMMIT;
```

#### 3. REPEATABLE READ（可重复读）
**特性**：同一事务内多次读取的结果一致，但可能出现幻读
```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- 事务A
BEGIN TRANSACTION;
SELECT COUNT(*) FROM orders WHERE customer_id = 1001;  -- 第一次：5

-- 事务B（并发执行）
INSERT INTO orders (customer_id, amount) VALUES (1001, 299.99);
COMMIT;

-- 事务A 继续
SELECT COUNT(*) FROM orders WHERE customer_id = 1001;  -- MySQL仍返回5（防幻读）
COMMIT;
```

#### 4. SERIALIZABLE（串行化）
**特性**：最高标准隔离级别，使成功提交的事务具有等价于某种串行执行顺序的效果；不要求物理串行执行，也不消除死锁、等待或事务重试。
```sql
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- 事务A
BEGIN TRANSACTION;
SELECT * FROM accounts WHERE balance > 5000;  -- 锁或冲突检测方式取决于数据库实现；MySQL InnoDB中的锁范围还取决于事务模式、索引及执行计划

-- 事务B（并发执行）
BEGIN TRANSACTION;
INSERT INTO accounts (account_id, balance) VALUES ('A999', 6000);  -- 等待锁释放
```

### 隔离级别对比表

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 性能 | 适用场景 |
|------------|------|----------|------|------|----------|
| READ UNCOMMITTED | ✓ | ✓ | ✓ | 最高 | 数据分析、报表生成 |
| READ COMMITTED | ✗ | ✓ | ✓ | 高 | Web应用、一般业务 |
| REPEATABLE READ | ✗ | ✗ | ✓/✗ | 中 | 批量处理、报表 |
| SERIALIZABLE | ✗ | ✗ | ✗ | 最低 | 金融系统、账务处理 |

## 🎯 业务应用场景

### 1. 电商订单系统
```sql
-- 订单提交事务：库存、订单、支付一致性
BEGIN TRANSACTION;

-- 1. 检查库存
SELECT quantity FROM inventory WHERE product_id = 'P001' FOR UPDATE;

-- 2. 更新库存
UPDATE inventory 
SET quantity = quantity - 2, 
    reserved = reserved + 2
WHERE product_id = 'P001' AND quantity >= 2;

-- 3. 创建订单
INSERT INTO orders (customer_id, total_amount, status) 
VALUES (1001, 599.98, 'pending');

-- 4. 创建订单项
INSERT INTO order_items (order_id, product_id, quantity, price) 
VALUES (LAST_INSERT_ID(), 'P001', 2, 299.99);

-- 5. 创建支付记录
INSERT INTO payments (order_id, amount, method, status) 
VALUES (LAST_INSERT_ID(), 599.98, 'credit_card', 'pending');

COMMIT;
```

### 2. 银行账户管理
```sql
-- 账户转账事务示意：必须校验金额、账户状态及每次更新的影响行数，并在任一步失败时回滚，才能维护资金守恒
BEGIN TRANSACTION;

-- 1. 验证账户状态
SELECT status FROM accounts WHERE account_id IN ('A001', 'A002') FOR UPDATE;

-- 2. 检查转出账户余额
SELECT balance FROM accounts WHERE account_id = 'A001' FOR UPDATE;

-- 3. 执行转账（仅在余额足够时）
UPDATE accounts 
SET balance = balance - 5000,
    last_transaction = NOW()
WHERE account_id = 'A001' 
AND balance >= 5000 
AND status = 'active';

-- 4. 转入目标账户
UPDATE accounts 
SET balance = balance + 5000,
    last_transaction = NOW()
WHERE account_id = 'A002' 
AND status = 'active';

-- 5. 记录交易日志
INSERT INTO transaction_log (from_account, to_account, amount, type, timestamp) 
VALUES ('A001', 'A002', 5000, 'transfer', NOW());

-- 检查影响行数，确保操作成功
IF (ROW_COUNT() > 0) THEN
    COMMIT;
ELSE
    ROLLBACK;
END IF;
```

### 3. 库存管理系统
```sql
-- 入库操作事务：库存、成本、供应商账务一致性
BEGIN TRANSACTION;

-- 1. 更新库存数量
UPDATE inventory 
SET quantity = quantity + 100,
    last_updated = NOW()
WHERE product_id = 'P001';

-- 2. 记录入库单
INSERT INTO purchase_orders (supplier_id, product_id, quantity, unit_cost, total_cost) 
VALUES (101, 'P001', 100, 25.00, 2500.00);

-- 3. 更新平均成本
UPDATE products 
SET avg_cost = (
    SELECT AVG(unit_cost) 
    FROM purchase_orders 
    WHERE product_id = 'P001' 
    AND created_at >= DATE_SUB(NOW(), INTERVAL 3 MONTH)
)
WHERE product_id = 'P001';

-- 4. 更新供应商账务
UPDATE supplier_accounts 
SET outstanding_balance = outstanding_balance + 2500.00
WHERE supplier_id = 101;

COMMIT;
```

## 🔒 并发控制与锁机制详解

### 锁机制技术原理

#### 1. 共享锁（Shared Lock, S-Lock）
**技术特性**：允许多个事务同时持有，但阻止排他锁的获取
```sql
-- 显式共享锁（MySQL）
BEGIN TRANSACTION;
SELECT balance FROM accounts WHERE account_id = 'A001' LOCK IN SHARE MODE;
-- 或者 MySQL 8.0+ 新语法
SELECT balance FROM accounts WHERE account_id = 'A001' FOR SHARE;

-- 其他事务可以继续获取共享锁
BEGIN TRANSACTION;
SELECT balance FROM accounts WHERE account_id = 'A001' LOCK IN SHARE MODE;  -- 成功
-- 但无法获取排他锁
UPDATE accounts SET balance = balance - 100 WHERE account_id = 'A001';  -- 等待
```

#### 2. 排他锁（Exclusive Lock, X-Lock）
**技术特性**：同一锁定对象上的排他锁与其他事务请求的共享锁、排他锁不兼容；这不意味着所有读取都会被阻塞，MVCC一致性读通常仍可读取可见版本。
```sql
-- 行级排他锁
BEGIN TRANSACTION;
SELECT balance FROM accounts WHERE account_id = 'A001' FOR UPDATE;
-- 其他事务对同一锁定记录请求不兼容锁时会等待；普通MVCC一致性读不一定等待
UPDATE accounts SET balance = balance - 1000 WHERE account_id = 'A001';
COMMIT;

-- 意向锁升级示例
BEGIN TRANSACTION;
-- 先获取意向排他锁(IX)，再获取行级排他锁(X)
UPDATE accounts SET balance = balance - 500 WHERE account_id = 'A001';
COMMIT;
```

#### 3. 锁的粒度层次
```sql
-- 表级锁
LOCK TABLES accounts WRITE;
UPDATE accounts SET interest_rate = 0.03;
UNLOCK TABLES;

-- 页级锁（存储引擎内部）
-- InnoDB不以页级事务锁作为行锁和表锁的中间层；内部页闩锁与事务锁不是同一机制

-- 行级锁（最细粒度）
BEGIN TRANSACTION;
-- 仅锁定满足条件的具体行
UPDATE accounts SET balance = balance + 100 WHERE account_id = 'A001';
COMMIT;
```

### 多版本并发控制（MVCC）

#### MVCC工作机制
```sql
-- InnoDB 的 MVCC 实现
-- InnoDB聚簇索引记录包含内部字段DB_TRX_ID和DB_ROLL_PTR；仅在需要生成隐藏聚簇索引时包含DB_ROW_ID。这些内部字段不是示例中可直接查询的业务version列

-- 事务A（读取）
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN TRANSACTION;
SELECT balance, version FROM accounts WHERE account_id = 'A001';  
-- 读取到版本100的数据：balance=5000

-- 事务B（修改）
BEGIN TRANSACTION;
UPDATE accounts SET balance = 8000 WHERE account_id = 'A001';  
-- 创建新版本101：balance=8000，旧版本保留在undo log中
COMMIT;

-- 事务A（再次读取）
SELECT balance FROM accounts WHERE account_id = 'A001';
-- 仍然读取版本100的数据：balance=5000（一致性读）
COMMIT;
```

#### 当前读与快照读
```sql
-- 快照读（Consistent Read）
-- 读取创建ReadView时的快照数据
BEGIN TRANSACTION;
SELECT balance FROM accounts WHERE account_id = 'A001';  -- 快照读

-- 当前读（Locking Read）
-- 读取当前最新提交的数据，需要加锁
SELECT balance FROM accounts WHERE account_id = 'A001' FOR UPDATE;  -- 当前读
SELECT balance FROM accounts WHERE account_id = 'A001' LOCK IN SHARE MODE;  -- 当前读
```

### 死锁检测与处理机制

#### 死锁产生的四个必要条件
1. **互斥条件**：资源只能被一个事务占用
2. **持有等待**：事务持有资源的同时等待其他资源
3. **非抢占**：资源不能被强制回收
4. **环形等待**：事务形成等待环路

#### 死锁预防策略
```sql
-- 策略1：统一资源获取顺序
-- ❌ 容易死锁的写法
-- 事务A：先锁A001，后锁A002
-- 事务B：先锁A002，后锁A001

-- ✅ 防止死锁的写法
BEGIN TRANSACTION;
-- 按主键排序统一加锁顺序
SELECT * FROM accounts 
WHERE account_id IN ('A001', 'A002') 
ORDER BY account_id FOR UPDATE;

-- 执行业务逻辑
UPDATE accounts SET balance = balance - 1000 WHERE account_id = 'A001';
UPDATE accounts SET balance = balance + 1000 WHERE account_id = 'A002';
COMMIT;

-- 策略2：减少事务持有锁的时间
BEGIN TRANSACTION;
-- 快速获取必要数据
SELECT balance INTO @balance FROM accounts WHERE account_id = 'A001' FOR UPDATE;
-- 立即执行更新操作，不在事务中进行复杂计算
UPDATE accounts SET balance = @balance - 1000 WHERE account_id = 'A001';
COMMIT;
```

#### 死锁检测与自动回滚
```sql
-- 查看死锁信息（MySQL）
SHOW ENGINE INNODB STATUS;

-- 死锁检测配置
SET GLOBAL innodb_deadlock_detect = ON;  -- 开启死锁检测（默认）
SET GLOBAL innodb_lock_wait_timeout = 50;  -- 锁等待超时时间

-- 死锁处理的存储过程示例
DELIMITER //
CREATE PROCEDURE safe_transfer(
    IN from_acc VARCHAR(10),
    IN to_acc VARCHAR(10), 
    IN amount DECIMAL(10,2),
    OUT result_code INT
)
BEGIN
    DECLARE deadlock_count INT DEFAULT 0;
    DECLARE max_retries INT DEFAULT 3;
    DECLARE done INT DEFAULT FALSE;
    
    retry_loop: WHILE deadlock_count < max_retries AND NOT done DO
        BEGIN
            -- 死锁异常处理
            DECLARE EXIT HANDLER FOR 1213  -- MySQL 死锁错误码
            BEGIN
                SET deadlock_count = deadlock_count + 1;
                IF deadlock_count >= max_retries THEN
                    SET result_code = -1;  -- 死锁重试失败
                    LEAVE retry_loop;
                END IF;
                -- 随机等待避免立即重试
                SELECT SLEEP(RAND() * 0.1);
            END;
            
            START TRANSACTION;
            
            -- 按ID顺序加锁避免死锁
            IF from_acc < to_acc THEN
                SELECT balance FROM accounts WHERE account_id = from_acc FOR UPDATE;
                SELECT balance FROM accounts WHERE account_id = to_acc FOR UPDATE;
            ELSE
                SELECT balance FROM accounts WHERE account_id = to_acc FOR UPDATE;
                SELECT balance FROM accounts WHERE account_id = from_acc FOR UPDATE;
            END IF;
            
            -- 执行转账
            UPDATE accounts SET balance = balance - amount 
            WHERE account_id = from_acc AND balance >= amount;
            
            IF ROW_COUNT() = 0 THEN
                ROLLBACK;
                SET result_code = -2;  -- 余额不足
                SET done = TRUE;
            ELSE
                UPDATE accounts SET balance = balance + amount 
                WHERE account_id = to_acc;
                COMMIT;
                SET result_code = 0;  -- 成功
                SET done = TRUE;
            END IF;
        END;
    END WHILE;
END //
DELIMITER ;
```

### 锁优化与监控

#### 锁争用监控
```sql
-- 查看当前锁等待情况
SELECT 
    r.trx_id AS waiting_trx_id,
    r.trx_mysql_thread_id AS waiting_thread,
    r.trx_query AS waiting_query,
    b.trx_id AS blocking_trx_id,
    b.trx_mysql_thread_id AS blocking_thread,
    b.trx_query AS blocking_query,
    l.lock_table,
    l.lock_index,
    l.lock_mode
FROM information_schema.innodb_lock_waits w
JOIN information_schema.innodb_trx r ON r.trx_id = w.requesting_trx_id
JOIN information_schema.innodb_trx b ON b.trx_id = w.blocking_trx_id
JOIN information_schema.innodb_locks l ON l.lock_trx_id = w.requesting_trx_id;

-- 锁超时监控
SELECT 
    COUNT(*) as lock_timeouts,
    DATE(created_time) as date
FROM performance_schema.events_statements_history
WHERE sql_text LIKE '%LOCK%'
AND errors > 0
GROUP BY DATE(created_time)
ORDER BY date DESC;
```

#### 减少锁争用的策略
```sql
-- 策略1：使用乐观锁替代悲观锁
-- 悲观锁（FOR UPDATE）
BEGIN TRANSACTION;
SELECT balance FROM accounts WHERE account_id = 'A001' FOR UPDATE;
UPDATE accounts SET balance = balance - 100 WHERE account_id = 'A001';
COMMIT;

-- 乐观锁（版本号机制）
-- 1. 读取数据和版本号
SELECT balance, version FROM accounts WHERE account_id = 'A001';

-- 2. 更新时检查版本号
UPDATE accounts 
SET balance = balance - 100, version = version + 1
WHERE account_id = 'A001' AND version = @original_version;

-- 3. 检查更新结果
IF ROW_COUNT() = 0 THEN
    -- 版本冲突，需要重试或返回错误
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Optimistic lock conflict';
END IF;

-- 策略2：批量操作减少锁获取次数
-- ❌ 低效：多次获取锁
UPDATE accounts SET balance = balance + 100 WHERE account_id = 'A001';
UPDATE accounts SET balance = balance + 200 WHERE account_id = 'A002';
UPDATE accounts SET balance = balance + 300 WHERE account_id = 'A003';

-- ✅ 高效：批量更新
UPDATE accounts 
SET balance = CASE account_id 
    WHEN 'A001' THEN balance + 100
    WHEN 'A002' THEN balance + 200  
    WHEN 'A003' THEN balance + 300
    ELSE balance
END
WHERE account_id IN ('A001', 'A002', 'A003');
```

## ⚠️ 企业级性能优化与最佳实践

### 1. 事务设计核心原则

#### 事务最小化原则
```sql
-- ✅ 最佳实践：事务仅包含必要的数据库操作
BEGIN TRANSACTION;
-- 1. 快速验证业务规则
SELECT balance FROM accounts WHERE account_id = 'A001' FOR UPDATE;

-- 2. 执行原子操作
UPDATE orders SET status = 'paid', updated_at = NOW() WHERE order_id = 12345;
INSERT INTO payments (order_id, amount, payment_time) VALUES (12345, 299.99, NOW());
COMMIT;

-- ❌ 反面案例：事务中包含非数据库操作
BEGIN TRANSACTION;
SELECT * FROM orders WHERE order_id = 12345;

-- 在事务中进行复杂计算（占用锁资源）
-- 计算税费、折扣等业务逻辑
-- 调用外部支付API（网络延迟）
-- 发送邮件通知（I/O操作）

UPDATE orders SET status = 'paid' WHERE order_id = 12345;
COMMIT;  -- 长时间占用锁，影响并发性能
```

#### 事务边界设计
```sql
-- 正确的事务边界设计
-- 第一阶段：准备数据（不在事务中）
SELECT product_id, price, stock_quantity 
FROM products WHERE product_id = 'P001';

-- 业务逻辑计算（不在事务中）
SET @total_amount = @price * @quantity;
SET @new_stock = @current_stock - @quantity;

-- 第二阶段：数据库操作（在事务中）
BEGIN TRANSACTION;
-- 验证库存仍然足够（防止并发问题）
SELECT stock_quantity FROM products 
WHERE product_id = 'P001' AND stock_quantity >= @quantity FOR UPDATE;

-- 原子操作
UPDATE products SET stock_quantity = stock_quantity - @quantity WHERE product_id = 'P001';
INSERT INTO orders (customer_id, total_amount) VALUES (@customer_id, @total_amount);
INSERT INTO order_items (order_id, product_id, quantity) VALUES (LAST_INSERT_ID(), 'P001', @quantity);
COMMIT;

-- 第三阶段：后续处理（不在事务中）
-- 发送确认邮件、更新缓存、记录日志等
```

### 3. 企业级事务重试与容错机制

#### 智能重试策略
```sql
-- 指数退避重试机制
DELIMITER //
CREATE PROCEDURE smart_transfer(
    IN from_account VARCHAR(10),
    IN to_account VARCHAR(10),
    IN amount DECIMAL(10,2),
    OUT result_code INT,
    OUT error_message TEXT
)
BEGIN
    DECLARE retry_count INT DEFAULT 0;
    DECLARE max_retries INT DEFAULT 5;
    DECLARE base_delay DECIMAL(3,2) DEFAULT 0.1;
    DECLARE done INT DEFAULT FALSE;
    DECLARE current_delay DECIMAL(3,2);
    
    retry_loop: WHILE retry_count < max_retries AND NOT done DO
        BEGIN
            -- 异常处理：区分不同类型的错误
            DECLARE EXIT HANDLER FOR 1213  -- 死锁
            BEGIN
                SET retry_count = retry_count + 1;
                -- 指数退避：延迟时间逐渐增加
                SET current_delay = base_delay * POWER(2, retry_count - 1);
                SELECT SLEEP(current_delay + RAND() * current_delay);  -- 添加随机抖动
                
                IF retry_count >= max_retries THEN
                    SET result_code = -1;
                    SET error_message = 'Transaction failed after maximum retries due to deadlock';
                    LEAVE retry_loop;
                END IF;
            END;
            
            DECLARE EXIT HANDLER FOR 1062  -- 重复键错误，不应重试
            BEGIN
                SET result_code = -3;
                SET error_message = 'Duplicate key error - transaction cancelled';
                SET done = TRUE;
            END;
            
            START TRANSACTION;
            
            -- 业务逻辑：转账操作
            UPDATE accounts 
            SET balance = balance - amount, version = version + 1
            WHERE account_id = from_account 
            AND balance >= amount 
            AND status = 'active';
            
            IF ROW_COUNT() = 0 THEN
                ROLLBACK;
                SET result_code = -2;
                SET error_message = 'Insufficient balance or inactive account';
                SET done = TRUE;
            ELSE
                UPDATE accounts 
                SET balance = balance + amount, version = version + 1
                WHERE account_id = to_account 
                AND status = 'active';
                
                IF ROW_COUNT() = 0 THEN
                    ROLLBACK;
                    SET result_code = -4;
                    SET error_message = 'Target account not found or inactive';
                    SET done = TRUE;
                ELSE
                    -- 记录转账日志
                    INSERT INTO transfer_log (from_account, to_account, amount, timestamp)
                    VALUES (from_account, to_account, amount, NOW());
                    
                    COMMIT;
                    SET result_code = 0;
                    SET error_message = 'Transfer completed successfully';
                    SET done = TRUE;
                END IF;
            END IF;
        END;
    END WHILE;
END //
DELIMITER ;
```

-- 长事务监控视图
CREATE VIEW v_long_running_transactions AS
SELECT 
    trx_id,
    trx_started,
    TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS duration_seconds,
    trx_query,
    trx_operation_state,
    trx_tables_locked,
    trx_rows_locked,
    trx_lock_memory_bytes

SELECT 
    ROUND(AVG(timer_wait)/1000000000000, 4) AS avg_duration_seconds,
    COUNT(*) AS transaction_count,
    SUM(CASE WHEN timer_wait/1000000000000 > 5 THEN 1 ELSE 0 END) AS slow_transactions,
    DATE(timer_start) AS date
FROM performance_schema.events_transactions_history_long
WHERE event_name = 'transaction'
GROUP BY DATE(timer_start)
ORDER BY date DESC;

#### 补偿事务模式（Saga）
```sql
-- 订单处理的Saga模式实现
DELIMITER //
CREATE PROCEDURE process_order_saga(
    IN order_id BIGINT,
    IN customer_id BIGINT,
    IN product_id VARCHAR(10),
    IN quantity INT,
    OUT result_code INT
)
BEGIN
    DECLARE step_completed INT DEFAULT 0;
    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
        -- 根据完成的步骤进行补偿
        CASE step_completed
            WHEN 3 THEN 
                -- 补偿步骤3：取消支付
                UPDATE payments SET status = 'cancelled' WHERE order_id = order_id;
            WHEN 2 THEN
                -- 补偿步骤2：恢复库存
                UPDATE inventory SET quantity = quantity + @order_quantity WHERE product_id = product_id;
                -- 补偿步骤1：取消订单
                UPDATE orders SET status = 'cancelled' WHERE order_id = order_id;
            WHEN 1 THEN
                -- 补偿步骤1：取消订单
                UPDATE orders SET status = 'cancelled' WHERE order_id = order_id;
        END CASE;
        
        SET result_code = -1;
        RESIGNAL;
    END;
    
    -- 步骤1：创建订单
    INSERT INTO orders (customer_id, status, created_at) VALUES (customer_id, 'processing', NOW());
    SET step_completed = 1;
    
    -- 步骤2：扣减库存
    UPDATE inventory SET quantity = quantity - @quantity 
    WHERE product_id = product_id AND quantity >= @quantity;
    IF ROW_COUNT() = 0 THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Insufficient inventory';
    END IF;
    SET step_completed = 2;
    
    -- 步骤3：创建支付记录
    INSERT INTO payments (order_id, amount, status) VALUES (order_id, @total_amount, 'pending');
    SET step_completed = 3;
    
    -- 所有步骤成功
    UPDATE orders SET status = 'confirmed' WHERE order_id = order_id;
    SET result_code = 0;
END //
DELIMITER ;
```

## 📝 事务管理最佳实践总结

### 设计原则
1. **最小化原则**：事务范围尽可能小，减少锁持有时间
2. **原子性保证**：相关操作必须在同一事务中完成
3. **一致性维护**：确保业务规则在事务前后都得到满足
4. **隔离性选择**：根据业务场景选择合适的隔离级别

### 性能优化
1. **索引优化**：为事务中的查询条件创建适当索引
2. **批量操作**：合并多个小事务为单个大事务
3. **锁优化**：使用乐观锁替代悲观锁，减少锁争用
4. **分区策略**：通过数据分区减少锁竞争范围

### 监控与维护
1. **性能监控**：建立事务性能监控和告警机制
2. **死锁检测**：配置自动死锁检测和处理策略
3. **容量规划**：基于事务压测结果进行系统容量规划
4. **故障恢复**：制定完善的事务故障恢复预案

**专家建议 💡**
- 在高并发系统中，根据业务不变量、可接受的一致性延迟和故障恢复能力选择强一致性或最终一致性；不能仅凭并发量决定
- 使用数据库连接池合理管理事务连接资源
- 建立完善的事务测试用例，覆盖各种异常场景
- 定期分析事务性能瓶颈，持续优化系统架构
