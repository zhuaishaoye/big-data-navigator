## 🤔 为什么需要Impala？

> [!abstract] 🎯 什么是Impala？
> Impala是一个**开源、分布式、大规模并行处理（MPP）**的SQL查询引擎，专为在Hadoop集群上运行的、存储在HDFS、HBase或Amazon S3中的数据提供**低延迟、高并发**的交互式查询分析。它绕过了MapReduce，直接访问数据，从而实现了极高的查询性能。
>
> **生活化类比**：
> - **Hive**：像一个**仓库管理员**，你需要提交一个详细的货物清单（SQL查询），他会去仓库（HDFS）里按执行计划找货、打包、运输（可使用MapReduce、Tez等执行引擎，具体取决于版本与配置），常用于处理大批量的订单（批处理），并非所有查询都慢。
> - **Impala**：像一个**超市导购员**，你直接告诉他你要什么（交互式SQL），他通过自己的执行引擎并行读取和处理数据（并非数据都在内存中），目标是较快响应查询，适合快速、即时的查询需求（交互式分析），实际速度取决于数据与资源条件。

## 关键特性

| 特性 | 描述 | 优势 |
| :--- | :--- | :--- |
| **MPP架构** | 基于大规模并行处理架构，查询被分解成多个片段，在集群中并行执行。 | 高性能、低延迟，能够快速处理大规模数据。 |
| **绕过MapReduce** | Impala拥有自己的查询执行引擎，不依赖MapReduce，直接与存储层（如HDFS）交互。 | 避免了MapReduce作业的启动开销及部分中间结果落盘开销，但不能消除磁盘I/O瓶颈；原稿“查询速度比Hive快几个数量级”未提供测试依据，不应作为普遍性能结论。 |
| **与Hadoop生态系统集成** | 与HDFS、HBase、Metastore、YARN、Sentry等组件无缝集成，共享相同的元数据和存储。 | 能够利用现有的Hadoop基础设施，与Hive共享数据和元数据，无需数据迁移。 |
| **支持多种文件格式** | 支持Parquet、ORC、Avro、Text等多种文件格式。 | 尤其是对**[[【技术与工具】/Impala/12-文件格式优化|文件格式优化|]]**所涉及的列式存储优化，应结合具体格式、数据布局与查询条件评估。 |
| **SQL-on-Hadoop** | 提供标准的SQL-92方言支持，用户可以使用熟悉的SQL技能进行数据分析。 | 学习成本低，易于上手，BI工具可以方便地集成。 |
| **高并发性** | 能够同时处理多个用户的查询请求，适合多用户环境。 | 满足企业级报表、即席查询等高并发场景的需求。 |

## Impala与Hive的对比

| 对比维度 | Impala | Hive |
| :--- | :--- | :--- |
| **定位** | 交互式SQL查询、即席查询；数据时效取决于摄取与元数据更新机制 | 大规模数据批处理、ETL，也可用于交互式分析 |
| **执行引擎** | 自研MPP引擎，读取存储数据并利用内存处理，部分算子可溢写磁盘 | MapReduce、Tez等；Spark执行支持取决于版本与发行版 |
| **查询延迟** | 面向低延迟交互式查询，不能保证秒级或亚秒级 | 随执行引擎、查询复杂度、数据规模及资源变化，不能固定为分钟级或小时级 |
| **数据更新** | 支持INSERT；UPDATE、DELETE主要用于Kudu表，不能套用于普通HDFS文件表，具体支持须按版本核对 | 支持INSERT；UPDATE、DELETE通常要求满足版本及ACID事务表条件，并非所有表都支持完整CRUD |
| **元数据** | **共享Hive Metastore** | 拥有自己的Metastore |
| **适用场景** | BI报表、数据探索、多维分析（OLAP） | 数据仓库ETL、离线数据分析、大规模数据处理 |
