## 一、生产环境资源规划

资源规划是生产部署的起点。规划不足会导致 OOM 崩溃，规划过度则浪费成本。

### 1.1 内存估算

Milvus 是内存密集型系统。向量数据需要加载到内存才能被搜索。内存估算分四个部分：

#### 向量原始数据内存

```text
向量数据内存（GB）= N × D × 4 / 1,073,741,824

N：向量条数
D：向量维度
4：float32 每维占 4 字节
```

**典型场景计算：**

| 规模 | 维度 | 计算 | 原始向量内存 |
|------|------|------|-------------|
| 1,000 万条 | 768 维 | 1000W × 768 × 4B | 约 28.6 GB |
| 5,000 万条 | 768 维 | 5000W × 768 × 4B | 约 143 GB |
| 1 亿条 | 768 维 | 1亿 × 768 × 4B | 约 286 GB |
| 1 亿条 | 1536 维 | 1亿 × 1536 × 4B | 约 573 GB |

> [!warning] 1 亿条 768 维向量的完整内存估算
> 这是最常见的生产规模（使用 BGE-base / text-embedding-ada-002 类模型），让我们做完整计算：
>
> - **向量原始数据**：286 GB
> - **HNSW 索引额外内存**：约 1.5x 倍率 → 429 GB
> - **标量字段**（假设 10 个 varchar 字段，平均 50 字节）：原始字段内容约 46.6 GiB，尚未计入字段存储结构等额外开销
> - **元数据与系统开销**：约 10 GB
> - **查询缓冲区（留 20% 余量）**：约 146 GB
>
> **原文总计 876 GB 及 1 TB 集群建议不能直接沿用**：标量数据计算已更正，HNSW 倍率还需明确是索引总占用还是额外占用，并结合副本、加载方式及峰值负载重新估算；每 Query Node 128-256 GB 仅作为部署示例。

#### 各索引类型的内存倍率

不同索引类型对内存的需求差异显著：

| 索引类型 | 内存倍率（相对原始向量数据） | 说明 |
|---------|--------------------------|------|
| FLAT | 1.0x | 无索引结构，原始数据即搜索数据 |
| IVF_FLAT | 1.0x + 量化中心点 | 中心点内存可忽略 |
| IVF_SQ8 | 0.25x | 量化压缩到 1/4，精度略损 |
| IVF_PQ | 约 0.1x | 乘积量化，压缩比最高，精度损失较大 |
| HNSW | 1.5x - 2.0x | 图结构索引，内存开销和召回效果受图参数、数据及搜索参数影响 |
| DiskANN | 磁盘为主 + 少量内存 | 磁盘存索引，内存仅存压缩导航层 |
| SCANN | 约 0.3x | 谷歌 ScaNN，压缩率与精度兼顾 |

> [!tip] 内存紧张时的选择策略
> - 内存充裕（> 2x 原始数据）：可优先测试 HNSW，并按目标召回率、延迟和实际内存占用比较选型
> - 内存中等（1-2x）：选 IVF_FLAT 或 SCANN
> - 内存紧张（< 1x）：选 IVF_SQ8 或 IVF_PQ，接受一定精度损失
> - 超大规模（百亿级）：DiskANN，成本可控

#### 标量数据与元数据内存

```text
标量内存（GB）= N × 每条记录标量字节数 / 1,073,741,824

典型标量配置：
- doc_id (VarChar 64)：64 bytes
- source (VarChar 256)：256 bytes
- created_at (Int64)：8 bytes
- metadata (JSON ~500 bytes)：500 bytes

1亿条记录 × (64+256+8+500) bytes ≈ 78 GB
```

#### 系统与操作系统预留

- 操作系统：预留 8-16 GB
- Milvus 进程自身（Go runtime、缓存等）：16-32 GB
- Growing Segment 写入缓冲区：按 `insertBufSize × 并发写入数` 估算

### 1.2 CPU 规划

Milvus 中 CPU 最重的工作发生在 **Query Node**（向量搜索计算）和 **Index Node**（索引构建）。

#### Query Node CPU 规划

```text
并发搜索下每次搜索的 CPU 消耗取决于：
1. 索引类型（HNSW 比 IVF 更 CPU 密集）
2. nq（单次请求的查询向量数量）
3. topk（返回结果数量）
4. nprobe / ef（搜索深度参数）

经验公式（HNSW 索引，单机 32 核）：
理想 CPU 吞吐上限（请求/秒）≈ 可用 CPU 核数 × 1000 / 单次请求累计 CPU 毫秒；实际 QPS 还受内存带宽、并发调度和其他开销限制
```

**性能数字示例（假设 HNSW 索引、1 亿条 768 维；未提供压测记录，不作为容量承诺）：**

| 硬件 | nq=1, topk=10 | nq=1, topk=100 | nq=10, topk=10 |
|------|--------------|----------------|----------------|
| 32 核 CPU | 约 800 QPS | 约 400 QPS | 约 200 QPS |
| 64 核 CPU | 约 1600 QPS | 约 800 QPS | 约 400 QPS |

> [!note] CPU 与内存的关系
> Query Node 的性能瓶颈通常先出现在内存带宽，而不是 CPU 核数。选择高内存带宽的 CPU 型号（如 AMD EPYC、Intel Xeon Scalable）比单纯堆核数更有效。

#### Index Node CPU 规划

索引构建是 CPU 密集型批处理任务：
- **HNSW 构建速度假设**：假设 768 维向量达到每核每秒 1 万条，仅用于演算，不代表实测吞吐
- 在该假设下，32 核处理 1 亿条向量的理想线性耗时约为 5.2 分钟；实际构建耗时还受索引参数、资源争用及并行效率影响
- 建议：Index Node 与 Query Node 物理隔离，避免索引构建抢占查询资源

### 1.3 存储规划

#### MinIO / S3 存储估算

Milvus 将所有持久化数据（向量、索引、标量）存储在对象存储中：

```text
总存储量 = 原始向量数据 + 索引文件 + 标量数据 + 日志
         ≈ (1 + 索引倍率) × 向量原始数据 × 副本数

示例：1亿条 768 维，HNSW 索引，3副本：
= (1 + 1.5) × 286 GB × 3
≈ 2.145 TB
```

> [!tip] 实际建议预留 3-5 倍
> Milvus 在 compact 过程中会产生临时文件，日志也需要空间，建议实际分配存储是理论值的 3-5 倍。

#### Pulsar / Kafka 消息队列磁盘需求

Milvus 用消息队列（默认 Pulsar）作为写入通道：

```text
消息队列磁盘 = 写入速率（条/秒） × 平均消息大小 × 保留时间（秒）

示例：写入速率 10,000 条/秒，768维向量（约3KB/条），保留2天：
= 10,000 × 3KB × 172,800 秒
≈ 5.18 TB（建议准备 8 TB SSD）
```

## 二、关键配置调优

Milvus 的核心配置在 `milvus.yaml`（Standalone 模式）或 Helm values（Kubernetes 模式）中。以下是生产环境最关键的参数。

### 2.1 完整配置模板（生产推荐）

```yaml
# milvus.yaml - 生产环境推荐配置

# ============ Proxy 配置 ============
proxy:
  # 最大并发任务数，根据 QPS 预期设置，避免请求积压
  maxTaskNum: 1024
  # 单次搜索允许的最大 topk（防止超大请求拖垮系统）
  maxTopK: 16384
  # 最大向量维度
  maxDimension: 32768

# ============ Query Node 配置 ============
queryNode:
  cache:
    # 内存水位线：超过此比例时停止加载新 Segment
    # 推荐值：0.7（留30%给增量写入和系统开销）
    memoryWatermark: 0.7
    # 是否启用磁盘索引（DiskANN 场景需要开启）
    disk:
      enable: false

  # 搜索线程池大小（建议等于 CPU 核数）
  segcore:
    nprobe: 8  # 初始 nprobe，会被搜索参数覆盖

# ============ Data Node 配置 ============
dataNode:
  flush:
    # 触发 Flush 的写入缓冲大小（默认 16MB，高吞吐写入可调大）
    insertBufSize: 67108864  # 64MB，单位字节

  # 删除缓冲区大小
  deleteBufBytes: 16777216  # 16MB

# ============ Data Coordinator 配置 ============
dataCoord:
  segment:
    # 单个 Segment 的最大大小（512MB 到 1GB 是合理范围）
    maxSize: 512  # 单位 MB
    # Segment 写入到多少比例时触发 Seal（封存）
    sealProportion: 0.75
    # 多少秒没有新数据写入时强制 Seal
    maxIdleTime: 600  # 10分钟

  compaction:
    # 是否启用自动 Compaction（生产环境应开启）
    enableAutoCompaction: true

# ============ Index Coordinator 配置 ============
indexCoord:
  gc:
    # 索引文件垃圾回收间隔
    interval: 600  # 10分钟

# ============ 消息队列配置（Pulsar）============
pulsar:
  maxMessageSize: 5242880  # 单条消息最大 5MB（超大向量需要调大）

# ============ 日志配置 ============
log:
  level: info  # 生产环境用 info，调试时改 debug
  file:
    rootPath: /var/log/milvus
    maxSize: 300    # MB
    maxBackups: 10
    maxAge: 20      # 保留天数

# ============ 监控配置 ============
metrics:
  enabled: true
  port: 9091  # Prometheus 抓取端口
```

### 2.2 Segment 配置详解

Segment 是 Milvus 存储和查询的基本单位，其配置对性能影响最大。

```text
Segment 生命周期：

Growing Segment（写入阶段）
    ↓ 达到 maxSize 或 sealProportion 时
Sealed Segment（封存阶段，等待 Flush）
    ↓ Flush 到 MinIO
Historical Segment（历史阶段，可被搜索）
    ↓ 触发 Compaction
Compacted Segment（合并后的大 Segment）
```

**关键参数影响分析：**

| 参数 | 调大的效果 | 调小的效果 | 推荐值 |
|------|-----------|-----------|--------|
| `maxSize` | 更少的 Segment 数量，减少元数据开销 | 更快 Flush，降低内存峰值 | 512 MB |
| `sealProportion` | 更充分利用 Segment 空间 | 更频繁 Seal，减少写入延迟抖动 | 0.75 |
| `maxIdleTime` | 减少不必要的 Seal 操作 | 更快将冷数据 Flush 到持久化存储 | 600s |
| `insertBufSize` | 提高批量写入吞吐量 | 降低单次 Flush 的内存占用 | 64MB |

> [!warning] maxSize 与内存的关系
> 每个 Query Node 最多同时持有：
> `内存 × memoryWatermark / maxSize` 个 Growing Segment
>
> 如果写入速率很高（大量并发写入），Growing Segment 数量会飙升，耗尽内存。此时需要调大 `insertBufSize`（减少 Segment 数量）或调小 `maxIdleTime`（加快 Flush）。

### 2.3 Kubernetes 环境下的资源限制

## 三、监控体系建设

没有监控的生产系统是在走钢丝。Milvus 内置 Prometheus 指标暴露，配合 Grafana 可以构建完整的可观测性体系。

### 3.1 核心监控指标

Milvus 在 `:9091/metrics` 端口暴露 Prometheus 指标。以下是最关键的指标分类：

#### 请求层指标（Proxy）

| 指标名 | 类型 | 含义 | 告警阈值参考 |
|--------|------|------|-------------|
| `milvus_proxy_req_count` | Counter | 各类请求总量（按类型/状态分） | - |
| `milvus_proxy_req_latency` | Histogram | 请求端到端延迟（ms） | P99 > 500ms 告警 |
| `milvus_proxy_sq_latency_bucket` | Histogram | 搜索请求延迟分布 | P99 > 200ms 告警 |
| `milvus_proxy_send_bytes_count` | Counter | 发送数据量 | - |
| `milvus_proxy_receive_bytes_count` | Counter | 接收数据量 | - |

#### 内存层指标（Query Node）

| 指标名 | 类型 | 含义 | 告警阈值参考 |
|--------|------|------|-------------|
| `process_resident_memory_bytes` | Gauge | 进程实际物理内存使用 | > 80% 节点内存告警 |
| `milvus_querynode_collection_num` | Gauge | 已加载的 Collection 数量 | - |
| `milvus_querynode_segment_num` | Gauge | 内存中的 Segment 数量 | 突增超 50% 告警 |
| `milvus_querynode_cache_hit_rate` | Gauge | 缓存命中率 | < 0.8 告警 |

#### 写入层指标（Data Node）

| 指标名 | 类型 | 含义 | 告警阈值参考 |
|--------|------|------|-------------|
| `milvus_datanode_flush_duration` | Histogram | Flush 耗时 | P99 > 30s 告警 |
| `milvus_datanode_encode_duration` | Histogram | 数据编码耗时 | - |
| `milvus_msgstream_consumer_lag` | Gauge | 消息队列消费延迟 | > 10000 条告警 |

#### 索引层指标（Index Node）

| 指标名 | 类型 | 含义 | 告警阈值参考 |
|--------|------|------|-------------|
| `milvus_indexnode_build_duration` | Histogram | 索引构建耗时 | - |
| `milvus_indexnode_index_size` | Gauge | 索引文件大小 | - |

### 3.2 Prometheus 配置

```yaml
# prometheus.yml
global:
  scrape_interval: 15s
  evaluation_interval: 15s

rule_files:
  - "milvus_alerts.yml"

scrape_configs:
  # Milvus Standalone 模式
  - job_name: 'milvus-standalone'
    static_configs:
      - targets: ['milvus-host:9091']
    metrics_path: /metrics

  # Milvus 分布式模式（K8s Service Discovery）
  - job_name: 'milvus-distributed'
    kubernetes_sd_configs:
      - role: pod
        namespaces:
          names: ['milvus']
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_label_app_kubernetes_io_name]
        regex: milvus
        action: keep
      - source_labels: [__meta_kubernetes_pod_ip]
        target_label: __address__
        replacement: '${1}:9091'
```

### 3.3 关键告警规则

```yaml
# milvus_alerts.yml
groups:
  - name: milvus_critical
    rules:
      # 搜索延迟告警
      - alert: MilvusHighSearchLatency
        expr: |
          histogram_quantile(0.99,
            rate(milvus_proxy_sq_latency_bucket[5m])
          ) > 500
        for: 2m
        labels:
          severity: warning
        annotations:
          summary: "Milvus 搜索 P99 延迟超过 500ms"
          description: "当前 P99 延迟: {{ $value }}ms"

      # 内存水位线告警
      - alert: MilvusQueryNodeHighMemory
        expr: |
          process_resident_memory_bytes{job="milvus-distributed"}
          / on(instance) kube_node_status_allocatable{resource="memory"}
          > 0.85
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "Query Node 内存使用率超过 85%"

      # 消息队列堆积告警
      - alert: MilvusMsgStreamLag
        expr: milvus_msgstream_consumer_lag > 50000
        for: 3m
        labels:
          severity: warning
        annotations:
          summary: "消息队列堆积严重，写入可能跟不上"

      # Collection 未加载告警
      - alert: MilvusCollectionNotLoaded
        expr: milvus_querynode_collection_num == 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "Query Node 中没有已加载的 Collection"

      # Flush 失败率告警
      - alert: MilvusFlushFailure
        expr: |
          rate(milvus_datanode_flush_duration_count{status="error"}[5m]) > 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "数据 Flush 出现失败"
```

## 四、性能调优实战

以下三个场景是生产环境中最常见的性能问题，每个场景给出完整的诊断步骤和解决方案。

### 4.1 场景一：写入性能低

**症状**：每秒写入量远低于预期，积压严重，消息队列 lag 持续增长。

**诊断步骤：**

```python
# Step 1：检查当前写入方式
# 低效：单条插入（每次 HTTP 请求开销巨大）
for vec in vectors:
    collection.insert([[vec]])  # 错误！

# Step 2：检查批量大小
# 高效：批量插入
BATCH_SIZE = 1000  # 每批至少 1000 条

# Step 3：检查 Flush 频率
from pymilvus import utility
utility.get_query_segment_info("my_collection")
```

**解决方案：**

```python
import time
from pymilvus import Collection, connections
from concurrent.futures import ThreadPoolExecutor

connections.connect(host="localhost", port="19530")
collection = Collection("my_collection")

def batch_insert_optimized(vectors: list, scalars: dict, batch_size: int = 2000):
    """
    批量写入示例函数：需匹配实际 Schema，尚未实现完整失败恢复

    假设性性能对比示例（768维，100万条；未提供测试记录，以下耗时不是实测承诺）：
    - 单条写入：约 20 分钟
    - 批量 1000 条：约 3 分钟
    - 批量 2000 条 + 并发：约 1 分钟
    """
    total = len(vectors)
    success_count = 0

    for i in range(0, total, batch_size):
        batch_vectors = vectors[i:i+batch_size]
        batch_data = [batch_vectors]

        # 加入标量字段
        for field_name, field_values in scalars.items():
            batch_data.append(field_values[i:i+batch_size])

        try:
            mr = collection.insert(batch_data)
            success_count += len(mr.primary_keys)

            if i % (batch_size * 10) == 0:
                print(f"进度: {i}/{total} ({100*i//total}%)")
        except Exception as e:
            print(f"批次 {i} 写入失败: {e}")
            # 生产环境：写入死信队列，后续重试

    # 写完后手动 Flush（确保数据持久化）
    # 注意：频繁调用 flush() 会降低性能，建议写完一批后调用一次
    collection.flush()
    print(f"写入完成: {success_count}/{total}")
    return success_count


# 并发写入（多线程，适合 CPU 不是瓶颈时）
def concurrent_insert(all_data: list, num_workers: int = 4):
    """
    多线程并发写入
    注意：Milvus 客户端线程安全，可以多线程并发写入同一 Collection
    """
    chunk_size = len(all_data) // num_workers
    chunks = [all_data[i:i+chunk_size] for i in range(0, len(all_data), chunk_size)]

    with ThreadPoolExecutor(max_workers=num_workers) as executor:
        futures = [executor.submit(batch_insert_optimized, chunk, {}) for chunk in chunks]
        results = [f.result() for f in futures]

    return sum(results)
```

```python
# 方案一：调整搜索参数（最立竿见影）

# HNSW 索引：ef 控制搜索深度
# ef 越大 → 召回率越高 → 延迟越高
# 生产环境根据延迟目标二分查找最优 ef

def find_optimal_ef(collection, query_vec, target_latency_ms=100):
    """二分查找最优 ef 参数"""
    low, high = 16, 512

    while low < high:
        mid = (low + high) // 2
        params = {"metric_type": "COSINE", "params": {"ef": mid}}

        # 测试10次取平均
        latencies = []
        for _ in range(10):
            start = time.time()
            collection.search(data=query_vec, anns_field="dense_vector",
                            param=params, limit=10)
            latencies.append((time.time() - start) * 1000)

        avg_latency = sum(latencies) / len(latencies)
        print(f"ef={mid}: 平均延迟 {avg_latency:.1f}ms")

        if avg_latency < target_latency_ms:
            low = mid + 1  # 可以更大，提高召回率
        else:
            high = mid     # 需要更小，降低延迟

    return low - 1

# IVF 索引：nprobe 控制搜索的聚类数量
# 同样需要根据延迟目标调整

# 方案二：增加 Query Node（水平扩容）
# 在 Kubernetes 中：
# kubectl scale deployment milvus-querynode --replicas=8 -n milvus

# 方案三：开启结果缓存（重复查询场景）
# 在 Proxy 层添加 Redis 缓存
import redis
import hashlib
import json

r = redis.Redis(host='localhost', port=6379)

def cached_search(collection, query_vec, search_params, limit, ttl=300):
    """带 Redis 缓存的搜索（适合重复查询多的场景）"""
    # 生成缓存 key
    cache_key = hashlib.md5(
        json.dumps({
            "vec": query_vec,
            "params": search_params,
            "limit": limit
        }).encode()
    ).hexdigest()

    # 尝试从缓存读取
    cached = r.get(cache_key)
    if cached:
        return json.loads(cached)

    # 缓存未命中，执行实际搜索
    results = collection.search(
        data=query_vec,
        anns_field="dense_vector",
        param=search_params,
        limit=limit,
        output_fields=["text", "source"]
    )

    # 序列化结果并缓存
    result_data = [
        [{"id": hit.id, "score": hit.score,
          "text": hit.entity.get("text")} for hit in hits]
        for hits in results
    ]
    r.setex(cache_key, ttl, json.dumps(result_data))

    return result_data
```

### 4.3 场景三：内存溢出（OOM）

**症状**：Query Node Pod 被 Kubernetes OOM Kill，或 Standalone 模式下 Milvus 进程崩溃。

**诊断步骤：**

```bash
# Step 1：确认是 OOM 导致的崩溃

# 或查看系统日志

# 在 Grafana 中执行：
# process_resident_memory_bytes{job="milvus"} / 1024 / 1024 / 1024
# 单位 GB，查看过去1小时的趋势

# Step 3：检查有多少 Growing Segment
# 在 Milvus 日志中搜索
grep "growing segment" /var/log/milvus/milvus.log | tail -50
```

**解决方案：**

```python
# 方案一：冷热数据分离
# 将历史数据移到只读 Collection，当前数据写入活跃 Collection

from pymilvus import Collection, connections, utility
from datetime import datetime, timedelta

def archive_old_data(
    source_collection: str,
    archive_collection: str,
    days_threshold: int = 30
):
    """
    将超过 N 天的数据迁移到归档 Collection
    归档 Collection 可以配置更高的压缩率（IVF_SQ8 索引）
    """
    source = Collection(source_collection)
    archive = Collection(archive_collection)

    # 计算时间阈值（时间戳，秒）
    threshold_ts = int((datetime.now() - timedelta(days=days_threshold)).timestamp())

    # 从 source 查询旧数据（标量过滤）
    old_data = source.query(
        expr=f"created_at < {threshold_ts}",
        output_fields=["*"],
        limit=100000  # 分批处理
    )

    if old_data:
        # 插入到归档 Collection
        archive.insert(old_data)
        archive.flush()

        # 从 source 中删除（需要主键列表）
        old_ids = [item["doc_id"] for item in old_data]
        source.delete(f"doc_id in {old_ids}")

        print(f"已归档 {len(old_data)} 条记录")

# 方案二：调整内存水位线（更保守的内存策略）
# 在 milvus.yaml 中：
# queryNode.cache.memoryWatermark: 0.6  # 从 0.7 降到 0.6

# 方案三：减小 maxSize，加快 Flush（减少 Growing Segment 内存占用）
# dataCoord.segment.maxSize: 256  # 从 512 降到 256
# dataCoord.segment.maxIdleTime: 300  # 从 600 降到 300
```

> [!warning] OOM 的根本原因分析
> Milvus OOM 通常有三个来源：
> 1. **索引未加载完成时的峰值内存**：加载过程中内存是加载后的 2-3 倍
> 2. **Growing Segment 积压**：写入速率超过 Flush 速率时，Growing Segment 无限堆积
> 3. **并发搜索的中间结果**：topk 极大的查询会产生大量临时内存
>
> 解决优先级：先排查 Growing Segment，再检查查询参数，最后考虑扩容。

## 五、索引构建优化

### 5.1 批量导入 vs 实时写入的索引策略

这是生产环境中最常见的策略选择题：

```text
策略 A：先写入所有数据，再统一建索引（推荐用于初始数据导入）

写入 N 条 → flush() → create_index() → load()

优点：索引构建一次完成，效率高（无碎片索引）
缺点：建索引期间无法搜索

策略 B：建完索引再写入新数据（推荐用于增量写入）

建完索引 → load() → 持续写入
新数据先在 Growing Segment 中，定期 Flush 后自动建索引

优点：数据实时可搜索
缺点：Growing Segment 中的数据用暴力搜索（效率低）
```

```python
# 初始导入流程示例（策略 A）：仅限确认可删除旧索引的测试或首次导入场景
from pymilvus import Collection, utility

def production_initial_load(collection: Collection, all_data: list):
    """
    初始数据导入步骤示例，需匹配实际 Schema 并补充失败恢复条件
    适用于：首次导入大量历史数据
    """
    print("Step 1: 确保索引未建立（或删除旧索引）")
    if collection.indexes:
        collection.drop_index()

    print("Step 2: 批量写入数据（不建索引，速度最快）")
    batch_size = 5000
    for i in range(0, len(all_data), batch_size):
        batch = all_data[i:i+batch_size]
        collection.insert(batch)
        if i % 50000 == 0:
            print(f"  已写入 {i}/{len(all_data)}")

    print("Step 3: 强制 Flush，确保所有数据持久化")
    collection.flush()
    print(f"  Flush 完成，总记录数: {collection.num_entities}")

    print("Step 4: 建立索引（HNSW 推荐参数）")
    index_params = {
        "index_type": "HNSW",
        "metric_type": "COSINE",
        "params": {
            "M": 16,           # 图中每个节点的最大连接数，越大召回率越高但内存更多
            "efConstruction": 200  # 构建时的搜索深度，越大质量越高但构建越慢
        }
    }
    collection.create_index(
        field_name="dense_vector",
        index_params=index_params
    )

    # 等待索引构建完成
    utility.wait_for_index_building_complete(collection.name, timeout=3600)
    print("  索引构建完成")

    print("Step 5: 加载到内存")
    collection.load()
    utility.wait_for_loading_complete(collection.name, timeout=600)
    print("  加载完成，可以开始查询")
```

### 6.2 数据迁移（Collection 跨集群）

```python
# 场景：将 Collection 从旧集群迁移到新集群
# 适用于版本升级、机房迁移、容量扩容等场景

from pymilvus import Collection, connections, utility
from pymilvus import CollectionSchema, FieldSchema, DataType
import numpy as np

def migrate_collection(
    source_host: str,
    target_host: str,
    collection_name: str,
    batch_size: int = 5000
):
    """
    跨集群数据迁移
    注意：适合中小规模（亿条以内），超大规模建议用 milvus-backup
    """
    # 连接源集群
    connections.connect("source", host=source_host, port="19530")
    source_col = Collection(collection_name, using="source")
    source_col.load()

    # 获取源 Collection 的 Schema
    schema = source_col.schema
    total = source_col.num_entities

    # 连接目标集群
    connections.connect("target", host=target_host, port="19530")

    # 在目标集群创建相同 Schema 的 Collection
    target_col = Collection(collection_name, schema=schema, using="target")

    # 分页读取并写入
    print(f"开始迁移，总记录数: {total}")
    offset = 0
    migrated = 0

    while offset < total:
        # 查询一批数据（包含所有字段）
        results = source_col.query(
            expr="doc_id != ''",  # 查询所有
            output_fields=["*"],
            limit=batch_size,
            offset=offset
        )

        if not results:
            break

        # 写入目标集群
        target_col.insert(results, using="target")

        migrated += len(results)
        offset += batch_size
        print(f"迁移进度: {migrated}/{total} ({100*migrated//total}%)")

    # Flush 并建立索引
    target_col.flush(using="target")

    # 复制索引配置
    for index in source_col.indexes:
        target_col.create_index(
            field_name=index.field_name,
            index_params={
                "index_type": index.params["index_type"],
                "metric_type": index.params["metric_type"],
                "params": index.params.get("params", {})
            },
            using="target"
        )

    print(f"迁移完成！共迁移 {migrated} 条记录")
```

## 七、版本升级

### 7.1 升级路径

Milvus 遵循语义化版本（Major.Minor.Patch）：

```text
当前版本 → 目标版本 的升级路径：

2.3.x → 2.4.x：属于跨 Minor 升级，需按具体源版本、目标版本和部署方式确认官方升级路径，不能仅凭版本号保证直接升级
2.4.x → 2.5.x：需要查看 Release Notes 确认兼容性
2.x.x → 3.x.x：大版本升级，必须查看迁移指南，通常需要数据迁移

推荐策略：每个 Minor 版本升级前，先在测试集群验证 1-2 周
```

## 八、故障排查手册

### 8.1 Collection Not Found

**错误信息：**
```text
pymilvus.exceptions.SchemaNotReadyException: collection not found: xxx
```

**排查步骤：**

```python
from pymilvus import utility, connections

connections.connect(host="localhost", port="19530")

# Step 1：确认 Collection 是否存在
exists = utility.has_collection("my_collection")
print(f"Collection 存在: {exists}")

# Step 2：列出所有 Collection
all_collections = utility.list_collections()
print(f"所有 Collection: {all_collections}")

# Step 3：若 Collection 存在，另行检查加载状态；此步骤不用于修复 Collection 不存在错误
if exists:
    from pymilvus import Collection
    col = Collection("my_collection")

    # 检查加载状态
    load_state = utility.load_state("my_collection")
    print(f"加载状态: {load_state}")

    # 重新加载
    col.load()
```

**常见原因：**
- Collection 未加载应作为独立的加载状态问题排查，不能据此解释 Collection 不存在错误
- 连接的是错误的 Milvus 实例（地址/端口错误）
- Collection 被意外删除

### 8.2 Connection Timeout

**错误信息：**
```text
grpc._channel._InactiveRpcError: StatusCode.DEADLINE_EXCEEDED
```

**排查步骤：**

```bash
# Step 1：确认 Milvus 是否在运行
docker ps | grep milvus
# 或
```

### 8.3 Memory OOM

**排查步骤：**

```bash
# Step 1：确认是 OOM 导致的重启
kubectl describe pod milvus-querynode-xxx -n milvus
# 查看 Last State 中的 Reason: OOMKilled

# Step 2：分析内存占用来源
# 在 Prometheus 中查询（5分钟间隔）：
# process_resident_memory_bytes{pod=~"milvus-querynode.*"}

# Step 3：检查当前 Collection 的内存占用
# 用 Python 估算：
from pymilvus import Collection, utility

col = Collection("my_collection")
col.load()

# 获取加载进度（间接判断内存状态）
progress = utility.loading_progress("my_collection")
print(f"加载进度: {progress}")
```

**紧急处置：**

```python
# 如果 Query Node 正在 OOM 边缘，紧急释放内存
from pymilvus import Collection

col = Collection("my_collection")

# 方案1：释放指定 Collection
col.release()

# 方案2：如果有多个 Collection，只保留最重要的
all_cols = utility.list_collections()
for col_name in all_cols:
    if col_name not in ["critical_collection_1", "critical_collection_2"]:
        Collection(col_name).release()
        print(f"已释放: {col_name}")
```

### 8.5 Search Result Empty

**症状**：搜索没有报错，但返回 0 条结果。

```python
# 这是新手最容易遇到的问题，排查清单：

# Check 1：数据是否已写入并 Flush
col.flush()
print(f"Collection 中的记录数: {col.num_entities}")
# 如果是 0，说明数据没有成功写入

# Check 2：Collection 是否已加载
utility.wait_for_loading_complete("my_collection")
load_progress = utility.loading_progress("my_collection")
print(f"加载进度: {load_progress}")

# Check 3：查询向量维度是否正确
query_vec = [[0.1] * 768]  # 必须与 Collection Schema 中的维度一致
print(f"查询向量维度: {len(query_vec[0])}")

# Check 4：metric_type 是否一致
# 索引建立时用 COSINE，搜索时也必须用 COSINE
# 不一致会导致结果为空或报错

# Check 5：过滤条件是否过于严苛
results = col.search(
    data=query_vec,
    anns_field="dense_vector",
    param={"metric_type": "COSINE", "params": {"ef": 64}},
    limit=10,
    # 先不加 expr 过滤，确认基础搜索能返回结果
    # expr="source == 'nonexistent_source'"  ← 这样的过滤会导致 0 结果
)

# Check 6：检查向量是否为有效非零向量；COSINE 本身按范数计算相似度，不应将未预先归一化视为搜索结果为空的必要原因
import numpy as np
vec = np.array(query_vec[0])
normalized = vec / np.linalg.norm(vec)
print(f"原始向量 L2 范数: {np.linalg.norm(vec):.4f}")
print(f"归一化后 L2 范数: {np.linalg.norm(normalized):.4f}")
```

## 小结

生产级 Milvus 运维的核心要点：

| 维度 | 关键行动 |
|------|---------|
| 资源规划 | 用公式初步估算，再按索引、加载峰值和实测负载校准余量，重点检查内存瓶颈 |
| 配置调优 | 优先调整 `memoryWatermark`、`insertBufSize`、Segment 大小 |
| 监控告警 | 搜索延迟 P99、内存使用率、消息队列 lag 是三个必设告警 |
| 写入优化 | 批量写入（2000条/批）+ 控制 Flush 频率 |
| 查询优化 | 先确认数据加载状态，再调整 ef/nprobe，最后扩容 |
| 备份恢复 | 生产环境每日备份到 S3，升级前必须备份 |
