# Flume 性能调优实战

> [!abstract] 本节概览
> - 学习目标：掌握 Flume Source/Channel/Sink 三环节的调优方法、JVM 参数配置和性能压测手段
> - 前置知识：Flume 架构基础（原引用“01-Flume概述与架构”未能确定有效目标，暂不可跳转）、Channel 类型（原引用“03-Channel详解”未能确定有效目标，暂不可跳转）
> - 预计用时：35 分钟
> - 后续学习：[[【技术与工具】/Flume/11-监控与运维|监控与运维]]

Flume 的性能瓶颈几乎总是出现在三个地方：Source 采集太慢、Channel 容量不足、Sink 写出太慢。调优的本质是找出**最慢的一环**并针对性优化，而不是盲目调大所有参数。

---

## 性能瓶颈分析思路

### Source / Channel / Sink 三环节排查

```text
Source（采集）──► Channel（缓冲）──► Sink（写出）
```

**定位瓶颈的核心指标：**

| 现象 | 瓶颈位置 | 排查方向 |
|------|---------|---------|
| Channel 持续满（ChannelFillPercentage > 90%）且 Source 正常 | Sink 太慢 | 提升 Sink batchSize、并发、目标端写能力 |
| Channel 持续空但 Sink 不忙 | Source 太慢 | 提升 Source batchSize 和线程数 |
| Source 采集被 Block（日志出现 channel full）| Channel 已满，可能由 Sink 持续写出不足或流量突发引起 | 先检查 Sink 与目标端能力，再评估缓冲容量；扩大容量不能解决持续吞吐不足 |
| CPU 高但 TPS 低 | 序列化或 GC 压力 | JVM 调优，检查 GC 日志 |

**Event TPS 估算：**
```text
实际 TPS = EventPutSuccessCount（每分钟增量）÷ 60

按缓冲容量折算的事件速率（不代表理论最大 TPS）≈ 可用于事件缓冲的内存量 ÷ 平均事件实际内存占用 ÷ 缓冲时间秒数
```

通过 Flume HTTP 监控端点可获取各组件的累计计数：
```bash
curl http://localhost:34545/metrics | python3 -m json.tool
```

## Source 调优

### Taildir Source（最常用 Source）

```properties
# taildir source 调优配置
agent.sources.tail.type = TAILDIR
agent.sources.tail.filegroups = f1
agent.sources.tail.filegroups.f1 = /var/log/app/.*\\.log

# 每次向 Channel 批量写入的事件数（默认 100，建议 500~2000）
# 增大批次可能提高吞吐量，但效果需压测确认，单次失败重试的代价也可能增大
agent.sources.tail.batchSize = 1000

# 原稿的文件组 monitorInterval 并非标准 Taildir 文件组配置项，暂不启用
# 目录发现与空闲轮询相关参数应按所用 Flume 版本确认后配置
# agent.sources.tail.filegroups.f1.monitorInterval = 1000

# position 文件路径（记录已读位置，Agent 重启后从断点续读）
agent.sources.tail.positionFile = /var/run/flume/taildir_position.json

# position 文件写入间隔（毫秒，默认 3000）
# 增大间隔可减少位置文件写入开销，但 Agent 崩溃时可能重读更多数据
agent.sources.tail.writePosInterval = 5000
```

### Avro Source（接收其他 Agent 推送）

```properties
agent.sources.avro.type = avro
agent.sources.avro.bind = 0.0.0.0
agent.sources.avro.port = 41414

# 接收线程数（默认 2，高并发场景增大）
agent.sources.avro.threads = 8

# Avro Source 接收上游发送的事件批次；不要将此键作为通用批次控制参数
# agent.sources.avro.batchSize = 1000
# 批次大小应在上游发送端配置，并与接收端 Channel 的事务容量匹配
```

> [!tip] Source 调优核心原则
> 对支持 `batchSize` 的 Source，可从 100 逐步增大到 1000、2000，观察 TPS、延迟和失败重试，并确保批次不超过 Channel 事务容量。文件发现和空闲轮询参数须按 Source 类型及版本确认；原稿的文件组 `monitorInterval` 不应直接使用。

## Channel 调优

### MemoryChannel 容量计算

MemoryChannel 是高性能场景的首选，但数据存于内存，Agent 崩溃时未持久化的数据**会丢失**。

```text
capacity（事件条数）计算公式：
  capacity = 峰值 TPS × 允许的最大处理延迟（秒）

示例：峰值 TPS = 5000 条/秒，最大延迟容忍 60 秒
  capacity = 5000 × 60 = 300,000 条

transactionCapacity（事务容量）建议：
  应覆盖 Source 写入和 Sink 取出各自的最大事务批次，且不超过 capacity
  原稿的 capacity ÷ 10（通常 10,000 ~ 50,000）仅为待压测的示例取值，不是通用公式
  Source 写入和 Sink 取出分别使用 Channel 事务
```

```properties
agent.channels.mem.type = memory

# Channel 最大容量（条数），超过后 Source 被阻塞
agent.channels.mem.capacity = 300000

# 每个事务最多处理的事件数，需覆盖 Source 和 Sink 各自的最大事务批次
agent.channels.mem.transactionCapacity = 10000

# Channel 中事件 body 的总字节容量，不是单个事件最大字节数
# byteCapacityBufferPercentage 为额外内存开销预留比例，仍需按实际 Event 占用压测
# agent.channels.mem.byteCapacityBufferPercentage = 20
# agent.channels.mem.byteCapacity = 800000000  # 800MB
```

### FileChannel 调优

FileChannel 将事件持久化到磁盘，可在正常的事务提交和磁盘可恢复条件下支持崩溃恢复，但不保证所有故障下零丢失。原稿所称性能比 MemoryChannel 低 3~5 倍是未核实的示例比例，不能替代目标环境压测。

```properties
agent.channels.file.type = file

# 数据目录：配置多个目录可以分散 IO（类似 RAID 0 效果）
# 每个目录最好对应一块独立磁盘，不要用 NFS 或网络磁盘
agent.channels.file.dataDirs = /data1/flume/channel,/data2/flume/channel,/data3/flume/channel

# Checkpoint 目录（记录事务状态，用于崩溃恢复）
# 与 dataDirs 分置独立磁盘可减少 IO 竞争；同盘并不意味着 checkpoint 失去恢复价值
agent.channels.file.checkpointDir = /data0/flume/checkpoint

# 单个数据文件的最大大小（字节），默认 2GB
# 适当减小可加速 Checkpoint 和恢复速度
agent.channels.file.maxFileSize = 2147483648

# Checkpoint 间隔（毫秒），默认 30 秒
# 减小可缩短崩溃恢复时间，但增加 IO 开销
agent.channels.file.checkpointInterval = 30000

# 事务容量
agent.channels.file.transactionCapacity = 10000

# 使用双 Checkpoint（提高恢复可靠性，轻微增加 IO）
agent.channels.file.useDualCheckpoints = true
agent.channels.file.backupCheckpointDir = /data0/flume/checkpoint-backup
```

> [!warning] FileChannel 选磁盘的关键
> 为分散 IO，dataDirs 中的目录宜对应独立物理磁盘；与 checkpointDir 分盘可降低 IO 竞争，但不是恢复能力的必要条件。原稿所称使用 SSD 可达到 MemoryChannel 性能的 70-80% 是未核实的示例比例，须在相同消息、持久化与硬件条件下压测。

### SpillableMemoryChannel（混合 Channel）

同时使用内存和磁盘：内存满时溢出到磁盘，是 MemoryChannel 和 FileChannel 的折中方案。

```properties
agent.channels.spill.type = SPILLABLEMEMORY
agent.channels.spill.memoryCapacity = 100000      # 内存容量（条）
agent.channels.spill.overflowCapacity = 1000000   # 磁盘溢出容量（条）
agent.channels.spill.checkpointDir = /data/flume/spill-checkpoint
agent.channels.spill.dataDirs = /data/flume/spill-data
```

## Sink 调优

### HDFS Sink

HDFS Sink 是最常见的性能瓶颈来源，小文件问题和 RPC 延迟是主要问题。

```properties
agent.sinks.hdfs.type = hdfs
agent.sinks.hdfs.hdfs.path = hdfs://namenode:8020/flume/logs/%Y/%m/%d/%H
# 本示例按本地处理时间展开路径；若按事件时间分区，应提供 timestamp header 并关闭此选项
agent.sinks.hdfs.hdfs.useLocalTimeStamp = true

# 每批次写入 HDFS 的事件数（默认 100，建议 500~5000）
# 增大批次可能减少事务或刷新开销，但不等于单次 HDFS RPC 的数据量，也不保证吞吐量持续提高
agent.sinks.hdfs.hdfs.batchSize = 2000

# HDFS 操作超时（毫秒），网络慢时需增大
agent.sinks.hdfs.hdfs.callTimeout = 30000

# 文件滚动策略：控制小文件数量的核心参数
# 按大小滚动（字节），建议 128MB 或 256MB（对齐 HDFS Block）
agent.sinks.hdfs.hdfs.rollSize = 134217728

# 按时间滚动（秒），0 = 禁用（推荐只用 rollSize 控制）
agent.sinks.hdfs.hdfs.rollInterval = 0

# 按事件数滚动，0 = 禁用
agent.sinks.hdfs.hdfs.rollCount = 0

# 闲置超时关闭文件（秒），防止低流量时文件长期不关闭
agent.sinks.hdfs.hdfs.idleTimeout = 60

# DataStream 选择流式文件写入方式，不会自动编码为 Parquet/ORC
# Parquet/ORC 需要额外的格式编码方案，不能仅靠此参数生成
agent.sinks.hdfs.hdfs.fileType = DataStream

# 并行写线程数（多线程并发写不同文件）
agent.sinks.hdfs.hdfs.threadsPoolSize = 10

# Kerberos 认证（安全集群）
# agent.sinks.hdfs.hdfs.kerberosPrincipal = flume/_HOST@EXAMPLE.COM
# agent.sinks.hdfs.hdfs.kerberosKeytab = /etc/flume/flume.keytab
```

**小文件问题排查与解决：**

```bash
# 查看 HDFS 上的小文件（小于 10MB 的文件）
hdfs dfs -ls /flume/logs/2026/03/21/ | awk '$5 < 10485760 {print $0}'

# 合并小文件：应离线处理已关闭的文件，并评估与 Flume 的资源竞争
# 标准 mapreduce-examples 未提供这里假定的 merge 子程序，以下原稿命令不可直接执行
# hadoop jar $HADOOP_HOME/share/hadoop/mapreduce/hadoop-mapreduce-examples-*.jar \
#   merge /flume/logs/input/ /flume/logs/merged/
# 需补充与文件格式匹配的合并作业及校验步骤后再执行
```

## JVM 调优

### FLUME_JAVA_OPTS 配置

在 `conf/flume-env.sh` 中设置：

```bash
# G1GC 适合大堆（4GB+），延迟更可控，推荐首选
export JAVA_OPTS="
  -server
  -Xms4g
  -Xmx4g
  -XX:+UseG1GC
  -XX:MaxGCPauseMillis=200
  -XX:InitiatingHeapOccupancyPercent=35
  -XX:G1HeapRegionSize=16m
  -XX:+ParallelRefProcEnabled
  -XX:+DisableExplicitGC
  -Xloggc:/var/log/flume/gc.log
  -XX:+PrintGCDetails
  -XX:+PrintGCDateStamps
  -XX:+UseGCLogFileRotation
  -XX:NumberOfGCLogFiles=5
  -XX:GCLogFileSize=50m
"

# JMX 监控端口
export JAVA_OPTS="$JAVA_OPTS
  -Dcom.sun.management.jmxremote
  -Dcom.sun.management.jmxremote.port=54321
  -Dcom.sun.management.jmxremote.ssl=false
  -Dcom.sun.management.jmxremote.authenticate=false
"
```

### G1GC vs CMS 对比

| 维度 | G1GC | CMS |
|------|------|-----|
| 适用堆大小 | 4GB 以上 | 4GB 以下 |
| 停顿时间 | 可设置停顿目标（MaxGCPauseMillis），不保证每次停顿达标 | 受并发回收进度及 Full GC 等因素影响 |
| 吞吐量 | 略低于 CMS | 高 |
| 碎片化 | 通过复制整理回收区域，但仍可能受大对象和空间布局影响 | 并发标记清除不整理，可能因碎片或空间不足触发 Full GC，不应据此定期强制 Full GC |
| 推荐 JDK | JDK 9+（默认 G1） | JDK 8 可用 CMS |
| Flume 建议 | **4GB+ 堆推荐 G1** | 4GB 以下可选 CMS |

**堆大小建议：**

| Channel 类型 | 建议堆大小 |
|-------------|-----------|
| MemoryChannel，capacity 10 万条，平均消息 1KB | 2GB 可作为待压测起点；10 万 × 1KB × 2 约为 200MB，仅是消息体的粗略估算，不能据此推导整个 JVM 所需堆大小 |
| MemoryChannel，capacity 50 万条，平均消息 2KB | 至少 4GB |
| FileChannel | 1~2GB 即可（数据在磁盘） |

## 性能压测：Load Generator Source

Flume 内置了压测用的 Load Generator Source，无需写测试数据即可评估 Channel 和 Sink 的极限性能：

```properties
# 压测专用配置：load-test.conf
agent.sources = load
agent.channels = mem
agent.sinks = hdfs

# Load Generator Source：持续生成固定大小的测试消息
# 使用 StressSource；原稿重复设置 type 会使后一项覆盖前一项
agent.sources.load.type = org.apache.flume.source.StressSource

# 每次批量发送条数
agent.sources.load.batch-size = 1000

# 事件数量上限参数；不是消息大小，-1 的语义需按所用版本确认
agent.sources.load.maxTotalEvents = -1     # 原稿拟设为无限制，运行前核验
agent.sources.load.maxSuccessfulEvents = -1

agent.sources.load.channels = mem

agent.channels.mem.type = memory
agent.channels.mem.capacity = 500000
agent.channels.mem.transactionCapacity = 10000

agent.sinks.hdfs.type = hdfs
agent.sinks.hdfs.hdfs.path = hdfs://namenode:8020/flume-perf-test/
agent.sinks.hdfs.hdfs.batchSize = 2000
agent.sinks.hdfs.hdfs.rollSize = 134217728
agent.sinks.hdfs.channel = mem
```

**启动压测并观察 TPS：**

```bash
# 启动压测 Agent
flume-ng agent --conf conf --conf-file load-test.conf --name agent \
  -Dflume.monitoring.type=http -Dflume.monitoring.port=34545 &

# 每 10 秒采样一次，计算入 Channel TPS；这不是端到端交付 TPS
prev_ts=
prev_put=
while true; do
  ts=$(date +%s)
  put=$(curl -fsS http://localhost:34545/metrics | python3 -c \
    "import sys,json; d=json.load(sys.stdin); \
     print(d['CHANNEL.mem']['EventPutSuccessCount'])") || break
  if [ -n "$prev_ts" ] && [ "$ts" -gt "$prev_ts" ] && [ "$put" -ge "$prev_put" ]; then
    awk -v n="$((put-prev_put))" -v s="$((ts-prev_ts))" \
      'BEGIN {printf "EventPut TPS=%.2f\n", n/s}'
  fi
  echo "$(date): EventPutSuccessCount=$put"
  prev_ts=$ts
  prev_put=$put
  sleep 10
done
```

## 调优参数速查表

| 参数 | 组件 | 默认值 | 调优建议 |
|------|------|--------|---------|
| `batchSize` | Taildir Source | 100 | 500~2000 |
| 文件发现与空闲轮询参数 | Taildir Source | 按版本核验 | 不使用原稿文件组 `monitorInterval` 键，按延迟与 CPU 实测调整 |
| `capacity` | MemoryChannel | 100 | 峰值TPS×延迟容忍秒数 |
| `transactionCapacity` | MemoryChannel | 100 | 覆盖 Source/Sink 最大事务批次，且不超过 capacity |
| `dataDirs` | FileChannel | 单目录 | 多磁盘多目录 |
| `batchSize` | HDFS Sink | 100 | 1000~5000 |
| `rollSize` | HDFS Sink | 1024 字节 | 128MB~256MB 可作为测试起点，不保证文件精确对齐 HDFS Block |
| `threadsPoolSize` | HDFS Sink | 10 | 根据并发写文件数调整 |
| `-Xmx` | JVM | 未设置 | MemoryChannel 场景 2~8GB |
| GC 策略 | JVM | - | 堆>4GB 用 G1GC |

> [!tip] 调优的正确姿势
>
> - 先建立监控，再开始调优，否则无法量化效果
> - 每次只改一个参数，对比调优前后的指标变化
> - 可接受进程故障导致内存事件丢失时，可评估 MemoryChannel；需要持久化与崩溃恢复时，可评估 FileChannel，但仍须设计磁盘故障、重放和去重机制
> - HDFS Sink 的 rollSize 可参考实际 HDFS Block 大小（如 128MB 或 256MB）设置，但实际文件大小还受批次、格式和其他滚动条件影响，不能保证消除小文件或精确对齐
> - JVM 堆内存不是越大越好，过大会导致 GC 停顿时间变长
