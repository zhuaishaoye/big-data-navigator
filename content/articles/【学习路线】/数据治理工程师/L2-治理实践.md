# L2-治理实践

> [!abstract] 数据治理项目实践实战手册
> L2 治理实践要求从制度认知走向真实项目闭环：能够围绕资产、标准、质量、血缘、权限和整改开展工作，写出可验证规则，推动责任人处理异常，并证明治理动作改善了风险或数据可用性。

## 1. L2-治理实践：定义、适用边界与决策出口

L2 治理实践要求从制度认知走向真实项目闭环：能够围绕资产、标准、质量、血缘、权限和整改开展工作，写出可验证规则，推动责任人处理异常，并证明治理动作改善了风险或数据可用性。

**本篇的适用边界。** 本篇面向开始参与数据治理项目的分析师、开发和管理人员，覆盖标准、质量、指标、权限与整改；不把平台功能配置或制度编写等同于治理落地。

**最常见的错误替代。** 不能用规则数量、扫描次数和工单关闭率代替风险降低，也不能把所有数据问题都归因于上游系统。

**最终决策。** 治理实践者要判断：先治理哪些资产，规则是否有效，问题是否阻断发布，整改是否真正完成，权限和豁免是否合理，以及如何向业务证明价值。 因此，这篇内容不从“应该建哪张表”开始，而从业务动作、责任人和失败后果开始。只有先确定谁在什么时点做出什么决定，字段、SQL、看板和模型才有明确用途。

围绕“L2-治理实践”，工作中至少要区分四类问题：

1. **身份问题**：对象是谁，主键能否跨系统稳定关联，合并、拆分、撤销后历史是否还看得见。
2. **时间问题**：业务发生、状态生效、数据入仓、计算完成和人员行动分别发生在哪一刻。
3. **状态问题**：当前状态是一段事件、一张快照还是最终结果，空值代表未发生、未采集还是已删除。
4. **责任问题**：谁确认口径，谁处理异常，谁有权放行或停止，谁在观察期后复盘。

## 2. L2-治理实践的完整业务流程

| 环节 | 要做的事 | 最小证据 | 失败后先查什么 |
| --- | --- | --- | --- |
| 范围与风险选样 | 按业务影响、监管、变更和事故选择资产 | 资产清单、风险分级和抽样理由 | 资产清单很大但无优先级和动作 |
| 资产与责任确认 | 明确所有者、口径、系统和消费方 | 资产卡、责任矩阵和口径版本 | 规则长期全绿却无法验证有效 |
| 标准与质量设计 | 定义字段标准、规则、阈值和测试样本 | 标准、规则、样例和阻断策略 | 动态任务和临时表没有覆盖 |
| 血缘与变更影响 | 建立字段和任务链路，识别变更范围 | 血缘、发布单、影响分析和回滚方案 | 历史数据修好但根因仍在 |
| 权限与用途验证 | 检查最小权限、敏感字段和导出路径 | 角色、审批、脱敏和访问日志 | 资产清单很大但无优先级和动作 |
| 异常处置与整改 | 把问题分派到根因责任人并保留证据 | 问题、根因、修复、对账和复核 | 规则长期全绿却无法验证有效 |
| 价值复盘 | 展示风险、质量、时效和采用变化 | 基线、护栏、复发和用户反馈 | 动态任务和临时表没有覆盖 |

把 范围与风险选样、资产与责任确认、标准与质量设计、血缘与变更影响、权限与用途验证、异常处置与整改、价值复盘 串起来后可以看出，L2-治理实践不是一个孤立字段，而是一条会跨系统、跨岗位、跨时间的证据链。流程图上每一段都应标出输入、输出、状态、时间戳、责任人和异常出口。只要其中一段只能靠口头解释，后续的统计、追责和自动化就会失去基础。

一个合格的需求说明应该写成：

> 在【授权数据范围】和【观察窗口】内，围绕“L2-治理实践”的【治理资产】，按【business_domain、asset_type、root_cause_type、owner_team】比较【关键资产治理覆盖率】及其【质量规则有效率】，定位一个可干预节点；行动后同时观察主指标、样本量和护栏，任何高风险异常先阻断再调查。

## 3. L2-治理实践的数据对象与系统契约

| 数据对象 | 建议主键 | 一行代表什么 | 不允许混淆 |
| --- | --- | --- | --- |
| 治理资产 | `governed_asset_id` | 纳入治理的库表、指标、接口、报表或模型 | 对象身份与业务事件 |
| 数据标准 | `data_standard_id` | 命名、类型、编码、口径和有效版本 | 事件、状态快照和结果粒度 |
| 质量规则 | `quality_rule_id` | 针对明确粒度和对象的可执行检查 | 事件、状态快照和结果粒度 |
| 血缘关系 | `lineage_edge_id` | 源字段到目标字段或任务之间的一条关系 | 事件、状态快照和结果粒度 |
| 权限授权 | `access_grant_id` | 主体、资源、用途和有效期关系 | 事件、状态快照和结果粒度 |
| 整改问题 | `remediation_id` | 根因、责任人、动作、期限和验收证据 | 事件、状态快照和结果粒度 |

对象表不是把所有字段塞进一张宽表。事件、状态快照和结果表应该分别保留粒度，再通过稳定主键与版本建立关联。尤其要避免三个常见混算：把一次业务事件算成多个对象、把每日快照相加当事件总量、把最新状态覆盖历史状态。

本主题的数据契约至少应包含：

- `remediation_id` 的唯一性规则、生成方式和跨系统映射。
- `opened_at` 的业务含义、时区、迟到和补录规则。
- `remediation_status` 的完整状态集合，以及删除、撤销、冻结和失效的表示方法。
- 控制对象 `governance_quality_rule_result.quality_rule_result_id` 与主对象的关系。
- 每次口径、规则、模型或源版本变化的影响范围和下游通知对象。
- 敏感字段、允许用途、访问角色、导出限制和审计保留时间。

## 4. L2-治理实践的指标、样本与验收口径

| 指标 | 公式或定义 | 口径提醒 |
| --- | --- | --- |
| 关键资产治理覆盖率 | 完成责任、口径、质量和权限四项登记的资产数 / 关键资产数 | 四项需分别核验 |
| 质量规则有效率 | 发现真实问题且能回到明细的规则数 / 已启用规则数 | 长期零命中规则需复审 |
| 血缘覆盖完整率 | 能追到源字段和消费方的关键字段数 / 关键字段数 | 动态 SQL 需额外确认 |
| 整改根因关闭率 | 完成根因修复并经过完整周期复查的问题数 / 已关闭问题数 | 临时补数不算根因关闭 |
| 高风险权限及时回收率 | 到期或身份变化后在规定时间内回收的授权数 / 应回收授权数 | 按小时或天设置 SLO |

指标字典至少写到“任何人都能按同一份数据复跑”的程度：中文名、业务定义、公式、分子、分母、事实粒度、时间字段、对象范围、排除项、版本、负责人和验收样例，一个都不能少。比例指标必须同时展示分子、分母和样本量；金额或数量必须做守恒；状态指标必须能回到事件时间线。

对于“L2-治理实践”，建议把观察分成三层：

| 层次 | 看什么 | 不能替代什么 |
| --- | --- | --- |
| 业务结果 | 关键资产治理覆盖率、质量规则有效率 | 不能替代过程证据和个案回查 |
| 过程护栏 | 血缘覆盖完整率、整改根因关闭率、高风险权限及时回收率 | 不能因为护栏暂时正常就跳过异常调查 |
| 数据证据 | 主键、时间、状态、版本、来源目标对账 | 不能只看任务成功或报表能打开 |

## 5. L2-治理实践：七个真实工作场景

以下七组场景均为公开方法结合常见工作流程构造的“脱敏复合示例”，不对应任何单一企业、患者、客户或雇员事实。场景的目的，是展示如何从现象走到证据、行动和验收，而不是虚构经营成果。

### 1. 治理项目从盘点开始但没有结论

**现场。** 团队整理了上千张表，几个月后仍无法说明风险。

**怎么查。** 检查范围和输出，发现只登记表名，没有业务影响、消费方和问题优先级。

**怎么处理。** 从关键指标和事故链路反推资产；先做少量高价值资产；每个问题绑定责任人和整改。

**验收结论。** 治理不是资产清单越长越好，而是优先处理高影响对象。

### 2. 质量规则只检查非空

**现场。** 核心订单表监控通过，但业务发现重复订单和金额异常。

**怎么查。** 建立规则覆盖矩阵，补充唯一性、状态、守恒、跨系统和及时性检查。

**怎么处理。** 按风险设计规则；每条规则有粒度、样本和阻断等级；上线前用历史事故回放。

**验收结论。** 规则覆盖率不能只数条数，要覆盖真正的失败模式。

### 3. 指标同名不同口径

**现场。** 财务、运营和数据团队分别维护活跃客户数，差异超过 10%。

**怎么查。** 追踪公式、时间窗、去重键、排除项和源系统，发现三个版本都有历史合理性。

**怎么处理。** 建立主口径和子口径关系；每个口径绑定消费方；变更走评审和通知；历史不追溯覆盖，增加版本。

**验收结论。** 治理不是消灭所有差异，而是让每个差异有明确适用边界。

### 4. 血缘解析漏掉动态任务

**现场。** 字段变更影响分析显示无下游，发布后多个报表异常。

**怎么查。** 比较静态解析、运行时依赖、临时表和脚本参数，确认关键链路未被覆盖。

**怎么处理。** 高风险链路补充运行时血缘；发布前要求关键消费方确认；血缘缺口进入整改。

**验收结论。** 血缘完整率必须经过故障和变更验证，不能只看平台展示。

### 5. 权限复核批量通过

**现场。** 季度复核显示全部授权合理，抽查仍发现过期项目账号。

**怎么查。** 结合身份状态、最后访问、用途和审批记录，发现复核人没有打开明细。

**怎么处理。** 高风险权限逐项复核；过期和离职自动回收；抽样访问日志；批量确认附风险声明。

**验收结论。** 流程完成不代表控制有效。权限结果必须能改变真实访问。

### 6. 整改关闭后再次复发

**现场。** 数据质量工单完成修复，两个月后同一指标再次异常。

**怎么查。** 回放根因、修复代码、补数范围和复发记录，发现只修正了历史数据。

**怎么处理。** 区分数据修复与流程修复；完整周期观察；同类规则自动回归；复发纳入责任域复盘。

**验收结论。** 关闭工单不是关闭风险。

### 7. 治理价值无法向业务说明

**现场。** 团队报告规则数、扫描数和问题数持续增长，业务仍认为没有价值。

**怎么查。** 把治理动作关联事故减少、报表可信、交付提速和权限回收，建立可验证基线。

**怎么处理。** 选择少量业务痛点做前后对比；同时报告成本；避免把自然改善归功于治理。

**验收结论。** 治理价值要落在风险和决策上，而不是平台活动量。

七个场景可以归成一条共同判断顺序：先确认对象和时间，再确认状态和版本；然后做总量、结构和明细三层对账；最后才讨论策略、模型或工具。若一条结论不能指出对应的原始记录、责任人和行动出口，就只能算观察，不能作为生产结论。

## 6. L2-治理实践的第一段 SQL：重建业务链路

下面的 SQL 用于说明对象、时间、状态、版本和分层口径如何进入同一条可复查路径。表名和部分字段是通用示例，落地时应映射到企业数据字典；SQL 方言也需按实际引擎调整。

```sql
-- L2-治理实践：按业务对象重建链路，避免事件、快照和结果混算
WITH ranked_remediation_id AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY remediation_id
      ORDER BY updated_at DESC
    ) AS version_no
  FROM governance_remediation
  WHERE opened_at >= TIMESTAMP '{start_time}'
    AND opened_at <  TIMESTAMP '{end_time}'
    AND remediation_status NOT IN ('deleted', 'test')
),
valid_rows AS (
  SELECT
    remediation_id,
    business_domain,
    asset_type,
    root_cause_type,
    owner_team,
    opened_at,
    remediation_status,
    ingested_at
  FROM ranked_remediation_id
  WHERE version_no = 1
)
SELECT
  business_domain, asset_type, root_cause_type, owner_team,
  COUNT(DISTINCT remediation_id) AS object_cnt,
  COUNT(DISTINCT CASE WHEN root_cause_verified_at IS NOT NULL THEN remediation_id END) AS numerator_value,
  COUNT(DISTINCT remediation_id) AS denominator_value,
  CAST(COUNT(DISTINCT CASE WHEN root_cause_verified_at IS NOT NULL THEN remediation_id END) AS DOUBLE PRECISION)
    / NULLIF(COUNT(DISTINCT remediation_id), 0) AS metric_value,
  MIN(opened_at) AS first_event_at,
  MAX(opened_at) AS last_event_at
FROM valid_rows
GROUP BY business_domain, asset_type, root_cause_type, owner_team
ORDER BY metric_value DESC, object_cnt DESC;
```

执行后至少回答六个问题：

- 同一对象是否因为多源回传产生多版本，版本保留是否符合业务要求？
- 业务时间与入仓时间是否分开，补录和迟到数据是否进入正确分区？
- 分子分母是否来自同一对象范围和同一统计窗口？
- 维度使用的是事件当时值还是当前值，跨期比较是否一致？
- 删除、撤销、冻结和测试数据是否按规则处理？
- 分组结果能否在明细中抽样复现？

## 7. L2-治理实践的第二段 SQL：源、控制和结果三方对账

```sql
-- L2-治理实践：源对象、控制对象和结果对象三方对账
WITH population AS (
  SELECT
    remediation_id,
    opened_at,
    remediation_status
  FROM governance_remediation
  WHERE opened_at >= TIMESTAMP '{start_time}'
    AND opened_at <  TIMESTAMP '{end_time}'
),
control AS (
  SELECT
    remediation_id,
    SUM(failed_record_count) AS control_value,
    COUNT(DISTINCT quality_rule_result_id) AS control_cnt,
    MAX(updated_at) AS control_updated_at
  FROM governance_quality_rule_result
  WHERE updated_at >= TIMESTAMP '{start_time}'
  GROUP BY remediation_id
),
result AS (
  SELECT
    remediation_id,
    COUNT(*) AS result_cnt,
    MAX(calculated_at) AS calculated_at
  FROM mart_remediation_id
  WHERE business_date BETWEEN DATE '{start_date}' AND DATE '{end_date}'
  GROUP BY remediation_id
)
SELECT
  COALESCE(p.remediation_id, c.remediation_id, r.remediation_id) AS object_key,
  CASE
    WHEN p.remediation_id IS NULL THEN 'source_missing'
    WHEN c.remediation_id IS NULL THEN 'control_missing'
    WHEN r.remediation_id IS NULL THEN 'result_missing'
    WHEN ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0 THEN 'count_or_value_gap'
    ELSE 'matched'
  END AS reconciliation_status,
  p.remediation_status,
  c.control_value,
  c.control_cnt,
  r.result_cnt,
  c.control_updated_at,
  r.calculated_at
FROM population p
FULL OUTER JOIN control c ON p.remediation_id = c.remediation_id
FULL OUTER JOIN result r ON COALESCE(p.remediation_id, c.remediation_id) = r.remediation_id
WHERE p.remediation_id IS NULL
   OR c.remediation_id IS NULL
   OR r.remediation_id IS NULL
   OR ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0;
```

这段查询故意不使用“总数相差小于某个随意百分比就算通过”。它先找出缺失对象和状态差异，再检查控制值与结果值。对于L2-治理实践，数量、金额、时长或状态任意一项无法解释，都不能用“业务波动”代替排查。

对账结果建议分成四类处理：

1. **阻断**：对象缺失、关键时间为空、状态非法、金额或数量不守恒、权限越界。
2. **严重**：比例或总量显著偏离基线，且无法由已确认的对象结构变化解释。
3. **观察**：小范围波动但来源、样本和趋势可控，进入责任人和观察窗口。
4. **探索**：只有弱信号或假设，不进入正式结论，更不直接触发业务处罚。

## 8. L2-治理实践的 Python 发布门禁与指标护栏

第一段代码把发布条件写成可执行对象，避免“检查过了”只存在聊天记录里：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class RemediationIdBatch:
    batch_id: str
    source_rows: int
    valid_rows: int
    duplicate_keys: int
    missing_required_fields: int
    reconciliation_gap: float

def release_remediation_id(batch: RemediationIdBatch) -> dict:
    checks = {
        "source_not_empty": batch.source_rows > 0,
        "valid_rows_in_range": 0 <= batch.valid_rows <= batch.source_rows,
        "duplicate_rate_ok": batch.duplicate_keys / max(batch.source_rows, 1) <= 0.001,
        "required_fields_ok": batch.missing_required_fields == 0,
        "reconciliation_ok": abs(batch.reconciliation_gap) <= 0.01,
    }
    return {
        "topic": "L2-治理实践",
        "batch_id": batch.batch_id,
        "checks": checks,
        "release_allowed": all(checks.values()),
        "blocking_checks": [name for name, passed in checks.items() if not passed],
    }
```

第二段代码演示如何为比例类结果附带样本证据和小样本下界。它不是替代统计学家的模型，而是防止把少量偶然样本直接包装成稳定结论：

```python
from dataclasses import dataclass
from math import sqrt

@dataclass(frozen=True)
class RemediationIdObservation:
    object_id: str
    numerator: float
    denominator: float
    sample_size: int
    scope_version: str

def calculate_remediation_id(rows: list[RemediationIdObservation]) -> list[dict]:
    output = []
    for row in rows:
        value = row.numerator / row.denominator if row.denominator > 0 else None
        # 小样本用 Wilson 下界做护栏，不把偶然的高比例直接当稳定结果。
        z = 1.96
        p = value or 0
        n = max(row.sample_size, 1)
        center = p + z * z / (2 * n)
        margin = z * sqrt((p * (1 - p) + z * z / (4 * n)) / n)
        lower = max(0, (center - margin) / (1 + z * z / n))
        output.append({
            "object_id": row.object_id,
            "metric": "关键资产治理覆盖率",
            "value": value,
            "lower_bound": lower if value is not None else None,
            "sample_size": row.sample_size,
            "scope_version": row.scope_version,
            "caution": "四项需分别核验",
        })
    return output
```

真正上线时还要补充参数配置、日志、血缘、告警级别、重跑幂等、异常样本保存和审批记录。代码通过不代表业务通过；自动检查只能证明已经定义的规则没有被违反，无法证明规则本身一定正确。

## 9. L2-治理实践的失败反例与上线验收

| 风险信号 | 错误做法 | 必须补齐的证据 | 发布或行动规则 |
| --- | --- | --- | --- |
| 盘点代替治理 | 资产清单很大但无优先级和动作 | 业务影响、消费方和责任人 | 先治理关键链路 |
| 规则没有失败样本 | 规则长期全绿却无法验证有效 | 历史事故和边界样本 | 上线前完成失败回放 |
| 血缘只看解析器 | 动态任务和临时表没有覆盖 | 运行时依赖和人工确认 | 关键字段多渠道验证 |
| 补数冒充整改 | 历史数据修好但根因仍在 | 根因修复和完整周期复查 | 临时与根因修复分开验收 |

上线验收不应只有一句“报表正常”。建议按下面四层验收：

| 验收对象 | 结构要求 | 测试样本 | 结果证据 |
| --- | --- | --- | --- |
| 治理资产 | `governed_asset_id` 能唯一定位纳入治理的库表、指标、接口、报表或模型 | 正常、重复、缺失、撤销与跨期样本 | 关键资产治理覆盖率可回到原始对象 |
| 数据标准 | `data_standard_id` 能唯一定位命名、类型、编码、口径和有效版本 | 正常、重复、缺失、撤销与跨期样本 | 质量规则有效率可回到原始对象 |
| 质量规则 | `quality_rule_id` 能唯一定位针对明确粒度和对象的可执行检查 | 正常、重复、缺失、撤销与跨期样本 | 血缘覆盖完整率可回到原始对象 |
| 血缘关系 | `lineage_edge_id` 能唯一定位源字段到目标字段或任务之间的一条关系 | 正常、重复、缺失、撤销与跨期样本 | 整改根因关闭率可回到原始对象 |
| 权限授权 | `access_grant_id` 能唯一定位主体、资源、用途和有效期关系 | 正常、重复、缺失、撤销与跨期样本 | 高风险权限及时回收率可回到原始对象 |
| 整改问题 | `remediation_id` 能唯一定位根因、责任人、动作、期限和验收证据 | 正常、重复、缺失、撤销与跨期样本 | 关键资产治理覆盖率可回到原始对象 |

还应为每一次发布保留一组固定回归样本：正常对象、边界状态、重复记录、缺失字段、撤销或退款、跨期、权限拒绝和失败恢复。回归样本不是演示数据，而是以后每次改规则都能重复执行的质量资产。

## 10. L2-治理实践的 30 天落地与复盘

| 阶段 | 主要交付 | 通过条件 |
| --- | --- | --- |
| 第 1 周：定义 | 对象、流程、状态、指标、排除项和责任矩阵 | 业务、数据、安全或质量负责人对同一口径签字 |
| 第 2 周：打通 | 源字段、主键、时间、版本、控制对象和失败样本 | 正常与异常样本都能回到原始记录 |
| 第 3 周：验证 | 总量对账、分层对账、抽样回查、权限测试、回滚演练 | 阻断问题清零，严重问题有责任人与期限 |
| 第 4 周：发布 | 灰度、SLO、监控、行动清单、停止条件和复盘模板 | 使用者在真实场景中完成一次闭环行动 |

如果必须用 90 秒说明“L2-治理实践”是否做对，可以按这个顺序自测：

1. 一行数据代表什么，主键是什么，哪些对象绝不能混在同一粒度？
2. 业务发生、数据可见、计算完成和行动确认分别在哪个时间点？
3. 本主题最重要的两个主指标、三个护栏和最小样本量是什么？
4. 一个异常出现时，先从原始记录、链路版本还是业务动作开始查？
5. 哪类错误必须阻断发布或停止使用，谁有权批准例外？
6. 上线后由谁在多长时间内观察，什么条件下回滚或结束？

> [!check] 完成标准
> 当另一位数据同事不看聊天记录，只根据口径卡、回归样本和代码就能复跑同一结果；当业务负责人能指出一个异常对应的原始对象、处置动作和复核证据；当系统能够阻止未授权或状态非法的数据进入下游，这篇“L2-治理实践”才算真正落到工作里。
