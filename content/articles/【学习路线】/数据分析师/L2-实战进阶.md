# L2-实战进阶

> [!abstract] 数据分析师实战能力实战手册
> L2 实战进阶的重点不是多学几个函数，而是能独立把模糊业务问题转换成对象、口径、分析设计、SQL 或实验、结论和行动，并能解释偏差、反例和局限。

## 1. L2-实战进阶：定义、适用边界与决策出口

L2 实战进阶的重点不是多学几个函数，而是能独立把模糊业务问题转换成对象、口径、分析设计、SQL 或实验、结论和行动，并能解释偏差、反例和局限。

**本篇的适用边界。** 本篇面向已经掌握基础 SQL、统计和可视化，开始独立承接专题分析的学习者；不覆盖算法研究或大型数据平台架构的全部内容。

**最常见的错误替代。** 不能用刷题数量代替真实问题拆解，也不能用“显著”“增长”“优化”等结论跳过口径、样本和因果限制。

**最终决策。** 学习者要判断：下一步该补业务理解、SQL、统计、实验还是表达能力，什么时候可以独立交付，以及作品是否足以支撑面试追问。 因此，这篇内容不从“应该建哪张表”开始，而从业务动作、责任人和失败后果开始。只有先确定谁在什么时点做出什么决定，字段、SQL、看板和模型才有明确用途。

围绕“L2-实战进阶”，工作中至少要区分四类问题：

1. **身份问题**：对象是谁，主键能否跨系统稳定关联，合并、拆分、撤销后历史是否还看得见。
2. **时间问题**：业务发生、状态生效、数据入仓、计算完成和人员行动分别发生在哪一刻。
3. **状态问题**：当前状态是一段事件、一张快照还是最终结果，空值代表未发生、未采集还是已删除。
4. **责任问题**：谁确认口径，谁处理异常，谁有权放行或停止，谁在观察期后复盘。

## 2. L2-实战进阶的完整业务流程

| 环节 | 要做的事 | 最小证据 | 失败后先查什么 |
| --- | --- | --- | --- |
| 问题澄清 | 确认决策、对象、时间窗、指标和约束 | 问题卡、干系人、当前决策和成功标准 | 花大量时间做无关维度 |
| 口径与数据审计 | 定义分母、状态、去重、缺失和渠道归属 | 指标卡、数据质量结果和样本 | 同一指标多人计算不同结果 |
| 探索与分群 | 做趋势、结构、漏斗、同期群和异常分析 | 图表、分层贡献和反例 | 探索分析被当成验证实验 |
| 方法选择 | 在描述、相关、实验或准实验之间选择 | 方法假设、对照和敏感性分析 | 报告完整但无人可执行 |
| SQL 与复现 | 编写可读、可验证、可扩展的查询 | CTE、测试样本、代码版本和结果对账 | 花大量时间做无关维度 |
| 结论与行动 | 把证据转成建议、负责人、护栏和观察窗口 | 决策备忘、风险与下一步 | 同一指标多人计算不同结果 |
| 复盘与作品化 | 记录失败、边界和个人贡献 | 复盘、代码说明和面试讲稿 | 探索分析被当成验证实验 |

把 问题澄清、口径与数据审计、探索与分群、方法选择、SQL 与复现、结论与行动、复盘与作品化 串起来后可以看出，L2-实战进阶不是一个孤立字段，而是一条会跨系统、跨岗位、跨时间的证据链。流程图上每一段都应标出输入、输出、状态、时间戳、责任人和异常出口。只要其中一段只能靠口头解释，后续的统计、追责和自动化就会失去基础。

一个合格的需求说明应该写成：

> 在【授权数据范围】和【观察窗口】内，围绕“L2-实战进阶”的【分析任务】，按【analyst_id、business_domain、method_type、quarter_code】比较【分析问题一次澄清率】及其【口径返工率】，定位一个可干预节点；行动后同时观察主指标、样本量和护栏，任何高风险异常先阻断再调查。

## 3. L2-实战进阶的数据对象与系统契约

| 数据对象 | 建议主键 | 一行代表什么 | 不允许混淆 |
| --- | --- | --- | --- |
| 分析任务 | `analysis_task_id` | 一个具有问题、决策和交付要求的分析工作 | 对象身份与业务事件 |
| 指标口径 | `metric_definition_id` | 公式、粒度、时间和排除项的唯一版本 | 事件、状态快照和结果粒度 |
| 分析样本 | `analysis_sample_id` | 经筛选和去重并用于计算的观察对象集合 | 事件、状态快照和结果粒度 |
| 分析结论 | `finding_id` | 一条由证据支持并可被质疑的发现 | 事件、状态快照和结果粒度 |
| 行动建议 | `recommendation_id` | 面向决策者的动作、责任人和护栏 | 事件、状态快照和结果粒度 |
| 学习作品 | `portfolio_project_id` | 可复跑并展示判断过程的分析项目 | 事件、状态快照和结果粒度 |

对象表不是把所有字段塞进一张宽表。事件、状态快照和结果表应该分别保留粒度，再通过稳定主键与版本建立关联。尤其要避免三个常见混算：把一次业务事件算成多个对象、把每日快照相加当事件总量、把最新状态覆盖历史状态。

本主题的数据契约至少应包含：

- `analysis_task_id` 的唯一性规则、生成方式和跨系统映射。
- `submitted_at` 的业务含义、时区、迟到和补录规则。
- `review_status` 的完整状态集合，以及删除、撤销、冻结和失效的表示方法。
- 控制对象 `analytics_metric_definition.metric_definition_id` 与主对象的关系。
- 每次口径、规则、模型或源版本变化的影响范围和下游通知对象。
- 敏感字段、允许用途、访问角色、导出限制和审计保留时间。

## 4. L2-实战进阶的指标、样本与验收口径

| 指标 | 公式或定义 | 口径提醒 |
| --- | --- | --- |
| 分析问题一次澄清率 | 首次评审即明确决策、对象和指标的任务数 / 总任务数 | 不能把反复改需求全部归因于业务方 |
| 口径返工率 | 因分母、时间或状态问题重算的分析数 / 交付分析数 | 按根因分类 |
| SQL 结果对账通过率 | 总量、分组和明细均通过对账的查询数 / 查询数 | 任务成功不算结果正确 |
| 建议采纳率 | 在观察期内被业务实际执行或试验的建议数 / 有效建议数 | 采纳不等于产生收益 |
| 作品可复现率 | 他人按文档和代码可重现核心结果的次数 / 验收次数 | 数据和权限须可合法获得 |

指标字典至少写到“任何人都能按同一份数据复跑”的程度：中文名、业务定义、公式、分子、分母、事实粒度、时间字段、对象范围、排除项、版本、负责人和验收样例，一个都不能少。比例指标必须同时展示分子、分母和样本量；金额或数量必须做守恒；状态指标必须能回到事件时间线。

对于“L2-实战进阶”，建议把观察分成三层：

| 层次 | 看什么 | 不能替代什么 |
| --- | --- | --- |
| 业务结果 | 分析问题一次澄清率、口径返工率 | 不能替代过程证据和个案回查 |
| 过程护栏 | SQL 结果对账通过率、建议采纳率、作品可复现率 | 不能因为护栏暂时正常就跳过异常调查 |
| 数据证据 | 主键、时间、状态、版本、来源目标对账 | 不能只看任务成功或报表能打开 |

## 5. L2-实战进阶：七个真实工作场景

以下七组场景均为公开方法结合常见工作流程构造的“脱敏复合示例”，不对应任何单一企业、患者、客户或雇员事实。场景的目的，是展示如何从现象走到证据、行动和验收，而不是虚构经营成果。

### 1. 需求是“看看为什么下降”

**现场。** 业务希望分析转化下降原因，但没有明确对象和时间。

**怎么查。** 先确认决策、指标、比较基线和可行动环节，发现管理层真正担心的是新客首单转化。

**怎么处理。** 拆成总量、结构、漏斗和渠道四层；约定输出是定位一个优先环节，而不是列全部图表。

**验收结论。** 好的分析不是回答所有问题，而是先把决策问题定义清楚。

### 2. SQL 跑通但口径错误

**现场。** 查询能正常返回日活，业务却质疑与看板不一致。

**怎么查。** 对比用户去重、登录事件、测试账号、跨时区和外部分享，发现看板排除了异常设备。

**怎么处理。** 建立口径卡和回归样本；分别输出原始、排除后和敏感性结果；差异签名确认。

**验收结论。** 代码运行成功是最低标准，口径一致才进入分析。

### 3. 显著结果只是多重比较

**现场。** 团队同时测试几十个分群，挑出两个显著改善。

**怎么查。** 检查实验设计、比较次数、样本量和事前假设，发现没有多重比较控制。

**怎么处理。** 回到预注册主指标；分群结果标注探索性质；使用置信区间和校正方法；不据此直接上线。

**验收结论。** 显著不是重要，更不是真实因果。分析越多，偶然结果越多。

### 4. 相关性被写成因果结论

**现场。** 高活跃用户的复购率更高，报告建议继续提高活跃。

**怎么查。** 检查共同原因、选择偏差和行动可执行性，发现会员权益同时影响活跃和复购。

**怎么处理。** 使用实验或准实验验证；区分相关、预测和因果；把建议改成待验证假设。

**验收结论。** 高价值用户的行为不一定能复制给所有人。

### 5. 图表很多但没有行动出口

**现场。** 20 页报告展示各种维度，会议结束没有任何决定。

**怎么查。** 回看问题卡和结论，发现没有优先级、负责人和观察窗口。

**怎么处理。** 围绕一个关键决策组织 1 到 3 条结论；明确动作、护栏和失败条件；把其他图表放附录。

**验收结论。** 分析的交付物是更好的决策，不是更多图片。

### 6. 作品集只有最终数字

**现场。** 候选人的简历写了提升 30%，面试无法解释数据和方法。

**怎么查。** 追问基线、口径、本人职责、失败试验和团队因素，发现数字来自多个团队共同结果。

**怎么处理。** 改写为问题、个人动作、证据、限制和复盘；准备原始数据结构与 SQL 讲解。

**验收结论。** 无法解释的数字会削弱可信度，清楚边界反而更专业。

### 7. 面试现场 SQL 只追求写出来

**现场。** 候选人给出了复杂嵌套查询，但没有处理重复和空值。

**怎么查。** 让其在普通、边界和重复样本上解释结果，发现主键假设错误。

**怎么处理。** 先说明粒度、去重键、时间范围和验收样例；用 CTE 分层；最后再做性能和写法优化。

**验收结论。** 面试考察的是能不能写出可被信任的结果，而不是函数数量。

七个场景可以归成一条共同判断顺序：先确认对象和时间，再确认状态和版本；然后做总量、结构和明细三层对账；最后才讨论策略、模型或工具。若一条结论不能指出对应的原始记录、责任人和行动出口，就只能算观察，不能作为生产结论。

## 6. L2-实战进阶的第一段 SQL：重建业务链路

下面的 SQL 用于说明对象、时间、状态、版本和分层口径如何进入同一条可复查路径。表名和部分字段是通用示例，落地时应映射到企业数据字典；SQL 方言也需按实际引擎调整。

```sql
-- L2-实战进阶：按业务对象重建链路，避免事件、快照和结果混算
WITH ranked_analysis_task_id AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY analysis_task_id
      ORDER BY updated_at DESC
    ) AS version_no
  FROM analytics_task_result
  WHERE submitted_at >= TIMESTAMP '{start_time}'
    AND submitted_at <  TIMESTAMP '{end_time}'
    AND review_status NOT IN ('deleted', 'test')
),
valid_rows AS (
  SELECT
    analysis_task_id,
    analyst_id,
    business_domain,
    method_type,
    quarter_code,
    submitted_at,
    review_status,
    ingested_at
  FROM ranked_analysis_task_id
  WHERE version_no = 1
)
SELECT
  analyst_id, business_domain, method_type, quarter_code,
  COUNT(DISTINCT analysis_task_id) AS object_cnt,
  COUNT(DISTINCT CASE WHEN reconciliation_passed THEN analysis_task_id END) AS numerator_value,
  COUNT(DISTINCT analysis_task_id) AS denominator_value,
  CAST(COUNT(DISTINCT CASE WHEN reconciliation_passed THEN analysis_task_id END) AS DOUBLE PRECISION)
    / NULLIF(COUNT(DISTINCT analysis_task_id), 0) AS metric_value,
  MIN(submitted_at) AS first_event_at,
  MAX(submitted_at) AS last_event_at
FROM valid_rows
GROUP BY analyst_id, business_domain, method_type, quarter_code
ORDER BY metric_value DESC, object_cnt DESC;
```

执行后至少回答六个问题：

- 同一对象是否因为多源回传产生多版本，版本保留是否符合业务要求？
- 业务时间与入仓时间是否分开，补录和迟到数据是否进入正确分区？
- 分子分母是否来自同一对象范围和同一统计窗口？
- 维度使用的是事件当时值还是当前值，跨期比较是否一致？
- 删除、撤销、冻结和测试数据是否按规则处理？
- 分组结果能否在明细中抽样复现？

## 7. L2-实战进阶的第二段 SQL：源、控制和结果三方对账

```sql
-- L2-实战进阶：源对象、控制对象和结果对象三方对账
WITH population AS (
  SELECT
    analysis_task_id,
    submitted_at,
    review_status
  FROM analytics_task_result
  WHERE submitted_at >= TIMESTAMP '{start_time}'
    AND submitted_at <  TIMESTAMP '{end_time}'
),
control AS (
  SELECT
    analysis_task_id,
    SUM(approved_version) AS control_value,
    COUNT(DISTINCT metric_definition_id) AS control_cnt,
    MAX(updated_at) AS control_updated_at
  FROM analytics_metric_definition
  WHERE updated_at >= TIMESTAMP '{start_time}'
  GROUP BY analysis_task_id
),
result AS (
  SELECT
    analysis_task_id,
    COUNT(*) AS result_cnt,
    MAX(calculated_at) AS calculated_at
  FROM mart_analysis_task_id
  WHERE business_date BETWEEN DATE '{start_date}' AND DATE '{end_date}'
  GROUP BY analysis_task_id
)
SELECT
  COALESCE(p.analysis_task_id, c.analysis_task_id, r.analysis_task_id) AS object_key,
  CASE
    WHEN p.analysis_task_id IS NULL THEN 'source_missing'
    WHEN c.analysis_task_id IS NULL THEN 'control_missing'
    WHEN r.analysis_task_id IS NULL THEN 'result_missing'
    WHEN ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0 THEN 'count_or_value_gap'
    ELSE 'matched'
  END AS reconciliation_status,
  p.review_status,
  c.control_value,
  c.control_cnt,
  r.result_cnt,
  c.control_updated_at,
  r.calculated_at
FROM population p
FULL OUTER JOIN control c ON p.analysis_task_id = c.analysis_task_id
FULL OUTER JOIN result r ON COALESCE(p.analysis_task_id, c.analysis_task_id) = r.analysis_task_id
WHERE p.analysis_task_id IS NULL
   OR c.analysis_task_id IS NULL
   OR r.analysis_task_id IS NULL
   OR ABS(COALESCE(c.control_value, 0) - COALESCE(r.result_cnt, 0)) > 0;
```

这段查询故意不使用“总数相差小于某个随意百分比就算通过”。它先找出缺失对象和状态差异，再检查控制值与结果值。对于L2-实战进阶，数量、金额、时长或状态任意一项无法解释，都不能用“业务波动”代替排查。

对账结果建议分成四类处理：

1. **阻断**：对象缺失、关键时间为空、状态非法、金额或数量不守恒、权限越界。
2. **严重**：比例或总量显著偏离基线，且无法由已确认的对象结构变化解释。
3. **观察**：小范围波动但来源、样本和趋势可控，进入责任人和观察窗口。
4. **探索**：只有弱信号或假设，不进入正式结论，更不直接触发业务处罚。

## 8. L2-实战进阶的 Python 发布门禁与指标护栏

第一段代码把发布条件写成可执行对象，避免“检查过了”只存在聊天记录里：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class AnalysisTaskIdBatch:
    batch_id: str
    source_rows: int
    valid_rows: int
    duplicate_keys: int
    missing_required_fields: int
    reconciliation_gap: float

def release_analysis_task_id(batch: AnalysisTaskIdBatch) -> dict:
    checks = {
        "source_not_empty": batch.source_rows > 0,
        "valid_rows_in_range": 0 <= batch.valid_rows <= batch.source_rows,
        "duplicate_rate_ok": batch.duplicate_keys / max(batch.source_rows, 1) <= 0.001,
        "required_fields_ok": batch.missing_required_fields == 0,
        "reconciliation_ok": abs(batch.reconciliation_gap) <= 0.01,
    }
    return {
        "topic": "L2-实战进阶",
        "batch_id": batch.batch_id,
        "checks": checks,
        "release_allowed": all(checks.values()),
        "blocking_checks": [name for name, passed in checks.items() if not passed],
    }
```

第二段代码演示如何为比例类结果附带样本证据和小样本下界。它不是替代统计学家的模型，而是防止把少量偶然样本直接包装成稳定结论：

```python
from dataclasses import dataclass
from math import sqrt

@dataclass(frozen=True)
class AnalysisTaskIdObservation:
    object_id: str
    numerator: float
    denominator: float
    sample_size: int
    scope_version: str

def calculate_analysis_task_id(rows: list[AnalysisTaskIdObservation]) -> list[dict]:
    output = []
    for row in rows:
        value = row.numerator / row.denominator if row.denominator > 0 else None
        # 小样本用 Wilson 下界做护栏，不把偶然的高比例直接当稳定结果。
        z = 1.96
        p = value or 0
        n = max(row.sample_size, 1)
        center = p + z * z / (2 * n)
        margin = z * sqrt((p * (1 - p) + z * z / (4 * n)) / n)
        lower = max(0, (center - margin) / (1 + z * z / n))
        output.append({
            "object_id": row.object_id,
            "metric": "分析问题一次澄清率",
            "value": value,
            "lower_bound": lower if value is not None else None,
            "sample_size": row.sample_size,
            "scope_version": row.scope_version,
            "caution": "不能把反复改需求全部归因于业务方",
        })
    return output
```

真正上线时还要补充参数配置、日志、血缘、告警级别、重跑幂等、异常样本保存和审批记录。代码通过不代表业务通过；自动检查只能证明已经定义的规则没有被违反，无法证明规则本身一定正确。

## 9. L2-实战进阶的失败反例与上线验收

| 风险信号 | 错误做法 | 必须补齐的证据 | 发布或行动规则 |
| --- | --- | --- | --- |
| 问题未定义就取数 | 花大量时间做无关维度 | 决策、对象、时间窗和成功标准 | 先评审问题卡 |
| 口径未版本化 | 同一指标多人计算不同结果 | 公式、排除项和负责人 | 分析前冻结口径版本 |
| 只挑显著结果 | 探索分析被当成验证实验 | 假设、比较次数和样本 | 主次结果分级 |
| 结论无行动 | 报告完整但无人可执行 | 责任人、护栏和观察窗口 | 每个建议写决策出口 |

上线验收不应只有一句“报表正常”。建议按下面四层验收：

| 验收对象 | 结构要求 | 测试样本 | 结果证据 |
| --- | --- | --- | --- |
| 分析任务 | `analysis_task_id` 能唯一定位一个具有问题、决策和交付要求的分析工作 | 正常、重复、缺失、撤销与跨期样本 | 分析问题一次澄清率可回到原始对象 |
| 指标口径 | `metric_definition_id` 能唯一定位公式、粒度、时间和排除项的唯一版本 | 正常、重复、缺失、撤销与跨期样本 | 口径返工率可回到原始对象 |
| 分析样本 | `analysis_sample_id` 能唯一定位经筛选和去重并用于计算的观察对象集合 | 正常、重复、缺失、撤销与跨期样本 | SQL 结果对账通过率可回到原始对象 |
| 分析结论 | `finding_id` 能唯一定位一条由证据支持并可被质疑的发现 | 正常、重复、缺失、撤销与跨期样本 | 建议采纳率可回到原始对象 |
| 行动建议 | `recommendation_id` 能唯一定位面向决策者的动作、责任人和护栏 | 正常、重复、缺失、撤销与跨期样本 | 作品可复现率可回到原始对象 |
| 学习作品 | `portfolio_project_id` 能唯一定位可复跑并展示判断过程的分析项目 | 正常、重复、缺失、撤销与跨期样本 | 分析问题一次澄清率可回到原始对象 |

还应为每一次发布保留一组固定回归样本：正常对象、边界状态、重复记录、缺失字段、撤销或退款、跨期、权限拒绝和失败恢复。回归样本不是演示数据，而是以后每次改规则都能重复执行的质量资产。

## 10. L2-实战进阶的 30 天落地与复盘

| 阶段 | 主要交付 | 通过条件 |
| --- | --- | --- |
| 第 1 周：定义 | 对象、流程、状态、指标、排除项和责任矩阵 | 业务、数据、安全或质量负责人对同一口径签字 |
| 第 2 周：打通 | 源字段、主键、时间、版本、控制对象和失败样本 | 正常与异常样本都能回到原始记录 |
| 第 3 周：验证 | 总量对账、分层对账、抽样回查、权限测试、回滚演练 | 阻断问题清零，严重问题有责任人与期限 |
| 第 4 周：发布 | 灰度、SLO、监控、行动清单、停止条件和复盘模板 | 使用者在真实场景中完成一次闭环行动 |

如果必须用 90 秒说明“L2-实战进阶”是否做对，可以按这个顺序自测：

1. 一行数据代表什么，主键是什么，哪些对象绝不能混在同一粒度？
2. 业务发生、数据可见、计算完成和行动确认分别在哪个时间点？
3. 本主题最重要的两个主指标、三个护栏和最小样本量是什么？
4. 一个异常出现时，先从原始记录、链路版本还是业务动作开始查？
5. 哪类错误必须阻断发布或停止使用，谁有权批准例外？
6. 上线后由谁在多长时间内观察，什么条件下回滚或结束？

> [!check] 完成标准
> 当另一位数据同事不看聊天记录，只根据口径卡、回归样本和代码就能复跑同一结果；当业务负责人能指出一个异常对应的原始对象、处置动作和复核证据；当系统能够阻止未授权或状态非法的数据进入下游，这篇“L2-实战进阶”才算真正落到工作里。
