# AI多Agent协作系统

> [!tip] 核心原则
> “AI多Agent协作系统”在会议里常常只有一句话，落到数据团队却会展开成口径、主键、时间、状态、权限和交付责任。下面用一个从问题到上线的顺序展开，并穿插三个脱敏的复合案例，帮助你把标题里的知识迁移到真实项目。

## 1. 从业务任务定义 AI 能力

围绕“AI多Agent协作系统”，先把任务写成输入、输出、成功标准和失败边界。不要从“上一套模型”或“接一个聊天框”开始。

| 设计项 | 必须回答的问题 | 错误示例 | 更好做法 |
| --- | --- | --- | --- |
| 用户 | 谁使用，谁复核，谁承担后果 | 所有人都能用 | 按角色和权限明确使用边界 |
| 输入 | 文本、表格、图片还是工具调用 | 把所有数据都塞进上下文 | 只提供任务所需且获授权的数据 |
| 输出 | 分类、生成、检索、SQL 还是动作 | 只要求“回答准确” | 定义可检查的输出结构 |
| 成功 | 任务完成、采纳、质量、时延和成本 | 只看离线准确率 | 离线 + 线上 + 人工复核 |
| 失败 | 无答案、拒答、转人工还是回滚 | 失败也生成看似合理内容 | 明确置信阈值和降级路径 |

## 2. 数据、知识库与版本

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 数据集 | `dataset_id` | 问题定义 |
| 过程对象 | 样本 | `sample_id` | 数据准备 |
| 过程对象 | 模型版本 | `model_version` | 方案设计 |
| 结果对象 | 应用请求 | `request_id` | 实验评估 |
| 结果对象 | 评测案例 | `eval_case_id` | 上线灰度 |
| 专题分析 | AI多Agent协作系统 | `topic_key = 'ai_agent'` | 用于把通用事件收窄到本主题 |

AI 项目的数据治理比传统报表更强调版本和来源。至少记录：

- 数据集和知识文档的来源、授权、时间、负责人和版本。
- 样本标注规则、标注人、抽检结果和争议处理。
- 训练、验证、测试与线上反馈是否隔离。
- 提示词、模型、温度、检索参数和工具权限的版本。
- 输入中的个人信息、商业秘密和敏感字段是否脱敏。

如果“AI多Agent协作系统”使用 RAG，文档切片应尊重标题、章节、表格和条款结构；如果使用微调，先证明提示词、检索或流程优化不足；如果使用 Agent，先限制工具白名单和最大执行步数。

## 3. 评估：不要只看一个准确率

| 评估层 | 指标 | 说明 |
| --- | --- | --- |
| 检索 | Hit@K、MRR、版本正确率、权限过滤 | 正确内容是否被召回且可用 |
| 生成 | 引用支持率、事实一致性、完整性 | 回答是否有证据、是否遗漏关键条件 |
| 任务 | 完成率、转人工率、采纳率、重复澄清 | 用户问题是否真的解决 |
| 安全 | 越权、注入、敏感输出、违规动作 | 是否突破权限与安全边界 |
| 工程 | P50/P95 延迟、错误率、并发、成本 | 能否稳定且经济地服务 |
| 业务 | 节省时间、转化、质量、投诉 | 是否带来可解释价值 |

离线集要包含高频问题、长尾问题、边界问题、对抗问题和“应该拒答”的问题。线上评估要按用户、任务和风险等级分层，避免总体平均掩盖高危错误。

## 4. 案例一：华南某电商客服 Agent

### 案例 1：华南某电商客服 Agent的“AI多Agent协作系统”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“AI多Agent协作系统”映射到“AI Agent、工具调用与安全边界”中的状态，而不是泛泛讨论概念。
- **触发事件**：多轮对话中智能体反复调用订单和优惠工具，成本上升但问题解决率没有改善。
- **业务与数据范围**：会话状态、工具轨迹、调用参数、解决状态、转人工、时延和 token 成本。数据侧重点采集状态版本、来源、TTL 和会话隔离，并与数据仓库、特征平台、向量数据库中的时间、状态和责任人信息对齐。
- **需要回答的问题**：上下文、记忆和中间结果是否准确、过期或污染。
- **关键障碍**：缺少停止条件，工具失败后继续重试，重复信息被反复放入上下文。同时要防止训练与线上样本泄漏把表面指标带偏。
- **处理过程**：增加任务状态机、最大步数、工具级超时与缓存，连续失败转人工，并按意图分层评估。实施时把“工具在服务端做身份、参数、对象、环境和权限校验”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：复合案例以一次解决率、平均步数、P95 和单位任务成本验收。验收至少同时看主指标、状态版本、来源、TTL 和会话隔离和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把任务目标、规划、工具、状态、权限、预算、评估和人工接管设计成受控系统，不允许模型绕过服务端授权直接执行高风险动作。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

## 5. Python：检索与任务评估

### 检索、Agent 或模型任务实现

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Tool:
    name: str
    read_only: bool
    allowed_roles: set[str]

TOOLS = {
    "search_logs": Tool("search_logs", True, {"operator", "analyst"}),
    "restart_service": Tool("restart_service", False, {"operator"}),
}

def execute_tool(name: str, arguments: dict, actor: dict, approved: bool = False) -> dict:
    tool = TOOLS.get(name)
    if not tool:
        raise PermissionError("tool_not_in_allowlist")
    if actor["role"] not in tool.allowed_roles:
        raise PermissionError("role_not_allowed")
    if not tool.read_only and not approved:
        raise PermissionError("human_approval_required")
    return {"tool": name, "arguments": arguments, "audit": "recorded"}

# 主题："AI多Agent协作系统"
# 记录计划、工具参数、结果、错误、模型版本、步数和人工操作；
# 设置最大步数、超时、预算、失败退出与转人工，模型不能自行扩大权限。
```

### 标题专属数据与失败分层 SQL

```sql
-- AI多Agent协作系统：同期基线诊断（业务场景 × 租户）
WITH scoped AS (
  SELECT
    dataset_id AS entity_key,
    event_id,
    request_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_ai_request
  WHERE request_time >= DATE '2026-02-01'
    AND request_time <  DATE '2026-05-01'
    AND subject_key = 'ai_agent'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '检索命中率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

示例代码只展示可测试结构。真实系统还需要模型服务、向量库、权限、日志、缓存、限流、敏感检查和人工反馈，不应把安全完全交给提示词。

## 6. 案例二：华北某金融分析 Agent

### 案例 2：华北某金融分析 Agent的“AI多Agent协作系统”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“AI多Agent协作系统”映射到“AI Agent、工具调用与安全边界”中的工具，而不是泛泛讨论概念。
- **触发事件**：Agent 生成 SQL 后自动执行并制作图表，但部分查询超出用户数据权限。
- **业务与数据范围**：用户身份、语义层权限、SQL、执行计划、数据范围、审计和答案。数据侧重点采集工具清单、Schema、权限、审计和回滚，并与数据仓库、特征平台、向量数据库中的时间、状态和责任人信息对齐。
- **需要回答的问题**：工具白名单、参数校验、幂等和副作用边界。
- **关键障碍**：权限只在最终展示层处理，SQL 已读取敏感明细，工具还会使用共享服务账号。同时要防止模型版本不可追溯把表面指标带偏。
- **处理过程**：执行前由语义层注入行级和字段权限，服务端限制扫描与导出，高风险查询要求复核。实施时把“完整记录计划、工具参数、结果、错误、版本和人工操作”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例工程证明 Agent 安全必须落在工具和执行层，而不是只靠提示词。验收至少同时看主指标、工具清单、Schema、权限、审计和回滚和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把任务目标、规划、工具、状态、权限、预算、评估和人工接管设计成受控系统，不允许模型绕过服务端授权直接执行高风险动作。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

## 7. 架构与工程链路

| 层次 | 本文建议 | 关键问题 | 验收证据 |
| --- | --- | --- | --- |
| 数据源 | 数据仓库、特征平台、向量数据库 | 权威源、更新频率、主键和权限 | 接口或表清单 |
| 接入 | 批、流或 CDC 按业务时延选择 | 重复、顺序、断点续传和回放 | 延迟与幂等测试 |
| 存储 | 按访问模式选择数据湖、数仓或 OLAP | 分区、格式、生命周期和成本 | 容量与查询评测 |
| 计算 | SQL、Spark、Flink 或 Python 服务 | 粒度、状态、资源和失败恢复 | 压测与执行计划 |
| 治理 | 元数据、质量、血缘、权限 | 责任、规则、影响分析和审计 | 规则结果与变更记录 |
| 服务 | 指标、API、看板或应用 | SLA、缓存、限流和版本 | 监控与验收样例 |

推荐把链路拆成六层：数据与知识准备、检索或特征、模型调用、工具执行、评估与审核、监控与反馈。每层都要有版本、日志和失败处理。Agent 工具调用应在服务端校验参数与权限，不能只依赖模型“自觉”。

## 8. 监控、成本与安全

- 监控请求量、延迟、错误码、超时、重试和缓存命中。
- 记录检索文档版本、模型版本、提示词版本和关键参数。
- 对失败分类：检索缺失、上下文过长、工具失败、权限拒绝、模型拒答、结果不合规。
- 设置单位任务成本、每租户预算和异常调用告警。
- 对提示注入、越权、敏感信息和危险动作做专门测试。
- 保留人工复核、转人工、回滚到旧模型和关闭工具的开关。

## 9. 第三个案例与上线验收

### 案例 3：华东某企业运维 Agent的“AI多Agent协作系统”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“AI多Agent协作系统”映射到“AI Agent、工具调用与安全边界”中的任务，而不是泛泛讨论概念。
- **触发事件**：智能体可以自动查日志并重启服务，一次错误判断导致非目标实例被操作。
- **业务与数据范围**：用户指令、工具参数、服务清单、权限、审批、执行日志和回滚记录。数据侧重点采集目标说明、完成条件、最大步数和失败分类，并与数据仓库、特征平台、向量数据库中的时间、状态和责任人信息对齐。
- **需要回答的问题**：成功是什么、何时停止、什么情况必须转人工。
- **关键障碍**：模型能直接调用高权限工具，目标实例仅由自然语言解析，没有环境标签和服务端校验。同时要防止评测与业务目标脱节把表面指标带偏。
- **处理过程**：只暴露只读工具给模型，写操作生成变更单并由服务端校验目标、环境和审批，执行后自动验证健康状态。实施时把“对越权、提示注入、循环调用、错误重试和数据泄露做专门测试”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例系统把越权、误操作和不可回滚动作设为阻断级风险。验收至少同时看主指标、目标说明、完成条件、最大步数和失败分类和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把任务目标、规划、工具、状态、权限、预算、评估和人工接管设计成受控系统，不允许模型绕过服务端授权直接执行高风险动作。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

| 验收项 | 最低要求 | 证据 |
| --- | --- | --- |
| 任务定义 | 输入输出和失败路径明确 | 产品说明、评测集 |
| 数据授权 | 来源、用途和权限可追溯 | 数据卡、授权记录 |
| 离线评估 | 覆盖常规、边界和拒答 | 评测报告 |
| 线上灰度 | 有对照组和护栏指标 | 实验或灰度记录 |
| 安全 | 越权、注入和敏感输出已测试 | 红队与审计报告 |
| 成本 | 单位请求预算和上限明确 | 账单与调用日志 |
| 运营 | 有反馈、复盘和回滚 | 周报、事故演练 |

1. 先写清“AI多Agent协作系统”的目标：把任务目标、规划、工具、状态、权限、预算、评估和人工接管设计成受控系统，不允许模型绕过服务端授权直接执行高风险动作。
2. 专题检查：任务必须有完成条件、最大步数、超时、预算和转人工规则
3. 专题检查：工具在服务端做身份、参数、对象、环境和权限校验
4. 专题检查：完整记录计划、工具参数、结果、错误、版本和人工操作
5. 专题检查：对越权、提示注入、循环调用、错误重试和数据泄露做专门测试
6. 明确“AI多Agent协作系统”服务的使用者、决策动作和不做范围，并把成功标准写成可观察指标。
7. 为数据集、样本、模型版本分别确认主键、时间和状态，画出从源系统到结果的链路。
8. 先做字段血缘和质量画像，检查训练与评测数据隔离、版本可追溯、敏感字段已脱敏。
9. 用同周期基线和至少两个维度拆解问题，避免只比较一个异常周。
10. 抽取正常、异常和边界样本回查原始业务单据，记录抽样方法与结论。
11. 选择一种代码实现并保留参数、版本、执行日志和结果快照，确保别人可以复跑。
12. 上线前定义告警阈值、回滚条件和责任人；上线后按周观察主指标与护栏指标。
13. 复盘时区分数据问题、业务变化、方案偏差和外部因素，并把改进项转成有时限的任务。

### 扩展代码一：从AI多Agent协作系统回到可核对明细

```sql
-- AI多Agent协作系统：状态链与时间间隔核查
WITH ordered_events AS (
  SELECT
    dataset_id AS entity_key,
    event_id,
    stage_code,
    request_time AS event_time,
    LAG(stage_code) OVER (
      PARTITION BY dataset_id
      ORDER BY request_time, event_id
    ) AS previous_stage,
    LAG(request_time) OVER (
      PARTITION BY dataset_id
      ORDER BY request_time, event_id
    ) AS previous_time
  FROM fact_ai_request
  WHERE request_time >= :start_date
    AND request_time <  :end_date
    AND subject_key = 'ai_agent'
)
SELECT
  entity_key,
  previous_stage,
  stage_code,
  event_time,
  event_time - previous_time AS elapsed,
  CASE
    WHEN event_time < previous_time THEN 'time_reversed'
    WHEN previous_stage = stage_code THEN 'duplicate_stage'
    WHEN previous_stage IS NULL THEN 'missing_prefix'
    ELSE 'candidate_delay'
  END AS exception_type
FROM ordered_events
WHERE event_time < previous_time
   OR previous_stage = stage_code
   OR event_time - previous_time > INTERVAL '1 hour'
ORDER BY exception_type, elapsed DESC;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把AI多Agent协作系统的验收证据写成门禁

```python
import pandas as pd

KEY = ["entity_key", "event_id"]
AMOUNT_COLUMNS = ["metric_value", "adjustment_value"]


def reconcile(source: pd.DataFrame, result: pd.DataFrame) -> pd.DataFrame:
    def aggregate(frame: pd.DataFrame, side: str) -> pd.DataFrame:
        grouped = (
            frame.groupby("entity_key", dropna=False)
            .agg(
                event_cnt=("event_id", "nunique"),
                metric_sum=("metric_value", "sum"),
                adjustment_sum=("adjustment_value", "sum"),
            )
            .reset_index()
        )
        return grouped.rename(columns={
            "event_cnt": f"{side}_event_cnt",
            "metric_sum": f"{side}_metric_sum",
            "adjustment_sum": f"{side}_adjustment_sum",
        })

    compared = aggregate(source, "source").merge(
        aggregate(result, "result"),
        on="entity_key",
        how="outer",
    )
    compared["metric_diff"] = (
        compared["result_metric_sum"].fillna(0)
        - compared["source_metric_sum"].fillna(0)
    )
    compared["event_diff"] = (
        compared["result_event_cnt"].fillna(0)
        - compared["source_event_cnt"].fillna(0)
    )
    compared["exception"] = compared.apply(
        lambda row: "missing_result" if pd.isna(row["result_metric_sum"])
        else "unexpected_result" if pd.isna(row["source_metric_sum"])
        else "count_diff" if row["event_diff"] != 0
        else "amount_diff",
        axis=1,
    )
    return compared.loc[
        (compared["metric_diff"].abs() > 0) | (compared["event_diff"] != 0)
    ].sort_values("metric_diff", key=lambda values: values.abs(), ascending=False)
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
