# AI伦理与治理

> [!tip] 分析目标
> 一个关于“AI伦理与治理”的结论能不能被信任，取决于它是否能回到原始事件、明确时间和对象，并说明排除了哪些记录。下面不会用单一模板概括所有场景，而是结合AI 与大数据中的多类任务，展示数据建模、代码分析和项目验收之间如何衔接。

## 1. 把主题翻译成可验证的问题

“AI伦理与治理”不能直接等同于“做一张趋势图”。一个可执行的分析问题至少包含对象、时间、比较基准和行动：

> 在【观察周期】内，对【有效对象】按【业务场景、模型版本、租户】比较【检索命中率】与【P95 延迟】，判断变化来自结构、行为还是数据口径，并验证【策略动作】是否带来可解释的增量。

在AI 与大数据场景中，用户行为、交易结果和策略曝光经常来自不同系统。先画数据流：

数据仓库 → 特征平台 → 向量数据库 → 模型服务 → 实验平台 → 监控平台

图中至少要有三个标记：业务事件发生时间、数据可见时间、策略或行动时间。只有三者分开，后续才能判断问题发生在业务、链路还是观察窗口。

## 2. 指标定义与分母检查

| 专题观测面 | 需要回答的问题 | 关键证据 | 判定与动作 |
| --- | --- | --- | --- |
| 版本（本标题优先） | 数据、Prompt、特征、模型和评测能否互相对应 | 版本标识、变更记录、回放和血缘 | 版本断链时停止发布 |
| 质量 | 样本是否代表目标人群，标注是否一致，偏差在哪里 | 抽样审核、标注一致性、分群覆盖和反例 | 只报总体准确率不充分 |
| 风险 | 隐私、偏见、越权、错误信息和滥用如何控制 | 红队、审计、人工复核和事故记录 | 高风险输出必须有降级路径 |
| 来源 | 数据从哪里来、是否授权、能否用于训练或评测 | 数据卡、授权依据、采集时间和用途 | 来源不清的数据不得进入训练 |

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 任务成功率 | `COUNT(DISTINCT success_request_id) / COUNT(DISTINCT request_id)`（视图字段 `task_success_rate`） | 业务场景、模型版本、租户 | 不混用测试、撤销和跨期状态；与“AI伦理与治理”相关时还要补充主题筛选 |
| 答案采纳率 | `COUNT(DISTINCT accepted_answer_id) / COUNT(DISTINCT reviewed_answer_id)`（视图字段 `answer_acceptance`） | 模型版本、租户、数据来源 | 不混用测试、撤销和跨期状态；与“AI伦理与治理”相关时还要补充主题筛选 |
| 检索命中率 | `COUNT(DISTINCT hit_query_id) / COUNT(DISTINCT evaluated_query_id)`（视图字段 `retrieval_hit_rate`） | 租户、数据来源、调用类型 | 不混用测试、撤销和跨期状态；与“AI伦理与治理”相关时还要补充主题筛选 |
| P95 延迟 | `PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY latency_ms)`（视图字段 `p95_latency`） | 数据来源、调用类型 | 不混用测试、撤销和跨期状态；与“AI伦理与治理”相关时还要补充主题筛选 |

针对“AI伦理与治理”，建议分别定义诊断指标、结果指标和护栏指标：

- **诊断指标**用于定位流程，例如曝光、有效访问、符合条件对象数和异常节点。
- **结果指标**用于判断是否改善，例如转化、留存、客单、毛利或处理时长。
- **护栏指标**用于防止局部优化伤害整体，例如退款、投诉、成本、公平性和长期留存。

每次计算都问四个问题：分母是谁、对象何时进入分母、例外状态怎么处理、窗口是否足够覆盖行为完成。尤其是训练与线上样本泄漏；模型版本不可追溯；评测与业务目标脱节，任何一项没有解释清楚，指标都可能“看起来合理但无法决策”。

## 3. 方法选择：描述、诊断、预测还是因果

| 目标 | 适合的方法 | 需要的证据 | 不要混淆 |
| --- | --- | --- | --- |
| 描述现状 | 趋势、结构、同期群 | 完整口径、稳定时间窗 | 描述不等于原因 |
| 定位异常 | 分层、贡献度、漏斗、异常检测 | 原始事件、基线和质量检查 | 排名靠前不等于因果 |
| 预测未来 | 时间序列、回归、机器学习 | 时间切分验证、误差成本 | 离线准确率不等于业务收益 |
| 评估策略 | A/B、灰度、准实验 | 对照组、样本量、护栏指标 | 上线前后对比容易混入季节和选择偏差 |

如果问题只是“发生了什么”，先别急着建模；如果问题涉及“采取某策略会怎样”，就必须讨论反事实和识别条件。围绕“AI伦理与治理”，应把观察分析、预测和因果评估的产出分开标注。

## 4. 案例一：华东某医疗 AI 团队

### 案例 1：华东某医疗 AI 团队的“AI伦理与治理”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“AI伦理与治理”映射到“AI 数据治理、合规与可解释性”中的版本，而不是泛泛讨论概念。
- **触发事件**：模型在总体测试集表现良好，但老年与罕见病人群错误率明显更高。
- **业务与数据范围**：影像、病历、年龄、疾病亚型、标注来源、训练版本和分群评估结果。数据侧重点采集版本标识、变更记录、回放和血缘，并与数据仓库、特征平台、向量数据库中的时间、状态和责任人信息对齐。
- **需要回答的问题**：数据、Prompt、特征、模型和评测能否互相对应。
- **关键障碍**：评测集人群结构失衡，数据卡没有记录排除标准。同时要防止训练与线上样本泄漏把表面指标带偏。
- **处理过程**：补充分群样本和专家复核，建立数据卡与模型卡，发布前检查弱势群体指标和错误类型。实施时把“建立隐私、越权、错误信息、滥用和人工复核控制”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例治理将总体准确率改为分群效果、风险差异和人工复核共同验收。验收至少同时看主指标、版本标识、变更记录、回放和血缘和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“为 AI 数据建立来源、授权、质量、版本、偏差、隐私、血缘和使用反馈的控制链，让模型效果与风险都能解释和追溯。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

落地时建议先把一个总指标拆成可行动的树：

```text
AI伦理与治理｜专题诊断画布
├── 业务问题：为 AI 数据建立来源、授权、质量、版本、偏差、隐私、血缘和使用反馈的控制链，让模型效果与风险都能解释和追溯。
├── 观测对象：数据集 / 样本
├── 主指标：检索命中率；辅助指标：P95 延迟
├── 风险边界：训练与线上样本泄漏；模型版本不可追溯；评测与业务目标脱节
└── 验收证据：SQL 结果 + 明细样本 + 责任人 + 观察窗口
```

如果某一分支变化最大，再进入下一层，而不是一开始就按十几个维度切碎。每个分层结果都应同时报告样本量，避免小样本的极端比例抢走注意力。

## 5. SQL：计算趋势、结构和贡献度

### 趋势、结构与贡献度诊断

```sql
-- AI伦理与治理：留存同期群诊断（租户 × 调用类型）
WITH scoped AS (
  SELECT
    dataset_id AS entity_key,
    event_id,
    request_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_ai_request
  WHERE request_time >= DATE '2026-04-01'
    AND request_time <  DATE '2026-07-01'
    AND subject_key = 'ai'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '单次调用成本' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

示例 SQL 只表达计算逻辑。实际实施应加入分区条件、业务状态过滤、时区和主题范围，并在结果中保留口径版本。

## 6. 案例二：华南某客服 AI 团队

### 案例 2：华南某客服 AI 团队的“AI伦理与治理”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“AI伦理与治理”映射到“AI 数据治理、合规与可解释性”中的质量，而不是泛泛讨论概念。
- **触发事件**：模型升级后回答质量波动，无法确认是数据、Prompt 还是检索变化。
- **业务与数据范围**：训练与评测数据、Prompt、检索索引、模型、请求日志和反馈。数据侧重点采集抽样审核、标注一致性、分群覆盖和反例，并与数据仓库、特征平台、向量数据库中的时间、状态和责任人信息对齐。
- **需要回答的问题**：样本是否代表目标人群，标注是否一致，偏差在哪里。
- **关键障碍**：各组件独立发布，没有统一版本和回放能力。同时要防止模型版本不可追溯把表面指标带偏。
- **处理过程**：为每次请求记录数据、索引、Prompt、模型和代码版本，建立可重放评测与一键回滚。实施时把“训练、评测和生产数据记录来源、授权、用途、版本和负责人”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：复合案例缩短问题定位时间，并支持影响范围分析。验收至少同时看主指标、抽样审核、标注一致性、分群覆盖和反例和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“为 AI 数据建立来源、授权、质量、版本、偏差、隐私、血缘和使用反馈的控制链，让模型效果与风险都能解释和追溯。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

当业务方要求“解释为什么下降”时，可以按下面顺序回答：

1. 先确认下降是否真实存在，排查采集、任务、维表和状态映射。
2. 把变化拆成对象数量、行为强度和结构占比。
3. 找到贡献最大的分组，但保留其他分组的抵消效应。
4. 抽取正负样本回查业务事件和操作日志。
5. 把尚不能证明的解释标为假设，并设计下一轮验证。

## 8. 异常、偏差与常见误区

- **辛普森悖论**：总体改善但每个分组都变差，可能由对象结构变化造成。
- **幸存者偏差**：只分析完成流程的对象，忽略中途流失和中止。
- **分母漂移**：渠道口径、登录状态、版本或活动范围变化，改变可比性。
- **回传延迟**：当天数据未回补，导致近期效果被系统性低估。
- **多重比较**：反复寻找显著分组，实际只是随机波动。
- **行动偏差**：只报告支持既定方案的结果，忽略反例和护栏指标。

围绕“AI伦理与治理”，应预先写出至少三条反例检查。比如方案是否说明了成本、边界和停止条件、上线后是否有人负责观察和复盘，以及 关键口径是否经过业务与技术共同确认。

```sql
-- AI伦理与治理：行动前后与分组增量
WITH scoped AS (
  SELECT
    dataset_id AS entity_key,
    租户 AS decision_group,
    request_time AS event_date,
    metric_value,
    CASE
      WHEN request_time <  :action_date THEN 'before'
      ELSE 'after'
    END AS period_label
  FROM fact_ai_request
  WHERE request_time >= :analysis_start
    AND request_time <  :analysis_end
    AND subject_key = 'ai'
),
grouped AS (
  SELECT
    decision_group,
    period_label,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    AVG(metric_value) AS metric_avg,
    SUM(metric_value) AS metric_sum
  FROM scoped
  GROUP BY decision_group, period_label
),
compared AS (
  SELECT
    decision_group,
    MAX(CASE WHEN period_label = 'before' THEN metric_avg END) AS before_avg,
    MAX(CASE WHEN period_label = 'after' THEN metric_avg END) AS after_avg,
    MAX(CASE WHEN period_label = 'before' THEN entity_cnt END) AS before_cnt,
    MAX(CASE WHEN period_label = 'after' THEN entity_cnt END) AS after_cnt
  FROM grouped
  GROUP BY decision_group
)
SELECT
  decision_group,
  before_avg,
  after_avg,
  after_avg - before_avg AS naive_delta,
  'P95 延迟' AS metric_name,
  '训练、评测和生产数据记录来源、授权、用途、版本和负责人' AS required_evidence
FROM compared
WHERE before_cnt >= 30 AND after_cnt >= 30
ORDER BY ABS(after_avg - before_avg) DESC;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把AI伦理与治理的验收证据写成门禁

```python
from dataclasses import dataclass
from datetime import datetime


@dataclass(frozen=True)
class ReleaseEvidence:
    subject: str
    source_watermark: datetime
    output_watermark: datetime
    source_rows: int
    output_rows: int
    duplicate_rows: int
    blocked_rows: int
    code_version: str
    parameter_version: str


def release_gate(evidence: ReleaseEvidence) -> tuple[bool, list[str]]:
    reasons = []
    if evidence.source_watermark != evidence.output_watermark:
        reasons.append("watermark_mismatch")
    if evidence.source_rows != evidence.output_rows:
        reasons.append("row_count_mismatch")
    if evidence.duplicate_rows:
        reasons.append("duplicate_keys")
    if evidence.blocked_rows:
        reasons.append("blocking_quality_rule_failed")
    if not evidence.code_version or not evidence.parameter_version:
        reasons.append("release_provenance_missing")
    return not reasons, reasons


evidence = ReleaseEvidence(
    subject="AI伦理与治理",
    source_watermark=datetime.fromisoformat("2026-11-06T02:00:00"),
    output_watermark=datetime.fromisoformat("2026-11-06T02:00:00"),
    source_rows=0,
    output_rows=0,
    duplicate_rows=0,
    blocked_rows=0,
    code_version="demo-v1",
    parameter_version="scope-v1",
)
print(release_gate(evidence))
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。

### 四个案例共用的验收清单

| 验证面 | 发布前问题 | 证据 | 不通过时 |
| --- | --- | --- | --- |
| 对象与粒度 | 一行数据代表数据集、事件、快照还是结果 | 主键、版本、有效时间和边界样本 | 阻断 |
| 时间语义 | 业务发生、数据可见、决策采用是否混用 | request_time、入仓时间、行动时间轴 | 阻断 |
| 指标口径 | 任务成功率的分子、分母和排除项是否冻结 | 指标字典、SQL、对账结果 | 阻断正式指标 |
| 状态与关联 | 问题定义 → 数据准备 → 方案设计 → 实验评估是否可达且可追溯 | 状态机、明细、操作日志 | 阻断关键链路 |
