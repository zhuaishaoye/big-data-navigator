# AI项目的数据治理

> [!abstract] 项目视角
> “AI项目的数据治理”既可能是业务概念，也可能是技术方案，还可能是岗位能力。判断学习是否有效，要看能否在训练数据准备、模型实验、RAG 检索、Agent 编排、离线评估和线上监控中做出一个可复现的小闭环。本文用多个案例展示从需求到数据结果，再回到业务行动和复盘的完整路径。

## 1. 项目背景与边界

“AI项目的数据治理”作为项目，必须同时定义业务目标、数据范围、技术边界和验收方式。建议在立项材料里写清：

- **业务目标**：改善哪个流程、服务哪个角色、影响什么决策。
- **现状基线**：当前耗时、错误率、覆盖率、成本或用户反馈，不能只写“比较落后”。
- **范围**：覆盖业务域、系统、表、指标和团队；明确不做什么。
- **约束**：数据权限、上线窗口、依赖系统、预算、合规和人员。
- **成功标准**：主指标、护栏指标、验收样例和观察周期。

一个合格目标示例：

> 在【时间】前，为【用户】交付“AI项目的数据治理”能力，使【任务成功率】达到【可解释目标】，同时保证训练与评测数据隔离、版本可追溯、敏感字段已脱敏，上线后由【负责人】按周复盘。

## 2. 现状诊断与数据资产盘点

先梳理数据仓库、特征平台、向量数据库、模型服务、实验平台、监控平台之间的数据流，记录源系统、接口、表、任务、负责人和延迟。不要用一张“系统架构图”掩盖数据质量问题，必须把主键、时间、状态和数量关系标出来。

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 数据集 | `dataset_id` | 问题定义 |
| 过程对象 | 样本 | `sample_id` | 数据准备 |
| 过程对象 | 模型版本 | `model_version` | 方案设计 |
| 结果对象 | 应用请求 | `request_id` | 实验评估 |
| 结果对象 | 评测案例 | `eval_case_id` | 上线灰度 |
| 专题分析 | AI项目的数据治理 | `topic_key = 'ai'` | 用于把通用事件收窄到本主题 |

盘点阶段至少输出：资产清单、接口清单、指标基线、质量问题清单、权限清单和依赖矩阵。对每个问题标记影响范围、发生频率、现有临时方案和根本原因。

## 3. 目标架构与方案取舍

| 层次 | 本文建议 | 关键问题 | 验收证据 |
| --- | --- | --- | --- |
| 数据源 | 数据仓库、特征平台、向量数据库 | 权威源、更新频率、主键和权限 | 接口或表清单 |
| 接入 | 批、流或 CDC 按业务时延选择 | 重复、顺序、断点续传和回放 | 延迟与幂等测试 |
| 存储 | 按访问模式选择数据湖、数仓或 OLAP | 分区、格式、生命周期和成本 | 容量与查询评测 |
| 计算 | SQL、Spark、Flink 或 Python 服务 | 粒度、状态、资源和失败恢复 | 压测与执行计划 |
| 治理 | 元数据、质量、血缘、权限 | 责任、规则、影响分析和审计 | 规则结果与变更记录 |
| 服务 | 指标、API、看板或应用 | SLA、缓存、限流和版本 | 监控与验收样例 |

方案评审至少比较两种选择。例如批处理与实时处理、现成工具与自研、集中式平台与数据网格。比较维度包括交付速度、时延、成本、可维护性、权限边界、扩展性和失败恢复，而不是只比较功能清单。

## 4. 数据模型与指标口径

| 专题观测面 | 需要回答的问题 | 关键证据 | 判定与动作 |
| --- | --- | --- | --- |
| 责任（本标题优先） | 谁定义、谁生产、谁使用、谁批准变更 | RACI、数据 steward 和升级路径 | 责任必须带决策权与时限 |
| 规则 | 哪些标准和质量规则需要自动执行 | 规则、阈值、样本、工单和豁免 | 规则失败要对应动作 |
| 资产 | 哪些数据影响关键决策、监管和资金 | 资产清单、等级、消费者和故障历史 | 先从高价值资产开始 |
| 运营 | 治理是否进入发布、事件和绩效流程 | 评审、复盘、成熟度和采用记录 | 没有业务使用的治理活动应重做 |

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 任务成功率 | `COUNT(DISTINCT success_request_id) / COUNT(DISTINCT request_id)`（视图字段 `task_success_rate`） | 业务场景、模型版本、租户 | 不混用测试、撤销和跨期状态；与“AI项目的数据治理”相关时还要补充主题筛选 |
| 答案采纳率 | `COUNT(DISTINCT accepted_answer_id) / COUNT(DISTINCT reviewed_answer_id)`（视图字段 `answer_acceptance`） | 模型版本、租户、数据来源 | 不混用测试、撤销和跨期状态；与“AI项目的数据治理”相关时还要补充主题筛选 |
| 检索命中率 | `COUNT(DISTINCT hit_query_id) / COUNT(DISTINCT evaluated_query_id)`（视图字段 `retrieval_hit_rate`） | 租户、数据来源、调用类型 | 不混用测试、撤销和跨期状态；与“AI项目的数据治理”相关时还要补充主题筛选 |
| P95 延迟 | `PERCENTILE_CONT(0.95) WITHIN GROUP (ORDER BY latency_ms)`（视图字段 `p95_latency`） | 数据来源、调用类型 | 不混用测试、撤销和跨期状态；与“AI项目的数据治理”相关时还要补充主题筛选 |

模型设计优先保证粒度清晰和可重算。事实表负责事件或结果，维度表负责对象属性与历史归属，汇总表负责稳定消费。对于“AI项目的数据治理”，如果既有事件又有状态，应分别建模，避免用最新状态覆盖历史。

## 5. 案例一：华北某工业集团

### 案例 1：华北某工业集团的“AI项目的数据治理”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“AI项目的数据治理”映射到“数据治理制度、责任与运营”中的责任，而不是泛泛讨论概念。
- **触发事件**：各工厂治理成熟度差异大，总部统一规则难以落地。
- **业务与数据范围**：工厂资产、系统、人员、问题、规则执行和本地流程。数据侧重点采集RACI、数据 steward 和升级路径，并与数据仓库、特征平台、向量数据库中的时间、状态和责任人信息对齐。
- **需要回答的问题**：谁定义、谁生产、谁使用、谁批准变更。
- **关键障碍**：总部按同一优先级推广全部规则，缺少本地负责人和差异化路径。同时要防止训练与线上样本泄漏把表面指标带偏。
- **处理过程**：按风险和场景分级，建立总部标准、本地执行、例外审批和成熟度评审。实施时把“标准、质量和安全规则进入项目与发布流程”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例机制兼顾统一控制与现场可执行性。验收至少同时看主指标、RACI、数据 steward 和升级路径和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“围绕关键数据资产建立标准、责任、质量、安全、血缘、变更和问题闭环，让治理机制进入日常交付。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

项目里最重要的一次评审通常发生在写代码之前。把对象、粒度、时间和成功标准画在白板上，让业务、数据、安全和运维共同指出歧义，往往比上线后修复便宜得多。

```python
from dataclasses import dataclass

TOPIC = "AI项目的数据治理"
POLICY_ID = "g_data_governance_ph2g5"

@dataclass(frozen=True)
class DataAsset:
    name: str
    criticality: str
    owner: str
    steward: str
    consumers: tuple[str, ...]
    controls: tuple[str, ...]
    last_reviewed: str

asset = DataAsset(
    name="enterprise_metric_snapshot",
    criticality="high",
    owner="business-domain-owner",
    steward="data-governance-steward",
    consumers=("management-reporting", "risk-monitor"),
    controls=("definition-version", "quality-gate", "lineage", "access-review"),
    last_reviewed="2026-11-06",
)

governance_checks = [
    "关键资产具有唯一负责人、业务定义、消费者和风险等级",
    "标准、质量和安全规则进入项目与发布流程",
    "血缘、版本和问题工单支持影响分析与审计",
    "治理成效由风险、返工、故障和采用衡量"
]

def validate_asset(item: DataAsset, checks: list[str]) -> list[str]:
    failures = []
    if not item.owner or not item.steward:
        failures.append("owner_chain_incomplete")
    if item.criticality not in {"critical", "high", "medium", "low"}:
        failures.append("risk_level_invalid")
    if not item.consumers:
        failures.append("consumer_list_missing")
    if len(item.controls) < len(checks):
        failures.append("controls_do_not_cover_checks")
    return failures

print({"policy": POLICY_ID, "failures": validate_asset(asset, governance_checks)})

```

### 上线前质量门禁

```python
# AI项目的数据治理：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "AI项目的数据治理"
TOPIC_KEY = "ai"
RULE_ID = "rule_ai_ph2g5"
GUIDE_CHECKS = [
    "关键资产具有唯一负责人、业务定义、消费者和风险等级",
    "标准、质量和安全规则进入项目与发布流程",
    "血缘、版本和问题工单支持影响分析与审计",
    "治理成效由风险、返工、故障和采用衡量"
]
RULES = {
    "required_columns": ["event_id", "dataset_id", "request_time", "status"],
    "duplicate_key": "event_id",
    "entity_key": "dataset_id",
    "time_field": "request_time",
    "max_duplicate_rate": 0.0006,
    "max_null_rate": 0.002,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：关键资产具有唯一负责人、业务定义、消费者和风险等级；标准、质量和安全规则进入项目与发布流程；血缘、版本和问题工单支持影响分析与审计；治理成效由风险、返工、故障和采用衡量
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

代码交付要求：

- 参数化日期、环境和业务范围，不在代码里硬编码生产密钥。
- 任务可重复运行，重复执行不会产生重复数据。
- 关键步骤记录输入行数、输出行数、过滤行数和质量结果。
- 失败时保留日志和中间状态，支持按分区重跑。
- 代码、配置和表结构纳入版本管理，并有变更记录。

## 8. 测试、灰度与上线

| 测试类型 | 检查内容 | 通过标准 |
| --- | --- | --- |
| 单元测试 | 字段映射、计算逻辑、边界条件 | 用例覆盖正常、异常和极端值 |
| 集成测试 | 上下游接口、主键关联、权限 | 端到端能跑通 |
| 数据测试 | 唯一、完整、及时、平衡 | 关键规则通过并留存结果 |
| 性能测试 | 扫描量、执行时长、并发和资源 | 在容量预算内且可扩展 |
| 灰度 | 小范围业务与新旧结果对照 | 差异可解释，问题可回滚 |
| 验收 | 业务样例、指标和操作流程 | 验收人签字或有系统记录 |

灰度阶段应保留新旧链路对照。差异不能简单要求“完全一致”，因为修复本身可能改变结果；正确做法是对每类差异给出原因、影响和审批。

### 案例 4：AI项目的数据治理跨团队交接的契约缺口

一次例行发布后，负责“AI项目的数据治理”的小组收到下游反馈：数字和源系统对不上，但任务本身全部成功。团队决定围绕“跨团队交接与责任”做一次完整回放。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 把数据定义、变更通知、失败动作、服务时限和责任人写成可测试的运行契约。在本场景里，核心风险还包括训练与线上样本泄漏，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：数据集、样本及其在方案设计前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注dataset_id与sample_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 上游认为字段已经交付，下游却持续遇到状态含义、历史归属和异常处理不一致，问题在群聊中反复流转。初看时，向量数据库与模型服务的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 数据契约版本、字段语义、接口样例、变更记录、工单时效、消费者验收和升级路径。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“运营与领域专家”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“AI项目的数据治理”的当前定义并记录版本；第二步用数据集明细核对向量数据库到模型服务的关联；第三步按业务场景与租户做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察任务成功率和护栏指标检索命中率。
- **行动与护栏：** 组织上游生产、数据开发、消费方和安全人员做一次契约评审，把模糊责任改成可执行的检查项。专题检查项“关键资产具有唯一负责人、业务定义、消费者和风险等级”被写成发布门禁，业务定义、粒度或状态语义发生破坏性变化时，未通知消费者不得直接发布。
- **失败路径：** 只建立群聊和文档链接，却没有版本、负责人、失败动作和下线流程。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“AI项目的数据治理”时，先验证RACI、数据 steward 和升级路径，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由运营与领域专家在明确时限内，根据任务成功率、检索命中率和训练与评测数据隔离决定继续、回退、补查还是转人工。 若训练与线上样本泄漏或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

- **处理步骤：** 第一步先冻结“AI项目的数据治理”的当前定义并记录版本；第二步用应用请求明细核对监控平台到权限审计的关联；第三步按数据来源与业务场景做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察P95 延迟和护栏指标任务成功率。
- **行动与护栏：** 先冻结本期对象范围，再分别按源系统口径和目标口径重算，对每一类差异写明原因和暂定处理。专题检查项“治理成效由风险、返工、故障和采用衡量”被写成发布门禁，口径未确认时只发布差异分析，不把任一结果包装成正式经营指标。
- **失败路径：** 用平均值掩盖差异，或直接把对不上的明细删掉。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“AI项目的数据治理”时，先验证评审、复盘、成熟度和采用记录，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由数据工程师在明确时限内，根据P95 延迟、任务成功率和失败请求已分类决定继续、回退、补查还是转人工。 若RAG 召回污染或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从AI项目的数据治理回到可核对明细

```sql
-- AI项目的数据治理：恢复后缺失、重复与跨期检查
WITH expected_keys AS (
  SELECT DISTINCT dataset_id AS entity_key, event_id
  FROM fact_ai_request
  WHERE request_time >= :restore_start
    AND request_time <  :restore_end
    AND subject_key = 'ai'
),
restored_keys AS (
  SELECT dataset_id AS entity_key, event_id, load_version, loaded_at
  FROM fact_ai_request
  WHERE request_time >= :restore_start
    AND request_time <  :restore_end
    AND subject_key = 'ai'
    AND load_version = :restore_version
),
coverage AS (
  SELECT
    (SELECT COUNT(*) FROM expected_keys) AS expected_cnt,
    (SELECT COUNT(*) FROM restored_keys) AS restored_cnt,
    (SELECT COUNT(*) FROM (
      SELECT entity_key, event_id
      FROM restored_keys
      GROUP BY entity_key, event_id
      HAVING COUNT(*) > 1
    ) duplicate_keys) AS duplicated_cnt,
    (SELECT COUNT(*) FROM (
      SELECT e.entity_key, e.event_id
      FROM expected_keys e
      LEFT JOIN restored_keys r USING (entity_key, event_id)
      WHERE r.entity_key IS NULL
    ) missing_keys) AS missing_cnt
)
SELECT *,
  CASE
    WHEN expected_cnt <> restored_cnt OR duplicated_cnt > 0 OR missing_cnt > 0
      THEN 'reject_release'
    ELSE 'accept_restore'
  END AS gate_result
FROM coverage;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把AI项目的数据治理的验收证据写成门禁

```python
from dataclasses import dataclass
from datetime import datetime


@dataclass(frozen=True)
class ReleaseEvidence:
    subject: str
    source_watermark: datetime
    output_watermark: datetime
    source_rows: int
    output_rows: int
    duplicate_rows: int
    blocked_rows: int
    code_version: str
    parameter_version: str


def release_gate(evidence: ReleaseEvidence) -> tuple[bool, list[str]]:
    reasons = []
    if evidence.source_watermark != evidence.output_watermark:
        reasons.append("watermark_mismatch")
    if evidence.source_rows != evidence.output_rows:
        reasons.append("row_count_mismatch")
    if evidence.duplicate_rows:
        reasons.append("duplicate_keys")
    if evidence.blocked_rows:
        reasons.append("blocking_quality_rule_failed")
    if not evidence.code_version or not evidence.parameter_version:
        reasons.append("release_provenance_missing")
    return not reasons, reasons


evidence = ReleaseEvidence(
    subject="AI项目的数据治理",
    source_watermark=datetime.fromisoformat("2026-11-06T02:00:00"),
    output_watermark=datetime.fromisoformat("2026-11-06T02:00:00"),
    source_rows=0,
    output_rows=0,
    duplicate_rows=0,
    blocked_rows=0,
    code_version="demo-v1",
    parameter_version="scope-v1",
)
print(release_gate(evidence))
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
