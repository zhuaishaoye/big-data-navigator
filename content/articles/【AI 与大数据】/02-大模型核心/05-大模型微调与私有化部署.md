# 大模型微调与私有化部署

> [!tip] 核心原则
> “大模型微调与私有化部署”在会议里常常只有一句话，落到数据团队却会展开成口径、主键、时间、状态、权限和交付责任。下面用一个从问题到上线的顺序展开，并穿插三个脱敏的复合案例，帮助你把标题里的知识迁移到真实项目。

## 1. 从业务任务定义 AI 能力

围绕“大模型微调与私有化部署”，先把任务写成输入、输出、成功标准和失败边界。不要从“上一套模型”或“接一个聊天框”开始。

| 设计项 | 必须回答的问题 | 错误示例 | 更好做法 |
| --- | --- | --- | --- |
| 用户 | 谁使用，谁复核，谁承担后果 | 所有人都能用 | 按角色和权限明确使用边界 |
| 输入 | 文本、表格、图片还是工具调用 | 把所有数据都塞进上下文 | 只提供任务所需且获授权的数据 |
| 输出 | 分类、生成、检索、SQL 还是动作 | 只要求“回答准确” | 定义可检查的输出结构 |
| 成功 | 任务完成、采纳、质量、时延和成本 | 只看离线准确率 | 离线 + 线上 + 人工复核 |
| 失败 | 无答案、拒答、转人工还是回滚 | 失败也生成看似合理内容 | 明确置信阈值和降级路径 |

## 2. 数据、知识库与版本

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 数据集 | `dataset_id` | 问题定义 |
| 过程对象 | 样本 | `sample_id` | 数据准备 |
| 过程对象 | 模型版本 | `model_version` | 方案设计 |
| 结果对象 | 应用请求 | `request_id` | 实验评估 |
| 结果对象 | 评测案例 | `eval_case_id` | 上线灰度 |
| 专题分析 | 大模型微调与私有化部署 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

AI 项目的数据治理比传统报表更强调版本和来源。至少记录：

- 数据集和知识文档的来源、授权、时间、负责人和版本。
- 样本标注规则、标注人、抽检结果和争议处理。
- 训练、验证、测试与线上反馈是否隔离。
- 提示词、模型、温度、检索参数和工具权限的版本。
- 输入中的个人信息、商业秘密和敏感字段是否脱敏。

如果“大模型微调与私有化部署”使用 RAG，文档切片应尊重标题、章节、表格和条款结构；如果使用微调，先证明提示词、检索或流程优化不足；如果使用 Agent，先限制工具白名单和最大执行步数。

## 3. 评估：不要只看一个准确率

| 评估层 | 指标 | 说明 |
| --- | --- | --- |
| 检索 | Hit@K、MRR、版本正确率、权限过滤 | 正确内容是否被召回且可用 |
| 生成 | 引用支持率、事实一致性、完整性 | 回答是否有证据、是否遗漏关键条件 |
| 任务 | 完成率、转人工率、采纳率、重复澄清 | 用户问题是否真的解决 |
| 安全 | 越权、注入、敏感输出、违规动作 | 是否突破权限与安全边界 |
| 工程 | P50/P95 延迟、错误率、并发、成本 | 能否稳定且经济地服务 |
| 业务 | 节省时间、转化、质量、投诉 | 是否带来可解释价值 |

离线集要包含高频问题、长尾问题、边界问题、对抗问题和“应该拒答”的问题。线上评估要按用户、任务和风险等级分层，避免总体平均掩盖高危错误。

## 4. 案例一：华南某制造文档团队

### 案例 1：华南某制造文档团队的“大模型微调与私有化部署”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“大模型微调与私有化部署”映射到“大模型、Prompt 与评估工程”中的任务，而不是泛泛讨论概念。
- **触发事件**：团队尝试微调模型解释设备手册，但更新型号后效果迅速下降。
- **业务与数据范围**：手册版本、问答样本、型号、检索结果、微调数据和生产失败案例。数据侧重点采集输入结构、输出结构、成功标准和失败路径，并与数据仓库、特征平台、向量数据库中的时间、状态和责任人信息对齐。
- **需要回答的问题**：模型输出是分类、生成、抽取、改写还是决策建议。
- **关键障碍**：知识更新频率高，微调把旧事实写入参数，缺少检索与版本控制。同时要防止训练与线上样本泄漏把表面指标带偏。
- **处理过程**：先优化检索和结构化输出，只把稳定语言能力留给微调，新知识由版本化知识库提供。实施时把“模型更新保留灰度、对照、回滚和人工接管”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：复合案例用更新时效、引用正确率和回归成本比较微调与 RAG。验收至少同时看主指标、输入结构、输出结构、成功标准和失败路径和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“先证明任务需要大模型，再用版本化 Prompt、评测集、人工反馈、成本与安全门禁管理迭代，避免只凭少数演示判断效果。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

## 5. Python：检索与任务评估

### 检索、Agent 或模型任务实现

```python
from dataclasses import dataclass
from statistics import mean

@dataclass
class EvalCase:
    case_id: str
    expected: str
    risk: str

def score_case(case: EvalCase, output: str, cited: bool, refused: bool) -> dict:
    checks = {
        "contains_expected": case.expected in output,
        "citation_supported": cited,
        "safe_refusal": refused if case.risk == "high" else True,
    }
    return {"case_id": case.case_id, "score": mean(checks.values()), "checks": checks}

eval_cases = [
    EvalCase("e1", "标准答案", "low"),
    EvalCase("e2", "需要澄清", "medium"),
    EvalCase("e3", "应转人工", "high"),
]

# 主题："大模型微调与私有化部署"
# 覆盖常规、长尾、边界、对抗和拒答；模型、Prompt、知识库、工具和参数全部版本化。
# 线下平均分提升不足以发布，还要看任务完成、人工采纳、P95、单位成本和风险事件。
```

### 标题专属数据与失败分层 SQL

```sql
-- 大模型微调与私有化部署：留存同期群诊断（数据来源 × 业务场景）
WITH scoped AS (
  SELECT
    dataset_id AS entity_key,
    event_id,
    request_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_ai_request
  WHERE request_time >= DATE '2026-08-01'
    AND request_time <  DATE '2026-11-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '任务成功率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

## 6. 案例二：华北某金融科技公司

### 案例 2：华北某金融科技公司的“大模型微调与私有化部署”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“大模型微调与私有化部署”映射到“大模型、Prompt 与评估工程”中的数据，而不是泛泛讨论概念。
- **触发事件**：生成式摘要成本快速增加，但业务只使用其中少量结果。
- **业务与数据范围**：请求类型、输入长度、模型路由、缓存、人工采纳和单任务成本。数据侧重点采集数据卡、标注规则、去重、授权和漂移，并与数据仓库、特征平台、向量数据库中的时间、状态和责任人信息对齐。
- **需要回答的问题**：训练、评测和线上反馈是否分离且覆盖边界。
- **关键障碍**：所有请求都走同一大模型和长上下文，没有模板、缓存或小模型路由。同时要防止模型版本不可追溯把表面指标带偏。
- **处理过程**：按任务复杂度和风险分层路由，常见问题模板化，长文档先检索压缩，再记录采纳反馈。实施时把“评测集覆盖高频、长尾、边界、对抗、拒答和真实失败样本”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例运营在质量护栏内降低单位成本，并对模型降级做 A/B 验证。验收至少同时看主指标、数据卡、标注规则、去重、授权和漂移和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“先证明任务需要大模型，再用版本化 Prompt、评测集、人工反馈、成本与安全门禁管理迭代，避免只凭少数演示判断效果。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

## 7. 架构与工程链路

| 层次 | 本文建议 | 关键问题 | 验收证据 |
| --- | --- | --- | --- |
| 数据源 | 数据仓库、特征平台、向量数据库 | 权威源、更新频率、主键和权限 | 接口或表清单 |
| 接入 | 批、流或 CDC 按业务时延选择 | 重复、顺序、断点续传和回放 | 延迟与幂等测试 |
| 存储 | 按访问模式选择数据湖、数仓或 OLAP | 分区、格式、生命周期和成本 | 容量与查询评测 |
| 计算 | SQL、Spark、Flink 或 Python 服务 | 粒度、状态、资源和失败恢复 | 压测与执行计划 |
| 治理 | 元数据、质量、血缘、权限 | 责任、规则、影响分析和审计 | 规则结果与变更记录 |
| 服务 | 指标、API、看板或应用 | SLA、缓存、限流和版本 | 监控与验收样例 |

推荐把链路拆成六层：数据与知识准备、检索或特征、模型调用、工具执行、评估与审核、监控与反馈。每层都要有版本、日志和失败处理。Agent 工具调用应在服务端校验参数与权限，不能只依赖模型“自觉”。

## 8. 监控、成本与安全

- 监控请求量、延迟、错误码、超时、重试和缓存命中。
- 记录检索文档版本、模型版本、提示词版本和关键参数。
- 对失败分类：检索缺失、上下文过长、工具失败、权限拒绝、模型拒答、结果不合规。
- 设置单位任务成本、每租户预算和异常调用告警。
- 对提示注入、越权、敏感信息和危险动作做专门测试。
- 保留人工复核、转人工、回滚到旧模型和关闭工具的开关。

## 9. 第三个案例与上线验收

### 案例 3：华东某 SaaS 客服团队的“大模型微调与私有化部署”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“大模型微调与私有化部署”映射到“大模型、Prompt 与评估工程”中的运营，而不是泛泛讨论概念。
- **触发事件**：模型升级后离线准确率提升，但线上转人工率没有下降。
- **业务与数据范围**：真实会话、意图、回答、解决状态、人工标注、模型版本和成本。数据侧重点采集版本、trace、P95、单任务成本和回滚，并与数据仓库、特征平台、向量数据库中的时间、状态和责任人信息对齐。
- **需要回答的问题**：模型、Prompt、参数、成本和故障是否可追踪。
- **关键障碍**：评测集来自早期样本，标注只看流畅度，没有衡量问题是否真正解决。同时要防止评测与业务目标脱节把表面指标带偏。
- **处理过程**：按意图和用户阶段重建评测集，加入任务完成、澄清轮次、转人工、引用和安全门槛。实施时把“Prompt、模型、参数、知识、工具和代码全部版本化”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例评测发现复杂退款问题存在过度自信，并加入低置信度澄清与转人工。验收至少同时看主指标、版本、trace、P95、单任务成本和回滚和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“先证明任务需要大模型，再用版本化 Prompt、评测集、人工反馈、成本与安全门禁管理迭代，避免只凭少数演示判断效果。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

| 验收项 | 最低要求 | 证据 |
| --- | --- | --- |
| 任务定义 | 输入输出和失败路径明确 | 产品说明、评测集 |
| 数据授权 | 来源、用途和权限可追溯 | 数据卡、授权记录 |
| 离线评估 | 覆盖常规、边界和拒答 | 评测报告 |
| 线上灰度 | 有对照组和护栏指标 | 实验或灰度记录 |
| 安全 | 越权、注入和敏感输出已测试 | 红队与审计报告 |
| 成本 | 单位请求预算和上限明确 | 账单与调用日志 |
| 运营 | 有反馈、复盘和回滚 | 周报、事故演练 |

1. 先写清“大模型微调与私有化部署”的目标：先证明任务需要大模型，再用版本化 Prompt、评测集、人工反馈、成本与安全门禁管理迭代，避免只凭少数演示判断效果。
2. 专题检查：评测集覆盖高频、长尾、边界、对抗、拒答和真实失败样本
3. 专题检查：Prompt、模型、参数、知识、工具和代码全部版本化
4. 专题检查：离线指标必须与线上任务完成、人工采纳、成本和风险关联
5. 专题检查：模型更新保留灰度、对照、回滚和人工接管
6. 明确“大模型微调与私有化部署”服务的使用者、决策动作和不做范围，并把成功标准写成可观察指标。
7. 为数据集、样本、模型版本分别确认主键、时间和状态，画出从源系统到结果的链路。
8. 先做字段血缘和质量画像，检查训练与评测数据隔离、版本可追溯、敏感字段已脱敏。
9. 用同周期基线和至少两个维度拆解问题，避免只比较一个异常周。
10. 抽取正常、异常和边界样本回查原始业务单据，记录抽样方法与结论。
11. 选择一种代码实现并保留参数、版本、执行日志和结果快照，确保别人可以复跑。
12. 上线前定义告警阈值、回滚条件和责任人；上线后按周观察主指标与护栏指标。
13. 复盘时区分数据问题、业务变化、方案偏差和外部因素，并把改进项转成有时限的任务。

WITH ordered_events AS (
  SELECT
    dataset_id AS entity_key,
    event_id,
    stage_code,
    request_time AS event_time,
    LAG(stage_code) OVER (
      PARTITION BY dataset_id
      ORDER BY request_time, event_id
    ) AS previous_stage,

      PARTITION BY dataset_id
      ORDER BY request_time, event_id
    ) AS previous_time
  FROM fact_ai_request
  WHERE request_time >= :start_date
    AND request_time <  :end_date
    AND subject_key = 'subject'
)
SELECT
  entity_key,
  previous_stage,
  stage_code,
  event_time,
  event_time - previous_time AS elapsed,
  CASE
    WHEN event_time < previous_time THEN 'time_reversed'
    WHEN previous_stage = stage_code THEN 'duplicate_stage'
    WHEN previous_stage IS NULL THEN 'missing_prefix'
    ELSE 'candidate_delay'
  END AS exception_type
FROM ordered_events
WHERE event_time < previous_time
   OR previous_stage = stage_code

ORDER BY exception_type, elapsed DESC;
