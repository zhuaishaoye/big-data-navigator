# 向量数据库与RAG工程实践

> [!tip] 核心原则
> “向量数据库与RAG工程实践”既可能是业务概念，也可能是技术方案，还可能是岗位能力。判断学习是否有效，要看能否在训练数据准备、模型实验、RAG 检索、Agent 编排、离线评估和线上监控中做出一个可复现的小闭环。本文用多个案例展示从需求到数据结果，再回到业务行动和复盘的完整路径。

## 1. 从业务任务定义 AI 能力

围绕“向量数据库与RAG工程实践”，先把任务写成输入、输出、成功标准和失败边界。不要从“上一套模型”或“接一个聊天框”开始。

| 设计项 | 必须回答的问题 | 错误示例 | 更好做法 |
| --- | --- | --- | --- |
| 用户 | 谁使用，谁复核，谁承担后果 | 所有人都能用 | 按角色和权限明确使用边界 |
| 输入 | 文本、表格、图片还是工具调用 | 把所有数据都塞进上下文 | 只提供任务所需且获授权的数据 |
| 输出 | 分类、生成、检索、SQL 还是动作 | 只要求“回答准确” | 定义可检查的输出结构 |
| 成功 | 任务完成、采纳、质量、时延和成本 | 只看离线准确率 | 离线 + 线上 + 人工复核 |
| 失败 | 无答案、拒答、转人工还是回滚 | 失败也生成看似合理内容 | 明确置信阈值和降级路径 |

- 数据集和知识文档的来源、授权、时间、负责人和版本。
- 样本标注规则、标注人、抽检结果和争议处理。

## 3. 评估：不要只看一个准确率

| 评估层 | 指标 | 说明 |
| --- | --- | --- |
| 检索 | Hit@K、MRR、版本正确率、权限过滤 | 正确内容是否被召回且可用 |
| 生成 | 引用支持率、事实一致性、完整性 | 回答是否有证据、是否遗漏关键条件 |
| 任务 | 完成率、转人工率、采纳率、重复澄清 | 用户问题是否真的解决 |
| 安全 | 越权、注入、敏感输出、违规动作 | 是否突破权限与安全边界 |
| 工程 | P50/P95 延迟、错误率、并发、成本 | 能否稳定且经济地服务 |
| 业务 | 节省时间、转化、质量、投诉 | 是否带来可解释价值 |

离线集要包含高频问题、长尾问题、边界问题、对抗问题和“应该拒答”的问题。线上评估要按用户、任务和风险等级分层，避免总体平均掩盖高危错误。

## 4. 案例一：华北某金融知识平台

### 案例 1：华北某金融知识平台的“向量数据库与RAG工程实践”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“向量数据库与RAG工程实践”映射到“RAG、检索与知识库工程”中的召回，而不是泛泛讨论概念。
- **触发事件**：RAG 上线后响应延迟和成本持续上升，团队不断缩小 TopK 导致漏召回。
- **业务与数据范围**：查询类型、召回数量、重排耗时、模型调用、缓存、答案采纳和成本。数据侧重点采集Hit@K、MRR、召回文档版本和权限过滤，并与数据仓库、特征平台、向量数据库中的时间、状态和责任人信息对齐。
- **需要回答的问题**：关键词、向量和混合检索是否覆盖长尾与同义词。
- **关键障碍**：所有请求走同一长上下文和大模型，简单问题与复杂分析没有分层。同时要防止训练与线上样本泄漏把表面指标带偏。
- **处理过程**：按问题路由到 FAQ、检索或人工流程，增加缓存、批量重排和上下文预算，保留失败样本回流。实施时把“低置信度、无证据、权限拒绝和工具失败都有明确降级路径”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例工程在质量、P95 和单位成本之间建立可解释取舍。验收至少同时看主指标、Hit@K、MRR、召回文档版本和权限过滤和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把文档解析、切片、索引、召回、重排、权限、引用和评估连成可回归链路，分别衡量检索是否命中、答案是否有据、任务是否完成。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

## 5. Python：检索与任务评估

### 检索、Agent 或模型任务实现

```python
from dataclasses import dataclass

@dataclass
class SearchHit:
    chunk_id: str
    document_id: str
    version: str
    lexical_score: float
    vector_score: float
    acl_group: str

def hybrid_search(hits: list[SearchHit], user_groups: set[str], k: int = 5):
    allowed = [hit for hit in hits if hit.acl_group in user_groups | {"public"}]
    reranked = sorted(
        allowed,
        key=lambda hit: 0.45 * hit.lexical_score + 0.55 * hit.vector_score,
        reverse=True,
    )
    deduped, seen = [], set()
    for hit in reranked:
        if hit.document_id not in seen:
            seen.add(hit.document_id)
            deduped.append(hit)
    return deduped[:k]

# 主题："向量数据库与RAG工程实践"
# 分别评估解析、Hit@K、引用支持、回答完整、权限过滤、P95 和单次成本。
# 失败样本必须能回到切片、文档版本、召回片段和最终引用。
```

### 标题专属数据与失败分层 SQL

```sql
-- 向量数据库与RAG工程实践：留存同期群诊断（业务场景 × 租户）
WITH scoped AS (
  SELECT
    dataset_id AS entity_key,
    event_id,
    request_time AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_ai_request
  WHERE request_time >= DATE '2026-04-01'
    AND request_time <  DATE '2026-07-01'
    AND subject_key = 'rag'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '检索命中率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

示例代码只展示可测试结构。真实系统还需要模型服务、向量库、权限、日志、缓存、限流、敏感检查和人工反馈，不应把安全完全交给提示词。

## 6. 案例二：华东某企业制度知识库

### 案例 2：华东某企业制度知识库的“向量数据库与RAG工程实践”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“向量数据库与RAG工程实践”映射到“RAG、检索与知识库工程”中的运营，而不是泛泛讨论概念。
- **触发事件**：员工问报销和休假规则时，助手引用了已废止版本，回答语气还很确定。
- **业务与数据范围**：制度文档、版本、生效日期、章节、权限、切片、召回片段和人工反馈。数据侧重点采集索引版本、延迟、成本、失败分类和人工反馈，并与数据仓库、特征平台、向量数据库中的时间、状态和责任人信息对齐。
- **需要回答的问题**：文档更新、权限变化和反馈是否进入回归集。
- **关键障碍**：文档只按固定长度切分，旧版本仍在索引，引用只显示文档名不显示版本和条款。同时要防止模型版本不可追溯把表面指标带偏。
- **处理过程**：按标题与条款结构切片，过滤失效版本和用户权限，答案强制给出版本、条款和更新日期。实施时把“至少分别评估解析质量、检索命中、引用支持、任务完成和安全”写成上线检查项，并为每一项保留日志、样本和负责人。

- **可迁移结论**：遇到类似标题时，先按“把文档解析、切片、索引、召回、重排、权限、引用和评估连成可回归链路，分别衡量检索是否命中、答案是否有据、任务是否完成。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

## 7. 架构与工程链路

| 层次 | 本文建议 | 关键问题 | 验收证据 |
| --- | --- | --- | --- |
| 数据源 | 数据仓库、特征平台、向量数据库 | 权威源、更新频率、主键和权限 | 接口或表清单 |
| 接入 | 批、流或 CDC 按业务时延选择 | 重复、顺序、断点续传和回放 | 延迟与幂等测试 |
| 存储 | 按访问模式选择数据湖、数仓或 OLAP | 分区、格式、生命周期和成本 | 容量与查询评测 |
| 计算 | SQL、Spark、Flink 或 Python 服务 | 粒度、状态、资源和失败恢复 | 压测与执行计划 |
| 治理 | 元数据、质量、血缘、权限 | 责任、规则、影响分析和审计 | 规则结果与变更记录 |
| 服务 | 指标、API、看板或应用 | SLA、缓存、限流和版本 | 监控与验收样例 |

推荐把链路拆成六层：数据与知识准备、检索或特征、模型调用、工具执行、评估与审核、监控与反馈。每层都要有版本、日志和失败处理。Agent 工具调用应在服务端校验参数与权限，不能只依赖模型“自觉”。

## 8. 监控、成本与安全

- 监控请求量、延迟、错误码、超时、重试和缓存命中。
- 记录检索文档版本、模型版本、提示词版本和关键参数。
- 对失败分类：检索缺失、上下文过长、工具失败、权限拒绝、模型拒答、结果不合规。
- 设置单位任务成本、每租户预算和异常调用告警。
- 对提示注入、越权、敏感信息和危险动作做专门测试。
- 保留人工复核、转人工、回滚到旧模型和关闭工具的开关。

### 扩展代码一：从向量数据库与RAG工程实践回到可核对明细

```sql
-- 向量数据库与RAG工程实践：恢复后缺失、重复与跨期检查
WITH expected_keys AS (
  SELECT DISTINCT dataset_id AS entity_key, event_id
  FROM fact_ai_request
  WHERE request_time >= :restore_start
    AND request_time <  :restore_end
    AND subject_key = 'rag'
),
restored_keys AS (
  SELECT dataset_id AS entity_key, event_id, load_version, loaded_at
  FROM fact_ai_request
  WHERE request_time >= :restore_start
    AND request_time <  :restore_end
    AND subject_key = 'rag'
    AND load_version = :restore_version
),
coverage AS (
  SELECT
    (SELECT COUNT(*) FROM expected_keys) AS expected_cnt,
    (SELECT COUNT(*) FROM restored_keys) AS restored_cnt,
    (SELECT COUNT(*) FROM (
      SELECT entity_key, event_id
      FROM restored_keys
      GROUP BY entity_key, event_id
      HAVING COUNT(*) > 1
    ) duplicate_keys) AS duplicated_cnt,
    (SELECT COUNT(*) FROM (
      SELECT e.entity_key, e.event_id
      FROM expected_keys e
      LEFT JOIN restored_keys r USING (entity_key, event_id)
      WHERE r.entity_key IS NULL
    ) missing_keys) AS missing_cnt
)
SELECT *,
  CASE
    WHEN expected_cnt <> restored_cnt OR duplicated_cnt > 0 OR missing_cnt > 0
      THEN 'reject_release'
    ELSE 'accept_restore'
  END AS gate_result
FROM coverage;
```

### 扩展代码二：把向量数据库与RAG工程实践的验收证据写成门禁

```python
from datetime import date
from hashlib import sha256

import pandas as pd

SUBJECT = "向量数据库与RAG工程实践"
BLOCKING_RULES = ["训练与评测数据隔离","版本可追溯","敏感字段已脱敏"]


def validate_release(frame: pd.DataFrame, start: date, end: date) -> dict:
    scoped = frame.loc[
        frame["event_date"].between(pd.Timestamp(start), pd.Timestamp(end))
        & (frame["subject_key"] == "rag")
    ].copy()
    checks = {
        "has_rows": len(scoped) > 0,
        "event_id_unique": not scoped["event_id"].duplicated().any(),
        "entity_key_complete": scoped["entity_key"].notna().all(),
        "event_time_present": scoped["event_time"].notna().all(),
        "scope_matches": scoped["subject_key"].nunique() == 1,
    }
    payload = f"{SUBJECT}|{start}|{end}|{len(scoped)}|{sorted(checks.items())}"
    return {
        "subject": SUBJECT,
        "rows": len(scoped),
        "checks": checks,
        "blocking_rules": BLOCKING_RULES,
        "release_allowed": all(checks.values()),
        "evidence_hash": sha256(payload.encode("utf-8")).hexdigest(),
    }
```
