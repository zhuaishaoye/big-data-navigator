# 主数据MDM建设项目

> [!warning] 核心判断
> “主数据MDM建设项目”在会议里常常只有一句话，落到数据团队却会展开成口径、主键、时间、状态、权限和交付责任。下面用一个从问题到上线的顺序展开，并穿插三个脱敏的复合案例，帮助你把标题里的知识迁移到真实项目。

## 1. 先判断应治理什么风险

“主数据MDM建设项目”通常不是买一个平台就能解决的问题。它至少涉及制度、标准、责任、流程、技术和审计六层。开始前先把风险写成可观察事实：

| 风险问题 | 观察信号 | 可能影响 | 首先核查 |
| --- | --- | --- | --- |
| 定义不一致 | 同名指标多个 SQL、多个业务解释 | 决策冲突、返工 | 指标字典与负责人 |
| 数据不完整 | 分区缺失、关键字段空值 | 报表失真、流程中断 | 采集与任务日志 |
| 责任不清 | 问题工单长期无人认领 | 修复延迟、同类复发 | 资产责任矩阵 |
| 访问过宽 | 长期权限、共享账号、无审计 | 泄漏与合规风险 | 权限清单与访问日志 |
| 变更不可见 | 表结构或逻辑变更无通知 | 下游批量故障 | 血缘与发布记录 |

1. **范围持续扩张**：需要在标准、系统或组织流程中设置对应控制。
2. **验收标准模糊**：需要在标准、系统或组织流程中设置对应控制。
3. **上线后无人跟踪业务效果**：需要在标准、系统或组织流程中设置对应控制。
4. **关键依赖延期**：需要在标准、系统或组织流程中设置对应控制。
5. **数据迁移不可回滚**：需要在标准、系统或组织流程中设置对应控制。

## 2. 用 DAMA 思路拆成可执行组件

| 组件 | 本文关注对象 | 最小可执行机制 |
| --- | --- | --- |
| 数据标准 | 字段、代码、指标和业务术语；结合“主数据MDM建设项目”重点检查范围与验收标准明确 | 标准登记、评审、版本与废弃 |
| 元数据 | 表、字段、任务、接口、负责人；结合“主数据MDM建设项目”重点检查上下游依赖确认 | 自动采集、业务补充、变更通知 |
| 数据质量 | 完整性、唯一性、及时性、准确性；结合“主数据MDM建设项目”重点检查回滚方案可执行 | 规则、阈值、工单与复盘 |
| 主数据 | 客户、商品、设备、机构等共享对象；结合“主数据MDM建设项目”重点检查结果可核对 | 源权威、去重、合并、历史关系 |
| 数据安全 | 分类分级、权限、脱敏和审计；结合“主数据MDM建设项目”重点检查上线后有运营指标 | 审批、最小权限、访问复核 |
| 数据血缘 | 表、字段、任务和指标关系；结合“主数据MDM建设项目”重点检查范围与验收标准明确 | 影响分析、问题追踪、变更评审 |

治理不是把所有数据都按同一优先级管理。建议依据使用范围、监管要求、决策影响和故障历史划分关键资产，再决定投入。关键资产应有唯一负责人、明确消费者、质量目标、访问策略和变更通知。

## 3. 资产、标准与责任矩阵

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 需求 | `requirement_id` | 立项 |
| 过程对象 | 里程碑 | `milestone_id` | 调研 |
| 过程对象 | 数据表 | `table_id` | 方案 |
| 结果对象 | 接口 | `interface_id` | 开发 |
| 结果对象 | 验收项 | `acceptance_id` | 联调 |
| 专题分析 | 主数据MDM建设项目 | `topic_key = 'mdm'` | 用于把通用事件收窄到本主题 |

一个可执行的数据标准至少包括：

- **业务定义**：业务人员如何理解和适用。
- **技术定义**：字段类型、长度、格式、枚举和空值语义。
- **计算口径**：时间、粒度、分子分母和排除项。
- **权威来源**：哪个系统是事实源，冲突时以谁为准。
- **生命周期**：创建、变更、废弃和归档规则。
- **责任人**：业务负责人、数据负责人、技术负责人和审批人。

资产责任可以使用 RACI：业务负责人对定义负责，数据负责人对实现与质量负责，平台团队对工具和权限负责，安全合规对访问与审计负责，消费者对使用边界负责。只有“责任人”一个字段，没有决策权和时限，问题仍会回到治理团队自己处理。

## 4. 案例一：华南某制造集团

### 案例 1：华南某制造集团的“主数据MDM建设项目”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“主数据MDM建设项目”映射到“数据标准、指标口径与主数据”中的定义，而不是泛泛讨论概念。
- **触发事件**：同一物料在采购、生产、仓储和财务使用不同编码，集团分析经常断链。
- **业务与数据范围**：供应商料号、内部料号、制造商料号、单位、批次和有效期。数据侧重点采集术语、适用范围、反例和负责人，并与项目管理、需求管理、代码仓库中的时间、状态和责任人信息对齐。
- **需要回答的问题**：业务到底如何理解对象、事件和指标。
- **关键障碍**：各单位独立维护编码，单位换算和停用状态没有统一标准。同时要防止范围持续扩张把表面指标带偏。
- **处理过程**：建立物料主数据权威源、映射与清洗规则，保留历史编码和有效期，关键变更需跨域评审。实施时把“标准变更执行影响分析、评审、通知、验证和回滚”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：复合案例让采购、生产和财务能够围绕同一主数据对账。验收至少同时看主指标、术语、适用范围、反例和负责人和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把业务定义、编码、主键、指标公式、权威源和责任人变成可执行标准，并通过版本、评审和对账控制变更。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

治理项目应先做小范围闭环，不要一开始铺满全公司。选择一个高影响业务域，完成从资产盘点、标准确认、质量规则、问题整改到复盘的完整链路，再复制机制。

## 5. 规则与代码：让控制可执行

### 发布前规则门禁

```python
# 主数据MDM建设项目：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "主数据MDM建设项目"
TOPIC_KEY = "mdm"
RULE_ID = "rule_project_1wh2r4j"
GUIDE_CHECKS = [
    "标准必须包含业务定义、技术定义、权威源、负责人、版本和生效时间",
    "主数据合并保留来源、规则、置信度和人工复核记录",
    "指标公式与粒度进入语义层，不允许散落在个人 SQL 中",
    "标准变更执行影响分析、评审、通知、验证和回滚"
]
RULES = {
    "required_columns": ["event_id", "requirement_id", "event_date", "status"],
    "duplicate_key": "event_id",
    "entity_key": "requirement_id",
    "time_field": "event_date",
    "max_duplicate_rate": 0.0008,
    "max_null_rate": 0.004,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：标准必须包含业务定义、技术定义、权威源、负责人、版本和生效时间；主数据合并保留来源、规则、置信度和人工复核记录；指标公式与粒度进入语义层，不允许散落在个人 SQL 中；标准变更执行影响分析、评审、通知、验证和回滚
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

### 治理对象与风险分层 SQL

```sql
-- 主数据MDM建设项目：留存同期群诊断（负责人 × 风险等级）
WITH scoped AS (
  SELECT
    requirement_id AS entity_key,
    event_id,
    event_date AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_project_delivery
  WHERE event_date >= DATE '2026-04-01'
    AND event_date <  DATE '2026-07-01'
    AND subject_key = 'mdm'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '投资回收周期' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

规则设计要同时考虑三件事：能否自动执行、误报成本是否可接受、失败后谁来处理。只写“不能为空”不够，必须明确哪类对象允许为空、谁能在何种情况下豁免、豁免多久、是否需要审批和复核。

建议把规则分成四级：

1. **阻断**：涉及监管、资金、身份或核心发布，失败即停止。
2. **严重告警**：影响大但可先隔离，要求在约定时间内响应。
3. **观察告警**：可能是正常业务变化，先记录趋势。
4. **探索检查**：尚未形成稳定阈值，仅用于发现异常模式。

## 6. 案例二：华北某互联网平台

### 案例 2：华北某互联网平台的“主数据MDM建设项目”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“主数据MDM建设项目”映射到“数据标准、指标口径与主数据”中的变更，而不是泛泛讨论概念。
- **触发事件**：不同团队对活跃用户和留存率有十几个版本，实验结论相互冲突。
- **业务与数据范围**：指标名称、公式、粒度、时间窗、排除条件、版本和下游使用清单。数据侧重点采集版本记录、影响分析、回滚和下游确认，并与项目管理、需求管理、代码仓库中的时间、状态和责任人信息对齐。
- **需要回答的问题**：谁提出、谁评审、谁批准、何时生效。
- **关键障碍**：指标只存在于 SQL 和文档，变更没有负责人和下游通知。同时要防止验收标准模糊把表面指标带偏。
- **处理过程**：建立原子指标与派生指标分层，公式版本化，关键口径进入语义层并通过单测。实施时把“标准必须包含业务定义、技术定义、权威源、负责人、版本和生效时间”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例治理用口径争议数、重复开发量、变更影响时间和使用覆盖率衡量。验收至少同时看主指标、版本记录、影响分析、回滚和下游确认和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把业务定义、编码、主键、指标公式、权威源和责任人变成可执行标准，并通过版本、评审和对账控制变更。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

治理指标不要只统计“生成了多少文档、接入了多少资产”。更值得观察的是规则覆盖的关键资产、问题发现前移比例、问题复发率、变更影响分析耗时和业务是否愿意使用。

## 7. 权限、安全与审计

围绕“主数据MDM建设项目”，权限治理至少应回答：

- 谁能申请、谁审批、审批依据是什么？
- 权限是否按角色、数据级别和用途最小化？
- 临时权限何时收回，离职和转岗是否自动处理？
- 查询、下载和导出是否留痕，异常访问如何发现？
- 脱敏、加密、水印和审计日志是否与数据类型匹配？

敏感字段不应通过“复制一份测试数据”绕过问题。更合适的做法是分级脱敏、合成数据或受控计算环境。所有示例和代码都不应包含真实身份、账号、密钥、客户名单或未公开经营数据。

## 8. 第三个案例：华东某零售集团

### 案例 3：华东某零售集团的“主数据MDM建设项目”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“主数据MDM建设项目”映射到“数据标准、指标口径与主数据”中的主键，而不是泛泛讨论概念。
- **触发事件**：会员数量与财务、门店、线上渠道各自口径不同，董事会无法判断真实用户规模。
- **业务与数据范围**：手机号、会员卡、设备、登录账号、匿名行为、合并关系和历史等级。数据侧重点采集重复率、误合并率、有效期和跨系统映射，并与项目管理、需求管理、代码仓库中的时间、状态和责任人信息对齐。
- **需要回答的问题**：唯一标识、合并、拆分和历史关系如何处理。
- **关键障碍**：手机号空值与变更造成误合并，匿名与登录身份未建立可信关联。同时要防止上线后无人跟踪业务效果把表面指标带偏。
- **处理过程**：定义会员唯一标识、候选匹配和人工复核规则，保留合并前后关系，指标区分注册、活跃和可触达会员。实施时把“主数据合并保留来源、规则、置信度和人工复核记录”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例项目用重复率、误合并率、覆盖率和跨期一致性评估 OneID。验收至少同时看主指标、重复率、误合并率、有效期和跨系统映射和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把业务定义、编码、主键、指标公式、权威源和责任人变成可执行标准，并通过版本、评审和对账控制变更。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

- **关键异常或争议：** 一次错误发布已经产生结果，团队只能凭负责人记忆寻找影响范围，补数后仍无法确认是否重复或遗漏。初看时，项目管理与需求管理的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。

- **处理步骤：** 第一步先冻结“主数据MDM建设项目”的当前定义并记录版本；第二步用接口明细核对项目管理到需求管理的关联；第三步按项目阶段与负责人做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察计划达成率和护栏指标上线成功率。
- **行动与护栏：** 保存现场并停止下游扩散，按影响边界回滚或隔离结果，使用幂等任务从最小必要范围重新计算。专题检查项“标准变更执行影响分析、评审、通知、验证和回滚”被写成发布门禁，恢复任务没有对账、没有版本记录或无法重复执行时，不宣布故障结束。
- **失败路径：** 直接覆盖目标表，或者把所有分区全部重跑以求省事。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“主数据MDM建设项目”时，先验证源系统字段、映射表、历史版本和样例，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由运维在明确时限内，根据计划达成率、上线成功率和范围与验收标准明确决定继续、回退、补查还是转人工。 若范围持续扩张或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从主数据MDM建设项目回到可核对明细

```sql
-- 主数据MDM建设项目：状态链与时间间隔核查
WITH ordered_events AS (
  SELECT
    requirement_id AS entity_key,
    event_id,
    stage_code,
    event_date AS event_time,
    LAG(stage_code) OVER (
      PARTITION BY requirement_id
      ORDER BY event_date, event_id
    ) AS previous_stage,
    LAG(event_date) OVER (
      PARTITION BY requirement_id
      ORDER BY event_date, event_id
    ) AS previous_time
  FROM fact_project_delivery
  WHERE event_date >= :start_date
    AND event_date <  :end_date
    AND subject_key = 'mdm'
)
SELECT
  entity_key,
  previous_stage,
  stage_code,
  event_time,
  event_time - previous_time AS elapsed,
  CASE
    WHEN event_time < previous_time THEN 'time_reversed'
    WHEN previous_stage = stage_code THEN 'duplicate_stage'
    WHEN previous_stage IS NULL THEN 'missing_prefix'
    ELSE 'candidate_delay'
  END AS exception_type
FROM ordered_events
WHERE event_time < previous_time
   OR previous_stage = stage_code
   OR event_time - previous_time > INTERVAL '1 hour'
ORDER BY exception_type, elapsed DESC;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把主数据MDM建设项目的验收证据写成门禁

```python
import pandas as pd

KEY = ["entity_key", "event_id"]
AMOUNT_COLUMNS = ["metric_value", "adjustment_value"]


def reconcile(source: pd.DataFrame, result: pd.DataFrame) -> pd.DataFrame:
    def aggregate(frame: pd.DataFrame, side: str) -> pd.DataFrame:
        grouped = (
            frame.groupby("entity_key", dropna=False)
            .agg(
                event_cnt=("event_id", "nunique"),
                metric_sum=("metric_value", "sum"),
                adjustment_sum=("adjustment_value", "sum"),
            )
            .reset_index()
        )
        return grouped.rename(columns={
            "event_cnt": f"{side}_event_cnt",
            "metric_sum": f"{side}_metric_sum",
            "adjustment_sum": f"{side}_adjustment_sum",
        })

    compared = aggregate(source, "source").merge(
        aggregate(result, "result"),
        on="entity_key",
        how="outer",
    )
    compared["metric_diff"] = (
        compared["result_metric_sum"].fillna(0)
        - compared["source_metric_sum"].fillna(0)
    )
    compared["event_diff"] = (
        compared["result_event_cnt"].fillna(0)
        - compared["source_event_cnt"].fillna(0)
    )
    compared["exception"] = compared.apply(
        lambda row: "missing_result" if pd.isna(row["result_metric_sum"])
        else "unexpected_result" if pd.isna(row["source_metric_sum"])
        else "count_diff" if row["event_diff"] != 0
        else "amount_diff",
        axis=1,
    )
    return compared.loc[
        (compared["metric_diff"].abs() > 0) | (compared["event_diff"] != 0)
    ].sort_values("metric_diff", key=lambda values: values.abs(), ascending=False)
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
