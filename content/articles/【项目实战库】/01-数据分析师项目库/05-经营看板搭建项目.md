# 经营看板搭建项目

> [!tip] 分析目标
> 讨论“经营看板搭建项目”时，最容易犯的错误是直接从工具或报表开始。更有用的顺序是：先看业务链条，再找可观察指标，随后确认数据粒度，最后才选择 SQL、模型或平台组件。本文按这个顺序给出可执行方案和常见的失败样本。

## 1. 把主题翻译成可验证的问题

“经营看板搭建项目”不能直接等同于“做一张趋势图”。一个可执行的分析问题至少包含对象、时间、比较基准和行动：

> 在【观察周期】内，对【有效对象】按【项目阶段、业务域、负责人】比较【缺陷关闭率】与【上线成功率】，判断变化来自结构、行为还是数据口径，并验证【策略动作】是否带来可解释的增量。

在项目实战库场景中，用户行为、交易结果和策略曝光经常来自不同系统。先画数据流：

项目管理 → 需求管理 → 代码仓库 → 调度平台 → 监控平台 → 数据质量平台

图中至少要有三个标记：业务事件发生时间、数据可见时间、策略或行动时间。只有三者分开，后续才能判断问题发生在业务、链路还是观察窗口。

## 2. 指标定义与分母检查

| 专题观测面 | 需要回答的问题 | 关键证据 | 判定与动作 |
| --- | --- | --- | --- |
| 问题与范围（本标题优先） | 项目改变什么行为，边界和不做什么是什么 | 决策记录、需求说明和现状基线 | 范围不清时先做诊断 |
| 方案与证据 | 为什么选择当前方案，关键假设如何验证 | 替代方案、原型、数据和评审记录 | 重大假设必须有试验 |
| 采用与收益 | 谁在使用，是否改变决策，副作用如何 | 使用日志、主指标、护栏和复盘 | 上线数量不等于项目成功 |
| 上线 | 权限、质量、监控、培训和回滚是否就绪 | 上线清单、演练、验收和责任人 | 关键风险未关闭不发布 |

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 计划达成率 | `COUNT(DISTINCT on_time_milestone_id) / COUNT(DISTINCT milestone_id)`（视图字段 `plan_attainment`） | 项目阶段、业务域、负责人 | 不混用测试、撤销和跨期状态；与“经营看板搭建项目”相关时还要补充主题筛选 |
| 缺陷关闭率 | `COUNT(DISTINCT closed_defect_id) / COUNT(DISTINCT raised_defect_id)`（视图字段 `defect_closure`） | 业务域、负责人、优先级 | 不混用测试、撤销和跨期状态；与“经营看板搭建项目”相关时还要补充主题筛选 |
| 上线成功率 | `COUNT(DISTINCT successful_release_id) / COUNT(DISTINCT release_id)`（视图字段 `release_success`） | 负责人、优先级、风险等级 | 不混用测试、撤销和跨期状态；与“经营看板搭建项目”相关时还要补充主题筛选 |
| 验收通过率 | `COUNT(DISTINCT passed_acceptance_id) / COUNT(DISTINCT acceptance_id)`（视图字段 `acceptance_rate`） | 优先级、风险等级 | 不混用测试、撤销和跨期状态；与“经营看板搭建项目”相关时还要补充主题筛选 |

针对“经营看板搭建项目”，建议分别定义诊断指标、结果指标和护栏指标：

- **诊断指标**用于定位流程，例如曝光、有效访问、符合条件对象数和异常节点。
- **结果指标**用于判断是否改善，例如转化、留存、客单、毛利或处理时长。
- **护栏指标**用于防止局部优化伤害整体，例如退款、投诉、成本、公平性和长期留存。

每次计算都问四个问题：分母是谁、对象何时进入分母、例外状态怎么处理、窗口是否足够覆盖行为完成。尤其是范围持续扩张；验收标准模糊；上线后无人跟踪业务效果，任何一项没有解释清楚，指标都可能“看起来合理但无法决策”。

## 3. 方法选择：描述、诊断、预测还是因果

| 目标 | 适合的方法 | 需要的证据 | 不要混淆 |
| --- | --- | --- | --- |
| 描述现状 | 趋势、结构、同期群 | 完整口径、稳定时间窗 | 描述不等于原因 |
| 定位异常 | 分层、贡献度、漏斗、异常检测 | 原始事件、基线和质量检查 | 排名靠前不等于因果 |
| 预测未来 | 时间序列、回归、机器学习 | 时间切分验证、误差成本 | 离线准确率不等于业务收益 |
| 评估策略 | A/B、灰度、准实验 | 对照组、样本量、护栏指标 | 上线前后对比容易混入季节和选择偏差 |

如果问题只是“发生了什么”，先别急着建模；如果问题涉及“采取某策略会怎样”，就必须讨论反事实和识别条件。围绕“经营看板搭建项目”，应把观察分析、预测和因果评估的产出分开标注。

## 4. 案例一：华北某制造数据治理项目

### 案例 1：华北某制造数据治理项目的“经营看板搭建项目”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“经营看板搭建项目”映射到“数据项目交付、验收与运营”中的问题与范围，而不是泛泛讨论概念。
- **触发事件**：试点质量问题改善明显，但推广到更多工厂后效果迅速衰减。
- **业务与数据范围**：试点机制、责任人、规则、工单、培训和复制成本。数据侧重点采集决策记录、需求说明和现状基线，并与项目管理、需求管理、代码仓库中的时间、状态和责任人信息对齐。
- **需要回答的问题**：项目改变什么行为，边界和不做什么是什么。
- **关键障碍**：项目依赖少数专家手工推动，没有形成角色、模板和自动化。同时要防止范围持续扩张把表面指标带偏。
- **处理过程**：把试点拆成可复制资产，建立本地负责人、规则模板、培训认证和月度复核。实施时把“项目目标包含业务行为、主指标、护栏指标和观察周期”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例推广以复制周期、规则复用、问题复发和本地自治能力评估。验收至少同时看主指标、决策记录、需求说明和现状基线和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“从问题、范围、基线、方案、数据、上线、采用和复盘管理项目，确保交付的是可验证的业务能力而不是一次性材料。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

落地时建议先把一个总指标拆成可行动的树：

```text
经营看板搭建项目｜缺陷关闭率结果偏离
├── 先验真伪：范围与验收标准明确是否有批次级证据
├── 再看规模：需求数量与上线成功率是否同向变化
├── 结构定位：项目阶段 → 业务域 → 负责人
├── 链路时点：项目管理 → 需求管理 → 代码仓库
└── 行动出口：项目目标包含业务行为、主指标、护栏指标和观察周期
```

如果某一分支变化最大，再进入下一层，而不是一开始就按十几个维度切碎。每个分层结果都应同时报告样本量，避免小样本的极端比例抢走注意力。

## 5. SQL：计算趋势、结构和贡献度

### 趋势、结构与贡献度诊断

```sql
-- 经营看板搭建项目：结构贡献诊断（业务域 × 优先级）
WITH scoped AS (
  SELECT
    requirement_id AS entity_key,
    event_id,
    event_date AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_project_delivery
  WHERE event_date >= DATE '2026-01-01'
    AND event_date <  DATE '2026-04-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '验收通过率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

示例 SQL 只表达计算逻辑。实际实施应加入分区条件、业务状态过滤、时区和主题范围，并在结果中保留口径版本。

## 6. 案例二：华东某零售数据项目组

### 案例 2：华东某零售数据项目组的“经营看板搭建项目”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“经营看板搭建项目”映射到“数据项目交付、验收与运营”中的方案与证据，而不是泛泛讨论概念。
- **触发事件**：项目按期上线看板，但业务仍用 Excel 决策，数据团队无法证明价值。
- **业务与数据范围**：需求访谈、用户任务、使用日志、指标口径、决策记录和反馈。数据侧重点采集替代方案、原型、数据和评审记录，并与项目管理、需求管理、代码仓库中的时间、状态和责任人信息对齐。
- **需要回答的问题**：为什么选择当前方案，关键假设如何验证。
- **关键障碍**：项目只定义功能范围，没有定义采用动作和决策改变。同时要防止验收标准模糊把表面指标带偏。
- **处理过程**：把关键决策、使用场景和验收样例写入范围，按业务角色灰度并跟踪真实查询与行动。实施时把“范围明确数据、系统、团队、权限和不在本期处理的事项”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例验收以采用率、决策闭环、口径争议和人工步骤变化评估。验收至少同时看主指标、替代方案、原型、数据和评审记录和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“从问题、范围、基线、方案、数据、上线、采用和复盘管理项目，确保交付的是可验证的业务能力而不是一次性材料。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

当业务方要求“解释为什么下降”时，可以按下面顺序回答：

1. 先确认下降是否真实存在，排查采集、任务、维表和状态映射。
2. 把变化拆成对象数量、行为强度和结构占比。
3. 找到贡献最大的分组，但保留其他分组的抵消效应。
4. 抽取正负样本回查业务事件和操作日志。
5. 把尚不能证明的解释标为假设，并设计下一轮验证。

```python
from datetime import date

TOPIC = "经营看板搭建项目"
PROJECT_ID = "g_project_delivery_8h7zq8"

@dataclass
class Milestone:
    name: str
    owner: str
    due: date
    evidence: str
    gate_passed: bool = False

milestones = [
    Milestone("问题与范围", "业务负责人", date(2026, 11, 8), "决策记录与基线"),
    Milestone("数据与权限", "数据负责人", date(2026, 11, 15), "接口、契约和授权矩阵"),
    Milestone("质量与灰度", "开发负责人", date(2026, 11, 22), "对账、回滚与演练"),
    Milestone("采用与复盘", "产品负责人", date(2026, 12, 6), "使用日志、主指标与护栏"),
]

required_checks = [
    "项目目标包含业务行为、主指标、护栏指标和观察周期",
    "范围明确数据、系统、团队、权限和不在本期处理的事项",
    "上线前完成质量、权限、监控、培训和回滚验收"
]

def release_gate(items: list[Milestone], checks: list[str]) -> dict:
    blockers = [item.name for item in items if not item.gate_passed]
    return {
        "project_id": PROJECT_ID,
        "topic": TOPIC,
        "blocked_by": blockers,
        "checks": checks,
        "release_allowed": not blockers and len(checks) >= 3,
    }

print(release_gate(milestones, required_checks))

# 项目管理以可验收能力为单位，不以代码提交、文档页数或看板数量代替结果。
# 变更必须同步评估范围、口径、权限、依赖、上线窗口和回滚成本。
```

## 8. 异常、偏差与常见误区

- **辛普森悖论**：总体改善但每个分组都变差，可能由对象结构变化造成。
- **幸存者偏差**：只分析完成流程的对象，忽略中途流失和中止。
- **分母漂移**：渠道口径、登录状态、版本或活动范围变化，改变可比性。
- **回传延迟**：当天数据未回补，导致近期效果被系统性低估。
- **多重比较**：反复寻找显著分组，实际只是随机波动。
- **行动偏差**：只报告支持既定方案的结果，忽略反例和护栏指标。

围绕“经营看板搭建项目”，应预先写出至少三条反例检查。比如结论是否能回到明细、指标是否在同一对象和同一时间窗内计算，以及 数据质量异常是否与业务变化分开。

## 9. 第三个案例：华南某银行数据中台项目

### 案例 3：华南某银行数据中台项目的“经营看板搭建项目”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“经营看板搭建项目”映射到“数据项目交付、验收与运营”中的采用与收益，而不是泛泛讨论概念。
- **触发事件**：平台组件全部交付，但跨部门数据接入进度严重滞后。
- **业务与数据范围**：资产范围、责任矩阵、接口、权限、迁移批次和依赖。数据侧重点采集使用日志、主指标、护栏和复盘，并与项目管理、需求管理、代码仓库中的时间、状态和责任人信息对齐。
- **需要回答的问题**：谁在使用，是否改变决策，副作用如何。
- **关键障碍**：技术任务完成被当作项目进度，业务口径、数据授权和源系统改造没有纳入计划。同时要防止上线后无人跟踪业务效果把表面指标带偏。

- **行动与护栏：** 从阻断、严重、观察三级建立规则，先修数据和逻辑，再决定是否允许有期限的业务例外。专题检查项“项目复盘同时衡量采用、收益、副作用和可复制性”被写成发布门禁，影响资金、安全、监管或核心经营判断的关键规则失败时停止发布。
- **失败路径：** 一直调低阈值让报表通过，却没有处理规则为何持续失败。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“经营看板搭建项目”时，先验证上线清单、演练、验收和责任人，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由数据开发在明确时限内，根据投资回收周期、缺陷关闭率和上线后有运营指标决定继续、回退、补查还是转人工。 若数据迁移不可回滚或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从经营看板搭建项目回到可核对明细

```sql
SELECT
  'subject' AS subject_key,
  stat_date,
  COUNT(*) AS row_cnt,
  COUNT(DISTINCT event_id) AS distinct_event_cnt,
  SUM(CASE WHEN event_id IS NULL THEN 1 ELSE 0 END) AS null_event_cnt,
  SUM(CASE WHEN event_date < business_time THEN 1 ELSE 0 END) AS time_reverse_cnt,
  SUM(CASE WHEN status NOT IN ('valid', 'completed', 'cancelled') THEN 1 ELSE 0 END) AS invalid_status_cnt,

GROUP BY stat_date
HAVING SUM(CASE WHEN event_id IS NULL THEN 1 ELSE 0 END) > 0

    OR COUNT(*) <> COUNT(DISTINCT event_id)
```

### 扩展代码二：把经营看板搭建项目的验收证据写成门禁

```python
from datetime import date
from hashlib import sha256

import pandas as pd

SUBJECT = "经营看板搭建项目"
BLOCKING_RULES = ["范围与验收标准明确","上下游依赖确认","回滚方案可执行"]


def validate_release(frame: pd.DataFrame, start: date, end: date) -> dict:
    scoped = frame.loc[
        frame["event_date"].between(pd.Timestamp(start), pd.Timestamp(end))
        & (frame["subject_key"] == "subject")
    ].copy()
    checks = {
        "has_rows": len(scoped) > 0,
        "event_id_unique": not scoped["event_id"].duplicated().any(),
        "entity_key_complete": scoped["entity_key"].notna().all(),
        "event_time_present": scoped["event_time"].notna().all(),
        "scope_matches": scoped["subject_key"].nunique() == 1,
    }
    payload = f"{SUBJECT}|{start}|{end}|{len(scoped)}|{sorted(checks.items())}"
    return {
        "subject": SUBJECT,
        "rows": len(scoped),
        "checks": checks,
        "blocking_rules": BLOCKING_RULES,
        "release_allowed": all(checks.values()),
        "evidence_hash": sha256(payload.encode("utf-8")).hexdigest(),
    }
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
