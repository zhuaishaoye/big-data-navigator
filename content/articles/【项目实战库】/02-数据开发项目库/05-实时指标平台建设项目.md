# 实时指标平台建设项目

> [!abstract] 场景速览
> “实时指标平台建设项目”在会议里常常只有一句话，落到数据团队却会展开成口径、主键、时间、状态、权限和交付责任。下面用一个从问题到上线的顺序展开，并穿插三个脱敏的复合案例，帮助你把标题里的知识迁移到真实项目。

## 1. “实时指标平台建设项目”在项目实战库业务链中的位置

项目实战库的核心流程可以概括为：立项 → 调研 → 方案 → 开发 → 联调 → 灰度 → 上线 → 验收 → 运营复盘。参与角色包括项目负责人、业务负责人、产品、数据开发、分析师、平台与安全、运维、验收方。“实时指标平台建设项目”通常不是一个孤立字段，而是连接业务动作、数据记录和管理决策的一层能力。

从数据团队视角，至少要回答四个问题：

1. **谁使用**：项目负责人、业务负责人、产品、数据开发分别要用它做判断、执行还是审计。
2. **对象是什么**：一行数据代表需求、一次事件、一个批次还是一天快照。
3. **流程在哪里变化**：通过调研、方案、开发、联调之间的状态和时间差定位问题。
4. **结果如何被采用**：谁在什么时间前采取行动，使用哪个指标观察改善或副作用。

一个合格的专题目标可以写成：

> 在【时间窗】和【授权数据范围】内，围绕“实时指标平台建设项目”，按【项目阶段、业务域、负责人】比较【验收通过率】与【投资回收周期】，定位一个可干预流程节点，并记录行动后的变化与边界。

## 2. 一张图看清角色、流程和数据

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 需求 | `requirement_id` | 立项 |
| 过程对象 | 里程碑 | `milestone_id` | 调研 |
| 过程对象 | 数据表 | `table_id` | 方案 |
| 结果对象 | 接口 | `interface_id` | 开发 |
| 结果对象 | 验收项 | `acceptance_id` | 联调 |
| 专题分析 | 实时指标平台建设项目 | `topic_key = 'subject'` | 用于把通用事件收窄到本主题 |

建模时不要先把所有系统字段堆进一张大表。更稳妥的做法是分别保留三类事实：

- **事件事实**：谁在什么时间做了动作，例如挂号、下单、开工、报警或学习。
- **状态快照**：对象在某一天的状态，例如会员等级、租约、账户余额或设备资产关系。
- **结果事实**：流程完成后的产出，例如结算金额、良品数量、签收结果或考试分数。

三者的粒度不同。把事件、快照和结果强行放在同一行，会让金额、数量和转化率在汇总时重复。若“实时指标平台建设项目”涉及状态变化，优先建立状态机；若涉及金额，先做借贷或收付平衡；若涉及对象归属，保留维度有效期。

## 3. 指标与口径：不要把相关数字直接当答案

| 专题观测面 | 需要回答的问题 | 关键证据 | 判定与动作 |
| --- | --- | --- | --- |
| 接口与变更（本标题优先） | 字段、分区、更新频率和 Schema 如何演进 | 接口契约、DDL、版本和变更记录 | 不兼容变更先新版本并存 |
| 需求与粒度 | 指标和明细分别服务谁，一行数据代表什么 | 需求说明、粒度声明、样例单据 | 粒度未确认不进入编码 |
| 发布与回滚 | 谁审批、如何灰度、失败后怎样恢复 | 发布单、监控、回滚脚本和验收记录 | 关键链路必须有回滚演练 |
| 测试与幂等 | 重复运行、空分区、乱序和边界值是否安全 | 测试数据、重跑结果、唯一键和事务 | 不幂等任务禁止自动补数 |

| 指标 | 计算思路 | 主要维度 | 使用边界 |
| --- | --- | --- | --- |
| 计划达成率 | `COUNT(DISTINCT on_time_milestone_id) / COUNT(DISTINCT milestone_id)`（视图字段 `plan_attainment`） | 项目阶段、业务域、负责人 | 不混用测试、撤销和跨期状态；与“实时指标平台建设项目”相关时还要补充主题筛选 |
| 缺陷关闭率 | `COUNT(DISTINCT closed_defect_id) / COUNT(DISTINCT raised_defect_id)`（视图字段 `defect_closure`） | 业务域、负责人、优先级 | 不混用测试、撤销和跨期状态；与“实时指标平台建设项目”相关时还要补充主题筛选 |
| 上线成功率 | `COUNT(DISTINCT successful_release_id) / COUNT(DISTINCT release_id)`（视图字段 `release_success`） | 负责人、优先级、风险等级 | 不混用测试、撤销和跨期状态；与“实时指标平台建设项目”相关时还要补充主题筛选 |
| 验收通过率 | `COUNT(DISTINCT passed_acceptance_id) / COUNT(DISTINCT acceptance_id)`（视图字段 `acceptance_rate`） | 优先级、风险等级 | 不混用测试、撤销和跨期状态；与“实时指标平台建设项目”相关时还要补充主题筛选 |

指标字典至少应包含：中文名、英文编码、业务定义、计算公式、事实粒度、时间字段、对象范围、排除条件、负责人和验收样例。对于“实时指标平台建设项目”，还应注明它使用的是业务发生时间还是入仓时间，是否包含撤销、退费、测试、跨期和补录记录。

一个常见误区是看到验收通过率变化就立即解释业务原因。更可靠的顺序是：

1. 检查数据覆盖和延迟是否变化。
2. 检查对象范围、状态映射和维度归属是否变化。
3. 按时间、结构和分组拆解贡献。
4. 回到明细寻找能解释变化的事件。
5. 如果已经采取行动，再评估行动带来的增量，而不是事后挑一个相关指标。

## 4. 工作案例：从现象到数据处理

### 案例 1：华南某 SaaS 数据平台的“实时指标平台建设项目”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“实时指标平台建设项目”映射到“数据开发、ETL 与交付流程”中的接口与变更，而不是泛泛讨论概念。
- **触发事件**：一次上游字段扩容导致多个 ETL 任务失败，发布窗口内无法快速定位影响。
- **业务与数据范围**：接口契约、DDL 历史、字段血缘、任务依赖、失败日志和下游资产。数据侧重点采集接口契约、DDL、版本和变更记录，并与项目管理、需求管理、代码仓库中的时间、状态和责任人信息对齐。
- **需要回答的问题**：字段、分区、更新频率和 Schema 如何演进。
- **关键障碍**：代码、表结构和调度配置分别发布，测试环境长期使用旧 Schema。同时要防止范围持续扩张把表面指标带偏。
- **处理过程**：建立契约兼容检查、字段级影响分析、影子表和灰度发布，生产前自动跑新旧结果对照。实施时把“每个任务声明输入输出粒度、分区、幂等键和重跑边界”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例流程把发布前检查、失败阻断、回滚和下游通知串成同一门禁。验收至少同时看主指标、接口契约、DDL、版本和变更记录和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把需求、源接口、分层模型、代码、配置、测试、发布和回滚连成一条可重复执行的数据交付链路。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

这个案例最关键的动作不是“跑一条 SQL”，而是把“实时指标平台建设项目”对应的业务对象和上下游系统放在同一张链路图上。链路图至少要标出源系统、事件时间、关联主键、状态变化、数据负责人和消费方。

## 5. SQL 示例：在统一口径下做分层诊断

下面的查询用于展示分析结构，表名和字段需映射到实际环境。重点是去重、范围筛选、基线比较和贡献率，而不是代码本身。

### 标题专属诊断 SQL

```sql
-- 实时指标平台建设项目：同期基线诊断（优先级 × 项目阶段）
WITH scoped AS (
  SELECT
    requirement_id AS entity_key,
    event_id,
    event_date AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_project_delivery
  WHERE event_date >= DATE '2026-06-01'
    AND event_date <  DATE '2026-09-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '计划达成率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

执行后要回答四类验证题：

- 结果总量能否与源系统或既有报表在相同口径下解释差异？
- 排名前几位的分组是否由少数超长、重复或补录记录造成？
- 缺失日期表现为“未发生”还是“未采集”，是否改变分母？
- 维度使用的是当时归属还是当前归属，跨期比较是否一致？

## 6. 第二个案例：跨系统、跨部门时怎样不失控

### 案例 2：华北某制造数据团队的“实时指标平台建设项目”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“实时指标平台建设项目”映射到“数据开发、ETL 与交付流程”中的需求与粒度，而不是泛泛讨论概念。
- **触发事件**：历史补数运行三天仍未完成，正常日批任务同时出现资源争抢。
- **业务与数据范围**：补数分区、任务耗时、资源队列、依赖层级、下游锁和人工处理记录。数据侧重点采集需求说明、粒度声明、样例单据，并与项目管理、需求管理、代码仓库中的时间、状态和责任人信息对齐。
- **需要回答的问题**：指标和明细分别服务谁，一行数据代表什么。
- **关键障碍**：所有日期一次性并发启动，任务内部没有分区级状态，失败后只能整批重跑。同时要防止验收标准模糊把表面指标带偏。
- **处理过程**：按依赖层级和业务优先级分批，记录每个分区的输入输出计数，并对重跑设置幂等与限流。实施时把“测试覆盖空分区、重复数据、迟到数据、Schema 变化和失败恢复”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例项目用补数进度、正常任务 SLA、重复率和人工介入次数衡量稳定性。验收至少同时看主指标、需求说明、粒度声明、样例单据和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把需求、源接口、分层模型、代码、配置、测试、发布和回滚连成一条可重复执行的数据交付链路。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

跨部门项目最容易在三个地方返工：业务术语没有冻结、主数据映射没有版本、验收时才发现权限不足。建议在开发前让业务负责人签字确认指标定义，让数据负责人确认粒度与主键，让安全负责人确认字段范围，让运维负责人确认发布与回滚窗口。

## 7. Python 示例：把数据质量变成发布门禁

### 可执行质量门禁

```python
# 实时指标平台建设项目：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "实时指标平台建设项目"
TOPIC_KEY = "subject"
RULE_ID = "rule_project_1n8jglp"
GUIDE_CHECKS = [
    "代码、配置、DDL、权限和调度依赖进入同一版本与发布记录",
    "每个任务声明输入输出粒度、分区、幂等键和重跑边界",
    "测试覆盖空分区、重复数据、迟到数据、Schema 变化和失败恢复",
    "上线前完成数量、金额、主键、时延和下游可读性验收"
]
RULES = {
    "required_columns": ["event_id", "requirement_id", "event_date", "status"],
    "duplicate_key": "event_id",
    "entity_key": "requirement_id",
    "time_field": "event_date",
    "max_duplicate_rate": 0.0005,
    "max_null_rate": 0.005,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：代码、配置、DDL、权限和调度依赖进入同一版本与发布记录；每个任务声明输入输出粒度、分区、幂等键和重跑边界；测试覆盖空分区、重复数据、迟到数据、Schema 变化和失败恢复；上线前完成数量、金额、主键、时延和下游可读性验收
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

这段代码适合放在离线任务完成之后、指标发布之前。真实环境还应从调度平台读取分区参数、把结果写入质量平台，并在关键规则失败时阻断下游。告警不是终点，工单中要记录影响资产、发现时间、临时处理、根因、修复时间和防复发动作。

## 8. 异常排查：从指标异常回到业务事件

| 专题检查项 | 失败时会看到什么 | 首选证据 | 处理动作 |
| --- | --- | --- | --- |
| 代码、配置、DDL、权限和调度依赖进入同一版本与发布记录 | 字段、分区、更新频率和 Schema 如何演进 | 接口契约、DDL、版本和变更记录 | 不兼容变更先新版本并存 |
| 每个任务声明输入输出粒度、分区、幂等键和重跑边界 | 指标和明细分别服务谁，一行数据代表什么 | 需求说明、粒度声明、样例单据 | 粒度未确认不进入编码 |
| 测试覆盖空分区、重复数据、迟到数据、Schema 变化和失败恢复 | 谁审批、如何灰度、失败后怎样恢复 | 发布单、监控、回滚脚本和验收记录 | 关键链路必须有回滚演练 |
| 上线前完成数量、金额、主键、时延和下游可读性验收 | 重复运行、空分区、乱序和边界值是否安全 | 测试数据、重跑结果、唯一键和事务 | 不幂等任务禁止自动补数 |

围绕“实时指标平台建设项目”排查时，可以按以下顺序进行：

1. **影响面**：哪些指标、报表、接口或业务团队受影响，是否需要暂停对外发布。
2. **时间线**：源系统变更、任务发布、数据回刷、组织调整和业务活动分别发生在什么时候。
3. **数据链路**：上游是否延迟，分区是否缺失，主键是否重复，状态是否映射错误。
4. **业务证据**：抽取异常记录，与原始单据、操作日志、客服记录或现场系统核对。
5. **修复与复核**：明确补数范围、重跑粒度、回滚版本和验收样例。
6. **防复发**：把一次性排查升级为规则、监控、责任人和变更评审。

特别要注意：范围持续扩张；验收标准模糊；上线后无人跟踪业务效果；关键依赖延期。这些问题如果不被单独标记，很容易被误写成业务趋势。

## 9. 第三个案例与延伸场景

### 案例 3：华东某零售数据开发组的“实时指标平台建设项目”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“实时指标平台建设项目”映射到“数据开发、ETL 与交付流程”中的发布与回滚，而不是泛泛讨论概念。
- **触发事件**：订单日报连续两天出现重复金额，重跑后差异进一步扩大。
- **业务与数据范围**：源订单、支付、退款、任务实例、写入模式、分区和质量结果。数据侧重点采集发布单、监控、回滚脚本和验收记录，并与项目管理、需求管理、代码仓库中的时间、状态和责任人信息对齐。
- **需要回答的问题**：谁审批、如何灰度、失败后怎样恢复。
- **关键障碍**：任务使用追加写，支付回调重复进入 ODS，开发只按订单号关联而没有确认退款粒度。同时要防止上线后无人跟踪业务效果把表面指标带偏。
- **处理过程**：为源事件补充唯一键和版本，按订单行统一事实粒度，改为分区幂等合并并建立金额桥接对账。实施时把“上线前完成数量、金额、主键、时延和下游可读性验收”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例交付以重跑一致、金额平衡、分区覆盖和下游验收作为恢复条件。验收至少同时看主指标、发布单、监控、回滚脚本和验收记录和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把需求、源接口、分层模型、代码、配置、测试、发布和回滚连成一条可重复执行的数据交付链路。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

另外两个适合继续拆分的工作场景是：

- **某全国连锁服务企业**：管理层发现营业额增长但利润下降，跨部门对原因判断不一致。可以先从门店、订单、客户、活动、成本、人员和工单数据建立最小数据闭环，再围绕“实时指标平台建设项目”检查收入与成本时间归属不同，活动优惠分摊不完整，组织调整导致门店历史归属变化。
- **某大型企业数据平台团队**：报表数量增长但业务仍反馈找不到可信数据，数据团队交付压力持续上升。可以先从表、任务、指标、血缘、质量规则、查询日志和问题工单建立最小数据闭环，再围绕“实时指标平台建设项目”检查同一指标多个 SQL 版本，血缘只覆盖部分任务，资产没有明确负责人。

### 案例 4：实时指标平台建设项目从源事件到结果的长链路核查

某组织希望用“实时指标平台建设项目”支持一次真实决策，但在取数与评审阶段发现，结果表出现缺失或延迟，单看调度状态却显示成功，无法判断问题发生在源端、接入、计算还是服务层。这个案例因此从问题定义重新开始。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 把业务发生时间、数据可见时间、任务完成时间和下游消费时间放到同一条证据链。在本场景里，核心风险还包括关键依赖延期，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：需求、里程碑及其在验收前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注requirement_id与milestone_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 结果表出现缺失或延迟，单看调度状态却显示成功，无法判断问题发生在源端、接入、计算还是服务层。初看时，需求管理与代码仓库的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 源端操作日志、CDC/批次水位、分区清单、任务参数、血缘关系、下游请求日志。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“平台与安全”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“实时指标平台建设项目”的当前定义并记录版本；第二步用需求明细核对需求管理到代码仓库的关联；第三步按优先级与项目阶段做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察验收通过率和护栏指标计划达成率。
- **行动与护栏：** 按时间轴核对每一跳的输入输出计数与水位，先阻断错误结果扩散，再确定重跑范围和补数窗口。专题检查项“代码、配置、DDL、权限和调度依赖进入同一版本与发布记录”被写成发布门禁，无法证明数据完整的链路不进入正式发布，优先保留旧版本供下游读取。
- **失败路径：** 看到任务成功就立即补数，却没有确认重复、乱序和迟到事件。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“实时指标平台建设项目”时，先验证接口契约、DDL、版本和变更记录，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由平台与安全在明确时限内，根据验收通过率、计划达成率和结果可核对决定继续、回退、补查还是转人工。 若关键依赖延期或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 案例 7：实时指标平台建设项目的三方取舍实验

团队准备把“实时指标平台建设项目”从个人分析脚本升级为多人共用的数据能力。第一次评审就暴露出：为追求更快结果不断增加资源，账单和重复计算同步上升，但业务真正使用的时效并没有显著改善。 下面的组织、规模和结果均为公开方法结合常见工作场景形成的脱敏复合示例，不对应任何单一企业事实。

- **为什么要做：** 把新鲜度、正确性和成本分别量化，找到满足真实决策节奏的最低必要资源。在本场景里，核心风险还包括验收标准模糊，所以项目从一开始就把“结果能解释”与“结果能产出”放在同等位置。
- **对象与数据范围：** 本次只使用为了回答该问题所必需的脱敏范围：接口、验收项及其在调研前后的状态记录；时间窗覆盖一个完整业务周期，并保留行动前后的观察窗口。 主键重点关注interface_id与acceptance_id，时间上区分业务发生、数据可见和下游采用三个节点。
- **关键异常或争议：** 为追求更快结果不断增加资源，账单和重复计算同步上升，但业务真正使用的时效并没有显著改善。初看时，监控平台与数据质量平台的状态字段似乎可以互换，但抽取边界记录后发现二者更新节奏和责任人不同。
- **核验证据：** 执行计划、扫描量、文件数、峰值资源、单位产出成本、业务截止时间和质量门禁。核验时至少抽取正常、边界、重复或迟到、权限拒绝四类样本，并让“项目负责人”确认什么结果可以进入下一步。
- **处理步骤：** 第一步先冻结“实时指标平台建设项目”的当前定义并记录版本；第二步用接口明细核对监控平台到数据质量平台的关联；第三步按业务域与优先级做基线和结构比较；第四步记录异常样本、规则豁免与人工判断；第五步发布小范围结果，观察缺陷关闭率和护栏指标验收通过率。
- **行动与护栏：** 先按使用场景和截止时间分级，再比较预聚合、增量计算、缓存、并发调整和生命周期策略。专题检查项“上线前完成数量、金额、主键、时延和下游可读性验收”被写成发布门禁，任何优化都必须同时通过结果对账、延迟目标与成本预算，不能只展示一次最快执行。
- **失败路径：** 为了压缩账单关闭质量检查，或为了刷新频率重复计算无人消费的全量结果。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“实时指标平台建设项目”时，先验证测试数据、重跑结果、唯一键和事务，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由项目负责人在明确时限内，根据缺陷关闭率、验收通过率和上下游依赖确认决定继续、回退、补查还是转人工。 若验收标准模糊或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从实时指标平台建设项目回到可核对明细

```sql
-- 实时指标平台建设项目：状态链与时间间隔核查
WITH ordered_events AS (
  SELECT
    requirement_id AS entity_key,
    event_id,
    stage_code,
    event_date AS event_time,
    LAG(stage_code) OVER (
      PARTITION BY requirement_id
      ORDER BY event_date, event_id
    ) AS previous_stage,
    LAG(event_date) OVER (
      PARTITION BY requirement_id
      ORDER BY event_date, event_id
    ) AS previous_time
  FROM fact_project_delivery
  WHERE event_date >= :start_date
    AND event_date <  :end_date
    AND subject_key = 'subject'
)
SELECT
  entity_key,
  previous_stage,
  stage_code,
  event_time,
  event_time - previous_time AS elapsed,
  CASE
    WHEN event_time < previous_time THEN 'time_reversed'
    WHEN previous_stage = stage_code THEN 'duplicate_stage'
    WHEN previous_stage IS NULL THEN 'missing_prefix'
    ELSE 'candidate_delay'
  END AS exception_type
FROM ordered_events
WHERE event_time < previous_time
   OR previous_stage = stage_code
   OR event_time - previous_time > INTERVAL '1 hour'
ORDER BY exception_type, elapsed DESC;
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把实时指标平台建设项目的验收证据写成门禁

```python
import json
from pathlib import Path


def build_evidence_manifest(
    subject: str,
    scope: dict,
    checks: dict,
    samples: list[dict],
    owner: str,
) -> dict:
    failed = [name for name, passed in checks.items() if not passed]
    return {
        "subject": subject,
        "scope": scope,
        "checks": checks,
        "failed_checks": failed,
        "sample_evidence": samples[:5],
        "owner": owner,
        "decision": "block" if failed else "review",
        "manual_questions": [
            "每一项失败是否已回到原始记录",
            "对象、时间和状态是否与指标字典一致",
            "回滚或修复后是否重新完成对账",
        ],
    }


manifest = build_evidence_manifest(
    subject="实时指标平台建设项目",
    scope={"systems": ["项目管理","需求管理","代码仓库","调度平台"]},
    checks={"definition_frozen": False, "reconciled": False},
    samples=[],
    owner="项目负责人",
)
Path("release-evidence.json").write_text(
    json.dumps(manifest, ensure_ascii=False, indent=2),
    encoding="utf-8",
)
print(manifest["decision"])
```

示例中的行数、时间戳和版本号均为占位值。生产实现应从调度参数、数据契约和质量平台读取真实信息，并将失败结果回写到工单、发布系统和责任人，而不是只打印在日志中。
