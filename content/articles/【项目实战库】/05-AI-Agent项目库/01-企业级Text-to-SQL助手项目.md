# 企业级Text-to-SQL助手项目

> [!tip] 核心原则
> “企业级Text-to-SQL助手项目”既可能是业务概念，也可能是技术方案，还可能是岗位能力。判断学习是否有效，要看能否在项目立项、现状诊断、方案设计、开发联调、上线验收、运营复盘和收益评估中做出一个可复现的小闭环。本文用多个案例展示从需求到数据结果，再回到业务行动和复盘的完整路径。

## 1. 从业务任务定义 AI 能力

围绕“企业级Text-to-SQL助手项目”，先把任务写成输入、输出、成功标准和失败边界。不要从“上一套模型”或“接一个聊天框”开始。

| 设计项 | 必须回答的问题 | 错误示例 | 更好做法 |
| --- | --- | --- | --- |
| 用户 | 谁使用，谁复核，谁承担后果 | 所有人都能用 | 按角色和权限明确使用边界 |
| 输入 | 文本、表格、图片还是工具调用 | 把所有数据都塞进上下文 | 只提供任务所需且获授权的数据 |
| 输出 | 分类、生成、检索、SQL 还是动作 | 只要求“回答准确” | 定义可检查的输出结构 |
| 成功 | 任务完成、采纳、质量、时延和成本 | 只看离线准确率 | 离线 + 线上 + 人工复核 |
| 失败 | 无答案、拒答、转人工还是回滚 | 失败也生成看似合理内容 | 明确置信阈值和降级路径 |

| 角色 | 业务对象 | 主键示例 | 在流程中的位置 |
| --- | --- | --- | --- |
| 核心对象 | 需求 | `requirement_id` | 立项 |
| 过程对象 | 里程碑 | `milestone_id` | 调研 |

AI 项目的数据治理比传统报表更强调版本和来源。至少记录：

- 数据集和知识文档的来源、授权、时间、负责人和版本。
- 样本标注规则、标注人、抽检结果和争议处理。
- 训练、验证、测试与线上反馈是否隔离。
- 提示词、模型、温度、检索参数和工具权限的版本。
- 输入中的个人信息、商业秘密和敏感字段是否脱敏。

如果“企业级Text-to-SQL助手项目”使用 RAG，文档切片应尊重标题、章节、表格和条款结构；如果使用微调，先证明提示词、检索或流程优化不足；如果使用 Agent，先限制工具白名单和最大执行步数。

## 3. 评估：不要只看一个准确率

| 评估层 | 指标 | 说明 |
| --- | --- | --- |
| 检索 | Hit@K、MRR、版本正确率、权限过滤 | 正确内容是否被召回且可用 |
| 生成 | 引用支持率、事实一致性、完整性 | 回答是否有证据、是否遗漏关键条件 |
| 任务 | 完成率、转人工率、采纳率、重复澄清 | 用户问题是否真的解决 |
| 安全 | 越权、注入、敏感输出、违规动作 | 是否突破权限与安全边界 |
| 工程 | P50/P95 延迟、错误率、并发、成本 | 能否稳定且经济地服务 |
| 业务 | 节省时间、转化、质量、投诉 | 是否带来可解释价值 |

离线集要包含高频问题、长尾问题、边界问题、对抗问题和“应该拒答”的问题。线上评估要按用户、任务和风险等级分层，避免总体平均掩盖高危错误。

## 4. 案例一：华北某 AI 数据平台

### 案例 1：华北某 AI 数据平台的“企业级Text-to-SQL助手项目”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“企业级Text-to-SQL助手项目”映射到“数据服务、API 与语义层”中的一致性，而不是泛泛讨论概念。
- **触发事件**：Text-to-SQL 助手生成的查询能运行，但经常扫描敏感字段或返回错误口径。
- **业务与数据范围**：表语义、字段权限、指标、查询历史、SQL 校验和执行结果。数据侧重点采集数据版本、延迟、对账和回放记录，并与项目管理、需求管理、代码仓库中的时间、状态和责任人信息对齐。
- **需要回答的问题**：服务结果来自哪张表、哪个快照和哪次更新。
- **关键障碍**：模型直接访问物理表，缺少语义层、权限前置和结果合理性验证。同时要防止范围持续扩张把表面指标带偏。
- **处理过程**：只暴露受控语义对象，生成后做语法、权限、成本和业务规则检查，高风险查询转人工。实施时把“服务端执行身份、租户、行级和字段级权限校验”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例项目以可执行率、口径正确率、越权拦截率和平均成本评估助手。验收至少同时看主指标、数据版本、延迟、对账和回放记录和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把数据能力封装成有契约、有版本、有权限、有 SLA、有监控的服务，并明确查询、缓存、限流和失败降级。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

## 5. Python：检索与任务评估

### 检索、Agent 或模型任务实现

```python
from fastapi import Depends, FastAPI, HTTPException
from pydantic import BaseModel, Field

app = FastAPI()

class MetricQuery(BaseModel):
    metric: str = Field(pattern="^(gmv|paid_orders|refund_rate)$")
    date_from: str
    date_to: str
    merchant_id: str
    page_size: int = Field(default=100, le=500)

def current_user() -> dict:
    return {"tenant_id": "demo", "scopes": {"metric:read"}, "merchant_scope": {"M1001"}}

@app.post("/v1/metrics/query")
def query_metric(body: MetricQuery, user: dict = Depends(current_user)):
    if "metric:read" not in user["scopes"]:
        raise HTTPException(status_code=403, detail="scope_missing")
    if body.merchant_id not in user["merchant_scope"]:
        raise HTTPException(status_code=403, detail="row_scope_denied")
    return {
        "topic": "\"企业级Text-to-SQL助手项目\"",
        "data_version": "2026-11-05T02:15:00+08:00",
        "p95_budget_ms": 800,
    }

# 版本、字段、错误码、权限、数据新鲜度、超时、扫描上限和分页都属于接口契约；
# Text-to-SQL 与 Agent-to-Data 必须经过同一权限、成本和审计链路。
```

### 标题专属数据与失败分层 SQL

```sql
-- 企业级Text-to-SQL助手项目：同期基线诊断（项目阶段 × 负责人）
WITH scoped AS (
  SELECT
    requirement_id AS entity_key,
    event_id,
    event_date AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_project_delivery
  WHERE event_date >= DATE '2026-06-01'
    AND event_date <  DATE '2026-09-01'
    AND subject_key = 'text_to_sql'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '上线成功率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

示例代码只展示可测试结构。真实系统还需要模型服务、向量库、权限、日志、缓存、限流、敏感检查和人工反馈，不应把安全完全交给提示词。

## 6. 案例二：华东某零售数据平台

### 案例 2：华东某零售数据平台的“企业级Text-to-SQL助手项目”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把标题中的名词还原成一个可以观测的运行问题。本例把“企业级Text-to-SQL助手项目”映射到“数据服务、API 与语义层”中的契约，而不是泛泛讨论概念。
- **触发事件**：多个活动页面直接调用明细接口，月初并发升高后数据库变慢。
- **业务与数据范围**：API 调用量、查询参数、热点租户、缓存命中、P95 和数据库执行计划。数据侧重点采集OpenAPI、Schema、兼容测试和样例，并与项目管理、需求管理、代码仓库中的时间、状态和责任人信息对齐。
- **需要回答的问题**：请求、响应、字段、错误码和版本是否稳定。
- **关键障碍**：接口允许任意维度和时间范围查询，无分页、限流与缓存，权限校验还会触发额外全表扫描。同时要防止验收标准模糊把表面指标带偏。
- **处理过程**：收窄查询契约，增加聚合结果缓存、租户限流、分页和慢查询拒绝，并把数据版本返回给调用方。实施时把“P95、错误率、限流、缓存、慢查询和成本都有监控”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例服务用 P95、错误率、缓存命中、数据库负载和结果一致性验收。验收至少同时看主指标、OpenAPI、Schema、兼容测试和样例和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“把数据能力封装成有契约、有版本、有权限、有 SLA、有监控的服务，并明确查询、缓存、限流和失败降级。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

## 7. 架构与工程链路

| 层次 | 本文建议 | 关键问题 | 验收证据 |
| --- | --- | --- | --- |
| 数据源 | 项目管理、需求管理、代码仓库 | 权威源、更新频率、主键和权限 | 接口或表清单 |
| 接入 | 批、流或 CDC 按业务时延选择 | 重复、顺序、断点续传和回放 | 延迟与幂等测试 |
| 存储 | 按访问模式选择数据湖、数仓或 OLAP | 分区、格式、生命周期和成本 | 容量与查询评测 |
| 计算 | SQL、Spark、Flink 或 Python 服务 | 粒度、状态、资源和失败恢复 | 压测与执行计划 |
| 治理 | 元数据、质量、血缘、权限 | 责任、规则、影响分析和审计 | 规则结果与变更记录 |
| 服务 | 指标、API、看板或应用 | SLA、缓存、限流和版本 | 监控与验收样例 |

推荐把链路拆成六层：数据与知识准备、检索或特征、模型调用、工具执行、评估与审核、监控与反馈。每层都要有版本、日志和失败处理。Agent 工具调用应在服务端校验参数与权限，不能只依赖模型“自觉”。

## 8. 监控、成本与安全

- 监控请求量、延迟、错误码、超时、重试和缓存命中。
- 记录检索文档版本、模型版本、提示词版本和关键参数。
- 对失败分类：检索缺失、上下文过长、工具失败、权限拒绝、模型拒答、结果不合规。
- 设置单位任务成本、每租户预算和异常调用告警。
- 对提示注入、越权、敏感信息和危险动作做专门测试。
- 保留人工复核、转人工、回滚到旧模型和关闭工具的开关。

## 9. 第三个案例与上线验收

### 案例 3：华南某 SaaS 公司的“企业级Text-to-SQL助手项目”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先确认业务对象和系统边界，再讨论工具或参数。本例把“企业级Text-to-SQL助手项目”映射到“数据服务、API 与语义层”中的性能，而不是泛泛讨论概念。
- **触发事件**：客户要求按租户配置指标，但每次变更都要修改接口代码。
- **业务与数据范围**：租户、指标定义、语义层、SQL 模板、权限和版本。数据侧重点采集指标、压测、慢查询和容量基线，并与项目管理、需求管理、代码仓库中的时间、状态和责任人信息对齐。

12. 上线前定义告警阈值、回滚条件和责任人；上线后按周观察主指标与护栏指标。
13. 复盘时区分数据问题、业务变化、方案偏差和外部因素，并把改进项转成有时限的任务。

### 扩展代码一：从企业级Text-to-SQL助手项目回到可核对明细

```sql
-- 企业级Text-to-SQL助手项目：恢复后缺失、重复与跨期检查
WITH expected_keys AS (
  SELECT DISTINCT requirement_id AS entity_key, event_id
  FROM fact_project_delivery
  WHERE event_date >= :restore_start
    AND event_date <  :restore_end
    AND subject_key = 'text_to_sql'
),
restored_keys AS (
  SELECT requirement_id AS entity_key, event_id, load_version, loaded_at
  FROM fact_project_delivery
  WHERE event_date >= :restore_start
    AND event_date <  :restore_end
    AND subject_key = 'text_to_sql'
    AND load_version = :restore_version
),
coverage AS (
  SELECT
    (SELECT COUNT(*) FROM expected_keys) AS expected_cnt,
    (SELECT COUNT(*) FROM restored_keys) AS restored_cnt,
    (SELECT COUNT(*) FROM (
      SELECT entity_key, event_id
      FROM restored_keys
      GROUP BY entity_key, event_id
      HAVING COUNT(*) > 1
    ) duplicate_keys) AS duplicated_cnt,
    (SELECT COUNT(*) FROM (
      SELECT e.entity_key, e.event_id
      FROM expected_keys e
      LEFT JOIN restored_keys r USING (entity_key, event_id)
      WHERE r.entity_key IS NULL
    ) missing_keys) AS missing_cnt
)
SELECT *,
  CASE
    WHEN expected_cnt <> restored_cnt OR duplicated_cnt > 0 OR missing_cnt > 0
      THEN 'reject_release'
    ELSE 'accept_restore'
  END AS gate_result
FROM coverage;
```
