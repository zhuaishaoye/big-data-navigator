# 技术选型横评-数据湖格式篇

> [!abstract] 工程视角
> 讨论“技术选型横评-数据湖格式篇”时，最容易犯的错误是直接从工具或报表开始。更有用的顺序是：先看业务链条，再找可观察指标，随后确认数据粒度，最后才选择 SQL、模型或平台组件。本文按这个顺序给出可执行方案和常见的失败样本。

## 1. 需求、SLA 与边界

“技术选型横评-数据湖格式篇”首先是工程问题，其次才是工具选择。立项时明确：

- 谁消费数据或服务，用来做什么决策或操作。
- 数据从产生到可用允许延迟多久，失败时能否接受部分结果。
- 更新频率、保留周期、回放范围、并发和数据量级。
- 上下游依赖、权限、敏感字段、审计和成本上限。
- 正确性、完整性和一致性中，哪些必须强保证，哪些可最终一致。

学习方法分享中常见的交付指标包括主动练习占比、间隔复习完成率、问题闭环率。不要只写“稳定”“高效”，应定义可监测的 SLI、SLO 和错误预算。

## 3. 案例一：华北某互联网平台

### 案例 1：华北某互联网平台的“技术选型横评-数据湖格式篇”现场

这是一个结合公开方法、常见工程故障和脱敏数据构造的复合案例，不对应任何单一企业事实。

- **标题落点**：先把正常链路跑通，再人为制造一次失败和恢复。本例把“技术选型横评-数据湖格式篇”映射到“数仓、数据湖与建模”中的分层，而不是泛泛讨论概念。
- **触发事件**：宽表数量快速膨胀，同一指标在不同数据集市重复开发。
- **业务与数据范围**：指标定义、查询日志、血缘、下游应用、任务成本和口径争议记录。数据侧重点采集血缘、复用率、查询模式和成本，并与笔记、代码仓库、问题清单中的时间、状态和责任人信息对齐。
- **需要回答的问题**：ODS、DWD、DWS、ADS 或湖仓分层各自解决什么问题。
- **关键障碍**：团队按报表而不是业务过程建模，宽表承担多种粒度，指标逻辑被复制。同时要防止信息过载把表面指标带偏。
- **处理过程**：建立一致性维度和原子指标，派生指标进入语义层，保留指标版本与负责人。实施时把“金额、数量、去重对象和状态转换都要有独立对账样例”写成上线检查项，并为每一项保留日志、样本和负责人。
- **验证方式**：示例方案用复用率、口径变更影响面和查询成本验证建模价值。验收至少同时看主指标、血缘、复用率、查询模式和成本和一次故障回放，不能只截取优化后最快的一次结果。
- **可迁移结论**：遇到类似标题时，先按“先定义业务过程、事实粒度和维度有效期，再决定分层、宽表、湖仓格式与查询引擎；模型要能被复算、追溯和稳定消费。”建立判断顺序，再决定是否调整代码、资源、口径或组织流程。

## 4. 代码实现：从可运行到可维护

### 专题实现代码

```sql
-- "技术选型横评-数据湖格式篇"
-- 先声明粒度：一行 = 一个订单商品行在支付成功时形成的可加事实。
WITH paid_order AS (
  SELECT
    order_id,
    order_line_id,
    merchant_id,
    paid_at,
    quantity,
    pay_amount,
    refund_amount,
    ROW_NUMBER() OVER (PARTITION BY order_line_id ORDER BY updated_at DESC) AS rn
  FROM dwd_order_line
  WHERE dt >= DATE '2026-10-01'
    AND dt <  DATE '2026-11-01'
    AND pay_status = 'PAID'
),
dim_merchant AS (
  SELECT merchant_id, category_name, valid_from, valid_to
  FROM dim_merchant
  WHERE valid_from < DATE '2026-11-01'
    AND valid_to >= DATE '2026-10-01'
)
SELECT
  DATE(p.paid_at) AS stat_date,
  m.category_name,
  COUNT(DISTINCT p.order_id) AS order_cnt,
  SUM(p.quantity) AS item_cnt,
  SUM(p.pay_amount - p.refund_amount) AS net_gmv
FROM paid_order p
JOIN dim_merchant m
  ON p.merchant_id = m.merchant_id
 AND p.paid_at >= m.valid_from
 AND p.paid_at <  m.valid_to
WHERE p.rn = 1
GROUP BY DATE(p.paid_at), m.category_name;

-- 对账：事实主键、金额平衡、维度有效期、跨期退款和源系统抽样分别留证据。
```

### 统一口径诊断 SQL

```sql
-- 技术选型横评-数据湖格式篇：分位对比诊断（掌握等级 × 学习阶段）
WITH scoped AS (
  SELECT
    question_id AS entity_key,
    event_id,
    activity_date AS event_date,
    dimension_value AS primary_dim,
    stage_code AS secondary_dim,
    metric_value,
    status
  FROM fact_learning_activity
  WHERE activity_date >= DATE '2026-03-01'
    AND activity_date <  DATE '2026-06-01'
    AND subject_key = 'subject'
    AND is_deleted = 0
),
dedup AS (
  SELECT *
  FROM (
    SELECT
      scoped.*,
      ROW_NUMBER() OVER (
        PARTITION BY event_id
        ORDER BY event_date DESC
      ) AS version_no
    FROM scoped
  ) ranked
  WHERE version_no = 1
),
grouped AS (
  SELECT
    primary_dim,
    secondary_dim,
    COUNT(DISTINCT entity_key) AS entity_cnt,
    COUNT(DISTINCT event_id) AS event_cnt,
    SUM(metric_value) AS metric_sum,
    AVG(metric_value) AS metric_avg
  FROM dedup
  WHERE status IN ('valid', 'completed')
  GROUP BY primary_dim, secondary_dim
),
contribution AS (
  SELECT
    *,
    metric_sum * 1.0 / NULLIF(SUM(metric_sum) OVER (PARTITION BY secondary_dim), 0) AS contribution_ratio,
    metric_avg - AVG(metric_avg) OVER (PARTITION BY secondary_dim) AS delta_to_peer
  FROM grouped
)
SELECT
  '间隔复习完成率' AS checked_metric,
  primary_dim,
  secondary_dim,
  entity_cnt,
  event_cnt,
  ROUND(metric_sum, 4) AS metric_sum,
  ROUND(contribution_ratio, 4) AS contribution_ratio,
  ROUND(delta_to_peer, 4) AS delta_to_peer
FROM contribution
ORDER BY ABS(delta_to_peer) DESC, entity_cnt DESC;
```

工程代码至少要满足以下要求：

1. 输入输出明确，参数来自配置或调度上下文。
2. 重跑同一分区不会产生重复结果。
3. 关键步骤记录度量，便于定位数据量和状态变化。
4. 失败可重试，但不会无限重试或放大副作用。
5. 版本、表结构和依赖变更可追踪。
6. 敏感信息不写进代码、日志和异常信息。

### 质量门禁与失败样本

```python
# 技术选型横评-数据湖格式篇：发布前的数据质量与分层检查
import pandas as pd
import numpy as np
import hashlib

TOPIC = "技术选型横评-数据湖格式篇"
TOPIC_KEY = "subject"
RULE_ID = "rule_method_1hkqdne"
GUIDE_CHECKS = [
    "为每个事实表写清业务过程、粒度、主键、时间字段和可加性",
    "维度保留历史有效期，跨期比较使用当时归属",
    "金额、数量、去重对象和状态转换都要有独立对账样例",
    "湖仓格式与分区、文件大小、元数据和生命周期必须一起评估"
]
RULES = {
    "required_columns": ["event_id", "question_id", "activity_date", "status"],
    "duplicate_key": "event_id",
    "entity_key": "question_id",
    "time_field": "activity_date",
    "max_duplicate_rate": 0.0006,
    "max_null_rate": 0.006,
    "allowed_status": {"valid", "completed", "cancelled", "refunded"},
}

def validate(frame: pd.DataFrame) -> pd.DataFrame:
    missing = [c for c in RULES["required_columns"] if c not in frame.columns]
    if missing:
        raise ValueError(f"{TOPIC}/{TOPIC_KEY} missing required columns: {missing}")

    checks = []
    checks.append(("duplicate_rate", frame[RULES["duplicate_key"]].duplicated().mean(), RULES["max_duplicate_rate"]))
    checks.append(("entity_null_rate", frame[RULES["entity_key"]].isna().mean(), RULES["max_null_rate"]))
    event_time = pd.to_datetime(frame[RULES["time_field"]], errors="coerce")
    checks.append(("invalid_time_rate", event_time.isna().mean(), 0.0))
    bad_status = (~frame["status"].isin(RULES["allowed_status"])).mean()
    checks.append(("invalid_status_rate", bad_status, 0.0))

    result = pd.DataFrame(checks, columns=["check_name", "value", "threshold"])
    result["rule_id"] = RULE_ID + "." + result["check_name"]
    result["topic"] = TOPIC
    result["topic_key"] = TOPIC_KEY
    result["passed"] = result["value"].le(result["threshold"])
    result["sample_fingerprint"] = hashlib.sha1(
        f"{TOPIC}|{RULE_ID}|{len(frame)}".encode("utf-8")
    ).hexdigest()[:12]
    return result

def diagnose(frame: pd.DataFrame) -> pd.DataFrame:
    return (
        frame.assign(stat_date=pd.to_datetime(frame[RULES["time_field"]]).dt.date)
        .groupby(["stat_date", "status"], dropna=False)
        .agg(
            event_cnt=(RULES["duplicate_key"], "nunique"),
            entity_cnt=(RULES["entity_key"], "nunique"),
        )
        .reset_index()
        .assign(topic=TOPIC, topic_key=TOPIC_KEY, rule_id=RULE_ID)
        .sort_values("stat_date")
    )

def release_gate(result: pd.DataFrame) -> None:
    failed = result.loc[~result["passed"], ["topic_key", "check_name", "value", "threshold"]]
    if not failed.empty:
        raise RuntimeError({"topic": TOPIC, "failed_checks": failed.to_dict("records")})

# 主题专属门禁：为每个事实表写清业务过程、粒度、主键、时间字段和可加性；维度保留历史有效期，跨期比较使用当时归属；金额、数量、去重对象和状态转换都要有独立对账样例；湖仓格式与分区、文件大小、元数据和生命周期必须一起评估
# 生产化时把结果写入质量平台，并携带批次、分区、代码版本、规则版本和处理工单。
```

测试分为开发环境和生产前门禁。开发环境可以使用抽样数据快速验证逻辑，生产前门禁必须检查分区覆盖、主键、比例异常、上下游对账和资源消耗。数据发布后还要验证消费者能够读取、权限正确且时延在 SLA 内。

## 7. 性能、容量与成本

| 瓶颈 | 先测量 | 可选手段 | 风险 |
| --- | --- | --- | --- |
| 扫描过多 | 分区命中、文件数、字节数 | 分区裁剪、列裁剪、压缩格式 | 分区过碎 |
| Shuffle 重 | 数据量、键分布、并发 | 预聚合、盐化、调整并发 | 资源争抢 |
| 热点倾斜 | Task 时长、输入大小 | 拆分热点键、两阶段聚合 | 结果顺序变化 |
| 状态过大 | Checkpoint、状态后端 | TTL、增量 Checkpoint、拆分 | 业务语义风险 |
| 查询慢 | 执行计划、缓存命中 | 预聚合、物化视图、OLAP | 数据新鲜度 |
| 成本高 | CPU、内存、存储、调用 | 生命周期、冷热分层、弹性 | SLA 退化 |

调优必须建立基线和回归对比：执行时间、扫描量、Shuffle 量、峰值内存、失败率和成本。只展示一次“从 30 分钟到 3 分钟”不够，还要说明数据量、资源和结果是否正确。

- **行动与护栏：** 按时间轴核对每一跳的输入输出计数与水位，先阻断错误结果扩散，再确定重跑范围和补数窗口。专题检查项“湖仓格式与分区、文件大小、元数据和生命周期必须一起评估”被写成发布门禁，无法证明数据完整的链路不进入正式发布，优先保留旧版本供下游读取。
- **失败路径：** 看到任务成功就立即补数，却没有确认重复、乱序和迟到事件。这类做法即使暂时让数字看起来一致，也会让后续无法区分“业务变化、数据缺失、规则例外和计算错误”。
- **可迁移结论：** 处理“技术选型横评-数据湖格式篇”时，先验证维度有效期、代理键和源系统映射，再讨论工具参数或资源调整。若证据只能支持一个假设，就把它标成假设，并为下一轮验证保留对照与样本。

> [!note] 本例验收
> 最终动作不是“把报表做出来”，而是由同伴在明确时限内，根据问题闭环率、迁移应用次数和练习有反馈决定继续、回退、补查还是转人工。 若缺少反馈或关键检查项没有证据，结论应停在“待核验”，不能用业务解释替代数据回放。

### 扩展代码一：从技术选型横评-数据湖格式篇回到可核对明细

```sql
-- 技术选型横评-数据湖格式篇：发布前质量画像
SELECT
  'subject' AS subject_key,
  stat_date,
  COUNT(*) AS row_cnt,
  COUNT(DISTINCT event_id) AS distinct_event_cnt,
  SUM(CASE WHEN event_id IS NULL THEN 1 ELSE 0 END) AS null_event_cnt,
  SUM(CASE WHEN activity_date < business_time THEN 1 ELSE 0 END) AS time_reverse_cnt,
  SUM(CASE WHEN status NOT IN ('valid', 'completed', 'cancelled') THEN 1 ELSE 0 END) AS invalid_status_cnt,
  ROUND(COUNT(*) * 1.0 / NULLIF(COUNT(DISTINCT event_id), 0), 4) AS duplication_ratio
FROM fact_learning_activity
WHERE stat_date BETWEEN :start_date AND :end_date
GROUP BY stat_date
HAVING SUM(CASE WHEN event_id IS NULL THEN 1 ELSE 0 END) > 0
    OR SUM(CASE WHEN activity_date < business_time THEN 1 ELSE 0 END) > 0
    OR COUNT(*) <> COUNT(DISTINCT event_id)
ORDER BY stat_date;

-- 至少人工核对一次：目标可验证；资料有出处；练习有反馈。
```

执行这段 SQL 后，不要只看总量。应同时保存查询参数、口径版本、异常对象清单和对应原始记录抽样。若结果依赖人工过滤，要把过滤条件登记为规则，而不是留在个人脚本里。

### 扩展代码二：把技术选型横评-数据湖格式篇的验收证据写成门禁

```python
import json
from pathlib import Path


def build_evidence_manifest(
    subject: str,
    scope: dict,
    checks: dict,
    samples: list[dict],
    owner: str,
) -> dict:
    failed = [name for name, passed in checks.items() if not passed]
    return {
        "subject": subject,
        "scope": scope,
        "checks": checks,
        "failed_checks": failed,
        "sample_evidence": samples[:5],
        "owner": owner,
        "decision": "block" if failed else "review",
        "manual_questions": [
            "每一项失败是否已回到原始记录",
            "对象、时间和状态是否与指标字典一致",
            "回滚或修复后是否重新完成对账",
        ],
    }


manifest = build_evidence_manifest(
    subject="技术选型横评-数据湖格式篇",
    scope={"systems": ["笔记","代码仓库","问题清单","练习集"]},
    checks={"definition_frozen": False, "reconciled": False},
    samples=[],
    owner="学习者",
)
Path("release-evidence.json").write_text(
    json.dumps(manifest, ensure_ascii=False, indent=2),
    encoding="utf-8",
)
print(manifest["decision"])
```
